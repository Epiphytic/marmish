## Outcome

**User scope amendment (2026-11-02):** working Tor command transport is deferred
to v0.3 and does not block v0.2. The required v0.2 live command acceptance route
is direct relays, including the full installed nine-pair platform matrix and its
recovery, authorization, cleanup and performance checks. Existing successful Arti
foundation results remain valid evidence for that narrower scope; they do not
establish working Tor commands. Tor failures must remain visible and must never
trigger direct fallback. This amendment supersedes Tor command gates in the
phase table and earlier detailed designs below.

The installer must be independently downloadable from both Radicle through Iris
and GitHub, with GitHub as the backup in the copy-and-paste bootstrap. Both paths
must serve the same reviewed script and be validated before claiming availability.
An unavailable Iris endpoint must not prevent installation through GitHub.
This is script-source redundancy; individual executable assets and pinned
manifests come from GitHub Releases. It does not promise installation
during a GitHub release-service outage. Existing `--tor` modes remain experimental
for commands in v0.2; onion command execution is not qualified for the release.

Ship native `marmish`, `marmishd` and `marmish-worker` binaries for Linux AMD64, Linux ARM64 and
macOS ARM64. Application, daemon, worker, setup and verified installation are Rust. A small
download bootstrap may invoke the native installer; it must not require Python,
uv, a browser, WASM or a system Rust compiler to install release binaries.
Reviewed CI-only license, provider and qualification helpers may use Python
outside the product runtime PATH. Python is never a native runtime dependency;
the retained legacy fixture remains optional and separate.

Use upstream mainline MDK directly, with no private fork or `wnd` subprocess.
Verify the supported upstream transport API rather than copying deaddrop's
fork-pinned WASM probe. Embed Arti for Tor endpoints. Keep relay selection
explicit, reject unconfigured destinations before connecting, and never fall
back from Tor to direct networking after a failure. The actual upstream pin
and connector contract are recorded in accepted Phase 1 designs and evidence.
Upstream's own pinned OpenMLS/rust-nostr dependencies remain upstream provenance;
the no-fork rule prohibits introducing a Marmish MDK fork, not those dependencies.

Follow deaddrop's native service patterns where useful: one state owner, bounded
work queues, durable accepted work, private identity state and explicit shutdown.
Its relay server is not a command server, and its relay authentication is not
Marmish command authorization. Preserve Apache-2.0 notices and attribution for
copied code. Do not copy its unencrypted storage or feasibility secret snapshots.

## Architecture

One Rust service owns one named Nostr identity, its MDK instance and its persistent
state. It can act as client, server or both. Multiple local CLI invocations use
authenticated local IPC to that owner rather than opening the MLS database
concurrently. Distinct named identities use distinct service/state instances.
Local IPC uses a socket in an owner-only directory and verifies the peer UID
with Linux `SO_PEERCRED` or macOS `getpeereid`. A client CLI may start its identity's
daemon under the profile lock. Persistent server operation uses a foreground
daemon or separately configured service supervision; setup does not install a
login/boot service.

The MDK adapter exposes authenticated group messages, membership and room
operations. A single explicit relay policy is applied to every connection path,
including discovery and retries. Prefer the smallest upstream library interface
and a native connector over embedding an unrelated application stack. Tor
bootstrap, relay delivery and application readiness have separate status and
bounded deadlines. `.onion` names are never handed to system DNS. Ordinary
explicit relays and all-Tor routing remain configurable. The configured default is
`auto`: onion relays use Arti and ordinary relays connect directly. `always`
routes every relay over Arti; `off` refuses onion destinations. No failure changes
the selected route. Mixed onion/ordinary sets in `auto` intentionally permit direct delivery on the
ordinary relays; use `always` for Tor-only delivery. A relay publication succeeds
after at least one configured relay accepts it, with per-relay failures reported.
That is an any-relay receipt, never proof of peer decryption or application receipt.

The command engine owns durable invocation admission, replay prevention, process
launch and output retention. Reuse the existing tested Rust engine, policy and
vault where their contracts fit. Client disconnection does not cancel accepted
commands. Direct argv and binary stdin/stdout/stderr are supported. There is no implicit
remote shell or ShellCommand request mode. An explicitly invoked interpreter
with literal arguments still requires server executable-policy permission. Default and per-key
command restrictions accumulate. Peer identity comes from authenticated MLS
metadata, not fields asserted inside a payload.

Keep SQLCipher for secret-bearing databases, named keychain entries on macOS and
Linux, and explicit file-backed operation for headless hosts. Do not silently
downgrade an already configured keychain after provider errors. Fresh sessions
create independent MLS groups; resumed sessions retain their correct MLS state.
Application messages default to one day of retention, selected at daemon
startup with `--retention-seconds`. Command payload/output retention is separate:
`limits.payload_retention` defaults to 86400 seconds. Engine tombstones are fixed
at 172800 seconds; the command replay horizon is seven days. Content expiry does
not cancel work or discard necessary MLS/replay state. Ordinary DM text never grants execution.

No namespace, Bubblewrap, privileged broker or macOS sandbox is a prerequisite
for v0.2. Optional OS confinement is defence in depth and does not supply relay
authorization. The design does not claim to sandbox commands intentionally
authorized to run as the local Unix user.

Ordinary commands reuse a default authenticated room. `--new-session` creates
an independent MLS group with durable preparation binding, preserved across
retries. Profiles have 64 active command-room slots, 4096 lifetime room metadata
rows and 4096 durable creation markers, with finite refusal/uncertainty and no
public room-retirement command. Handles identify invocations separately.

## Compatibility and scope

The user explicitly authorized breaking v0.2 wire compatibility. The approved
Phase 2 protocol is `marmish-command/1`; legacy `marmish/1` envelopes are reference
material, not a conformance or release gate. Native Rust↔Rust byte/exit/authentication
vectors and actual command flows remain required. Optional legacy/upstream
key-package, Welcome or authenticated-content comparisons must distinguish envelope
conformance from MLS compatibility and report incompatible or unverified prerequisites
honestly. Do not introduce an MDK fork, production legacy-profile flag or synthesized
authentication to force interoperability. Retaining the fixture makes no Rust↔Python
compatibility claim.
Retain the Python implementation and its pinned legacy dependencies as an
optional, isolated interoperability fixture. Do not make v0.2 depend on the old
daemon RPC, broker, Python storage layout or MDK fork. Wire compatibility and
in-place state migration are separate claims; migration requires its own tested
design. The user explicitly permits breaking on-disk compatibility because there
is no installed base. Use fresh v0.2 profile/database/reference formats; no legacy
migration is required. Never open a legacy MLS database with the new implementation.

Native acceptance uses concurrent hosted `ubuntu-24.04`, `ubuntu-24.04-arm` and
`macos-15` jobs. Each holds a bounded server while the other jobs run clients;
the nine directed pairs are the Cartesian product of Linux AMD64, Linux ARM64
and macOS ARM64 as client and server, including each same-platform pair. Phase 1
requires direct and Arti message exchange/restart on each platform. Phase 2
requires same-platform direct command flows; Phase 3 requires native installation
on each; Phase 4 adds the full nine-pair direct matrix. The previously planned
Arti command matrix is deferred to v0.3. Client and server
must remain simultaneously live: v1's short-lived challenges and tokens rule out
serialized cross-job staging. The serialized laptop pool is supplementary only.

Preflight hosted concurrency, explicit test-relay reachability and Tor bootstrap
egress before committing to live gates. An explicit onion relay must be reachable;
provision a bounded test relay if none is available. Network/concurrency failures
remain failed acceptance, not successful skips. Notify the user if jobs have not
started within five minutes. The optional legacy fixture runs on the local Linux
AMD64 host only after its existing namespace preflight succeeds; other legacy
platform cells are unverified unless their prerequisites actually pass. Those
legacy-only prerequisites never enter native runtime/install/build requirements
and do not block native Rust platform acceptance. Build/install checks and live
command evidence remain distinct. No runner privilege escalation is required.

The source tree retains legacy Python/tools/patches for reference and an optional
fixture pinned to `3edf7ae7003ebd0b9075e3453cb17b79475eba63`. New default build and
release jobs select native Rust targets and never bootstrap legacy wnd. Existing
Rust engine/vault crates may remain shared; the root SQLCipher patch must stay
coherent with upstream MDK. Upstream git-only, `publish=false` dependencies mean
source builds are separate from the verified binary installer. Do not claim
crates.io publication or a tested standalone Cargo install without independent
evidence. Keep Rust 1.97 as the initial minimum toolchain.

Release version is `0.2.0`, with reviewed prereleases under `v0.2.0-rc.N` if needed,
distinct from all v0.1 experimentals. macOS executables are ad-hoc signed unless real
signing credentials are available; document quarantine/notarization limitations
and test actual downloaded installation instead of claiming notarization.
Source is published to GitHub and Radicle; individual executable assets and their
manifest are published through GitHub Releases. Native keychain-provider results are reported
separately from explicit file-backend flows; full real-provider qualification
remains pending for the initial release.

Preserve the original destination form `marmish npub@relay`, aliases, explicit
relay sets and asynchronous noninteractive commands. Interactive PTY/tmux,
takeover/readers, multi-device conformance, privileged Unix-user mapping, X11,
forwarding and file transfer remain separately scoped follow-ups. No unsupported
capability is advertised in v0.2.

Publish sanitized JSON and Markdown for real measurements: cold session setup,
command wall time, first output, drain time and verified bytes per second.
Identify source, platform pair, route (direct/Tor), payload, samples and Arti
cold/warm bootstrap state, with bootstrap duration as a separate stage. Failed
or unverified cells have null metrics and zero samples. Do not infer one-way
latency or percentiles from single observations. Legacy measurements stay labelled
as legacy, not as v0.2 performance.
