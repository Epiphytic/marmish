I checked the uncommitted working-tree code the amendment depends on. Auto-exit is checked at the top of every daemon loop iteration (`daemon.rs:226`) and does not look at the cleanup state. The check uses the durable ledger counts from `command_admission_budget()`, not a per-launch counter. A count exit and an uptime exit leave through the same `break`, both with exit 0. `CommandCleanupStatus`, `CommandLocalCancel` and `CommandPrepareCleanup` exist in `command_local.rs:110-132`.

## Blockers

**B1. The ceiling fix only covers the matrix.** The base Phase 4 table still runs several protected-cleanup cohorts with a ceiling equal to their planned admissions:
- benchmark: `max-commands 4` with exactly 4 admissions
- recovery: `max-commands 2`
- policy: up to 1 admitted baseline

Once every admitted command in those cohorts Finishes, the predicate `admitted>=N ∧ reserved==0 ∧ finished==admitted` becomes true. The daemon then exits before or during prepare and drops CleanupGuard. That is the same failure the amendment fixes for the matrix. The fix needs a general rule: every protected-cleanup cohort sets its ceiling to planned admissions + 1, and any admission beyond the plan fails the rollup. Zero-grant should say it runs without `max-commands`, which is rejected when the grant set is empty.

**B2. The base recovery restart rule now breaks.** Base Phase 4 lines 181-184 restart the daemon with "only planned admissions still remaining", or with admission closed. Under the durable budget, `N = remaining` is compared against the lifetime admitted total. That closes admission too early. If every admitted command has Finished, `N = admitted` makes the restarted daemon exit on its first loop iteration, before any status, poll or prepare. The amendment must replace this rule: restart with the same total ceiling (planned + 1), and never reduce it.

**B3. The auto-exit cohort is not scheduled and leaves too much open:**
- **Topology:** it doesn't say whether this is a concurrent cross-platform wave using the three platform clients, or three local client profiles on each runner.
- **Budget:** it has no wave slot or caps (launch-to-ready, workload, auto-exit deadline, cleanup-instance launch/activation, removal) checked against the 55-minute job. The 150-second activation clamp also applies to the cleanup instance.
- **Proving auto-exit:** the code gives no distinct exit signal. The design must require exit 0 with no supervisor Stop sent and well before `L+U`. Otherwise an uptime exit could pass.
- **Cleanup:** "If removing that cohort's engine state" makes cleanup optional, but the base design requires cleanup records for every cohort. Either require it or define an explicit preserved-state disposition.
- **Admission window:** the cleanup instance has admission open while grants remain, until prepare. It needs its own bounded uptime, a feasibility check before launch, and a full-ledger check for unexpected admissions at the fence.

**B4. The installer qualification order is impossible as written.** Lines 34-36 run HTTPS qualification "through both public script URLs" as part of the first installed qualification. Lines 92-94 only make both URLs select v0.2 after that. Under `phase3-release-entrypoints` (lines 35-38), the mirrors' `scripts/install.sh` serves the native bootstrap only after acceptance passes, so the public URLs cannot yet install v0.2. The amendment needs an explicit sequence:
1. Matrix run using the local asset directory.
2. Publish immutable assets.
3. Commit the generated pinned script to both mirrors.
4. HTTPS install on all three platforms, with a byte-identity check between the two scripts.
5. README/quickstart cutover.

It also needs a rollback if the HTTPS step fails, and a statement that the published version string is exactly the qualified one. A qualified `-rc.N` cannot be relabelled 0.2.0 without a rebuild and requalification.

## Nonblockers
1. **List the superseded base clauses explicitly:**
   - the Arti cells and T-waves (lines 22-33, 120-136)
   - the onion owner and the Phase 1 Arti predecessor (lines 191-201)
   - `--max-commands 3` and closing admission at the expected count (lines 241-250)
   - the "9+5" rollup (line 335)
   - the ~600-minute scheduling budget

   Tor results should go in a separate, non-gating job or report.
2. **Ceiling 4 detects an extra admission but doesn't prevent it.** If a 4th admission happens and Finishes, auto-exit fires and drops the guard. Say that this is red with state preserved, and that the rollup reads the complete evidence ledger by cursor.
3. **Say whether the matrix requires Finish.** The current evidence schema has no `finished` field, and the budget isn't exposed over IPC. Either state that the auto-exit cohort alone covers Finish, or propose a reviewed evidence field.
4. **Define where the run nonce comes from.** It should be generated once, for example in the resolve job and pinned in the candidate tuple, alongside the existing per-role nonces.
5. **Client terminal artifacts must not wait for the Finish acknowledgement.** Per server-limits, a Finish acknowledgement timeout is only a diagnostic. Late Finish or Busy-Poll traffic after draining gets `server_draining`.
6. **Possible product hardening, for later review:** suppress count exit once cleanup is no longer `Open`. Today only the harness ceilings keep the predicate from firing during Draining/Quiesced.
7. **Setup ordering:** grants must be updated before the server daemon launches. Setup fails while a daemon holds the lease, and `max_commands` is rejected with an empty grant set. That ordering has to fit the 10-15 minute identity barrier.
8. **Doc status:** the `phase3-release-entrypoints` header still says "approval pending", although `docs/reviews/v0.2-phase3-entrypoints-design-r2.md` records APPROVED.

- No new cancellation on expiry or disconnect.

`★ Insight ─────────────────────────────────────`
- The admission budget is stored durably in the profile's ledger, not counted per process. So any restart rule phrased as "remaining credit" turns into an exit trigger once every admitted command has Finished. That's why B2 is a blocker, not a wording issue.
- Count exit and protected cleanup conflict whenever the ceiling equals the planned admissions. "Ceiling = planned + 1, extra admission fails" keeps auto-exit from firing during cleanup, and B1 applies it to every cohort.
