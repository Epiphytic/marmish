**Contract checks that hold**
- **Rust grammar:** `stable_version` (`installed_version_lifecycle.rs:7`) wraps `native_manifest::version`, which already enforces `0.2.` plus a decimal parsed as `u64` with no leading zeros. It then excludes anything containing `-`. That rejects `-rc`, `+build`, a trailing newline, other major/minor versions, and a patch above u64 or longer than 20 digits. The 43-byte cap is redundant but harmless.
- **Rust derivation:** A and C are checked against `format!("{B}-rc.N")`, so a swapped or relabelled A/C fails. `LifecycleContext::validate` and `Variants::validate` both apply the stable check.
- **Untouched controls:** no changes to the provenance, source/run/attempt, signing, inode or journal controls. C still requires format 4 and the candidate format still has to be above 4 (`require(formats[1] > 4, …)` in `build()`).
- **Builder:** `candidate_version` requires exactly one `[package] marmish-native` declaration and exactly one matching `Cargo.lock` entry. It validates through `checks.version_value`, which caps the patch at 20 digits and u64, and rejects `-`. `patch_sources` keeps the closed exact-text replacement.
- **Builder order:** `build()` now runs `prepare()` (toolchain, source and clone checks, version derivation), then `verify_assets` for B against the derived version and SOURCE commit, then `cargo fetch`, then the patch directory. `verify_assets` checks both manifest version and commit. No deadlines changed.
- **Builder naming:** the license path, A/C asset names, release-info checks and inventory all use the derived versions. No workflow inputs or result schema fields were added.
- **Provider triplet:** `lifecycle_arguments` requires A assets, A pin and B version all present or all absent, and validates both the pin and the B grammar. `main` calls it before any account operation. Ordinary mode is unchanged because B is only used when A assets are present.
- **Provider forwarding:** B is forwarded through the Rust adapter (`--lifecycle-b-version`, always alongside the other two) and through the macOS outer-to-inner argv. It is used for the A binary glob, the B and A release-info checks, `select()`, and `staged_provider_inputs` names.
- **Error label:** a subprocess test asserts the real outer report label `qualification_prerequisite_failed`.
- **Scope:** no `Cargo.toml`, `Cargo.lock`, workflow, script or pin changes.
- **Docs:** the amendment, the table in the original lifecycle design and the `docs/agent-spec.md` note are consistent. They claim only offline tooling, with hosted qualification still pending.

**Nonblockers**
1. **Rust provider test:** `provider_forwards_exact_validated_candidate_version` tests only the `version_argument` helper. It does not check B's position in the real `run()` argv. The Python subprocess test covers the receiving end.
2. **Rust `Variants::load` test:** `variants_load_checks_real_manifest_formats_patch_and_outer_pins` (around line 311) still uses only `0.2.0`. The new `stable_patch_versions_require_exact_derived_variants` test covers `validate` for 0.2.1, 0.2.12 and u64 max, but nothing exercises `load` with a patch version above 0.
3. **Builder ordering:** no Python test asserts that B verification happens before `cargo fetch`, or that a wrong B manifest stops the build before the fetch. The ordering is correct in `build()`, and `verify_assets` has the wrong-version and wrong-commit negative test.
4. **Redundant check:** the `stable_version` call inside `Variants::validate` repeats the one in `ctx.validate()`.
5. **Builder labels:** `candidate_version` can raise `invalid_version` (from `checks.version_value`) as well as `variant_version_patch`. Both are existing finite labels.
