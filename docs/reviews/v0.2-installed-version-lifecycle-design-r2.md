## Remaining blockers

**B1 — The sidecar prerequisite only covers the journal.**
- The preflight opens the **MDK** database first (`native_preflight.rs:68`), with the same read‑only flags and no `readonly_shm`.
- MDK storage also runs in WAL mode (pinned `mdk 8abc51b` `storage-sqlite/src/shared.rs:195`).
- C rejects at the journal step (L99‑101), so the engine database is never opened.
- **Fix:** the offline test must use real state for both databases (MDK created through the real owner path, journal through `Journal::open`), close them cleanly, run the real `check()`, and record the sidecar inventory per database. Otherwise a journal‑only test can't tell whether a production fix is needed.

**B2 — The macOS qualification stages don't fit together as written.**
- The lifecycle context is 1800s: 1500s of qualification plus 300s of cleanup.
- At submission, the fixture needs 900s + 300s = 1200s left (L195‑198).
- The provider stage can take up to 540s plus its own cleanup, and steps 1, 5 and 6 also need time.
- If the provider stage runs before the fixture, only about 60s is left for install, setup and daemon start, which isn't feasible.
- **Fix:** state the order (provider stage after step 6 is the sensible choice). Give each stage an entry minimum, and pass the provider supervisor `min(540, remaining − provider cleanup)`. Say whether the fixture's 300s "protected cleanup" is the same reserve as the 5‑minute cleanup reserve or an additional one. A stage refused for lack of time is red.

**B3 — The provider input cap of "at most 10 files" is wrong.**
- The real set is 11 files: A and B's three binaries each (6), two manifests (2), the B bootstrap (1), and **two** license files (2).
- A's native install checks versioned file names, so it needs its own `THIRD-PARTY-LICENSES-0.2.0-rc.1-<target>`.
- Because the design says to reject anything over the bound, an implementation that follows it would refuse a legitimate input.
- **Fix:** list the exact 11‑file set, which is still under the supervisor's limit of 16.

## Nonblockers

- **Supervisor provenance:** the provider supervisor is `tools/marmish_native_keychain_check.py`, which is outside the `tools/v02-actions` digest set (`v02-release.yml:152-153`). Name it explicitly in the bound and recorded inputs.
- **Dispatch ref:** `github.sha == SOURCE` needs a dispatch ref that points exactly at SOURCE, because master moves on. Say how this is done without A/C tags.
- **Bootstrap utilities:** the bootstrap checks for `curl` (and `awk`, `sha256sum` or `shasum`, etc.) even with `--asset-dir` (L41). The utility‑only PATH must include them.
- **Stopping A after the switch:** after step 3 the launchers point to B. Say that A is stopped through its retained process handle or A's own versioned binaries, not B's command line, unless compatibility between B's command line and A's daemon is shown.
- **Cargo dependency sources:** "reuse the verified B job inputs" is unclear, because another run's Cargo registry isn't transferable. Say `cargo fetch --locked` inside the lifecycle job.
- **Undefined term:** "original uptime deadline" (L161) should say which deadline it means.
- **Candidate artifact retention:** the lifecycle run should refuse to start if the candidate's artifacts may expire before it finishes.
- **Build budget:** there are 752 locked packages including `arti-client`, and no release LTO. One cold release build (A) plus one incremental build (C, which only rebuilds `marmish-native`) within 45 minutes is realistic. Linux ARM64 is the riskiest target, so record per‑variant build times.
- **macOS rollup:** with the expected ad‑hoc keychain denial, the macOS record can't be complete, so the rollup stays red. That is consistent with L232‑234, but say it directly in the rollup section.

## Your added requirements

All of these are met:
- **Variant commits:** A and C are genuine isolated local commits whose actual variant commit is embedded. `build.rs:25` honours the override, and `native_layout.rs:53` checks commit consistency per version. SOURCE is never presented as the modified source.
- **B and harness:** B and the harness stay immutable.
- **macOS keychain:**
  - An ad‑hoc keychain‑access denial is reported as a failed or unqualified unattended upgrade.
  - No keychain ACL changes are authorized.
  - Reauthorization is never assumed to succeed.
  - Initial qualification is kept separate from the upgrade.
- **Sidecar criterion:** the stronger criterion needs the offline WAL test and a separately reviewed fix, the main‑database result is reported separately, and failures are not accepted silently.
- **Journal format:** F is derived from the manifest and release‑info and proven by a successful open, so a move from 5 to 6 is handled.
- **Planning only:** the document is planning only and authorizes no implementation.
