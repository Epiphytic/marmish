## Blocking finding

**F1: The regular-file check in `.github/workflows/v02-release.yml:91-92` can never fail.**

```bash
read -r mode kind object rest <<< "$(git ls-tree "$MARMISH_BUILD_COMMIT" -- "$changed")"
test "$mode" = 100644 && test "$kind" = blob
```

Under `set -e`, bash ignores a failing command in an `&&` list unless it is the last one. So when the first `test` fails, the shell keeps going. The `while` loop then returns non-zero only because of a failure that `-e` was already ignoring, and bash does not exit on that either. The step passes.

I checked this offline with a small bash 5.2 script that feeds this exact construct a `120000` (symlink) entry. Whether the symlink came first or last, execution reached the line after the loop and the exit code was 0. The macOS runner's bash 3.2 handles errexit the same way.

As a result, an allowlisted path that is deleted, a symlink, an executable (`100755`) or a submodule (`160000`) is not rejected. That misses r2 condition 2 and the amendment's "regular100644 blob" rule. Also, if `git ls-tree` itself fails inside the here-string, the error is swallowed.

The fix is to make each check fail on its own and to run `git ls-tree` outside the here-string. For example:

```bash
entry=$(git ls-tree "$MARMISH_BUILD_COMMIT" -- "$changed")
case "$entry" in
  "100644 blob "*) ;;
  *) echo 'caveated release: changed path is not a regular file' >&2; exit 1 ;;
esac
```

(Equivalently: `[ "$mode" = 100644 ] || exit 1; [ "$kind" = blob ] || exit 1`.)

Today's diff from 347 to the worktree touches only the workflow, and that file is a regular `100644` file, so nothing is being exploited right now. But the guard is supposed to enforce this on its own, and it doesn't. The fix changes the workflow blob, so the code-review record needs the new blob ID, and root must compare `SOURCE:.github/workflows/v02-release.yml` against that new ID before dispatch.
