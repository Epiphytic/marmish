## Feasibility, security and acceptance boundaries

- **Feasibility:** the timing and API-call numbers add up. The doc correctly makes the first hosted run responsible for proving that artifacts can be exchanged mid-run, instead of assuming it.
- **Security:** dispatch inputs are handled safely. Tokens are limited to the supervisor (supervisor doc lines 29 and 65), and the product runs with a curated environment. The trust root is master-branch workflow code plus the checks on `manifest.commit` and the tooling records. That root is stated explicitly, which is acceptable.
- **Acceptance boundaries:** this qualifies the matrix only. Auto-exit, benchmark, recovery, policy, keychain, asset publication and HTTPS stay pending, and `scripts/install.sh` doesn't change until the controlled cutover.

## Non-blocking notes for the code review

1. **Expiry validator is looser than the design.** `installed_records.rs:66` still accepts up to 2400 s (40 min) between creation and expiry. Tighten it to 2220 s (37 min) so the code enforces the internal-deadline arithmetic.
2. **Say what the tooling record's `harness_sha256` must equal.** Line 23 introduces the field, but the doc never says it must equal the context's tooling-source digest and the checked-out tree digest. Add that check explicitly.
3. **Clock skew in the identity barrier.** `created_at` is stamped on the resolve runner and `identity_ready_at` on each matrix runner. Either state a small skew tolerance or say explicitly that there is none.
4. **Concurrency queue behaviour.** With `cancel-in-progress: false`, a newly queued run still replaces an already-pending one. That fails closed, but it's worth a sentence.
5. **Operational friction.** `source == github.sha` means any later commit to master, including review documents, invalidates the candidate. The candidate build and the installed run need to happen back-to-back.
6. **Name the rollup tool.** The tooling record lists exactly two binaries, so the doc should say that rollup is a subcommand of `marmish-installed-check`.
7. **Editorial.** Lines 11, 14, 38, 43 and 52 are run-on, overlong lines that should be reflowed.

The remaining gates are the code review of the driver additions in progress, actionlint, the offline tests, and the first hosted run proving artifact exchange on all three platforms.
