## Amendment: APPROVED

**A1 (read-only presence path): resolved.**
- Lines 81-87 now name the path: `owner(ctx)` (with `check_uid`), then `job_for`, `job_state`, `worker_identity`, then `root.presence`.
- It explicitly forbids `authorized_job`, `reconcile_step`, `recover_absent` and storage writes.
- The result mapping matches `launcher.rs:598-623`.
- An Accepted job with a missing directory counts as Absent but never as exited, and that case has a test (line 232).

**A2 (consuming cleanup lifecycle): resolved.**
- **Failure:** the document now says plainly that `into_cleanup` consumes the engine even on error. A failure is terminal for that daemon instance: no reopen, a finite `server_draining`/unavailable reply for engine-dependent calls, ordinary stop only, and no deletion.
- **Lifecycle:** cleanup moves `open → draining → quiesced | failed` and never returns to open.
- **Preconditions:** the harness requires active, uncertain, worker_running and worker_unknown all zero and `observation_pending=false`, and the actor rechecks them.
- **Uptime:** expiry or a stop during draining or quiesced loses the proof, and cleanup time is reserved inside the original uptime.
- **UnknownLaunch/Lost:** described accurately. They disqualify the run, cleanup still requires every job to be Exited, and no wrapper may rewrite those states.

**A3 (evidence freshness at quiescence): resolved.**
- **Fence:** `final_seq` is allocated and committed before the refresh. Every included row then gets a status read and a raw-presence check, both committed through CommitAck with `observed_seq ≥ final_seq`, before the engine is consumed.
- **Fence semantics:** the document notes that the fence is not the maximum sequence at the end of the pass.
- **Invalidation:** an invalidation after the fence voids the proof, even after quiescence.
- **Supervisor check:** the same-socket status reply after removal must show the same `final_seq`.

**Bounds: sound.**
- Each row is capped at 4096 bytes, and the error detail at 1024 JSON-encoded bytes.
- A page is cut at row boundaries to fit the 64 KiB frame (at worst about 15 rows) and returns its last included cursor.
- Truncation is forbidden, and there is a worst-case vector.
- Two r2 items are fixed: `--max-commands` without `--max-uptime` is now rejected, and a definitive refusal releases its credit immediately.

**Non-blockers** (fold in at implementation handoff):
1. **The final refresh should not use the reconciling status call.** Lines 103-104 say "authoritative engine-thread status". In the source that is `Engine::status`, which goes through `authorized_job` → `reconcile_step` → `start_accepted`, so it can launch an Accepted job during draining.
   - Not a blocker: local cancel turns Accepted jobs into Exited/NotStarted at once (`store.rs:1281-1297`), and the preconditions exclude active rows, so this only matters if the actor's cache is wrong.
   - **Fix:** do a read-only `job_state` check first. Any state other than Exited makes prepare fail before consumption instead of reconciling. Otherwise use a read-only status (owner → `job_for` → `store.status`).
2. **Define "included rows"** as every server ledger row in the profile, not just the expected ones. That way an unexpected admission is also refreshed under the fence and is visible to Phase 4's "no unexpected admission" check.
3. `engine_quiesced` duplicates `cleanup=="quiesced"`. Keep one, or state that they always agree.

## Phase 4: APPROVED

**P1 (launch-relative deadlines): resolved.**
- At launch the harness freezes `L` and `U = min(30m, remaining)`.
- Deadlines: clients `L+U−6m`, prepare `L+U−5m`, removal plus renewed liveness proof `L+U−1m`, then one minute for stop/reap.
- If readiness leaves less than 20 minutes for clients, the cohort fails before any client is admitted.
- The fixed 45..50 cleanup window is explicitly superseded.
- **Arithmetic:** for `L=20`, `U=30`, clients end at 44, prepare starts by 45, removal ends by 49, and stop/reap by 50. That fits the 55-minute job, and the Arti owner's lifetime of minute 50 plus 5 minutes.

**Ordering: resolved.**
- Lines 315-319 now run local cancel first, then polling, then prepare. Ordinary stop comes last and is explicitly not allowed first.
- Lines 260-261 prepare cleanup only on the final instance after the restart test.
- The fixture is re-hashed before launch and before cleanup.

**Qualification feasibility:** handled safely, though not yet shown to fit. Each profile has its own frozen U with the same 6m/5m/1m reservations, a feasibility check before launch, and an offline validator.

**Non-blockers:**
1. **Publish a qualification budget table.** Per platform, qualification runs a benchmark, detach/restart and zero-grant profiles plus forbidden-path/digest-conflict negatives. That is 3–4 profiles in the 15..50 window (35 minutes). At an assumed ~5 minutes per workload plus a 6-minute reserve, profiles cost about 11 minutes each, and the 6-minute reserves alone take 18–24 minutes. The design fails closed, but it could end up never able to pass, and T-qualification also needs Arti bootstrap time per profile. Before implementation, either:
   - give per-workload caps whose sum, reserves included, is at most 35 minutes, or
   - combine the negative tests into one profile, or
   - split qualification into a further wave.
2. **Readiness window.** With `U=30`, a server must be ready within `L+4m`. Arti readiness timing is still unproven given Phase 1 run 41569702092, so record actual readiness times and make missing the window a named failure stage.
3. **Remote clients can't see a server's deadline.** Clients on other machines can't use that server's monotonic clock. ServerReady should carry the client deadline as a wall-clock time with a 120-second skew allowance, so a client doesn't start a pair that can't finish. Missing the deadline would still be red, not unsafe.

`★ Insight ─────────────────────────────────────`
- **Fence before refresh:** taking the observation fence before the final refresh means every row refreshed in that pass counts. Using the maximum sequence at the end would wrongly exclude rows refreshed early in the same pass.
- **Liveness proof:** a zombie daemon has already dropped its flocks. That's why the supervisor's check pairs `waitpid(WNOHANG)` with a same-socket reply showing the same fence, rather than trusting that the process was spawned.
- **Status isn't a read:** the one remaining hazard is the same class as A1. In this engine "status" is a reconciling operation, so every new "read" path has to say which internal path it uses.
