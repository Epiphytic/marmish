## Blockers

**B1. The probe's first setup is always rejected, so the cohort can never pass.**
- `installed_policy.rs:383-396`: `setup()` rejects any report with `s.owner_opened`. The first probe call is a fresh `--role client --no-grants` that creates a new identity, so it expects `identity_created == true`.
- In the product, creating an identity always opens the owner. When the profile isn't ready yet, `native_setup.rs:339-391` runs `MdkOwner::open` and reports `owner_opened: opened = true`. The product's own test asserts `identity_created && owner_opened` on first setup (`native_setup.rs:474`), and `installed_prepare.rs:194` requires `owner_opened` for the same kind of setup.
- **Result:** `zero_grant` fails at its first step on every platform.
- **Fix:** require `s.owner_opened == fresh`, matching the `identity_created` check. Add an offline test of the setup-report predicate for all four calls: probe create, probe trust, server grant and client trust.

**B2. The failure-path cancel can never run when it's needed.**
- The design says failure cleanup uses `cancel_policy_execution` to cancel "the sole possibly executed invocation using its exact known key". The framing doc also says known handles are kept through a failed wait.
- In the code, `state.expected` is set only after `executed_case` returns `Ok` (`installed_policy.rs:1304`). `close()` runs cancel and the guard only when `expected.len() == 5` (`:719-730`).
- So when the real risk occurs (the wait times out or is interrupted, the output is wrong, or the conflict check fails), the expected rows are still empty. The known handle and its group digest (fetched at `:1087`) are thrown away, nothing is cancelled, and the server just gets an ordinary stop.
- The only failures that do reach the cancel are the probe-session check and the receipt inventory (`:1305-1332`). By then the attached wait has already returned exit 7, so there is nothing left to cancel.
- It is still safe against deletion: the engine is preserved and the run is red.
- **Fix:** before the wait, record the four denial keys plus the executed key (invocation, session, and the group digest as soon as it's known) in `Runtime`. Then call `cancel_policy_execution` whenever a failure occurs after the submit is known to be admitted. `prepare_policy` will still correctly refuse removal for a cancelled row, which is not Exited/7.

## Checked and found correct
- **Budgets:**
  - Minimums are checked at the right points: 2400 s before extra setup, 2100 s before the first daemon, 1500 s before the granted server.
  - Phase slices are 300 / 150 / 45 / 120 (proof 60 s) / 300 / 150 / 600 / 300 (proof 240 s) / 60.
  - All are capped by `global = expiry − 300`, so the 300 s publication reserve can't be borrowed.
  - `--max-uptime` is capped at 1800 s and by the remaining budget. The probe uses `--wait-seconds 20`.
- **Zero-grant phase:**
  - It uses a separate `client-probe` identity, and the server config is checked to have `execution_clients == []`. No EngineTree is created and no `--max-commands` is passed.
  - `require_no_engine` and the held profile receipts are checked before launch, around each proof and after the stop.
  - The probe's server evidence is read through the PID-bound, paginated `verify_no_engine`. The probe gets no fixture receipt and the receipt inventory catches strays.
  - The CLI result is recorded only as an unconfirmed, closed-set diagnostic. The probe's sessions must differ from every granted-phase session.
- **Config edit:** the policy shape matches the design exactly. The roles, grants, trusts, relays, tor-off setting and aliases are checked before the edit and preserved. `setup` stores principals as hex (`update_set`), so comparing against the hex account is correct.
- **Denials:**
  - `CommandDenied` with `detail: None` matches the product at `command_service.rs:248-258`.
  - The response's binding, ID, op, rebuilt request digest and SHA/base64 round-trip are all checked. The group digest is read before the response is consumed.
- **Lost-reply retry:** the request is written, the socket is shut down without reading the reply, then the listing is polled for exactly one entry before the same-ID retry. The retry must return the same handle with still exactly one entry.
- **Wait and local conflict:** the public CLI wait has no relays and checks exact bytes and the receipt. The changed-bytes submit with a fresh request ID must fail with `command_handle_binding` / `handle: None`, and the client must still have exactly five rows afterwards.
- **Refused-row reader:**
  - `Some(0)` / `CommandDenied` / outcome `None` / worker `Unknown` / zero, open, hashless streams match the product's `CommandEvidence` construction (`command_store.rs:3570`) and its stream projection (`:3499-3512`).
  - The freshness rule (`observed_seq ≥ fence`) matches the actor's `command_cleanup_fresh`.
  - Executed rows are unchanged, and the new `refusal` field must be `None` on them. The required-nullable fields and the cap of five rows with one executable are enforced.
- **Cleanup and stops:**
  - `prepare_policy` hands the existing guard an exact set of five rows.
  - Dropping an `EngineTree` doesn't delete anything.
  - `remove_private_workspace` runs only after a completed close with receipts verified and no signal, and it checks `require_no_engine` for all three profiles first.
  - Stops on uncertainty are ordinary stops. Every helper is joined, and the final emergency stop includes the inherited 5 s force-reap.

## Nonblockers
1. Failed records can be lost. `run` ends with `validate_record(...)?`, so a genuine failure that leaves cases inconsistent (mixed sessions across denials, or a probe-session overlap caught at `:1306`) returns `Err` instead of the closed failed record. That's unlikely, but it goes against "failed report preserved".
2. `Failure::Output` and `Failure::Conflict` are never set; the whole executed case is labelled `Retry`.
3. In `executed_case`, `client_group_submit(...)?` at `:1087-1088` can hide the real wait error, including a signal interruption.
4. The CLI's `--wait-seconds 180` equals its 180 s process slice, so a slow startup could hit the harness kill. 170 s would leave headroom.
5. `config_value` overwrites `limits` without first checking it is `{}`. The design's "revalidate config digest before launch" is done only as a read-back after writing, not re-read just before launch.
6. The probe listing records only sessions that have invocation rows. A room that never got an invocation isn't recorded, but the granted client is a different identity anyway.
7. The automatic Finish disposition after a denial isn't recorded (design §Additive).
8. There are no offline tests of the `run` / `close` lifecycle, the failure-cleanup branches, or the setup-report predicates. Such a test would have caught B1.
