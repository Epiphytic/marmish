# Explicit Keychain authorization design review r1

Reviewer: Claude Code, claude-sonnet-5-5, --permission-mode auto. Session: 9860c3e4-daff-4cb7-993b-c210efe088f0

Reviewed design SHA256: a8f9bf4d639026529b042e90679555793133d6685bb967321625a9b282d6d8b8. No builds/provider calls/source edits.

## Verdict: CHANGES_REQUIRED

The design is sound in direction. Four blockers remain, none needing a redesign. Findings are from reading the source only; I made no edits and ran no builds or providers.

## Blocking findings

**B1. Cancellation has no mechanism in the current code, and the verification budget can be starved.**
- `helper_exchange` (`identity.rs:726`) takes only `(path, request, deadline)`. It has no cancel input and returns only bytes, discarding the `ExitStatus`. The design's "verify child status and payload agreement" and "nonzero cannot be success" therefore need a signature change, not just a new caller. Existing tests call it directly with three arguments, so ordinary callers must keep that shape.
- The frontend installs no synchronous signal handling. The only signal use is tokio's SIGTERM handler in `daemon.rs:238`.
- The design must say how a handler is installed before the first spawn, how the 2 ms poll loop checks it, and which signals are covered. It should name SIGINT, SIGTERM and SIGHUP, and say the handler only sets an atomic flag. It should also say the helper stays in the foreground process group so Ctrl-C reaches it, with no `setsid`, and that kill-then-wait still runs on the cancel path.
- Hard-killing the frontend (SIGKILL) orphans the helper until its 120 s watchdog. Document that limit.
- A single 120 s deadline covers both helpers. A user who takes 119 s on the dialog leaves the verification process about 1 s, including cold macOS exec. A genuine success then reports as a timeout. Reserve a verification slice (for example, interactive phase ends at T0+105 s and verify gets 15 s). Alternatively, state a 120 s interactive window plus a fixed 15 s verify, so the hard maximum is 135 s.
- Map helper exit 124 (watchdog) to the timeout category rather than `keychain_failed`.

**B2. The UI-policy path conflicts with `Provider`/`UiLease` as written.**
- `Provider` holds a mandatory `_ui: UiLease` (`macos.rs:77`), acquired in both constructors. Its guard drop calls `SecKeychainSetUserInteractionAllowed(1)` unconditionally (security-framework `keychain.rs:248`), and `UI_STATE` is process-global. The design's "record previous, enable, restore" does not say how this coexists with that lease.
- The design must specify one of two approaches. One is a dedicated constructor with no lease (for example, `_ui: Option<UiLease>`). The other is a strict ordering of enable, reads and restore around the lease's lifetime.
- In either case it needs a checked `Set` result, a restore guard that fails the process nonzero if restoration fails, and a test that the ordinary constructor still disables UI.
- The `security-framework` crate only exposes disable and get. `security-framework-sys-2.17.0` already declares `SecKeychainSetUserInteractionAllowed` and `SecKeychainGetUserInteractionAllowed`, but it is only a transitive dependency. A local `extern` block is the right call, since the design forbids dependency changes.
- Add the requirement that `run_authorization` is the sole caller. Hidden entrypoints are invocable by any same-user process, and the helper cannot prove foreground status itself (stdin is a pipe). That is acceptable but should be stated.

**B3. The global-argument rejection list is incomplete and its detection is unspecified.**
- `Args` has many globals: `socket`, `tor`, `relay`, `key_storage`, `allow_peer`, `retention_seconds`, `user`, `srv`, `stdin`, `stdin_none`, `detach`, `new_session`, `wait_seconds`, `no_autostart`, `max_commands` and `max_uptime`.
- `key_storage` (default `auto`), `retention_seconds` (default 86400) and `wait_seconds` (default 180) have defaults. "Explicitly supplied" is not detectable from the parsed struct. It needs `ArgMatches::value_source`, or the options changed to `Option`.
- Specify a closed allowlist: only `--debug`, `--state-dir` and `-i`. Reject everything else, and say how that is detected.
- Define "actual marmish frontend" as `!daemon_binary`. A name test would break the standalone `marmish-<ver>-<target>` helper layout, where `layout.helper` is the frontend itself.

**B4. `acquire_existing` must not reuse `private_dir`.**
- `ProfileLease::acquire` calls `private_dir(base)` and `private_dir(&root)`, which `mkdir` (`identity.rs:481`). It also calls `open_private(.., true)` for `owner.lock`.
- The design says "no creation" but not that the existing `private_dir` code must be replaced by `check_dir` only, with `open_private(lock, false)`. Without that, a typo'd `-i` would create state.
- Also require the manifest to be exactly `phase == Ready`, `backend == Keychain` and `format == 2`. Take the refs only after `validate_manifest`, and require a missing manifest to fail with no write.
- Add a test that snapshots the directory tree before and after to prove nothing was created.

## Nonblocking observations
- **Diagnostic feasibility is good, but only on the new path.** `status()` collapses -25308, -25293 and -128 into `LockedOrDenied`, and `probe` returns the same value for the locked bit. Mapping them separately in the new path is feasible. `SecKeychainGetStatus` errors also need the finite mapping, not only the item queries. Ordinary daemon output stays collapsed, so the user's current symptom stays undiagnosed until they run the new command. Say so in the README.
- **Verification proves access, not identity.** The helper loads 32 bytes and drops them, so a later `identity_mismatch` is still possible even after "verified". The helper already has `derive_nostr`, so it could return the public key, which is not secret, for the frontend to compare to the manifest. That would change the `result: {}` schema. If kept as designed, the success message "Keychain access verified" is accurate and should stay narrow.
- Rust's `Instant` on macOS does not advance during system sleep. Note this under the 120 s "monotonic" claim.
- The helper's `RESPONSE_LIMIT` is 131072, while the design says 8192. Use a dedicated 8192 cap for the new encoder.
- Finite failure categories must map to `&'static str` values in `Error::Identity`. Specify the stderr failure format for the new command.
- The new helper entrypoints and the unsupported path must compile and run on Linux. macOS-only code needs `cfg`.
- The existing `tcgetpgrp` check in `native_setup.rs:174` (it opens `/dev/tty`) is a reusable precedent. Use `tcgetpgrp(0)` per the design.
- `harden()` hardcodes the 15 s watchdog. Parameterize it for the 120 s interactive helper.

## Contracts inspected
- **Docs:** `AGENTS.md`, `docs/agent-spec.md` (the credential-helper note at line 446), and the phase doc.
- **`native_layout::resolve`:** `marmish`, `marmishd` and `marmish-worker` all resolve to the sibling `marmish` helper. A downloaded standalone uses itself.
- **`cli.rs`:** `main(daemon_binary)`, the `_vault-helper` pre-Tokio route, the global args, and the `run()` ordering.
- **`identity.rs`:** `ProfileLease::acquire`, `private_dir` and `open_private`, `validate_manifest`, `prepare_with`, the `NativeProvider` response parsing, and `helper_exchange` (nonblocking pipes, kill and wait on error, the oversize guard).
- **`marmish-vault`:** `helper.rs` (closed request enum, `deny_unknown_fields`, `harden`, `run`), `macos.rs` (`UiLease`, `Provider`, `probe`, `query`, `load`, `status`), and the `lib.rs` error categories.
- **`security-framework` 3.7.0:** `keychain.rs` (`disable_user_interaction`, `user_interaction_allowed`, the lock whose drop always sets 1) and `item.rs` search options.
- **`security-framework-sys` 2.17.0:** `SecKeychainSetUserInteractionAllowed`.

I did not verify what the OS actually does with a prompt, an "Allow once" grant, or a SecurityAgent dialog dismissed by process kill. Those belong to the macOS qualification gate. I also did not establish the cause of the user's `locked_or_denied`. Candidates the new categories can distinguish include a disallowed prompt, a differently locked or default Keychain in this session, and a code-identity ACL mismatch.
