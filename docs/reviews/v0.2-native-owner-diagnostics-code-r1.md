## Non-blocking findings
1. **First line after the tail cut (`v02-onion-fixture.sh`, `owner_diagnostics`):** the first, possibly partial, line after `tail -c` isn't dropped explicitly. It's harmless, because a cut line can't produce an exact four-key object, but dropping it would make the intent explicit.
2. **Test gap (`test-v02-owner-diagnostics.sh:63-65`):** the comment says invalid records don't split consecutive duplicates, but the flood vector contains no invalid lines between the duplicates. My own probe confirms the behaviour (`valid, junk, {"x":1}, valid` gives one entry); a test vector should pin it.
3. **Multiple JSON values:** the `events` check uses `jq -e`, which looks only at the last value in a stream. If extraction ever printed several JSON values, `--argjson diagnostics` would fail and, under errexit, `cleanup.json` wouldn't be written. The real filter can't do this, because `reduce` always produces exactly one value. A `jq -s 'length==1'` guard would close it completely.
4. **Validation failure in the workflow:** if `validate` fails, the stop step exits before `cp` and `rm`. Nothing is published, which is the intended fail-closed behaviour, and the private root is left on the ephemeral runner. That's acceptable, but worth knowing when a run shows no `cleanup.json` artifact.
5. **Doubled `--argjson` arguments:** `owner_diagnostics` passes `run`, `attempt` and `sha` to the extract and events modes, which don't use them. It's harmless, since jq requires every `$var` to be defined.
6. **Uncaptured stderr:** raw native and relay stderr remain private and are deleted. The public result is only `fixture_stage` plus the rebuilt pairs, as approved.
