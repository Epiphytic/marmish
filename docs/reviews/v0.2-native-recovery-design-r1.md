# Native foundation recovery-check design review

Actual Claude Code Opus 5.5, session `5022baae-f832-444d-83bf-1048f9f569d1`, `--permission-mode auto`. Recorded before implementation.

**Verdict: CHANGES_REQUIRED.** The direction is sound and I'd expect to approve it after a short revision. Five gaps need to be pinned down before code. No edits, tests, live work, network, keychain, tracker or publish actions were taken.

## Diagnosis is plausible
- `foundation_check::exchange` (`foundation_check.rs` ~L155–200) uses `?` on the first error from `receiver.tick` or `sender.tick`. During catch-up, `MdkOwner::tick` deliberately returns `Transport("transport_recovery_pending")`, and can also return `Transport("subscription_sync")`, `Transport("journal_backpressure")` or `Timeout`.
- The daemon contract (`daemon.rs` ~L150–164) treats `Transport(_) | Timeout` as degraded and retries on the next 15 s turn. The check is stricter than production, which matches a failure about 36.6 s into the post-restart exchange window, right after a 36.7 s warm activation.
- The failure is consistent with this explanation but doesn't prove it. The label is unknown, so the design correctly avoids calling this a fix.

## Required changes
1. **Join loop.** `execute` L244–251 (`b.tick(join_deadline)?; a.tick(join_deadline)?`) has the same propagate-on-first-error pattern. Either give it the same bounded-turn policy through the same helper, or state explicitly why it's excluded. As written, "change only the exchange wait loop" leaves an identical failure open on cold Arti joins. Also state that activation, `open_conversation` and the initial send stay one-shot.
2. **Category when the deadline expires after recoverable errors.** Today this becomes `Timeout`, reported as "deadline", which loses the cause. Specify the outcome: either the category stays `deadline` and a `last_recoverable` diagnostic records the role (receiver or sender) plus a finite label, or the category stays `transport`. Choose one and test it.
3. **Non-transient transport labels.** The code base has labels that retrying cannot fix, including `tls_verification`, `tls_hostname`, `proxy_forbidden`, `arti_configuration`, `relay_not_configured`, `shutdown`, `delivery_closed` and `notification_forwarder_stopped`. Either make an explicit terminal subset or justify retrying every `Transport(_)` to match the daemon. The diagnostic mapping should name the allowed labels and send everything else to `other`. The allowlist should at least cover `transport_recovery_pending`, `subscription_sync`, `journal_backpressure`, `relay_reconnect`, `recovery_subscription`, `notification_loss` and `group_state_unavailable`. `Transport` holds a `&'static str`, so the mapping is cheap.
4. **Cancellation safety.** Require that the per-turn bound is passed as `tick`'s own deadline. Do not wrap `tick` in an outer `tokio::time::timeout`, because cancelling `drain`, `apply_effects` or `submit_unsubmitted` partway is outside the daemon's tested contract.
5. **Post-receipt duplicate sends.** I checked `MdkOwner::send` (`mdk_adapter.rs:1165`): `verify_outgoing` returns the existing row's status before any network I/O or `submit`. So these calls never retransmit, and they can't produce the `Transport` errors that come from network sends. State that any error from them is terminal and not covered by the retry policy.

Your item (c), both owners ticking every cycle, is already covered by "give both owners turns". The test plan should still assert it explicitly.

## Recommended minimal private test seam
The seam stays private to `foundation_check.rs`. It goes in `#[cfg(test)]` or a private module and needs no public API:

```rust
trait ExchangeOwner {            // private; impl for MdkOwner just forwards
    async fn send(&mut self, s:&str, id:&str, b:&[u8], d:Instant) -> Result<SendStatus>;
    async fn tick(&mut self, d: Instant) -> Result<()>;
    fn received(&self, s:&str, id:&str) -> Result<Option<Vec<u8>>>;
    fn sent_status(&self, s:&str, id:&str) -> Result<SendStatus>;
}
fn turn_deadline(now: Instant, exchange: Instant) -> Instant;   // min(exchange, now+15s)
fn recoverable(e: &Error) -> Option<&'static str>;              // finite label or None=terminal
async fn exchange<O: ExchangeOwner>(...);                        // also reused by the join loop
```

Use a scripted fake owner that holds a queue of `tick` results and records the call deadlines and the `send` count. Run the tests under `#[tokio::test(start_paused = true)]`. Required cases:
- If the receiver returns recoverable errors, the sender still ticks in the same cycle, and vice versa.
- `Storage`, `Identity`, `Mdk`, `Invalid`, `Io` and the terminal transport labels stop on the first occurrence.
- Every recorded deadline is ≤ the exchange deadline and ≤ the turn start + 15 s.
- Persistent `transport_recovery_pending` ends exactly at 120 s with the category and diagnostic chosen in item 2.
- `send` is called exactly once before receipt, and the post-receipt duplicate and conflict calls still happen.
- An initial `send` error is terminal.
- Existing report keys are still present, and the new keys come from the finite set only.
