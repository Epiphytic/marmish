## Findings to fix later (non-blocking, most important first)

1. **Nothing checks that the source checkout stays unchanged.** The digest comes from the commit's tree (`ls-tree`), but the binaries are built from the working tree. The test at `v02-release.yml:128` only re-checks `HEAD`. If an earlier step (Python inspection, license collection or `cargo test`) changed a tracked file, the record would still claim the reviewed tree. Add `git diff --quiet HEAD --` and an empty `git status --porcelain --untracked-files=no` before the feature build and again before hashing. This also covers the existing product build.

2. **A missing harness path is silently skipped.** `v02-installed.yml` doesn't exist yet, and `ls-tree` exits 0 without it. This fails safe today, because the consumer requires `source == github.sha` and that commit must contain the workflow. But a candidate built now would produce tooling records nothing can use, with no warning. You could either:
   - document this, or
   - add `git cat-file -e "$MARMISH_BUILD_COMMIT:<path>"` for each of the four paths once the installed workflow lands. Adding it before then would block every candidate build.

3. **No test checks the exact record filename or the Rust consumer contract.** The test finds the record by its `.json` extension, so a typo in the role mapping would pass and then break the consumer. Add two things:
   - an assertion that the output names are exactly `{marmish-installed-check, marmish-installed-fixture, <role>-tooling.json}`, with the role computed from the target;
   - a test gated on `#[cfg(feature = "installed-checks")]` that deserializes the record into `records::ToolingManifest` and calls `validate(role, commit, harness)`.

4. **Output file modes aren't checked.** `verify_file(.., false)` skips the mode, and the test doesn't assert 0555 for the tools or 0444 for the record. Upload strips modes anyway and the consumer runs `chmod 0500`, so this is cosmetic.

5. **The tool is probed before it is hashed.** If the tool rewrote itself while being probed, the bytes it ran with and the bytes it shipped could differ. The impact is low because the consumer probes the shipped bytes again (`probeTool`). Reordering to hash, then probe, then copy and verify would close the gap.

6. **The `shasum --check` doesn't catch added files.** It catches changed or missing files in `native-assets`, but not new ones. Nothing writes there today; comparing a file listing would make the check complete.

7. **The job may run out of time.** Each package job now runs the full feature test, Clippy and a second release build in a cold target folder, still under `timeout-minutes: 60`. macOS is the most likely to approach that. Watch the first hosted run.

## Shell portability

The step pins `shell: bash` and uses only syntax that macOS's bash 3.2 supports (`set -euo pipefail`, `[ ]`, `$(...)`). It also uses `shasum` and `cut -d ' ' -f 1`, which behave the same on macOS and Linux. The `ubuntu-24.04` and `-arm` images include `shasum` through Perl. Its only other use in these workflows is in `v02-native.yml`, which runs on Linux, so the first hosted run will be the first real proof on the ARM image.
