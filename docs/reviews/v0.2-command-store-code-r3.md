## 3. N3, uncertain publications: blocker introduced

**B1 (new), at `command_store.rs:2698`.** The change excludes every `'uncertain'` publication from moving to `'published'`. But `'uncertain'` has two sources:

1. **Quarantine**, set at `:2663` and `:2679`. This is the case N3 was aimed at.
2. **Runtime send ambiguity.** `command_publication_uncertain` (`:2107–2110`) moves a publication from `prepared` to `uncertain`. The runtime calls it at `command_runtime.rs:273–276` when MDK retains no fanout and no queued intent for it. The comment there says "Convergence alone may retire it".

For the second case, a later genuine `Published` update still inserts the binding and returns `Ok(true)`, so that binding is ACKed. But the publication now stays `'uncertain'` forever. `command_maintain` only retires a publication whose state is `published`, `invalidated` or `expired` (`:2454–2455`). Nothing in the store ever sets `expired`. So a publication that converges after being marked uncertain can now only retire through invalidation.

That is a regression against the round 2 code, where converging to `published` was what let it retire. It also weakens the r4 retention contract that terminal, ACKed publications retire.

My N3 suggestion was too broad here; quarantine already blocked retirement through the quarantined row check (`:2459–2463`), so the state change it asked for was only diagnostic.

**Required fix (either option):**
- Keep a persistent quarantine marker on the publication, set at `:2663` and `:2679` for both affected events, and exclude only marked publications at `:2698`. A runtime-uncertain publication can then still become `published`.
- Or revert `:2698` to `NOT IN('invalidated','expired')` and rely on the quarantined-row gate. That gives up sticky diagnostics but keeps retirement safe.

A plain "no quarantined row for this event" check would not be enough. At `:2663`, when a native id moves to a different event, the second event is marked uncertain but owns no quarantined row.

**Regression assertions to add:**
- Claim a publication, call `command_publication_uncertain`, apply a genuine `Published`, and expect state `published`. After the ACKs, maintain should retire it.
- Keep the existing test at `:5553` asserting that a quarantined publication stays `uncertain`. That test is fine as written; it just doesn't cover the runtime path.

## Scope limits

- Whether the live runtime ever delivers `Published` after `command_publication_uncertain` depends on runtime integration, which I did not review. The store regression applies regardless.
- I made no claims about the separate store run of 30 tests, the full suite, live native ACKs or phase acceptance.

`★ Insight ─────────────────────────────────────`
- In this store, `'uncertain'` covers two different situations: evidence that conflicts (quarantine) and a send whose outcome isn't known yet. They need opposite rules, one sticky and one able to converge, so a rule keyed only on the state name can't serve both.
- The sticky-state fix was redundant for safety because the quarantined-row gate in maintain already blocked retirement. A narrow "make this sticky" change can still lose recovery paths that other states depended on.
