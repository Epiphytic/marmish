### Blocking corrections

**R2-B1. The stated user-facing lifetime limit is inaccurate.**
- The doc says the limit is "4096 attempted explicit fresh preparations". In practice, active rooms are never retired: `command_revoke_room` is only called on authority failure, forget or invalid join (`command_adapter.rs:115,155,340`).
- So every successful fresh session permanently takes one of the 64 active command-room slots (`command_rooms.rs` accept cap). Those slots are shared with default rooms and inbound server-role rooms.
- Successful fresh rooms also count toward the 4096 total-room metadata cap, so the 4096 marker cap can only bind through failed or uncertain attempts.
- **Required doc fix:** state that successful fresh sessions are limited to at most 64 live command rooms per profile lifetime, minus default and server rooms, with no retirement. Exhausting them also refuses new default rooms for other peers and inbound server rooms with `command_room_capacity`. The 4096 marker cap mainly bounds failed or uncertain attempts.
- **Required tests:**
  - At active capacity, `--new-session` is refused before any marker is written.
  - An existing default room is still reused at active capacity.
- **Evaluation of 4096 vs the previous 64:** 4096 is acceptable and better than 64. Rows are about 80 bytes, so roughly 330 KB worst case, and all of them are attempt-bearing. It is just not the limit users will hit.

**R2-B2. The installed default-Prepare probe has no budget or position.**
- The approved recovery doc says its stage sum (1355 s) already exceeds the work deadline (L+1350) by 5 s, and exhausted stages never extend work.
- The new probe is "bounded LocalBusy polling" with no limit and only "after its original ordinary room is ready" as its position.
- **Required doc fix:** fix its position after the first sample's completion and `bind()`, and before the second submit. Bound it to at most 15 s and at most 15 requests at least 1 s apart, clipped to the work deadline. Read server evidence and client `CommandInvocations` immediately before and after it.
- Also state that the probe's time reduces the final second-sample wait clipping; it is not added to the budget. If the probe times out the cohort is red, not retried.
- Confirm the fresh Prepare (up to 60 s) plus Submit stays inside the existing 90 s detach stage (it does) and needs no new stage.

### Optional suggestions
1. Clarify the Submit-gate wording. "Do not reselect the first room and compare" reads as though it conflicts with "currently selected ready default room". Suggested wording: "default session must equal the current default selection; fresh session must be marker-bound; nothing else."
2. Reserve active-room headroom for fresh rooms, for example refusing fresh creation at 56 or more active rooms, so `--new-session` use can't lock out inbound server rooms.
3. The turn can finish right at the CLI's 60 s deadline, before the Welcome drain lets Ready be observed. Consider a drain margin of a few seconds. Alternatively, have the CLI report a distinct finite category such as `fresh_session_unobserved`, so the user knows a room may exist.
4. Name the exact agent that owns `command_preparation.rs` ("delegated agent" is ambiguous). Sequence the one-line `pub(super)` change in `command_store.rs` with the agent currently editing that file.
5. Serialize `fresh` with `skip_serializing_if = "Option::is_none"` so default Prepare bytes stay identical, and add `fresh` cases to the closed vectors at `ipc.rs:312`.
