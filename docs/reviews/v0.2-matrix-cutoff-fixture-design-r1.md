## Exact result

**APPROVED**, with two non-blocking notes.

I read the design against `installed_matrix.rs` (`fixture_command` at line 490, the test at lines 1213–1269), `installed_process.rs`, and the tail of `/tmp/marmish-021-c05-macos.log`. I made no edits and ran no Cargo or live commands.

**Diagnosis matches the evidence**
- The log shows 445 passed, 1 failed. The failure is `failed_wait_retains_handle_and_second_child_cannot_renew_cutoff` at `installed_matrix.rs:1259:37`, an `unwrap()` on `Err(Timeout)`.
- Line 1259 is `fixture_command(...).unwrap()`, the outer result. In the third case the deadline is 230ms (line 1253) and submit sleeps 150ms (line 1236) before it prints the handle. That leaves about 80ms for process startup, so the test is cold-start sensitive.
- Production behaves correctly. Submit failure returns `Err` before any handle is known (lines 500–513), and a wait failure is stored in `output` while the handle is kept (lines 525–539). The fix touches only the test.

**Two 1.2s stages under one 2s deadline**
- Both children share one `sample_deadline` (lines 499, 504, 530).
- Submit finishes at about 1.2s plus startup, so it succeeds if startup stays under 0.8s. That is about 10 times the old 80ms headroom.
- Wait then has under 0.8s left but sleeps 1.2s, so `process::run` hits `timeout_at(deadline, child.wait())` and returns `Err(Error::Timeout)` (`installed_process.rs:132–139`).
- If a mutation gave wait a fresh 2s deadline, its 1.2s sleep would finish with exit 7 and `output` would be `Ok`. The inner-error assertion would then fail, so the check does not depend on elapsed time alone.
- On timeout, `terminate` kills the whole process group (`process_group(0)`, `kill(-pid)`) and aborts the drains. Elapsed time therefore stays near 2s, and the `< 3s` bound leaves about 1s of margin.

**Assertions preserved and strengthened**
- The `result.encoded == encoded` check stays.
- `output.is_err()` becomes `matches!(result.output, Err(Error::Timeout))`. `Error` is in scope through `use super::*` (`crate::Error`, line 7), and `Error::Timeout` is already used in this file.
- The elapsed bound moves from `< 2s` to `< 3s`, which fits the new 2s deadline.

**Other cases and gates**
- The first two cases, `(0,255,"0")` and `(1,7,"0")`, keep their 5000ms budget and zero pause, so they are unchanged. The `detach_code != 0` and `pause == "0"` branches stay as they are.
- No production code changes and no gate is weakened.

**Non-blocking notes**
1. The remaining cold-start budget is about 0.8s for submit startup. A 1.1s sleep gives 0.9s of headroom, and wait still always times out. 1.0s is too marginal, because the timeout then depends on a positive startup time. Keeping 1.2s is acceptable.
2. The mutation check detects the renewal only when wait's own startup stays under about 0.8s. That is fine for a deliberate local run, but the design should say the mutation run is expected to fail at the inner-timeout assertion, not on the elapsed-time bound.

The doc's other conditions are sound. A fresh immutable macOS candidate is still required. The completed-code review before parent publication stays as planned.

## Disposition

Keep proposed 1.2s stages. The local mutation must fail at the exact inner-timeout assertion, not merely any earlier or elapsed-time failure. Source implementation began only after this approval.
