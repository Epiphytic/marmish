### Blockers

1. **It doesn't match the candidate's actions, though the doc says it does.** The candidate's macOS build is in `v02-release.yml:46,68-70`, not `v02-native.yml`. It uses:
   - `actions/checkout@11d5960a326750d5838078e36cf38b85af677262`
   - `dtolnay/rust-toolchain@59a558e8c538bf4a23bbffa19e5a278b703f2920 # 1.97.1` with `toolchain: 1.97.1`

   The design names `dtolnay/rust-toolchain@1.97.1`, which is a tag that can move and isn't what the candidate used. It doesn't pin checkout at all. Require both exact SHA pins and the `toolchain:` input, and correct the "same as the candidate" sentence.

2. **The commit check accepts commits from forks.** A 40-hex SHA passed to `actions/checkout` can resolve to a commit that exists only in a fork, because GitHub shares objects across a fork network. So "Checkout only the current repository" isn't actually enforced. The candidate prevents this with `fetch-depth: 0` plus `git merge-base --is-ancestor "$SOURCE" refs/remotes/origin/master` (`v02-release.yml:50,59`). Add the same: `fetch-depth: 0`, the ancestry check against `origin/master`, and the existing `rev-parse HEAD` equality. Locally, `e9a134f` is on `origin/master`, so the initial source passes.

3. **Nothing ties the source to candidate 41647399978.** The doc says root "will select `e9a134f…`" but never says that is the candidate's `source_commit`. If they differ, the diagnostic tells you nothing about the failed candidate. Record the candidate's `source_commit` in the design and require the dispatched `source` to equal it. If it can't be confirmed yet, the design must say the observations bind only to the commit actually dispatched.

### Required clarifications (small, but should be written into the design)

- **Validator form:** validate with bash `[[ $SOURCE =~ ^[0-9a-f]{40}$ ]]` from `env:`. Don't use `grep`: it works line by line, so a multi-line API input with one valid line would pass. `${{ inputs.source }}` may appear only in `env:` and in checkout's `with: ref:`, never inside `run:` (and not in `run-name`).
- **Build environment:** the candidate sets `MACOSX_DEPLOYMENT_TARGET=15.0`, which matches the design. It also sets `MARMISH_BUILD_COMMIT`, which `build.rs` only embeds as a string, so it has no effect on linking. Setting `MARMISH_BUILD_COMMIT=$SOURCE` anyway is cheap, keeps the build as close to the candidate's as possible, and removes a source of doubt. `MARMISH_NATIVE_TOOLCHAIN` only affects the Python tools and isn't needed. Leaving out `codesign` is fine because ad hoc signing doesn't change `otool -L` output.
- **Load-command filter:** in `otool -l` output the `Load command N` line comes before its `cmd` line, so the awk filter must buffer that header. If no `LC_BUILD_VERSION` or `LC_VERSION_MIN_MACOSX` record is found, it should print an explicit "none" marker rather than nothing. Also print `lipo -archs` (or `file`) per binary to confirm each is a thin arm64 binary. The current script's `NR>1` parsing would be wrong for a universal binary.
- **Platform assertion:** use `case "$(uname -s):$(uname -m)" in Darwin:arm64) ;; *) exit 1;; esac`, matching the candidate. Log `rustc -Vv` and `cargo -V`. `rust-toolchain.toml` also pins `1.97.1`, so the versions agree.
- **The existing inspection script:** either never call it, or call it only as a final step after the diagnostics. Say which in the design.
- **Concurrency:** adding a `concurrency` group without cancel-in-progress is optional and matches the repo's other workflows.

### Confirmed OK

The 45-minute job timeout and `set -Eeuo pipefail` keep the job bounded and make failures turn it red. `otool -L` output is small and printed verbatim, and the three binary names are fixed. Nothing creates runtime or private state.
