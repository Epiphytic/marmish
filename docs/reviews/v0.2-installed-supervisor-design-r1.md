# Installed artifact supervisor design review, round 1

Actual Claude Opus review in auto permission mode. Session `bd254f76-3612-4a6b-99a4-fb0ae3baa41d`. Read-only design scope; no implementation approval claimed.

**Verdict: CHANGES_REQUIRED**

The overall direction is sound and fits the amendment. A build-only Node transport, the Rust driver as the authority on whether a cell passed, uploads while the driver is still running, names bound to run/attempt, and bounded ZIP reads with no extraction are all fine. Four gaps block implementation.

Context: there is no Rust installed driver in this worktree or any other. `marmish-release-tool` is only the packaging entry point (`native_release::entry`), and nothing implements `run`/`exchange`, an inbox, or the record schemas. So I checked the supervisor doc against the amendment, the official client and README, and the earlier Python rendezvous (`tools/marmish_installed_rendezvous.py`).

## Blocking

**B1. The upload credentials aren't available to a `run:` step.** `uploadArtifact` needs `ACTIONS_RUNTIME_TOKEN` and `ACTIONS_RESULTS_URL`. The runner only gives those to JavaScript actions, not to `node …` started from a `run:` step. The doc must say how the supervisor gets them. My recommendation is a local JS action wrapping `supervise.mjs`, with `npm ci` run first. Exporting the token to `GITHUB_ENV` would hand it to every later step, which breaks the credential-isolation claim. Also, "credentials go only to api.github.com" is wrong for uploads, which talk to the results service and blob storage. Scope it per credential: `GITHUB_TOKEN` (actions:read) goes only to api.github.com, and the runtime token stays inside the library.

**B2. The supervisor↔driver protocol isn't defined.** The driver doesn't exist yet, so this doc is the contract and needs to pin down:
- The exact `run` and `exchange` argv.
- How filenames in the output directory map to stages, and which files are terminal ("both local terminal files" is never named).
- Which records each mode downloads into the inbox, and from which roles. Run mode needs at least the three server-ready records and, for the server's cleanup binding, the three remote client-results. Right now only exchange's downloads are described.
- An explicit rule that client-result is uploaded as soon as it's renamed, during the run. Otherwise the jobs deadlock: each server waits for remote client-results that would only be uploaded when their own supervisors exit.
- How supervisor exit codes combine with the driver's.

**B3. Two-second polling will exceed the `GITHUB_TOKEN` rate limit.** That limit is 1,000 requests per hour per repository. Three concurrent jobs polling every 2 s is about 90 requests per minute, so the limit goes after roughly 11 minutes of combined waiting, plus downloads and any other waves running in the same hour. Fixes:
- Set a per-job request budget and a longer or backoff interval.
- Use the list API's `name=` filter.
- Treat 403/429 rate-limit responses as transient within the deadline and honour `Retry-After`.
- Run one cheap list request per round, not one per name.

**B4. The deadlines don't match the amendment.**
- Exchange is bounded by the context expiry, but the amendment requires the 10–15 minute identity barrier, and missing it fails before any daemon starts. Exchange needs that barrier deadline instead.
- "Expiry + 10-minute cleanup reserve" has no check against the job's `timeout-minutes`. If it doesn't fit, GitHub kills the job and the supervisor never reports the failure. At startup the supervisor should check that expiry + reserve + margin fits the 55-minute job, and that it fits the auto-exit wave's 20 min + 9.5 min + 5 min budget.

## Non-blocking (recommended)

1. **Digest check:** verify the downloaded ZIP's SHA-256 against the list entry's `digest`, as the Python rendezvous did.
2. **Stable upload copy:** copy each renamed file into a staging directory only the supervisor can write, then upload from there. Hashing the original before and after the library reads it leaves a window where it could change.
3. **Redirect allowlist:** name the exact hosts (Azure blob storage for results) instead of "GitHub artifact storage allowlist".
4. **Artifact cap:** count against the README's 10-artifacts-per-job limit, diagnostics included, and set `retentionDays`.
5. **Kill after the reserve:** killing the driver can leave product daemons running. Record that outcome as red with state preserved.
6. **Other waves:** state which mode and inputs the auto-exit wave and the cleanup instance use. They have no exchange and no remote downloads.

Once B1–B4 are folded into the doc, it should be approvable without a structural redesign.
