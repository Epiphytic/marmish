My r4 review should have caught this. I checked `configure_value` against `CommandConfig::from_bytes` but not against the daemon's `apply_limit_overrides`. That function rejects `max_commands` on a client, so under r4 every client daemon would have failed at startup.

## The fix (`installed_matrix.rs`, SHA-256 4d4112d8…, matching the validation doc)
- **Code:** `configure_value` now writes `{"max_commands":4,"max_uptime":1800}` only for the server, and `{"max_uptime":1800}` for the client. Nothing else in the function changed. The file grew by 22 lines, which fits the limits branch plus the new test block.
- **Test:** the test takes the real setup-generated config for each role, applies `configure_value`, and runs `from_bytes` and then the same `apply_limit_overrides` the daemon uses. It asserts the server gets `max_commands` 4, the client gets none, and both get `max_uptime` 1800 s.

## How the daemon actually starts
I traced `cli.rs`, `daemon.rs`, `command_config.rs` and `command_limits.rs`:
1. **Flag accepted:** `--max-uptime` is a global flag and is only allowed with `daemon`. The driver passes `--max-uptime {uptime} daemon`, so that is accepted.
2. **Config overrides:** `daemon::open` loads `config.json` and calls `apply_limit_overrides` with no command-count override and the driver's uptime override.
   - **Client:** no command count is set, so the client-role rejection can't fire. Its uptime is the override, which is at most 1800 s and therefore valid.
   - **Server:** the count of 4 comes from the config. The role is server and `execution_clients` is not empty, so it is accepted. The uptime override (the driver's uptime) takes priority over the config's 1800.
3. **Uptime clock:** `ServiceLifetime::start` begins its clock inside `open`, after the driver has taken its `launch` time. So the D1 work and cleanup cutoffs (uptime − 360 and uptime − 30) still fall within the daemon's real uptime.
4. **Relay check:** the relays and Tor setting the driver passes still match the config, so the runtime binding check passes.

**Non-blocking:** the test applies the default override (none), while the real daemon passes an uptime override. By inspection that only changes the resulting uptime and can't affect whether it's accepted. Making the test use the same override would remove the gap.
