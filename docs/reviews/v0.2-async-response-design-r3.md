## B3 is now closed

Every point the r2 fix asked for is now written into the design as a requirement:

| r2 requirement | Amendment text |
|---|---|
| Durable attempt counter, increased in the same commit that clears the operation link | "Every Pending slot has a durable failed-attempt counter, incremented in the same completion transaction that clears its operation link." |
| Fixed, mandatory maximum | "After exactly three failed attempts, it must Answer" (replaces the old "may") |
| Finite retryable error; never `not_found`, Missing or a request to resubmit | "finite retryable recovery_uncertain, never not_found, Missing or an instruction to resubmit" |
| Wrong observation types count as failures | "Failures include wrong observation types and stale still-authorized completions." |
| Retries are paced | "at most once per maintenance tick per slot; there is no immediate retry loop" |
| Test | Force every Poll `read_output` attempt to fail, prove the slot is Answered after three attempts, and prove normal retirement after actual native ACKs |

This ends the starvation path from r2: a damaged or orphaned job directory, spool integrity failure, or decrypt error now gets a final answer after three attempts. The slot then retires and frees both the invocation's one outstanding Poll and its share of the 256 global slots.

## Both r2 non-blocking notes are addressed

- **When Suppressed is set:** a pending slot with no publication becomes Suppressed "in the same transaction as revoke_record". The recovery query therefore can't start an operation for an already-revoked slot.
- **Mismatched publications:** a mismatched completion publication "fails closed with a diagnostic and halts that actor completion path for explicit recovery" instead of retrying the same commit forever.

## Non-blocking notes for implementation review

1. **When the third-failure answer is written.** The text doesn't say whether the `recovery_uncertain` Answer is written in the same transaction as the third failure, or on a later tick. If it's later, the recovery query must skip a slot whose counter is already at 3. Otherwise it would register a fourth operation, and "exactly three" would be broken. The implementation should either write the Answer in the same transaction or filter those slots in the query.
2. **Stale completions count as failures.** Each revision bump on a running invocation can make a Poll's completion stale. On a busy invocation, a Poll could use up its three attempts and get `recovery_uncertain` even though nothing is broken. That is safe, because the answer is finite and retryable and the client simply polls again, so it isn't a blocker. It's still worth a test to confirm it doesn't happen during ordinary progress.
3. **Section heading.** It still reads "pending independent approval". Once the human approval is recorded, update it and drop the "only after approval" wording that keeps the mandatory `CommandProjection.response` field in place.
