**How each r2 item was resolved**
1. **Arti/tor-dirmgr barrier:** The design now puts `initialize_storage()` in `RelayConnector::bootstrap_inner` on the `needs_tor` branch, before `TorClient` is built. That placement matches the source:
   - `TorClient` is only built at `crates/marmish-native/src/transport.rs:371-375`, and it runs inside `bootstrap_lock`, after the `ready` check.
   - No other file in the repo uses `arti_client` or `tor_dirmgr`.
   - The public `bootstrap` (`transport.rs:344`) and its direct test callers go through `bootstrap_inner`, so the tests are covered too, as the design says.
   - `TorClientConfigBuilder::build()` only builds the config and doesn't open SQLite, so running it before the barrier is fine.
   - Failures map to the finite `Storage("sqlcipher_init")`, the same as the other native boundaries.
2. **First-initializer rule:** The design now says the barrier "MUST be the first SQLite initializer in the process". It explains why: once `isInit` is set, a later caller can't detect that the extra-init hook is still running on another thread. The design also limits its guarantee to first use and makes no claim about arbitrary third-party code.
3. **`Cargo.lock` reverse-dependency audit:** I checked the lock file myself:
   - There is exactly one `rusqlite` (0.40.1) and one `libsqlite3-sys` (0.38.1, pinned git revision `5ae7fdf…`).
   - Only `marmish-engine`, `marmish-native`, `storage-sqlite` and `tor-dirmgr` depend on `rusqlite`. Only `rusqlite` depends on `libsqlite3-sys`.

   That matches the design's list. The design also requires repeating the check whenever dependencies change and after implementation.

**Rest of the design:** It still makes no hook or compiler changes, caches failures, adds no shutdown, reset or retry, adds no dependency, and keeps connection mutex ownership and the encryption and negative-key tests as they are.

**Not blocking, for the implementation review:**
- r2 suggested that the regression child assert no SQLite call happens before `initialize_storage()`. The design implies this but doesn't require it. Making it an explicit check would keep the test honest about the first-initializer rule.
- The Tor barrier is placed inside `bootstrap_lock`. That serializes startup, which is fine, because the `OnceLock` makes every call after the first one cheap.

`★ Insight ─────────────────────────────────────`
- An "exhaustive opener audit" has to cover the linked C library, not just the repo's own `Connection::open*` calls. Every crate that shares the one `libsqlite3-sys` also shares its one-time global setup, so the lock-file dependency graph is the real list of SQLite users.
- Putting the barrier at the point where `TorClient` is built covers production and the direct `bootstrap()` test callers alike. It no longer relies on the call order inside `MdkOwner::activate`.
