## The four blockers

- **B1 — fixed.** The supervisor now runs as a local JavaScript action, which does receive the upload credentials, and a plain `run: node` step is explicitly unsupported. Each token's scope is now stated correctly, and the child's environment excludes both.
- **B2 — fixed.** The doc now pins down:
  - The exact `run` argv.
  - Which files each mode publishes.
  - Which records are downloaded into the inbox, named `${role}-${kind}.json`.
  - The two terminal files.
  - That client-result is uploaded during the run and can't wait for the server result, so the cross-job deadlock is gone.
  - How supervisor and driver exit codes combine.
- **B3 — fixed.** Rough count per role:
  - Exchange: about 30 list calls over 15 minutes.
  - Run: about 80 list calls over the 40-minute context.
  - Downloads: about 9.
  - Total: roughly 120, inside the 200-call cap. Three jobs come to about 600 per hour, under the 1,000 limit, with room for the build's own artifact downloads.
- **B4 — fixed.** Exchange now ends at the earlier of the context expiry and the 15-minute barrier. The run budget also fits: the context is created in the resolve job with a 40-minute expiry, the matrix job starts after that, and 40 + 10 + 5 = 55, so the job-deadline check passes as long as the job starts after the context was created, which it always does.

## Non-blocking cleanups for implementation

1. **Exchange source file:** lines 24–28 don't say where the local `identity-ready.json` is read from before it's published (presumably `output/`). State it.
2. **Pagination wording:** line 78 still allows 1000 entries over 10 pages, but lines 79–80 allow a single 100-entry list and reject anything larger. Keep one. The single 100-entry rule is fine only if the whole run produces fewer than 100 artifacts.
3. **Cancellation signal:** when a job is cancelled or times out, the runner sends SIGINT before SIGTERM. Handle SIGINT the same way as SIGTERM: send SIGTERM to the driver once, then wait for it to exit.
4. **`job-deadline` source:** compute it from the job's actual start in a first step, and keep `timeout-minutes: 55` in the workflow matching it, so a caller can't set it wrong.
5. **Retries and the budget:** state explicitly that Retry-After retries count against the 200-call cap.
