## Blocking finding

**R3-B1. The grant and trust check depends on list order (`installed_matrix.rs:205`, `:256-257`).**
- Product setup stores `execution_clients` and `trusted_remotes` as sorted lists of hex keys (`native_setup.rs:86-109`).
- `configuration_peers` builds the same keys in role order (linux-amd64, linux-arm64, macos-arm64), not sorted order.
- `configure_value` compares the two lists in order, so it fails whenever the order differs.
- Every job configures both its server and its client, so it only passes if both sets of random keys happen to be sorted already. That is 1/6 × 1/6, about 2.8%, and the result is the same for all three jobs because they share the key sets. So roughly 97% of real runs go red before any daemon starts. They fail safely, but no run would qualify.
- The regression test `actual_setup_updates_grants_and_trust_then_preserves_them` sorts `peers` at line 978, which is exactly what hides the bug.
- **Fix:**
  - Sort the list in `configuration_peers`, or compare the two as sets.
  - Make the test feed deliberately unsorted peers, for example the sorted list reversed. It should accept the setup result and still reject a missing or extra key.

## r2 fixes verified in the code
- **D1 (cleanup reserve), fixed.**
  - `budgets` sets uptime to the smaller of 1800 and (remaining − 60), work to uptime − 360, and requires work ≥ 600.
  - Both run from one monotonic `launch` origin taken after setup, just before the server starts. The daemon starts its own uptime clock later, so the driver's cutoffs stay inside the daemon's real uptime.
  - Cleanup, client stop and server stop all share the `uptime − 30` cutoff (lines 726-731 and 818).
  - The test checks the arithmetic, including that 1019 seconds remaining is refused.
- **D2 structure, correct apart from R3-B1.**
  - The driver runs the installed `bin/marmish setup --update` with three `--grant` or `--trust` npubs.
  - It checks the setup report, including that the npub matches its own account, that no identity was created and no owner was opened, and that every stop flag is true.
  - It then changes only `allow_exec`, `cwd` and `limits`, preserves every other field, re-checks the config and reads it back.
- **Fixture copy:** the copied fixture is re-hashed against the pin before use (line 697).
- **Server-ready and rollup:** `validate_ready` now ties `fixture.sha256` to the context tooling pin.
- **Pre-spawn check:** the engine-path check now uses no-follow metadata (line 716), and any existing entry fails.
- **Stop timeout:** the process group is killed and reaped within a 5-second bound, the drains are aborted and joined, and the result stays red. A test using a real child that ignores SIGTERM covers this.
