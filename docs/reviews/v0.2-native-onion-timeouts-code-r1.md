## What I verified

**Transport timing (`transport.rs`)**
- `tor_connect_timeout` defaults to 120 s and must be greater than 0 and at most 120 s. `route_timeout` is 15 s for Direct and 135 s for Tor (a checked sum).
- `connection_timeout(&Url)` goes through `policy().destination`, so an unconfigured URL is an error, and it is the only place the route-to-timeout mapping lives.
- In `connection_phases`:
  - Direct keeps a single 15 s window covering the permit wait, TCP, TLS and WebSocket.
  - Tor gets 120 s for the permit wait plus the stream, then one 15 s window shared by TLS and WebSocket.
  - The whole attempt is capped at 135 s, and `cancelled` stays a `biased` select arm throughout.
- The permit is acquired inside `connect_stream` and passed on to `finish_socket`, so it still lasts until both SDK halves are dropped. The existing test for that passes.
- Every existing diagnostic event (`relay_slot`, `arti_connect`, `relay_stream`, `tls`) is still emitted, and no new event pairs were added, so the jq allowlist does not change.

**The transport tests run the real production wrapper.** They cover:
- a 20 s Tor stream followed by 2 s TLS and 3 s WS: succeeds at 25 s;
- a 20 s Direct stream: fails at 15 s;
- a Tor stream over 121 s: fails at 120 s;
- a 1 s stream followed by 8 s TLS and 8 s WS: fails at 16 s, which proves TLS and WS share one budget;
- the permit wait using up 15 s or 120 s;
- cancellation during each of the three phases, with the permit freed every time.

**Explicit per-relay SDK options.** `add_relay` now sets `.connect_timeout(connection_timeout)` and `.limits(relay_limits())`. This matters because the pinned `AddRelay::new` starts from `RelayOptions::default()` and the pool uses those options unchanged. Setting `.limits` also fixes an older problem where the ClientBuilder limits were silently ignored. With these limits the SDK caps messages and events at 1 MiB, matching the connector's frame cap. The SDK defaults are `MAX_MESSAGE_SIZE` for messages and no limit for events.

**Startup.** `turn_end = min(deadline, now + connection_timeout)`, there are still 3 attempts, and the original deadline is used throughout. The new test covers:
- 30 s already spent on bootstrap;
- a 20 s Tor connect on the first endpoint;
- the second endpoint's wait being exactly the 100 s left, ending at exactly the 150 s deadline.

**Recovery (`recover_relay`) matches the pinned SDK contract:**
- Connected means the relay is done.
- Initialized or Terminated gets `connect()`, but only on a turn that passes the 2 s reconnect gate.
- Pending, Connecting, Disconnected and Sleeping are only observed, never cancelled or re-dialled.
- Banned is reported as the retryable `relay_reconnect`.
- Shutdown is reported as `Transport("shutdown")`, which is one of the terminal labels.

The SDK's `request_connect` already does nothing unless the status is Initialized, Terminated or Sleeping, so this is safe twice over. The tests drive a real `Relay::builder().websocket_transport(..)`:
- a 50 s dial lasts over three 15 s turns with exactly one transport call;
- a 200 s dial ends as Terminated at the fixed 135 s, which shows the timeout is not restarted by repeated status checks;
- the permit is released, a later explicit retry works, shutdown frees the pending dial's permit, and nothing restarts after shutdown.

**Owner test.** `pending_owner_recovery_keeps_publication_paused_and_forwarder_alive` checks, over four 15 s turns, that publication stays paused, the forwarder task keeps the same ID, and there is exactly one dial. Dropping the owner then frees the permit; that relies on the SDK's `RelayPool::drop` → `shutdown`, which I confirmed exists.

**The `|| !connected` fix.** This change clears `recovery_subscribed` when a relay drops after recovery had already resubscribed. I agree it is a fix: previously that state could wait forever without ever re-dialling. Turn 2 of the owner test covers it.

**Keeping a healthy forwarder instead of restarting it every turn is safe.** The pinned MDK forwarder (`sdk_client.rs:3749-3830`) exits whenever it loses notifications (lag or queue overflow), so a loss always ends with the forwarder stopped and then restarted.
- There is a brief window where the loss has been recorded but the task hasn't finished (during `worker.await`).
- Even so, the publication fence can't reopen during it. Resuming needs `account_subscription_eose` for the latest activation snapshot, and those EOSE notifications can only arrive through a working forwarder.
- On the next turn `stopped` is detected and recovery runs again.

**Shutdown.** Ordering is unchanged: `client.shutdown()` sends the SDK's `notify_one` terminate and then `connector.cancel()` runs. `Drop` cancels the connector. No Marmish background task or registry was added.

**Docs.** They state the outcome accurately:
- The owner failed readiness and no onion client flow ran.
- The three direct reports each show `ok`, `cleanup_ok` and `route:"off"`.
- A longer timeout is not claimed to be a fix.
- Acceptance is not claimed.

## Non-blocking notes
1. **Clippy on test targets fails.** `--all-targets` fails on new test code at `transport.rs:904`. The project gate (`--workspace`, without test targets) passes, and the only workflow that runs `--all-targets` is the legacy v0.1 `native-validation.yml`. Since this is a one-line fix in code added by this change, I'd fix it before committing.
2. **The phase doc has changed since design approval.** It now hashes to `c0bcc406…` because of the updated status header ("Design approved by … Implementation and hosted acceptance remain pending"). I couldn't diff it byte-for-byte against the approved `05e87313` text. If the review record needs to cite exact bytes, either confirm the change is only the header or record both hashes.
3. **Recovery can't say why a relay failed.** `recover_relay` maps Banned to the retryable `relay_reconnect`, so a banned relay is retried until the stage deadline rather than failing at once. That matches the old behaviour and is bounded. A recovery that fails also no longer reports a cause from the SDK (`connect()` gives no feedback). The connector's `connector_failure` events still show the reason in `--debug` output.
4. **Timeout reporting at 135 s.** The SDK timer (135 s) is equal to the connector's total and starts first. A Tor attempt that uses its whole budget therefore usually ends as an SDK timeout with no `connector_failure` event. `arti_connect begin` without `relay_stream connected` still shows which phase it was in.
5. **The recovery tests depend on scheduling.** `settle()` relies on 16 `yield_now` calls on a current-thread runtime. It was stable in 20 runs, but if a future SDK update adds await points, a missed transition will show up as an assertion failure, not as an incorrect pass.
6. **The 570 s budget may still run out on hosted runs.** Four sequential Tor activations could exhaust it. If so, the honest result is a `deadline` failure on a fresh full matrix, not a wider budget.

**Still required:** a fresh hosted run of all four jobs proving actual Tor encrypted exchange, binary payloads, receipts, restart and cleanup. Until then Phase 1 stays open and Phase 2 code stays gated.
