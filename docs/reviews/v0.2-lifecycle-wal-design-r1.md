# Lifecycle WAL amendment review, round 1

Actual Claude Code auto-mode. Session: `887eb95f-10bf-41d0-a76c-46a51733d20a`. Model: `claude-sonnet-5-5`. Read-only design review.

**CHANGES_REQUIRED**

I read the amendment (`docs/phases/v0.2-installed-version-lifecycle.md:313-356`), `native_preflight.rs`, `/tmp/marmish-lifecycle-wal-prerequisite.log` and `identity.rs::open_private`. I ran nothing. Nothing in this review is an implementation review or phase acceptance.

**Supported by the evidence**
- The log shows MDK (2,129,920 bytes) and Journal (200,704 bytes) main files unchanged. For each database, an absent `-wal` became 0 bytes and an absent `-shm` became 32,768 bytes.
- This is correct SQLite behavior. A clean last close of a WAL database deletes the sidecars. Opening a WAL database read-only afterwards creates an empty WAL and a 32 KiB wal-index in SHM. A read-only connection does not checkpoint or write database pages.
- The test fails at the strict `before == after` assertion, as the amendment says. Sidecars are probably also created in the on-disk `commands/engine.sqlite3` path, but the log doesn't show that.
- The test snapshots only after the owner has shut down and the mode probes have closed. The probes use the same read-only `open()`.

**Blocking findings**
1. **Engine database is not covered.** The amendment says "the three captured database names", but the genuine test and log cover only MDK and Journal. `check()` also opens `commands/engine.sqlite3`, and the engine uses `Journal::Wal` (`marmish-engine/src/cipher.rs:107`). Either extend the genuine test to a real engine DB, or say plainly that the engine sidecar behavior is unobserved. The three-platform lifecycle run cannot be the first place that behavior is seen.
2. **Ownership and mode rule is looser than the existing private-file rule.** The amendment says "current UID, no group/other write". The existing `open_private` requires a regular file, `nlink==1`, `uid==euid` and mode exactly `0600`, with no symlink. SQLite creates sidecars with the main DB's mode, so exact `0600` is achievable. A 0644 sidecar would pass the draft rule and still be a private-state exposure. Require exact `0600`, `nlink==1`, regular and no-follow. The predicate should also check the `commands/` directory perms with the existing `check_dir`.
3. **No-live-writer prerequisite is not enforced by the predicate.** A writer that starts after the snapshot would also create an empty WAL and a 32 KiB SHM, and the predicate would accept them. The amendment relies on the profile lease and owner-lock exclusivity, and says "start with no owner or worker". That is acceptable, but it must be an explicit precondition. The predicate should run only while the lease is held across the snapshot, C startup and the final check, and the spec should state that this is the only defense. Also confirm that `owner.lock` is held through preflight at `daemon.rs:98`.

**Non-blocking suggestions**
- **Pre-existing sidecars may fail closed.** A read-only open of a preexisting nonempty WAL with an SHM can rebuild the wal-index and rewrite SHM bytes. That would fail the "exact bytes" rule for existing sidecars even without a real mutation. The required genuine-WAL test will show whether this happens. State that a failure there is fail-closed and needs a new amendment, not a quiet waiver. Also say whether a preexisting empty WAL or SHM counts as preserved.
- **Cleanup wording.** "Do not delete sidecars after C exits" is correct. Add that cleanup is the existing owned-state removal and that no sidecar deletion happens outside it.
- **SHM contents.** The size is checked but the wal-index header bytes are not, which is fine. Say so explicitly, so it isn't read as a content guarantee.
- **Test hygiene.** The new predicate tests should reuse the same private-file helper as production so the two don't drift. Keep the lifecycle log free of paths and bytes.
- **Test sufficiency.** The listed negative cases (changed main bytes, changed or deleted preexisting sidecar, new nonempty WAL, wrong-size SHM, symlink, unsafe mode, wrong owner, unexpected names) are adequate. Add hard-linked sidecars (`nlink>1`), an `-journal` or other unexpected suffix, and an engine-database case. Do not claim that mutation tests prove SQLite semantics.

**Exact scope of this verdict**
- It covers only the draft WAL auxiliary-file amendment: new empty WAL and 32,768-byte SHM allowed under exact private checks, with main DB and preexisting sidecars byte-identical.
- It forbids `immutable=1`, production flag or journal-mode changes, checkpointing and write-capable connections.
- It does not re-open lifecycle r4 approval, and it does not validate any code that implements the amendment.
- Once findings 1–3 are fixed in the doc, I'd expect to approve the design. That is not approval now.
