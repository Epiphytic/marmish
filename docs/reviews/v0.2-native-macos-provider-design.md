# macOS v2 provider: scoped design review

Actual Claude Code Opus 5.5, session `5022baae-f832-444d-83bf-1048f9f569d1`, `--permission-mode auto`. Recorded before implementation. Approval is limited to the additive selected-keychain API, disposable-keychain qualification and standalone manual workflow; all five conditions below are binding.

# Verdict: APPROVED, design only, with five binding conditions

The proposal needs no redesign. It does leave five implementation details unspecified; they are listed below as binding, and the code review will check them. This review is based on the current source: `crates/marmish-vault/src/lib.rs` (L158–186), `src/macos.rs` and `tests/support/native_macos.rs`, phase 1 doc L75, L112 and L118, and the conventions in `v02-native.yml`.

## Why the API is safe as proposed

- **`Provider::open_keychain` already takes a namespace** (`macos.rs`). Only the public wrapper in `lib.rs` hardcodes `Legacy`. The change is:
  - add `#[cfg(target_os = "macos")] pub fn open_keychain_namespaced(keychain: &SecKeychain, namespace: Namespace) -> Result<Self, Error>`, which sets `namespace` and calls `Provider::open_keychain(keychain, namespace)`;
  - make `open_keychain(k)` simply call `Self::open_keychain_namespaced(k, Namespace::Legacy)`.
  - Behavior is unchanged for every existing caller.
- **Namespace isolation already exists in code:**
  - `check_reference` returns `Malformed` when the version differs;
  - services are disjoint: `marmish.v1.*` vs `marmish.v2.*`, case-sensitive;
  - `list()` checks `svce` for each item.
- **Linux builds don't change:** the new function is macOS-only, and Linux builds are token-identical.
- **Native production is untouched:** it keeps using `open_namespaced(MarmishV2)` on the default keychain through the helper. Nothing in native, the helper or the CLI gains a keychain selector.

## Binding conditions

**P1. Restart child (`restart_load`).**
- Open the vault with `open_keychain_namespaced(&kc, MarmishV2)` and load **both** a v2 Nostr and a v2 SQLCipher reference, checking the exact bytes.
- The outcome is `ok` only if both load.
- It is `locked_or_denied` only if **both** return `LockedOrDenied`. A mixed result, or any other error, panics, which makes the gate fail.
- Write only those fixed tokens.

**P2. Same-process proof, all in the one owned keychain.**
1. Using the Legacy vault, create the existing two v1 items.
2. Using the v2 vault, create four items: two Nostr and two SQLCipher, with distinct labels. At least one v2 ID must equal a v1 ID, with a different secret.
3. Check:
   - each namespace loads only its own secret;
   - v2 `list()` returns exactly the 4 expected (ref, label) pairs, and v1 `list()` still returns exactly 2;
   - a v2 vault given a v1 ref returns `Malformed`, and a v1 vault given a v2 ref returns `Malformed`;
   - creating an existing v2 ref returns `Exists`, and the original secret is unchanged;
   - a missing v2 ref returns `Missing`.
4. Never call `open_namespaced` or `open_default` anywhere in this file.

**P3. Lock and no-UI checks.**
- With the keychain locked, v2 `probe`, `load` and `create` must each return `LockedOrDenied`.
- After unlocking, the v2 list must still have exactly 4 items, proving the locked create wrote nothing.
- While a vault is alive, assert `!SecKeychain::user_interaction_allowed()`.
- After all vaults are dropped, assert that the setting is back to its value at the start of the test. This is what "no UI" means concretely.

**P4. The report path is currently undefined and must be specified.**
- Because the workflow unsets `MARMISH_VAULT_MAC_TEST_ROOT`, the test runs its supervising parent. That parent deletes the private root on success, so no report survives unless one is written explicitly.
- Add one explicit variable, for example `MARMISH_VAULT_MAC_REPORT=<absolute path under RUNNER_TEMP>`.
- Only the supervising parent writes it, once, using create-new with mode 0600, and only from fixed tokens read from the root.
- The report has exactly these keys:
  - `{"schema":1,"provider":"macos-selected-keychain","namespace":"marmish-v2","same_process":"pass","lock_denial":"pass","restart":"ok|locked_or_denied","replacement":"ok|locked_or_denied","cleanup":"pass"}`.
- If the test fails, no report is written.
- The workflow fails when the report is missing or when `jq -e` doesn't match exactly.
- The workflow adds the signing kind (`adhoc`, `linker-signed` or `other`) separately. It takes this from `codesign -dv` on the executable path that `--no-run --message-format=json` reports. Never include raw codesign output, paths, IDs or key bytes.

**P5. Acceptance wording.**
- What a pass proves: the macOS v2 provider's behavior is verified on an **explicitly selected, owned, disposable keychain**.
- What it does not prove, and the record must say remains unverified:
  - selecting the default keychain;
  - the production helper's binary and ACL identity;
  - interactive prompts.
- A `locked_or_denied` restart result is recorded as such. It never counts as cross-process access.
- If the workflow hasn't run, the provider is "unverified", never "pass".

## Workflow (new manual-only `v02-provider.yml`): approved

- Use `workflow_dispatch` only, `permissions: contents: read`, and no secrets.
- Use `macos-15`, `dtolnay/rust-toolchain@1.97.1` and `Swatinem/rust-cache@v2`, matching `v02-native.yml`. Set a 15-minute job timeout.
- Steps:
  1. `cargo test --locked --release -p marmish-vault --test native_vault --no-run --message-format=json`, with a time bound, to capture the executable for the signing check.
  2. `cargo test --locked --release -p marmish-vault --lib`. This runs the sanitization and namespace unit tests at the new source.
  3. `env -u MARMISH_VAULT_MAC_TEST_ROOT -u MARMISH_VAULT_MAC_TEST_LOAD MARMISH_VAULT_MAC_REPORT="$RUNNER_TEMP/provider.json" cargo test --locked --release -p marmish-vault --test native_vault -- --exact macos::disposable_keychain_round_trip_lock_and_restart --ignored --nocapture --test-threads=1`, with `timeout-minutes: 3`. The test's internal 45-second supervisor and its rule to preserve owned state on failure stay as they are.
  4. Validate the report with `jq -e`, then upload it.
- Recommended: add `cargo check --locked --release -p marmish-native` on macOS. It's cheap proof that the native crate still compiles against the new vault source.
- Leave the existing workflows unchanged.

## Is a provider gate on the new source plus the foundation matrix at `112bb3a` enough?

Yes, for this additive API scope, provided all of the following hold:

1. The diff against `112bb3a` is limited to:

3. Each piece of evidence stays bound to its own SHA:
   - the transport and foundation matrix (run `41519670193`) to `112bb3a`;
   - the provider gate to the new SHA.
   The record must say that transport was not retested at the new SHA, and justify that with item 1.

If anything outside that file set changes, this justification no longer holds and the affected gates must be rerun.
