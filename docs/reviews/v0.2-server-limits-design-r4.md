## Round 3 blocker B1 (no way to retry Finish after Busy): resolved
The revised text (lines 144-157) does everything the r3 fix asked for:
- **Busy is now a durable trigger:** the latest Finish slot answered Busy, with no Finish pending.
- **The retry works when nothing moves:** the client sends a fresh Poll at its durable cursors, then consumes the terminal response and creates the new Finish in one step. This works even when the chunks are empty and neither cursor moves.
- **Strict preconditions:** produced must equal the durable cursor exactly on both streams, the gap-aware traversal must be valid, and no other unconsumed response or unanswered request may remain.
- **Status source:** the client always uses the Poll response, never `record.status`.
- **Attempt cap:** at most 4 attempts in total, and the count is persisted, so a restart doesn't reset it. A network retry of identical bytes isn't a new attempt. Repeating the same consumption reuses the same frozen request ID. After the cap, uptime is the exit.
- **Regression test:** lines 373-377 add the expire-output → Busy → restart → empty Poll → new Finish → exactly-one-increment test.

The scenario also holds up against the code. `expire_output` adds only a prefix `Expired` gap after the job exits, and an exited job never changes produced. So a Poll at cursor == produced has nothing left to read, and the equality check passes.

## Non-blocking refinements (none of them gate approval)
1. **Make Busy mean only "changed fingerprint" for Finish.** `ErrorCode::Busy` is already a general transient code: the store treats it as one alongside `StorageFailure` and `TransportDegraded` (`command_store.rs:754-763`). Because a Finish Busy is frozen per request ID and spends an attempt, a Busy from some other cause would eat into the 4-attempt cap. Either state that Finish projection returns Busy only for a changed fingerprint, or note that any Busy counts as an attempt. The cap keeps this bounded either way.
2. **Name the attempt state explicitly.** Spell out where the attempt counter and latest trigger live, for example new fields in the client invocation's facts JSON, defaulting to 0 for old records. Then the code review can check that restart is idempotent without guessing.
3. **Typos (cosmetic):** missing spaces remain in `max4`, `at most4/stream`, `and32KiB`, `one100ms`, `a30minute`, `exceedsN`, `prepare30s`, `activation150s` and `at most100ms`.

I'd recommend folding in item 1 before implementation starts, since it's a one-sentence clarification.
