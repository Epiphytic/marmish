## Nonblockers

1. **Little slack for the count exit.** Readiness (150s) plus workload (7m) is 9.5 of the 10 minutes, so only 30 seconds remain for the third Finish, its Published response and the daemon's next loop check. Server-limits lines 234–240 say a pending or uncertain publication delays exit until uptime. That would make the run red, which is correct, but a slow relay could fail an otherwise good run. Either cut the workload cap to about 6 minutes or state that the remaining 30 seconds is the Finish-and-exit allowance.
2. **Missing pre-launch check for the auto-exit server.** Before launch, require that the remaining time fits the 20-minute uptime, the 9.5-minute cleanup instance and the 5-minute end margin. Line 93's check for the cleanup instance should also measure against minute 50, not the full 55 minutes.
3. **No failure path when the server misses its count exit.** Say what happens if it hasn't exited by L+10. Either the supervisor uses the live server (Stop is allowed because the run is already red) to do failure cleanup while CleanupGuard is held, or it waits for the uptime exit at L+20 and then runs the cleanup instance. Either option fits the schedule. It just needs to be written down.
4. **Name the entrypoints clause being replaced.** Entrypoints item 5 (line 189) says "Before default-head/README cutover", which can't be done literally, because the head URLs are what get tested. The amendment's step 3 (head script live with rollback) settles this, but the supersession paragraph should cite entrypoints item 5 and lines 35–38 explicitly. It should also accept that between step 3 and step 4, users of the public default URL get the v0.2 script before HTTPS qualification has passed.
5. **Burned versions.** If HTTPS fails after a final `0.2.0` is published, that version is used up. Say that published version assets are never overwritten and that requalification uses a new version (rc.N+1 or 0.2.1). Consider publishing an rc first.
6. **Relay path for the local clients.** State that the three local clients reach the server through the direct relay, never local IPC, matching base line 25.
7. **Update the schedule estimate.** Replace the superseded ≈600-minute figure with about 6×55 = 330 minutes plus builds. Also state that the cross-wave barrier and the limit of three concurrent jobs apply to the new wave.
8. **Bind the exit reason if one exists.** If the daemon prints a final count-versus-uptime exit reason, bind it as extra evidence. Otherwise the timing inference above is the proof, which is acceptable.

`★ Insight ─────────────────────────────────────`
- Ceiling = planned + 1 turns the count limit into a detector rather than a gate: the auto-exit condition (admitted ≥ N, Finish count matching) can never be true during planned cleanup, so CleanupGuard is still held when the removal runs.
- The count exit and the uptime exit both return exit 0. The design tells them apart by timing alone: exiting at L+10 with uptime ending at L+20 can only be a count exit. That is also why the 30-second slack in nonblocker 1 is worth widening.
