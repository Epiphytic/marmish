## Checks performed

- **Secrecy**
  - The handle holds exactly format, profile, remote, session, invocation and submit hash. It has no request ID, argv, stdin, group bytes or authority.
  - `CommandHandle`, `PreparedClientOperation` and `ClientInvocation` derive no `Debug`, so they can't leak through logging. `ClientInvocation` has no `Serialize`, so the Submit request ID it carries stays inside the process.
- **Strict decoding**
  - `HandleFields` uses `deny_unknown_fields`, and the serde struct derive rejects duplicate keys.
  - `format` is a `u8`, so `true` or `1.0` is rejected.
  - Remote and digest must be 64 lowercase hex; session and invocation go through `id_timestamp` (32 lowercase hex).
  - The profile grammar matches `identity::validate_name` exactly. Input is capped at 1024 bytes on decode and on encode.
  - The panicking accessors (`expect`) are safe: the fields are private and every way to build a handle goes through `validate`.
- **`for_submit`** accepts only a Submit, and re-checks that the encoded bytes and digest still match the request. This closes the tampered-prepared-operation path, and a test covers it.
- **First request ID wins** (`command_store.rs:837-848`)
  - A Submit with a different request ID for an existing invocation is rejected before any slot or publication is inserted: the error drops the transaction, which rolls it back. The test shows `command_find_request` returns none afterwards.
  - Comparing only the ID is enough: the same owner and binding, the same ID and the same Submit digest imply the same canonical request bytes.
- **Schema invariant**
  - The table CHECK forces client rows (`server_side=0`) to have a 16-byte request ID and a 32-byte digest.
  - The only other callers of `insert_invocation` are the server admit path (`:766`, guarded at `:695`) and test owners built with `CommandDirection::Server`. So the CHECK cannot reject a legitimate write.
- **Retention**
  - `save_record` only runs `UPDATE facts, active`. Payload GC only sets `submit=NULL` (`:2795`). Only the floor-and-protection rule at `:2702` deletes the row.
  - So the immutable cursor and the original-request metadata survive slot and payload GC and an encrypted reopen, which the test confirms.
- **Discovery**
  - Pages are filtered to `server_side=0`, ordered by the AUTOINCREMENT cursor, and fetch `limit+1` rows to compute `next`. The limit must be 1..=64 and `after` must fit in an i64, so the work is bounded at about 3×64 point queries per page.
  - Every row goes through `check_local_binding`, so a corrupt row stops the page instead of being skipped silently.
- **Revocation**
  - Revoked rows still appear in discovery with `authority_valid=false`.
  - `validate_entry` checks the binding first, then returns `command_authority_revoked`.
  - `command_client_invocation` and slot state both refuse a revoked room or record.
- **Slot state** returns all four closed states: `Absent`, `Pending`, `Answered` and `Consumed`. A wrong owner or authority with a present slot returns an error, not `Absent`.

## Nonblocking findings

1. **Slot state depends on the caller checking the invocation first.**
   - `command_client_slot_state` (`:1127`) returns `Absent` before any record check if the slot row is gone. That includes a revoked room whose room row and slots were later retired, and an owner whose authority digest is stale.
   - This is the approved composition: the actor must first validate the handle with `command_client_invocation`. It is safe only if the actor really does that.
   - Suggested fix: add a doc comment stating the requirement. Better, change the signature to `(owner, invocation, id)`: call `client_record` first, and when the slot exists, require that `slot.request.op.invocation() == invocation`. That removes the requirement, adds no new state, and costs about three lines.
2. **An exact Submit retry after slot GC queues a new publication.**
   - Once the original slot has retired, an identical first-ID retry passes `freshness` and inserts a new slot and publication. The test at `NOW+86401` exercises this.
   - The server attaches by invocation digest (its existing path), so nothing executes twice. It does use a slot and a publication, though.
   - The future actor should resolve through ledger discovery before retrying a Submit whose `local_queued` it already confirmed. That matches the design's CLI rules; I note it so it isn't lost at integration.
3. **Old dev databases fail late.** `CREATE TABLE IF NOT EXISTS` won't add the new columns to an existing v4 development database. It then fails closed at the first client insert or ledger query, with a database error rather than an error at open. This is acceptable under the no-migration rule.
4. **Handle decoding is not byte-canonical.** Reordered keys, whitespace or `\u0061`-style escapes still decode. The decoded values are canonical, which is all the design requires.
   - If you later add an `encode()? == bytes` check like the evidence codec has, the CLI must first trim a trailing newline from `--handle-file`.
   - `decode` also calls `validate()` a second time even though `try_from` already did; that can be removed.
5. **Dead code against the commit gate.** `CLAUDE.md` requires `cargo clippy --workspace -- -D warnings` to be clean before a commit. The new unused items add to dead-code warnings that already existed. Either root wires them up before committing, or apply a narrowly scoped `allow(dead_code)` that is deleted at integration.

## Code-quality assessment

- **`command_submit_client`** (complexity 18→21, 58→78 lines)
  - The increase is real, but its cause is a security guard the design requires.
  - Worthwhile reduction: move the guard into `fn check_original_submit(tx, key, id) -> Result<()>`. This gets back most of the lines and complexity without hiding any logic.
  - Separately, `InvocationAdmission` plus the `insert_invocation_with_client_request` wrapper is ceremony. Adding a seventh parameter (`client_request: Option<(Id, Digest)>`) to `insert_invocation` stays within clippy's default `too_many_arguments` threshold of 7. That removes a struct, a function and a level of indirection, at the cost of touching two callers and a test.
- **Similarity to the evidence codec:** I agree it should not be generalized. The two codecs share about 8 lines of size-check-then-serde with different error types and canonicality rules, and a shared abstraction would cost more than it saves.
- **The four hex accessors** (`remote`, `session`, `invocation`, `submit_sha256`) could share a private `fn decode_hex<const N: usize>(&str) -> [u8; N]`. This is optional.
- **Profile grammar:** it is copied from `identity::validate_name`, which is private. Making that function `pub(crate)` and calling it with `map_err` would prevent the two copies from drifting apart. This is small and safe.
- **Test fixture growth:** the two new tests repeat the body of the existing `client_request` helper at `:4960` and `:5124`, and nearly repeat it at `:5073`.
  - Split `client_request` into a pure `client_outgoing(owner, request)` plus the submit call.
  - The paging loop can then call `client_request(&mut journal, &owner, &submit(seq))`. This removes about 30 lines with no loss of coverage.

I made no test claims beyond the commands listed above.
