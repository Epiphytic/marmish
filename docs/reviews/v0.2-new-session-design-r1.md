I've read the design (hash verified) and checked it against the current code. **Verdict: CHANGES_REQUIRED.** The core idea is sound: a durable reservation and a one-time "attempted" mark (compare-and-set) before the non-atomic native create, a daemon-generated session, and an attempted mark with no room being treated as permanently uncertain. But six blocking gaps would make the feature fail as written or weaken its guarantees.

## Design review: `docs/phases/v0.2-new-session.md` (SHA256 e47d99ff…82b1)

### Blocking findings

**B1. A fresh session can never be submitted to.**
- `command_local.rs:413-418` only accepts a first Submit if `command_ready_room(remote, relays) == Some(session)`.
- `command_ready_room` (`command_local.rs:262-290`) returns the *first* verified Client room for that peer. That is the default room, not the fresh one.
- So every fresh Submit returns `command_room_pending`, and the CLI loop in `command_cli.rs:1121-1140` turns that into failure or uncertainty.
- The design says "Submit bytes unchanged" but never says how Submit gets past this gate.
- **Fix:** add an exact-session readiness check in `command_local`. It accepts `session` only if it is the default ready room, or it is bound in `command_preparations` to this exact peer and passes `command_context` plus the fanout/queued-intent drain checks. It never falls back to another room. The wire Submit stays unchanged; adding `fresh` to IPC `CommandSubmit` is an optional alternative.
- **Tests:** fresh Submit attaches; Submit with a session from an unrelated room, another peer, or a revoked room is refused.

**B2. Plain (default) commands may silently land in a fresh room.**
- `command_rooms()` orders by `group_id` (`command_rooms.rs:57`), which is random.
- Both default selectors take the first Client room for the peer: `command_ready_room` (`command_local.rs:268`) and `open_command_room` with `!new_session` (`command_runtime.rs:110-121`).
- So once a fresh room exists, later plain commands can go into it. That contradicts "fresh, independent" and makes "default reuse unchanged" nondeterministic.
- **Fix:** both default selectors skip sessions present in `command_preparations`. Add a test where the fresh room has the lower `group_id`.

**B3. Reservations can leak and exhaust capacity permanently.**
- **Reserved but never queued:** `RoomIntents::enqueue` (`command_local.rs:~124-130`) silently drops a ninth intent and still returns `LocalBusy`. A token reserved before queue admission then holds one of the 64 never-deleted rows without ever being attempted.
- **Rooms created after the CLI has given up:** the CLI's Prepare deadline is a fixed 15 s (`command_cli.rs:1027`), while the daemon's queue start-by is 60 s. The daemon can therefore create a fresh room after the CLI has exited. If the user retries, a new token makes a second group, which is exactly the extra group this design is meant to prevent.
- **Permanent ceiling:** each such room holds one of the 64 active-room slots forever (`command_rooms.rs` accept cap; no room retirement exists), and the 64 reservation rows are never deleted. The profile's total number of fresh sessions is therefore permanently capped near 64, and the design doesn't say so.
- **Fix:**
  - (a) Reserve only when the `(remote, token)` intent is admitted, or the token is already known.
  - (b) Rows with attempted=0 never touched native state, so they may be deleted on start-by expiry, failure, or cap pressure. Only attempted=1 rows are retained permanently.
  - (c) Add one shared constant for the CLI's fresh Prepare window. The daemon must not start a fresh creation after `token_timestamp + window − 15 s turn`. The window must fit the installed 90 s detach stage.
  - (d) Check room capacity (active < 64, total < 4096) and the reservation cap before reserving, and again before the attempted mark, so a capacity refusal can't burn a token after the mark.
  - (e) State the permanent lifetime ceiling explicitly, with its finite refusal category, and test it.

**B4. Missing check after creation.**
- `open_command_room` only checks `room.peer` after `accept_command_group` (`command_runtime.rs:147-157`).
- **Fix:** the fenced path must also require `room.session == reserved session` and Client direction. On a mismatch it must forget the group and leave the token uncertain.

**B5. The file list for the implementer is incomplete.**
- `daemon.rs` has to change, but it isn't in the author's file list:
  - Prepare/`LocalBusy` enqueue at `daemon.rs:133-147`
  - `RoomIntents::next` and `command_open_room_turn(remote, …)` at `daemon.rs:306-323`
  - error-category mapping, which needs `command_room_uncertain`
- **Fix:** add `daemon.rs`, and the CLI category reporting, to the author's files.

**B6. Several installed recovery assertions conflict with approved contracts or can't be implemented from current evidence.**
- **Contradiction:** the approved `v0.2-phase4-installed-recovery.md:159-160` requires the second sample to use the "same authenticated session", and the code enforces it twice:
  - `installed_recovery.rs:448-455`: `bind()` rejects a changed session
  - `installed_recovery.rs:849-853`: `validate_record` requires an equal session

  The design must amend that doc text and invert both checks explicitly. "Extend" is not enough.
- **Transport binding can't be proven installed:** no current finite evidence interface carries it. Server `CommandEvidence` (`command_store.rs:3563-3583`) has `group_sha256` and `session` but no transport. Client `InvocationEntry` has neither group nor transport. Adding a field would break the shared deny-unknown-fields `installed_cleanup::Evidence` used by other cohorts.
- **Fix:** prove the installed case using only:
  - read-only server `CommandEvidence` rows, exactly 2: `group_sha256[0] != group_sha256[1]`, each row's `session` equals its handle's session, the two sessions differ, and principal = client account for both
  - client `group_submit_sha256` (from `client_group_submit`) equal to each row's group-bound `submit_sha256`

  Leave transport distinctness to offline tests, backed by the journal's `UNIQUE(transport)` constraint. Relay set and direction come from the driver's own CLI arguments and from rows being server-side; don't claim them as evidence.
- **Make the reuse probe concrete:** a raw IPC `CommandPrepare` on the client socket with `fresh` absent, bounded `LocalBusy` retries, and `Ready.session == handle0.session` and `local_account == client`. Then show the client's `CommandInvocations` count and the server evidence count are unchanged.
- Use a separate read-only helper; do not change the shared `cleanup::prepare` or `Evidence` schema.
- Bump `RecoveryResult.schema` to 2 with the new fields required, so old green records fail.
- Also name `installed_cleanup.rs` (helper only), the rollup in `installed_check.rs`, and the doc amendment in the delegated file set.

### Checked and acceptable as designed
- **Format 6 propagation:** `native_manifest.rs:60` and `native_preflight.rs:100` both read `journal::JOURNAL_*`, and `install-native.sh:139-140` compares the binary's formats with the manifest's. Bumping `JOURNAL_FORMAT` to 6 and adding 6 to the supported list propagates, and an older binary's preflight refuses a format-6 journal. Fixtures that hardcode `journal=5` / `[1,5,1,1,1]` are only synthetic parse vectors.
- **Serialization:** room turns run in the same daemon loop as dispatch, so no Prepare can observe the attempted mark mid-creation.
- **Cancellation:** a shutdown or timeout that drops the create future after the mark gives uncertain, and `reconcile_orphans` forgets the native group without allowing a retry.
- **Server side:** it accepts multiple rooms per peer (`command_adapter.rs` join path).
- **No caller-chosen session or keys:** the token is only a lookup key; the session comes from `foundation::fresh_id`.
- **CLI rejection placement** has a precedent: the `server_limit_operation` check at `cli.rs:233-237`.

### Optional recommendations
- Put the `--new-session` rejection in `cli.rs::run` next to the server-limit check, so `release-info`, install and daemon reject it too. Test that `marmish peer -- /bin/echo --new-session` keeps it as a command argument.
- Have the CLI omit `fresh` when it's None, so default Prepare bytes are unchanged, and update the closed vectors at `ipc.rs:312`.
- Later: clean up attempted=1 rows only once the token's timestamp is below the durable floor.
- Disclose an existing limitation: a durable welcome fanout for an orphan group could be published before it is forgotten.
