## Confirmed native integration seams

- `marmot-session::SessionConfig` accepts identity bytes, a typed SQLCipher key,
  a transport peeler and an account proof signer. `AccountDeviceRuntime::open`
  opens encrypted storage before invoking the host factory for adapter, routing
  and KeyPackage publisher. This is a public production boundary; importing the
  whole White Noise application or enabling test-support is unnecessary.
  [Configuration](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-session/src/session.rs#L107),
  [runtime entry](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-session/src/runtime.rs#L575).
- `NostrTransportAdapter` accepts a `NostrRelayClient` implementation. With the
  SDK feature, `NostrSdkRelayClient::with_account_signer` accepts an externally
  constructed Nostr client and immutable account signer. The pinned SDK exposes
  `ClientBuilder::websocket_transport`; its transport trait returns WebSocket
  sink/stream pairs. Marmish can implement TLS/WebSocket over app-owned Arti
  streams, select explicit direct or Tor routes and preserve WSS certificate
  validation. No MDK fork or process-global proxy mutation is required by this
  seam. MDK's optional `WN_SOCKS5_PROXY` helper is a separate process-wide route.
  [Adapter contract](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/transport-nostr-adapter/src/lib.rs#L859),
  [SDK injection](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/transport-nostr-adapter/src/sdk_client.rs#L1953),
  [pinned SDK builder](https://github.com/erskingardner/rust-nostr/blob/48801bf6f2f1cd55bb1729e94159946c8832a786/nostr-sdk/src/client/builder.rs#L250),
  [transport trait](https://github.com/erskingardner/rust-nostr/blob/48801bf6f2f1cd55bb1729e94159946c8832a786/nostr-sdk/src/transport/websocket.rs#L63).
- Official Arti `0.47.0` provides `TorClient::create_bootstrapped`, `connect`,
  isolated clients and configurable state/cache directories. Tokio streams and
  onion-service client support provide the required native building blocks.
  MDK does not itself bundle Arti; its injection hooks enable Marmish-owned Arti.
  Deaddrop's separate native onion-service example uses `hypertor 0.3.0`
  (Arti `0.45`), while its browser/WASM pieces serve different roles.
  [Arti APIs](https://docs.rs/arti-client/0.47.0/arti_client/struct.TorClient.html),
  [onion preferences](https://docs.rs/arti-client/0.47.0/arti_client/struct.StreamPrefs.html#method.connect_to_onion_services),
  [deaddrop native example](https://github.com/Epiphytic/deaddrop/blob/b38b2841b081952dc7728da391fe0e26fc7c6181/crates/onion-probe/src/lib.rs#L53).
- Public proof signer, `MarmotNostrSigner`, peeler and routing traits cover
  identity proofs, Welcome decryption and explicit publication/subscription
  routes. `KeyPackagePublisher` separates no-network preparation from publishing
  the same signed artifact on retry. Host code must provision device slots and
  consume effects, failures and publication acknowledgements; successful local
  `send` is not peer receipt. Runtime exposes outbound recovery/acknowledgement.
  [Proof signer](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/cgka-engine/src/account_identity_proof.rs#L193),
  [Nostr signer](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/transport-nostr-peeler/src/signer.rs#L47),
  [publisher](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-session/src/key_package.rs#L103),
  [routing](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-session/src/routing.rs).

## Persistence and protocol boundaries

`SqliteAccountStorage::open_encrypted` stores Marmot/OpenMLS state in SQLCipher;
`SqlCipherKey::raw([u8;32])` accepts a separate high-entropy database key.
The storage handle is `Clone` over one shared connection, and
`SessionConfig::with_storage` accepts a pre-opened handle. Public
`MessageStorage::list_pending_application_events` and
`delete_pending_application_events` support projection-then-ack recovery.
Delete only after the application projection commits; a crash between commits
requires idempotent replay. Sharing a handle does not create a transaction across
separate databases. Keep one actor and exclusive profile ownership.
[Storage handle](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/storage-sqlite/src/protocol/handle.rs#L17),
[pre-opened configuration](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-session/src/session.rs#L161),
[pending event contract](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/traits/src/storage.rs#L389).

`AccountHome::open` defaults to a plaintext secret file; keychain use must be
explicit (`open_with_keychain`/`open_with_secret_store`) or supplied by Marmish's
own key custody. Identity and SQLCipher keys are separate custody requirements.
[Secret-store selection](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-account/src/home.rs#L210).

Current MDK enforces the current protocol profile; production legacy creation
is rejected. Current account proof component `0x8009` differs from legacy
extension `0xf2f1`; old MLS leaves/groups cannot be presumed interoperable merely
because an application JSON envelope is unchanged. Legacy v0.1 is an optional
fixture, not a mandatory wire compatibility target. The user accepts breaking
on-disk formats and has no installed base: **no v0.1 migration is required**.
Core account/device leaves do not establish released user-facing pairing;
the application pairing feature remains explicitly unreleased.
[Engine/profile contract](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/cgka-engine/src/engine.rs#L442),
[proof format](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/cgka-engine/src/account_identity_proof.rs),
[pairing feature](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/marmot-app/Cargo.toml#L8).

The inspected Marmish legacy baseline is
`3edf7ae7003ebd0b9075e3453cb17b79475eba63`, with legacy MDK
`37c248a11239e108afc9bd4ee62b8f60542012e3` plus local patches.
Its `marmish/1` application protocol supplies useful compatibility vectors:
strict exact-field JSON, duplicate-key rejection, canonical padded base64 for
byte arguments/streams, authenticated two-party room binding, freshness challenges,
durable invocation tokens and output cursors. Existing Rust execution/vault
crates are reuse candidates, but private legacy daemon RPC and Python/native
confinement are not the remote wire protocol. JSON codec conformance and actual
cross-version MLS exchange are separate acceptance questions. Any optional
legacy live fixture needs a capable host and independently pinned old artifacts;
it is not a Rust production dependency or a proven interoperability path.
[Legacy protocol](https://github.com/Epiphytic/marmish/blob/3edf7ae7003ebd0b9075e3453cb17b79475eba63/tools/marmish_protocol.py),
[application binding](https://github.com/Epiphytic/marmish/blob/3edf7ae7003ebd0b9075e3453cb17b79475eba63/tools/marmish_app.py),
[legacy MDK pin](https://github.com/Epiphytic/marmish/blob/3edf7ae7003ebd0b9075e3453cb17b79475eba63/patches/mdk/README.md).

Binary application messages and authenticated sender/group metadata are exposed.
Dedicated Marmish rooms still need an authenticated purpose/version handshake,
request/session binding, authorization and durable replay/execution deduplication.
Fresh MLS groups or ephemeral outer Nostr event keys alone do not prevent command
replay. Do not invent an unallocated application component identifier.
[Message/group types](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/crates/traits/src/engine.rs).

## Dependency and acceptance unknowns

Upstream uses unpublished Git workspace crates, pinned OpenMLS
`94f57b829d95840fc5b415b7a86f547f5c1f65ba` and rust-nostr
`48801bf6f2f1cd55bb1729e94159946c8832a786`, plus `rusqlite 0.40.1` with
`bundled-sqlcipher-vendored-openssl`. Its root patches `libsqlite3-sys` to
`5ae7fdf83085c595fd54f977b3a56ccacabaf16b`; dependency workspace patches are not
automatically inherited by Marmish. Arti `0.47.0`'s directory manager permits
rusqlite `>=0.36,<0.41`, but that compatible range is not Cargo/linkage proof.
“No Marmish MDK fork” does not mean upstream's transitive dependencies contain no
forks. [MDK dependency pins](https://github.com/marmot-protocol/mdk/blob/8abc51befbf71a1ae3bdbb25eb0860c731e75db2/Cargo.toml),
[Arti directory-manager manifest](https://docs.rs/crate/tor-dirmgr/0.47.0/source/Cargo.toml).

The reviewed phase must compile the selected coherent graph on all target
platforms; verify one SQLite native-link owner, actual SQLCipher encryption and
wrong-key refusal; implement real signer/publisher/routing effects; and exchange
authenticated bytes between fresh identities over explicit direct and actual
onion relays. Reopen, duplicate delivery, publication retry, bootstrap failure
and no direct fallback require tests. None of those outcomes is established by
this source audit.
