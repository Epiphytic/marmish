**What I confirmed in the code:**
- **Canonical helper identity.**
  - In the ordinary layout, a named frontend (`marmish`, `marmishd` or `marmish-worker`) validates the actual current executable first.
  - It then requires the helper to equal `parent.join("marmish")` after validation, otherwise it rejects. A symlinked or noncanonical helper therefore fails closed.
  - The worker is validated separately.
  - In the managed layout, every frontend uses the verified `versions/<id>/marmish`, and the manifest file checks are unchanged.
- **Downloaded exception.** The exact `marmish-<version>-<target>` name stays its own helper with an unvalidated worker path. Neither `marmishd` nor the worker gets that exception.
- **Retention.** The helper and worker are fixed once, under the canonical version directory. The managed test checks this through the real `bin/marmish`, `bin/marmishd` and `current/marmish-worker` launchers, and the paths survive `Uninstall`. The ordinary retarget test covers the symlink case that the managed fixture cannot reach.
- **Lifecycle.** The four helper sites (capture and the three verifies) use `marmish`. The `bin/marmishd` selection assertion is unchanged. The lifecycle doc helper wording is updated and consistent.
- **Python.**
  - `daemon_reload` is a separate method, called only from `Qualification.run`, twice: after the first reload and after unlock.
  - Inherited `reload()` and the lifecycle call sites are untouched.
  - Its test pins the argv, environment and 120-second timeout, rejects an identity mismatch, and propagates `Refused`.
  - Keeping it separate from the lifecycle `upgrade_reload` is the right call, given the different timeouts and error maps. I would not add a generic abstraction.
