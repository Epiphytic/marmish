**Verdict: CHANGES_REQUIRED.** The revised `docs/phases/v0.2-phase1-retention.md` (161 lines, sha256 prefix `5729b155a9ddc935`) has two blockers. Both are small, local fixes. I made no edits and ran nothing live; I only read the pinned MDK `8abc51b` source.

## Blockers

**B1 — The five-minute future check permanently drops valid messages when the local clock is slow.**
- The doc says IDs more than five minutes in the future "are terminally refused". It also says that in `clock_behind_floor` the daemon keeps "continuing ingest".
- These two rules contradict each other. If local time is below the floor, then local time plus five minutes is close to or below the floor. Almost every fresh incoming message from peers with correct clocks then counts as "future". It would be refused permanently and acknowledged, so it is lost for good.
- The same happens to new room admissions: they would be definitively rejected and forgotten.
- It is not limited to `clock_behind_floor`. Any local clock more than five minutes slow permanently drops valid, authenticated traffic. Only the local clock is at fault.
- **Fix:** an ID or session past the future allowance is deferred, not refused. It stays unacknowledged, counts as an attempt, and is retried once local time catches up. Permanent refusal is allowed only beyond a much larger bound measured from `max(now, floor)`, for example the seven-day retry horizon. That bound still stops peers from minting IDs that never expire. Add tests for a slow local clock and for receiving while in `clock_behind_floor`.

**B2 — A native group with no journal decision and no pending join is stuck forever.**
- R1 now says a message for a group with "no conversation decision yet, stays unacknowledged". That wording came from my own R1 refinement, and it misses this case.
- `mdk_adapter.rs:995-1004` calls `runtime.create_group` before `journal.accept_conversation`. If `check_group` returns an error, `conversation_peer` mismatches, the journal write fails, or the process crashes in between, a native group is left behind. It has an outstanding Welcome, no journal decision, and no pending `GroupJoined` will ever arrive for it.
- That group's messages would stay unacknowledged for ever and its Welcome would be redelivered with no end. It also has no clear place in the live-room count.
- The first two cases happen without any crash.
- **Fix:**
  - "Awaiting decision" applies only while a pending `GroupJoined` for that group exists.
  - Any other undecided native group is an orphan. Record a definitive rejection, call `forget_group_local` (which also drops its outstanding Welcome), then re-list and acknowledge.
  - Either record a durable create intent before `create_group`, or reconcile on open.
  - Add a test for a failure injected between create and accept.

## R1–R4 status (apart from B1/B2)
- **R1 (joins and admission caps):** resolved. A definitive admission-cap or metadata rejection is followed by forget and acknowledgement. Other faults leave the join undecided.
- **R2 (obligations and collection):** resolved.
  - The predicates match real APIs: `AccountDeviceRuntime::outbound_fanouts_for_group` (by `app_event_id`), `OutboundIntentStorage::list_queued_outbound_intents(group)`, and `outstanding_welcome_deliveries`.
  - Source and binding rows are removed in the same transaction as their parent row, and `trust` with its conversation.
  - Dropping the `rejected` table is correct.
  - The upstream contract supports "forget, re-list, then acknowledge": `forget_group_local` returns `Ok(false)` when the group is already forgotten, and `delete_pending_application_events` says "unknown ids are harmless".
- **R3 (round robin):** resolved. Upstream's `put_pending_application_event` only accepts `MessageReceived` and `GroupJoined`, and the outbox is keyed by `message_id`. So the `(kind, via_welcome | message_id)` key covers every outbox entry and is stable. A frozen cohort with blocked entries counted as attempts gives the stated ⌈N/64⌉ bound.
- **R4 (receipts):** resolved. The receipt digest doesn't use the native message ID, the incoming row and receipt are admitted in one transaction with a precheck on both tables, and acknowledgement happens only after commit. The existing-row binding check means a re-encrypted copy can neither create a second receipt nor bring back expired content.
- **Refinements:** these are in: exact ID encoding, no clamping of new IDs, a floor that never goes down, `+5 min` in the retired-room collection test (covers future-skewed session IDs), and the re-join and stale-replay acceptance tests.

## Non-blocking refinements
1. **Invalidations:** invalidations are never put in the durable outbox; they only arrive through `effects.events`. Change "late invalidations … acknowledged as no-ops" to "applied as no-ops". Also, the current `AppMessageInvalidated` arm in the pending loop can never run.
2. **Global cap shared by rooms:** 512 per room × 64 rooms is well above the 4096 global limit, so eight flooding rooms can still fill the global cap. State this next to the "one full room" claim.
3. **Full `rejected_groups`:** say what a new admission does when this cap is full. For example: reject without a durable row, and accept that a replayed Welcome is evaluated again. That is safe because session freshness is always checked.
4. **Group-wide protection when correlation fails:** together with the round-3 note that the runtime never wakes `RetryableUnavailable` fanouts, this can hold a room's rows indefinitely. Add a diagnostic for it.

No phase or code approval is implied. The code still needs its own independent review.

`★ Insight ─────────────────────────────────────`
- Any check that compares remote timestamps with the local clock should, when it fails, defer the event rather than refuse it permanently. Otherwise a fault in our own clock turns into permanent loss of valid messages.
- Two-step create sequences (native first, journal second) leave orphans whenever the second step can fail. A design that says "wait for a decision" also needs a way to decide for objects that will never get one.
