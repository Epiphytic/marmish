## What the pinned SDK actually does (nostr-sdk `48801bf`)
- **No-op success is real.** `try_connect` (`relay/api/try_connect.rs`) returns `Ok(())` without dialling whenever `!status.can_connect()`. `can_connect` is true only for `Initialized`, `Terminated` and `Sleeping` (`status.rs:131`). So the no-op states are `Pending`, `Connecting`, `Disconnected` and `Connected`. `reserve_try_connect` returning `Ok(false)` gives a second no-op path. Activation at `mdk_adapter.rs:915-931` treats `is_ok()` as connected, so the readiness defect is confirmed.
- **Retries are real dials.** A failed or timed-out dial goes through `_try_connect(timeout, RelayStatus::Terminated)`, and the SDK's own `test_try_connect_to_unreachable_relay` asserts `Terminated` afterwards. So turns two and three really dial, and three 15-second turns plus bootstrap fit the observed 48.9 s and 55.8 s timings.
- **`other` hides the activation labels.** The current foundation allowlist sends `relay_connect`, `add_relay`, `activate` and the Arti labels to `other`, so the report couldn't name any of them. Your proposed label additions are correct.
- **Recovery already checks.** `recover_transport` already confirms with `network_connected()` after its dial.

## Blocking findings
1. **The planned diagnostics miss the most likely failure.** The SDK wraps the connector in its own timer (`time::timeout(Some(timeout), connect_fut)` in `_try_connect`), set to `remaining.min(15 s)`. The connector's own deadline is also 15 s (`handshake_timeout`, `transport.rs:396`) but starts slightly later. So in a 15-second timeout, the SDK timer fires first and drops the connector future. "Emit a category before erasing the native error" never runs, and the only signal left is "SDK result `error`".
   Required changes:
   - **Activation side:** emit a finite SDK error kind by matching the pinned `ErrorKind`, for example `timeout`, `transport`, `state`, `rejected`, `shutdown`, `banned` and `other`. Never format the error.
   - **Connector side:** report a cancelled handshake finitely, for example a drop guard that emits the last phase reached: `slot_wait`, `arti_connect`, `direct_connect`, `tls`, `websocket_handshake`. Alternatively, state explicitly that the existing ordered `begin` events are the evidence, and add a `tls` begin event for the direct route, which currently has none.
   - Without this, a fresh `--debug` run can repeat the same failure and still not show where the 15 seconds went.
2. **Correct the SDK contract in the doc and cover the queued-restart error.**
   - Replace "Pending/Connecting/Disconnected" with the exact rule: `try_connect` dials only from `Initialized`, `Terminated` or `Sleeping`; otherwise it returns `Ok` without dialling.
   - `reserve_try_connect` can return `Err(state)` while setting `Pending` and queuing a restart ("previous connection task is stopping"). The helper must apply the same status wait after an SDK **error** that leaves `Pending` or `Connecting`, not only after `Ok`. Otherwise the next turn is a no-op success.
   - State the two limits of `wait_for_connection`, so the tests model them:
     - It doesn't stop on `Disconnected`, and it reads the status before it subscribes, so it can miss a change and wait out the whole remaining turn. That is bounded and correct, because the helper always rechecks `Connected` afterwards.
     - It returns at once on `Terminated`, `Banned` and `Shutdown`. `Banned` and `Shutdown` then fail fast through `try_connect`'s own errors, so they don't add delay.

## Non-blocking notes
- An elapsed-milliseconds field in debug events would be valuable for attributing time. It is a finite number and can be opt-in. Note that both owners share one process's stderr; activation order (A then B) keeps the events attributable.
- Keep the outer `timeout_at(deadline)` only around `add_relay`, as now. Don't wrap the dial itself.
- The recovery reconnect path also fails a turn with `relay_reconnect` when a no-op success leaves `Pending`. The daemon retries it, so it can stay out of scope; say so in the doc.

## Test obligations
All scripted, using paused time, with no real SDK and no network:
- An SDK `Ok` with `Pending` then `Connecting`: wait within the same turn, no second dial, and success only once `Connected` is observed.
- An SDK `Ok` with `Connected` already set before dialling: no dial.
- An SDK `Err(state)` that leaves `Pending`: wait, then succeed or move to the next turn.
- A wait that ends early on `Terminated`: the next turn really dials.
- Three failed turns give `Transport("relay_connect")`, and deadline truncation gives `Timeout`. Every dial and wait budget is at most `min(original deadline, turn start + 15 s)`, and the original deadline is never reset.
- Neither key-package publication nor `activate_transport` is reached before a `Connected` observation.
- The status, SDK error-kind and connector-phase classifiers map unknown and private-looking inputs to `other` without formatting them.
- The foundation label set includes the five new startup labels, and the JSON keys and shape stay unchanged.
- The Tor/no-direct-fallback and TLS regressions are unchanged.
- `actionlint` on the `--debug` workflow change.
