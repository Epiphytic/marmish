## What I checked

**The hosted evidence matches the diagnosis.** For the second owner, the run shows three attempts, each going `relay_slot waiting` → `arti_connect begin` → `connector_failure timeout` → `relay_startup_error transport` → `terminated`. No `relay_stream connected` ever appears.
- Our own 15 s limit fired first (`transport.rs:396-401`). The SDK's timer would have dropped the future without emitting `connector_failure`. Its `Some(Err)` path (`inner.rs` `_try_connect`) reports a connector error as Transport, which is why the report says `transport` and not `timeout`.
- The first owner's bootstrap events are missing only because the extraction keeps the last 32 entries (the file has exactly 32).

**Current source matches what the design says:**
- `TransportLimits` caps the handshake at 15 s (`transport.rs:67,78-79`).
- One `open_socket` deadline covers the permit wait, the Arti/TCP stream, TLS and WebSocket.
- Each startup turn is limited to 15 s (`mdk_adapter.rs:175`).
- Recovery uses `try_connect_relay` with at most 15 s inside the caller's deadline (`:1961-1974`).
- Activation is 150 s in both the daemon and the foundation check (`daemon.rs:129`, `foundation_check.rs:430/433/526/529`). Ticks are 15 s, and the overall budget is 570/600 s.
- Fixture `native_check` allows 660 s and the client steps allow 12 min, so a 135 s attempt fits without any CI change.

**The pinned SDK contracts (rust-nostr `48801bf`) hold:**
- `AddRelay::new` starts from `RelayOptions::default()`, and the pool passes those options through unchanged (`pool/mod.rs:212`). `ClientBuilder::connect_timeout` only reaches `compose_relay_opts`, which this path never calls. So the design is right that setting `AddRelay::connect_timeout` explicitly is the setting that actually applies.
- `Relay::connect()` → `request_connect` does nothing unless the status is Initialized, Terminated or Sleeping. If the old task is still shutting down, the request is kept and restarted later in `finish_connection_task`.
- The connection task uses `opts.connect_timeout`. With `reconnect(false)`, a failed attempt goes Disconnected → Terminated and the loop exits.
- Shutdown can't lose its wake-up:
  - `terminate()` uses `notify_one`, which stores a permit.
  - The `_try_connect` select races the connect against termination, so dropping the connect future releases our permit.
  - Pool shutdown only sends a signal; it doesn't wait.
  - The owner calls `connector.cancel()` right after `client.shutdown()` and also in `Drop` (`mdk_adapter.rs:876-882`). So even a missed SDK wake-up gets `Transport("shutdown")` quickly.
  - A `connect()` made while the old task is shutting down sets Pending. Shutdown then clears `restart_requested`, so no new connection task starts after shutdown.

**The pinned Arti 0.47.0 claim holds:** `get_or_launch_tunnel` runs before the `begin_stream!` 10 s timeout (`client.rs:1601-1695`), and `tor-hsclient` `state.rs` runs circuit building as a shared spawned task.

**The tests are workable:** `RelayBuilder::new(url).websocket_transport(..).opts(..).build()` is public, `WebSocketSink`/`WebSocketStream` are boxed trait objects, and SDK timers use tokio time, so paused-time tests with a fake, delayed transport can drive the real public `Relay`.

**The publication fence stays safe while a connection is pending.** Resuming at `mdk_adapter.rs:2069-2078` requires `recovery_subscribed`, which is false until all relays are Connected and `activate_transport` has succeeded. Returning either `Ok(false)` or `Err(Transport("relay_reconnect"))` while pending therefore keeps publication paused.

## Non-blocking notes (worth folding in before or while coding)

1. **Name the recovery test seam.** `MdkOwner`'s client always uses the real connector (`transport.rs:302`), so a fake transport can't reach `recover_transport` without a test flag. Pull the per-endpoint decision (observe, schedule or fail) into a private helper that takes an SDK `Relay` (or a small trait, like `StartupRelay`), and test it against a real builder-made `Relay`. For "eventually recovers at >15 s", spell out two separate checks:
   - the helper observes Connected;
   - the owner keeps `recovery_subscribed=false` and publication paused while any endpoint is pending.

2. **Pin down what recovery returns while pending.** Write down which result Pending/Connecting produces. The simplest choice is to keep `Err(Transport("relay_reconnect"))`, which `foundation_check` already retries and which keeps `last_recoverable` meaningful. Banned/Shutdown currently fall into that same retryable label; if "finite failure" is meant to stop retries immediately, give them a label from the terminal list.

3. **The notification forwarder restarts on every pending check.** The pacing block at `:1940-1950` aborts and respawns the forwarder on every turn after 2 s. With a 135 s attempt, that's roughly nine restarts per pending recovery. Consider restarting only when the forwarder has stopped, loss has changed, or a new recovery cycle begins, and keep turns that only observe from restarting it. This is behaviour that already exists, not a regression.

4. **The SDK's limits are silently ignored too.** For the same `AddRelay` reason, the `relay_limits` set on ClientBuilder (`transport.rs:297-306`) never reach these relays, so the SDK uses its default message limits. The connector still enforces the 1 MiB frame cap at WebSocket level (`:473-476`). Since the design already requires explicit per-relay options, also pass `.limits(..)` on `AddRelay`, or drop the dead builder settings, so the configuration isn't misleading.

5. **Equal SDK and connector timeouts hide where the time went.** The SDK `connect_timeout` (135 s) equals the connector's total, and the SDK timer starts first. A full-budget stall will usually end as the SDK's own timeout, with no `connector_failure` event. The same happens at startup whenever the turn is cut short by the activation deadline. That's acceptable; `arti_connect begin` without `relay_stream connected` still shows the phase. If you add recovery diagnostic events, extend the pair table in `scripts/v02-owner-diagnostics.jq` and its test in the same change.

6. **Budget risk on hosted runs.** Four activations (`foundation_check.rs:430-433, 526-529`), each possibly needing an onion rendezvous of 60–135 s after bootstrap, can use up most of the 570 s before join or exchange. If that happens, the right outcome is a reported `deadline` failure, not a wider budget. The design already says to record that honestly.

7. **Startup with several endpoints is sequential,** so one slow Tor endpoint can use the entire activation budget. The design accepts this; keep the "multiple endpoints" startup test asserting that the absolute deadline is never exceeded.

## Test checklist to hold the code review to

- **Tor timing:** a 20 s stream then a short handshake succeeds. A stream over 120 s fails. A fast stream followed by TLS+WS over 15 s in total fails. Direct still fails at 15 s, with the permit wait counted.
- **Cancellation and permits:**
  - cancellation works during the permit wait, the stream phase and the handshake phase;
  - an expired or cancelled attempt frees the permit;
  - the existing test that both halves share one permit (`transport.rs:903`) still passes.
- **Startup:** `turn_end` is `min(original deadline, now + route timeout)`, and time already spent on bootstrap is subtracted. There are at most 3 attempts, and Pending never counts as success.
- **Recovery (real SDK `Relay`):** an attempt spanning several 15 s turns results in exactly one `transport.connect` call. Each turn observes without dialling again. The SDK's 135 s timeout is never restarted. A Terminated relay becomes eligible again only on a later paced turn.
- **Shutdown while a connection is pending:** no Marmish task is left behind, the permit can be acquired within a short wait, and there is no restart after shutdown.
- **Existing suites:** no-direct-fallback, teardown races, notification-loss, journal and trust suites pass, plus fmt and clippy with `-D warnings`.

Live acceptance still requires a fresh full hosted run across all four jobs after the code is approved.
