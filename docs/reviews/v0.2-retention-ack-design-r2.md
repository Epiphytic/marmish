The new consumption and tombstone sections bring three blocking problems.

### Blocking

**N1 (High): a client response can be stuck forever, with no way to consume or discover it.** (§Client response consumption, lines 64–85)

- **How it gets stuck:**
  - `insert_slot` refuses a second Poll while *any* Poll slot exists for the invocation (`command_store.rs:1087-1097`, `command_poll_busy`).
  - The draft makes consumption a precondition for slot retirement, and unconsumed slots are never evicted.
- **Paths to the stuck state:**
  - **(a) Restart discovery.** The CLI writes output and crashes before consuming. After restart there is no way to learn the request `Id`. The three methods need an `Id` or return only cursors. Polling again gets `command_poll_busy` forever.
  - **(b) Stale start cursors.** `command_submit_client` (`command_store.rs:761-806`) does not require the Poll's start cursors to equal the durable `ClientDelivery`. A Poll from the wrong cursors produces a response whose consumption is always a "finite conflict".
  - **(c) Valid but irregular chunks.** "Validate both returned chunks" is undefined, and the engine legitimately returns chunks where `next_cursor - start != bytes.len()`:
    - `poll_outputs` (`command_engine.rs:675-718`) can jump over a gap;
    - `read_output` (`marmish-engine/src/lib.rs:419-423`) returns `g.start` for an open-ended gap, which is *below* the cursor if the cursor is inside that gap. That is a regression.
  - **Result:** in all three cases the invocation's output becomes permanently unreadable, which is not "blocked-but-recoverable".
- **Change:**
  1. In the same transaction, `command_submit_client` rejects a Poll unless its `(stdout_cursor, stderr_cursor)` equal the durable `ClientDelivery`. The error is a finite `command_cursor_stale`.
  2. Add `command_client_unconsumed(&Owner, invocation, max ≤ 64) -> Result<Vec<(Id, Op, Digest)>>`, returning sealed, unconsumed client slots in `created, request_id` order.
  3. Define chunk validity per stream exactly:
     - `start ≤ next_cursor ≤ MAX_CURSOR` and `bytes.len() ≤ next_cursor - start`;
     - if `next_cursor - start > bytes.len()`, the status for that stream must report a gap that overlaps `[start, next_cursor)`.
  4. If a chunk fails that rule (including a regression), consumption marks the slot consumed **without** advancing cursors and emits a finite diagnostic. Do not leave the slot conflicting.
  5. Add tests:
     - crash after write, then rediscovery through the new method;
     - a gap jump;
     - an open-ended-gap regression (cursors must not move);
     - rejection of a stale-cursor Poll at admission.

**N2 (High): early-invalidation tombstones can disable maintenance for the whole account, permanently.** (lines 124–139, 174–175)

- **What happens:**
  - A tombstone is created for *any* unknown `(group, native_id)` in a known command room. It is resolved only by a later Published.
  - Invalidations of IDs that will never be Published leave rows that can never be resolved. Examples are incoming frames that were refused and never bound (`reject_command_frame`, `command_adapter.rs:168-173`) and messages from a peer's losing fork.
  - A room member can therefore fill 256 rows per room, and 16 such rooms fill the 4096 global cap.
  - Line 137 offers "explicit revocation/rotation" as the recovery, but lines 135 and 174–175 say revocation never deletes tombstones. So the recovery described doesn't exist.
  - Once the cap is full, the event is "deferred/unACKed". That leaves an `AppMessageInvalidated` pending, and `maintain_journal` returns early whenever *any* such event is pending (`mdk_adapter.rs:1079-1085`).
  - As a result, all journal maintenance stops for the account, including this amendment's payload TTL and slot retirement. `forget_and_confirm` also fails for that group (`mdk_adapter.rs:1876-1886`).
- **Change:**
  1. Create a tombstone only if, at that moment, either:
     - the unfiltered `storage.list_outbound_fanouts()` holds a fanout with `outcome.message_id == native_id` whose `application_message().app_event_id` is a known command publication in that group; or
     - the current effect set contains a Published for that `(group, message_id)`.

     Upstream records a Published only from a stored fanout (`runtime.rs:5665-5666`, `record_published_application_fanout`), so with neither a binding nor a fanout, no Published can follow. Otherwise apply the invalidation as today and delete the pending event.
  2. Delete a tombstone when its binding is invalidated, or when a fresh unfiltered scan shows no matching fanout and no binding. This gives real GC, bounded by stored fanouts.
  3. Replace the global `maintain_journal` early return with a per-group protection: exclude groups with pending invalidations from retirement and let everything else proceed. Then a deferred invalidation stalls only its own group.
  4. Remove the line 137 claim, or make revocation actually free the room's tombstones.

**N3 (Medium, blocking for boundedness): deferring at a lifetime cap moves unbounded growth into MDK.** (lines 166–178)

- **What happens:** the total of 4096 accepted/revoked rooms is a lifetime cap with no GC. Yet new rooms at capacity get "busy/deferred" admission, and `command_room_capacity` is classified as a projection deferral that keeps the native source (`command_adapter.rs:375-387`). Once the lifetime cap is reached, every later Welcome is kept forever in MDK: the pending `GroupJoined` event plus live group state. That is unbounded upstream storage, contrary to the section's boundedness claim.
- **Change:** keep deferral only for the active-64 cap, which revocation can free. At the 4096 total cap, refuse terminally:
  - `forget_and_confirm` the group and delete its pending join;
  - allocate no metadata row;
  - emit a finite diagnostic, `command_room_lifetime_exhausted`.

  Test that a Welcome after exhaustion leaves no pending event and no live group.

### Medium (non-blocking)

**M1: replaying a response after consumption must change nothing.** `command_project_response` rewrites `slot_state='answered'` and `received_response` even for an identical replay (`command_store.rs:876`). State that once a response has been projected, an identical replay performs no column writes: `local_consumed`, the cursors and the slot state stay as they are. Add a test where a replay arrives after consumption and before retirement.

### Low

- **L1:** line 5 links to `../reviews/v0.2-retention-design-r1.md`. The actual file is `v0.2-retention-ack-design-r1.md`.
- **L2:** repeating a consume after the slot has retired should return a distinct finite `command_response_retired`, and the CLI then reconciles through `command_client_cursors`. Also, "returning the already committed pair" should mean the current durable pair.
- **L3:** `command_client_response` should return the stored response digest as well, so the CLI doesn't depend on re-encoding to compute it.
- **L4:** do one unfiltered fanout scan per page of up to 64 rows, after the batched ACK, rather than one full scan per binding. Also state that a non-live group's binding keeps its marker unset until that group is live again.
