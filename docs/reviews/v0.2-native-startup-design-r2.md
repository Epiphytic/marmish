## My r1 findings
- **B1, diagnostics fixed.**
  - The design now matches the SDK's `ErrorKind` exhaustively and never formats it. Its 14 labels match the pinned enum exactly, which I checked against `nostr-sdk/src/error.rs` at `48801bf`: Protocol, IO, Transport, Database, Gossip, Policy, Timeout, NotFound, Invalid, State, Rejected, Unsupported, LimitExceeded and Other.
  - It states that the SDK's 15-second timer can cancel the connector before the connector reports anything. In that case the ordered phase "begin" events show the last phase reached.
  - It adds the missing direct-connect and TLS begin events, so every blocking phase leaves a visible marker even when it is cancelled.
  - Skipping a drop guard is fine under that reasoning.
- **B2, SDK contract fixed.**
  - The doc now has the exact rule for which statuses actually dial.
  - A `State` error that sets `Pending` and queues a restart now gets the same status wait as a no-op success.
  - It documents how the wait API behaves: it doesn't stop on `Disconnected`, it can miss a change because it reads the status before subscribing, it returns early on `Terminated` or `Sleeping`, and `Banned` or `Shutdown` refuse fast. The final `Connected` recheck is mandatory.

The fixed contracts still hold:
- three turns, each bounded by `min(original deadline, turn start + 15 s)`, with no reset;
- every endpoint must be seen `Connected` before the original deadline and before key-package publication or subscriptions;
- no extra dials, and no outer timeout that cancels a dial;
- no route, TLS or production recovery changes;
- the foundation JSON keeps its shape, with five labels added;
- `--debug` output goes only to job stderr.

The test list now includes all my r1 obligations: queued restart, no dial when already `Connected`, a real dial in the next turn after an early `Terminated`, and fast refusal on `Banned`/`Shutdown`.
