## Round-2 items: resolved

**R2, recovery barrier.** The barrier is sound against the actual code.
- **Only `maintain` deletes jobs.** Tombstone deletion is called only from `maintain` (`lib.rs:540,560`). Its only other route, `cleanup::acquire`, belongs to the migration/cleanup guard, and the doc forbids using that.
- **Status and cancel never collect.**
  - `status` goes through `authorized_job` → `reconcile_step`, which never deletes.
  - `cancel` uses `job_for`, which returns NotFound only when the owner-keyed lookup misses (`store.rs:766,1541`).
  - So the barrier can safely let status, poll and cancel continue.
- **The selected operation can safely run its own maintenance.** The `maintain(128)` that `issue_execute_token` or `submit` runs before admission (`lib.rs:196,236`) can only collect *other* jobs. All of those must already be recorded as `engine_known=true`, so the worst case is an honest `result_expired`, never a resubmit.
- **Ambiguous results keep the barrier closed.** Checking status after submit returns either success or error, and holding the barrier while the outcome is unclear, covers the case where `await_worker` returns an error after a durable admit.

**Startup reset (lines 359–364, 397–403).** The doc's description is accurate.
- `create_frontend` deletes all tokens (`store.rs:566`). For each job with state<3 (at most 128) it clears the generation, endpoint, records, accepted and delivered counts. It adds a gap only if pending record bytes existed, and it rewrites a declared EOF to `Some(0)` (`store.rs:567–592`). It does no tombstone GC.
- In the worker, a generation mismatch sets a failure (Gap) **without closing the pipe** (`worker.rs:395–400, 438–444`). Revocation therefore never sends the child an implicit EOF. Choosing to cancel instead of replaying is the correct, conservative response.

**R1, stdin.**
- Gating EOF on `delivered == len` while health is neither Gap nor Uncertain is correct.
- Once the leader exits, input ticking stops (`worker.rs:609`). A naturally exited child therefore leaves `delivered < len` with healthy input, and that maps cleanly to `stdin_unconsumed`.

## Nonblocking

1. **Nondeterministic exit code for commands that ignore stdin.**
   - If a child exits between the worker's exit check and its pipe write, the write fails with EPIPE and input health becomes Gap.
   - The feeder may then cancel a job that is already finishing. Its `code 0` plus `cancel_requested=true` cannot be proven natural, so the result becomes `input_failed` (exit 255).
   - Example: `printf x | marmish peer -- /usr/bin/true` will occasionally exit 255.
   - This is honest, but tests and the docs should expect it.
2. **Status for refused rows is unspecified.** The `admission` enum (accepted/dispatching/engine) has no refused state. The doc should say that a status query on a durably refused row returns the stored refusal error code.
3. **Withholding EOF does not fully prevent partial execution.** Interpreters that run input line by line can still act on a partly delivered program before the cancel lands. A single record of at most 16 KiB written to a fresh pipe makes partial delivery rare, but the "truncated program" wording should say this.

Once F1 is corrected, I'd expect this to pass. That would be a doc-only change; the protocol requires a fresh independent review to confirm it.
