# Installed workflow design review r1

Reviewer: Claude Opus 5.5 auto. Session `a3fb6a8b-af9b-4889-bc17-2fd22fb24468`.

**Verdict: CHANGES_REQUIRED**

I read all three docs, the actual `v02-release.yml`, and the `installed_{check,prepare,records,process}.rs` contracts. I didn't edit anything or run any network command. The direction is sound: Rust is authoritative, Node only moves artifacts, the candidate run is selected explicitly, and the doc doesn't claim release qualification. Ten gaps should be fixed in the design before the workflow is written.

### Blocking

1. **Python is on the product runtime PATH.** `installed_process.rs:30` sets `PATH=/usr/bin:/bin:/usr/sbin:/sbin`. Hosted Ubuntu 24.04 and macOS 15 both have `/usr/bin/python3`, so the amendment's "Python, uv, Cargo, rustc must not be available" rule is broken. The existing quickstart check already uses a curated utilities directory as PATH (`marmish_native_quickstart_check.py:118`). **Fix:** the driver builds a private utilities directory with only the installer's tools (`curl uname id mktemp chmod mkdir rm rmdir mv cat wc tr awk sh` plus any hash tool) and checks that `python3`, `uv`, `cargo`, `rustc` and `node` can't be found. Separately, `LANG=C.UTF-8` doesn't exist on macOS, so set the locale per platform.

2. **The macOS `/tmp` symlink will fail prepare.** `/tmp` is a symlink to `/private/tmp`. `installed_prepare.rs:329-333` canonicalizes the launcher and then checks `starts_with(workspace/install/versions)`. With a `/tmp/...` workspace that check always fails. **Fix:** require the workspace path to already be canonical (refuse it if canonicalizing changes it), and have the workflow pass `/private/tmp/<mktemp>` on macOS. Prepare creates the leaf directory itself, so the workflow must not create it first.

3. **The context binds too little.** `Context` (`installed_records.rs:25`) has no:
   - candidate run ID or attempt (`run_id` is the current installed run);
   - bootstrap SHA-256. `IdentityReady.bootstrap_sha256` is only checked to be hex, so each job could install from a different bootstrap;
   - per-target SHA-256 for the `installed-check` and `installed-fixture` binaries;
   - run nonce. The amendment says resolve "generates the fresh run nonce once and pins it in the candidate binding".

   **Fix:** add all four to the context. Have identity-ready, prepare and every matrix job compare their bootstrap and tool digests to it before running anything. Define "tooling metadata" as a small candidate-built record listing name, target, commit and sha256 for each tool, and pin its digest.

4. **It's unclear which tree the tooling digest covers.** The workflow YAML and the local action come from the dispatched master HEAD (`github.sha`). The tools are built from `source_commit`. As written, "checked-out source and common tooling digest must match" doesn't say which commit is hashed. **Fix:** compute the `git ls-tree` digest at both `github.sha` and `source_commit` and require them to be equal (or require `github.sha == source_commit`). Include `.github/workflows/<this>.yml`, `tools/v02-actions/{package.json,package-lock.json,*.mjs,action.yml}`, and the Rust paths. Note that the Rust tool really depends on the whole `marmish-native` crate plus `Cargo.lock`; the commit binding through the manifest covers that, not the tree digest.

5. **The deadlines contradict the amendment's uptime.** The context expires 40 minutes after creation, and the identity barrier is up to 15 minutes. The amendment allows the matrix server up to 30 minutes of uptime, so it could run to minute 45, past the run-mode deadline. **Fix:** state that server uptime = min(30 min, context expiry − launch − cleanup reserve), and fail before launch if that is shorter than ready + workload + Finish needs.

6. **The cancellation semantics are unrealistic.** When GitHub cancels a job or hits `timeout-minutes`, the runner sends SIGINT, then SIGTERM about 7.5 seconds later, then SIGKILL. The 10-minute "cleanup reserve on SIGINT/SIGTERM" can never happen under runner-initiated cancellation. Also, "first step + 55" is later than GitHub's real timeout, because the job clock starts at runner setup. **Fix:**
   - Only the supervisor's own internal deadline may trigger cleanup.
   - Set the internal job deadline a few minutes below the real limit (for example first step + 52 with `timeout-minutes: 55`). If you keep the input named "actual job deadline", say how it is derived.
   - State that a runner cancellation or timeout always means red, cleanup unproven, with the ephemeral VM as the only teardown.

### Required clarifications

7. **Trust anchors for resolve.** The candidate run's `head_sha` is master HEAD at dispatch time, not `source_commit`. The REST API doesn't return dispatch inputs. Write down what resolve actually checks:
   - `GET /runs/{id}/attempts/{n}` has `conclusion == success`;
   - `path` is `.github/workflows/v02-release.yml`, `event` is `workflow_dispatch`, `head_branch` is `master`, and `head_repository` is this repository;
   - the source binding comes only from `manifest.commit` (already enforced at `installed_check.rs:95`) plus the tooling record.
   - Re-running only failed jobs (in either workflow) is unsupported and fails closed because artifact names include the attempt. Say so.

8. **Injection and input handling.** Pass the relay, run ID, attempt and `source_commit` to steps only through `env:`. Never interpolate `${{ inputs.* }}` inside `run:`. Check the formats in shell before any API URL is built. Run `npm ci --ignore-scripts` from the lockfile, with no token in the environment. Downloaded tools lose their executable bit, so verify the digest first, then `chmod 0500`, then execute.

9. **API budget and concurrency.** 200 calls per role is about 600 per run, and the 1000/hour GitHub token limit is shared across the whole repository. Two overlapping runs would exceed it. **Fix:** add `concurrency: {group: marmish-v02-installed, cancel-in-progress: false}`, and count the resolve, rollup and `download-artifact` calls in the budget.

10. **Rollup scope and diagnostics.**
    - The rollup must take the matrix `needs.*.result` values as an input and refuse to call itself green if any is not `success`.
    - It must run a rollup binary whose digest is pinned in the context.
    - It must require all 9 directed cells and exactly 3 admissions under ceiling 4 per server.
    - Its JSON should say `scope: "installed-matrix"` and list the gates still pending: auto-exit, benchmark, recovery, policy, keychain, asset publication and HTTPS. It must not have any qualified or release boolean.
    - The workflow doc's "failure diagnostics" upload conflicts with the supervisor doc's "no additional supervisor artifacts". Give diagnostics a separate name namespace that the rollup ignores, and limit them to the four reviewed records.

### Lower priority

- **Barrier check in Rust:** `IdentityReady::validate` lets `identity_ready_at` run up to expiry + 120 seconds. Enforce the 15-minute barrier (`created_at + 900`) in Rust as well, not only in the Node deadline.
- **Queue delay:** a runner that waits more than 15 minutes in the queue (more likely on ARM64 or macOS) misses the exchange barrier. That is correctly a failure, but the doc should label it an infrastructure red, not a product result.
- **Tooling build checks:** the doc already notes 25c5340 can't qualify. Add one requirement: candidate packaging re-hashes the copied product binaries after the separate tooling build and checks they didn't change.

Once these are in the design, I'd expect it to be approvable. Item 1 and the context fields in item 3 also need code changes, not just doc changes.
