## Round-1 blockers rechecked

**B1 (probe observation and the unowned probe publication): resolved.**
- The single armed slot sits inside the normal `project_command_message`. It fills only after `decode_command_event` has authenticated the frame (sender, leaf, direction, binding, app-event checks) and only when `project_response` returns exactly `Invalid("command_not_found")`.
- That is the real contract today. A response with no client slot reaches exactly that error and then `reject_command_frame`.
- Normal `tick`, `drain`, `receive_one` and the deletion of unmatched responses stay unchanged. Buffered responses arriving through `drain()` are covered, and no concurrent tick can race the observation.
- The capacity of one, no overwriting, arm/take/clear, being destroyed at stop, and having no IPC exposure satisfy "no forged context, no global hook."
- The probe can be built from existing pure builders: `command_wire::encode_request`, `request_digest`, and `mdk_adapter::prepare_command_publication`, which runs `validate_command_publication` without any journal row.
- Retaining the unowned outbound publication matches the actual ACK rule in `project_application_publications`. The interfaces clause also requires "unknown ownership" handling and "actual fanout absence rather than ACK success alone." The design claims neither an ACK nor absence, which is consistent.

**B2 (server refusal contract): resolved as a pinned acceptance contract.**
- It specifies a durable source/request/terminal refusal tied to the existing invocation, with the original Submit's payload, digest and slots unchanged.
- The response carries the probe's ID, the conflicting request's SHA256, op=Submit, `Err(InvocationConflict)` and `detail=null`.
- Replay is idempotent, and the existing request-ID conflict rule still applies.
- The refusal adds nothing to the counts `begin_cleanup` checks (active, uncertain, worker_running, worker_unknown).
- The existing test that asserts `is_err()` will be updated.
- This matches the phase-2 clauses "digest conflicts" and "identical retry gives one admission… never automatic rerun."

**B3 (root identity and guard after reopen): resolved.**
- After reopen, both original directory receipts (profile root and `commands`) are compared against fresh `O_NOFOLLOW` opens. Nothing is captured again, and a mismatch makes the run red with state kept.
- Cancellation and cleanup use only the reopened owner and its new lease. The protected unlink uses the original receipt under the new owner's `CleanupGuard`.

**B4 (Pair lifecycle and the pending stop): resolved.**
- `server_stop: Option<PendingStop>` plus the closed `Running | Stopping | Stopped | Reopened` states, each with its own invariant.
- Reopen is allowed only after a completed stop with all three flags set, and never from Stopping.
- A failed open goes to Stopped and keeps state, with no engine removal.
- If the owner was acquired but activation failed, that owner is stopped through `stop_owned`.
- The old server is never stopped a second time, and the two-owner `turn` is not used while stopped.

**B5 (time budget): resolved.**
- The stage budgets add up to 321 s (20+20+30+30+150+20+20+1+30), under the script's 360 s fail-safe. All are clipped to the original exercise deadline.
- The recovery case runs first.
- If the probe times out, the release gate is written or the job is cancelled, so the 30 s cleanup reserve is preserved.

## Non-blocking notes for the implementation (none of these block design approval)

1. **The retained probe shares the room with the next three cases.** In `command_runtime.rs` around lines 263–273, the Prepared sweep does not mark a missing-fanout publication as uncertain while *any* queued intent exists for the group. If the probe stays as a queued intent rather than a frozen fanout, it can hide uncertainty classification for later client publications in the same room. This has no effect in a healthy run, but:
   - record whether the probe is a fanout or a queued intent, and
   - say that the three later cases don't rely on that classification.

   The fanout scan in `maintain_journal` (around 1096–1110) will also protect that room's group and the probe's publication key from pruning on the client. That is expected for disposable state.
2. **Name the exact APIs behind `probe_native_retained`:**
   - `storage.list_outbound_fanouts()` (or `runtime.outbound_fanouts_for_group`), matched by `application_message().app_event_id`;
   - `storage.list_queued_outbound_intents(&group)`, matched by the exact `SendIntent::AppMessage` payload.

   Also say whether `false` is reported as-is or makes the run red. The design currently requires only a truthful value.
3. **Recovery observation:** tie "actual recovery_caught_up" to the owner's real state (`recovery == false` after EOSE catch-up), not to the diagnostic event string.
4. **Probe ordering:**
   - Arm the slot before sending.
   - Send exactly `encode_request(armed_request)` via `prepare_command_publication`.
   - Have the slot also check `op == Submit`; the design lists it in the server contract but not in the slot's match.

   The design calls the builder a "signed builder," but the builder itself doesn't sign. MLS sender authentication does that, so drop the word.
5. **Unbounded keeper finish:** finishing a `PendingStop` after the observer expires has no deadline, as the owner-stop contract intends. The report should still finalize red without waiting on it, if that's feasible in the implementation.

No implementation, test or live acceptance is implied. The successful live run of the first three cases is outside this review.
