## Nonblocking notes for whoever implements it

1. **There is a second fixed budget constant.** Cleanup in `mac_account` has its own `600 − elapsed` limit (`marmish_native_keychain_check.py:424`), separate from the `570` at `:493`. L267–269 only names the 570. The rule "cleanup fits inside the supplied cap" still covers it, but the implementation must change both constants. Otherwise cleanup can run up to 60s into the shared 300s reserve.
2. **"Binding" applies to Linux only.** On macOS, stages 3–4 must finish with at least 1140s left for stage 5. That is tighter than the 1200s needed at submission, so L207 calling the submission check "binding" is only true on Linux. Every check refuses and goes red when time runs short, so this is wording only.
3. **Stages 5 and 6 get very little time.** Because each stage has a minimum entry time, stage 5 effectively has at most 120s and stage 6 at most 180s on both platforms. Stage 6 has a lot to do in that time. The design records measured durations; adjust the minimums from those measurements.
4. **The launch +1800s deadline is redundant.** It always comes after `runtime_end − 300`, so it never applies. That's harmless because every operation is already limited to `runtime_end − 300`.
