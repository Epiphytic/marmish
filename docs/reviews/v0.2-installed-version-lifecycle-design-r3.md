## Remaining blocker

**N1 — "Exactly 11" conflicts with the supervisor's own staging.**
- The existing supervisor adds two entries of its own to `input-pins.json`: its own script and `marmish_native_quickstart_check.py`. The bootstrap and every asset are added on top (`marmish_native_keychain_check.py:465-480`).
- The inner side enforces `len(values) <= 16` over that whole pin map (L375).
- So an extended run would produce 13 pins: 2 scripts + bootstrap + 10 assets.
- L264/266 says "Stage exactly11 files… Any extra staging must be rejected". If that check is applied to the pin map, a legitimate run is refused. This is the same failure class as B3.
- **Fix:** say "exactly 11 product/bootstrap inputs, plus the existing 2 pinned supervisor scripts = 13 pins (≤16)". Name both scripts in the recorded inputs and the harness digest. L105 currently names only `marmish_native_keychain_check.py`.

## Nonblockers

1. **Supervisor budget:**
   - The outer supervisor currently ignores any caller budget. It uses a fixed `570 − elapsed` and allows a 60s account setup (L443, L493–495). Account cleanup then runs after the inner budget.
   - L261–262 requires supervisor cleanup to fit inside the supplied cap. The design should say plainly that the fixed 570 is replaced by the supplied cap, with the inner budget = cap − setup − cleanup margin.
   - With a 60s cap, the 60s account setup alone uses the whole budget, so the "minimum 60s entry" will always end red.
2. **The provider budget isn't reserved on macOS:**
   - The provider stage needs 360s to start, and stage 6 starts with as little as 360s.
   - So a macOS run can pass stages 1–6 and still be certain to go red for lack of time, losing the provider evidence.
   - Consider macOS-specific entry minimums for stages 5 and 6 that include a realistic provider allowance.
3. **Stage 6 minimum looks too low:** it needs only 360s (60s of usable time) even though it initializes a profile with a completed command, installs C, snapshots, restores B and reopens. Stage 5 is lighter but needs 420s. Base both on measured durations.
4. **Stage 1–2 threshold is misleading:** the binding check is the 1200s required at submission (L210). Entering stage 1 with exactly 1200s guarantees a refusal later. Either say the submission check is the one that binds, or raise the stage 1 entry minimum.
5. **Step 4 wording (L163–166):**
   - "Stop A only using its retained Child or exact A versioned CLI" comes after "Restart through B", so it reads as a later step rather than a rule for the earlier stop. Move it.
   - "Original first A server launch uptime deadline" still has no definition.
6. **Bootstrap PATH (L82–83):** the bootstrap also requires `uname id mktemp chmod mkdir rm rmdir mv cat wc tr` (`install-native.sh:41`). Say the utility-only PATH covers that full list, not just curl, awk and the checksum tool.
7. **Offline sidecar test (optional):** cover both the accepting preflight path and the incompatible-journal path, using a `cfg(test)` support list rather than a product hook. That shows the sidecar behaviour when MDK is opened but the journal is rejected.
