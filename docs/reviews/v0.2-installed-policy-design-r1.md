## Blockers

**B1. The zero-grant server and the client have no engine, so the sealed-guard cleanup can't run on them.**
- `CommandConfig::engine_policy` returns `None` when the granted clients plus historical principals are empty (`command_config.rs:188-190`). No engine is started (`command_runtime.rs:77-88`), so no `<profile>/commands` directory is created. `installed_prepare.rs:203` already asserts that directory is absent after a no-grant setup.
- Because of that, `EngineTree::capture_path` fails. `CommandPrepareCleanup` reaches `begin_cleanup` and fails with `command_engine_missing` (`command_service.rs:483-486`), which `installed_cleanup::prepare` turns into `bad()`. `CommandCleanupStatus` can never report `engine_quiesced`, so no fence exists.
- This breaks three parts of the design: the zero-grant guards on "both original live children", the zero-grant "complete fresh-fence cleanup scan", and the guards for the client in both phases (it is `--role client --no-grants`).
- **Fix:** define a strict no-engine proof instead. Check with a nofollow lookup that `<profile>/commands` is absent before launch, after the observation and after the joined stop. Read every page of `CommandEvidence` and require it to be empty; this still works because the command service exists (`command_local.rs:171-174`). Record the actual cleanup status (`open`, all counts zero) as a diagnostic only, never as a fence. Then do the ordinary joined stop and validate its stop report. Create the server engine only in the granted phase: check it doesn't exist before start, then capture it after ready.

**B2. Refused rows actually show `worker_state` = `Unknown`, not `Exited`.**
- New rows start as `Unknown` (`Facts::new`, `command_store.rs:540-555`).
- During cleanup, the final observation of a refused row finds nothing in the engine. That path sets the worker to `Unknown` (`command_store.rs:3662-3664`).
- Cleanup accepts refused-before-engine rows whatever their worker state (`command_service.rs:799-813`), and the `worker_unknown` count excludes refused rows (`:3630`).
- As written, the `Refused` disposition can never pass. Require exactly what the code produces: `engine_admitted` `Some(0)`, `refusal` `CommandDenied`, `outcome` `None`, worker `Unknown`, `authority_valid` true, `observed_seq` at or past the fence, and both streams at `{0, false, 0, None}`.
- Add an offline test that sends a real `CommandDenied` admission through cleanup to quiesced and reads the projected row. The existing pattern is `real_engine_cleanup_refreshes_refusal_before_consuming_guard` (`command_service.rs:1458`).

**B3. The server's submit digest is not the handle's digest, and the harness can't reconstruct it.**
- Server evidence `submit_sha256` is `wire::submit_digest(raw group, binding, submit)` (`command_store.rs:747`, projected at `:3566`).
- `CommandHandle.submit_sha256` is `request_digest` of the whole canonical request, including the request ID (`command_client.rs:55-77`).
- No local API exposes the raw group ID; `CommandPrepare` returns only the session and local account. So "exact planned Submit digest" on server rows can't be met or rebuilt independently.
- **Fix:** bind each denial through the authenticated response's `request_sha256`, compared with a request digest the harness rebuilds itself. Bind server rows by (principal, invocation) to session. Record the server `submit_sha256` as an observed value: valid hex, different for each row, and all five rows sharing one `group_sha256`. The only other route is a new read-only projection, which the parent hasn't authorized.
- The same mismatch appears in the existing matrix (`installed_matrix.rs:823-829`), benchmark (`installed_benchmark.rs:610`) and autoexit (`:1206` vs `:1527`). If so, their all-row equality checks would reject genuine rows. The parent should confirm this before the design relies on "reuse existing cleanup".

**B4. A missing `refusal` field won't be rejected without an explicit mechanism.**
- serde's derive reads a missing `Option<T>` field as `None`, even with `deny_unknown_fields`.
- A plain `refusal: Option<ErrorCode>` field therefore quietly accepts old-format rows. That contradicts "missing field is an error", and the planned missing-field test would fail.
- **Fix:** name the mechanism, e.g. a `deserialize_with` required-but-nullable helper or a closed non-`Option` enum. Apply it in both `installed_cleanup::Evidence` and autoexit's `EvidenceRow`.

**B5. The deadline budget leaves out the second setup and the zero-grant stops.**
- The 1800 s requirement before the first daemon covers 1725 s of allocated work, leaving 75 s of slack.
- The second setup run (`--update --grant`, the canonical read-modify-write and revalidation) has no time allocated.
- The four ordinary stops (two daemons in each phase) aren't assigned to a budget line.
- **Fix:** split setup600 explicitly or add a re-grant slice. State that zero-grant cleanup120 includes both joined stops, and give each stop its own reserve. Recompute both thresholds, all capped by the original Context.

## Non-blockers
1. Preparation creates the server with role `server` (`installed_prepare.rs:160`), not "both". Fix the wording, or specify and pin the role change.
2. With no grants, the client CLI probably fails waiting for the room before any Submit is frozen or published. "Attempted" should mean the CLI ran and returned an exact finite category. Don't claim a Submit crossed Marmot.
3. The retry only proves local idempotency. The handle is computed from the request bytes (`for_submit`, `command_local.rs:409-420`), so matching handles proves nothing by itself. Make it a lost-reply retry (disconnect before reading the response). Prove it from the stores: exactly one `CommandInvocations` entry whose stored handle matches, and one server row. State that remote duplicate-delivery suppression is left to the protocol gate, as the conflict section already does.
4. For the conflict, pin a fresh request ID with changed bytes, which gives `command_invocation_conflict` (`command_store.rs:874-876`, returned via `LocalResult::Failure`). Reusing the same ID with changed bytes fails earlier in the slot check with a different category.
5. The engine requires a canonical executable path (`command_engine.rs:550-562`). Require the root to equal its own canonical path, as autoexit does at `:1786`.
6. `cancel_fixture` allows at most 4 rows (`installed_cleanup.rs:367`), but the policy run leaves 5. Specify what the failure path does.
7. Consuming a refused response may send a Finish request. Record its finite disposition, and don't count Finish slots as ledger rows.
8. There's no existing `CommandPrepare`/`CommandSubmit` controller in the installed harnesses; only autoexit's response and consume helpers exist. `installed_cleanup::request` rejects responses that carry a `command` result, so the new file needs a narrow typed helper.
9. The four denials can use 360 of the 600 s policy budget. State the time caps for execution, retry, resume and conflict.
10. The hidden `command-evidence` CLI output gains a field. That's acceptable given there's no stable-format requirement.
11. Outside this design: autoexit requires the stream SHA-256 to be present (`:1540-1541`), but the projection always sets it to `None` (`command_store.rs:3495-3510`). Autoexit also captures engine trees for no-grant clients (`:1966`), which has the same problem as B1. Pass both to the owners.

## Confirmed sound
- **Policy semantics:** all five paths come out as the design states. The service-level denial calls the engine's own checker (`command_config.rs:227-261` → `policy.rs:249`), and refusal happens before the engine is involved (`command_service.rs:249-262`; the test at `:1684-1688` asserts no engine).
- **Additive rules:** each key entry adds a layer that must allow, any deny wins, and order doesn't matter (`policy.rs:64-71`, `:181-195`). Key principals must already be granted, so writing the policy after the grant is correct. The only metacharacters are `*` and `\`.
- **Budget accounting:** refusals neither reserve nor consume admission budget (`command_store.rs:2085-2088`), and `max-commands` requires grants (`command_config.rs:290-293`).
- **Projection details:** cleanup refreshes `observed_seq` on refused rows. `ErrorCode` is a closed enum. The daemon serializes the evidence page directly, so the new field is forwarded unchanged. Absent streams really are `closed:false`.
