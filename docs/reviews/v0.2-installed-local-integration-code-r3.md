**Verdict: APPROVED.** I found no blockers in these root common changes. Hosted qualification stays pending.

**Rollup uses `validate_record` plus an independent `complete == true` check (`installed_local.rs:~92-125`).**
- **Qualification is unchanged.** `benchmark::validate` is `validate_record` followed by rejecting `!complete` (`installed_benchmark.rs:936-942`). The autoexit validator has the same shape (`installed_autoexit.rs:427-436`). The rollup now runs `validate_record`, then requires `record["complete"] == true` on the serialized value (`:111-112`). That is exactly the old strictness for passing records.
- **Missing keys fail closed.** If the serialized record has no boolean `complete` key, the check reads it as not complete.
- **Failed records are kept.** Both validators still check the Context, the identity and the digest, the installation and tooling pins, and the structural invariants. A genuine failed record therefore keeps its stage, category and bound details in `platform_results`. It never sets `complete` to true.
- **Invalid records stay red.** A record that fails binding or structure still gets the `{"role", "complete": false, "category": "missing_or_invalid"}` placeholder. Missing, extra or wrong-named files fail the exact-set check. A job result other than `success` fails it too. Exclusive output writes and the nonzero return on any failure are unchanged.
- **The run path is unchanged.** `local::run` still calls `autoexit::validate` (complete required) and `benchmark::run`, so nothing there weakens.
- **New regression test.** `genuine_failed_benchmark_survives_rollup_without_qualification` builds a record with `benchmark::tests::failed_record()`. It asserts the rollup returns an error, `complete` is false, the failed record is preserved verbatim, and the Markdown shows `Warm n=0` and `unqualified | null | null`. The other two roles are missing, so the rollup is red either way. The test therefore proves preservation and non-qualification, not that `complete=false` alone causes the red.

**Matrix `configure_value` now requires `command_policy == {"version":1}` (`installed_matrix.rs:~266`).**
- The check runs before the configuration write. The test adds `command_policy.defaults = {"deny_exec":["**"]}` and expects rejection.
- The check is strict, so a setup that omits `command_policy` entirely is also rejected. That is the intended fail-closed behaviour. The "actual setup" test, which I did not run, is what proves the real installer emits this value.
- The other matrix edits are the same visibility, `require_cohort("matrix")` and `cancel_fixture(..., 3, ...)` changes I reviewed before. They are unchanged.
