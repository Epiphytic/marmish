# Explicit SRV raw-query completed-code review, round 1

Actual Claude Code Opus5.5 `--permission-mode auto`, session `f52faf86-bd14-45c1-839a-e22d55add382`. Exact result follows. Reviewed source preceded the test-only Message.metadata compile correction; no production difference.

**Verdict: CHANGES_REQUIRED.** There is one blocker, and it's test-only. The production logic in `command_srv.rs` (SHA-256 `63e085d1…14e7d`, which I confirmed) matches the approved design. No test credit given; the author's focused tests haven't been reported yet.

**Reviewer:** Claude Opus 5.5 (`claude-opus-5-5`), the same Claude Code session as the design review, worktree `marmish-v02`. Everything was read-only: no edits, Cargo, tests, network or process scans.

**What I inspected:** all 537 lines of the current `command_srv.rs`, the 501-line original from the design review, the `crates/marmish-native/Cargo.toml` diff, and the pinned 0.26.3 sources (`NameServerPool::lookup/send/try_send`, `NameServer::send_inner`, `DnsError::from_response`, the UDP client's question check and retransmit floor, `DnsRequestOptions`, `Query`'s derives).

**What I verified**
1. **No queries to names taken from a response.** `Resolver` and `CachingClient` are gone. Each caller-supplied owner gets exactly one `pool.lookup(Query::query(name, SRV), …)`, and nothing in the pool path reads CNAME or SRV data. The only repeat traffic is Hickory's UDP retransmit of the same owner query. That happens after the 333 ms `DEFAULT_RETRY_FLOOR`, so up to about two resends within the 1 s pool timeout.
2. **Response validation:**
   - `response_code != NoError` is rejected. This catches NXDOMAIN with answers, which `from_response` otherwise lets through. Other error codes, and empty NoError responses, already fail in the library.
   - `truncation` is rejected (backstop only; the pool already retries over TCP or errors).
   - The question must be exactly `[query]`. `Query` derives `PartialEq` and name comparison ignores case, so name, type SRV and class IN are all checked, as is "exactly one question". This check really matters on the TCP path, which doesn't verify the question.
   - Class: the pool rejects foreign-class records in every section, and `answers()` requires IN.
   - The authority and additional sections are ignored, as designed.
3. **Deadline.** Each lookup has one `timeout_at` on the original deadline, there's a check before every owner, and nothing renews it. The pool's own budget is 1 s.
4. **Options.** `options()` is trimmed to the fields the pool reads, and `case_randomization` is set to false at the `ResolverOpts` level, which is where the pool actually takes it from. Request options are built from `Default` and then set from `ResolverOpts`. DNSSEC, DoH and DoT are not compiled in.
5. **Teardown.** The pool and its connections are created and dropped inside `block_on`, then the runtime is dropped before returning. Early returns via `?` still leave the async block cleanly. `TlsConfig` and stream-end (`None`) errors fail closed.
6. **No new dependency from this correction.** The only `crates/marmish-native/Cargo.toml` change is the `hickory-resolver` line, which predates this correction. `futures-util` and tokio's timer were already present.

**Blocker**
- **The approved acceptance list includes "wrong question … fails", and no test covers it.** The new `raw_pool_never_queries_response_directed_names` corpus covers CNAME+SRV succeeding, CNAME-only, a `.onion` target, a numeric target, and NXDOMAIN with answers. It has no wrong-question case. Over UDP, Hickory silently drops a forged question and waits for the timeout, so a UDP fixture can't reach the app-level check. The smallest fix is to move the `response_code`/`truncation`/`queries` check into a pure helper and unit-test it with:
  - a wrong name
  - a wrong type
  - a wrong class
  - zero questions or two questions
  - truncation set
  - non-NoError with answers

  Optionally, also add one UDP case with a wrong-question reply that must fail and send no second datagram.

**Useful notes (not blocking)**
- The 100 ms no-second-datagram window is safe from false positives, because the reply goes out immediately and the retransmit floor is 333 ms. It would also catch a follow-up query, since that would be sent immediately.
- Fixtures only use UDP (`NameServerConfig::udp`), while production uses UDP and TCP. TCP fallback after truncation is still unexercised. A test would be welcome but isn't required.
- The point from the design review still stands: in practice, a silent first server uses up the 1 s pool budget, so servers 2 and 3 are only tried after fast errors.
- `command_cli.rs` is out of scope. I didn't review the test-only `assert_eq` change and give it no credit here.
