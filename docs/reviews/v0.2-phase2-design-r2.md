## Remaining blocking issues

**R1. Inline stdin: queuing EOF early can feed the child truncated input as if it were complete.**
- The engine closes the pipe on a declared EOF even after bytes were lost (`marmish-engine/src/store.rs:373-381`).
- Records expire after their deadline (`store.rs:382-389`). A write error or EPIPE also becomes a `Gap` (`worker.rs:453-466`).
- The draft queues EOF "only after every byte accepted" (line 308). In the engine, accepted means queued, not delivered.
- Failure case: the job waits more than 60 s for a worker start slot or engine turn, the record expires, and the child then reads EOF with missing input. With a granted interpreter like `python3 -`, that runs a partial or empty script.
- **Fix:**
  - Queue the inline stdin as a single record of at most 16 KiB. That is the engine's `RAW_BYTES` limit (`marmish-core/src/frame.rs:10`), so the 4096-byte chunking isn't needed.
  - Queue EOF only once `delivered == len`.
  - If `Gap` or `Uncertain` appears before EOF was queued, request cancellation. The child never saw EOF, so it never treated a truncated stream as complete.
  - If the outcome is a natural exit (not caused by our cancel) with stdin unconsumed, for example EPIPE from `true` or `head -c1`, pass the remote exit code through with a `stdin_unconsumed` category. Don't report `input_failed` 255 or cancel.
  - Drop the separate 120 s stall deadline; the engine's 60 s record deadline already covers it.

**R2. Maintenance protection: the hazard is real, but the proposed API is the wrong shape.**
- Collection deletes terminal records once they reach tombstone age with nothing retained (`store.rs:1403-1406`, `1444-1452`).
- `issue_execute_token` and `submit` run `maintain(128)` implicitly when quota is exhausted (`lib.rs:193-199`, `236-240`).
- Failure case: a crash leaves a ledger row in `dispatching`. Later, before it is reconciled, another submit triggers quota maintenance and deletes the job's tombstone. Recovery then sees an authoritative NotFound and runs the command again.
- The draft's alternative, supplying a key set before every pass that is persisted "before admission can return", is underspecified. It needs an engine schema change, can wedge on the 10000-record quota, and still has to be in place before `Engine::open`.
- **Preferred fix (no engine change):** a recovery barrier on the single engine thread.
  - Run no maintenance-capable operation (`issue_execute_token`, `submit`, `maintain`) while any ledger row is `dispatching`.
  - Record each submit's outcome, success or error, before the next operation.
  - Once the ledger has recorded that the engine job exists, a later NotFound means "collected" and never triggers a resubmit.
  - If status keeps failing for a dispatching row, block new admissions (fail closed); status, poll and cancel continue.
- **If you keep the engine extension anyway:** make it a per-job `retain_until_released` flag set inside the admission transaction, plus an idempotent `release(owner, invocation)` and a bounded enumerator to clean up leaked flags. Document the quota impact.

**R3. The exact codec is still a "freeze later" item (line 194).**
- The design must itself list:
  - each op's result schema, including field names for submit, status, input and output;
  - the finite list of error codes;
  - the exact byte layout of the digest's "versioned length-prefixed encoding".
- The draft explicitly defers these; your instructions treat deferred items as not implementation-ready.

**R4. Capacity lockout, with no per-principal bound.**
- Ledger rows can't be collected until their timestamp falls below the 7-day floor. With 10000 records, that caps an identity at about 1,430 commands per day.
- One granted peer spamming `/usr/bin/true` can lock every other peer out for up to 7 days.
- The ledger is owned by the service, so counting retained rows and non-terminal rows per principal is cheap. "Engine provides global quotas only" (line 331) no longer justifies deferring.
- **Fix:** specify a ledger row cap and per-principal shares for both retained rows and active jobs. Alternatively, shorten the command horizon to the client retry window and state the throughput limit explicitly.

**R5. The engine construction condition.**
- "Construct lazily once server configuration has grants" (line 88) conflicts with recovering and locally cancelling historical jobs after the last grant is removed, or after a switch to client-only.
- **Fix:**
  - Construct the engine whenever the union of current grants and historical principals is non-empty, regardless of role. Role and current grants gate network admission only.
  - Cap the union at 4096 (`admission.rs:12`), with a defined failure mode.
  - Require the engine `tombstone_retention` to be no longer than the command horizon, so ledger-derived history always covers engine records.

## Nonblocking corrections and simplifications

- **Worker binary:** line 98 says the worker goes "alongside … the vault helper". There is no vault-helper binary: both bins dispatch `_vault-helper` internally (`marmish-native/src/cli.rs:157`). Consider a thin `marmish-worker` binary inside `marmish-native` that sets `RLIMIT_CORE=0` like `marmish-engine/src/bin/marmish-worker.rs` and calls `worker_main`. Then native tests get `CARGO_BIN_EXE_marmish-worker` and packaging follows the native package.
- **Digest wording:** reword the digest-match claim as an invariant. An engine job exists only for a ledger row that reached `dispatching`, and the engine key `(principal, server, uid, invocation)` is unique.
- **Submit error after admission:** `submit` can return an error after durable admission, because `await_worker` returns `WorkerUnavailable` or `RecoveryUncertain` after `admit` commits (`lib.rs:256-262`, `403-426`). Name this case in the fault tests.
- **Poll inconsistency:** "2 outstanding nonoverlapping polls" contradicts "never speculates past next_cursor". Specify one outstanding poll, or one per stream.
- **Poll gap metadata:** the engine keeps at most 4 gaps per stream (`spool.rs:40-44`). The 16-range bound and the `gap_summary_truncated` flag are dead code. The response size is then provably under 32 KiB, so drop the "reduce or `response_too_large`" alternative.
- **TTY stdin:** if stdin is a terminal, default to no stdin or require an explicit choice. Otherwise `marmish host -- /bin/ls` hangs until Ctrl-D.
- **Quota filtering:** the journal's `capacity()` and the 64-room cap must be filtered by purpose, so command traffic doesn't count against foundation's 512/4096 limits.
