## The main decision: keep v1 wire and streaming stdin?

My recommendation is not to treat v1 preservation as a product constraint.

- **Compatibility evidence is weak.** The recorded legacy probe outcome is `unverified-prerequisite` (`docs/validation/v0.2/native-foundation.md:193`). No trusted legacy fixture exists, and no golden `marmish/1` vectors exist (`tests/fixtures/` has none). So "preserve v1" currently buys an interop claim nobody can test.
- **v1 rooms would fail native admission anyway.** Legacy rooms carry a 1-day `message_retention` component (`tools/marmish_rpc.py:296-317`). The native `check_group` forbids `GROUP_MESSAGE_RETENTION` (`mdk_adapter.rs:803-827`). The draft keeps the v1 room name and also applies Phase 1's component policy, which contradicts itself.
- **Streaming stdin causes real product failures.**
  - The child's stdin is always a pipe (`launcher.rs:1116`). With no EOF it blocks indefinitely (`store.rs:1185`).
  - The plan deliberately doesn't synthesize EOF on disconnect. So a detached `cat` or `sort`, or a client that dies mid-upload, holds an active-job slot until someone cancels it.
  - Each record expires after at most 60 s (`fresh_ms`). A slow or reconnecting client turns stdin into a permanent `Gap`.
  - `begin_input` silently discards undelivered bytes.
- **Round trips are expensive.** hello → token → submit → begin_input → eof → poll is at least 4–5 MLS round trips before the first output byte. Over Arti that is several seconds.

**Proposed simpler native protocol (fresh discriminator, e.g. `marmish-command/1`):**
- **One-round-trip submit:** `submit{invocation, argv, stdin:{none | inline ≤~16KiB | staged len+sha256}}`. stdin is bound into the invocation digest.
- **Server-internal token:** the service calls `issue_execute_token` and `submit` together in one engine turn. Drop `hello`, challenges and client-held tokens. MLS already authenticates sender and group; the engine's unique `(principal, server, uid, invocation)` key (`store.rs:524`) gives at-most-one admission.
- **Timestamp-bound invocation IDs** using the foundation/2 floor logic, with a separate command ledger. This closes the draft's open "bounded invocation-ID guarantee after tombstone collection" by design, without a later protocol version.
- **Immutable stdin is fed locally.**
  - Staged chunks are idempotent by offset+hash.
  - Launch waits until the declared length and hash are complete.
  - The service then feeds the engine locally, so there are no network deadlines on records.
  - `none` sends local EOF immediately.
  - This needs no engine change: one internal generation with local `write_stdin`/`stdin_eof`.
- **Keep v1 as optional legacy test material only**, outside the Phase 2 gates, unless a compatible probe is actually recorded.

If you still want v1, the blocking items below still apply. The "Initial CLI supports finite stdin streaming" path then needs the disconnect/hang contract spelled out.

## Blocking findings

1. **Engine calls block; no placement is defined.**
   - `submit` sleeps-polls up to 8 s in `await_worker` (`lib.rs:403-426`). It also runs fsyncs, orphan scans and possibly `maintain(128)`.
   - SQLite `busy_timeout` is 2 s. `Engine::open` reconciles up to 128 jobs.
   - The daemon actor runs SQLCipher/MDK inline on one async loop (`daemon.rs:141-166`). Its only `spawn_blocking` is in `open`.
   - The design must specify:
     - a dedicated engine OS thread owning `Engine`, with a bounded queue;
     - per-call deadlines;
     - what a timed-out call means: the outcome is unknown, and recovery is by a status lookup;
     - that convergence ticks never wait on the engine.

2. **Grant reload and local cancel don't fit the engine API.**
   - `EnginePolicy` is fixed at open. `allowed_principals` must be non-empty (`admission.rs:11-13`). Every `CommandPolicy.keys` principal must be in it (`policy.rs:39-46`).
   - So "server role with zero grants" means no engine can be opened, and reload means drop-and-reopen with blocking reconciliation.
   - "Local administration may cancel" a revoked peer's job is impossible: `cancel` needs an `AuthorizedContext`, which `authorize` refuses for removed principals (`admission.rs:63-67`).
   - Pick one of these:
     - keep historical principals in the engine list and enforce current grants in the service;
     - add a small engine admin-cancel/status API.
   - Also state the reopen sequence and that workers survive it.

3. **Absolute-path and no-PATH guarantees are not enforced by the engine.**
   - `require_canonical_exec` only runs when a policy layer is effective (`policy.rs:146-158`, `lib.rs:224-226`).
   - Otherwise a bare `argv0` resolves through the child's `PATH=/usr/bin:/bin` (`launcher.rs:918-926`).
   - The service must reject non-absolute `argv0` unconditionally and force canonical spelling. One way is an implicit defaults layer of `allow_exec:["/**"]`, or an engine flag.
   - Note the cost of the symlink-rejection choice: on merged-usr Linux, `/bin/ls` and `/usr/bin/python3` are denied. The error must report the canonical path.

4. **Recovery with fresh tokens is mis-specified.**
   - `existing()` returns `InvalidToken` when the job exists but the token hash differs (`store.rs:1558`). Tokens die on every engine reopen, because the epoch and in-memory `deadlines` reset (`lib.rs:219-232`).
   - The safe rule is: status first; `NotFound` lets the client get a new token and reuse the same invocation; found means the job exists. (Legacy `marmish_app.py:504-524` does exactly this.)
   - But `status` doesn't compare the request digest. The service must keep its own digest, or the engine needs `find_existing(owner, id, request)` that ignores the token. Without one of these, a conflicting retry after restart reports a stale "existing" job.

5. **Cross-store crash ordering lacks a schema and cache rules.** Four stores are involved: MDK db, journal, engine db and the client record.
   - Define which store holds client invocation records. The journal is the natural choice: commit the invocation record and its outgoing request in one transaction.
   - Define which responses are cached versus transient (`busy`, `worker_unavailable`, `stale_challenge`), and the cache eviction rule.
   - Suggested simplification: request/status/poll responses are derived state. ACK the native event only after the engine effect is durable, and let the client's idempotent retry recompute the reply. You then don't need a durable "response obligation" table or foundation's "never fresh ciphertext" rule for responses. Responses can be regenerated safely; foundation messages can't.
   - If you keep a cache under v1, its lifetime can equal the challenge lifetime, which bounds it naturally.

6. **Output transport: sizing and goodput are unspecified.**
   - Legacy polls read 4096 bytes per stream.
   - The engine allows 16 KiB per stream, but two base64 streams at 16 KiB (~43.7 KB) exceed the 32768-byte envelope.
   - At about 8 KiB per Arti round trip, an 8 MiB stream takes tens of minutes.
   - Freeze the per-message raw budget (≈22 KiB combined), pipelining (K outstanding polls by cursor), and an expected-goodput calculation. Otherwise the Phase 4 latency/goodput gates are locked into a pull design that can't meet them.

7. **Worker executable placement is missing.**
   - The engine requires an explicit, absolute, trusted `marmish-worker` path: owned by root or the user, with no group/world-writable ancestors (`launcher.rs:892-917`). No env or PATH fallback exists.
   - Release binaries need a rule. A multi-call `marmish _worker` via `worker_main` (`lib.rs:614`) mirrors `_vault-helper`. Specify how it behaves in user-writable install dirs.

8. **Per-principal fair share doesn't exist.**
   - The engine has a global `active_jobs` only, and no per-principal count or list.
   - "Default 4 within 32" needs either durable service-side accounting that agrees with engine state after a crash, or an engine count query.

9. **There is no configuration system to "reload atomically".**
   - Everything today is CLI flags (`cli.rs:34-55`, `daemon::Config`). Nothing parses roles, aliases, grants, `npub`/bech32 or `npub@relay`.
   - Specify:
     - config file location and format;
     - the reload trigger (IPC method or SIGHUP);
     - the validation-then-swap sequence, which ties into B2.

10. **The IPC contract for the CLI is missing.**
    - IPC has 4 methods, a 64 KiB frame, a 15 s I/O timeout and a 150 s owner wait.
    - `wait`/`output` streaming needs defined long-poll or paging methods, plus behaviour when IPC returns `busy`.

11. **The endpoint identity must be fixed.**
    - Legacy uses `sha256(MDK group_id bytes)` as the endpoint.
    - Native keeps both the MLS `group_id` and `transport_group_id` (`mdk_adapter.rs:188,209`).
    - State "the MLS group id, never the routing id" now. Don't defer it to vectors that don't exist.

12. **The CLI exit-code mapping must be exact.** Signal, `unknown_launch`/`lost`, gaps and transport failures need fixed codes. Suggestion: remote exit 0–255 passes through; signal N → 128+N; local/transport failure → 255; uncertain → a distinct reserved code, with a stable stderr category.

## Factual corrections

- **Token lifetime:** the engine default is 60 s (`model.rs:75`, range 1–300 s). The prototype set 120 s explicitly. The draft's "existing … 120s lifetime" is wrong; state the explicit value.
- **Worker environment:** it exists and is now inspected. The child gets exactly `HOME, USER, LOGNAME, PATH=/usr/bin:/bin, LANG=C`, with cwd = policy cwd or home, umask 077, `setsid`, CLOEXEC sweep and no rlimits beyond core = 0. Freeze it rather than leaving it open. Note that there is no `TMPDIR`, and on macOS `/opt/homebrew/bin` is not on PATH.
- **No migration code:** `Engine::open` (file key mode) and `prepare_native_migration` exist. Since you accept fresh formats, use only `open_with_master` and leave the migration path out.
- **Room cap:** the 64-active-conversation cap and the `marmish/v2/` prefix check are hardcoded in `check_group` and shared with foundation. Command rooms need a stated cap and a purpose selector.

## Nonblocking

- Reuse the journal's outgoing state machine with a separate purpose column and quota, rather than a parallel outbox.
- With an 8 MiB per-stream cap, any larger output always yields a `Limit` gap, so the command can never report success. Document it in the CLI text.
- The unbounded allocation in upstream `list_pending_application_events` is honestly disclosed. Keep the stress test.
- Reusing the engine is the right call. Its admission, launch-claim, `unknown_launch`/`lost`, spool and tombstone code is substantial and tested. The cost is integration (B1–B4, B7, B8), not rewriting.
