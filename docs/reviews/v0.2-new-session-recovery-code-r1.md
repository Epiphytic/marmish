## Blocker

**B1. The rollup can report a record as passed even when the schema2 proofs are missing.**
- **Where:** `installed_local.rs:128-130` checks a cohort by calling `recovery::validate_record` and then reading `result.is_complete()`, which only returns `self.complete` (`installed_recovery.rs:111`). The new schema2 checks that a passing record must have are only in `validate()` (`installed_recovery.rs:1111-1114`):
  - `server_group_sha256` must be present on both samples;
  - `default_reuse` must be present;
  - every sample must have passed.
- **Example:** a record with `complete:true` and `failure:null` passes the rollup's check if either:
  - `samples[1].server_group_sha256` is `null`, or
  - `samples[1]` never submitted, so `default_reuse` is `null`.

  Your own negatives 1 and 7 in `new_session_schema_and_independent_bindings_are_required` only fail because that test calls `validate()`. On the rollup path, case 7 is accepted.
- **Why it blocks:** the design says "Required schema2 proof booleans and values must be checked by rollup, with negatives for … missing reuse proof". The job's `job_result == "success"` check reduces the risk in practice but doesn't satisfy that requirement. The gap existed in schema1 for the old fields, and schema2 widens it.
- **Fix (inside `installed_recovery.rs`):** in `validate_record`, add an `if r.complete { … }` block that enforces all of `validate`'s pass conditions. Then add negatives that call `validate_record` with `complete:true` and a null group, a null `default_reuse`, or an unpassed sample.

## Requirements that are met
- **First invocation survives restart:** the stop/reopen and marker path is unchanged.
- **Probe placement:** the default-reuse probe runs after `bind(samples[0])` and the marker check, and before the second Submit (`:893-895`).
- **Probe request:** it sends `CommandPrepare{fresh: None}`, and `skip_serializing_if` means `fresh` is actually left off the wire.
- **Probe limits:** at most 15 requests, each started at least 1 s after the previous response. The deadline is `min(work deadline, now+15s)`, the probe never retries, and a timeout goes to `Failure::DefaultReuse`. Only `LocalBusy` counts as "not ready yet", which matches the production CLI loop.
- **Ready check:** `Ready` must carry the exact sample0 session and the client account.
- **Counts:** client invocations must be exactly one entry equal to the sample0 handle, before and after the probe. Server rows must be byte-identical before and after (canonical comparison), which is stricter than comparing counts.
- **`--new-session` on the second command:** the flag comes after the global options and before the npub destination and the `--` separator. It is only added for index 1.
- **Session checks:** `bind()` and `validate_record` were both flipped to require different sessions.
- **Server rows:** exactly two, read-only, with `ExecutedFixture` disposition and `authority_valid`. Each row's principal must equal the client account, its session must equal its own handle's session, and its `submit_sha256` must equal the client-cached group-bound digest, never the plain handle digest. The two native `group_sha256` values must differ.
- **No invented fields:** no transport or authority DTO was added.
- **Failure handling:** if the probe fails, `expected` still holds only sample0 and `pending_binding` is false, so cleanup prepares and cancels exactly as before. If the second bind sees the same session, it sets `unknown` and skips protected cleanup, which is conservative and red. No deadline was added or extended: the probe and second sample stay inside launch+1350 and before cleanup at 1710.

## Non-blocking
1. The `submit_args` test only asserts that the flag comes before `--`. Also assert it comes before the npub destination, which is the actual requirement.
2. The 15 s window also covers the after-probe reads. If `Ready` arrives near 15 s, those reads can time out and turn the cohort red without anything actually being wrong. This fails safe, but consider a small reserve for the reads.
3. In `validate_record`, `default_reuse.is_some()` should also require `samples[0].server_group_sha256.is_some()`, since the work path always binds that first.
4. `markdown_summary` doesn't show the reuse proof, either sample's session, or the server groups. Reviewers of the rollup can't see the new evidence.
5. Test gaps:
   - nothing exercises the probe's scheduling (request count, spacing, clipping); consider pulling it out as a pure function;
   - `bind_server_rows` has no negatives for a wrong row-0 principal, a missing second row, or `group_submit_sha256: None`;
   - the fixtures give both samples the same group-submit digest (`"3"×64`), which can't happen across two groups. Consider requiring the two digests to differ too.
6. The before/after reads in `invocation_count` and `recovery_rows` don't watch for SIGTERM. They're bounded by the 15 s deadline, so this is only a latency issue.
