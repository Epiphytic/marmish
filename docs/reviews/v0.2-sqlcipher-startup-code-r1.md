**APPROVED.** I found no blockers. I only read code: no edits, no Cargo runs, no processes, no network, no keychain.

**Upstream contract, checked against the pinned code** (libsqlite3-sys `5ae7fdf8…`, rusqlite 0.40.1)
- `build.rs:153` keeps `-DSQLITE_EXTRA_INIT=sqlcipher_extra_init`, and no compiler hooks changed.
- In `sqlite3_initialize`, `isInit = 1` is set and `pInitMutex` is released before `SQLITE_EXTRA_INIT(0)` runs. That hook's return code is what the function returns. So any caller that arrives later and sees `isInit` takes the fast path and returns OK, even while the hook is still running on another thread. This matches the race the design describes.
- rusqlite 0.40.1's `ensure_safe_sqlite_threading_mode` calls `sqlite3_mutex_alloc`, which triggers SQLite's automatic initialization. Nothing in rusqlite wraps that in a `Once`, so the barrier you added is needed.
- `initialize_storage`: `OnceLock::get_or_init` makes every concurrent caller wait until the first call, including the extra-init hook, has returned. Any non-OK result is stored permanently and maps to `StorageFailure`. This is the right choice: if the hook fails after `isInit` is set, calling SQLite again would wrongly return OK. There's no shutdown/reset and no retry.

**Every SQLite opener now crosses the barrier first**
- I searched all of `crates/**` for `Connection::open*`, `open_in_memory`, `sqlite3_open`, `rusqlite::ffi`, `SqliteAccountStorage::` and `storage_sqlite`. Every hit is gated before its first SQLite call:
  - `cipher::open`, which covers state, spool, `Engine::open` and `worker_main`
  - `Journal::open`
  - `native_preflight::open`, gated after the filesystem-only early returns
  - `MdkOwner::open`, gated before both `open_encrypted` calls
  - `bootstrap_inner`, gated on the `needs_tor` branch before `TorClient::builder`
  - the raw test opens in cipher, spool, encrypted_storage, faults and native_preflight
- The other modules (`store.rs`, `spool.rs`, `command_store.rs`, `command_rooms.rs`, `launcher/tests.rs`) only use connections passed to them; none opens one.
- The only `TorClient` construction is the one at `transport.rs:373`.

**Non-blocking findings**
1. `concurrent_storage.rs:76`: if `concurrent_storage_child` is ever renamed, `--exact` would match zero tests and the child would exit successfully, so the regression would pass without testing anything. A cheap fix is to have the child write a sentinel, such as a file or stdout marker, and have the parent assert it's there.
2. The r3 review suggested explicitly asserting that nothing in the child calls SQLite before `initialize_storage`. This is still covered only by a code comment. That's acceptable, since the child does no SQLite work before the barrier, but it isn't enforced.
3. `transport.rs:363`: the barrier can briefly block inside async code. That's acceptable because initialization is fast and happens once.
4. As the design says, any future dependency bump must repeat the Cargo.lock reverse-dependency check, and any new direct SQLite user must call `initialize_storage` first.

The local baseline result doesn't prove the original bug reproduces, because the race only fails some of the time. A fresh three-platform candidate run is still required after review.
