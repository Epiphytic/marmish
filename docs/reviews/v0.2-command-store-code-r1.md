## Blocking

**B1. A client slot that is revoked before it is consumed never retires, so global and per-principal slot capacity leaks permanently.**
- **Where:** `command_store.rs:2388`, together with `:941`, `:1059`, `:1079`, `:1112`, `:2742–2755` and `:2757`.
- **The skip:** `command_maintain` skips every client row unless it is both projected and consumed: `if client && (!projected || !consumed) { continue; }`.
- **How a slot gets stuck:** authority is revoked through one of these paths:
  - room revocation: `command_rooms.rs:126` calls `revoke_group_in`;
  - `record_invalidation` → `invalidate_publication` on the client's own request publication;
  - any other call to `revoke_record`.

  The slot then has `authority_valid=0`. If it has no response yet, it also gets `slot_state='suppressed'`.
- **Why nothing can clear it:**
  - `command_client_response`, `command_client_unconsumed` and `command_consume_response` all require valid authority, so the local client can no longer read or consume the response.
  - If the response never arrived, `projected` stays 0 forever.
  - The only write to `local_consumed=1` is `:1171`, which is unreachable once authority is revoked.
  - The only `DELETE FROM command_requests` is `:2463`, which runs after the skip at `:2388`.
- **Failure path:**
  - Each revoked room or invalidated request holds its rows indefinitely.
  - `insert_slot` (`:1404–1411`) counts every row against the 256 global and 64 per-principal slot limits, so new client requests eventually fail permanently with `command_slot_capacity`.
  - The invocation can never be deleted while it still has requests, so retained capacity leaks too.
  - `expire_payloads` (`:2564`) also keeps the payload, because the row counts as `client=1 AND local_consumed=0`.
- **Design conflict:** `interfaces.md:509–511` says a revocation-Suppressed slot "retires once incoming sources are actually ACKed", and that otherwise the publication ACK rules apply. Neither rule requires local consumption. The "never age-evicted" rule (`retention-and-ack.md:108`) protects output the client can still read; a revoked slot's output can never be delivered.
- **Fix direction:** in maintain, treat `authority_valid=0` (or a suppressed client slot) as exempt from the consumed and projected requirement, while still applying the source, publication, quarantine and protection gates. Add a test that revokes a client slot before it is projected and one that revokes it after projection, then proves both retire after real ACKs.
- **Not tested:** none of the inline tests revokes a client slot and then runs maintenance. The two revocation tests (`:3766`, `:4176`) cover server-side and feeder paths only.

## Nonblocking
1. **A transient error leaves a permanent refusal on client records** (`:916–918`). An `Err` response to a client Status, Poll or Cancel (for example `recovery_uncertain`, busy or `result_expired`) sets `record.refusal`, and a later `Ok` never clears it. As a result `active()` (`:322`) stays false for that invocation. I found no other code that reads it, so this only affects active-count and retention accounting. It is worth making the refusal Submit-only.
2. **A third native binding fails the whole batch** (`:2632`). When a third native binding arrives for the same app event, `record_published` returns `Err(command_outgoing_capacity)` instead of quarantining it. The caller (`command_runtime.rs:531–532`) passes the error up, so the native update is replayed indefinitely and blocks progress for the account. The design calls for quarantining conflicts. This involves both the store and the integration layer.
3. **Quarantined bindings hold their slot and publication forever.** This matches the design, but it is another long-lived drain on capacity. Operators should get a diagnostic or recovery path.
4. **No upper bound on payload retention.** `command_configure` does not cap `payload_retention` at 7 days. That is harmless given the replay floor, but it differs from the documented bound.
5. **Incoming ACKs are not counted.** `command_record_native_acks` does not check the changed-row count for incoming source keys, so an unknown key is silently accepted. Outgoing keys error correctly when unknown.
6. **The retention design doc header still says "DRAFT round 4"**, so the approval status recorded in the file is out of date.

## Verified correct
- **Three failed reads.**
  - The third failure is answered in the same transaction: `failed_attempts=min(3,n+1)`, and at 3 a `RecoveryUncertain` response is written.
  - `command_pending` filters out slots with `failed_attempts>=3`, so a fourth operation cannot be registered.
  - Stale or wrong observations count as failures.
  - `load_request` refuses rows with more than 3 failed attempts.
- **Durable association and read recovery.**
  - `check_request_operation` pairs Status↔Observe, Cancel↔Cancel and Submit↔Dispatch (exact match).
  - Poll requires identical cursor and `max_bytes`.
  - Dispatch is excluded from read recovery.
  - A refusal for an unknown read takes a slot but allocates no invocation.
- **Replay and duplicates.**
  - `check_slot` returns a digest conflict before any write.
  - An identical projected replay only attaches the source and writes no columns, so revision, consumption and cursors are unchanged (tested).
- **Native batches.** Pass 1 handles Queued and Published, and pass 2 handles terminal Failed and Invalidated, so a terminal invalidation cannot be resurrected.
- **Evidence and quarantine.**
  - Evidence is persisted in the same transaction as `published`, before an ACK is possible.
  - ACKs need `quarantined=0` and stored evidence.
  - A conflicting binding is quarantined, its publication is marked uncertain and it is not ACKed.
- **Early invalidation.**
  - It requires proof from the same group and an existing publication.
  - Caps are 256 tombstones per room and 4096 globally.
  - A tombstone is consumed when the binding is published.
  - The `invalidation_groups` skip runs before any deletion.
- **Payload expiry.** The fair 256-row cursor wraps, and it skips payload-required, protected, pending-submit and unconsumed-client rows.
- **Client consumption.**
  - It is cursor-safe.
  - A repeated consume returns the current pair.
  - An invalid cursor marks the slot consumed without advancing it and returns `command_output_cursor_invalid` after commit.
  - A retired slot returns `command_response_retired`.
- **Cleanup freshness.** `command_cleanup_fresh` requires a fence-current observation with valid authority, no uncertainty, and either a pre-engine refusal or an Exited status.
- **Strict DTO against pinned MDK `8abc51b`.**
  - `PublishedApplicationMessage` (`runtime.rs:6955`) has `group_id`, `app_event_id: String`, `message_id`, `source_epoch: EpochId(u64)`, `retention: AppMessageRetentionDecision{retention_seconds: u64, expires_at: Option<u64>}` and `authority: Option<AppMessageAuthority{source_context: [u8;32], moderation_grant: bool}>`.
  - The evidence stores only the non-key fields, with `deny_unknown_fields`.
  - Decoding enforces the 4096-byte limit and requires canonical re-encoding, which rejects duplicate keys, extra whitespace and omitted `null` fields.
  - The group and message ids are rebuilt from the binding rather than taken from the stored JSON.
