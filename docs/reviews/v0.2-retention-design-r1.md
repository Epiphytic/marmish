# Retention amendment review: CHANGES_REQUIRED

I reviewed `docs/phases/v0.2-phase1-retention.md` (sha256 prefix `468a011e68167514`, untracked) as a design only. I made no edits, ran nothing live, and treated the current N2 code as irrelevant. I checked it against the current `journal.rs`, `mdk_adapter.rs` and pinned MDK `8abc51b`. That includes `storage-sqlite/src/cross/wipe.rs` and `marmot-session` `forget_group_local`.

The direction is right: IDs carry their own timestamp, a monotone persisted floor, payload expiry kept separate from the replay horizon, and caps that bound the working set. Several of the points you asked about are stated as goals but have no mechanism yet. Code written from the current text would very likely repeat N2-style bugs.

## Upstream facts that shape the design

- **Forget is not a terminal tombstone.** `forget_group_local` deletes the group's pending application events, outstanding Welcome deliveries (`app_pending_welcome_delivery`), group state and Welcomes. It then inserts `locally_forgotten_groups(awaiting_welcome=1)`, which is explicitly built to allow re-joining via a later Welcome. Session-freshness admission is therefore the only lasting barrier once Marmish deletes its rejection row. The amendment is correct to require that check, and it has to apply to every GroupJoined.
- **Forget also clears pending events.** Once forget completes, the "acknowledge its pending event" step is idempotent. The amendment should say forget plus a re-listed empty pending set for that group is the completion proof. A boolean the adapter writes itself is not enough.
- **The `rejected` table is never read.** Nothing makes a decision from it today, so dropping it costs nothing.

## Blockers to fix in the amendment before N2 code starts

### R1. Continuing past blocked events can reject legitimate messages too early

The amendment says to continue processing other events past a blocked one. As written, that can reject and ACK a message before its room is decided:
- If a `GroupJoined` stays pending (storage fault or blocked capacity), the `MessageReceived` events for the same group fall through to `ensure_trusted`.
- That returns `Mdk("unaccepted_group")`, and the message is terminally rejected and ACKed (`mdk_adapter.rs` `project_message`).

**Required rule:** a message whose group has an unresolved pending `GroupJoined`, or no conversation decision yet, stays unacknowledged. It must never be terminally rejected. Also state that admission caps and metadata caps produce a definitive rejection (forget, then ACK), never a blocked join. That keeps the dependency short-lived.

### R2. Retained native obligations and per-table collection need exact predicates

"Supported terminal transition" and "remove related rows consistently" are too vague to implement. Write them as rules:

- **Outgoing row with state `unsubmitted`:**
  - If its ID is below the floor, mark it `expired` and never submit it.
  - This covers receipt intents left over from long downtime.
- **Outgoing row with state `prepared`:**
  - Retain it while `outbound_fanouts_for_group` lists its `app_event_id`, or while a `queued_bindings` intent is still in `list_queued_outbound_intents`.
  - Otherwise it becomes `uncertain`, as in the restart rule.
- **Outgoing rows that are `uncertain`, `published`, `received`, `invalidated` or `expired`:** collectable once the ID is below the floor and the payload has expired.
- **Outstanding Welcome deliveries:** never collectable while a live room still owes one.
- **Row groups that must be collected together, in one transaction:**
  - `incoming_sources` with their `incoming` row;
  - `outgoing_sources` with their `outgoing` row;
  - `queued_bindings` with their outgoing row, after the native queue no longer holds the intent;
  - `trust` with the `conversations` row, at retirement.
- **AppMessageInvalidated for collected rows:** a late invalidation that maps to nothing is ACKed as a no-op. Say explicitly that invalidations arriving after collection are not reflected.
- **Rejected messages:** delete the per-message `rejected` table. Content rejection depends only on the content, and upstream deduplicates native IDs, so ACKing without a tombstone is safe. Say so explicitly, because undecodable content has no ID to compare with the floor.

### R3. The "no starvation" goal needs a concrete mechanism

"Avoid starving later events" is not enforceable. Specify:
- joins first, but at most 64 attempts per turn in total;
- an in-memory round-robin cursor over the stable key, `(kind, via_welcome | message_id)`;
- blocked entries are skipped and still count as attempts;
- the cursor wraps around;
- every pending event is attempted within ⌈N/64⌉ turns.

Retained publications, `drive_retained` and `submit_unsubmitted` must run every turn, whatever the result of the pending batch. Remove the fatal 4096 pending-length check.

### R4. Receipt identity and receipt atomicity

- **Receipt IDs must not depend on the native message ID.** Today the receipt token is group + native `message_id`. A peer re-encrypting the same application message therefore produces a second receipt ID, a second outgoing row and a second send. Define the receipt suffix as a domain-separated digest over: group, session, original sender, recipient, original application ID and `payload_sha256`. The original timestamp is the prefix.
- **Project and prepare the receipt in one transaction.** Do the incoming projection and the receipt intent together, with a single capacity pre-check covering both tables. Prefer this over a "reserved receipt capacity" pool, which is harder to reason about. The source message is ACKed only after that transaction commits.

## Refinements (should be in the amendment, not blocking)

1. **Clock behind the floor.** Define a finite daemon state, for example `clock_behind_floor`. In that state:
   - new sends and new admissions are refused with a public error;
   - native obligations and ingest keep running;
   - the floor is never lowered automatically.

   Document the recovery: wait for the clock, or explicitly re-create the profile. Own IDs must use the current time and fail if it is below the floor. They must never be clamped up to the floor.
2. **Future-skew policy.** A 60 s allowance with terminal rejection means honest peers with skewed clocks lose messages for good. Either allow about 5 minutes, or keep future-dated events pending (unacknowledged) up to a bounded limit and reject terminally after that.
3. **Exact ID encoding.**
   - The 12-hex-character prefix is big-endian, zero-padded, lowercase seconds, and parsing rejects anything else.
   - The floor applies only to IDs not yet seen. If a row with that ID still exists (long payload retention), the existing row's result is returned.
   - Session IDs in the room name use the same format, and live rooms are never re-checked for freshness.
4. **Fairness and throughput.**
   - With 4096 rows retained for at least 7 days (peers can timestamp IDs up to 60 s ahead), the ceiling is about 290 two-way exchanges per day per account. One allowed peer can use it all up.
   - Add per-conversation quotas so one room can't block others.
   - State the throughput ceiling in the amendment.
5. **Live-room slot leak.** A room we created whose peer never joins (for example, its Welcome expired after 7 days) holds a live slot forever. Define how it is retired, or document that it stays.
6. **Retired-room rule check.** Collecting only when `max(session_ts, rejected_at + 60) < floor` is correct. Add a test where a new Welcome re-joins the same `group_id` after collection: an old session must be rejected, and a fresh session must become a clean new conversation with no rows left over.
7. **Acceptance tests to add:**
   - R1 ordering, with a blocked join followed by messages;
   - the round-robin bound;
   - duplicate re-encryption producing exactly one receipt;
   - `unsubmitted` below the floor never being sent;
   - late invalidation after collection;
   - clock-behind-floor state;
   - a peer flooding one room while another room keeps progressing.
