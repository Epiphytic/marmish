**Verdict: CHANGES_REQUIRED**

The scope amendment itself is fine. The Iris-then-GitHub shell fallback works. But the README text around the fallback is now out of date, and one Tor-status point is ambiguous. No files were modified.

**Fallback check (offline):** The new block passes `sh -n`. I simulated the `( A || B ) && sh …` logic: Iris succeeds → run; Iris fails and GitHub succeeds → run; both fail → not run. That matches the new README text. `curl -f` stops on HTTP errors, and the second `curl -o` overwrites anything partial the first left, so a half-downloaded Iris file is never run on its own. `scripts/install.sh` is identical on this branch and on `master`, so the GitHub `master` URL points at the same file as this branch.

### Findings

1. **README trust/pinning paragraph is stale (must fix).** The paragraph starting "The script is served from Radicle through Iris…" still describes Iris as the only source:
   - It says pinning means replacing `head` in the Iris URL with a commit SHA. But the fallback line still uses the mutable GitHub `master`, so anyone who pins only Iris can silently get unpinned `master` if Iris fails. The pinning advice should cover both URLs (replace `head` and `master` with the same reviewed SHA).
   - "Mutable `head` trusts the script currently served by Iris" should also say that the fallback trusts whatever GitHub `master` currently serves.

2. **"Independently" overstates what the backup gives you (wording).** In `docs/agent-spec.md` and `docs/v0.2-plan.md`, "installation must work independently through Radicle/Iris and GitHub" is true only for downloading the script. The legacy installer always fetches its archives and `SHA256SUMS` from GitHub Releases (`api.github.com` / `github.com`). So Iris is a backup source for the script, not a separate install path: if GitHub is down, installation fails anyway. Say this explicitly. Also state whether the native v0.2 installer must remove that single dependency or keep it.

3. **No recorded evidence that both sources serve the same bytes (process).** `docs/v0.2-plan.md` requires both paths to be validated before claiming they're available. The README now presents GitHub as a working backup, but no validation record backs it, and I couldn't check under the no-network constraint. Iris `head` and GitHub `master` are both moving targets and could drift apart. Either add a validation record (Iris `head` bytes = GitHub `master` bytes = reviewed SHA) or soften the README claim until one exists. Also note that an Iris HTTP 200 with stale or wrong content won't trigger the fallback.

4. **Unclear Tor status for what v0.2 ships (clarify).** The amendment defers working Tor commands, but the plan still says "Embed Arti for Tor endpoints" with `auto` as the proposed default (onion relays go over Arti). README line 10 still says "targeting Tor endpoint support". State what v0.2 actually exposes for onion relays: experimental, disabled, or documented as not working for commands. Otherwise `auto` ships a route the release is explicitly not certifying. "Never fall back to direct" is stated correctly.

5. **Old Tor gates are left in place (minor).** Phase table rows 1, 2 and 4, plus the paragraph around line 160 ("Arti commands on each"), still list Arti command gates. The blanket "supersedes" sentence technically covers them, but a short "(deferred to v0.3 per amendment)" note on rows 2 and 4 would stop readers from treating them as live gates.

### Accurate as written
- The legacy vs native labels are correct: the quickstart is still marked "Legacy v0.1 only" and says no native installer exists.
- The Arti command failures are kept and described as "have not passed / deferred", not as passed.
- Existing Arti results are correctly limited: they don't establish working Tor commands.
- The direct-relay acceptance requirements (nine-pair matrix, recovery, authorization, cleanup, performance) are kept consistently across all four docs.
