## What I confirmed against the code
- **Finish verification matches what the client sees.** The status in a server Poll response is `record.status` from the same completion commit (`command_store.rs:3141`, `response_value` at about 3196). So the client's fingerprint and the server's stored terminal facts come from the same data.
- **The atomic consume-plus-Finish step is feasible.** `command_consume_response` (`:1124`) and `command_submit_client` (via `client_request`, `command_service.rs:213`) both work on the one journal connection. A combined store method can commit both in one transaction.
- **The counter rules fit the existing code.** The `finished < admitted` guard fits the `admitted` increment at `:1870`. Client-side projection never increments `admitted`. Old binaries already reject unknown `user_version` (`journal.rs:138`).
- **No fabricated ACK, authority or command side effect, and no ordinary cancellation.** Finish runs synchronously, is authorized through `authorize`/`can_accept`, issues no engine operation, and never cancels anything. Exit always goes through ordinary Stop.

## Blocking correction

**B1. The design requires a retry Finish after Busy but gives no way to create one.**

When the server answers Busy, the design requires "fresh Poll then fresh Finish request ID". But Finish may only be created inside the consumption transaction that brings the cursors to `produced`. After a Busy, the client's cursors are already at `produced`, so the fresh Poll moves nothing and no transaction qualifies. Read literally, no retry Finish can ever be created.

This can happen in practice:
- `expire_output` (engine `store.rs:1413`) adds an `Expired` prefix gap after the job exits. The next server Poll or Status commits that gap into `record.status`.
- Any Finish built from an earlier Poll then gets Busy permanently.
- The run falls back to the uptime exit, so acceptance fails even though nothing went wrong.

**Minimal fix:**
1. Make "latest Finish slot answered Busy, no Finish pending" a durable trigger. It must survive a restart.
2. The client sends a fresh Poll at its durable cursors.
3. Create the new Finish atomically with consuming that Poll's response, under three conditions:
   - the status is terminal;
   - its `produced` equals the durable cursors on both streams, with gap-aware traversal and an empty chunk allowed;
   - the same "no other unconsumed response" precondition holds.
4. Never build Finish from `record.status`.
5. Cap retries (for example at 4, the per-stream gap limit). After that, create no Finish and leave uptime as the exit.
6. Add a test: expire output between the terminal Poll and the Finish, then check that Busy leads to a fresh Poll, a new Finish, and exactly one increment.

## Non-blocking refinements
1. **A Finish after engine job collection gets the wrong refusal.** When the engine has collected the job, the server records `refusal = ResultExpired` (`command_store.rs:3066-3076`) but keeps the terminal `record.status`. "Refused invocations first return the original stored refusal" would then answer every later Finish with ResultExpired. Apply the stored-refusal shortcut only when `!engine_known`, and verify `engine_known` rows against their retained terminal status. Otherwise document that this case falls back to uptime.
2. **Unanswered requests at exit.** The precondition covers unconsumed *responses*, not unanswered *requests*. Either require that the client has no unanswered request for the invocation before creating Finish, or state that a Poll still in flight when the server auto-exits is left pending, harmlessly.
3. **Schema wording.** "Existing earlier schema upgrades must remain transactional" doesn't match the code: open runs separate DDL, then `command_init`'s own transaction, then `user_version=4`. Say instead:
   - the v5 column is checked and idempotent (a `table_info` probe);
   - fresh `CREATE TABLE` statements include `finished`;
   - the 3→5 path is covered;
   - `user_version=5` is written last.
4. **Dependency on the local client.** In production, nothing calls `command_consume_response` yet; only `command_check.rs` and tests do. The local-client design is approved but not implemented. State that Finish integration lands with or after that work, and that `command_check` exercises the combined consume-plus-Finish store API.
5. **Typos:** missing spaces in "yields1..1800seconds", "max3", "documented1800second" and similar.
