## Blockers

**N1. The Status check doesn't say which mismatches mean "keep polling" and which mean "fail".** (lines 118–119, 142–143)
- Line 119 lists the full Running predicate, but only "under-prefix remains pending, over-prefix fails" is classified.
- The detached submit returns as soon as the server accepts the request (`command_cli.rs:782`). The worker launches after that.
- So the first Status, about a second later, can legitimately show:
  - `state` Accepted or Launching (`model.rs:96-103`)
  - `admission` not yet Engine
  - input still arriving: delivered below 16384, health Open or EofPending (`model.rs:121-127`)
- A literal implementation would treat that reply as invalid, which makes the cohort red on almost every run.
- Fix: state the classification explicitly, and apply the same rule to the post-reopen Status.
  - **Pending:** those pre-launch states and input still arriving, as long as authority is valid, there is no warning, no cancel request, no gaps and no outcome.
  - **Fatal:** Exited, Lost or UnknownLaunch; invalid authority; any warning or cancel request; any gaps; health Gap or Uncertain; produced above 65536; input counts above 16384.
- Also require each Status CLI to exit 0 with exactly one JSON line on stdout and empty stderr. The error paths print a handle line and return a non-zero code (`command_cli.rs:966-971`).

**N2. "Canonical JSON" for the handle line contradicts the actual CLI bytes.** (line 112)
- The CLI writes `serde_json::to_vec(CommandHandle)` (`command_client.rs:136-142`) in struct field order: format, profile, remote, session, invocation, submit_sha256 (`command_client.rs:11-18`).
- The repo's `records::canonical` sorts keys and appends a newline (`installed_records.rs:288-294`).
- If the driver checks the handle line against `canonical`, every handle is rejected.
- Fix: say "the CLI's exact encoded bytes, parsed strictly by a deny-unknown-fields handle type". Write those same bytes to the handle file. `CommandHandle::decode` reads them back from raw JSON with no newline required (`command_client.rs:130-135`).

## Nonblockers
1. **Atomic gate.** The hard-link publication matches the `write_raw` pattern and removes the partial-content race.
   - Between the link and the temporary's unlink, the final gate has a link count of 2.
   - The fixture predicate at lines 95–97 doesn't check link count, so this is correct as written.
   - Pin it anyway: either the link count isn't checked, or 2 means "still pending". Otherwise a hardened implementation could bring back the race.
   - Also name the temporary file so it can never match `<nonce>.started` or `<nonce>.release`.
2. **Detached submit output.** Require stdout to be empty as well as stderr being exactly one handle line.
   - A detached call that consumed any output would advance the client's read position. The later `wait` would then lose the prefix.
   - The plan already fails closed on an exact-byte mismatch; stating it makes the reason clear.
3. **Worst-case budget.** The maximum stages sum to just over the work cutoff:
   - readiness 150 + detach 90 + Status 90 + stop 35 + reopen 150 + Status 90 + wait 330 + detach 90 + wait 330 = L+1355
   - That is 5 seconds past L+1350. Clipping keeps it safe and red, but the plan should say the last wait may be truncated.
4. **Fixture fail-safe bound.** "Fixture starts by L+330" holds only on the success path. After a Status timeout or an unknown admission, a delayed launch could start later. Its 900-second fail-safe could then outlast cleanup, with state preserved and the run red. Say so.
5. **Interrupted ordinary stop.** For a SIGTERM during the ordinary stop, state that the driver keeps owning the stop and finishes it within its 35 seconds before closing.

## Verified against source
- **Detach, then wait.** With `--wait-seconds 90`, the submit returns exit 0 plus a handle line once accepted, or exit 254 plus a handle and `local_pending` at the deadline (`command_cli.rs:1101-1106`, `957`). A successful `wait` with exit 7 prints no handle line, and `delivery_pending` adds a handle line and a message (`command_cli.rs:591-597`, `957`). The no-stripping wait check and the observable for Finish success are therefore correct.
- **Policy shape.** Setup writes `command_policy` exactly as `{"version":1}` (`native_setup.rs:133`), so the line 74 requirement is feasible.
- **Status binding.** Status has no session field. The CLI binds each reply to the handle and a fresh request ID (`command_cli.rs:975-1000`).
- **Ordinary stop.** A narrow `Daemon::ordinary_stop` that records observed quiescence fits the daemon's stop report. That report says quiesced only after cleanup reaches `Quiesced` (`command_engine.rs:265,282`). Autoexit's `OriginalStop` (`installed_autoexit.rs:78-100`) is the existing precedent. The final strict stop is unchanged.
- **Restart uptime.** The config alone keeps `max_commands`, and the `--max-uptime` override replaces the config value (`command_config.rs:285-289`).
- **Cleanup timing, failed records and tests.** Cleanup is bounded at L+1710 with `tokio::join!` stops at L+1770 and a kill fallback ending by L+1775. Failed-record validation with `validate_record`, typed stages and root embedding, the stopped-window signal rules, and the pure negative-test list resolve B4–B7. The test list covers what it names; I didn't write or run any tests.
