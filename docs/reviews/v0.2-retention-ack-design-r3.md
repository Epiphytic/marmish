## Findings

**R3-1 (High, blocking): "add those group IDs to the protected set" (lines 167–170) does not protect anything the global early return protects today.**

The early return at `mdk_adapter.rs:1080-1087` exists so that "late invalidation [can't] lose its owner". The protected set the design reuses is consumed by two functions, and neither one guards source retirement for a protected group:

- **Command side:** `command_maintain`'s slot-retirement loop (`command_store.rs:1993-2075`) never checks `protected.groups`. Only the invocation delete does (line 2103). It deletes `command_incoming_sources`, `command_outgoing_sources`, `command_publications` and `command_requests` whenever publications are published/invalidated/expired and the source ACKs are set.
  - Under the amendment, slot retirement doesn't wait for seven days (line 110), so the following can happen:
    1. A consumed, ACKed client slot in group G is waiting.
    2. An `AppMessageInvalidated` for that slot's response source is deferred, so it stays pending.
    3. The next maintenance turn retires the slot and its source binding.
    4. The invalidation then finds no binding. Under lines 152–153 it is applied "normally", so `revoke_record` never runs.
  - Result: the invalidation silently stops overriding the response, which is a regression from today.
- **Foundation side:** `journal.rs:874-875` deletes `incoming_sources` and `incoming` before the `if protected { continue }` check at line 876. So foundation incoming owners are not protected for a protected group either. That also contradicts line 253, "no foundation-purpose behavior change".

**Exact change:** Define a separate set, `invalidation_groups`, holding the group IDs of all pending `AppMessageInvalidated` events at the time maintenance runs. Don't reuse `protected.groups`: that set also contains every group with a fanout, and gating slot retirement on it would stall retirement for every active group. Then specify:
1. **(a)** `command_maintain` skips slot, source, publication and payload retirement for any group in `invalidation_groups`.
2. **(b)** For the foundation, choose one of these and state it explicitly:
   - keep the existing account-global early return for `journal.maintain` only. This leaves foundation behavior unchanged, which matches line 253.
   - or move the `incoming`/`incoming_sources` deletes under an `invalidation_groups` check and remove the "no foundation-purpose behavior change" claim.
3. **(c)** Add a test: a deferred invalidation in group A plus a consumed, ACKed slot in A. The slot and its source must survive maintenance, while group B's slot retires in the same turn. Then the invalidation applies and revokes.

**R3-2 (Low): the payload-clearing "bounded step" (line 28) has no bound.** The existing invocation scan uses `LIMIT 10001` (`command_store.rs:2078`). State a per-turn limit, for example 256 rows using the same rolling cursor as reconciliation, so payload clearing can't turn into a whole-table update inside one transaction.

**R3-3 (Low): the `command_client_response` signature contradicts itself (lines 64–66).** It is declared as `Result<Option<Response>>`, then the text says it returns `Option<(Response, Digest)>`. Write the signature as `-> Result<Option<(Response, Digest)>>`.

**R3-4 (Low, clarity): the first proof clause in early invalidation (line 147) is redundant.** If an outgoing binding already exists, the invalidation applies directly to that binding, so no tombstone is ever needed. Say that a tombstone is only considered for an unbound native ID.

Once R3-1 is reflected in the document, I would expect to approve it. R3-2 to R3-4 can be fixed in the same pass and don't need another round on their own.
