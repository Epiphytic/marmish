## Verdict: APPROVED for this partial scope (root + identity only)

This round covers only the daemon, IPC, CLI, identity, error and diagnostics modules, the two native binaries, and the vault edits. It does not approve the phase, and it says nothing about `mdk_adapter`, `journal`, `foundation`, `foundation_check` or `transport`, which I did not review. I found no blocking defects in scope, and I made no edits. The scope hashes did not change between my reads and the end of testing.

### Round-1 fixes in scope, all confirmed
- **Shutdown signals:** the TERM handler is created before the IPC socket is bound and the server is spawned (`daemon.rs:113-119`). Shutdown is honoured during activation (`:128-131`), during a dispatch (`:145-148`) and during a tick (`:153-156`). A dispatch cut short drops its reply channel, so the client gets `operation_uncertain` rather than a false success. The pinned shutdown future is never polled again after it completes.
- **Tick errors:** a Transport or Timeout error sets `transport_degraded` and the daemon keeps running (`:157-163`). Every other error is still fatal.
- **Shutdown order:** after the loop, the IPC server stops, then the owner shuts down, then the socket is removed. The profile lease is released last, so a new daemon cannot race the old socket.
- **IPC accept errors:** they now retry after 50 ms and no longer end the server (`ipc.rs:148-155`). Other bounds: 64 client permits, a 64 KiB frame limit checked before allocating the body, a 15 s read/write timeout, an owner queue that answers `busy` when full, Status served from the snapshot, and the peer's UID checked on both server and client.
- **Vault helper argument check (old B7):** fixed, and the vault tests now pass.

### Secret handling and identity initialization (checked path by path)
- **Request:**
  - The request is serialised into a preallocated `Zeroizing` 8192-byte buffer.
  - The `secret` value is removed and zeroised before the encoding result is checked, so the oversize error path wipes it too (`identity.rs:601-615`).
  - `Zeroizing<Vec>` also wipes spare capacity, so truncating the buffer leaves nothing behind.
- **Response:**
  - Reads go into a buffer preallocated to 8193 bytes and are capped to the space left, so it never reallocates; a test asserts this.
  - The 1 KiB read chunk is zeroised after each read.
  - The secret string, the decoded bytes and the re-encoded canonical comparison string are all zeroising.
  - Helper error text maps to fixed categories, so no provider text leaks through.
- **File provider:** reads into a 33-byte buffer with a 33-byte read cap. I traced `std`'s probe reads: secret bytes are never copied outside the buffer.
- **Key objects:** nostr `Keys` and `SecretKey` wipe themselves on drop at the pinned revision (`nostr/src/key/mod.rs:233`). `Keys`' Debug output prints only the public key.
- **No secret output:** nothing in scope prints secrets. `IdentityMaterial` has no Debug or Serialize, and the CLI prints only fixed error categories.
- **Initialization is crash-safe at every step:**
  - The manifest is written atomically with temp file, rename and directory fsync, and contains the random references before any key exists.
  - A Nostr key is created only while initializing and before its public key is recorded. Once the public key is persisted, a missing key fails closed.
  - Every create is followed by a read-back comparison, and `exists` means verify.
  - The Ready phase never creates keys.
  - Tests cover each of these cases.
- **No provider downgrade:** files are chosen only when `Auto` meets a fresh profile and the keychain reports `unavailable`.
  - Timeouts, helper crashes, I/O errors, `locked_or_denied`, `ambiguous` and `uninitialized` all fail instead.
  - An existing manifest's backend always wins, and an explicit choice that contradicts it returns `backend_mismatch`.
- **Same-user filesystem checks:**
  - The lock is taken before the manifest or any provider is touched.
  - Directories must be exactly 0700 and owned by the current user, with no symlinks.
  - Files are opened with `O_NOFOLLOW`, must be 0600, owned by the current user and have a link count of 1; hardlinks are rejected, and tests cover this.
  - `binding.json` ties the runtime directory to the profile root, so a copied state directory reports a collision instead of sharing a socket.

## Nonblocking findings
1. **Other users can block the runtime directory.**
   - `identity.rs:106-107` and `:368-372` place it at `std::env::temp_dir()/mr2-<uid>-<profile_id>`. The profile ID is visible in a shared `/tmp`.
   - After a reboot clears `/tmp`, any local user can pre-create that path. The ownership check then refuses to start the identity until the profile is recreated or `TMPDIR` is changed.
   - The daemon and CLI must also agree on `TMPDIR`. A systemd `PrivateTmp`, or a different `TMPDIR`, makes the CLI fail closed with NotFound.
   - Suggested fix: on Linux, prefer `$XDG_RUNTIME_DIR`, which is per-user and 0700.
2. **The status snapshot is rebuilt on every 100 ms loop pass** (`daemon.rs:135-140`).
   - Today `owner.status()` counts received messages by loading every one with its payload, and any error from it is fatal.
   - Suggested fix: publish the snapshot only when it changes, or on a slower timer. Use count queries in the adapter (adapter round).
3. **Contract for the adapter round:** the daemon treats every non-Transport/Timeout tick error as fatal (`:163`). The adapter must therefore guarantee that no input a peer controls can surface as `Invalid`, `Mdk` or `Io` from `tick`. Otherwise a remote peer could stop the daemon. I did not verify that here.
4. **Short Ctrl-C gap at startup:** `tokio::signal::ctrl_c()` registers its handler on first poll, after the socket is bound. A SIGINT in that window leaves a stale socket, which the next bind removes. Fix: create `signal(SignalKind::interrupt())` up front, as is already done for TERM.
5. **Native helper argv is not strict:** `cli.rs:157` launches the helper whenever argument 1 is `_vault-helper` and ignores any extra arguments. Match the keychain binary and require exactly two arguments.
6. **No backoff while degraded:** the daemon retries at a fixed 100 ms, and no test covers the degraded/fatal error classification. Add backoff and a unit test.
7. **Stale queued requests still run:**
   - Requests that wait more than 150 s, for example behind activation, are reported `operation_uncertain` but may still run later.
   - That is truthful, since "uncertain" covers it. The owner could still skip any request whose reply channel `respond.is_closed()`.
8. **Umask edge case:** a umask that removes the owner's write bit makes creation fail the strict mode checks. This fails closed; `fchmod` after create would make it robust.
