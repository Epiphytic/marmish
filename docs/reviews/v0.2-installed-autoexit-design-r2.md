## r1 blockers: all resolved

- **r1-B1 (resolved).** The revision drops Submit reconstruction and the `submit_request_*` fields. The source matches the new approach:
  - `--detach` exits 0 once the Submit is accepted (`command_cli.rs:782,925`).
  - It writes `marmish handle: <json>` to stderr (`:102,957`).
  - `CommandHandle` is closed with deny-unknown-fields (`command_client.rs:20`).
  - Exit 254 is `local_pending` (`:1105`) and 255 is `local_busy` (`:1104`). The design treats both as a red `submission`, with no second invocation.
  - The only request ID in `Terminal` is the controller's own Poll ID. Nothing is invented.
- **r1-B2 (resolved).** The uptime cleanup instance now uses `max_commands 1`. `CountDrain::ready` needs `admitted >= max > 0` (`command_limits.rs:48`), so the cleanup restarts at 1/0 and at 4/3 cannot trigger a count exit.
- **r1-B3 (resolved).**
  - The driver owns the config write, done after setup and before any spawn.
  - The field list matches `RawConfig`, which is deny-unknown (`command_config.rs:307`).
  - It uses `limits {}` everywhere, with limits passed only as CLI flags (`apply_limit_overrides`, `:285`).
  - The matrix `configure()` is explicitly not reused.
  - Config digests go in `ConfigPin`.
- **The terminal is written before Finish, with no product hook.** The existing `CommandConsume` mints `finish_id` and returns `finish_request_id` (`command_local.rs:478–503`). Writing the terminal record before the final Consume is therefore enough.
- **r1 nonblockers 1–5 are addressed.** These were the R+180+35 window, at least 16 Polls with matching `expected_cursors`, the 104-byte socket check using the `identity.rs:121` formula, the count latch at L+600, and requiring no invocations and no evidence rows for uptime.

## New blockers

**B1. Gate independence is unspecified, and the planned Context change would make the matrix accept the wrong cohort.**
- **Source:**
  - Today the only cohort check is `Context::validate`, which requires `cohort=="matrix"` and a lifetime of at most 2220s (`installed_records.rs:64–66`).
  - `installed_prepare.rs:50` and `installed_matrix.rs:654,867` call only `ctx.validate()`.
  - The design widens `validate` to accept autoexit/uptime with up to 3300s, but says "matrix entrypoints … remain unchanged."
  - As a result, the matrix would accept an autoexit or uptime Context, up to 3300s, and run on it.
- **Also missing:**
  - Who creates the autoexit/uptime Contexts. Today `workflow.mjs resolve` passes `--cohort matrix` only and writes one `context.json`.
  - Which jobs carry the 65-minute host / 62-minute internal timeouts. Today matrix is `timeout-minutes: 55` with a deadline of start+3120s.
  - Any statement that the remote-conflict (real-MdkOwner) gate is separate. The revision no longer mentions it at all.
- **Fix:**
  1. Give `validate` a per-cohort lifetime table: matrix ≤2220s, autoexit ≤3300s, uptime ≤3300s.
  2. Every entrypoint must also require its own cohort. `prepare`, the matrix commands and `cohort` must reject a Context minted for another cohort, and `cohort` must also match its argument.
  3. Say that resolve mints a separate Context per cohort, each with its own nonce, `created_at` and artifact name (the prefix already includes the cohort).
  4. Name the exact autoexit/uptime jobs that get the 65m/62m timeouts. State that matrix keeps 55m/3120s.
  5. Add one sentence: neither cohort replaces or satisfies the matrix gate or the remote-conflict protocol gate. Each gate reaches its own verdict.

**B2. The worst-case budget leaves out the three client stops, so cleanup can't fit.**
- **The arithmetic:**
  - The launch check guarantees at least 2255s to expiry, so the cleanup cutoff (expiry − 300s) is at least L+1955.
  - The worst-case server exit observation is R+1235, and R ≤ L+150, so L+1385.
  - That leaves exactly 570s. But between server exit and restart, the design requires joined stops of all three clients (line 191). Each is a 30s `stop_owned` plus an unbounded `pending.finish()` (`daemon.rs:206–212`), plus reaping.
  - So the 570s pre-restart check (line 194) fails whenever any time is spent stopping clients.
- **Why it matters:** this violates the root requirement that the remaining-time checks cover worst-case origin + joined shutdown + cleanup + the 300s reserve. It doesn't produce a false success, but on the late path cleanup can never be attempted.
- **Fix:** add an explicit client-stop term, for example 40s (three concurrent stops: 30s stop + 5s terminate + 5s slack), and make any overrun red.
  - Launch check: 2295s (150 + 1200 + 35 + 40 + 570 + 300).
  - Entry check: 2895s.
  - Update the record minimum, `work_budget_at_entry_ms >= 2895000`, to match.
  - Context lifetime stays at 3300s.
  - Alternatively, keep 2255s and split the 570s explicitly so it includes client stops. Either way, the numbers must add up.

## Nonblockers (fix in the same revision)

1. **Client `allow_exec` must be written explicitly.** If `defaults.allow_exec` is omitted, it becomes `["/**"]` (`command_config.rs:149–150`). Clients should get `"defaults":{"allow_exec":[]}`. The server pattern must also be glob-safe: reject or escape metacharacters in the pinned fixture path.
2. **`engine_quiesced` has no field.** The design says to record it "truthfully" (line 177), but the "complete" closed schema has nowhere to put it. Add a field for the original exit report.
   - Note that `cleanup::stop_report` requires `engine_quiesced=true` (`installed_cleanup.rs:349`). Say whether it is reused for the natural-exit report.
3. **The admission rule leaves out `Dispatching`.** `Admission` has three states: `Accepted`, `Dispatching` and `Engine` (`command_wire.rs:144`).
   - Allowing only Accepted/Engine could turn a valid transient state red.
   - Either allow `Dispatching` with `authority_valid` and require Engine later, or justify excluding it.
4. **Recovering from a lost Consume or a Busy Finish isn't specified.**
   - If the Consume reply times out after it committed, `finish_request_id` is lost. Recover it through `CommandUnconsumed` (op Finish) and `CommandResponse`, and never re-Consume.
   - A Busy Finish needs a fresh Poll at the final cursors, as `command_cli.rs:582` does.
5. **The cleanup instance's uptime is unclear.** The text says "≤600s bounded by remaining budget", but the window is only 570s.
   - Fix the value, for example min(600, expiry − now).
   - Require the guard/remove deadline to end at least 60s before that lifetime expires, so a natural exit can't race `remove_installed`.
6. **Teardown after a red verdict.** If the server misses its observer bound (for example, `pending.finish()` runs past 30s), say that the retained child is torn down with `process::terminate`, the result is red, and no deletion happens.
7. **Uptime cohort details.**
   - Say whether its client daemon is ever launched; it shouldn't be.
   - Say that L is captured immediately after the launch-budget check.
8. **Expect queue flakes.** With 2855s (or 2895s) needed out of 3300s, only about 445s (or 405s) is left for queueing, download, checkout and `npm ci`. That fails closed, which is correct, but macOS runner contention will cause reds. The job layout from B1 should keep the cohorts from contending for runners.

No implementation is authorized. B1 and B2 need a re-review.
