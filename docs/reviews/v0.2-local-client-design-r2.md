# Native local command client design review, round 2

Reviewer: Claude Code, claude-opus-5-5. Scope: design only, `docs/phases/v0.2-phase2-local-client.md`. SHA256 `9e26d2f3…0a66b8` matched before and after the review. This review does not approve any implementation. I edited no files.

## Verdict: CHANGES_REQUIRED

All six round-1 blockers are closed or mostly closed. The client-ledger amendment works with the current store, adds no second database owner, and exposes no group bytes. Two narrow blockers remain.

## Closure of round-1 blockers

- **B1 (submit digest): closed.** `submit_sha256` is now `wire::request_digest(encode_request(Submit request))`. `Request` is `{binding{session,client,server}, id, op}` (`command_wire.rs:19-81`), so no group bytes go into the hash. The local account now comes from the prepare result or `status.identity`.
- **B2 (room-intent deadlines and failures): closed.** The draft now has:
  - a start-by limit of arrival + 60 s;
  - an absolute 15 s per-turn deadline that also covers the final sync;
  - a `can_open` check before enqueue;
  - an 8-entry last-outcome map that lasts 60 s;
  - an honest statement of the first-use and latency limits.
- **B3 (cursors and false pending): partly closed.** `command_cursors` is added, and consumed and retired answers are now separate results. See new blocker N2.
- **B4 (consume cursors): closed.** The draft now uses the Poll request's own start cursors, which matches `command_consume_response`.
- **B5 (unconsumed paging): closed.** The query is cursorless with a limit of 1..=64, which matches `command_client_unconsumed` (`command_store.rs:1083`).
- **B6 (lost handles): closed at the IPC level only.** See new blocker N1.

## Blocking findings

**N1. Ledger recovery has no CLI path, so B6 is not fully closed for users.**
- `command_invocations` is IPC-only. The only local subcommands are `command-status`, `wait`, `output` and `cancel`, and they take exact handle JSON or `--handle-file`.
- After a SIGHUP or SIGKILL following the submit commit, the user has no handle to give any subcommand. The "retained discovery after a CLI restart" (lines 178-180) can't be reached.
- It's also a problem for an operator who can't copy and paste from a terminal.
- **Minimal fix:**
  - Add a bounded local `commands` subcommand that pages `command_invocations` and prints one handle per line, with invocation ID, remote, creation time and cached disposition. No argv.
  - Let `command-status`, `wait`, `output` and `cancel` accept `--invocation <32hex>` (within `-i` profile), resolved by the actor through the ledger, so the user doesn't need to paste JSON.
  - Add an acceptance test: SIGKILL after the commit, list, then `wait` recovers the output with no second engine admission.

**N2. "Queue if absent" contradicts "retired returns `command_response_retired`" for status, cancel and poll.**
- The store deletes retired slots outright (`DELETE FROM command_requests`, `command_store.rs:~2493`) and keeps no record that they existed. `freshness` only rejects IDs below the floor (`:1354-1379`).
- So the actor can't tell a retired request ID from one that was never queued. Lines 95-98 tell it both to queue and to report retired for the same state. One reading of that needs a tombstone store extension that no one has reviewed.
- Separately, `command_client_response` returns `Ok(None)` both for an answer that is consumed and for one that hasn't arrived yet (`:1062-1081`). Telling those apart needs one small read-only store query, and the draft doesn't say so.
- **Minimal fix:**
  - On status, cancel and poll, an absent slot (never queued or retired) always re-queues the identical bytes. The approved retention rule allows this ("Read operations are safe to recompute after slot retirement"). An old Poll whose cursors have since advanced fails with the existing `command_cursor_stale`.
  - Only `command_response`, `command_consume` and `command_unconsumed` return `command_response_retired`.
  - State the narrow store query for `consumed` versus `pending`: `local_consumed=1` versus `projected=0`.

## Nonblocking refinements

1. **Schema for the retained Submit metadata.**
   - Put the request ID and digest in the `command_invocations` row, `NOT NULL` for client rows, written in the same transaction as `insert_invocation`. Never backfill them from the payload: `submit` can already be NULL (`:2623`).
   - The command store is still uncommitted and `user_version=4` exists only in the working tree, so either finalize v4 or bump to v5. Say which.
2. **One request ID per invocation.** Today `command_submit_client` lets a different request ID attach to an existing invocation if the submit digests match (`:817-826`). The retained-first-ID rule would then hand the second caller a handle that never validates. Reject a new request ID for an existing client invocation, or return the retained handle.
3. **Lifetime wording.** Deletion actually requires `created <= now − payload_retention` (default 86400 s, max one week), an invocation timestamp below the floor, no remaining slots, and no protection (`:2500-2535`). Say "until the replay floor and the existing deletion conditions retire the row", and define a finite `command_not_found` once that happens.
4. **Exit code 254 scope.** The approved mapping reserves 254 for lost or ambiguous admission, and uses 255 `remote_pending` for timeout. Use 254 only while the Submit's local commit is unconfirmed. Once `local_queued` or ledger discovery has confirmed it, a timed-out read should exit 255.
5. **Socket-task wait for command methods.** Use the time left in the 15 s budget minus a write margin, instead of the existing 150 s (`ipc.rs:170`). Otherwise abandoned tasks hold the 64 permits. Also, when all permits are taken, `ipc.rs:157` drops the connection silently. The CLI must treat any lost connection after sending a submit as `local_pending`, which the draft already implies.
6. **The 60 s last-outcome entry acts as a cooldown.**
   - Say so explicitly: a new CLI run within 60 s gets the stored failure again.
   - Define eviction when a ninth remote arrives (oldest first).
   - Add a `welcome_pending` category. An intent for an existing room must only drive the retained Welcome, never create a new room.
7. **Digest as a guessing oracle.** A handle carries a hash over argv and stdin. Short commands can't be brute-forced from it only if the request ID has at least 80 random bits from the OS RNG and the handle or listing never shows the request ID next to the digest. State both.
