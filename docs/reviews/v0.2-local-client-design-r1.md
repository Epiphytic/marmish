# Verdict: CHANGES_REQUIRED

This is an independent Claude design review of `docs/phases/v0.2-phase2-local-client.md`. The SHA256 was `420e5771…22aed` both before and after the review, matching the expected value. This verdict covers the design only; it does not approve or claim anything about implementation.

The overall structure is sound. There is still one MDK owner, the daemon owns the room intents, there is no client catalog, and `local_busy` is kept separate from post-enqueue ambiguity. Six concrete gaps against the approved contracts and current source still block approval.

## Blocking findings

**B1. The handle's `submit_sha256` can't be computed by the client as specified.**
- The draft says the client freezes the canonical bytes and digest and builds the full handle before sending. It also says the actor matches the "submit digest" against its records.
- The stored record digest is `wire::submit_digest(group, binding, submit)` (`command_wire.rs:633-651`, stored at `command_store.rs:812-818`). It hashes the MLS group bytes, which the draft rightly says the client never sees.
- **Fix:** define `submit_sha256` as `wire::request_digest(encode_request(Submit request))`, the canonical request bytes. `check_slot` (`command_store.rs:1370`) already compares those bytes.
- The client also needs `binding.client` (the local account) to encode those bytes. Say where it comes from: either the probe's `local_busy` returns it, or it comes from the `identity` field in the status snapshot (`mdk_adapter.rs:1176`).

**B2. The room-intent deadline makes progress unlikely, and failures are never reported.**
- *The deadline has no origin.* "Original monotonic deadline" doesn't say where it comes from, and a CLI `Instant` can't cross processes.
- *Intents behind the first one will mostly expire.* If the deadline is arrival + 15 s, a tick ahead of the turn can take up to 15 s (`daemon.rs` tick deadline), and so can each earlier intent's turn. `discover` alone already uses its own 15 s (`mdk_adapter.rs:1424`). Under Arti, an intent at queue position 2 or later will usually expire before it starts. Discovery and creation persist nothing, so repeated runs can fail forever.
- *Room-turn failures reach nobody.* Intents hold only remote + deadline, so failures such as `command_unauthorized`, `command_room_capacity`, `clock_behind_floor`, or no KeyPackage just look like busy until the CLI's 15 s runs out.
- **Fix:**
  - Give each turn its own fixed 15 s budget from turn start.
  - Give the intent a separate daemon-derived start-by limit (for example arrival + 60 s).
  - Check `can_open` before enqueuing, and return a definite failure instead of busy.
  - Keep a bounded, volatile last-outcome map keyed by remote (at most 8 entries) and return it as `failure{category}` on the next probe.
  - State honestly that the first use may end `local_busy` while the room finishes in the background.

**B3. There's no IPC for the durable cursor pair, and a consumed slot is reported as `remote_pending`.**
- The approved retention amendment says "the CLI reconciles through `command_client_cursors`" after `command_response_retired` (`command_store.rs:1043`). The draft has no IPC method for it.
- After a restart, `output`/`wait` can't build a Poll, because the store requires the start cursors to equal the durable pair or it returns `command_cursor_stale` (`command_store.rs:832-838`).
- `command_client_response` returns `Ok(None)` for a slot that is consumed but not yet retired (it filters `local_consumed=0`, `command_store.rs:1062`). The draft's "cached unconsumed answer or `remote_pending`" therefore tells a re-asked consumed request "pending" until the 180 s timeout.
- **Fix:**
  - Add `command_cursors { handle } -> consumed{stdout,stderr}`.
  - Return a distinct finite `command_response_consumed` or `command_response_retired` instead of `remote_pending`.

**B4. `command_consume`'s cursor rule doesn't match the store.**
- The draft says Poll passes "the exact durable pair". The store requires `expected == the Poll request's start cursors` (`command_store.rs:1123-1133`).
- On a repeated consume after the cursors have advanced, the durable pair ≠ start, so the draft's rule returns `command_cursor_stale` instead of the approved current-pair result.
- **Fix:** specify that `expected_cursors` are the Poll request's own start cursors.

**B5. `command_unconsumed { after }` / `page { next }` has no approved store API behind it.**
- The approved `command_client_unconsumed(&Owner, invocation, max)` has no cursor (`command_store.rs:1072-1099`).
- **Fix:** drop `after`/`next`. Unconsumed slots count against the per-principal 64-slot cap until they retire, so a single `limit ≤ 64` page is complete. A cursor would instead need a separately reviewed store extension.

**B6. A CLI crash can lose the handle permanently, against the approved "handle… persisted locally".**
- The draft saves or prints the handle only on an ambiguous submit or on Ctrl-C. SIGHUP (terminal closed) or SIGKILL after the submit write orphans a running remote command, and no IPC can find it again.
- Printing on stderr every time would break the exact stderr copy.
- **Fix (either works):**
  - Persist the provisional handle to a private, fsynced, bounded, profile-local file before the submit write.
  - Or add a bounded `command_invocations { after, limit ≤ 64 }` over the existing client ledger rows.

## Nonblocking refinements

1. **The delay claim is too optimistic.** "A room turn can delay … by up to 15 seconds" leaves out the shared 64-deep FIFO. That includes foundation `OpenConversation`/`Send` with a 120 s dispatch deadline (`daemon.rs` `dispatch`) and the 15 s tick. State the real worst case, and rely on the per-exchange `local_pending` behaviour.
2. **Responses should be verified client-side.** Route the embedded response through a typed or `RawValue` path, not `serde_json::Value`, which silently collapses duplicate keys. The client should re-encode it, check its SHA-256 against `response_sha256`, and run `decode_response`'s canonical check.
3. **The probe doesn't need a payload.** It currently carries `request_id` + `submit`, up to 32 KiB of unused data. A separate `command_prepare { remote }` would be cleaner.
4. **Map exit codes for uncertain outcomes.** Say which exit code `local_pending` uses: 254 (ambiguous admission) versus 255. Also say that an explicit busy following any earlier ambiguous attempt must still exit as pending.
5. **Define a minimum poll pace.** Each read is a remote publication that holds a slot until retirement, and the cap is 64 per principal. Set a minimum interval (for example ≥ 1 s), prefer Poll over Status, and map Poll-credit or slot-capacity busy to a retryable variant.
6. **"Ready" should exclude pending Welcomes.** Consider requiring that the room has no outstanding Welcome delivery (`drive_retained`, `mdk_adapter.rs:2177`), or record why that isn't needed.
7. **Relay-equality check.** The status snapshot doesn't expose the daemon's relay policy, so the relay-equality check has no specified source. The actor should check it, or status should expose a policy digest.
8. **Alias collisions.** Reject aliases that collide with reserved subcommand names. The `command-status` spelling differs from the approved `status`; that's acceptable as an explicit amendment.
9. **Bound the stdin wait.** Read at most 16 KiB + 1 bytes. Note that a pipe that never reaches EOF waits outside every budget, or bound that wait.
10. **Revoked-only room.** Say whether a remote whose only room is revoked may get a fresh create. The current code does this (`command_runtime.rs:107-116`).
