## Required

**R1. The doc says the existing `CommandEngine::shutdown` drains events while retrying the control queue. It doesn't.** In `crates/marmish-native/src/command_engine.rs:248-258`, when `Control::Stop` hits a full control queue, the code only sleeps and retries. It calls `self.collect()` only later, in the join-wait loop (`:261-264`). The engine thread sends events with a blocking `tx.send` (`:369`, `:401`). So if the events channel and the control queue are both full, the engine thread waits for events to be drained and `shutdown` waits for control space. Every one-second turn then ends incomplete, and the keeper loops forever on an engine that is otherwise healthy. This is unlikely given the `CAPACITY` registration bounds, but the design relies on the property for liveness.
- **Fix:** add `self.collect()` in the `Full` retry arm, or remove the claim from the doc and justify termination another way. The fix is one line; adding it to the design is better.

**R2. `OwnedIdentity`'s field order releases the lease first.** Rust drops struct fields in the order they're declared, and `profile` comes first. Any implicit drop (a panic while unwinding, a stray `?`, an in-process test failure) therefore unlocks the profile (`identity.rs:88-95`) before `MdkOwner` closes MDK/journal and before the engine is dropped. Dropping the engine without `shutdown` detaches its thread, because `CommandEngine` has no `Drop`. That breaks the doc's own invariant that the lease is released only after both have ended.
- The engine's own `FrontendGuard` lock still protects the engine store (the existing test at `command_engine.rs:1184-1194` shows a second open fails). The exposed window is MDK/journal only.
- **Fix:** declare `owner` before `profile`, and say in the doc that implicit drop is a degraded path, not a clean stop.

## Non-blocking notes

1. **Queued blocking tasks are cancelled at runtime shutdown.** Tokio drops the closure of a `spawn_blocking` task that hasn't started yet, which would drop the engine and lease together. Running tasks are waited for. The doc's rule that "a caller cannot begin runtime shutdown first" covers this; stating the reason would stop someone relaxing it later. `#[must_use]` on `PendingStop` warns but doesn't enforce, so a dropped `PendingStop` detaches the keeper.
2. **Poll the keeper and MDK shutdown concurrently.** Both use the same observer deadline. Waiting on the keeper handle only after `MdkOwner::shutdown`, which can use the whole deadline, would report a stop as pending even when the engine joined quickly.
3. **Readiness reorder is fine.** After the change, the profile is marked `Ready` even if `enable_commands` then fails. That's acceptable: `Ready` only controls key creation (`identity.rs:218`), and the MDK binding is genuinely open by then.
4. **Name clash.** `command_engine::StopReport` already exists; give the new lifecycle report a different name or module path.
5. **Uptime.** The doc lists "uptime expiration" as a stop trigger, but `daemon.rs` has no uptime today. That's harmless.

## Confirmed against the code

- **Ordinary stop leaves workers running.** `Control::Stop` returns from `Worker::run` and drops the engine. The engine frontend's drop paths don't kill anything; the only `SIGKILL`/`SIGTERM` calls are in the separate worker process's `ChildOwner` and in launcher test code. Cancellation and `into_cleanup` happen only through explicit `Control::Cleanup`.
- **Retrying shutdown reuses the same thread handle.** An incomplete turn keeps `self.thread`. A panicked join returns `Err` only after `thread.take()` and `join()`, so the thread really has ended. Once the engine thread exits, the control receiver is gone, so a retried Stop gets `Disconnected` and moves on to the join.
- **The keeper's resources can move to a blocking thread.** `CommandEngine` is `Send`, since its channel types already cross a thread boundary, and so is `ProfileLease`. Neither `MdkOwner::open` nor `enable_commands` keeps a reference to the profile. `timeout_at(deadline, &mut JoinHandle)` works without aborting the task.
- **Initialization order works.** `mark_ready(owner.opened_binding())` can move before `enable_commands`. Inside `enable_commands`, nothing fallible runs after `CommandEngine::start` (`command_runtime.rs:47-58`), so `open` can't fail after the engine is spawned. The fallible daemon setup (`signal()?`, `ipc::bind()?` at `daemon.rs:146-148`) currently runs outside the stop path, and the doc correctly requires moving it inside.
- **Fixture cleanup matches the real API.** `try_prepare_cleanup` and `fail_cleanup` exist. `into_cleanup` checks Exited state and process identity itself, through `cleanup::acquire` and `terminal`. `CleanupGuard` stays on the engine thread until Stop, and its parts only close files; none of them unlink on drop, so removing the subtree under a live guard and then dropping it is safe. The deletion primitive (held handles, nofollow, receipts, 4096 entries, depth 8) doesn't exist in code yet, but it's specified by the approved acceptance design rather than claimed as existing.
- **No overclaiming.** The doc never treats an engine-thread exit as proof that workers are gone, never reopens an engine, and treats an external kill as non-green.

Once R1 and R2 are in, I'd expect to approve without further design changes.
