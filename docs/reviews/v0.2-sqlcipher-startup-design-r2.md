**CHANGES_REQUIRED.** One blocker. Everything else in the revised design holds up against the pinned source.

I read only the design, r1, the pinned `sqlite3.c` and rusqlite 0.40.1 source, `Cargo.lock` and the relevant repo files. I made no edits and ran no Cargo, network or test commands.

### What I verified
- **The barrier mechanism is sound when it is the first caller.** In the first-initializing thread, `sqlite3_initialize` (`sqlite3.c:193434`) runs `SQLITE_EXTRA_INIT` (193599–193603) before it returns. `sqlcipher_init = 1` is set only on success (around 111383), so a returned `SQLITE_OK` from that thread means SQLCipher is ready. `OnceLock::get_or_init` blocks other callers until that first call finishes. No compiler flag or hook changes, so r1's blockers 1 and 2 (the `#error` and the STATIC_MAIN self-deadlock) no longer apply.
- **Caching the failure is correct and needed.** If `sqlcipher_extra_init` fails (`goto error`), `isInit` is already 1. Calling it again would hit the fast path and wrongly return `SQLITE_OK`. Caching the first `rc` is the only honest result.
- **The error types exist:** `EngineError::StorageFailure` (`cipher.rs:29`) and native `Error::Storage(&'static str)` (`error.rs:12`).
- **The repo opener list matches.** Production opens are at `cipher.rs:72`, `journal.rs:100`, `native_preflight.rs:27` and `mdk_adapter.rs:900/904`. Raw test opens are in the `cipher.rs` tests, `encrypted_storage.rs`, `faults.rs`, the `native_preflight` tests and `spool/tests.rs:255`. `launcher/tests.rs`, `store.rs`, `spool.rs`, `command_rooms.rs` and `command_store.rs` only use already-open connections. marmish-mdk, core, vault and prototype have no openers. rusqlite's implicit `sqlite3_mutex_alloc(0)` (`inner_connection.rs:432`) runs inside open, after the barrier.
- **Nothing weakens locking or encryption.** The design keeps NO_MUTEX ownership, key checks and the negative tests, and adds no shutdown/reset, retry or new dependency.

### Blocker: an in-process SQLite user is missing, and the "first initializer" requirement isn't stated
1. **The barrier only works if it is the process's first `sqlite3_initialize` caller.** At 193458, a thread that sees `isInit` already set returns `SQLITE_OK` immediately. Suppose an ungated thread starts initialization first and is still inside `sqlcipher_extra_init`. A barrier caller then gets `SQLITE_OK`, the OnceLock caches success, and gated opens race again. That is the original `sqlcipher not initialized 1` failure, with the barrier itself vouching for it. The design never states this requirement.
2. **That ungated caller exists: Tor's directory cache.** `Cargo.lock` shows `tor-dirmgr` depends on `rusqlite`, and `arti-client` (a direct marmish-native dependency, `Cargo.toml:60`) pulls it in. Because the workspace patch pins a single `libsqlite3-sys`, it links the same SQLCipher. It opens SQLite through `TorClient::builder()...create_unbootstrapped_async()` (`transport.rs:371–374`). The design's audit only searched repo `Connection::open*`, so it says "all database users in product processes are controlled by these boundaries", which is false as written.
3. **Production is currently safe only by call order.** Bootstrap runs only from `MdkOwner::activate(&mut self)` (`mdk_adapter.rs:1370`), which needs an already-opened owner, and the doc comment at `transport.rs:343` says the same. Nothing enforces this, though, and `Connector::bootstrap` is `pub` and called directly in tests (`transport.rs:1026/1051`).

**Required revision:**
- Call `marmish_engine::initialize_storage()` at the start of `bootstrap_inner` (before `TorClient` creation, at least on the `needs_tor()` branch). Map a failure to the finite `Storage("sqlcipher_init")`, like the other native boundaries.
- Add `tor-dirmgr`/arti to the exhaustive list.
- State the requirement plainly: every in-process SQLite user, including third-party crates found by walking `Cargo.lock` reverse-deps of `rusqlite`/`libsqlite3-sys` (today: engine, native, storage-sqlite, tor-dirmgr), must cross the barrier before its first SQLite call, because a later barrier caller cannot detect an initialization still running on another thread.
- In the post-implementation audit, re-check `Cargo.lock` reverse-deps as well as literal openers.

### Not blocking
- The `MdkOwner::open` claim is correct: once the barrier completes, `sqlcipher_init` is globally 1 for the rest of the process, so upstream storage-sqlite's internal connections are covered.
- In the regression test, have a child-side assertion fail if any non-barrier SQLite call happens before `initialize_storage()`. This keeps the test honest about point 1.

`★ Insight ─────────────────────────────────────`
- In this SQLite build, `sqlite3_initialize` only finishes SQLCipher setup before returning for the thread that did the initialization. Any other thread may return early.
- Crates that share one linked `libsqlite3-sys` share its initialization, so a dependency like arti's directory cache counts as an opener even though no repo code calls `Connection::open` for it.
