**CHANGES_REQUIRED.** The spawn-race fix (B1 from r1) is sound, but there is one new blocker. After the identity fix, `ChildOwner::signal` on a zombie leader will most likely still fail on macOS.

## Blocker

**B2: `kill(-pgid)` on a zombie-only group returns EPERM on Darwin, and the design leaves that unchanged.**

- The design says "Kill behavior and errno handling remain unchanged". `ChildOwner::signal` (`worker.rs:70-74`) tolerates only ESRCH and maps everything else to `RecoveryUncertain`.
- The repo already documents this behavior:
  - `docs/phases/macos-zombie-group-cleanup.md` records a native run (41394907662) where `/usr/bin/false` produced `group_signal_failed/permission_denied`. XNU `killpg1` skips `SZOMB` members and returns EPERM when none are signalable.
  - `docs/phases/native-lifetime-zombie-groups.md` records the same mechanism and the reviewed fix: accept EPERM only after a zombie-only group proof.
- Every ordinary macOS command completion hits this path.
  - At `worker.rs:624-627`, the leader has exited and the pipes are closed. Normally no descendants remain, so `signal(SIGKILL)` sees a group containing only the unreaped zombie leader.
  - Fixing the identity check (the arg1 helper) only moves the failure from `WorkerUnavailable` to `RecoveryUncertain`.
- The tests are affected too:
  - The planned native regression ("kill it, observe exit, signal its owned group, reap") fails at the signal step.
  - `worker/tests.rs:73` and `:88` fail the same way.
  - `Drop` (`worker.rs:113`) returns without reaping, because its signal call fails.
- Fast-exit capture at spawn is fixed, but the following supervision step then fails the same way.

**Required amendment** (the design currently treats this as unchanged):

1. State a Darwin-only EPERM rule and keep ESRCH as is.
   - EPERM is accepted only when the arg1 snapshot reports `pbi_status == SZOMB`, so add status to the snapshot struct.
   - The same snapshot must match the recorded identity, `pgid == pid` and parent.
   - A `waitid` WNOWAIT call must confirm the exit, and the leader must be unreaped.
2. Decide whether that is enough or whether the existing reviewed group-absence proof is reused.
   - Reuse means `lifetime_zombie_group` semantics: all visible members terminal across two snapshots.
   - Accepting EPERM on leader state alone could report success while same-user descendants with unusual state survive. Pick one and justify it.
3. EPERM with a live leader stays fatal. Wrong errnos, including EACCES, stay fatal.
4. Say what `Drop` does with a zombie-only group, which today leaks the zombie.
5. Add tests.
   - Zombie-only group with EPERM passes.
   - Live-leader EPERM fails.
   - Mismatched identity or group fails.
   - A zombie leader with a live descendant is still killed and reaped.
   - These need an injectable kill result or a Darwin-only test.

## Items that hold up

- **Fast-exit spawn capture.**
  - `launcher.rs:1122-1130` currently captures identity with arg0 after `spawn`.
  - `setsid` has already run because `spawn` returns after the exec handshake, so requiring `pgid == pid` is valid.
  - The unreaped `Child` holds the PID.
  - The parent check holds, because the only caller (`worker.rs:794`) and the tests spawn from the same process.
  - A capture failure still goes to `discard_spawned_child`, which is safe because it ignores kill errors and uses `waitid` WNOWAIT.
- **Unreaped PID and group ownership.**
  - The only reaper is `Child::wait` in `reap()`, after the last group signal.
  - The existing `Child` is stored privately.
  - A live-to-zombie transition between checks is harmless.
- **Zombie PGID.** `tools/native/marmish-lifetime-group.h:45-52` already relies on arg1 returning `pbi_pgid` for an `SZOMB` leader. The native zombie-group test is part of the hosted native workflow. I did not check its results.
- **Descriptor test.**
  - Opening the descriptor before the baseline, with `ceiling = max(64, max_fd + 1)`, is consistent with `prepare_spawn_below` (`macos.rs:401-407`).
  - The `ceiling - 1` case isolates the descriptor gate.
  - The fix removes the hard-coded 64 that caused the original failure.
  - The test is already isolated by re-executing the test binary under `MARMISH_TEST_DARWIN_FD_LIMIT`. State that the isolation is kept.

## Non-blocking

- The decoder-split suggestion (r1 improvement 5) is not adopted. The pure validation could then be tested under Linux.
