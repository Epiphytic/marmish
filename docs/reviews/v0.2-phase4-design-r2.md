## 1. Phase 2 amendment: CHANGES_REQUIRED

**Checked against the source and correct:**
- `Engine::status` reconciles. It calls `authorized_job`, then `reconcile_step`, and that path can start Accepted work or mark a job `UnknownLaunch`/`Lost`. So keeping status calls off the actor is the right call.
- `cancel` only records the request (`lib.rs:384-395`).
- `into_cleanup` takes the engine by value, checks UID, requires every job to be `Exited` and checks the recorded worker identity (`cleanup.rs:46-62`). It holds the frontend, job and IO locks inside `CleanupGuard`.
- `StateRoot::presence` returns Live, Initializing or Absent (`launcher.rs:598-623`).
- The 64 KiB frame limit matches Phase 2 line 481.
- Clients disconnecting don't cancel commands, which matches Phase 2 line 23.
- Engine state uses only 0700 directories and 0600 regular files, with no sockets, so the bounded delete walk can work.
- No raw PID path and no second database owner is introduced.

### Blockers

**A1. The worker-presence wrapper doesn't say clearly enough that it never reconciles.**
- Line 77 says it "uses existing authorized job/store identity". In the source, `authorized_job` is the path that calls `reconcile_step`, then `recover_absent`, then `start_accepted`, or `mark_unrecoverable`. Taken literally, a presence query could launch a worker or mark a job terminal.
- **Fix:** specify it as `owner(ctx)` (with `check_uid`) → `store.job_for` → `store.job_state` → `store.worker_identity` → `root.presence`.
  - It must make no `reconcile_step`, `recover_absent` or store writes.
  - Map `Live` with the recorded identity to `Present`.
  - Map `Initializing`, `UnsafePath` and any other error to `Unknown`.
  - Map `Absent` to `Absent`. It counts as `exited` only together with state `Exited`.
  - A job dir that is missing for an `Accepted` job must not count as exited.
- **Test:** an Accepted job with no directory gives `Absent`. The job stays `Accepted`, no worker is spawned, and the job's store row is unchanged.

**A2. A failed `into_cleanup` destroys the engine, and that lifecycle isn't defined.**
- `into_cleanup(mut self)` drops the `Engine` when it returns an error. It does that after a 5-second `Busy` retry loop, or straight away on `RecoveryUncertain`. "Failure preserves state" is only true of what's on disk. That daemon instance no longer has an engine.
- `{queued:bool}` plus `engine_quiesced:bool` can't tell "pending" apart from "failed".
- **Fix, part 1:** add to cleanup status `cleanup:"open"|"draining"|"quiesced"|"failed"`. Failure is terminal for that instance:
  - every engine-dependent IPC call and Marmot status/poll/cancel gets a finite `server_draining`/unavailable reply;
  - no reopen within that instance;
  - only an ordinary stop follows, and the run is red with state preserved.
- **Fix, part 2:** precondition. The harness calls `command_prepare_cleanup` only when `active=0`, `uncertain=0`, `worker_running=0`, `worker_unknown=0` and `observation_pending=false`.
- **Fix, part 3:** define what happens if `--max-uptime` expires, or an ordinary stop arrives, while the daemon is in `draining`/`quiesced` or holding the guard. The guard is dropped, the cleanup proof is lost, the run is red, and nothing is deleted.
- **Fix, part 4:** state that a job ending as `UnknownLaunch` or `Lost` makes cleanup permanently uncertain.
- **Tests:**
  - a live worker during prepare gives `failed`, the engine stays unavailable afterwards and nothing is deleted;
  - uptime expiring while the guard is held gives red with no deletion.

**A3. Cached evidence has no defined freshness relative to the quiescence proof.**
- Every evidence value comes from committed observations, which is good for authenticity. But a row has no observation sequence, and "final quiescent pass" is undefined. After the guard is taken nothing refreshes, so rows can freeze at `running`/`unknown`, or with stale `produced`/`closed` values.
- **Fix:** `command_prepare_cleanup` does a bounded final refresh before calling `into_cleanup`:
  - for each non-final row, an engine-thread status read and `owned_worker_presence`;
  - each result committed through CommitAck;
  - add `observed_seq:U64` to each `Evidence` row and `final_seq:null|U64` to cleanup status;
  - acceptance requires `cleanup="quiesced"` and every row to have `observed_seq ≥ final_seq`.
- **Tests:** a terminal job whose worker has exited but hasn't been observed yet shows `worker_state=exited` after prepare. A row with a stale sequence fails.

### Non-blockers
1. **max-commands wording conflicts with Phase 2.**
   - Phase 2 lines 511-517 say "allow admitted jobs to become terminal and bounded response drain" and have the supervisor reap on deadline. Add a precedence sentence saying the amendment replaces exactly those lines.
   - Make `--max-commands` require `--max-uptime`; the default is `None`, so `--max-commands` alone gives a daemon that never exits.
   - "Denials … retain their required credit" contradicts admission-only counting. A definitive refusal before the engine should release its credit immediately. Only uncertain reservations should keep it.
2. Line 70 says "never clears engine_known", but the field is named `engine_admitted`.
3. Line 17 says "matching owned job directory set". The source actually requires job directories ⊆ recorded jobs, with at most 256 jobs.
4. **Supervisor liveness check.** Use `waitpid(WNOHANG)` before the first unlink and after the last one, plus a same-socket `command_cleanup_status` reply showing `cleanup="quiesced"` after removal. A zombie daemon has already released its flock.
5. Add a worst-case encoded-row vector proving the 896-byte cap. Define what "uncertain" counts.
6. `command_local_cancel` is a product-visible same-UID capability. Record it in the spec's threat model and list its finite errors (busy/not_found/unknown).

## 2. Phase 4: CHANGES_REQUIRED

**r1 resolution:**
- **B1, resolved** by the amendment. Line 63 correctly labels the gates "unimplementable, not passable".
- **B2, resolved:**
  - four waves, at most four concurrent jobs;
  - a mandatory onion owner with RelayReady by minute 15;
  - a 60-minute owner lifetime, which covers minute 50 plus 5 minutes;
  - one run attempt.
- **B3, resolved:**
  - admission stops without stopping the daemon;
  - the daemon is stopped only after ClientTerminal records or a failed deadline;
  - retries reuse the same invocation;
  - negative tests run in separate profiles.
- **B4, resolved:**
  - the receipts directory comes from the fixture's canonical executable;
  - argv carries only the nonce, vector ID and fixed vectors;
  - private cwd, no writes under passwd HOME.
- **All eight r1 non-blockers** are folded in: build-job pinning, manifest/inode provenance, ±120 s skew, per-pair cap, goodput formulas with 1 cold + 3 warm runs, trigger restrictions, worker passwd HOME, and the macOS Arti dependency on Phase 1 with the stdin race kept out of the main vector.

### Blocker

**P1. Server uptime expires before protected cleanup can run.**
- A matrix server launches at minute 15–20 with uptime of at most 30 minutes, so it expires at minute 45–50. Clients run until minute 45 and cleanup runs at 45–50.
- The amendment needs that same daemon alive, in prepare and holding the guard, through engine-subtree removal. A server launched at minute 15 dies right at minute 45, so every cleanup is red, or someone is tempted to delete without proof. Qualification profiles have the same problem.
- Lines 294-296 also order things wrongly. They ask daemons to stop and then cancel workers, but local cancel needs a live daemon.
- **Fix:** freeze `U = min(30m, remaining)` at launch, then:
  - client deadline = `launch + U − 6m`;
  - local cancel of any remaining fixture rows → poll cleanup status → `command_prepare_cleanup` by `launch + U − 5m`;
  - removal finished and the daemon's liveness re-proved by `launch + U − 1m`;
  - ordinary stop → reap → remove the remaining profile.
  - Readiness must still leave at least 20 minutes for clients. If not, fail before clients start.
- **Test:** an offline schedule check rejects any cohort where prepare plus removal can't finish before the frozen uptime runs out.

Phase 4 also carries over A1–A3 until the amendment passes.

### Non-blockers
- The grant is path-based. Re-hash the fixture both before launching the server and before cleanup.
- In the restart qualification, prepare cleanup only on the final daemon instance, and check evidence-cursor continuity across the restart.
- The `--max-commands 4` benchmark servers follow the same P1 timeline.

`★ Insight ─────────────────────────────────────`
- Engine methods that look like reads aren't always read-only. In this engine `status` can launch a worker, which is why the new presence wrapper has to name the exact read-only path it uses.
- `into_cleanup(mut self)` uses Rust's consuming ownership to prove nothing else can use the engine. The catch is that a failure destroys it too, so the design has to say what the daemon does afterwards.
- Phase 4's minute-by-minute schedule assumed cleanup could happen after the server's uptime ran out. Under the amendment, cleanup has to fit inside that uptime.
