## What I checked

- **The change is only what you described.** I reverted the new `mkdir`/copy lines and changed `--input-dir` back to `$GITHUB_WORKSPACE/target/release`. The result hashes to r3's `6039e7cc…213b` byte for byte. So the diff is exactly: one `mkdir`, a comment, and a copy of the three fixed binary names into `$RUNNER_TEMP/package-input`. Every other step is unchanged.
- **Failure behaviour.** GitHub's default shell is `bash -e`, so a failed `mkdir` or `cp` stops the job. Because `mkdir` has no `-p`, the step also fails if the folder already exists. Only `marmish`, `marmishd` and `marmish-worker` are copied, so the extra `marmish-release-tool` binary from N6 can't end up in the package.
- **The copies match what was signed and inspected.** `cp` writes a new single-link file with the same bytes. The macOS ad hoc signature is stored inside the binary, so the copy keeps it. The packager then reads its provenance and hashes the copy, so the manifest describes the bytes actually uploaded.
- **The link check stays strict.** No Rust code changed, so the packager still rejects input files that are hard links.
- **actionlint passes** (run without shellcheck).

## Nonblockers

1. The copy isn't compared back to the original. Adding `cmp "target/release/$binary" "$RUNNER_TEMP/package-input/$binary"` inside the loop would prove the bytes that were inspected are the bytes that were packaged. Running the inspection script against `package-input` instead would also do it.
2. The render tool upload still comes straight from `target/release`, where it is hard-linked. That's fine for an artifact upload and it is never an install asset.
3. The earlier open items still stand: N2, N4, N6, N7 and N9 from r1, plus the r3 and r4 nonblockers.
