**Verdict: APPROVED** — this approves the design of `docs/phases/v0.2-phase1-retention.md` (revision `4eb3839981cefedd`, 202 lines) only. It is not code approval or phase approval. The implementation still needs its own independent review. No blockers remain. I made no edits and ran nothing live.

**B3 is fixed** (lines 90–98 and 113–119 of the doc):
- When a room has never been accepted, a policy rejection (untrusted peer, purpose/membership/admin mismatch, missing author, invalid session) is forgotten and acknowledged without writing a rejection row or moving the admission frontier.
- Policy is checked before capacity. Only an allowed peer whose room passes every policy check can write a capacity-refusal record or move the frontier. So people with only our public KeyPackage can no longer block new admissions.
- Rooms that were accepted and later revoked keep their durable authority and rejection history until the retirement rules say they can be collected. They never take the shortcut, so no authority check is weakened.
- The new acceptance case (a flood of unsolicited or policy-invalid Welcomes leaves row counts and the frontier unchanged) tests this directly.

**Orphan enumeration is fixed** (lines 142–149). The union of `live_group_ids`, `unhydrated_group_ids`, `quarantined_groups` and `outbound_fanout_group_ids` matches the pinned `AccountDeviceRuntime` APIs, and covers the groups that `live_group_ids` alone misses.

**B1, B2 and R1–R4 are unchanged** from what I confirmed last round.

**Two notes for the implementation review (not blocking):**
1. When an orphan is rejected, it may write a row or move the frontier. That's fine because orphans only come from our own room creation, which only we can trigger. The implementation should still run the normal policy checks first: if the orphan's metadata is itself invalid, it should take the no-row path.
2. Policy re-evaluation uses the current allow-list. If a peer is added later, a Welcome they previously sent and we rejected could be accepted if it's redelivered, but only while its session timestamp is still within the freshness window. That fits the design; a test that pins this behaviour would help.
