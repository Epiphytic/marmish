**Verdict: APPROVED.** I found no blockers. I edited nothing and ran no Cargo, network or live tests. `installed_benchmark.rs` has no diff against HEAD, so I reviewed the plan against the source as committed.

**The plan matches the logs**
- `outcomes.txt` shows both tests exited with status 101. `source.txt` pins source `9d28523…`, which is the same product tree as the original failing source `347cf79`.
- **Case 3:** the test panicked at `:1641` with `outer_error=Some(Timeout)`, and the replay with a fresh 3s deadline exited 0 and printed a handle. So the shared 80ms budget ran out during submit itself (30ms sleep plus `/bin/sh` and `cat` startup), before the wait step started. That fits the doc's diagnosis.
- **Printf:** the test panicked at `:1720` with `unix_wait_status(9)` and empty stdout and stderr, and the whole test finished in 0.04s. That is a SIGKILL, not the 2s deadline expiring. The Python probe cases all returned 0, so the doc is right not to claim it reproduced the failure or to name a mechanism.

**Case 3 fix (2s deadline, wait sleeps 10s, elapsed under 3s) works**
- `Client::command` (`:566`) uses one deadline for both submit and wait. When the deadline wins the race in `execute`'s `select!`, the result is an inner `Err(Timeout)` while the outer result stays `Ok`, so the handle, locator, `sw` calls marker and byte checks still run.
- The wait script has to sleep for 10s. With a 2s budget, `sleep 1` would finish, hit `exit 7`, and fail `exact_output` instead of timing out.
- On timeout, `terminate` kills the whole process group (`process_group(0)` plus `kill(-pid, SIGKILL)`) and reaps the child. So `/bin/sh`'s `/bin/sleep 10` child is killed too and doesn't hold the pipes open. Elapsed will be about 2s plus the kill and reap time, which fits under 3s.
- The other cases keep their 1s budgets and the `>= 30ms` check. No product deadline changes.

**Printf fix (rename the copied sleep, then copy printf to the empty path) works**
- Before the rename, both earlier `execute` calls have already killed and reaped the sleep child, through `terminate`'s `child.wait()`.
- Renaming keeps the old inode alive under `bin/retired-sleep`, so the filesystem can't hand that inode number to the new printf copy. That makes the distinct-inode assertion meaningful.
- The existing sleep test's timeout check, the cancellation (`installed_interrupted`) check, the expired-deadline check against a missing executable, the status and byte assertions, and the no-retry rule are all unchanged.

**Optional improvements for the implementation**
1. Case 3 is currently picked out by `wait_body.contains("sleep 1")`. That string also matches `"sleep 10"`, so it would keep working, but it's fragile. A per-case deadline or flag in the tuple would be clearer.
2. Compare `(dev(), ino())` rather than `ino()` alone, using `MetadataExt`.
3. A test limitation the plan neither causes nor fixes: an "under 3s" bound can't tell one shared deadline from a fresh deadline for the wait step, because submit only adds about 30–80ms. The old 80ms/500ms version had the same weakness. If you want the test to actually prove one deadline, a later change could make submit take a large share of the budget and check a tighter upper bound. This is not a blocker.
4. The plan's "all 10 focused benchmark tests" matches the 10 test functions in that module's `tests`.

`★ Insight ─────────────────────────────────────`
- On macOS, `fs::copy` onto an existing path truncates and rewrites the same inode. The kernel caches code-signing state per file, so rewriting a signed binary that has already run is a known cause of SIGKILL ("Killed: 9"). Creating a fresh file avoids that.
- Renaming instead of deleting keeps the old inode in use, so the inequality check can't pass or fail because the filesystem reused an inode number.
- Because the child runs in its own process group, killing the group also kills its children, so a timed-out shell can't leave a grandchild holding the stdout or stderr pipes open.
