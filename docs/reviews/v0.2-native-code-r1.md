## Blocking findings

**B1. Retained work is published before the account is active, so activation and restart fail.**
- **Where:** `mdk_adapter.rs:694-699`.
- **What happens:**
  - `activate()` runs `drain()`, `apply_effects()` and any receipt sends before `activate_transport(None)`.
  - Upstream `publish` returns `AccountNotActive` until the account is active (`transport-nostr-adapter/src/lib.rs:3577-3583`). The runtime records that as a target failure with a backoff starting at 30 s.
  - `apply_effects` then returns `publication_failed` (`:1216`), so `activate` fails.
- **Effect:** any restart with an unacknowledged fanout or a pending receipt cannot activate. This likely blocks the restart stage.
- **Fix:** call `activate_transport` after relay admission and before the first `drain`.

**B2. One per-relay failure ends the daemon.**
- **Where:** `daemon.rs:149` (`owner.tick(...) => result?`), `mdk_adapter.rs:1216` (`publication_failed`), and `ensure_ingress` at `:1240`.
- **What happens:**
  - Any tick error stops the daemon.
  - A failed Welcome (`welcome_failures`) or a one-relay `failures` entry becomes a hard error after its effects were already applied.
  - A stopped forwarder also stops the daemon. Upstream stops it on `Lagged` or when its internal queue fills; the 64-slot notification channel at `:656` makes lag likely.
- **Fix:**
  - Treat publication failures as journal and status state, and keep ticking.
  - Supervise and restart the forwarder using `notification_loss()`, with a re-sync, instead of failing.
  - Reserve fatal errors for storage or authority corruption.

**B3. Welcomes and queued sends are never driven again.**
- **Where:** `mdk_adapter.rs:1216`.
- **Unhandled Welcome failures:**
  - Nothing calls `redeliver_welcome` (`runtime.rs:6940`, `welcome_delivery.rs:310`).
  - `open_conversation` journals the conversation before the error surfaces. The next call returns that conversation, so the peer may never be invited.
- **Unhandled queued work:** the adapter never reads `effects.queued` or `pending_convergence`, and never calls `advance_convergence`. Upstream `send` can queue instead of publishing (`cgka-engine/src/message_processor/mod.rs:881-940`), and `IngestOutcome::Buffered` needs the same driver. Those sends stay "prepared" until a restart marks them "uncertain".
- **Fix:**
  - Redeliver failed Welcomes with bounded retries.
  - Call `advance_convergence` for groups that have queued or pending work on each tick.
  - Handle the `QueuedIntentRefused` event so its row does not stay "prepared".

**B4. Transient errors permanently revoke conversations.**
- **Where:** `mdk_adapter.rs:597-623` (`rebuild_routes`) and `:952-975` (`ensure_trusted`).
- **What happens:**
  - The `_ =>` arm treats any `check_group` error as a terminal trust failure: a storage read error, an `Err` from `bind_authority`, or a quarantined group. It revokes and calls `forget_group_local`, which deletes the group.
  - This runs on every 100 ms tick and in every `apply_effects`.
  - Changing `--allow-peer` also wipes existing conversations without warning.
- **Fix:**
  - Revoke only on a definite authority mismatch.
  - Pass I/O and storage errors up without revoking.
  - Skip groups that are already revoked: forgetting them again is idempotent but opens a `secure_delete` write transaction every tick.
  - Call `sync_transport_groups` after removing routes, which the tick never does.

**B5. Receipts and rejected messages can be lost.**
- **Rejected messages:**
  - At `:1073`, a `MessageReceived` from an untrusted or unaccepted group is deleted from the pending queue with no journal "rejected" row, which the design requires.
  - Pending events come back in queue order, so a message listed before its group's `GroupJoined` is deleted rather than processed.
  - Fix: defer events for groups that have a pending `GroupJoined` in the same batch, and journal a rejection before deleting.
- **Receipts:**
  - Pending events are deleted before the receipt `send` loop at `:1202`.
  - Any error aborts the remaining receipts, which exist only in memory. Causes include a timeout, `rebuild_routes` at `:1201` forgetting the group, or a nested `publication_failed`.
  - `replay_pending` (`:1220`) then marks them "uncertain" and never sends them.
  - A receipt never sent has no fanout and was never encrypted. Re-sending the identical deterministic payload is therefore safe and keeps the "no fresh ciphertext for exposed data" rule.
  - Fix: persist the receipt intent and resend it when no fanout exists.

**B6. Relays are never reconnected.**
- **Where:** `mdk_adapter.rs:655` (`.reconnect(false)`).
- **What happens:** there is no health check or re-admission. A dropped TCP connection or Tor circuit leaves the daemon "active" but deaf. Activation's three connect attempts also have no backoff.
- **Fix:** keep the Tor-only, no-direct-fallback rule, but re-admit through the same `RelayConnector` with bounded backoff, then call `sync_transport_groups`.

**B7. A vault helper test fails, and clippy does not catch it.**
- **Where:** `crates/marmish-vault/src/bin/marmish-keychain.rs:2-4`.
- **What happens:** the new binary exits with empty stdout when given an extra argument. The existing test `tests/helper.rs:44` (`malformed_requests_and_arguments_have_fixed_nonsecret_errors`) expects the fixed `{"version":1,"ok":false,"error":"malformed"}` line.
- **Fix:** write that fixed response before exiting, or route argument rejection through `helper::run`.

## Nonblocking improvements

**Upstream-contract follow-ups**
- Log `effects.outcome` (for example `Ignored{category}`) on ingest. Join rejections are currently invisible; only `no_application_events` is logged.
- When `apply_effects` errors, `ack_replay_delivery` is skipped (`:1282`), so replay placement pins leak.
- A `bind_native` conflict, or more than 4096 pending events (`:1019`), puts every tick into the same error loop.
- `replay_pending` can mark a send "uncertain" when `outbound_fanouts_for_group` returns empty for a quarantined group. This is recoverable, since uncertain→published is allowed.
- Routing-only failures, such as `MissingGroupRoute`, never appear in `failed_app_messages`, so their journal rows stay "prepared".
- Welcome publication targets the sender's own relay list (`ExplicitRouting` inbox routes). Document that both peers must share a relay, or discover the peer's inbox relays.

**Local hygiene**
- In `journal.rs`, `PRAGMA cipher_compatibility` and `page_size` run before `sqlite3_key`, so they likely have no effect. Set them after keying, or assert that they read back.
- `identity.rs` grows the helper response buffer without preallocating, so reallocations can leave secret copies in freed memory. Use a preallocated `Zeroizing` buffer.
- `ipc.rs`: an error from `accept` ends the server. Log it and continue.
- Running the full drain and `check_group` on every conversation every 100 ms is expensive; drive it from events instead.
- The SDK's internal outbound queue is fixed at 1024 while the app and notification queues are 64. The doc refinement you mentioned is still pending.
- The `/tmp/mr2-<uid>-…` runtime directory can be pre-created by another user. Ownership and mode are checked, so this is only a denial-of-service risk.
