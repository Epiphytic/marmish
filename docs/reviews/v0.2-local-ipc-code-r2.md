## Blocking

**B1. Some local failures on the remote-command path still don't exit 255** (the remainder of r1 B3)
- **Where:** `cli.rs:437-441`, `cli.rs:447`, `cli.rs:457-459`, and `failure_code` at `:462`.
- **Problem:** three kinds of failure happen before `failure_code` is computed:
  - an invalid layout (for example a damaged managed install) returns `ExitCode::FAILURE` (1);
  - a Tokio startup failure also returns 1;
  - clap usage errors from `Args::parse_from` exit 2, for example `marmish --wait-seconds 0 host -- /bin/x`.
- **Why it matters:** phase2 lines 532-535 require 255 for local, transport and policy errors. A script can't tell exit 1 or 2 here from a real remote `/bin/false` or a remote exit 2, and clap's message is not a `marmish: <category>` line.
- **Remedy:**
  - Keep the `argv[1]=="_vault-helper"` check first, with the layout resolved before it.
  - For every other invocation, run `Args::try_parse_from` first. It needs no state, provider or profile.
  - Map every clap error except help/version to 255, or decide by `command_action`.
  - Then resolve the layout and return `failure_code` if it fails. The layout is still resolved before any provider or profile access.
  - Add exit-code tests for a layout failure and a usage error on a remote invocation.

**B2. The new admin IPC methods don't return the finite results the design specifies**
- **Where:** `daemon.rs:103-113`, `command_local.rs:122-132`, `command_service.rs:438-450`.
- **What the design requires** (acceptance-interfaces lines 134-148): `command_local_cancel` returns `{queued:bool}` or a finite `busy`/`not_found`/`unknown`/`server_draining`, and `command_prepare_cleanup` returns `busy`/`server_draining`.
- **What happens now:** errors go through `daemon::failure`, which turns every `Error::Invalid(_)` into `invalid_input` and every `Storage(_)` into `storage`. So `command_not_found`, `server_draining`, `command_fixture_unknown`, `command_cleanup_busy` and `commands_disabled` can't be told apart. The harness can't decide between retrying (busy) and giving up (not_found or draining).
- **Also:** `queued` is always `true`. A terminal row registers no Cancel operation but still reports `queued:true`.
- **Remedy:** have `command_acceptance` map errors to the design's finite category strings itself. Have `cancel_fixture_invocations` (or a key-based variant) report whether it actually enqueued, and return that as `queued`. Add tests for each category.

## Non-blocking
1. **Missing reserved names.** `command_config.rs:435` doesn't reserve the new hidden subcommand names (`command-evidence`, `command-cleanup-status`, `command-local-cancel`, `command-prepare-cleanup`). The local-client design says aliases that collide with subcommand names must be rejected. Today such an alias just causes a clap error. Fix before acceptance.
2. **`command_room_pending` on the first Submit is treated as ambiguous.** See `command_local.rs:240` and `command_cli.rs:1116-1121`. On the first attempt this error definitely means nothing was admitted, because a committed retry would have attached through `local_owner`. Instead the CLI loops for the whole wait budget (180 s by default) and may exit 254 with a handle that doesn't exist. That is safe, but it goes against "254 only while admission is unconfirmed". Treat it as ambiguous only after an earlier ambiguous attempt.
3. **Local cancel matches by invocation ID, not by cursor.** `command_local.rs:124-126` resolves the cursor to a row, but `cancel_fixture_invocations` (`command_service.rs:402-431`) then matches only the invocation ID, scanning every server row synchronously on the actor. If two principals reuse an invocation ID, it fails closed with `command_fixture_unknown`. Select by the row's `InvocationKey` and skip the full scan.
4. **Count exit and explicit cleanup can collide.** `daemon.rs:226` and `command_local.rs:140-144` evaluate count exit without looking at the cleanup state. On a daemon started with `--max-commands`, auto-exit fires once finished==admitted. Prepare-cleanup and the protected engine removal therefore can't run on that daemon, and an exit while draining or quiesced drops the guard. This comes from the two designs fitting together, not from a code defect. Either document that the two acceptance flows run separately, or suppress count exit while cleanup is not open.
5. **Count exit can stall until uptime.** The pending-events check is unfiltered. Any `GroupEvent` whose `pending_key` is None (`mdk_adapter.rs:1878`) is never processed, so it blocks count exit until uptime. That fails safe, but it would fail standalone auto-exit acceptance. Record it, or test that only the known variants can occur.
6. **Shutdown report output.** `daemon::stop` now prints the shutdown report, so `marmish init` emits two JSON documents (`cli.rs:273-281`, `daemon.rs:184`). Also, `println!` panics on EPIPE if the supervisor has closed stdout. Use `writeln!` with an error path, and decide what `init` should print.
7. **Launch time is captured late (carried over).** A manually started `daemon` without `--relay` loads config (`cli.rs:257`) before `ServiceLifetime::start` (`daemon.rs:31`).
8. **Autostart and layout reuse.**
   - Autostart still doesn't `try_wait` the child, so a daemon that dies at startup costs the full 15 s (carried over).
   - Autostart works out the `marmishd` path from `current_exe` instead of the resolved layout.
   - `daemon.rs:96` resolves the layout again instead of reusing the one resolved at startup. The phase3 design says to reuse its paths.
9. **`marmishd` will run client actions.** `command_action` (`cli.rs:252`) is checked before the `daemon_binary` refusal at `:287`.
10. **Misleading categories.** `fixed_hex` still reports IPC input errors as `command_room_binding` (carried over). Prepare while draining reports `command_unauthorized` instead of `server_draining`. The CLI's `prepare()` still folds every Failure category into `command_prepare` (carried over).
11. **Misleading comment.** `command_local.rs:99-100` says the admin methods "never reconcile or launch engine work". In fact LocalCancel enqueues `EngineOperation::Cancel` and PrepareCleanup allocates a fence. Fix the comment.

## Checked and found correct
- **r1 B1 fixed:** `validate_separator` requires `--` immediately after the destination (`cli.rs:317-322`, `:419`), and the test covers `-i`, `--detach` and stray positionals.
- **r1 B2 fixed:** autostart runs `setsid` in `pre_exec` and a reaper thread waits on the child (`cli.rs:336-345`, `:381-382`). The test asserts both sid and pgid.
- **r1 B3 mostly fixed:**
  - `command_cli::run` maps errors to 255, or 254 for `unknown_launch`/`lost`.
  - `failure_code` is 255 for command actions.
  - `--max-commands`/`--max-uptime` are refused on anything other than `daemon` (`cli.rs:206`).
  - The pre-dispatch gaps are B1 above.
- **r1 B4:** the store probes `table_info(command_invocations)` and adds the missing columns (`command_store.rs:622-634`). I did not review this in depth; the migration owner covers it.
- **Exact Submit retry:** `local_owner` re-checks current authority on every retry. That covers relay policy equality, `can_open`/trust/not-draining, a non-revoked `command_context`, and `validate_entry` (profile, local account, digest). It then attaches through the store's original-submit check. New submissions still need `command_ready_room == session`.
- **Count exit:**
  - The full CountDrain predicate is combined with durable source ACKs (incoming and outgoing unacked or quarantined, early invalidations, queued bindings) and an empty native pending-event list.
  - It is evaluated at the top of the loop after each committed turn.
  - Without N configured it is never ready.
- **Evidence paging:** rows over 4096 bytes are rejected without truncation, pages are cut at 64,000 bytes on row boundaries with the actual last cursor returned, `next` is correct, and the limit is 1..64.
- **Cleanup status:** it reads a cached snapshot, which `tick` refreshes through `process_completions` → `advance_cleanup`/`cleanup_snapshot` (`command_service.rs:393-394`). `engine_quiesced` always equals `cleanup=="quiesced"`, and `begin_cleanup` re-checks the counts and allocates the fence.
- **Worker probe:** the layout is validated before `release-info`, the argv match is exact, and it opens no state or provider.
- **Startup order:** the layout is resolved before vault-helper dispatch and before any provider or profile access.
- **Smaller fixes:**
  - The numeric-host guard uses `url::Host::parse`, which rejects `0x7f.1` and `2130706433`.
  - `fixed_hex` now requires canonical lowercase.
  - Journal format constants are `5` / `[0,3,4,5]`.
  - All 64-row command pages fit the frame.
