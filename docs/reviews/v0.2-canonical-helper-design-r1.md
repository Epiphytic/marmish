# Canonical helper design review r1

Actual Claude Code (`claude-sonnet-5-5`) `--permission-mode auto`; session `480650f9-1d97-40e0-8e05-cd67d8c7c394`. Read-only independent design review, no tests or provider runs.

**CHANGES_REQUIRED**

The design is sound against the source, but it has three blockers. Each needs only a sentence or two in the doc, with no change to scope. I read files only and ran no tests, live commands or network.

**What the source confirms**
- **Setup and daemon use different helpers.** In the managed branch, `native_layout.rs:70-74` picks `parent.join(name)` as the helper, except `marmish-worker`, which maps to `marmish`. So `marmishd` uses itself as helper, while setup through `marmish` uses `marmish`. That matches the doc's premise.
- **Ordinary branch.** `native_layout.rs:87-91` makes every non-worker frontend its own helper, which is the same split.
- **`marmishd init` loads credentials.** `cli.rs:383-420` runs `daemon::open` with `layout.helper`, so the proposed fresh `marmishd init` check does exercise the helper.
- **Installed `marmishd` launcher exists.** `LAUNCHERS` in `native_install.rs:19` includes `marmishd`.
- **Strict checks stay in place.** `executable()` is `trusted_worker_executable`, which canonicalizes, checks owner, mode and every ancestor. The managed branch also keeps `read_version`, the compiled-metadata equality check and the per-file `safe_file` checks (`native_layout.rs:49-68`). The doc keeps all of these.
- **Downloaded exception.** The code (`native_layout.rs:79-99`) matches the name `marmish-<CARGO_PKG_VERSION>-<target>`, which is its own helper with an unvalidated worker path. The doc's description is faithful. In a claimed install, `NAMES[..3]` already rejects that name.
- **Retained versions persist.** `native_install.rs` only unlinks temp and staging entries, never `versions/<id>`. The existing test confirms the version directory survives uninstall.
- **Retained-version lifetime holds in the code.** `resolve` canonicalizes `current_exe` once, and helper and worker are `parent.join(..)` of that canonical version directory. Nothing re-reads `current`.

**Blockers**
1. **Fresh `marmishd` init must not go into `reload()`.** The Python lifecycle `run` (lines 420, 439, 444, 462) inherits `Qualification.reload`. Folding the `marmishd init` into it would change lifecycle A/B mode, where A is `0.2.0-rc.1` with the old per-frontend helper. The doc says the lifecycle contract is unchanged but doesn't say how. Require a separate method, for example `daemon_reload`, called only from `Qualification.run` before `fresh_reload=True` at line 339 and in the post-unlock block. It must not be added to `reload()`.
2. **The managed-branch retention test can't be written as worded.** The installer `Fixture` only produces one version at the compiled metadata, so no second version can be selected to show a retarget fails to move the helper. State what the managed test asserts:
   - Resolve through the actual launcher paths `bin/marmish`, `bin/marmishd` and `current/marmish-worker`, not just canonical ones.
   - Every returned `helper` equals the canonical `versions/<id>/marmish`, and every `worker` equals `versions/<id>/marmish-worker`.
   - Neither contains `current`.
   - Both survive `Uninstall`.

   Put the selector-retarget test in the ordinary branch only, which the doc already covers with a symlink. Say plainly that the managed test cannot cover a retarget.
3. **There is no control for the Mac evidence.** The doc correctly leaves Keychain causation unconfirmed and keeps denial red. But a green post-fix run alone can't show the fix addressed the reported denial, or that the new check can fail at all. Require the same ordinary-provider check and the real-Mac diagnostic to be run on a pre-fix build (`49d1314` or equivalent) with the result recorded. Without that, a green post-fix run shows only that frontend credential loads work now. Also reword line 13's "should use the same image after this fix" as a prediction to verify, not a result.

**Non-blocking, worth one line each**
- **Rust lifecycle harness.** `installed_version_lifecycle.rs:1717-1800` and the lifecycle phase doc treat retained `marmishd` as the A helper. That stays valid only while A is an older pinned release. State this, or note that the harness needs updating if A is ever built from this source.
- **Downloaded-CLI test.** Add one case: the downloaded name next to existing `marmish` and `marmishd` siblings still selects itself. Another case: `marmishd` or `marmish-worker` names never get the downloaded exemption.
- **Downloaded worker path.** Say that the downloaded branch keeps its unvalidated worker path. It is checked later by `worker_preconditions`.
- **Missing sibling `marmish`.** A `marmishd` with no sibling `marmish` now fails closed. The same was already true of the worker sibling, so this is a consistent tightening, but say so.
