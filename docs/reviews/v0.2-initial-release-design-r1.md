## What already matches the code
- **Build outputs:** `cargo build --locked --release -p marmish-native --bins` builds exactly the three products plus `marmish-release-tool`. The two installed-check bins need a feature flag, so they are skipped automatically. That matches "no installed-checks feature".
- **Five files per target:** `package` writes the three products, the license text and `marmish-0.2.0-<target>.manifest`, then re-checks its own output before returning. It refuses to write into an existing output directory, so earlier artifacts can't be overwritten.
- **Render checks:** `render` checks version, target, commit and formats for all three targets, verifies each target's files against its manifest, and pins the three manifest SHAs. It fails if any `@MARMISH_` placeholder is left. So reusing `render` unchanged is correct.
- **Artifact names don't collide:** the download pattern `v02-initial-assets-*-RUN-ATTEMPT` cannot match `v02-initial-render-tool-…`.
- **Installer URL:** it downloads from `releases/download/v$version/<name>`, so the bootstrap only works once the `v0.2.0` release holds these exact 15 files. Being a prerelease doesn't affect that URL.
- **No accidental publish on tag:** no existing workflow runs when a tag is pushed, and `release.yml` only runs when dispatched by hand. Root's manual `v0.2.0` tag won't trigger a stray publish.
- **Source is reachable:** `347cf79…` is current HEAD, so it will be a strict ancestor once the workflow commit lands.
- **Provenance is honest:** the existing HTTPS resolver only accepts `v02-release.yml` candidates. The design deliberately doesn't pretend this new run is one, which is the right call.

## Blockers
1. **Restrict the workflow to master and record the run's own commit.** The existing release workflow only runs from `master` (`if: github.ref == 'refs/heads/master'`). The new design drops that. Because the source pin lives inside the workflow file, anyone who can push a branch could dispatch an edited copy from that branch. It would produce artifacts and an `install.sh` whose names look the same. The design should say:
   - add the same master-only condition to every job;
   - root takes assets only from a run whose head branch is `master`, whose workflow file is `.github/workflows/v02-initial-release.yml`, and whose run commit (`github.sha`) is the reviewed workflow commit;
   - that run commit is written into the evidence.
2. **Say exactly what "strict ancestor of workflow HEAD" means.** After checking out the source, `HEAD` *is* the source commit, so an ancestry check against `HEAD` proves nothing. The design should require `git rev-parse HEAD == source` and `git merge-base --is-ancestor source "$GITHUB_SHA"` with source ≠ `$GITHUB_SHA`. Optionally also require that source is an ancestor of `origin/master`, as the old workflow does.

## Useful refinements (not blocking)
- **Re-run default tests on the new build.** The package job should run the same non-feature `cargo test --locked -p marmish-engine -p marmish-native -p marmish-vault` and clippy as the old "Verify native components" step. These are basic checks, not the acceptance gate. Run 41655210565 passed them on the same source, but these are newly built bytes and the check is cheap. If you skip it, the release notes should say they rely on run 41655210565.
- **Count the files in the render job.** After `merge-multiple`, assert there are exactly 15 regular files with the expected versioned names and nothing else. `render` reads only what it looks for and would silently ignore extra or misnamed files.
- **Tag the source commit.** The design should say `v0.2.0` points at `347cf799…`, not at the workflow commit or the later bootstrap commit. That keeps `--release-info`, the manifest `commit` line and the tag in agreement.
- **Make the release notes specific.** They should name the two failing macOS feature-enabled tests (426 passed, 2 failed) and give the evidence run IDs. They should also state that macOS binaries are ad-hoc signed and not notarized, and that HTTPS bootstrap proof is pending for v0.2.1.
- **Give it its own concurrency group** (e.g. `marmish-v02-initial`, no cancel-in-progress) and keep the 90-minute and 5-minute timeouts.
- **Write out the post-render checks.** Before mirroring the bootstrap, root should check that its three SHA pins equal the SHA-256 of the three published manifests and that the published bytes match the artifact bytes. This is the external byte check the design already implies.

When both blockers are added to the design, this becomes APPROVED.
