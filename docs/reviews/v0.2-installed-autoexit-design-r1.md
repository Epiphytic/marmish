## Blocking findings

**B1. You can't reconstruct or record the Submit request after `--detach`.**
- **Design:** lines 90–93 say to "discover the original Submit response by its bounded durable entry; reconstruct its expected request…". The Terminal record also has `submit_request_id` and `submit_request_sha256`.
- **Source:**
  - The CLI makes a fresh random `request_id` (`command_cli.rs:1070`) and never prints it.
  - `CommandHandle` deliberately leaves out request IDs (`command_client.rs:8`).
  - On `--detach`, the CLI waits for the authenticated Submit answer and consumes it (`apply_answer`→`consume`, around `command_cli.rs:782`). Only then does it return 0.
  - After that, `CommandUnconsumed` no longer lists the answer, and `CommandResponse` fails with `command_response_consumed` (`command_local.rs`, `local_answer`).
  - So the design's step can't be carried out, and those two record fields can't be filled truthfully.
- **Fix:** remove the reconstruction step and both fields. Bind the submission this way instead:
  1. Require `--detach` to exit 0, with empty stdout and exactly one stderr line `marmish handle: <closed json>`. Parse it with deny-unknown-fields.
  2. Look up `CommandInvocations` for exactly that handle. Require authenticated admission, `authority_valid=true` and no refusal.
  3. Cross-check the handle's `submit_sha256`, session and invocation against the server's cleanup Evidence row (`submit_sha256`, session, invocation, `engine_admitted==1`) and the fixture receipt.
  4. State explicitly that a `--detach` exit of 254 (`local_pending`), 255 (busy) or anything else is a red `submission`. It must never be retried in a way that creates a second invocation.

**B2. The ceiling on the uptime cohort's cleanup restart breaks the amendment's rule.**
- **Design:** lines 188–189 restart "under max_commands2".
- **Controlling rule:** the amendment (lines 54–57) says that for every protected-cleanup cohort, the ceiling equals planned admissions + 1. The uptime cohort has 0 durable admissions and 0 planned ones, so the ceiling is 1.
- **Source:** a ceiling of 1 is valid, because `max_commands` only requires a non-Client role and a non-empty `execution_clients` (`command_config.rs:289–293`), and one grant exists.
- **Fix:** use `--max-commands 1`, or add a reviewed, explicit replacement of the amendment rule. (The count cohort's restart at 4, over a durable admitted count of 3, is consistent with the rule and doesn't trigger a count exit.)

**B3. The design doesn't say who writes the server config, or what the limits are.**
- **Design:** lines 55–61 say to "use installed setup to trust … grant …", then that server policy grants only the pinned fixture and that cwd is fixed.
- **Source:**
  - Installed `marmish setup` can't set `command_policy.allow_exec`, `cwd` or `limits`. Its template is `{version:1}`, with `cwd:null` and `limits:{}` (`native_setup.rs:133–160`).
  - The existing matrix `configure()` writes config.json directly before any lease, including `"limits":{"max_commands":4,"max_uptime":1800}` (`installed_matrix.rs:217`).
  - The CLI override takes priority over config limits. But a config `max_commands` that is never overridden would still apply. For example, the uptime cohort ("No max_commands is needed", line 181) would quietly inherit `max_commands` 4 if it reused `configure()`.
- **Fix:** specify an exact, driver-owned config write that happens before the first owned spawn. It should come after the installed setup trust/grant and must not use symlinks. It needs:
  - `allow_exec` set to exactly the pinned fixture path;
  - `cwd` set to its exact parent directory;
  - `"limits":{}`.

  The limits must then come only from CLI flags:
  - count cohort: `--max-commands 3 --max-uptime 1200`;
  - uptime cohort: `--max-uptime 180` only;
  - restarts: per B2.

  The record must include the config's digest. Also say whether this module reuses or forks `configure()`, because the matrix's limits of 4/1800 must not leak into these cohorts.

## Verified feasible (no change needed)

- **Finish is required before count exit.** `CountDrain::ready` needs `finished==admitted`, `reserved==0`, the control path idle, publications terminal and all sources acknowledged (`command_count_exit_ready`). So saving the terminal state before the final Consume that triggers Finish is necessary, and it's enough to stop the server exiting early.
- **Natural exit path works.**
  - When `command_count_exit_ready` holds or `expired` fires, the loop breaks (`daemon.rs:271` and the `select!` arms).
  - `run` then calls `stop` → `stop_reporting(emit=true)`. That writes exactly one `LifecycleStopReport` line and returns an error unless all three completion flags are true.
  - So exit 0 plus one stop-report line is a sound oracle for a natural exit.
- **Durable state survives restart.** The admitted/finished counts are durable in `command_replay_state`, and the `max_commands` ceiling is rewritten each launch. A sealed restart keeps the original count and the original EngineTree receipt, and doesn't reset either.
- **Uptime can't expire early.** The lifetime origin is taken at the start of daemon open, which is at or after spawn time L. So expiry can't come before L+180.
- **Polling behaves as the design needs.** `--detach` sends no Poll, so the design's limit of one outstanding Poll per client is achievable. `CommandPoll` accepts an exact `request_id` retry. Local IPC has a 15s bound.
- **No test-only product hooks needed.** Keeping the real-MdkOwner remote-conflict gate separate (as you accepted) means nothing in this design requires them.

## Nonblockers (fix these in the same revision)

1. **Define the uptime overrun window exactly** (lines 181–183).
   - The driver can't see the origin; it only knows L. Actual exit is roughly origin + 180 + up to 100ms tick + `stop_owned`, which has its own 30s bound plus `pending.finish()` for the engine join.
   - Measured from L, "≤10s" could turn a valid joined shutdown red on slow macOS runners. That fails closed, but the result would be flaky.
   - Specify the window as [L+180, L+180+startup_cutoff+30s+slack], or measure from the readiness-observed time, and record both timestamps.
2. **Poll count and cursor binding.**
   - `wire::MAX_BYTES` is 16384, so 2×128KiB of output needs at least 16 Polls per client. Each fits the 64KiB IPC frame.
   - State this, and require that each Consume's `expected_cursors` equal the start cursors of the Polls actually made.
3. **Socket path length.** Assert the derived `TMPDIR/mr2-UID-profileID/s` length is under 104 bytes for each extra client profile (client-2 and client-3), not just the matrix pair.
4. **Count timing (lines 129–138).** Say in the record that exit within L+600 means exit at least 600s before the 1200s deadline. Also state that a count failure latched at L+600 stays red even if a later Finish happens.
5. **Rule out a pre-existing listener on the uptime cohort.** Its zero-admission requirement should also check `CommandInvocations` is empty and the evidence ledger has zero rows. Then a concurrent stray submit can't slip through as merely "no fixture receipt".

No implementation is authorized by this review. Re-review is needed after B1–B3 are addressed.
