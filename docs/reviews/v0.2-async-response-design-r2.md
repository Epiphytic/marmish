## Resolved

- **B1 (which operation belongs to which slot):** Resolved. The design stores OperationId and revision on the slot in the same transaction that registers the operation. A slot can only be filled when key, operation, revision and an empty `response_id` all match, and the request matches the operation (Status→Observe, Cancel→Cancel, Poll→Poll with identical cursors and `max_bytes`). Dispatch and feeder operations never fill a slot, and a publication with no matching slot is rejected.
  - I checked "stale": `revision` is the invocation record revision (`command_store.rs:345-347`). So "stale but still authorized" means the record moved on, not that a different operation completed. Clearing the operation link on that path cannot orphan a newer operation, because each invocation has only one registered operation.
- **B2 (response must match committed facts):** Resolved. One shared pure function derives the committed facts, and the commit re-checks the response against them, including admission, authority, `engine_known`, the input warnings and the known-then-Missing → `result_expired` case. A Poll slot needs a `Polled` observation, chunks within the budget, and `next_cursor` values at least the request cursors. Found or Failed from a failed output read can't be encoded as a successful Poll. It also fixes the per-stream 8192 deviation.
- **B4 (pick up pending work after restart or full queue):** Resolved. There is a bounded (256) recovery query for pending slots with no operation and for registered read operations, including finished invocations. Those reads are re-enqueued with the same OperationId and revision. Dispatch and feeder keep their own recovery barriers, and the active-only query (32) is explicitly not used for slot recovery.
- **B5 (when `response=None` is allowed):** Resolved. None is allowed only for an Existing, server-side Status, Poll or Cancel on an existing invocation with valid authority. Duplicates attach with None, Submit included, and never re-enqueue. A conflicting digest is refused.
- **B6 (busy/capacity means defer):** Resolved. The four errors leave the native event pending and unACKed and never cache a refusal. A new Poll waits until the previous Poll slot is retired. Maintenance runs promptly after recorded ACKs.

## Remaining blocking issue: B3 is not fully closed

B3 asked for every pending slot to have a final state. The design still leaves a read that fails every time stuck in Pending forever:

- It says a failed engine operation or a wrong observation type "leaves Pending and atomically clears its operation link". The bound that would end this is optional: "A bounded-attempt implementation **may** instead Answer…".
- Some failures do repeat every time:
  - `read_output` returns `RecoveryUncertain` when the job directory is gone but output isn't closed (`marmish-engine/src/lib.rs:414-418`).
  - Spool status or integrity failures make `Spool::read` return `InvalidRequest` (`spool.rs:365-371`).
  - Spool decrypt and IO errors can also repeat.
  - `execute_operation` turns each of these into `Found` for a Poll (`command_engine.rs:620-640`). The design treats that as a wrong observation, so the slot goes back to Pending and recovery starts a new operation.
- **Result:** the slot loops forever (a hot loop unless retries are paced). It holds the invocation's one outstanding Poll, blocks invocation GC, and uses up one of the 256 global slots. A client with access can start a Poll on each of several damaged or orphaned invocations, and those slots are never reclaimed. That is the capacity starvation B3 was meant to prevent.

**Fix needed:** make the bound mandatory and specific.
- Keep a durable attempt counter on the slot, increased in the same commit that clears the operation link.
- Set a fixed maximum N. When it is reached, Answer with a finite retryable error (`recovery_uncertain` or `busy`). Never `not_found`, Missing, or a request to resubmit.
- Space retries out, for example once per maintenance tick rather than immediately.
- Add a test: a Poll whose `read_output` always fails ends Answered after N attempts and then retires normally.

## Non-blocking notes for implementation

- **When Suppressed is set:** say that a pending slot with no publication becomes Suppressed in the same transaction as `revoke_record`. Otherwise the recovery query could start an operation for an already-revoked slot.
- **Rejected publications:** "rejected, not silently ignored" combined with "pending completion is retained on failure" means an actor bug that keeps producing a mismatched publication would retry the same commit forever. It should fail closed with a diagnostic rather than silently loop.

Once the B3 bound is written in as mandatory with a test, I'd expect to approve. The rest of the design is precise enough to implement as written, and the completed code will still need its own review.
