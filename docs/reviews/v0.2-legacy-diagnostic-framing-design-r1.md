**Why the parser repair is acceptable**
- It is narrow and test-only. It changes only marker extraction.
- It keeps every security and diagnostic assertion:
  - the child exit assertion
  - exact quoted-path containment in stderr
  - `different --bin-dir`
  - `expected.contains("\\n")`
  - exactly one stderr line
- The producer's `serde_json::to_string` escaping means the marker's value can't contain a raw newline, so reading to end of line is safe.
- The proposed vectors (libtest-prefixed, standalone, missing, duplicate, empty) are meaningful and not tautological.

**Refinements to apply during implementation (none block approval)**
1. **Wording:** "read its following line" is ambiguous. The marker and value are on the same line (`EXPECTED_PATH=<json>`), so the doc should say "the remainder of the line after the marker". Do not read the next line.
2. **Keep the quotes:** `expected` must remain the JSON-quoted form, including the surrounding `"`. The stderr `contains(format!("conflicting launcher {expected};"))` assertion depends on that. The helper must not unquote or re-escape it.
3. **Stronger "empty" check:** require the remainder to parse as a JSON string, for example `serde_json::from_str::<String>(rest).is_ok()` while still returning `rest` verbatim. That is stricter than non-empty and catches truncated or garbled output. Also add vectors for a trailing `\r` or whitespace, and for a non-string value.
4. **Duplicate counting:** count `"EXPECTED_PATH="` substring occurrences over the whole stdout, not per line. The design's "anywhere" semantics imply this, so make the test vector prove it. For example, put two markers on one line.
5. **Diagnosability:** the helper's error, or the `assert!` message, should include the captured stdout (`{stdout:?}`). If a fresh macOS candidate still fails, the real bytes will then be in the log. This is cheap and addresses the unproven-hypothesis gap.
6. **Helper shape:** make the helper a pure `fn(&str) -> Result<&str, &'static str>` or similar, so the vectors can run without a subprocess. Keep it in the test module with no production exposure.
7. **Optional simpler alternative:** make the child emit `println!("\nEXPECTED_PATH=…")` so the marker is at line start, and keep a stricter line-start parse. The design's approach is equally valid and more robust to any prefix, so this is only a note.

**Process notes:** the plan to run offline focused tests, clippy, rustfmt and diff checks, then get completed-code review and a fresh immutable macOS candidate, is appropriate. Linux passing should not be claimed as macOS qualification, and the design already says so.
