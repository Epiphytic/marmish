# Installed cleanup authority design review

Reviewer: Claude Opus 5.5, permission mode auto. Actual verdict APPROVED. Session 67aaca76-93f7-4be8-8b04-0e7897ed1484. Scope: sealed retained-child, PID/UID-bound local cleanup guard and original EngineTree receipt. Exact reviewer result:

**APPROVED**

This was a read-only review. I read the revised design, the r2 findings and the relevant source, and ran no edits, Cargo, tests, network, keychain or process actions.

All three r2 blockers are now handled:

- **N1 (a restarted instance fails the "commands absent" check): fixed.**
  - The absence proof now runs only before the *first* owned spawn per profile, and the receipt belongs to the profile, not the child.
  - Its descriptors are kept after the first child is reaped.
  - Every later restart or cleanup instance compares against the original root inode twice: before spawn, and after readiness but before traffic. It never recaptures.
  - The guard binds the current live child plus the original receipt, and any mismatch preserves state.
- **N2 (feature-gated code never built or tested): fixed.**
  - The design adds a release gate that runs `cargo test` and `cargo clippy --all-targets -- -D warnings` with `--features installed-checks`. Today `v02-release.yml:73-76` has only the unfeatured runs, so this gate is new.
  - It declares two new bins, `marmish-installed-check` and `marmish-installed-fixture`, both with `required-features`. `marmish-release-tool` stays unfeatured; it's auto-discovered from `src/bin/` and has no `[[bin]]` entry.
  - The three product binaries are copied and hashed first, and the feature build uses a separate `--target-dir`. That stops feature unification from overwriting package inputs.
  - `cargo build --release --bins` skips bins whose required features aren't enabled, so the existing build step is unaffected.
- **N3 (a normal "busy" reply is fatal): fixed.**
  - Prepare and local cancel retry only a finite number of `busy` replies, at 50ms intervals, inside the original cutoff.
  - `server_draining` is accepted only after this driver's own prepare timed out with an unknown outcome. It then reads the fence through PID-bound status and never invents success.
  - An unsolicited `server_draining`, or any other error, still fails closed.

The r2 text fixes are also in:
- `LOCAL_PEEREPID` is named correctly.
- The 4096-row bound is labelled as driver-local.
- Fence stability is proven by status reads before the first page and after the last.
- A short private TMPDIR keeps the socket path under 104 bytes.

Two things to sort out during implementation (not blocking):
1. **Module location.** The design puts `installed_check` under `mdk_adapter`, and `pub(super)` privacy for EngineTree depends on that. But the untracked draft is at the crate root (`crates/marmish-native/src/installed_check.rs`). Either move it under `mdk_adapter` or make the privacy boundary match where the file actually lives.
2. **Feature name.** The design uses `installed-checks`; r2 suggested `installed-acceptance`. Pick one and use it everywhere: Cargo `[features]`, `required-features` and the workflow commands.
