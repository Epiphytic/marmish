## What I checked in the code

**The bug fix is real.** The old quickstart called `setup` without `--interactive`. A new config then has no role, no grants and no `--no-grants`, so `proposed()` returns `grant_choice_required` (`native_setup.rs` ~124-131). The interactive path never ran.

**The forwarding is correct.**
- `--key-storage`, `--state-dir` and `--debug` are global clap options (`cli.rs` ~44-58), so they work after `setup`. The harness's repeat run puts them before `setup`, which also works.
- The values match `Backend {Auto, Keychain, File}`.
- The default is still `auto`.
- Running offline, `bogus` and `FILE` fail with `invalid_key_storage`, and a bare `--key-storage` fails with `missing_argument`, all at the arguments stage before anything else runs.

**The terminal handling is sound.**
- Setup opens `/dev/tty` itself with `O_NOCTTY` and checks that its process group is the terminal's foreground group (`native_setup.rs` ~164-178).
- The `</dev/tty` on the bootstrap's setup call is redundant but harmless.
- With `curl | sh`, the children's stdin comes from `/dev/null` or `/dev/tty`, so they can't swallow the rest of the piped script.

**The harness dialog matches the code.** All five prompt strings are byte-identical to `choices()`. Role `both` asks all five, and the harness fails unless it saw all five prompts and the child exited 0.

**Harness contracts:**
- The first run requires exactly one setup report showing: identity created, owner opened, role both, inbound disabled, backend `file`, and all three stop/cleanup flags.
- The repeat run with `--no-grants` requires: the same npub, owner not opened, no identity created, config unchanged, and all stops complete. It passes `proposed()` because the existing `execution_clients` list is empty and nothing changed.

**CI permissions don't need special handling.** Downloaded artifacts lose their exec bits, but the bootstrap copies each asset with `cat` (or `curl`) into a 0600 temp file under `umask 077`. Install's source check accepts 0600, 0555 and 0444 (`native_install.rs:403`). So the CI asset-dir path behaves the same as the real download path.

**Workflow.** `install-quickstart` needs `render`, which needs the `package` job gated to master, so it inherits that gate. It pulls the target's candidate assets and the pinned bootstrap from this exact run ID and attempt. It checks out `inputs.source_commit` (an exact SHA), so the harness comes from the reviewed source. Permissions stay `contents: read`. The package and render jobs are unchanged.

## Nonblockers

1. **Some report fields are constants, not measurements.** `network_activation: false` and `python_in_runtime_path: false` are hardcoded. They're true by construction (Python isn't in the utilities list, and setup is documented as local-only), but they aren't observed. Also, the runtime PATH only keeps Python, uv, Cargo and rustc off the PATH; a child could still call one by absolute path. The workflow comment "cannot invoke" overstates this slightly.
2. **The local report was edited by hand.** Its `scope`, `assets_source_commit`, `notice_inventory` and `other_target_pins` fields aren't produced by the harness. That's fine as annotation, but it isn't raw harness output.
3. **The harness doesn't check the config it wrote.** The relay URL and `tor: off` are entered but never verified in the committed config. Only role and inbound are checked.
4. **No independent leftover-process check.** Stop and cleanup are trusted from setup's own report flags. The process group is only killed if the child didn't exit.
5. **Failed runs leave a disposable key behind.** On failure the temp directory under `$HOME` is kept, including a file-backend key. That's harmless on ephemeral CI runners but worth knowing for local runs. Also, if `rmtree` raised, the report would not be written; the workflow's `if-no-files-found: error` still fails the job.
6. **`--key-storage` is silently ignored without `--quickstart`.** Rejecting it, or documenting it, would be cleaner.
7. **Path-length risk on macOS (unverified).** If setup or the owner uses Unix sockets under `~/.marmish-quickstart-check-XXXX/state/...`, macOS's 104-byte `sun_path` limit could matter. I can't tell from the code; the macOS CI job will show it.
8. **Install-quickstart checkout.** It doesn't re-verify HEAD or ancestry the way `package` does. That's acceptable because it's an exact SHA and the package gate runs first.

`★ Insight ─────────────────────────────────────`
- The original bug got past component review because the non-interactive setup refuses to guess grants (`grant_choice_required`), which is correct, so the setup component was right on its own. The failure was in how the bootstrap composed the call. Only an end-to-end terminal harness could catch that.
- The harness uses `pty.fork()`, which makes the child a session leader with a controlling terminal. That is what satisfies setup's foreground-process-group check; a plain pipe-based driver could never pass it.
