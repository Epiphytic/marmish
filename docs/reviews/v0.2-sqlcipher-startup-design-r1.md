# SQLCipher startup design review r1

Actual Claude Code Opus, permission mode auto; session `338ff13e-d088-44fb-8095-6ff557a8eed6`. Verdict CHANGES_REQUIRED. Rejected build-flag proposal was never implemented. Exact review follows.

**CHANGES_REQUIRED**

The design gets the race right, but the proposed fix can't work against the pinned source. It would fail to compile, and even with that check removed it would deadlock on Linux and macOS.

### Confirmed: the observed race (§ "cause" is accurate)
In `libsqlite3-sys/sqlcipher/sqlite3.c` (SQLite 3.53.3):
- `sqlite3_initialize` (193434) sets `isInit = 1` (193556), releases `pInitMutex` (193562), and only then calls `SQLITE_EXTRA_INIT` (193599–193603).
- A second thread's `sqlite3_initialize` returns at the `isInit` fast path. Its open/key then reaches `sqlcipherCodecAttach` (114344), which reads `sqlcipher_init` without a lock. That value is set only near the end of `sqlcipher_extra_init` (111390), so the attach returns `sqlcipher_init_error`, which starts at `SQLITE_ERROR` = 1 (111138). That matches `sqlcipherCodecAttach: sqlcipher not initialized 1` exactly.
- `build.rs:153` defines `SQLITE_EXTRA_INIT=sqlcipher_extra_init`. Per `build.rs:300–311`, `LIBSQLITE3_FLAGS` tokens are added after the default flags and `-U` is accepted, so the build-script part of the design is described correctly.

### Blocker 1: `-USQLITE_EXTRA_INIT` causes a hard compile error
`sqlite3.c:110843–110845`:
```c
#if !defined(SQLITE_EXTRA_INIT) || !defined(SQLITE_EXTRA_SHUTDOWN)
#error "SQLCipher must be compiled with -DSQLITE_EXTRA_INIT=sqlcipher_extra_init ..."
```
The core step of the correction ("Undefining the old hook… the mutexed hook becomes the sole SQLCipher startup hook") cannot build. Keeping both hooks avoids the `#error`, but then the unsafe non-mutexed call still runs. It's only a no-op because of the `if(sqlcipher_init)` check, and the design gave no analysis of running it twice.

### Blocker 2: the mutexed hook self-deadlocks on pthread platforms
The claim that "recursive SQLite initialization is explicitly supported" is wrong for this hook:
1. `sqlcipher_extra_init` first takes `SQLITE_MUTEX_STATIC_MASTER` (111256). That is id 2, the same mutex as `SQLITE_MUTEX_STATIC_MAIN` (8994, 9010).
2. While holding it, the function calls `sqlite3_mutex_alloc(SQLITE_MUTEX_FAST)` (111296). For ids ≤ `SQLITE_MUTEX_RECURSIVE`, `sqlite3_mutex_alloc` calls `sqlite3_initialize()` (30406).
3. With the old hook this was harmless, because `isInit` was already 1 and the call returned at the fast path. Under `SQLITE_EXTRA_INIT_MUTEXED`, `isInit` is still 0. The recursive call goes straight to `sqlite3_mutex_enter(pMainMtx)` (193479), before it ever reaches the `pInitMutex`/`inProgress` re-entry guard.
4. The static mutexes are plain `PTHREAD_MUTEX_INITIALIZER` (30771–30776), which is non-recursive. So the first `sqlite3_initialize` in every process deadlocks on Linux and macOS. On Windows, critical sections are re-entrant, so it would appear to work there, which would hide the problem.

The doc only notes that STATIC_MASTER is released before `sqlite3_auto_extension`. It misses the allocation made while the mutex is still held.

### Other required changes
3. **Fix direction.** There's no way to fix this with build flags alone without patching or vendoring the C. The revised design needs a different mechanism and the same source-level proof of safety. One option that fits the source: a single process-wide barrier that calls `sqlite3_initialize()` and lets it finish (it returns only after `SQLITE_EXTRA_INIT` returns) before any SQLite use. It would have to cover every opener in the process (engine, journal, MDK, dedicated worker processes), not just the engine, so it doesn't conflict with the doc's ban on an engine-only `Once`. It would also need to check `sqlcipher_init` failure, or at least surface `rc`. The design should list each opener's entry point.
4. **Build env scope.** This only matters if a flag-based approach comes back. You'd need to state the minimum Cargo version where `[env]` values trigger `rerun-if-env-changed` rebuilds, how `-U`/`-D` ordering behaves under MSVC `cl` for the Windows leg, and whether `PRAGMA compile_options` (`EXTRA_INIT*` entries at 23521–23526) is checked in a test so a stale cached C object can't pass.
5. **Test design.** The structure is sound: fresh child processes, 16 threads behind a barrier, a bounded parent timeout with kill/reap, no shutdown, honest reporting if it's probabilistic. Two additions:
   - Require the timeout to be reported as a deadlock failure, not a flaky failure. That timeout is exactly what would catch Blocker 2.
   - Require the regression to pass on Linux and macOS, not just Windows, because Windows' re-entrant critical sections hide Blocker 2.
