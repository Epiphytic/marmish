## Blocking issues

**B1. Setup opens MDK storage, but the read-only format check isn't required before it.**
- Today `MdkOwner::open` (`mdk_adapter.rs:868-1010`) makes changes as soon as it runs:
  - It opens `SqliteAccountStorage` twice, which runs upstream migrations.
  - It opens the journal, which accepts versions `0|3|4` and upgrades 3 to 4 in place (`journal.rs:136-171`).
  - It writes the key-package lifecycle record, and runs `reconcile_orphans` and `maintain_journal`.
- The parent design (lines 206-219) requires a read-only format check before any of that.
- The amendment assigns that check to the root, "before mutable MDK/engine open" (line 100). But `native_setup` opens `MdkOwner` itself, so nothing places the check before setup's own open.
- It also only covers "a fresh local profile" (line 124). It doesn't say what happens to a profile left half-initialized by a crash, which has to be reopened to call `mark_ready`, or to an already-ready profile.
- **Fix (one or two sentences):**
  - Setup calls the same read-only format check before any `MdkOwner::open`, and stops with `incompatible_state` on a proven version mismatch.
  - Setup opens `MdkOwner` only when the profile isn't ready yet (fresh, or a retry of a crashed initialization).
  - A ready profile never opens MDK or the journal during setup; config edits and printing the npub use the profile manifest only.

**B2. The source scripts must contain the pins directly.**
- Line 36 says the default `scripts/install.sh` "will point to" the bootstrap. That could be read as a redirect script that downloads `marmish-install-0.2.P.sh` from GitHub and runs it without pinning its hash. That would break the trust chain for the Radicle URL.
- **Fix:**
  - At cutover, `scripts/install.sh` on both Radicle head and GitHub `main` is the generated bootstrap itself, byte-for-byte, with the version and all three manifest SHA256s embedded. Any indirection must also embed the SHA256 of the script it fetches.
  - Acceptance item 5 also checks that the two URLs serve identical bytes and pins.

## Confirmed against source (no change needed)

- **Lease and shutdown:**
  - `ProfileLease::acquire` uses `try_lock_exclusive` and fails with `profile_in_use` (`identity.rs:97-131`).
  - `mark_ready` checks the profile ID and public key from `OpenedAccountBinding` (`identity.rs:343`).
  - `stop_owned(OwnedIdentity{owner, profile})` keeps the lease until the keeper actually joins. An expired observer hands back the same `PendingStop` (`command_lifecycle.rs:47-190`).
  - The test `actual_unactivated_owner_closes_before_runtime_cleanup_and_unlock` (lines 238-282) already exercises exactly the setup sequence: acquire, prepare, unactivated open, `mark_ready`, then `stop_owned`, with all flags true and the lease released.
- **No engine or network start:**
  - The command engine only starts through `enable_commands`, which `daemon::open` calls when `config.json` exists (`daemon.rs:84-89`). The amendment is right that setup must not use `daemon::open` or the existing `init` path that goes through it (`cli.rs:133`).
  - `RelayConnector::new` creates Tor lazily (`tor: None`). `MdkOwner::open` builds the SDK client but doesn't connect.
- **Config API:**
  - `CommandConfig::load` reads at most 1 MiB, then deserializes and calls `normalize` (`command_config.rs:72-100`). A `from_bytes` built on that path is a clean extraction.
  - The config version is the literal `1` (line 88), so it needs exporting as a named constant.
- **Format constants:**
  - Profile `format: 2` and engine `user_version=1` match.
  - The journal writes the literal `4`, and there is no named constant yet. The rule "export the actual final constant, don't hardcode 4 or 5" is correct.
  - I found no `user_version` in `command_store.rs`, so the owner of the command-ledger format still has to define and export it.
- **Layout check before vault-helper dispatch: feasible with the existing helper arguments.**
  - The helper is launched as `<path> _vault-helper` with a cleared environment (`identity.rs:705-722`). Dispatch happens first in `cli::main` (`cli.rs:171`).
  - Resolving the layout needs only `current_exe`, not extra arguments.
  - "Unavailable" is only reported from an explicit helper protocol reply (`identity.rs:659`). So a helper that exits early on a bad layout can't trigger the automatic fallback to file storage.
  - All three binaries (`marmish`, `marmishd`, `marmish-worker`) exist. The worker takes `(root, jobhex)`, so a resolve that doesn't use arguments works there too.
- **The two source URLs:**
  - Each script stands alone, and the GitHub one works during a Radicle outage.
  - The version is pinned exactly, there's no `releases/latest` lookup, and a failed download is final with no fallback to an older or legacy release. That fits the trust model already approved in the parent.
- **Scheduling vs. release acceptance:** the amendment keeps them clearly separate. It drops only the scheduling rule that Phase 2 had to be fully accepted first. The direct installed-platform gates on all three targets and central publication still apply. Tor is cleanly excluded from the v0.2 gates.

## Non-blocking notes (fix during implementation)

1. `resolve` must check the version's own `manifest` and `.version-receipt.json`. It must not require that version to be the active one, otherwise a running old daemon or detached worker breaks after `select`. It should parse rather than rehash every file (up to 784 MiB) on each helper launch, which has a 30 s deadline. In the helper child it must write nothing to stdout.
2. Replace the non-canonical `current_exe()` used today for the helper and worker paths (`cli.rs:128`, `daemon.rs:85`) with the paths from `ExecutableLayout`.
3. `verify_directory` has to handle two naming schemes: versioned download basenames and fixed installed names. Make that an explicit parameter.
4. The journal's supported set is {3, 4} plus in-place upgrades. The format check should declare the current format and the set it accepts for upgrade separately.
5. `prepare` must run outside Tokio worker threads (via `spawn_blocking`, as `daemon::open` does).
6. The Radicle script fetches its assets from GitHub releases, so it doesn't help during a GitHub outage. The README should say that.
7. The parent's journal value of 3 (line 98) is now stale. The amendment overrides it, but a cross-reference in the parent would help.
8. Existing users with a Python-era launcher in `~/.local/bin` will hit `unrelated_launcher` when they run the default quickstart. That's existing parent behavior; the README guidance for that case should be clear.

★ Insight ─────────────────────────────────────
- In this codebase, opening `MdkOwner` changes on-disk state (migrations, the journal upgrade, reconciliation), not just reads it. That's why it matters which code path checks formats before the open.
- `stop_owned` passes the lease to a keeper thread that drops it last, so setup can't release the lease before shutdown actually finishes. The amendment relies on the existing code here rather than new design.
