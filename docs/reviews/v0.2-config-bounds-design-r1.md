## Identity helpers: making them crate-visible is safe

`identity.rs:468` `check_dir` and `:475` `open_private` do exactly what the doc says:
- `check_dir` uses lstat and requires a directory owned by the effective user with mode 0700.
- `open_private` opens with `O_NOFOLLOW|O_CLOEXEC`, then checks the opened file itself (`fstat`): regular file, `nlink==1`, owned by the effective user, mode 0600.
- With `create=false` it opens read-only.

Changing only their visibility leaves their bodies and existing callers (lines 103–560) untouched. Their finite errors (`Identity("unsafe_profile_path"|"unsafe_profile_file")`) are acceptable for config. Since the config module is `cfg(test)`-only, normal builds see no new use of either helper. "Read with an overflow sentinel after validating the opened file" matches the existing `take(LIMIT+1)` pattern at `identity.rs:430`.

## Account parsing in the pinned `nostr` (48801bf): the doc is right, but one API is a trap

I checked `nostr/src/key/public_key.rs:112–131` and `nips/nip19.rs:282`.

- **Don't use `PublicKey::parse`.** It accepts npub, nprofile, `nostr:` URIs and hex, including uppercase hex (via `faster_hex`). Each of those is broader than "valid npub or canonical lowercase hex64".
- **`from_bech32` also accepts `nprofile`.** Check that the prefix is exactly lowercase `npub1` before calling it.
- **Hex:** call the existing `foundation::valid_hex(value, 32)` (`pub(crate)`, lowercase only), then `PublicKey::from_hex`.
- **Off-curve keys:** neither path checks that the key is a valid curve point (`from_byte_array` just copies the bytes). If off-curve keys should be refused, add `.xonly().is_ok()`. Accepting one is harmless, since it can never authenticate, but say which you chose.
- **Private keys:** "never accept private-key encodings" is met by refusing any prefix other than `npub1` (`nsec`/`ncryptsec` included).

## Notes for the config agent (not blocking)

1. **Duplicate alias names:** serde-derived structs reject duplicate fields, but a JSON object deserialized into `BTreeMap`/`HashMap` silently keeps the last value. "Duplicate names refused" needs an array shape or a map visitor that detects duplicates, plus a test for it.
2. **Combined maxima can exceed 1 MiB:** 2×4096 npubs (~540 KB), 256 aliases × 16 relays, and 256×1024-byte patterns add up to more than 1 MiB. The file cap correctly wins, so tests shouldn't expect a config with every maximum at once to load.
3. **Applying the identity bound:** keep "never accept private-key encodings" as a whitelist (prefix must be exactly `npub1`), not a list of blocked formats.

The refinement doesn't change any acceptance criterion, phase gate, dependency or production call site, and it doesn't create any new phase acceptance.
