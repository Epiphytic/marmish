# Native journal fixture: scoped design review

Actual Claude Code Opus 5.5, session `5022baae-f832-444d-83bf-1048f9f569d1`, `--permission-mode auto`. Review occurred before implementation. The first review required the symlink to be above the immediate parent; the revised design below adopts that requirement. This test-only increment preserves production path protections.

## Round 1

# Verdict: changes required to the regression test only

The diagnosis is right, and the test-only `setup()` fix is approved. The proposed regression would fail for a different reason than the one it's meant to prove, so it needs one change before you implement. Nothing in production should change.

## Evidence

- **The failure is the SQLite symlink check, not the Rust checks.**
  - `journal.rs:56` maps every rusqlite error to `Storage("journal")`. The Rust-side refusals all return `Storage("journal_path")` (L62–90).
  - So `Storage("journal")` at setup means the Rust checks passed and `Connection::open_with_flags(... SQLITE_OPEN_NOFOLLOW)` at L91 refused.
- **The pinned SQLCipher rejects a symlink anywhere in the path.** This is rusqlite `5ae7fdf`, `libsqlite3-sys/sqlcipher/sqlite3.c`:
  - `appendOnePathElement` (~L47275) calls `lstat` on every path component and counts symlinks.
  - `unixFullPathname` (L47359) returns `SQLITE_OK_SYMLINK` if it found any.
  - L64726–64728 turn that into `SQLITE_CANTOPEN_SYMLINK` when `SQLITE_OPEN_NOFOLLOW` is set.
  - So a symlinked ancestor such as macOS's `/var` → `/private/var` is refused. The Rust `O_NOFOLLOW` only applies to the last component, which is why it lets the path through.
- **Production is not affected.** The only production callers are `mdk_adapter.rs:480-481`, which use `profile.journal_database()`. That path comes from `ProfileLease::acquire`, which calls `base.canonicalize()` (`identity.rs:100`).
- **This explains why the other mac tests pass.** The adapter and trust tests reach the journal through `ProfileLease`, so their paths are already canonical. 67 passed + 23 failed = 90, which matches the 87 + 3 native tests on Linux. Only the 23 journal tests use a raw `tempdir()` (`journal.rs:937`).

## Approved: the `setup()` change

- Use `tempfile::Builder::new().permissions(Permissions::from_mode(0o700)).tempdir_in(std::env::temp_dir().canonicalize().unwrap())`.
  - This matches `mdk_adapter_tests.rs:21-23` and makes the separate `set_permissions` call unnecessary.
  - Your `tempdir_in(...)` plus the existing `set_permissions` is also acceptable.
- Every `temp.path().join("journal.db")` reopen then inherits the canonical path. No other test changes are needed.
- Keep `NOFOLLOW`, the `O_NOFOLLOW` create, and the uid, mode and nlink checks exactly as they are.

## Required change: the regression's path layout

As proposed, `alias → child`, opening `alias/journal.db`, would return **`Storage("journal_path")`**, not `Storage("journal")`.
- The immediate parent of `alias/journal.db` is `alias` itself.
- `fs::symlink_metadata(alias)` reports a symlink, so `!is_dir()` triggers at L65 before SQLite is ever called.

To test the SQLite ancestor walk, the symlink has to sit **above** the immediate parent:

```
root   = Builder(0o700).tempdir_in(temp_dir().canonicalize())
real   = root/real   (0700)
child  = real/child  (0700)        // immediate parent: a real dir, owned, 0700
alias  = root/alias -> real        // std::os::unix::fs::symlink
```

1. Open `root/alias/child/journal.db`. Assert `matches!(r, Err(Error::Storage("journal")))`. Match the exact error; `is_err()` is not enough.
2. Then open `root/real/child/journal.db` with the same key and account. It must succeed, and so must a reopen after a drop.
   - Step 1 leaves an empty 0600 `journal.db` behind, because the Rust `create_new` succeeds before SQLite refuses. Step 2 therefore also proves that a refused attempt doesn't block the canonical path.
   - Optionally assert that the file is empty after step 1, and that it doesn't start with `SQLite format 3` after step 2.
3. Recommended: open `root/alias2/journal.db` with `alias2 -> child`. Assert `Err(Error::Storage("journal_path"))`. This pins the Rust immediate-parent check too.

Leave the regression ungated rather than `cfg(target_os = "macos")`. It builds its own symlink, so it reproduces the macOS condition on Linux as well.

## Round 2

# Verdict: APPROVED (design only)

The revised design is approved as written. I made no edits and ran nothing.

## Why each assertion holds

- **`alias/child/journal.db` → `Storage("journal")`.**
  - The immediate parent `child` is reached by following `alias` higher up the path. `symlink_metadata` follows symlinks in the ancestors, so it sees a real directory, owned by the test user, mode 0700. The Rust checks at L62–70 pass.
  - The `create_new` with `O_NOFOLLOW` at L71–78 only checks the last component, so it succeeds and leaves an empty 0600 file.
  - SQLCipher's walk over every path component then finds `alias`, returns `SQLITE_OK_SYMLINK`, and with `NOFOLLOW` set that becomes `SQLITE_CANTOPEN_SYMLINK`. `db()` maps it to `Storage("journal")`.
- **The file is empty after that refusal.** It was created and synced by the Rust code; SQLite refused before writing anything to it.
- **The canonical `real/child/journal.db` opens and reopens.** The file left behind passes the L80–86 checks (regular file, same uid, 0600, one link). SQLCipher accepts the empty file as a new database.
- **`alias2/journal.db` → `Storage("journal_path")`.** `symlink_metadata(alias2)` reports a symlink, so `!is_dir()` triggers at L65 before any file is created.
- **The `setup()` change** makes every reopen in the 23 existing tests use the canonical path. Production keeps `NOFOLLOW` and the ownership/mode checks unchanged.

## Notes for implementation (non-blocking)

- Set `real` and `child` to 0700 explicitly with `set_permissions` or `DirBuilder::mode`. Don't rely on the umask.
- Match the errors exactly with `matches!(…, Err(Error::Storage("journal")))` and `matches!(…, Err(Error::Storage("journal_path")))`.
- Run the `alias2` case after the file-is-empty check. Running it in either order is fine, because it creates no file.
