## Verdict: **CHANGES_REQUIRED**

There are three blockers. B1 breaks every real install done through the bootstrap script. B2 is a mandatory part of the approved design that isn't implemented. B3 breaks the rule that an identical repeat changes nothing.

## Blockers

**B1 — Every first install through the bootstrap fails because of umask.**
- `scripts/install-native.sh:6` sets `umask 077`, and the native install at `:135-138` inherits it.
- `native_install.rs:806` creates `versions` with `DirBuilder::mode(0o755)`, which the umask turns into 0700.
- `native_install.rs:809` then requires exactly 0755 (`check_owned_dir(&versions, Some(0o755))`), so a fresh prefix always fails with `unsafe_install_path`.
- The 4 installer tests pass because they run under the test runner's umask, not 077.
- Minimal fix: after the `create` at :806, call `fs::set_permissions(&versions, Permissions::from_mode(0o755))`, the same pattern already used at :602 and :668. Add a test that runs install under umask 077.
- Other directories are fine: `path()` at :230 checks with `None`, and the staging and final version directories are already chmodded explicitly.

**B2 — The held-directory transaction requirement isn't implemented.**
- The parent design makes it mandatory that directory operations run relative to held, validated handles. The implementation is entirely path-based:
  - `atomic()` at :201 and `sync()` reopen by path.
  - `stage()` at :589, `cleanup_staging()` at :378, `set_selector()` at :336 and `rename_exclusive()` at :566 all work on `prefix.join(...)` paths.
  - Nothing uses openat, a dirfd, `renameat2` relative to a held fd, or fstat on a held handle.
- Ancestors are validated once by `path()` and then re-resolved by name on every operation.
- To be fair: under the existing same-UID/root attacker boundary, most ancestor-swap attacks are already out of scope, so the practical exposure is small.
- But the design states this as a requirement, not as optional hardening. Two minimal options:
  - (a) Hold dirfds for prefix, `versions`, the staging directory and bin_dir after validation, and switch the mutations to `*at` calls (`openat`/`mkdirat`/`renameat2`/`symlinkat`/`unlinkat`, plus `fsync` on the held fd).
  - (b) Get an explicit design amendment that downgrades this to path-based operations, justified by the same-UID boundary.
- Either one clears the blocker. As written, the code doesn't meet the approved contract.

**B3 — An identical setup repeat can fail with `config_exists` or rewrite unchanged fields.**
- `native_setup.rs:85-108` (`update_set`) always rewrites `execution_clients` and `trusted_remotes` as sorted lowercase hex.
- `command_config.rs:409-419` (`account`) accepts both `npub1…` and hex.
- So a valid config holding npub-form or unsorted principals compares as changed at `native_setup.rs:150` (`before != value`) even when the request adds or removes nothing:
  - without `--update` it returns `config_exists`;
  - with `--update` it rewrites fields the user didn't ask to change.
- That breaks "identical requested fields are a no-op" and "preserve unmentioned fields".
- Minimal fix: in `update_set`, compare the parsed set before and after the edit, and only write `value[field]` when the set actually changed. Alternatively, compute `changed` from the normalized `CommandConfig` (via `from_bytes`) instead of from raw JSON.
- Add a test: repeat setup against an npub-form config and expect `config_changed=false` with no error.

## Nonblockers (each is a real but minor issue)

1. **`native_install.rs:630` (`stage()`):** it re-reads the source manifest without re-hashing it against `t.manifest_sha256`.
   - If the source file changes between the earlier verification and staging, the version is committed as owned but fails `reverify` forever, leaving a stuck `version_conflict`.
   - Fix: hash the bytes just read and compare before writing.
2. **`native_install.rs:566` (`rename_exclusive`):** EINVAL/ENOSYS (filesystem without RENAME_NOREPLACE/RENAME_EXCL) is reported as `version_conflict`. It should be a distinct `unsupported_filesystem` error.
3. **Failed installs aren't rolled back immediately.**
   - After an ordinary failure, the pending `.transaction.json` stays until the next run, so newly created launchers dangle until then.
   - `install-status` also mutates state through `recover()`.
   - Recovery is bounded, so this works, but say so in the docs or roll back on the failure path.
4. **Path comparisons are lexical.**
   - The receipt check (`prefix != prefix`) and `contained()` in `validate_options` compare paths as text, with no canonicalization.
   - Equivalent spellings (trailing `/`, `..`, symlinked prefix) give a false `receipt mismatch` or slip past the containment check (the latter is within the same-UID boundary).
   - Fix: canonicalize after `path()`, or require normalized paths in the CLI.
5. **`native_manifest.rs:275` (`verify_directory`):** `filter_map(|e| e.ok())` silently drops `read_dir` errors. Propagate them instead.
6. **`native_layout.rs`:** some raw `io::Error`s propagate through `?` instead of finite error codes.
7. **Interactive setup:** `native_setup.rs:199` (`choices`) never prompts for the identity name, which the design calls for. The `-i` flag only works non-interactively.
8. **`native_setup.rs:263` (`commit`):** a crash leaves a stale `.config-<hex>` temp file that is never cleaned up.
9. **`native_setup.rs:353-362`:** if `commit` fails after `mark_ready`, the profile ends up Ready but without the new config. The next repeat takes the Ready branch and commits it, so this self-heals; worth one line in the docs.
10. **`native_preflight.rs:27-33`:**
    - The read-only open of a WAL database with no `-shm` file fails closed as `state_preflight` rather than giving a misleading result. Acceptable, but untested.
    - The HKDF salts and info strings match `mdk_adapter.rs:887-892`.
    - The engine key path (`command_identity::derive` plus `marmish-storage-hkdf-v1`) and `cgka_schema_migrations` ≤ 166 can't be checked without upstream code and tests.
11. **`install-native.sh:124`:** the `release-info` probe doesn't redirect stdin, so a piped `curl | sh` run could have its script consumed. Add `</dev/null`.
    - Also, a missing /dev/tty at :144 surfaces as `native_setup_failed` rather than `no_tty`.
    - Non-ASCII manifest bytes get through awk, but Rust rejects them again.
12. **`build.rs:39`:** the fallback commit of 40 zeros passes the grammar, so release packaging must reject that value explicitly.

## Contracts verified by reading the code

- **No profile, keychain or provider access** during install, install-status, select or uninstall. `native_install::run` only touches the prefix, bin_dir and HOME metadata.
- **Every asset is verified before any mutation.** Manifest hash, size and digest for all four files, plus the compiled provenance, are checked in `run()` (:680-703), before the transaction is written.
- **Receipts and transactions are strict.** Both use `deny_unknown_fields` with transaction ownership. Recovery is bounded, and staging cleanup only removes fixed names that are regular files with nlink 1 and an expected mode.
- **Launchers are exact links only** (`link()` / `validate_links`).
- **Selector swaps are atomic.** A temp symlink is renamed over `current`. Unselected malformed versions are never adopted: `reverify` and the `.version-receipt.json` check guard this.
- **The engine trust predicate isn't weakened.** `validate_executable_ancestor` and `validate_executable_path` delegate to the existing `launcher::ancestor` and `trusted_worker_executable`, keeping the root-sticky exception. The engine diff is +12 lines in lib.rs plus 1 visibility change in launcher.rs.
- **Setup order matches the design.**
  - Choices are validated and `config_exists` is checked before `prepare`.
  - A not-Ready identity goes through `prepare`, then `native_preflight::check`, then `RelayConnector::new` (lazy, no network), then `MdkOwner::open(..., vec![])` without activation, then `mark_ready` and commit.
  - `stop_owned` plus `PendingStop::finish` **always** runs before `action?` is surfaced, and the lease is held through `OwnedIdentity`.
  - Incomplete stops become `setup_stop_incomplete`.
  - A Ready repeat only rewrites the config under the lease, with no keychain or MDK access.
  - The defaults are role `both` with empty grants meaning inbound is off. `grant_choice_required` fires when a fresh setup is non-interactive. Grants are independent of `trusted_remotes`, and `--no-grants` together with existing grants gives `explicit_revoke_required`.
- **The format gate runs before migration.** Read-only, query-only, nofollow opens distinguish a proven mismatch (`incompatible_state`) from corrupt or wrong-key data (`state_preflight`). The daemon also runs preflight before opening (`daemon.rs:91`).
- **No Tor success is required.**
