# Installed local workflow design review, round 1

Actual Claude Code `--permission-mode auto`, session `4093a879-376b-437b-8b5d-696233463084`. Exact result follows.

**Verdict: CHANGES_REQUIRED.** The overall shape is feasible and I'd approve it once the five items below are fixed. The shape is: one cohort per dispatch, a common pre-queue Context, a token-free local supervisor, per-role artifacts, and a `cohort-rollup`.

I checked the cohort-doc budget arithmetic and it is internally consistent. The terms sum to the stated values: autoexit 2925/2325, uptime 1865/1265, benchmark 2670/2070.

The Context expiry + 60 + 300 ≤ first-step+62min check always holds, because the first step starts after Context creation. The supervisor's TERM point is therefore always the Context expiry. This is design review only: I read the docs, `.github/workflows/v02-installed.yml`, `tools/v02-actions/*.mjs`, and the `installed_records.rs`, `installed_check.rs` and `installed_prepare.rs` sources. I ran no Cargo or network commands and edited nothing.

## Blockers

1. **Source freeze across waves, and the matrix must be rerun.**
   - Resolve requires `source_commit == github.sha`, and the workflow only runs from `refs/heads/master`. Any push to master between waves, including a `docs/validation` evidence commit or a review doc, makes the later waves undispatchable for that candidate.
   - `harness_sha256` also covers the whole `crates/marmish-native` tree, `tools/v02-actions` and `v02-installed.yml`. Adding the local cohorts therefore changes the digest, and earlier matrix evidence is void.
   - **Fix:** state that master is frozen from candidate build through the last wave. The matrix and all local waves must run at the one final candidate, and evidence is committed only after the last wave. Any master movement means a new candidate and a full rerun.

2. **Conflicting controlling specs, and an unspecified workflow and tooling delta.**
   - The autoexit and benchmark designs still describe the old model. In that model, resolvers run in the same run after the previous wave, with `context-autoexit.json`, `cohort-autoexit` and `cohort-uptime` jobs. The local doc replaces it with dispatch-per-wave.
   - **Fix:** list the superseded clauses and fix one canonical artifact and Context naming.
   - The local doc must also enumerate the touchpoints that the current code hard-codes:
     - `workflow.mjs` resolve uses `--cohort matrix` and `+2220`, so it needs a cohort-to-lifetime table.
     - `transport.mjs` `binding()` requires `cohort === 'matrix'` and suffixes `-matrix`, and `artifactName` has a fixed list of kinds.
     - `ArtifactTransport` hard-codes a budget of `< 120`, but the local doc calls for a 30-call budget.
     - `singleJson` accepts exactly one member, but the rollup needs an exact two-member extractor.
     - The existing `matrix` and `rollup` jobs have no cohort `if:`. The current rollup runs on `always() && resolve success`, so with the matrix skipped it would run and fail. Both need `inputs.cohort == 'matrix'`, and the local jobs need the inverse.
     - `verify-context` must assert `context.cohort == inputs.cohort`.
     - The matrix `prepare` step passes no `--cohort`, but both detailed designs require an explicit `prepare --cohort` equal to Context.

3. **Identity binding gap in the rollup.** `cohort-rollup` requires identity digests to match. The autoexit/uptime `CohortResult` has no identity-ready digest field, while the benchmark result does. **Fix:** add `identity_ready_sha256` to `CohortResult`, and have each cohort's `validate` check it against the uploaded identity-ready record.

4. **Output location vs `workspace_removed`.** `installed_prepare.rs:89` requires `--output` to be a direct child of the workspace, and the doc keeps `prepare --output` unchanged. The autoexit `Cleanup.workspace_removed` must be true for a complete result. A literal workspace removal would delete both `identity-ready.json` and the result before upload. **Fix:** define `workspace_removed` as removing everything owned except the `output` directory, and make the cohort result the last write.

5. **`prepare` runs outside the supervisor.**
   - In the current workflow it is a plain step before any supervisor, so the TERM/60s/KILL/close-joined bounds cover only `cohort`. **Fix:** put `prepare` under the same local supervisor (a `prepare` mode, or one supervisor running prepare then cohort under a single deadline).
   - Entry age also includes queue, checkout, `npm ci`, five downloads, verify-context and prepare. Autoexit leaves only 375s for all of that (3300−2925), and benchmark leaves 630s. Say so explicitly.

## Smaller changes to make

- **Redispatch policy.** "Qualify only complete subsequent runs" still permits unlimited retries after real failures. Allow a same-candidate redispatch only for closed pre-spawn infrastructure categories: queue-late, entry-budget rejection, or an artifact download failure. Any failure after the first server spawn or admission fails the candidate, so a new candidate and all waves are needed.
- **Supervisor.**
  - Do not use `uses: ./tools/v02-actions`. `action.yml` defaults a token input to `github.token`. Use `run: node …/local.mjs` with explicit arguments.
  - Spawn with `detached: true` and signal `-pid`. The existing `ownedChild` kills only the PID.
  - `supervise.mjs timing()` hard-codes `≤2220`, so don't reuse it.
  - After the 64KiB cap, keep draining and discarding while latching failure. Otherwise the child blocks on a full pipe.
- **Concurrency.** `cancel-in-progress: false` still replaces a pending run with a newer one, so dispatching while a wave is running can silently cancel a queued wave. State "dispatch only after completion" as an operator rule.
- **Names.** Specify the rollup artifact name, for example `v02-installed-<cohort>-rollup-<run>-<attempt>`. Also specify whether the upload step is one artifact with two files, since the doc says "under an immutable name".
