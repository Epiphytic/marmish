## Blockers

**B1. Output can be silently skipped (breaks write-before-consume). Lines 376–386, 421–426, 479–493.**
`copy_poll` refuses to write anything if `status_failed` is true (any warning, Lost/UnknownLaunch, a gap anywhere, or input Gap/Uncertain), or if a chunk is short because of a gap. `apply_answer` then consumes the answer at the start cursors. The comment at line 479 says the store won't advance the cursors in that case, but it does. `consume_response_in` (`command_store.rs:1537-1546`) moves both cursors forward for any chunk that passes `chunk_progress`, and gap-shortened chunks are explicitly valid there (retention-and-ack: "Gap jumps therefore need not equal byte count").
- **Failure case:** `printf x | marmish … -- head -c0` (or any command that ignores stdin). The answer carries `warning=stdin_unconsumed` and stdout `"abc"`. The CLI writes nothing, the durable stdout cursor still moves to 3, and the CLI exits 255. Running `output` again can never recover "abc".
- **It also breaks the design rule** that a natural exit with unconsumed stdin keeps its real exit code and reports `stdin_unconsumed`.
- **Minimal fix:**
  1. Copy the store's `chunk_progress` rule into the CLI.
  2. If a chunk is invalid, consume without writing (the store doesn't advance) and fail with `output_gap`/invalid-output.
  3. If the chunks are valid, always write and flush both streams, then consume, and only after that judge status health.
  4. Treat `StdinUnconsumed` as a diagnostic on a successful outcome, not a failure.
- **Test:** the existing assertion `out.is_empty()` at line 1135 encodes this bug and has to change.

**B2. An ambiguous Submit is never retried, and an unknown failure is reported as "not admitted". Lines 841–857.**
- **No retry.** The design says: "The CLI retries that same operation", "test commit-before-lost-reply exact retry", and once an attempt was ambiguous a later busy must not downgrade it. The code makes exactly one 15 s exchange and then exits 254. The design also admits the actor can be delayed past 15 s (room turns of 15 s, foundation dispatches up to 120 s). In that case the daemon drops the expired request (`daemon.rs:239`), the handle points at nothing, and the Submit bytes are gone. The user's only option is to re-run, which creates a new invocation.
- **Unknown failures exit 255 with no handle.** `Failure{category} if category != "local_pending"` is a denylist: any unexpected failure becomes a definite "not admitted". At least one actor path can fail after commit: `command_request` → `client_request` → `command_get` runs after `tx.commit()`. A user who then re-runs gets a duplicate execution.
- **Minimal fix:**
  - Retry the identical `CommandSubmit` (same session, request_id and submit bytes) on Timeout, Io or `operation_uncertain`, within the overall wait deadline, until you get `local_queued` for that exact handle.
  - Exit 255 only for `LocalBusy` on the first attempt.
  - For any other non-`LocalQueued` result: print the handle, print the category, exit 254.
- **Note for root (outside my scope):** the actor's `CommandSubmit` checks `command_ready_room` before the idempotent attach. If a just-committed Submit's publication is still queued, an exact retry may get `command_room_pending`. That must not count as a definite no-admission.

**B3. `command-status` and `cancel` exit 0 when the remote answers Busy/QuotaExceeded/FutureDeferred. Lines 754–764 together with 455–466.**
`apply_answer` returns `Ok` for those three error codes, so `read_operation_inner` returns 0 having printed nothing. For `cancel` that is a false success: no cancellation was recorded. Minimal fix: return 0 only for `Ok(status)`. For retryable wire errors, retry with a fresh request ID within the 180 s budget, or exit 255 with the category.

**B4. Exit codes and categories don't match the approved mapping (phase2:532–536, referenced by local-client line 271).**
- Unknown_launch/lost should exit **254**; today they come out as 255 via `status_failed` (378).
- Local 255 and a remote exit of 255 are supposed to be told apart by a stable stderr category. Today every error becomes the single message "remote_pending or incomplete result" (716/727), and remote 254/255 exits get no `remote_exit` category (715). The categories `output_gap`, `input_failed`, `invalidated`, `stdin_unconsumed`, `remote_pending` and the refusal code are all lost.
- Errors before admission exit **1**, not 255. This covers stdin overflow or timeout (801–806), local_busy when prepare times out (787), and prepare failures (783, whose category is also thrown away). They exit 1 because `run` returns `Err` and `cli.rs:403-407` maps that to `ExitCode::FAILURE`.
- **Minimal fix:** keep a small closed enum of outcome categories inside `command_cli`. Print one `marmish: <category>` line, and map pre-admission errors to `Ok(255)` inside `run`.

**B5 (plausible). A Poll that reaches the server before the Submit fails the whole wait. Lines 455–467, 658.**
For a non-Submit request on an unknown invocation, the server replies NotFound (`command_service.rs:226-234`). The submit path polls immediately after `local_queued`, before any authenticated Submit answer. If relays reorder the two messages, or the Submit publication is retried after the Poll was published, the CLI consumes NotFound and exits 255 while the command runs. Minimal fix: while no authenticated status has been seen in this wait, treat NotFound on Poll as retryable (consume, then re-poll with a fresh ID).

## Non-blocking (small, bounded)

- **N1, line 675–677.** `Ok(LocalBusy)` falls into `Ok(result)` and sets `queued = true`, even though the request was rejected before reaching the queue. If another process's Poll is recovered afterwards, `pending` keeps stale cursors and the next send gets `command_cursor_stale`, exiting 255. Fix: add a `Ok(LocalResult::LocalBusy) => {}` arm.
- **N2, lines 510, 641.** After a Finish comes back Busy, `terminal = None`. If the deadline hits before the next terminal Poll, the already-known outcome is replaced by 255 remote_pending. Fix: keep `known_terminal` and return it with `delivery_pending` when the deadline expires.
- **N3, lines 547 and 747.** `finish_delivery` and `read_operation_inner` give up on a single 15 s IPC Timeout or Io error. `wait_inner` retries those until its deadline; these two should do the same.
- **N4, lines 843–846.** No Ctrl-C handler is active during the Submit exchange, so SIGINT kills the process without printing the handle. Recovery still works via `commands`, but the design asks for the handle to be printed. Fix: print the handle before sending, or wrap the call in a select on `ctrl_c`.
- **N5, line 109.** Opening a FIFO given to `--handle-file` blocks until a writer appears. Fix: add `O_NONBLOCK`; the `is_file()` check already rejects it once opened.
- **N6.** A complexity tool flags `wait_inner` (31), `apply_answer` (23) and `read_stdin` (24). Rather than suppressing that, the B1 and B2 fixes are natural points to split out `poll_once` / `write_then_consume`.

## Confirmed correct

- **Response checking:** strict base64 and canonical re-encoding, the 43,692/32,768 byte limits, SHA-256 binding, and checks on id, server, session and the status invocation. The CLI doesn't check local account; that is correctly left to the actor's `validate_entry`.
- **Op and digest cross-checks:** the recovered op and digest are checked against `AnswerEntry`.
- **Stable read IDs:** each Poll keeps one stable ID until answered or consumed, and pending/queued resets behave correctly apart from N1.
- **Finish delivery:**
  - Finish only ever uses the request ID the actor persisted.
  - `delivery_confirmed` comes from durable `finish_confirmed` or an authenticated `finished:true`; a `None` is never read as confirmed.
  - Busy replacements and the 4-attempt cap stay with the actor.
- **Stdin:** at most 16 KiB+1 is read with a 15 s budget measured monotonically. EOF and POLLHUP are handled, no reader thread is left behind, and stdin is read before any IPC.
- **Selectors:** cursors must strictly increase and `next` must equal the last cursor, with the 10,000 cap. `--invocation` requires exactly one match and `--latest` is explicit.
- **Handle file:** O_NOFOLLOW, owned by the current user, mode 0600, at most 1024 bytes.
- **Detach:** `--detach` succeeds only on an authenticated `authority_valid` status. In the wire format every Status means the server admitted the invocation.
- **Ctrl-C** during wait/status prints the handle and never sends Cancel.
- **Secrecy and shell:** no argv, stdin or Submit request ID is printed. Argv bytes go through without UTF-8 conversion or any shell.

## Existing tests

The six offline tests check `read_stdin`, the `decode_answer` binding, `copy_poll` on its own, the `finish_delivery` happy path, selector paging and the handle-file checks. They never exercise the consume side of `apply_answer` (which would have caught B1), the Submit 254/255 and retry paths (B2), a Busy reply to status or cancel (B3), the `wait_inner` pending/queued logic (N1), Finish Busy replacement, or NotFound before Submit. Minimal additions using the existing `serve_replies` harness:
1. A `stdin_unconsumed` Poll: bytes are written before `CommandConsume`, and the exit code is preserved.
2. A Submit Timeout followed by an identical `request_id` retry that gets `LocalQueued`.
3. A Busy status/cancel reply does not exit 0.

These need `apply_answer` to take injectable writers. As you asked, I don't infer acceptance from tests passing.
