The overall shape is sound: one immutable candidate tuple, one run attempt with no stitching of failed cells, concurrent jobs with no cross-job `needs`, monotonic per-process timing, fixture claims checked against authenticated server evidence, and no percentiles. Four contracts the acceptance logic depends on are missing or conflict with the approved Phase 2 interfaces.

## Blocking

**B1. No interface exists for the server-side evidence and cleanup checks the rollup needs.**
- Lines 52-57 and 172-174 require evidence from the server's own records: the authenticated principal, MLS group and session, invocation and digest, the one engine admission, outcome, and authority validity. Lines 229-232 need registered worker ownership to prove cleanup.
- The approved local IPC has exactly four methods: `command_submit`, `command_status`, `command_poll` and `command_cancel` (Phase 2 lines 478-484). All of them are keyed by a client handle.
- The interfaces document gives the actor owned snapshots internally, but no server-side local read method. It also exposes no worker process identity.
- Calling the gap a "bounded interface review blocker" (line 57) postpones a decision about a new trust-relevant IPC surface until implementation.
- **Fix:** specify the method here and send it through a Phase 2 interface amendment review. For example, `command_evidence { after: Option<cursor>, limit: 1..64 }`:
  - same-UID only, read-only, actor-owned, with frames of at most 64 KiB;
  - each row carries principal npub, a hash of the MLS group, session, invocation, `submit_digest`, an `engine_admitted` count, terminal outcome, per-stream `produced/closed/gaps`, output SHA256s, `authority_valid`, and `worker_state` (`running|exited|unknown`);
  - no argv, stdin or output bytes, no paths, no secrets;
  - add a server-side status for cleanup that proves every job is terminal and every worker exited.
- Until that is approved, mark the evidence and cleanup gates as unimplementable, not as passable.

**B2. Cohort scheduling and timing are underspecified, and the stated budget can't hold all the work.**
- The single 30-minute server lifetime and 70-minute job cover one cohort. Each platform job must also run:
  - a direct server and client;
  - an Arti server and client with fresh identities (line 23);
  - the benchmark servers (`--max-commands 4`, direct and Arti);
  - the detach/reconnect and restart workload;
  - the zero-grant negative.
- The doc never says whether these run concurrently in one job, sequentially, or in separate jobs. It doesn't split the budget either.
- The onion relay is optional ("may run", line 75). Its lifetime, readiness binding and deadline relative to the Arti cells are undefined.
- Line 24's "all required cells pass in one exact run attempt" doesn't say which gates belong in that attempt. Provider qualification, for one, is separate by design (131-136).
- **Fix:**
  - Give a per-job timeline that lists each cohort's daemons, whether they run concurrently or sequentially, and its frozen deadline.
  - Make the onion owner mandatory for Arti cells. It publishes a bound `RelayReady` record (onion URL digest, expiry) before any Arti server starts, and its lifetime must cover every platform job's Arti deadline plus cleanup.
  - Name the exact gate set that must share one run ID and attempt. Name what qualifies separately and how the rollup links it to the same candidate tuple.

**B3. The draining and shutdown conditions are undefined, and can kill a server before clients finish.**
- Clients retrieve 2×128 KiB through remote `command_poll` pages of at most 16 KiB (Phase 2 lines 265, 484), so the server must keep answering after the third command finishes.
- Phase 2's `--max-commands` permits only a "bounded response drain", whose length is never given (lines 511-513).
- Line 147 says "drains admitted outcomes". Line 149 needs every client acknowledgement, but nothing says how a server learns that a client is done.
- **Fix:**
  - Stopping admission at N must not stop the daemon. The supervisor stops it only when (a) a verified `ClientTerminal` record exists for every expected pair, or (b) the frozen deadline passes, which is a failure.
  - Require Phase 2's implementation to keep serving status and poll after N until that stop, or until `--max-uptime`.
- **Admission accounting:**
  - The client harness must never resubmit with a new invocation. After uncertainty it reuses its handle.
  - Otherwise one client's retry is a second unique admission and takes another client's slot, because N is global, not per principal.
  - List which negative probes run against the main servers and prove they don't count toward N.

**B4. The fixture receipt's location and the worker's environment are unspecified, and the obvious implementations are wrong.**
- The worker clears the environment and sets HOME, USER and LOGNAME from passwd, PATH to `/usr/bin:/bin`, and cwd to the configured directory or the passwd home (Phase 2 lines 116-118). `launcher.rs` `child_environment` matches.
- So the fixture sees the runner's real home, not the harness's disposable HOME, and inherits no harness variables.
- If the receipt path comes from argv, the client controls it, which would make the fixture a general file-write primitive.
- **Fix:**
  - The fixture derives its receipt directory from its own canonical executable location: a sibling owner-only directory created by the harness.
  - It accepts only a strictly formatted public nonce and vector ID from argv, and creates `<dir>/<pair-nonce>.receipt` exclusively.
  - Configure `cwd` to a private harness directory.
  - Assert the fixture never writes under passwd HOME.
  - The harness verifies the fixture's canonical path and digest against the grant before launch.

## Non-blocking

1. **Build placement:** build the fixture and the harness in the build jobs, and pin their digests in `RunBinding` and the candidate tuple. Building them in platform jobs repeats the old macOS disk-exhaustion failure and complicates keeping compilers out of the product's runtime.
2. **Worker provenance:** the worker can't report a version, because Phase 2 forbids a worker discriminator in its argv. Its agreement with the tuple must come from manifest digest and inode checks, never from running it with flags (line 41).
3. **Expiry vs cross-machine clocks:** checking expiry and future timestamps (line 92) compares clocks across machines, which line 189 forbids. Set a skew tolerance (e.g. ±120 s), and treat run ID, attempt and nonce binding as the real freshness check.
4. **Per-pair time cap:** because clients run serially, one hung pair can use up the remaining budget and erase diagnostics for the other cells. Cap each pair at the remaining time divided by the cells left; the failure verdict is unchanged.
5. **Goodput formulas:** give both formulas exactly. Command goodput = verified stdout+stderr bytes ÷ (immutable submit → verified drain). Drain goodput = bytes ÷ (first nonempty → last byte). `--max-commands 4` allows exactly 1 cold + 3 warm, so drop "at least".
6. **Workflow triggers:** limit them to `workflow_dispatch` and protected-branch pushes. Never use `pull_request_target`, and never run with fork-supplied inputs.
7. **Worker HOME:** document that granted commands run with the real passwd HOME even in disposable test profiles, as approved in Phase 2.
8. **Upstream dependencies:** Arti macOS cells inherit the open Phase 1 Tor restart failure, and the rollup should name that dependency explicitly. The stdin vector reads all its input, so it avoids the `input_failed` race from Phase 2 lines 420-424. Keep a separate `head -c1` probe if you want that race measured.

Once B1–B4 are specified, and B1's interface has passed its Phase 2 amendment review, I expect to approve, still conditional on Phase 1 acceptance and Phase 2/3 implementation.
