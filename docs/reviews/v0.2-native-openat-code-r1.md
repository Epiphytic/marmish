## C ABI correctness (from reading the code)

- **What the C side expects.** `openat(int, const char *, int, ...)` takes its mode as a variadic argument. C promotes anything narrower than `int` to `int` in that position, and libc reads it back as an `int`-sized value (`va_arg(ap, int)` on Darwin, an unsigned int on glibc). Rust refuses to pass a `u16` variadic argument (E0617), which is the error you hit with macOS's 16-bit `mode_t`. Passing a 32-bit `c_uint` is the correct promoted form on both platforms.
- **Linux.** `mode_t` and `c_uint` are both `u32`, so the binding is an identity with no change in behaviour.
- **macOS arm64.** The variadic argument now goes out as a 32-bit unsigned value in Apple's variadic stack slot, matching what Darwin's `openat` reads. No `as` cast is involved, so nothing is truncated.
- **Matches existing code.** `crates/marmish-engine/src/launcher.rs:125` already passes `mode as libc::c_uint` to `openat`.
- **The rest of the crate is fine.** Every other `open`/`openat` call (lines 35 and 48 of this file, `command_check.rs` 1244/1276, `platform/mod.rs:106`, and `platform/macos.rs` 238/257/275) passes no mode argument. `mkdirat` is not variadic, so its `as libc::mode_t` cast is legal; for the 0o700/0o755 values it gets, truncation is a no-op.

`★ Insight ─────────────────────────────────────`
- C's default argument promotion is invisible in C itself, but Rust's FFI makes it explicit. Rust won't promote for you, so any `u16`, `u8`, `i16` or `f32` passed to a variadic C function is a compile error by design. Platform type aliases like `mode_t` hide this until you build on the platform where the alias is narrower.
- The typed binding `let promoted_mode: libc::c_uint = mode;` is slightly better than `mode as c_uint`. Because the input is `u32`, it compiles only while the conversion is lossless, so a later change to the parameter type would become a compile error instead of a silent truncation.
