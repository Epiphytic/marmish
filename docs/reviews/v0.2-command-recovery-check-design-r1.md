## What holds up against the current code

1. **Identical Submit with a fresh request ID is feasible on the normal path.**
   - On the server, the fresh ID finds no request row. `admission_response` returns `Submit{Existing}` for the existing invocation when the digest matches.
   - On the client, `command_submit_client` accepts an identical digest.
   - The response is projected with `client=1` and consumed normally.
   - Together with the one-line marker, this is real evidence that no second launch happened, not a local cache hit.
2. **The local conflict refusal exists.** `command_submit_client` returns `invalid("command_invocation_conflict")` before anything is published. The design correctly says this local check alone does not prove remote refusal.
3. **Reusing the same room under the same identity is consistent with the code.**
   - `command_request` and `open_command_room(peer, false)` reuse the accepted client-direction room.
   - The server's room row survives reopen in the journal.
   - `rebuild_command_routes` and `command_context` re-verify session, peer, transport and authority digest against the frozen metadata.
   - A changed authority revokes the room instead of silently replacing it, so a substitute room cannot pass as reuse.
4. **The stop contract matches `stop_owned`.**
   - The keeper keeps the `ProfileLease` until the engine has joined, the frontend has closed and runtime cleanup has run.
   - `engine_quiesced=false` on an ordinary stop is correct. The design rightly does not treat ordinary stop as proof that the worker is gone (see finding B4).
5. **One-shot observation is technically reachable with existing crate-private access.**
   - `command_check` is a child of `mdk_adapter`, so it can reach the private `receive_one`, the `runtime` and `adapter` fields, `storage`, and the `pub(super)` method `decode_command_event`.
   - `decode_command_event` returns the decoded `wire::Response` with an authenticated context and source, after the sealed-sender, leaf, direction, binding and app-event checks.
   - So capturing the response without a forged context is possible. Doing it safely is underspecified; see B1.

## Blocking findings

### B1. The remote probe has no defined observation point, and normal client projection will discard its response

What actually happens on the client today:

- The probe's Submit is sent with a raw `SendIntent::AppMessage`. That bypasses `client_request` and `command_submit_client`, so the client never gets a `command_requests` row with `client=1` for the probe request ID. That is unavoidable, because the normal path refuses the conflict locally.
- When the server's response arrives, `project_command_message` → `project_response` → `command_project_response` returns `invalid("command_not_found")`.
- `project_command_message` treats `Error::Invalid` as `reject_command_frame`. That emits `frame_refused` and calls `delete_pending_application_events`.
- `receive_one` then calls `ack_replay_delivery`.
- The response is therefore deleted and acknowledged by the normal path. "Normal projection acknowledges an unmatched client response" really means "normal projection deletes it." If anything else processes it first, it can never be observed again.

The design leaves four things open:

1. **Racing with the normal tick.**
   - `turn()` ticks both owners concurrently.
   - `tick_inner` brings in application events through two routes: `receive_one`, and `runtime.drain()` → `apply_effects`. The drain route covers MDK-buffered or epoch-deferred messages.
   - `apply_effects` projects from the durable pending queue (`list_pending_application_events`), not from `effects.events`.
   - A "fixture-local receive turn that mirrors `receive_one`" therefore misses responses that arrive by `drain()`. Any concurrent normal `client.tick` can also consume and delete the response first.
   - **Fix:** specify the exact capture point as the durable pending queue, immediately before `project_command_message`, and not the delivery. Also require that during the probe window the client owner is driven only through the capturing path, with no ordinary `tick` interleaved.
2. **Duplicating `tick_inner` / `receive_one` versus adding a seam.** Copying `receive_one` would leave out `progress_commands`, `reconcile_command_sources`, `recover_transport`, `drain`, `drive_retained`, `submit_command_publications`, and replay ACK / sync. The fixture would drift from production. Pick one exact contract:
   - **Option (a), preferred.** Add a crate-private `Option<ProbeCapture>` field on `MdkOwner`. Only `command_check` can arm it, and the arming carries `{group, request_id, request_sha256}`, with capacity 1. Inside `project_command_message`, only when the envelope is a Response, `response.id == request_id`, and `project_response` returned exactly `Invalid("command_not_found")`, store the already-decoded `(context, source, response)` and then run the unchanged `reject_command_frame`. Everything else is untouched. The field is disarmed after one capture or at stop.
     - This is not a global hook or callback. It is a bounded, armed slot inside the same projection transaction.
     - The design currently forbids a "production callback / global event hook". It should say explicitly that this armed, one-entry, crate-private slot is allowed. Otherwise the probe cannot be both safe and non-duplicating.
   - **Option (b).** The fixture runs the real `tick` and, before each tick, scans `storage.list_pending_application_events()` for `MessageReceived` events in the command group, calls `decode_command_event` on each, and keeps the first match.
     - This is weaker. It is a read before projection with no transaction relationship.
     - `decode_command_event` can revoke a room through `command_context` on an authority change. That side effect needs to be stated.
     - It also only works if the response is still pending at the start of a tick. A response that arrives and is projected within the same tick is missed.
   - Either way, name the API (signature, arming and disarming, capacity, and what happens on a second match) in the design.
3. **The probe's outbound publication is unowned.**
   - `project_application_publications` acknowledges only publications owned by the foundation journal or the command journal. Anything else emits `purpose_ownership_unknown` and is never acknowledged.
   - The raw probe send is owned by neither. That leaves MDK publication state retained on the client: `drive_retained` may republish it, and diagnostics stay degraded until the client is torn down.
   - **Fix, one of:**
     - Define a crate-private, fixture-only ownership record for exactly one probe publication. It must not create a client request slot, so the immutable ledger is not bypassed.
     - Or state the expected behaviour. Republication must be idempotent at the server (same native source, so `command_project_request` replays the same refusal), and this case must count the retained, unacknowledged publication as expected and still allow client cleanup.
   - Also state that the client's journal cleanup checks do not see this state, and whether final client removal must still prove that the MDK outbound queue is drained.
4. **Probe budget.**
   - Until the service/store fix lands, the server deletes the frame and no response ever arrives.
   - The design must give the probe its own sub-deadline, for example 60 s clipped to the original deadline.
   - When that expires, record `remote_conflict_refused=false`, then still write the release gate, or cancel, and clean up. Otherwise the probe uses up the 600 s budget and turns a known defect into a cleanup failure.

### B2. The server-side InvocationConflict response the live check depends on is not specified

Today, `admission_response` returns `Existing` for an existing record without comparing digests. `command_project_request` then fails at line 725 with `invalid("command_invocation_conflict")`, the adapter calls `reject_command_frame`, and the frame is deleted.

The design correctly treats this as a defect and must keep the requirement. But it makes acceptance depend on a fix whose observable contract it doesn't define. Pin the following here, or reference an approved document that pins it:

1. **Durable state for the conflicting request ID.** Does the server record a source and a response slot for it, so the publication is owned by the command journal and replay is idempotent? It must not touch the original invocation record, its digest, or its slots.
2. **Exact response fields.**
   - `id` = the probe request ID.
   - `request_sha256` = the canonical SHA256 of the probe's own inner Submit, not the original.
   - The binding is unchanged.
   - The result is `Err(InvocationConflict)` with no status or invocation payload, or state precisely which fields it does carry.
3. **Replay.** A replay of the same conflicting request (same native source, or same request ID with the same digest) returns the same refusal. The same request ID with a different digest is handled by the existing request-identity conflict rule.
4. **Cleanup accounting.** The refusal slot is terminal. It must not count as active, uncertain, or unknown in `begin_cleanup`'s all-zero check. Otherwise the probe, once fixed, permanently blocks cleanup.
5. **Existing test.** `accepted_bytes_duplicate_attach_and_conflict_are_atomic` currently asserts `is_err()` for this case, which encodes the defect. The design should say it changes to assert a durable `InvocationConflict` publication with the invocation unchanged.

### B3. Root identity after reopen and guard ownership are asserted but not specified

- `EngineTree::capture` takes its parent and root descriptors and inodes from the old `server_profile`.
- After `stop_owned`, that lease is dropped. The descriptors in `pair.engine_tree` stay open, which is good.
- "Verify the same root identity after reopen" needs an exact rule:
  - After `daemon::open` and `enable_commands`, open the new `server_profile.root()` and `root().join("commands")` with `O_NOFOLLOW`.
  - Require their device and inode to equal the receipts captured before stop.
  - Mismatch means red with state retained. Never re-capture.
  - The design should state that `ProfileLease::acquire` and `CommandEngine::start` must not recreate or rename either directory, or that this check is what detects it if they do.
- `remove_engine_tree` must explicitly use the reopened `pair.server` for `command_cancel_fixture`, `begin_cleanup` and `poll_cleanup`, and the new lease. It must say that the old owner and lease no longer exist.

### B4. Where pending stop and partial-reopen ownership live in `Pair` is not specified

- `Pair` holds owners and profiles as `Option`s, and its `Drop` forgets everything. That is the correct fail-safe.
- The design says "retain and finish that same keeper", but `Pair` has no field for a `PendingStop`.
- **Fix:**
  - Add an explicit `Pair` state, such as `server: Running(owner, lease) | Stopping(PendingStop) | Stopped | Reopened(owner, lease)`.
  - If the 30 s observer expires, the case is red. The `PendingStop` is kept and finished, without its own deadline, before any final cleanup or root removal.
  - Never attempt reopen from `Stopping`.
  - If `daemon::open` or activation fails, whatever was acquired goes through `stop_owned`. If nothing was acquired, the state is `Stopped`, and `remove_engine_tree` is skipped because there is no owner or guard. State is kept and the result is red.
- State also that the old server identity must not be passed to `stop_identity` again during final cleanup. Only the current owner is stopped.

### B5. The time budget is inconsistent with the script's 300 s fail-safe

- The script exits with 124 if the gate is not written within roughly 300 s of starting.
- Before the gate is written, the timeline includes the existing three cases (if they run first), Submit, the first Running poll, stop (up to 30 s), reopen, activation and recovery, the post-reopen poll, the identical Submit, the local conflict check and the remote probe.
- **Fix:**
  - Give each stage between Submit and gate its own sub-budget, all clipped to the original deadline, with a total under 300 s minus a margin.
  - Run the fourth case so its pre-gate window is not affected by the earlier cases.
  - State that hitting 124 means the recovery case is red, but cancellation and cleanup must still proceed normally.

## Required non-blocking fixes

1. **Cancel bound.**
   - `cancel_fixture_invocations` hard-codes `ids.len() > 3`, so the change to 4 is in service code and needs service-owner review. The design admits this but should name the file and function.
   - `pair.invocations` must hold four unique invocation IDs. The identical Submit and the probe reuse the fourth invocation and must not be added again, or the uniqueness check will reject the cancellation.
   - Also state how cancellation's "known admission / ambiguity" check treats the extra request rows (the identical Submit, and the fixed conflict slot) that point at, or near, the same invocation. They must not make cancellation ambiguous.
2. **Driving owners while the server is stopped.** `turn()` assumes both owners exist. Specify a turn that drives only the client, or no turn at all, while the server is stopped. Client transport errors during that window are tolerated and do not count as failure.
3. **EOF evidence.** Name the exact wire fields: `InputStatus.eof_sent` and a healthy `InputHealth`, checked from the status before stop and again after reopen. Do not rely on "empty stdin auto-EOF" as an inference.
4. **Report schema.** Replace the existing `"restart_while_running":"not_tested","replay_conflict":"not_tested"` fields with the listed finite fields. Their values must be false or null whenever any stage failed, including the case where the probe's sub-deadline expired.
5. **Marker.** The script writes with `>>` (which follows symlinks). The check only detects problems after the fact. State that the fixture verifies the parent directory receipt and the marker's absence before Submit, and verifies with `O_NOFOLLOW` afterwards. It does not prevent a race, and nothing in a remote request ever names these paths.

## Optional notes

- After reopen, the server reaches the running worker through the recovery set (`schedule_active` issuing Observe), and Status and Poll go through `schedule_requests`. The design's "fresh Status/Poll before the gate" is the right proof. It could say explicitly that the reopened owner must complete `activate` and recovery catch-up (`recovery_caught_up`) before that poll counts.
- The design says it changes no protocol or ordinary command lifetime. Adding a `ProbeCapture` field (B1a) would not break that, but it is a production-build change to `MdkOwner` and needs the same independent code review as the service/store fix.
