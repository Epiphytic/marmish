**Verdict: CHANGES_REQUIRED**

I reviewed `docs/phases/v0.2-phase2-retention-and-ack.md` against the working-tree `command_store.rs`, `command_service.rs`, `command_runtime.rs` and `mdk_adapter.rs`, and the pinned upstream MDK at `8abc51b` (`marmot-session/src/runtime.rs`, `traits/src/app_event.rs`). I edited nothing, used no network and ran no live tests. I didn't run `cargo test` either, because other agents are building in this tree; this is a design-only review. The direction is sound and two things check out: the upstream evidence types do support serde, and existing retirement already refuses to retire while a matching fanout exists (`mdk_adapter.rs:1088-1105`). There are 3 blocking findings, 3 medium and 4 low.

### Blocking

**B1 (High): "terminal" is not a stable condition for expiring the payload, and the fail-closed recovery rule would crash on valid states.** (§1, lines 19–23 and 39–41)
- **What happens:** `InvocationRecord::active()` (`command_store.rs:310-319`) can become true again. `project_completion` sets `uncertain = true` on any `EngineObservation::Failed`, such as a Status Observe timing out on an exited job (`command_store.rs:2428-2432`), and the refusal stays `None`. So a valid sequence is: job finishes → payload is cleared → a later Status times out → the row is "nonterminal" with no payload. Under the amendment's "inconsistent nonterminal payload absence fails closed", that row breaks `command_recovery`/`command_init` even though nothing will ever need its bytes.
- **Change:** define one predicate and use it everywhere: `payload_required(r) = r.owner.server_side && ((!r.engine_known && r.refusal.is_none()) || !matches!(r.feeder, Complete | Failed))`, or the row has a registered `Dispatch`/`WriteInput` operation.
  - Clear the payload only when `!payload_required`, `operation IS NULL`, no Submit slot is pending and no protection applies.
  - Fail closed only when `payload_required && submit IS NULL`.
  - Make the Dispatch, WriteInput, `advance_feeder` and Exited-unconsumed paths (`command_store.rs:1386-1450`, `1583-1609`, `2464`) return a finite `command_payload_expired` storage error.
  - Add this test: exited → expired → Observe `Failed(Timeout)` → reopen → recovery only observes, with no error and no Dispatch.

**B2 (High): an `Ok(())` from upstream ACK does not mean the ACK happened.** (§2, step 4 and lines 81–88)
- **What happens:** the pinned `acknowledge_published_app_messages` (`runtime.rs:4263-4287`) deletes a fanout only if `accepted_targets > 0 && fanout_complete && mls_state` is not `Pending`; otherwise it does nothing and returns `Ok(())`. But `published_app_messages` is already emitted when the message is accepted by any endpoint (`runtime.rs:5665-5667`, `6559`), which can be before the fanout completes. So "only after ACK succeeds, commit the marker" sets the marker while the upstream fanout still exists. The current code already does this (`mdk_adapter.rs:1850-1853`). Today it converges only because upstream re-emits Published on each recovery pass and retirement checks for fanouts.
- **Change:** define the marker as "a genuine ACK returned `Ok` **and** a post-ACK `outbound_fanouts_for_group(group)` scan finds no fanout matching `(app_event_id, outcome.message_id)`". Otherwise leave it unmarked and retry in a later bounded turn. Reword line 87: absence verified after a genuine ACK *is* the marker condition, so state that instead of "fanout absence alone never becomes an ACK marker". Add a test where the fanout is accepted but incomplete or MLS-pending: ACK returns `Ok`, and the marker must stay unset.

**B3 (High): invalidation only beats confirmation inside a single transaction.** (lines 69–71)
- **What happens:** in the store, `Invalidated` is a silent no-op when no outgoing binding exists yet (`command_store.rs:1830-1840`). The adapter sorts invalidations first and commits in 64-update chunks, each its own transaction (`mdk_adapter.rs:1837-1845`). The pending-queue path applies `Invalidated` and then deletes the pending event (`mdk_adapter.rs:1910-1920`). So if an invalidation reaches the store before the matching `Published` binding — in an earlier chunk, or an earlier turn — it is lost. The later `Published` then sets state `published` and stores ACK evidence.
- **Change:** either
  - persist a bounded invalidation tombstone keyed by `(group, native_id)` for command rooms, kept until the replay horizon, which `Published` must check before binding; or
  - apply all of an effect set's command updates in one transaction.

  Add tests for an invalidation in chunk *k* with Published in chunk *k*+1, and for an invalidation before any binding exists.

### Medium

**M1: a duplicate Submit returning `result_expired` contradicts both "no wire change" and the Status behaviour.** (lines 31–33)
- `admission_response` (`command_service.rs:113-131`) never reads the payload: it answers from `status(record)` or the stored refusal. Phase 2 says responses are "derived state, recomputed without reexecuting" (`v0.2-phase2.md:340`). Under the amendment, a Status on the same invocation would return the exit status while a duplicate Submit returns `result_expired`. It also hides a stored refusal such as `command_denied`.
- **Change:** a duplicate Submit with an expired payload answers exactly as before (`Existing` + status, or the stored refusal). `result_expired` stays reserved for the known-then-Missing case (`command_store.rs:2404-2412`). State the precedence: authority revoked → digest conflict → stored refusal → status.

**M2: the list of plaintext copies is incomplete, and line 44 cites a mechanism that doesn't exist.**
- No request or publication payload expiry exists in the code; slots are deleted whole (`command_store.rs:2060-2070`). The full Submit bytes (argv and stdin) also live in:
  - `command_requests.request`, which `check_slot` compares byte-for-byte;
  - `command_publications.wire`/`native` (client Submit, server Poll output);
  - `command_requests.received_response`;
  - the `operation` snapshot.
- **Change:** list each copy with its retirement rule. Anchor the TTL (`created + payload_retention <= now`). Do the clearing as a bounded step inside the existing `command_maintain` transaction, under the same protection set. Say whether client rows (`server_side=0`) are cleared.

**M3: a conflict that rolls back the batch can permanently block native processing.**
- Upstream replays the same Published record on every pass. A persistent evidence conflict therefore makes `apply_effects` return an error every time, which halts native processing for all groups. Also, "complete update batch" really means one 64-update chunk; earlier chunks stay committed.
- **Change:** quarantine the conflicting binding (keep it, don't ACK, emit a diagnostic, keep it blocked from retirement) rather than failing the whole effect set. Define what "batch" means.

### Low

- **L1:** `command_native_bindings` (`command_store.rs:1878-1924`) returns rows that are already acked or invalidated, with no flags. Add `acked`, `invalidated` and `Option<evidence>` to `NativeBinding`, pass at most 64 records per upstream ACK call, and say how an ACK error interacts with the cursor. Today the cursor doesn't advance on error, so one failing binding blocks every later one.
- **L2:** the evidence DTO's strictness. The nested upstream types (`AppMessageRetentionDecision`, `AppMessageAuthority`) don't set `deny_unknown_fields`, so mirror them as local strict structs and require that the stored bytes equal a canonical re-encoding. Say explicitly whether `group_id`/`app_event_id`/`message_id` are stored in the DTO or rebuilt from the binding row.
- **L3:** line 97's "existing safe horizon" for slot and binding retirement isn't in the code. Slot retirement has no time check (`command_store.rs:1975-2070`); only invocation deletion requires the floor and TTL. Reword to the actual conditions or add a horizon.
- **L4:** `stdin_length` must be its own column, not part of the mutable `facts` JSON that `save_record` rewrites, with `CHECK(stdin_length BETWEEN 0 AND 16384)`. `load_record` should then check: with a payload, the invocation matches, the length matches and the digest recomputes; without one, only the bounds. Consider adding `CHECK(submit IS NOT NULL OR active=0)` in support of B1.

Re-review once B1–B3 and M1–M3 are reflected in the document.
