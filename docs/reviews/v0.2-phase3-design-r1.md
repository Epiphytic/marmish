## Blocking findings

**B1. The default prefix collides with the legacy install and with the v0.2 state root.**
- Legacy installs to `~/.local/share/marmish` on both OSes (`scripts/install.sh:803`), with `.marmish-install.json` and `current`. The v0.2 Linux profile root is `~/.local/share/marmish/v2` (`cli.rs:94`), which sits inside the legacy prefix.
- The draft never names a native prefix, and "documented private per-user prefix" could land on either path.
- **Fix:**
  - Default the prefix to `$HOME/.local/share/marmish-native` on both OSes.
  - Native install must reject any prefix that equals, contains or sits inside the legacy prefix or the v0.2 state root (default or `--state-dir`).
  - Never derive the prefix from `XDG_DATA_HOME`.
  - Test that the legacy state and the v0.2 profile trees are byte-identical before and after install, upgrade and uninstall.

**B2. How a running binary finds its own version is unspecified, and macOS breaks the obvious approach.**
- `cli.rs:111` uses `helper: std::env::current_exe()` without canonicalizing it.
- On macOS, `current_exe` returns the path the process was started from. A symlink path through `current` therefore re-resolves after an upgrade, and a running daemon would start the new version's `_vault-helper`.
- The engine canonicalizes the worker path at open (`launcher.rs:892-916`, `lib.rs:114`), but the vault helper path is never canonicalized.
- **Fix:**
  - At startup, every native binary canonicalizes `current_exe()` once.
  - Its parent must be `<prefix>/versions/<id>/` containing a valid `manifest`; that canonical binary is the helper, and the worker is the canonical sibling `marmish-worker`.
  - Outside an installed tree (development or Cargo route), use the canonical sibling and the same checks, without a manifest.
  - Never use PATH, `argv[0]` or the `current` link at runtime.
  - Test: start the daemon, upgrade, then confirm the helper calls and worker launches still use the old version's inodes.

**B3. Upgrading while workers run, and deleting old versions, are deferred to Phase 2, which doesn't define either.**
- **Fix for this phase:**
  - No automatic version garbage collection.
  - Upgrade and rollback only change the selection.
  - Uninstall removes the selection, launchers and marker, and keeps `versions/`, printing the path.
  - A later reviewed `--prune` operation is out of scope.
- The manifest declares `state <profile-format> <engine-format>`. A daemon refuses to open a newer format with a finite `incompatible_state` error and never touches the database.
- Required test: with a daemon and a detached worker running a long command, install the next version and restart the daemon. The command's exact output and exit code must be recovered. Repeat with a rollback, using a synthetic newer state version, and expect `incompatible_state`.

**B4. macOS keychain access may not survive an upgrade or rollback.**
- Items are created with `SecItemAdd` in the file-based keychain with no explicit access list (`macos.rs:163-191`). The default access list trusts the creating binary. For an ad-hoc signature that means its exact code hash, which every upgrade changes. Over SSH, the new version will most likely get `locked_or_denied`.
- Falling back to files is already correctly forbidden; this case is undefined, not unsafe.
- **Fix:**
  - Specify that after an ad-hoc upgrade, keychain profiles may fail with `locked_or_denied`.
  - The error must name the recovery: rollback to the creating version, or re-authorize in a GUI session.
  - It must never trigger a regeneration or a switch to file storage.
  - Rollback to the creating version must restore access, which B3's version retention guarantees.
- Gate: a disposable owned keychain qualification on macOS covering create → upgrade → load → rollback → load, recorded honestly per signing kind (ad-hoc or Developer ID).

**B5. The manifest and its trust root are left to "finalize during review". That decision belongs in this design.**
- **Fix:** one line-oriented format, parsed identically by shell and Rust, with an exact field order:
  ```
  marmish-manifest 1
  version 0.2.0
  target aarch64-apple-darwin
  commit <40 lowercase hex>
  signing adhoc|developer-id notarized=no|yes
  minimum glibc=2.39|macos=15.0
  state <profile-format> <engine-format>
  file <sha256> <bytes> 0755 marmish
  file <sha256> <bytes> 0755 marmishd
  file <sha256> <bytes> 0755 marmish-worker
  file <sha256> <bytes> 0644 THIRD-PARTY-LICENSES
  end
  ```
  The manifest is named `marmish-0.2.0-<target>.manifest`.
- The version-specific bootstrap embeds the SHA256 of each target's manifest. The script and manifest therefore form one trust unit served over HTTPS.
- Rules:
  - Reject a CR, a tab, a trailing space, any unknown or repeated line, or a missing `end`.
  - Download the manifest before any binary.
  - Fetch each binary with `--max-filesize <bytes>`, then check the exact byte count.
  - Compute hashes with `sha256sum` or `shasum -a 256` and compare to the manifest; never run `-c`.
- `SHA256SUMS` remains for humans and is not consumed by the installer.
- Per-binary assets are fine. Reconcile the plan's wording, which still says "archives" (`v0.2-plan.md:145`).

**B6. Install-path validation must match the worker's own check.**
- `trusted_worker_executable` requires a file mode without group/world write. It also requires every ancestor to be owned by root or the user and not group/world-writable, unless it is a root-owned sticky directory (`launcher.rs:158-167`, `892-916`). A home directory with mode `0775` passes install but fails at the first command.
- **Fix:**
  - Export one engine predicate, e.g. `marmish_engine::validate_executable_path`.
  - Native install calls it on the staged and final canonical paths before activation, failing with a finite `unsafe_install_path`.
  - Installed files are `0555`; version directories are `0755` and are sealed after population.
  - Test with a group-writable ancestor, expecting refusal before any change.

**B7. The crash and rollback transaction has no defined order or recovery.**
- **Fix:** take the lock `<prefix>/.lock`, then:
  1. Create `.staging-<rand>` (`0700`) with exclusive creation.
  2. Copy, fsync and rehash each file against the manifest, then apply its mode.
  3. Rename to `versions/<version>-<target>`.
  4. Fsync the prefix.
  5. Create `.current.tmp` as a symlink to `versions/<id>` (relative), then rename it over `current`.
  6. Create launchers that don't exist yet the same way: `bin_dir/{marmish,marmishd}` as absolute symlinks to `<prefix>/current/<name>`.
  7. Rename a temporary marker into `.marmish-native-install.json` (`0600`) and fsync.
- Recovery under the lock:
  - Remove stale `.staging-*` directories you own.
  - Adopt an unreferenced complete `versions/<id>` only after rehashing it against its own manifest.
  - Reconcile `current` against the marker.
- An existing version directory with identical bytes is a no-op. Different bytes give a finite `version_conflict` error.
- Gate: a test-only fault-injection feature, never present in release binaries, kills the process after each step. Each case must leave either the old selection working or the new one complete, and must keep unrelated files.

**B8. The coexistence policy and the protection of the legacy route are undefined.**
- **Fix:**
  - Phase 3 offers no replace flag.
  - If `bin_dir/marmish` or `marmishd` exists and is not one of our own launcher symlinks, refuse with `unrelated_launcher`. That covers a legacy launcher (bytes starting `#!/bin/sh\n# marmish installer format 1`, from `install.sh:470`).
  - The error offers `--bin-dir DIR`, or a legacy uninstall pinned to its version.
- The native bootstrap must live at a new path and as a release asset (`marmish-install-0.2.0.sh`). Leave `scripts/install.sh`, which the README fetches from iris `head` (`README.md:61`), plus `release.yml` and `installer-validation.yml`, unchanged until the publication gate. New workflows go in separate files.
- Gate: run the legacy selector logic (`install.sh:197-210`) against v0.2 tags. It must skip `v0.2.0-rc.N` and `v0.2.0`, because its pattern only matches `-experimental.N`.

**B9. Setup's interaction with config and a running daemon is underspecified.**
- **Running daemon:**
  - The daemon holds the exclusive profile lease, and config is restart-only (Phase 2 draft lines 74-83).
  - While the daemon holds the lease, setup refuses with `identity_in_use` and changes nothing.
- **Config mapping:**
  - Map setup only onto Phase 2's exact `config.json` v1 fields; invent no `inbound_enabled` field.
  - "Inbound disabled" means `role:"both"` with `execution_clients:[]`.
  - Reword "re-enabling" to "enabling", since there was never an earlier enabled state.
- **Repeat runs:**
  - Setup never writes `command_policy`, `limits`, `aliases` or `cwd` on an existing config. They are preserved semantically.
  - Identical input is a no-op.
  - Any changed field requires `--update`, which changes only the named fields.
  - Removing a grant needs an explicit `--revoke`.
- Phase 2 still has to say whether a granted npub also needs `trusted_remotes` or transport-room trust. Setup binds to that answer and must not guess it.

**B10. Bootstrap execution is fragile.**
- **Stdin:**
  - With `curl | sh`, the script's stdin is the rest of the script.
  - Run native install with `</dev/null` and setup with `</dev/tty`. Setup opens `/dev/tty` itself and fails `no_tty` when it can't.
  - Wrap the whole script in `main() {…}` with `main "$@"` on the last line, so a truncated download runs nothing.
- **Pre-install probe:** run `"$tmp/marmish" --version` before calling install. Map failures to finite diagnostics:
  - exit 126 (noexec temp) suggests setting `TMPDIR`;
  - exit 127 or a loader error means an unsupported libc (musl), a 32-bit userland on an aarch64 kernel, or glibc older than the manifest's minimum.
- **Rosetta:** detect `sysctl.proc_translated=1` and advise running a native arm64 shell.
- **Root and tracing:**
  - Reject root (`id -u` = 0) in both shell and native code.
  - Never use `set -x`.
  - `--debug` only forwards bounded stage names.

## Required interfaces (proposed; conditional on the final Phase 2 CLI)

```
marmish-install-0.2.0.sh [--prefix DIR] [--bin-dir DIR] [--asset-dir DIR]
                         [--quickstart] [--debug] [--help]
marmish install --source-dir DIR --manifest FILE [--prefix DIR] [--bin-dir DIR]
marmish install --select-version VERSION [--prefix DIR]      # rollback; verified versions only
marmish install --status [--prefix DIR]
marmish uninstall [--prefix DIR] [--bin-dir DIR]             # keeps versions/ and all state
marmish setup [-i NAME] [--state-dir DIR] [--key-storage auto|keychain|file] [--debug]
marmish setup --non-interactive --role client|server|both --relay URL... [--tor auto|always|off]
              (--grant NPUB... | --no-grants)  [--update] [--revoke NPUB...]
```

- `--asset-dir` performs the same manifest and hash verification on local files. CI uses it for candidate assets, and the HTTPS path is tested separately after publication and before any README switch.
- Server and Both in non-interactive mode require either `--grant` or `--no-grants`.
- Finite setup errors: `no_tty`, `identity_in_use`, `invalid_relay`, `invalid_grant`, `config_invalid`, `config_exists`, `keychain_locked_or_denied`, `keychain_failed`, `incompatible_state`, `interrupted`.

## Test criteria (root owns CI; these are criteria, not workflow edits)

- **No Python, uv or compiler:**
  - Run the bootstrap and then the installed commands under `env -i HOME=<disposable> PATH=<allowlist dir>`.
  - The allowlist directory holds symlinks to `sh`, `curl`, `sha256sum` or `shasum`, `uname`, `mktemp`, `id`, `chmod`, `mkdir`, `rm`, `mv`, `cat`, `wc`, `tr` and `sysctl`.
  - Assert that `python3`, `uv`, `cargo` and `rustc` are not resolvable. macOS's `/usr/bin/python3` shim is excluded because `/usr/bin` is not on that PATH.
- **Linux binaries:**
  - The ELF NEEDED entries must form an exact allowlist: libc, libm, libgcc_s, the dynamic loader, and pthread/dl only if they appear.
  - Record the highest `GLIBC_` symbol version and put it in the manifest's `minimum` line.
  - Run on that declared baseline. If the build is on Ubuntu 24.04, honestly declare its glibc 2.39.
- **macOS binaries:**
  - The `LC_BUILD_VERSION` minimum must equal `MACOSX_DEPLOYMENT_TARGET` (15.0 today).
  - `codesign --verify --strict` must pass on every installed Mach-O, including the worker.
  - Hashes are computed after signing.
- **Install-transaction coverage:**
  - B7's fault points; B6's group-writable ancestor.
  - Paths with spaces.
  - Symlink and unowned destinations.
  - Existing legacy launchers.
  - Two concurrent installs.
  - Identical repeat; same version with different bytes.
  - Upgrade, rollback, uninstall, then reinstall.
- **Setup coverage:**
  - The single keys `c`, `s` and `b`, plus Enter defaulting to Both, through a controlled PTY.
  - Non-interactive mode.
  - An empty grant list really refuses inbound, proven by a real remote attempt that gets `unauthorized`/`role_disabled` with no worker started.
  - Named identity reuse keeps the same npub.
  - An existing restriction set survives a repeat setup.
  - Setup while the daemon runs gives `identity_in_use`.
  - Ordinary CI uses `--key-storage file`. Provider qualification runs separately, per B4.
- **Secrets:** scan shell traces, process arguments and environment, logs and CI artifacts for both 32-byte roots and the nsec. The scan must find neither.
- **Commands:** same-platform installed client/server commands per target, as stated in the draft, plus B3's upgrade-while-running recovery.

## Not blocking

- **Cargo route:** adopt the plan's `cargo install --locked --git … --tag v0.2.0 marmish-native`. That needs the worker binary to move into `marmish-native`, as Phase 2 lines 106-108 propose. Drop the crates.io framing.
- **Debug output:** fix the list of debug stage names in the design.
- **HOME:** state that both shell and native code use the `HOME` environment variable, and reject relative or missing values.
- **Worker name:** Phase 2 already names `marmish-worker`, so Phase 3 can state that conditionally instead of "depends on Phase 2".

`★ Insight ─────────────────────────────────────`
- Pairing a versioned `current` symlink with startup canonicalization is what lets one atomic rename switch versions while running daemons and detached workers keep the exact inodes they started with. Without canonicalization, macOS quietly undoes that.
- Embedding the manifest's digest in the version-specific script turns "HTTPS plus a checksum file from the same place" into one trust unit. It still isn't a publisher signature, which the draft already says correctly.
