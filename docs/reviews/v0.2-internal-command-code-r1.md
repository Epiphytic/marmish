## Blocker

**B1. A valid Poll is dropped on the server when the earlier Poll slot hasn't been retired yet.**
- **Path:**
  - `command_store.rs:1418-1449`: `insert_slot` returns `Invalid("command_poll_busy")` when any `op='poll'` slot exists for the invocation key.
  - Server projection reaches it through `command_store.rs:791`.
  - It reaches `command_adapter.rs:158`: `Err(Error::Invalid(_)) => reject_command_frame`.
  - `reject_command_frame` (`command_adapter.rs:169-174`) deletes the pending application event.
  - `command_projection_deferred` (`command_adapter.rs:354-370`) defers the `*_capacity` categories plus `operation_busy`, `admission_closed`, `duplicate_sources`, `future_deferred` and `clock_behind_floor`. It does **not** include `command_poll_busy`. Its test (`:376-397`) doesn't cover it either.
- **Contract violated:** Phase 2 interfaces, L527: "command_poll_busy, command_operation_busy, command_slot_capacity and command_source_capacity mean defer with native pending event unACKed; never cache a refusal."
- **When it happens:** The client retires its own answered Poll #1 slot and sends Poll #2 for the same invocation. The server has not yet retired its answered Poll #1 slot. Server retirement (`command_maintain`, `command_store.rs:2372-2510`) needs four things, in order:
  1. a published, invalidated or expired publication;
  2. the outgoing rows ACKed and not quarantined;
  3. the fanout absence scan;
  4. a later maintenance tick.

  A single failing ACK can also stall the reconcile page of 64 (root r2 note). Nothing ties the client's next Poll to server retirement. `command_check.rs` `request()` (`:374-396`) only loops `pair.turn()` until the client reads a response.
- **Consequence:** Poll #2 is permanently lost on the server and never answered. Because the client's Poll #2 slot stays pending, the client can't issue another Poll for that invocation and can't regenerate the request. Output and exit retrieval for a live command stalls with no error surfaced. This is reasoned from the code; I did not execute it. The recorded live cases may simply have missed the timing window.
- **Minimal fix:** Add `"command_poll_busy"` to `command_projection_deferred`. The pending event then stays unACKed and is retried after server maintenance retires Poll #1.
- **Tests:**
  - Extend the adapter unit test at `command_adapter.rs:376` to assert that poll_busy is deferred.
  - Add a store/service test: an answered but unretired Poll slot plus a new Poll source gives `command_poll_busy`. After the ACK and `command_maintain`, the same source projects and is answered.
  - Add an adapter-level test: a poll_busy projection leaves the MDK pending application event in place and creates no rejection record.
