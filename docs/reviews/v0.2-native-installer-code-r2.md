## Blocker

**B4. `setup` reports a future config format as `config_version`, not `incompatible_state`.**
- `native_setup.rs:310` calls `config_read` → `CommandConfig::from_bytes`. That fails with `Invalid("config_version")` (`command_config.rs:95-96`).
- This happens before `prepare` and before preflight, on both the Ready and not-Ready paths. So the mapping at `native_preflight.rs:121-123` is never reached from setup.
- The contracts require a proven unsupported version to fail as `incompatible_state` (phase3.md:213, release-entrypoints.md:145), and that category is in the stable error list (phase3.md:397). The claimed "future format → incompatible_state" fix therefore doesn't hold on the main entrypoint.
- The current behaviour fails safely with no write; only the error category is wrong.
- **Minimal fix:** in `config_read`, map `Err(Error::Invalid("config_version"))` to `Err(Error::Storage("incompatible_state"))`, the same way preflight does.
- **Test:** an existing `config.json` with `"version":2`. Setup should return `incompatible_state`, leave the file byte-identical, open no owner, and leave no `.config-*` temp file.

## Nonblockers

1. **Path-based reads.** Checks and reads (`exists`, `checked_metadata`, `reverify`, `read_link`) are still path-based. That's within the same-UID trust boundary.
2. **Anchors cache re-keying.** The cache only re-keys exact paths on rename and unlink, not their descendants.
3. **macOS rename path.** The `renameatx_np` FFI binding is unverified without a compile.
4. **Leftover r1 items:**
   - A failed install leaves its transaction pending until the next run.
   - `status` can mutate state through `recover`.
   - Containment checks compare paths lexically.
   - The `.lock` mode check depends on an unusual umask.
5. **Normalisation on real changes.** When a set really does change, `update_set` rewrites every entry as sorted hex, including npubs the user didn't touch. Consider keeping existing entries as written and appending the new ones.
6. **Interactive repeat defaults.** Interactive prompts default to Both and `auto`, not the existing config's values. Pressing Enter through a repeat on an existing Client config or a Tor-`off` config fails with `config_exists`. It fails safely, but the defaults should come from the existing config.
7. **Release-tool probe race.** There is a window between probing a binary and hashing it, so a different binary could be swapped in. Copies are re-verified against the hash; this is same-UID and build-time only.
8. **Build commit provenance.** build.rs doesn't detect a dirty worktree, and it doesn't track `packed-refs`. A binary built from uncommitted changes would still report the clean HEAD commit. That needs handling in the future workflow (not approved here).
9. **Build output.** `marmish-release-tool` is built automatically into `target/` alongside the shipped binaries. Packaging selects by exact name, so it isn't shipped.

`★ Insight ─────────────────────────────────────`
- B4 is a failure that is safe but still breaks the contract. A preflight error mapping only helps callers that actually reach preflight. Setup parses the config earlier, so it never gets the mapping.
- B3 shows a good pattern for configs that accept two spellings of the same key: compare decoded values, and only rewrite if they differ. Rewriting is the part that loses the user's original spelling.
