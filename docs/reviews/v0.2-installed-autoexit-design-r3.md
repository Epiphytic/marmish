## r2 blockers

**B1: resolved.**
- **Lifetime table:** `validate` now has a per-cohort table (matrix ≤2220s, autoexit ≤3300s, uptime ≤3300s) and rejects any other cohort (lines 31–34).
- **Entrypoint checks:** each entrypoint requires its own cohort. The matrix commands require `matrix`, `prepare` requires a `--cohort` argument that equals the Context's, and `cohort` requires its argument to match the Context. Common validation alone never authorizes an entrypoint (lines 34–37).
- **Separate Contexts:** autoexit and uptime each get their own Context, with its own nonce, `created_at`, digest and cohort-prefixed artifact name.
- **Resolver waves:** the autoexit resolver runs after all matrix jobs, and the uptime resolver after all autoexit jobs. Nothing re-mints or retries automatically.
- **Timeouts:** only the `cohort-autoexit` and `cohort-uptime` jobs get the 65-minute host timeout and the start+3720s first-step deadline. Matrix keeps 55 minutes and 3120s.
- **Gate independence:** the design states that neither cohort replaces or satisfies the matrix gate or the real-MdkOwner remote-conflict gate (lines 56–57).
- **Timing check:** the Context is minted before queueing and lasts at most 3300s, so it always expires before the 3720s internal deadline. The extra host time therefore cannot turn a late run green.

## Nonblockers (fix in place, no re-review needed)

1. **Line 19 is stale.** "The matrix entrypoints and records remain unchanged" now contradicts lines 34–36, which add matrix cohort checks and make `prepare --cohort` mandatory. The `matrix` and `prepare` workflow invocations must also pass `--cohort matrix`. Reword it to: "matrix behaviour, limits and records are unchanged apart from the explicit cohort guard."
2. **Who mints the contexts is ambiguous.** Line 45 says "root-owned workflow resolve mints" the two contexts, but lines 47–51 say the wave resolvers mint them. State that the initial `resolve` job mints only `context.json`, and that each wave-resolver job runs `workflow.mjs resolve --cohort <c>`. Each should keep the `refs/heads/master` guard, a 10-minute timeout, and re-check source/run/attempt and candidate pins against the original resolve.
3. **Use `!cancelled()`, not `always()`.** A cancelled run should not mint later contexts. The intent stated in line 49 is already right.
4. **Name the reconciliation job.** Name the strict always-run reconciliation for the cohorts (line 406), give its `needs`, and say whether the existing `rollup` changes or a new per-cohort job verifies each result against its own Context digest.
5. **The 375s margin also has to cover `prepare`.** The install step has a 300s cap, plus the two initial setups. The queue/checkout/`npm ci` figure is therefore optimistic, and reds will be more frequent than line 120 suggests. This fails closed, so it is fine, but the text should say so.
6. **Zero slack in the worst case.** The late path fits the 600s cleanup window exactly. The inode checks and pre-spawn validation between client stops and the cleanup spawn can push the worst case red by a few milliseconds. That is acceptable fail-closed behaviour; consider stating it explicitly.

None of these reopen points that r1 or r2 already resolved.
