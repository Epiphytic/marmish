## r1 B1: closed
- `recognize` now maps any per-launcher `wrapper()` failure to `launcher_conflict(&p)`, at `native_install_legacy.rs:173`. That covers edited bytes, wrong mode, hardlinks and symlinks, including dangling ones.
- The error is now `unrelated_launcher`, and stderr carries the JSON-escaped path plus the `--bin-dir` guidance.
- The foreign-pair test now uses `matches!(run(o), Err(Error::Invalid("unrelated_launcher")))` for the regular, symlink, dangling and hardlink cases. It still checks that `marmish` is byte-identical, that the foreign `marmishd` keeps its inode, and that no transaction file exists.
- The new separate-process diagnostic test runs with a root containing a quote, `$`, backticks and a newline. It checks that stderr contains the exact `serde_json` path, that the path contains an escaped `\n`, that the line count is 1, and that the `--bin-dir` text is present.

## Do the new tests weaken ownership or rollback checks?
No. Production code did not change in this round. The `native_install.rs` diff is identical to what I reviewed in r1, and only the tests grew.
- **Occupied backup:** a foreign file at the backup name makes `validate_destinations` fail and Status refuse. The foreign backup stays, the original wrapper stays, and the transaction is retained.
- **Partial restore:** I read the setup as the mirror image of the state it models. `marmish` is an original wrapper with no backup, and `marmishd` is a backup with the launcher absent. The test then drives real `legacy_status` recovery and asserts both originals come back byte-exact. It models the pending-restore state by renaming, but recovery itself is the production code.
- All earlier tests are unchanged apart from the stricter error assertion.
