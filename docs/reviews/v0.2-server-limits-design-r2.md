## Prior round-1 blockers

All three are resolved in the design text.

1. **Refusal frozen while only reserved.** Fixed. Lines 82–91 freeze `QuotaExceeded` only when `admitted >= N`. When the budget is merely reserved-full, the request keeps the actual deferred `command_admission_closed` path (`command_adapter.rs:352-370`). The `exhausted`/`reserved_full` split is in the proposed budget struct.
2. **Uptime cannot stop admissions inside a tick.** Fixed. Lines 209–215 add a gate on `CommandService`. It is checked before every New admission and before every `EngineOperation::Dispatch` (actual sites: `command_service.rs:123`, `:599-631`). After expiry, requests take the deferred, un-ACKed path, not `QuotaExceeded`.
3. **macOS clock.** Fixed. The design now uses an explicit, reviewed `unsafe extern "C"` declaration for `mach_continuous_time`, with checked `mach_timebase_info` conversion.

All round-1 non-blocking items are also addressed:

## The irreversible Finish aggregate versus native invalidation: acceptable

Actual code: invalidating an incoming source calls `record_invalidation`, which calls `revoke_record` (`command_store.rs:2702-2779, 2794-2808`). That makes the whole invocation's authority invalid and revokes its slots. Under the design, the `finished` counter stays incremented after this. I judge that safe, for these reasons:
- **Structurally limited to the owner.** The invocation key is `(server, principal = binding.client, invocation)` (`command_service.rs:666`). `authorize` requires the current direction, the current grant (`can_accept`) and the binding (`:75-104`). A principal can therefore only finish its own invocations.
- **Each Finish maps to one real admission.** Finish requires `engine_known`. `admitted` increments exactly once, on the first `engine_known` transition (`command_store.rs:1870-1874`). Each Finish therefore pairs with one distinct admission.
- **No single principal can stop the server early.** Exit requires *every* admission to be finished. A Finish that is later invalidated can at most give up the asserting principal's own output. It cannot cut off another principal's output. It creates no engine work and grants no authority.
- **The effect is only a local stop, which is reversible.** Ordinary Stop keeps all state, and `admitted` stays N, so a restart at the same N would immediately re-qualify to exit.

The design's framing at lines 157–163 is therefore correct. The aggregate must stay what the design says: a peer's consumption claim, never job success, current authority or acceptance evidence.

## Blocking findings

**B1. Auto-exit can fire before the Finish response is published.**

Actual tick order (`mdk_adapter.rs:2389-2425`):
1. `receive_one` projects requests.
2. `submit_command_publications` tries to submit responses. It may defer on network or pipeline state, and native confirmation arrives in a later tick.
3. `progress_commands` runs last. It also re-projects deferred pending sources, so a deferred Finish gets its response committed *after* submission has already run for that tick.

The proposed predicate runs "after an actor turn commits", so the Nth Finish can commit and trigger exit while its response is still `unsubmitted`, `pending` or `prepared`. The last client would then never receive `finished:true`. That leaves an indefinitely pending client slot, and makes the acceptance item "N=3 … durably Finish and automatically ordinary-stop" flaky or impossible.

Minimal correction:
- Add one conjunct to the predicate: no command publication is in a non-terminal state. Only `published`, `invalidated` and `expired` count as terminal; `uncertain` keeps waiting until uptime. Stop stays ordinary Stop; never fabricate or delete anything.
- State the client contract: the CLI's exit code reflects the remote command result. A missing Finish response is reported separately (bounded by the existing client deadline) and never affects the command's success or failure.

**B2. The predicate ignores outstanding reservations.**

Actual code: `schedule_active` dispatches any row with `!engine_known` and no refusal, without re-checking the budget (`command_service.rs:615-623`). Without a config change, `admitted + reserved ≤ N` always holds. But the design explicitly allows lowering N across a restart (line 63). With leftover reservations, `admitted >= N'` and `finished == admitted` can both be true while a reserved row is undispatched or uncertain. The daemon would then exit with a possibly running job. That job would later push `admitted` past N on recovery, and its output would never be finished.

Minimal correction: define the predicate using the proposed budget snapshot:

`maximum.is_some() && admitted >= maximum && reserved == 0 && finished == admitted`

together with the existing "no in-flight turn" conditions and B1's publication drain. Add a test: lower N with one reservation outstanding, and assert there is no exit until it resolves.

## Non-blocking refinements

1. **Schema migration is not specified.** The actual code uses `CREATE TABLE IF NOT EXISTS` (`command_store.rs:568`) and accepts only `user_version` 0/3/4 (`journal.rs:138`). That will not add a `finished` column to existing profiles.
   - Specify the v4→v5 migration in one transaction: `ADD COLUMN finished … DEFAULT 0`.
   - The new `Facts.client_finished` field needs a serde default of false (`command_store.rs:517`).
   - Old binaries must fail closed on v5.
   - Guard the increment with `WHERE finished < admitted`. A failed guard should be a storage error, not success.
2. **Finish must never become an engine operation.** Answer it synchronously in `admission_response`. In `schedule_requests`, treat it like `Submit(_) => continue` (`command_service.rs:582`). In that branch, check `record.refusal` first, so a refused Submit returns its frozen refusal.
3. **`ResponseResult::status()` assumes every result carries a status.** It is used by `result_value`, `decode_client_response` and `command_project_response` (`command_wire.rs:112-117, 509`; `command_store.rs:909-934, 991-995`). A Finish response has no status. On the client, projecting it must not change `engine_known`, authority, status or feeder.
4. **Where the client takes the fingerprint from.** The client's `record.status` is the *last-projected* response (`command_store.rs:909-934`), which can arrive out of order. Derive the fingerprint from the terminal Status inside the consumed response that brought the cursors to `produced`.
   - Preconditions: `command_client_unconsumed` is empty, and `command_client_cursors` equals `produced` on both streams.
   - Also note: `command_consume_response` marks a response consumed even when `chunk_progress` fails (`:1185-1200`). Finish must require the cursors to actually equal `produced`, not just a consumed flag.
5. **Busy is frozen per request ID.** Retrying after Busy needs a new request ID after a fresh Poll. Also define what a fresh request ID with a *different* fingerprint gets on an already-finished invocation. I suggest a frozen `InvocationConflict`. Note that `expire_output` adds an `Expired` prefix gap after exit (engine `store.rs:1412-1436`), so the fingerprint really does change over time.
6. **Which outcomes can finish.** Say explicitly that `NotStarted` with state Exited can finish. Rows ending in UnknownLaunch or Lost are admitted but can never finish, so they leave uptime as the only exit. Ordinary row GC of an unfinished exited row has the same effect. Document this, or protect unfinished rows from GC while `max_commands` is set.
7. **Revoked Finish handling.** A Finish on a revoked row hits the existing non-deferred `command_authority_revoked` error (`command_service.rs:130-132`). Add a test that the source is not deferred forever and that nothing is incremented.
