## Blocking findings

**B1. A fresh room that was created successfully can be reported as `command_room_start_expired` or a cached failure.** This is a deadline and correctness problem.
- `command_local.rs:374`: once the marker and the accepted room exist but the Welcome hasn't drained yet, `command_ready_preparation` returns `Ok(None)`, which becomes `LocalBusy`.
- `daemon.rs:136-142`: every `LocalBusy` reply to a `CommandPrepare` goes back through `rooms.enqueue`.
- `command_local.rs:167-185`: `enqueue` checks the cached failure outcomes first. It then recomputes `fresh_start_window`, which fails once the time is past token + 45 s.
- **Example:** a turn passes the window check at token + 44 s and creates and accepts the room. The Welcome goes out on a later 100 ms tick. The CLI's next probe (token + 46 s, still inside its own 60 s window) gets `command_room_start_expired` for a room that exists.
- **Same problem after accept:** if `apply_effects` or `sync_transport_groups` overruns the 15 s turn after the room was accepted, `daemon.rs:310-320` caches `command_room_discovery_timeout` or `command_room_creation` for 60 s. The CLI then fails with `command_prepare`.
- **Why it matters:** the design says the window and its refusal apply to the first enqueue, and that bound rooms only wait for delivery. The CLI's 60 s wait for the Welcome to drain is cut short at 45 s, and the error category is wrong. The user will likely retry with a new token. Since nothing retires rooms, each retry permanently uses up another of the 64 live slots.
- **Fix:** when a marker for the token already exists, answer `LocalBusy` (or Ready, or uncertain) directly. Don't enqueue, don't apply the window, and don't consult the outcome cache. Keep the window refusal for tokens that have no marker. Add a regression test where the marker and room exist, the Welcome is undrained, and the time is past token + 45 s.

**B2. The full native lib suite now fails 1 of 399 tests.**
- The failing test is `native_install::tests::bootstrap_and_rust_share_manifest_vectors_with_utility_only_path`. It asserts at `native_install.rs:1093` that "Rust vector 4" is invalid, but the vector parses as valid.
- **Cause:** the valid manifest is now built from `compiled_release_metadata()`, so it contains `journal=6`. `native_install.rs:1081` still does `valid.replace("journal=5", "journal=4294967296")`. That is now a no-op, so the negative vector is valid and the test fails.
- **Fix:** build the replace strings from `JOURNAL_FORMAT` so the overflow negative case is kept. None of the author's focused filters ran this test.

**B3. The design's required tests for the fenced creation path are missing.**
- `create_command_room(.., Some(token), ..)` at `command_runtime.rs:166-250` has no test coverage. That covers the window recheck after discovery, the begin step, the `Existing` result becoming uncertain, the deadline checks before and after the fence, the `create_group` call, and the forget-on-mismatch check of the reserved session.
- Both native tests (`mdk_adapter_tests.rs:1824` and `:1983`) call `command_begin_preparation` by hand and join through the fixture.
- These design-required tests are absent:
  - an interrupted-creation seam that **counts create attempts**, so the same token yields at most one;
  - a fresh room with a pending Welcome that stays `LocalBusy`;
  - discovery failure, expired start-by and runtime room-capacity refusal each leaving no marker;
  - at active capacity, fresh refused while an existing default room is still reused;
  - two different tokens producing different sessions, groups and transports;
  - fresh Submit refusals (wrong peer or relay digest, missing room, an unmarked non-default room);
  - fresh Prepare refusal for an invalid relay, a disabled role or an absent trust.
- **Ordering is random:** the test that is meant to show "fresh group sorts before default" depends on random group IDs, so that order is covered only about half the time.
- **Fix:** add a `cfg(test)` key-package/creation seam (no live discovery is needed) and these cases, including the B1 regression test.

## Checked and found correct
- **Flag scope:** `--new-session` is rejected before any state access for everything except a new remote command (`cli.rs:241`). One frozen token is used across retries, and the CLI's 60 s monotonic deadline is fixed once.
- **IPC:** the `fresh` field is optional and closed (`ipc.rs`).
- **Marker table:** the module is a journal child with CHECK lengths, an immutable peer + relay-digest binding, and Existing returned before freshness or capacity checks. Capacities are 64 active, 4096 total and 4096 markers, checked inside the transaction, with the session unique across markers and rooms.
- **Relay digest:** computed over the normalized sorted URL list (test included).
- **Default exclusion:** marked rooms are skipped in all three default selectors (Prepare readiness, `open_command_room`, the Submit gate).
- **Submit gate:** a fresh session is bound to its marker, and a default session must be the current default selection.
- **Marker without room:** Prepare and room turns return uncertain and never discover or create.
- **Format bump:** schema 6 is in the supported list; preflight and release-info derive from the constants.
- **Internal `new_session` bool:** the only production caller (`command_check.rs:1120`) passes `false`; nothing passes `true`.
- **Installed recovery:**
  - the default-reuse probe makes at most 15 requests at least 1 s apart, inside 15 s clipped to the work deadline, with no retry;
  - client invocation and server evidence counts are exactly 1 before and after, with canonical equality;
  - `bind()` and `validate_record()` now require the second sample's session to differ, and schema 2's required-nullable fields are present;
  - the completeness checks moved into `validate_record`, so the rollup (`installed_local.rs:127-129`) enforces them;
  - two admissions with ceiling 3 are unchanged.
