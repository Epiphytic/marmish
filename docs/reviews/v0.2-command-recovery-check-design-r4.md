**My earlier non-blocking notes are all addressed**
1. **Retired original publication:** if the original publication has been retired and can't attach safely, the case is red, and it never swaps the request ID to force acceptance. This matches the association-check fallthrough in `insert_publication`.
2. **Stage clocks:** each probe's 15 s runs from its own send. The 20 s identical-retry stage starts before the local original-ID retry and covers the whole first probe, and nothing resets either bound. Worst-case sums stay within the earlier 321 s total.
3. **Server response slots:** each server response adds only bounded request-retention and publication obligations, never an active or uncertain invocation. That matches `admission_response`, which doesn't reserve budget for Existing or refused Submits.
4. **Timed-out daemon reopen:** the in-progress open stays an owned task. Its eventual lease and owner are joined-stopped, and a second open is never launched. Observer expiry is still red, and the wall-clock limit is still the external supervisor's, not a claim of bounded cleanup. This is the same ownership priority as the existing `PendingStop` keeper.

Everything I verified last time still holds: original-ID idempotency, the server behaviour for the fresh identical and conflict probes, a probe that only observes the `command_not_found` rejection, no fake ownership or ACK, and the lifecycle and receipt proofs.

**Non-blocking implementation notes**
- **How to hold the reopen:** "owned task" shouldn't be read as requiring `tokio::spawn`. `daemon::open` returns `(ProfileLease, MdkOwner)`, and if those aren't `Send`, a pinned future kept inside `Pair` and polled during cleanup does the same job. Treat its result like `PendingStop`, as a fifth lifecycle state such as `Opening(pinned future)`. Then it can never be reopened from or deleted before it is joined.
- **Retirement detection:** the red condition for a retired original publication should fail on the actual `command_publication_binding` / `command_submit_request_conflict` error. Don't pre-check whether the row was pruned, since that check could race.
