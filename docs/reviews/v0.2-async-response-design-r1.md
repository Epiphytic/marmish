# Verdict: CHANGES_REQUIRED

Making the response optional, backed by an explicit durable obligation, is the right fix. A Poll's bytes can't exist until the engine operation finishes, so the approved "prepared response" field can't be filled at projection time for Status/Poll/Cancel. The proposal also keeps the immutable Submit admission path and the authority rules. But checked against the actual store, engine and wire code, the slot lifecycle has gaps that would strand obligations or attach responses to the wrong slot. Implementation should wait until these are written into `v0.2-phase2-interfaces.md` and approved.

## Blocking changes

**B1. The store must record and check which operation belongs to which slot.**
- **Current code:** an operation is registered on the invocation row (`command_invocations.operation`), and `command_requests` has no operation column. `command_commit_completion` (`command_store.rs:360`) finds the slot only by `(group, request_id)` and checks `binding`. A binding covers a whole session, which can hold several invocations, so a publication could fill a slot that belongs to a different invocation.
- **Fix:**
  - Store `operation_id` and `revision` on the slot, written in the same transaction that registers the operation.
  - Fill a slot only when all of these hold: `slot.k == completion.key`, the slot's operation ID matches the completion, `response_id IS NULL`, and the slot's request matches the registered operation. The mapping is Status→Observe, Poll→Poll with the same `stdout_cursor`, `stderr_cursor` and `max_bytes`, and Cancel→Cancel.
  - Dispatch and feeder operations never fill a slot.
  - Reject a publication that has no matching slot. Today such publications are skipped without any signal.

**B2. The frozen response must match the facts committed in the same transaction.**
- **Problem:** commit changes the engine snapshot before saving it. It overwrites `authority_valid` and sets `admission=Engine`. It can add a `StdinUnconsumed` or `InputFailed` warning. A `Missing` result for an engine-known invocation becomes `result_expired`. A response built from the raw "operation snapshot" can therefore contradict the ledger.
- **Fix:**
  - Use one shared pure function to derive the committed status. The actor uses it before preparing the response, and the store re-checks the decoded response against the saved `record.status` or `record.refusal`.
  - A Poll slot can only be filled from a `Polled` observation. Its chunks must sum to no more than the request's `max_bytes`, and their `next_cursor` values must be at least the request cursors.
  - This matters because `execute_operation` can return `Found` or `Failed` for a Poll when `read_output` errors (`command_engine.rs:612-640`).

**B3. Every pending slot needs a defined final state.**
- **Current code:** `command_maintain` skips any slot with no publication (`if pubs.is_empty(){continue;}`). Invocation GC requires that no `command_requests` row exists. The one-Poll check in `insert_slot` counts every retained Poll row.
- **Consequence:** without a final state, a suppressed or failed slot permanently uses up the 64/256 slot capacity, blocks all future Polls for that invocation, and prevents the invocation from ever being collected.
- **Required:**
  - *Engine `Failed`, wrong observation type, or a stale but still-authorized completion:* the slot stays pending and its operation link is cleared in the same commit, so the actor can start a new operation for it. Optionally, after a bounded number of attempts, fill it with a finite retryable wire error (`busy` or `recovery_uncertain`). Never `not_found` or `Missing`.
  - *Authority revoked:* a durable **Suppressed** state with no publication. GC may retire a Suppressed slot once its incoming sources are ACKed. Absence is trivially proven because no publication ever existed.

**B4. Pending work must be picked up again after a restart or a full queue.**
- **Problem:** the ledger keeps an operation's registration across a restart, but the engine's in-memory `registered` map starts empty.
  - `command_begin_operation` then returns `command_operation_busy` forever.
  - No completion can ever match the old registration.
  - The same thing happens when `try_enqueue` returns `QueueBusy` after `begin_operation` has committed.
- **Not covered by recovery:** `command_recovery` only returns active rows (`LIMIT 33`), so a finished invocation with a pending Status or Poll slot is never seen.
- **Fix:** add a bounded listing (at most 256 slots) of:
  - pending slots that have no operation, and
  - read-only operations still registered in the ledger.

  Re-enqueue those read operations with the **same** OperationId and revision. Dispatch and feeder registrations keep their existing barrier and recovery rules and must not be re-run blindly.

**B5. The store must enforce when `response=None` is allowed.**
- **When None is allowed:** only when all of these hold:
  - the decision is `Existing`
  - the op is Status, Poll or Cancel
  - the request is server-side
  - the invocation record exists
  - `authority_valid` is true

  A new Submit, a refusal, or a revoked-authority request must carry `Some`.
- **Duplicates:** a duplicate of an existing slot, Submit included, must be attach-only with `None`.
- **Why this matters today:** `command_project_request` always calls `insert_publication(plan.response)`. A re-prepared response for a slot that already has a `response_id` gets a different event ID and fails with `command_publication_binding`. That duplicate is then never ACKed and is retried forever.

**B6. Busy and capacity errors must mean "defer", not "refuse".**
- **Which errors:** `command_poll_busy`, `command_operation_busy`, `command_slot_capacity` and `command_source_capacity` must leave the native event pending and unACKed. They must never produce a wire refusal or a cached decision.
- **What the design must say:** a new Poll waits until the previous Poll slot is retired, not just answered. GC must run promptly after `command_record_native_acks` so this wait actually ends.

## Non-blocking clarifications
- "Client retries its same durable request" should say: the same frozen native event, driven by MDK convergence. Never new ciphertext.
- `command_commit_completion` should report which slots were filled and which were suppressed, so the actor isn't left guessing.
- A separate existing deviation, outside this proposal: the Poll path gives stdout the whole `max_bytes`, where Phase 2 says each stream gets up to 8192 first.

Once B1–B6 are added, the proposal changes nothing else: Submit admission, the barrier and CommitAck rules, authority suppression, native ACK and fanout absence, and the 64/256/16/2/2 caps and byte limits all stay as approved. With them in place, I'd expect to approve it.
