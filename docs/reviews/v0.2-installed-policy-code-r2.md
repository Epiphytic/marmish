## Blocker fixes verified

**B1: setup check (`installed_policy.rs:351-367`, `setup` at `:400`)**
- `validate_setup` now requires both `identity_created == fresh` and `owner_opened == fresh`. Only the first probe call (`client-probe`, no peer) counts as fresh, so it now matches the product, which opens the owner when it creates an identity.
- The other three calls (probe trust, server grant, client trust) must report no identity creation and no owner open.
- The test at `:1695` covers all four calls, including both mismatches for each.
- Note: `out.status.success()` is now checked after the report parses. An `Err` is still returned, so behaviour is the same.

**B2: the failure path keeps all five rows (`:1330`, `:1058-1061`, `retain_execution` at `:1148-1172`)**
- **Four denials first:** `state.expected` gets the four denial rows from `expected_rows_partial` before the executed case starts.
- **Fifth row before anything can fail:** the client finds the durable invocation with the exact handle (count == 1). Right after that, the code reads `client_group_submit` and saves the fifth row. That happens before the same-ID retry, the second listing, the CLI wait, the output and receipt checks, and the conflict check, so a failure in any of them still leaves exactly five rows.
- **The saved key is real data, not a claim of admission:**
  - The handle comes from `CommandHandle::for_submit` on the prepared operation.
  - The digest is the client's own durable `group_submit_sha256`, which must appear exactly once with `authority_valid` (`installed_cleanup.rs:320-333`).
  - `retain_execution` requires exactly four rows beforehand, a 64-character hex digest, and no duplicate key.
  - It only records the row as "possibly executed"; nothing claims the server admitted it.
- **Cancel reads the server's actual ledger:** `run` sets `result.failure` before `close` (`:1427-1435`). `close` then calls `cancel_policy_execution` when there are five rows (`:724-735`). That function pages the server's ledger and requires:
  - at most five rows, in increasing cursor order, with valid pagination;
  - every row to be in the expected set, with the exact session and digest;
  - at most one executable row.

  Only then does it send a cancel for that row's cursor. A row that was never admitted causes no cancel. An unexpected or mismatched row stops it.
- **Removal is still guarded:** `prepare_policy` runs against the same five rows, so a cancelled outcome still refuses engine removal. That leads to an ordinary stop and a red run. `remove_private_workspace` is still reachable only after a completed close.
- **Final binding on success:** after a successful case, `state.expected` is rebuilt with the strict `expected_rows`, which rejects any missing case. It must produce the same five rows.
- **Regression test (`:1725`):** with the fifth case missing, the five-row binding survives, its session and digest match exactly, and a duplicate key is rejected.
- **r1 nonblocker 3 is gone:** the group-digest read no longer comes after the wait, so it can't hide a wait error or a signal.

**Wait headroom:** the CLI now uses `--wait-seconds 170` inside its 180 s process slice.

## Nonblockers
1. **Accepted risks you already named:**
   - If the request is admitted but the client listing or `client_group_submit` fails before the fifth row is saved, there are only four rows. Nothing is cancelled, the engine is preserved, the server gets an ordinary stop and the run is red.
