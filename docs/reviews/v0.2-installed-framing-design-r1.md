## What the source confirms
- **Detached submit:** a successful `--detach` exits 0 and prints exactly one `marmish handle: <JSON>\n` line on stderr (`command_cli.rs:957`). Stdout stays empty because no Poll is sent before the Submit is accepted (`command_cli.rs:858-868`, `782`).
- **Wait:** `wait --handle` exits with the remote exit code (7 here) and writes the remote output raw. It prints no handle when the code is below 254 (`command_cli.rs:942-958`, `1191-1193`). A `delivery_pending` notice (`:591-597`, `:814`) or a `stdin_unconsumed` warning (`:571`) can be added to stderr, so failing the sample on any extra diagnostic is the right rule.
- **Flags:** `--detach`, `--wait-seconds` (1–86400), `--no-autostart` and `--stdin` are all global flags (`cli.rs:65-76`). `wait` takes `--handle <JSON>` (`cli.rs:85`, decoded at `:478`).
- **Handle format:** the handle is plain JSON with six fields (`format, profile, remote, session, invocation, submit_sha256`), capped at 1024 bytes and strictly validated (`command_client.rs:11-143`). Passing the observed bytes back unchanged is safe. It contains no key material, although the CLI help calls it "private" (`cli.rs:84`).
- **Root-owned matrix vs child-owned benchmark:** matrix sampling is in `installed_matrix.rs:460-536` (`process::run_input`), benchmark sampling in `installed_benchmark.rs:513-584` (`execute`, which already handles signals and owns its stream readers). They are separate except that the benchmark calls `matrix::base` (`installed_benchmark.rs:521`).

## Blockers
1. **The wait stage as specified exits 255.** Both drivers build arguments with `matrix::base`, which adds `--relay <r>` for every relay (`installed_matrix.rs:184-186`). The context check rejects an empty relay list (`installed_records.rs:81`), so relays are always present. A `wait --handle` with relays but no destination fails with `conflicting_destination` before it reads the handle (`cli.rs:637-648`, used for Wait at `:690-694`).
   - The design says the wait "bypasses account resolution" but never gives the exact wait argument list.
   - It must state that the list is the base arguments without `--relay` (keeping `--socket`, identity and so on), plus `--no-autostart --wait-seconds 300 wait --handle <exact bytes>`.
   - Each owner should build this list locally. Changing the shared `matrix::base` would break the root/child split.
2. **"A known handle must survive a failed wait for exact-key cleanup" can't be done in the matrix without changing its record shape.**
   - Matrix cleanup runs on the server side. Its list of expected handles comes only from the other hosts' complete, validated client results (`installed_matrix.rs:808-830`).
   - A failed client never writes its pairs. On error, `clients()` returns early, and the fallback record has `pairs: []` (`:794-806`, `:837-848`).
   - Cleanup requires the server's actual rows to equal that list exactly (`installed_cleanup.rs:257`). So a handle held only by the client host can't reach the server's cleanup.
   - Only the benchmark already supports this: `record_sample` inserts `sample.handle` (`installed_benchmark.rs:594-627`). That conflicts with the design's "existing result shape remain".
   - Fix: limit the requirement to the benchmark, and state that the matrix keeps its current fail-closed behaviour (no pairs, server cleanup fails safely, red).
3. **"Recovery uses this same framing" contradicts the frozen, approved recovery design.** That design uses a 90-second detach with `--handle-file` (`v0.2-phase4-installed-recovery.md:112,159`). This document specifies `--detach --wait-seconds 300` and `--handle <JSON>`. Either delete the sentence or narrow it to "two separate checks, as recovery already does".

## Non-blockers (wording fixes)
- **Handles from a non-zero detach exit:** "preserve a valid observed handle" doesn't say what happens to a handle printed with exit 255 or 130 (`:959`, `:962`, `:1107`). Say that only exit 0 with exactly one handle line counts as known admission. A handle seen with any other exit should be kept as a diagnostic and treated as unknown admission. Today the benchmark adds any parsed handle to the expected list. That still fails safe through the exact-equality check, but it should be stated on purpose.
- **Signal between stages:** in the matrix this is the existing top-level SIGTERM `select`, which drops the work future and the child (`installed_matrix.rs:833`); there is no receiver per stage. The design should say the per-stage pending-signal check, and its offline test, applies to the benchmark (`pending_signal`, `:630`), and the matrix keeps its existing behaviour.
- **Shared 330-second deadline:** both drivers currently compute `deadline.min(now+330)` inside each call (`installed_matrix.rs:508`, `installed_benchmark.rs:543`). The design should say this is computed once, before the detach, and passed to both stages. The wait's own `--wait-seconds 300` can then outlast the time left, which is fine because the outer kill bounds it.
- **Field names:** the design says "digest"; the field is `submit_sha256`. It should also say to reuse the CLI-encoded bytes without re-canonicalizing them, matching `recovery.md:112`.
- **Metric labels:** the matrix `metric_definitions` text and the Markdown ("CLI process lifetime", `installed_matrix.rs:946-949`) must change to the detached-submit-plus-wait scope. The benchmark design text "existing run_input monotonic interval" (`benchmark.md:226`) is superseded and should be named as such.
- **Wait stdin:** with "empty local stdin", the matrix's `Stdio::null()` and the benchmark's empty piped write are equivalent, since `wait` never reads stdin.

Once these are fixed, the rest is feasible as written: one invocation per sample, no resubmission, the 330-second budget, measurement across both processes, the 262144-byte goodput numerator, the matrix n=1 and benchmark cold n=1 / warm n=3 sample counts, and the plan for offline tests only, with no acceptance claimed.
