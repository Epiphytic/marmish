## Round 1 fixes

- **B1 (doctor) is fixed.** The design now uses commands that exist:
  - `release-info` on all three binaries works. `marmish` and `marmishd` handle it after validating the installed layout (`cli.rs:238`, after layout resolution at `cli.rs:775`). `marmish-worker` accepts only the exact argument `release-info`, also after layout validation (`bin/marmish-worker.rs:11-23`).
  - `install-status --prefix --bin-dir` exists (`cli.rs:120`, `276`).
  - `--version` prints `marmish-native VERSION`, because the CLI takes the crate name. It and `--help` exit before layout validation, and the design correctly marks them as informational.
  - The native code has no doctor feature anywhere, so dropping it is right.
- **B2 (candidate binding) is fixed.** Requiring the candidate run's commit to equal the candidate source, a manual dispatch, the master branch and the exact attempt is checkable through the attempt-specific run endpoint. This makes `v02-release.yml`'s `inputs.source_commit` provable.
- **B3 (provenance ordering) is fixed.**
  - Candidate → bootstrap may change only `scripts/install.sh`.
  - The bootstrap commit must equal the checked-out workflow commit.
  - The workflow must already exist in the candidate.

  Together these mean the checker, the template (`native_release.rs:285` uses `include_str!` on `scripts/install-native.sh`) and the product source are all bytes from the reviewed candidate. This is consistent with the release workflow's ancestor-of-master check.
- **B4 (process-group check) is fixed.** A dedicated terminal runner that keeps the child's PID and group through a normal exit, plus the reviewed `execute`/`stop` pattern for other children, satisfies the descendant check without changing existing helpers.
- **Time budget is finite.** The install step gets at most 1020 s: 5 × 180 s asset fetches plus 120 s. The 120 s cleanup reserve brings that to 1260 s, which leaves about 60 s of the 1320 s supervisor budget for the two script downloads and the final checks. Each step's timeout is the smaller of its own limit and the time remaining minus the reserve, so a slow run fails red rather than passing falsely. The 25-minute job leaves about 180 s for checkout, artifact transfer and upload.

## Install-status report fields

`install-status` prints exactly `{"schema":1,"operation":"status","version":…,"target":…,"active":bool,"generation":N,"prefix":PATH,"bin_dir":PATH}` (`native_install.rs:48-57`, `834-843`).

- **There is no launchers field.** Launcher correctness shows only through exit 0: before reporting, status checks that each recorded launcher is a symlink to `PREFIX/current/NAME` and that the version selector is valid (`native_install.rs:821-825`). Write the requirement as: exit 0, `operation == "status"`, `active == true`, exact version and target, and `generation == 1` for a fresh install. Then confirm the launchers independently with `readlink`.
- **The report contains private paths.** `prefix` and `bin_dir` are full paths. Compare them in memory and never upload them.
- **Status is not purely read-only.** It takes an exclusive lock on `PREFIX/.lock` and runs recovery. On a clean install recovery does nothing, but status must run only while no other install operation is in progress.

## Lock-file semantics (implementation must match these exactly)

**Lock files:**
- **Profile lease, `STATE/default/owner.lock`.** Held with a whole-file `flock` on both Linux and macOS (the `fs2` crate's `try_lock_exclusive`, `identity.rs:109-111`). It is taken before any provider, database or network access, and the file stays on disk after the lock is released. A Python probe of `fcntl.flock(fd, LOCK_EX|LOCK_NB)` on a fresh read-only descriptor opened without following symlinks is the correct authoritative check. Hold that probe lock while deleting the owned root.
- **Engine `frontend.lock` and the per-job `worker.lock`/`io.lock`.**
  - On Linux these use open-file-description locks (`fcntl F_OFD_SETLK`, `platform/linux.rs:15-21`). A `flock` probe will not see them; only `fcntl.lockf` or an `F_OFD_GETLK`-style check conflicts with them.
  - On macOS they use `flock`.

  No jobs are admitted in this gate, so the `owner.lock` probe is the primary proof. If engine locks are probed at all, use the correct lock type for each platform.
- **Install lock, `PREFIX/.lock`.** `flock`, and the file stays on disk.

**Owner socket location (the design text gets this wrong):** the socket is not in the state directory. It lives at `$TMPDIR/mr2-<euid>-<profile_id>/s` (`identity.rs:117-119`, `175-177`), next to `binding.json`. Because the child's TMPDIR is the private root, the check should be that no `mr2-*` runtime directory is left in the owned root. Every child must get the same TMPDIR. As written, checking the state directory would always pass. That isn't a blocker only because the `owner.lock` probe is the authoritative signal and the whole root is deleted afterwards.

## Notes (not blocking)

1. Reword line 121–122 to name the real socket location and the per-platform lock types above.
2. Runtime socket paths are limited to under 104 bytes (`identity.rs:120`). Keep the private root's name short, because the full path is `$HOME/<root>/mr2-<uid>-<32 hex>/s`.
3. Only the resolve job needs a full-history checkout; cells can use shallow ones. The pinned `download-artifact` action (v4, `d3f86a1…`) supports downloading from another run with a run ID and token. Check `size_in_bytes` and `expired` from the API before downloading.

`★ Insight ─────────────────────────────────────`
- On Linux, `flock` locks and `fcntl` locks are separate systems, and a probe of one type can't see a lock of the other. That is why "use the actual lock-file contract" has to be spelled out for each lock: `flock` for `owner.lock` everywhere, and open-file-description locks for the Linux engine locks.
- The profile's lease lock is the outermost lock (acquired "before any key provider/database/network operation"). That makes a single `owner.lock` probe enough proof that no owner is running in this gate, with no jobs admitted.
