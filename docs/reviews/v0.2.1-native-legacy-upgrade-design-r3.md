**APPROVED.** The correction is right, and my earlier B4 wording over-reached.

I checked `validate_options` (`native_install.rs:259-279`). The Linux default state is `HOME/.local/share/marmish/v2` (or `XDG_DATA_HOME/marmish/v2`), and `HOME/.local/share/marmish` is itself in the forbidden list. Native prefix and `bin_dir` are therefore already barred from overlapping the default legacy root and its v2 state. A blanket legacy-root/state disjointness rule would reject every default upgrade, so it has to go.

The risk I wanted to protect against was the migration helper touching state. The revised doc covers it:
- **Read-only evidence:** The helper reads only the fixed marker, lock, `current`, version root and `bin` evidence, and never traverses or removes the state subtree (lines 34-36).
- **Disjointness kept:** The doc keeps the overlap rejection between legacy root and native prefix in either direction (line 32), which is the one that matters. A native prefix inside, or containing, the legacy root is still refused.
- **Existing guards kept:** `validate_options` still keeps the native prefix and `bin_dir` out of the state paths (line 33).
- **Custom state:** A custom `--state-dir` inside a legacy root is harmless on the same reasoning.

Add one test: a legacy root that contains `v2/` with a sentinel file. After migration the sentinel must be byte-identical, and no state path may be opened. The doc's "no identity/key/profile files opened" case roughly covers this. Make the nested-state fixture explicit, and use it for the default-root case too.
