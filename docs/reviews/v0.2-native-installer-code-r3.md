## Checks

- **B4 is fixed.**
  - `config_read` (`native_setup.rs` ~247-266) now turns `Invalid("config_version")` into `Storage("incompatible_state")`. It runs before `prepare`, preflight and any owner open, on both the Ready and not-Ready paths. No other error is relabelled.
  - The test `future_config_is_incompatible_without_identity_or_config_mutation` checks the result of a real `run`:
    - the error is exactly `incompatible_state`;
    - `config.json` is byte-identical;
    - no public key is created;
    - the profile directory has the same entries afterwards, so there is no extra temp file.
- **The render bug is fixed.**
  - The template header comment no longer contains a wildcard. Exactly 4 `@MARMISH_` tokens remain, at lines 9-12, and all four are replaced.
  - The invariants are unchanged: the template is embedded at compile time, render refuses if any `@MARMISH_` is left, and the output is created with `create_new` at mode 0555.
  - The new success test checks for no leftover placeholders, refuses to overwrite an existing output, and refuses a manifest with the wrong commit without creating the output.
- **The layout simplification is sound.**
  - `ExecutableLayout` is now just `{helper, worker}`.
  - Every validation call is still there. In managed mode the current executable is still checked (`executable(&current)?`), along with ownership and mode for each manifest file and the version, target, commit and format match. Development mode still validates the frontend, helper and worker as before.
  - Nothing outside the module used the removed `frontend`/`mode`/`LayoutMode` items. `cli.rs` only uses `layout.helper`.
- **Everything else in scope is unchanged** from my r2 hashes, so the r2 conclusions on B1, B2, B3 and the release tool still apply.

## Nonblockers carried forward

1. **Path-based reads.** Checks and reads are still path-based. This is within the same-UID trust boundary.
2. **Anchors cache re-keying.** The cache re-keys only exact paths on rename/unlink, not descendants.
3. **macOS rename.** `renameatx_np` has not been compiled or verified.
4. **Pending transactions.** A failed install stays pending until the next run, and `status` can change state through `recover`.
5. **Lexical containment.** Containment checks compare paths lexically, and the `.lock` mode check is sensitive to unusual umasks.
6. **Config rewrites.** When a principal set really changes, every entry is rewritten as sorted hex.
7. **Interactive repeat defaults.** Interactive prompts default to Both and `auto`, not the existing config's values. This fails safely with `config_exists`.
8. **Release-tool probe race.** There is a window between probing a binary and hashing it. This is same-UID and build-time only.
9. **Build commit provenance.** build.rs doesn't detect a dirty tree or track `packed-refs`.
10. **Release tool in `target/`.** `marmish-release-tool` is built automatically alongside the shipped binaries. Packaging selects by exact name, so it isn't shipped.
11. **Render test coverage.** The success test doesn't check that each pin equals its manifest's sha256, or that the rendered script passes `sh -n`. Both would be cheap to add.

`★ Insight ─────────────────────────────────────`
- The render bug was a substitution check catching its own documentation. The comment that described the placeholders contained the placeholder prefix, so the leftover-token check refused every render. Only a test of the success path could find this; the failure-path tests all passed while render could never succeed.
- Removing unused fields from a validation struct is only safe if the checks that produced them are still run. Here `executable(&current)?` is kept as a bare statement for exactly that reason.
