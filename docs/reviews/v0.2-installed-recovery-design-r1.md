**Verdict: CHANGES_REQUIRED**

I reviewed `docs/phases/v0.2-phase4-installed-recovery.md` read-only; its SHA256 matches `0e68b722…2baf`. I read the four controlling documents, the benchmark code review r1, and the actual source behind the interfaces the plan relies on. I edited nothing and ran no Cargo, tests, processes or network operations.

Most of the plan is sound. Four blockers are recovery-specific: one makes the mid-run stop step fail every time as written, one is a race in the gate, and two leave required behaviour unspecified. Three more are the benchmark r1 fixes, which this plan doesn't yet include.

## Blockers

**B1. The existing `Daemon::stop` will always reject the mid-run ordinary stop.** (source evidence)
- Plan lines 126–128 stop the server "through the existing owned Daemon stop API".
- That API calls `cleanup::stop_report` (`installed_matrix.rs:139-165`), which requires `engine_quiesced == true` (`installed_cleanup.rs:349`).
- The daemon only reports `engine_quiesced` as true when the cleanup state is `Quiesced` (`command_engine.rs:265,282`, set at `command_lifecycle.rs:134`). That happens only after a cleanup prepare.
- A stop with a preserved running worker and no prepare therefore reports false. The stop exits 0 with all three joined flags true, yet `Daemon::stop` returns an error, so the cohort can never reach reopen.
- `Daemon::stop` also returns `()`, so the "both stop reports" the record needs can't come from it.
- Autoexit already has a parser for this case: `OriginalStop` (`installed_autoexit.rs:78-100`) requires the joined flags but allows non-quiesced. It is tested at line 2089.
- `Daemon`'s output-drain fields are private to `installed_matrix.rs`. The plan must therefore say which of two options it uses:
  - a root-owned `Daemon` method for ordinary stop that returns the parsed report and doesn't require quiescence, or
  - a recovery-local bounded owner built from `process::command`, `process::drain` and `cleanup::stop`.
- It must also say what is recorded for `engine_quiesced` (record the observed value; no authority follows from it). The final post-prepare stop keeps the strict quiesced check.

**B2. Release-gate race.** (design defect)
- Plan line 151: the driver creates the release file exclusively, then writes `release\n`.
- Plan lines 95–97: the fixture treats any wrong-content entry as conflicting and exits 125.
- A fixture check that lands between the driver's create and its write sees an empty or partial file. It then fails a healthy run and writes no receipt.
- Fix: publish the gate atomically. Write and sync a private temporary name, then hard-link or rename it into place, the pattern `records::write_raw` already uses (`installed_records.rs:324-345`). Alternatively, define a too-short prefix as "still waiting".
- Add a test for this race.
- The started marker has the same create-then-write window. The driver must read it only after Status shows the prefix, or treat a partial marker as not ready.

**B3. CLI stderr framing and the second handle are not specified correctly.** (source evidence; one inference)
- In `command_cli.rs`, only `report_handle` (lines 100–107) writes a handle line. On success it is called only when the command is detached or the code is ≥254 (`command_cli.rs:957`). It is also called on error, on signal, and on `delivery_pending` (lines 591, 596).
- So a successful `wait --handle-file` emits no handle line. Plan line 154's "after strict handle-line separation" is wrong for `wait`: stderr should be exactly vector0's stderr.
- For the vector1 immediate submit, the plan needs that command's handle to build the expected map (line 168). My reading finds no line that would print it on an exit-7 success.
- The matrix and benchmark parsers nonetheless require a leading handle line (`installed_matrix.rs:441`, `installed_benchmark.rs:137`). I couldn't resolve this conflict without running anything, so treat it as a discrepancy to verify, not a confirmed bug.
- The plan must pin the exact exit code and stderr for each of its three CLI calls:
  - detached submit: exit 0, stderr is exactly one handle line
  - `wait`
  - the vector1 submit
- The safest option is to submit vector1 with the same detach-then-wait pattern, so its handle provably exists.
- "Terminal Finish outcome" (line 163) should be defined as an observable: stderr contains no `marmish: delivery_pending` and no extra handle line. Otherwise the record risks a fabricated finish field.
- The plan should also say how the handle file is written: exclusive, mode 0600, owned, at most 1024 bytes, which `read_handle` at line 108 requires, plus the exact encoded bytes it contains.

**B4. Signal handling while the server is stopped is undefined.** (design ambiguity)
- Line 179 says SIGTERM "releases or cancels known work". Cancelling needs a live server, and the sealed guard needs the live child.
- The plan must define behaviour for a SIGTERM or failure that arrives while the server is stopping, stopped, or reopening before readiness:
  - never reopen just to clean up
  - release only the started job (via B2's atomic gate)
  - stop the client
  - record `engine_cleanup` as false with state preserved
- It must also define a "known started job" when the marker exists but admission is unknown, for example a detached exit 254 with a handle. Releasing such a job fabricates nothing. Protected removal still needs the exact expected map.

**B5 (benchmark r1 B1). A failed run must keep its record in the rollup.**
- The interface at lines 33–37 is still `validate` plus `markdown_summary -> Result`. That is the shape r1 rejected.
- Add a `validate_record` step that checks a record is genuine, run red or not:
  - bindings, nonces and slot order
  - handles and receipts are present only for passed slots
  - failure fields are null exactly where required
  - the failure stage is set exactly when the run is incomplete
- `validate` then becomes `validate_record` plus the completeness checks.
- `markdown_summary` must render both slots for a red record, and the rollup must embed failed records with `complete:false`.
- Make the stage and category closed serde enums.
- Write the failure record even when the clock reads earlier than the Context's `created_at` (r1 nonblocker).

**B6 (benchmark r1 B2). Cleanup reserve and concurrent stops.**
- The plan never states L+1710 anywhere. Line 57 only says cleanup plus both stops end by L+1770, and line 63 sends cleanup to L+1770.
- State it explicitly: release, cancel, prepare, refresh and protected removal are bounded by L+1710.
- Both final daemon stops run concurrently (`tokio::join!`) against L+1770, so the 5-second kill fallback ends by L+1775.
- The mid-run 30-second stop also gets that extra 5 seconds of kill and reap; say whether its cutoff is 30 or 35 seconds.

**B7 (benchmark r1 B3). Test obligations missing from lines 195–201.**
- A missing handle, a timed-out submit, or exit 254 sets unknown admission, and cleanup then skips cancel and prepare.
- The vector1 sample is never run after a recovery failure.
- Cancellation is limited to known keys (at most 2).
- The atomic gate and partial-content race from B2.
- The ordinary-stop report parser from B1: accepts non-quiesced, requires the three joined flags.
- B4's stopped-window SIGTERM path: no reopen, release only, red cleanup flag.
- Pull the handle-binding and cleanup-plan decisions out as pure functions so they can be tested, as r1 recommended.

## Nonblockers

1. **Spell out the exact Status checks.** "Healthy fully delivered stdin" could be read as allowing `EofPending`. Fields exist on `wire::Status` and are printed by `command-status` (`command_cli.rs:1230-1262`; `InputHealth` at `model.rs:121`). Require:
   - `admission` Engine, `engine_known` true, `state` Running, `outcome` null
   - `cancel_requested` false, `warning` null, `authority_valid` true
   - input: accepted = delivered = length = 16384, `eof_sent` true, health Closed
   - each stream: produced exactly 65536 (fail if over; poll while under), `closed` false, no gaps

   Status prints no session field. The session proof is the CLI binding the reply to the handle and a fresh request ID (`command_cli.rs:975-1000`). Say so rather than "shows the same session".
2. **Bound the number of Status requests.** Each `command-status` call is a fresh remote request with server-side request retention. Set a poll interval and a maximum count per 90-second stage. The 90-second cap is driver-enforced by killing the owned CLI child; the CLI's own internal limit is 180 seconds (`command_cli.rs:979`).
3. **Name the cleanup-authority checks.** Before the first server spawn, prove with a nofollow lstat that `commands/` is absent. Capture the receipt after first readiness and before any traffic. Compare it before the restart spawn and again after readiness, before the post-restart Status. Line 135 says only "after completed stop and after reopen".
4. **Stage budget.** The detached submit has no stated stage bound or `--wait-seconds` value (the default is 180). The listed stages sum to about the full 1200-second work window. Pin a submit bound, and show the fixture's 900-second fail-safe ends before L+1710 in the worst case.
5. **Pending signal checks (r1 nonblocker).** Check for a pending signal without blocking before every CLI spawn, before both daemon launches and the restart, and after cleanup closes.
6. **Configuration shape (r1 nonblocker).** Require `command_policy.keys` and `deny_exec` to be empty before merging `allow_exec`.
7. **Failure-path cleanup red.** Cancellation can never yield a valid guard: the guard's evidence check requires exit 7 and 131072 produced bytes per stream (`installed_cleanup.rs:166-186`). Say plainly that cleanup after cancellation is red, and prefer releasing a started job.
8. **Name the other recovery gate in the rollup.** Add a named entry to the rollup's pending gates for the separate native identical/conflicting-Submit protocol gate, so this cohort can't be read as covering it.
9. **Restart arguments.** Clarify whether the restart passes `--max-commands 3` or relies only on the config. The CLI override replaces the config value (`command_config.rs:285-289`); the config alone is enough.

## Source evidence that supports the plan as written
- **Fixture.** Argv layout, vector0 bytes with 2×65536 per stream, nonce validation, and the executable-derived receipt path all fit a `recovery` selector added beside the vector (`installed_fixture.rs:33-80, 113-160`).
- **Workers survive a daemon stop.** They start in their own session with stdin, stdout and stderr null (`launcher.rs:946-958`, `platform/linux.rs:140-155`). A daemon SIGTERM or group kill doesn't reach them, and they don't hold the daemon's pipes.
- **CLI flags.** `--no-autostart`, `--stdin`, `--detach`, `--wait-seconds` (1–86400), and `command-status`/`wait --handle-file` all exist (`cli.rs:66-100, 158-163`). A detached submit returns 0 only after authenticated acceptance (`command_cli.rs:782`).
- **Restart uptime.** `--max-uptime` overrides the config value and is capped at 1800 (`command_config.rs:281-299`, `command_limits.rs:20-29`). That the count is durable across restarts is inferred from the `CountDrain` "durable actor facts" comment and the amendment; I didn't trace the SQL.
- **Receipt checks.** `EngineTree::verify_path` provides comparison without recapture (`command_check.rs:1506-1513`). `remove_installed` revalidates the guard before unlinking.
- **Cleanup guard.** It is sealed and PID-bound, pages through the complete ledger, and requires an exact expected map (`installed_cleanup.rs:203-330`).
- **Benchmark already patched.** Its `close` now has the 60-second cleanup reserve and concurrent stops (`installed_benchmark.rs:380-411`); the recovery plan should require the same.
- **Budgets.** The 3300/2670/2220/2070 numbers, the 65-minute and 62-minute bounds, and the 900-second identity limit are consistent with the local-workflow design.

I make no acceptance or timing claims, and I added no tests beyond those listed above.
