## Blocker

**B1: Numeric SRV targets turn into IP literals.** `target()` (`command_srv.rs:143-168`) only rejects hosts that Rust's `IpAddr` parser accepts. The `url` 2.5.8 crate in Cargo.lock follows the WHATWG URL rules for `wss`: if the last label of a host is a number (`host.rs:115`, `ends_in_a_number`), it parses the whole host as IPv4.
- So a target of `2130706433.`, `0x7f.1.` or `1.2.3.` passes the label check and is formatted as `wss://2130706433:443/`.
- `RelayPolicy::parse` then turns that into `wss://127.0.0.1/` and accepts it, because it allows IP hosts.
- This breaks "absolute ASCII non-IP targets" in the approved design. The exact-equality check against the profile limits the damage, but this component still returns an IP literal.
- **Fix:** reject a target whose last label is all digits or starts with `0x`/`0X`, or check after `canonical()` that every URL's `host()` is `Host::Domain`. Add test cases for `2130706433.`, `0x7f.1.` and `1.2.3.`.
- **Related, outside this scope:** the guard at `command_target.rs:201-204` only rejects hosts made of digits and dots, so `0x7f.1` gets through there too.

## Checklist items verified against the pinned source
- **Owner grammar:** `validate_srv_name` is reused, owner names are deduplicated, and the 16-name / 4096-byte caps apply.
- **System config:** Linux `into_resolver_config` already errors when no nameservers are found, and `rebuild` fails closed again if none are usable. `into_parts` drops `domain` and `search`, and the resolv.conf options are thrown away. Up to 3 servers are kept in the configured order, rebuilt as UDP+TCP on port 53. Unspecified, multicast and IPv6 link-local addresses are rejected; a zone-scoped resolv.conf entry loses its scope in `ip.into()`, so rejecting link-local is correct.
- **Resolver options:** every field the design lists exists and is set. Opportunistic encryption is `Disabled` by default, and the TLS/QUIC features aren't compiled in.
- **Deadline:** `began` is taken before the config read. The deadline is checked again before the runtime is built, and every lookup shares the same `timeout_at`.
- **Runtime teardown:** the resolver drops when `block_on` finishes, and the runtime drops before the result is returned. Hickory's `TokioHandle` keeps its tasks in a `JoinSet` on this runtime. There is no `spawn_blocking` or `std::thread` anywhere in `hickory-resolver`/`hickory-net` `src`, so dropping the runtime cancels all DNS tasks.
- **Answer validation:** in 0.26.3, `Lookup::answers()` is the answer section only, so glue in the additional section is ignored. When no filtering is needed (`caching_client.rs:409-462`), Hickory returns the server's message unchanged. That means `answers()` really does have to enforce the class, record type, chain shape and owner, and it does. It is fail-closed throughout.
- **Counts and output:** the 16-record limit counts across all owners before dedup. There are no partial results. Priorities and weights are ignored, and the output goes through `RelayPolicy` (BTreeSet dedup).

## Non-blockers worth fixing or documenting
1. **CNAME-aliased SRV owners never succeed in Hickory 0.26.3.** At `caching_client.rs:336-375` (upstream FIXME), the fold sets the search name to the last SRV *target*. So `owner CNAME alias; alias SRV … relay.example.` is not treated as found. Hickory then sends a follow-up **SRV query for `relay.example.`** and ends with NoRecords, which becomes `srv_resolution_failed`. The chain-acceptance unit test only covers a path the real resolver never produces, and there is one extra library-issued query for a name taken from the response. Document this in the phase doc and add a loopback test that pins the fail-closed result.
2. **A query can go out just after the deadline.** `tokio::time::timeout_at` polls the inner future before it checks the deadline, so a later owner can still send one packet if the deadline passes between lookups. Fix: add `if Instant::now() >= deadline` before each owner.
3. **Cancelling `resolve()` detaches the setup thread.** If the caller drops the future, the thread keeps running until the config read finishes plus up to 5s, though its runtime is still destroyed. Document this, or make the entry point synchronous. Also, `thread.join()` inside the async fn blocks, but only briefly.
4. **Hickory's own timeout maps to `srv_resolution_failed`, not `srv_timeout`.** This is acceptable, but it should be documented.
5. **`ServerOrderingStrategy::UserProvidedOrder` isn't in the design's option list.** It's consistent with "configured order"; add it to the design so the two match.
6. **Test gaps:** the fixtures are UDP-only, so truncation-to-TCP isn't exercised. There's no test of the `resolve()` wrapper (thread and oneshot) or of the 4096-byte cap. You already noted there's no cross-platform or real-DNS evidence.
7. **Optional:** passing `Name::from_ascii(&owner)?` instead of a `String` would avoid the UTF-8 name conversion path. The owner is already ASCII-validated.

This is a component review, not product or phase acceptance.
