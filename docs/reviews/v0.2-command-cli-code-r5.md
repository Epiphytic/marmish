### The fix: `wait_loop` lines 862–872
- **What changed:** while `progress.authenticated` is false, each pass of the loop only runs `recover`, which lists unconsumed answers and applies them, then sleeps for up to 100 ms (capped at the deadline) and loops. It never reaches `fresh_id`, `cursors` or `CommandPoll`.
- **Why the race is closed:** a Submit-path wait now can't send a Poll before the Submit answer has been consumed with `status.authority_valid` set. So the server can never freeze a NotFound for this invocation.
- **No cached acceptance:**
  - `authenticated` only comes from `!pre_accept` (line 799) or from `applied.accepted` (lines 767 and 912).
  - `applied.accepted` is only true when an answer with Ok status and `authority_valid` was consumed (lines 586–606).
  - Refusals always set `accepted: false` (lines 540–546). Error answers can't flip it, and nothing is cached between runs.
- **Standalone Wait and Output are unchanged:** `wait()` still passes `pre_accept = false` (line 935), so `authenticated` starts true and the new guard is skipped.
- **Detach:** in `recover`, `detach && applied.accepted` returns 0 straight away. Without detach, `recover` returns `(None, None)` after an accepted Submit. The same loop pass then goes past the guard and creates the first Poll, so nothing stalls.
- **Deadline and interrupts:** the deadline is unchanged.
  - The top-of-loop check still returns Timeout, which becomes 255 `remote_pending` with the handle printed.
  - Ctrl-C is still handled by the `select!` in `wait_deadline`.
  - No new authority or retry budget was added.
- **Busy or quota refusal of the Submit:** a retryable refusal keeps `authenticated` false, so the CLI waits until the deadline and exits 255 `remote_pending`. Before the fix, the Poll path would also have ended in NotFound retries and a timeout, so this is no worse.

### The regression test: `submit_wait_does_not_poll_before_authenticated_admission` (line 1529)
- **Real IPC:** the test peer accepts four `CommandUnconsumed` calls in a row, with an assertion on each. The first three get empty replies; the fourth returns the Submit entry.
- **It catches the old bug:** any Poll sent before acceptance would land on one of those accepts and fail the `matches!` assertion, so this test would have failed on the old code.
- **Order after acceptance:** it then asserts `CommandResponse` with the real Submit answer, followed by `CommandConsume { expected_cursors: None }`. `wait_inner(.., detach = true, pre_accept = true)` returns 0.
- **Timing:** three rounds take about 300 ms against a 3 s deadline, so it shouldn't be flaky.

### Non-blocking notes
- **N-c (liveness, rare):** if the local IPC reply to the Submit-answer consume is lost after the store has committed it, the answer is no longer listed as unconsumed. `authenticated` then never becomes true, and the wait ends at the deadline with 255 `remote_pending` and the handle. That is honest and recoverable, because a standalone `marmish wait` starts authenticated. A possible fix later: pass the Submit `request_id` into the wait and, while unauthenticated, re-read that one answer with `CommandResponse` instead of relying only on the unconsumed list. It isn't required now.
- **N-d (coverage):** no test covers the non-detach Submit path moving on to the first Poll after acceptance. The code path is straightforward (it falls through in the same pass), but the test only exercises detach.
- **N-e (dead branch):** `recover`'s pre-authentication NotFound tolerance for Poll (lines 774–777) can no longer be reached from the Submit path, because no Polls are sent before acceptance. It's harmless, so I'd leave it.
