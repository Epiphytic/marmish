## B1 (reconcile sweep): fixed
`command_runtime.rs:294-329`
- **What invalidates:** only a `group_id` mismatch, `EpochInvalidated` or `Failed`.
- **What is deferred:** `Created`, `Retryable`, `ConvergenceDeferred` and `PeelDeferred` all hit `return Ok(())`, which is everything in the pinned `MessageState` enum (`traits/src/message.rs:1082-1107`) other than `Sent`/`Processed`. `NotFound` returns the same way. A deferred binding never reaches the pending-event delete, the incoming ACK or the outgoing evidence push, so there is no ACK and no invalidation.
- **Fairness:** the cursor still advances regardless of outcome. A per-binding error only produces the `binding_deferred` diagnostic.
- **Terminal path:** the sweep is retained as the durable recovery path. A terminally invalid outgoing binding is still ACKed upstream after it is invalidated. That is correct cleanup and not a false ACK, because the publication state stays `invalidated` and the acked marker only means the upstream ACK completed.

## B2 (unknown queued refusal): fixed

## B3 (capacity fallback and gate): fixed and documented
- **Pin facts confirmed:** pending events only accept `MessageReceived`/`GroupJoined` (`traits/src/storage.rs:390-398`). The `maintain_journal` gate is now documented as defensive and normally empty at `8abc51b` (`mdk_adapter.rs:1084-1087`), with the terminal-state sweep named as the real backstop.
- **When the fallback runs:** the store raises `command_invalidation_capacity` only when there is no outgoing source yet and a proof was supplied (`command_store.rs:2722-2742`). So the fallback only ever runs against a proved publication. Proofs come from the same effect set's `Published` entries or from owned fanouts.
- **Why it can't abort the effect set:** the fallback's `Failed { key }` fails only on an unknown publication, which the ownership check in the proof rules out. `invalidate_publication` is idempotent and skips `expired`. So the `?` on that line cannot abort the effect set.
- **Skipping the matching `Published`:** invalidations, `Failed` and refusals are sorted ahead of `Published`/`Queued`, so the `deferred` set skips the matching `Published` in the same pass.
- **Later replays of that `Published`:** `record_published` won't overwrite an `invalidated` state (line 2686). The new source row then gets `invalidated=1` from the B1 sweep once the row reaches `EpochInvalidated`.

## Non-blocking notes
1. **No runtime-level regression tests for B1/B2/B3.** I found tests for the store-level codes but none that drive the runtime paths. Before phase acceptance I'd add offline tests for:
   - a transient or `NotFound` row being left alone with no ACK;
   - an unknown queued refusal followed by a later update in the same effect set, which still applies;
   - the capacity fallback marking the publication failed and skipping the matching `Published`.
2. **`Failed` is not strictly terminal upstream.** `reopen_rows_refused_by_the_removed_copy` (`openmls_projection.rs:844-876`, called from `group_lifecycle.rs:2194` on a removed-copy re-join) can move `Failed` rows back to `Retryable` or release them for replay. It only touches raw-transport rows that were refused while removed. A bound command source was already processed, so it shouldn't be in that set, and removal is already a terminal revocation for command rooms. So treating `Failed` as terminal is acceptable, but a comment at line 300 saying why would help.
3. **A permanently missing source stays deferred forever.** If a released row is never redelivered, its binding and its pending event are retried on every sweep with no finite outcome. This is bounded by paging and the pending-event cap, so it belongs to retention design rather than this review.
4. **Incoming bindings re-run `Invalidated` on every sweep.** The store reports `0 AS invalidated` for incoming rows, so the `!binding.invalidated` guard never stops them. It's idempotent and cheap; filtering it out is optional.
5. **Still open from r1, still non-blocking:** one failing ACK stalls its whole page of 64, and nothing yet confirms that Init's stop succeeds on an account that was never activated (that needs one offline test).

None of these block approval of this limited scope.
