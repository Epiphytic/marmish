## Blocking issues

**B1. The design requires a command that doesn't exist (design line 95–96).**
The design says to run `marmish --doctor` and require valid JSON. The native CLI has no doctor flag: the parser at `crates/marmish-native/src/cli.rs:35-80` has no such option, and searching `crates/` for "doctor" finds nothing. `--doctor` comes from the old Python installer. Passing it fails argument parsing with exit 255 and the message `invalid_arguments`, so every cell would fail. Adding the flag would change the product, which the design rules out.
- **Fix:** drop the doctor step, or replace it with an existing check. Release-info on all three binaries plus the repeated `setup --no-grants` already covers installed-binary resolution.

**B2. The check that the candidate run built the supplied source can't work as written (line 28).**
The design says to require the candidate run "has the exact source HEAD". `v02-release.yml` is started manually from master and builds `inputs.source_commit` (lines 24, 44 and 221). For a manual run, GitHub's run endpoints report the master commit at the time of dispatch as the run's commit. GitHub's REST API doesn't return the dispatch inputs. So comparing the run's commit to the candidate source either:
- fails whenever the two differ, or
- is quietly loosened during implementation.

The cells' release-info commit check does bind the binaries to the source later, but the resolve job's stated provenance check is undefined.
- **Fix:** pick one rule and write it down. Either require that the run's commit equals the candidate source (so releases must be dispatched with source equal to master tip), or have the resolve job download the three bounded `v02-candidate-<target>-<run>-<attempt>` manifests. It would then check each manifest's digest against the script pins and its `commit` and `version` lines against the inputs.
- Also require that the run was a manual dispatch from master.

**B3. Nothing stops unreviewed changes between the candidate and the bootstrap commit, or in the code that does the checking (lines 16–26).**
The design only requires that candidate → bootstrap → workflow commit are ancestors of each other. That allows the bootstrap commit, or anything after it, to change other files, including:
- `tools/marmish_native_https_check.py`
- `tools/marmish_native_quickstart_check.py`
- `.github/workflows/v02-installer-https.yml`

The supervisor that actually runs is checked out at the master workflow commit, not the candidate commit. So "lands before the final candidate build" is never enforced. The amendment's step 3 says the bootstrap commit adds only the generated `scripts/install.sh`.
- **Fix:**
  - Require that the files changed from candidate to bootstrap are exactly `scripts/install.sh`.
  - Require that nothing from bootstrap to the workflow commit changes `scripts/install.sh` or the three files above. Requiring the workflow commit to equal the bootstrap commit also works.
  - Use a full-history checkout so these comparisons can run.

**B4. The plan to reuse `interactive` unchanged conflicts with the required descendant check (lines 12, 81–82).**
The design reuses the quickstart module's `interactive` and also requires failing "if any owned descendant survives natural leader exit". `interactive` (`marmish_native_quickstart_check.py:29-91`) can't support that:
- it keeps the child PID to itself and never returns it;
- after a normal exit it only reaps the leader and closes the terminal;
- it signals the process group only on timeout.

A wrapper can't probe a group it can't identify.
- **Fix, either way:**
  - Change `interactive` (a reviewed change that also affects the release workflow's quickstart gate, so list that file) so that after reaping it checks the process group with signal 0. If the group still exists, kill it and fail.
  - Or write a new terminal runner inside the HTTPS checker.
- In both cases, run every non-terminal child through the keychain tool's `execute`/`stop` pattern, not `subprocess.run` (the quickstart tool's current approach). Each timeout should be the smaller of the step limit and the time left in the 1320 s budget.

## Small notes (not blocking)

1. **`--version` output.** The CLI takes its name from the crate, so `marmish --version` prints `marmish-native 0.2.0`. It also returns before installed-layout validation, so it proves nothing about the installation. State the exact expected text and don't count it as installed evidence. An rc release would also need `Cargo.toml` set to the rc version, because `release-info` reports `CARGO_PKG_VERSION`.
2. **Artifact retention.** Candidate artifacts are kept for 14 days. Installed checks, publication, the bootstrap commit, Iris sync and HTTPS all have to finish inside that window. Expiry fails safely, but with Iris currently stopped it is a real schedule risk. Note it, or allow the published manifests as a fallback source for the pins.
3. **Mirror ordering.** Before pushing the bootstrap to GitHub master, confirm Iris is serving. Otherwise the GitHub raw URL serves v0.2 while Iris can't, and the amendment's step 5 rollback window has no end. Record the rollback as a separate action triggered by a red rollup.
4. **GitHub raw caching.** raw.githubusercontent.com can serve stale content for about 5 minutes. Wait at least 5 minutes after the push before dispatching, and don't retry failed downloads.
5. **Artifact download hosts.** Name the exact host allowlist for the redirect. Set permissions only on the resolve job (`actions: read`, `contents: read`). Use `persist-credentials: false` in the cell checkouts.
6. **Script size cap.** Enforce the 64 KiB limit in the supervisor itself, not only through curl's `--max-filesize`. Pass both `--proto =https` and `--proto-redir =https` explicitly.
7. **Target in reports.** Take the reported target from `uname` (as the keychain tool does at lines 581–583), and have the rollup check it against the matrix entry.
8. **Leftover services.** Setup returns before the service is ever launched, and that launch path (`cli.rs:499`, `spawn_service`) starts each service in its own session, so a process-group check wouldn't catch one. State what proves "no account/worker remains", for example no socket or lock in the owned state directory.
9. **Time budget.** 1100 s for the install (five 180 s asset fetches = 900 s) plus 120 s reserve leaves about 100 s inside 1320 s for the two script downloads (up to 120 s) and the post-install checks. That is finite and fails red rather than green. Decide whether the two downloads count against the supervisor budget or the remaining job time.

## Requirements checked and found sound

- **Attempt binding:** the run endpoint is per attempt, artifact names carry `run_attempt`, and expiry plus exact `install.sh` contents are checked.
- **Template and bootstrap bytes:** substituting the four values into the candidate source's `scripts/install-native.sh` matches what `native_release.rs:282-307` does. Both the bootstrap commit's bytes and the explicit SHA are required.
- **Real HTTPS:** with no `--asset-dir`, the script downloads `https://github.com/Epiphytic/marmish/releases/download/v$version/...` itself (`install-native.sh:88`), and the native installer verifies the manifest's digest pin.
- **No Python at runtime:** `UTILITIES` contains no interpreter. On macOS, `shasum` is a Perl script with an absolute shebang, which works with the restricted PATH.
- **All three platforms:** the target mapping matches the installer. On macOS the installer checks `sysctl.proc_translated`.
- **Honest rollup:** exactly six cells, with missing, skipped, extra or foreign reports treated as failures. Iris is kept as an honest blocker.

`★ Insight ─────────────────────────────────────`
- With a manually dispatched GitHub workflow, the commit the run reports and the commit it builds can differ. That's why B2 matters: provenance has to come from build outputs (manifests, release-info) or a strict "source equals master tip" rule.
- The terminal library starts the child as the leader of a new session. Once the leader exits and is reaped, the process-group ID is the only handle left on its descendants, so any runner that needs to detect leftovers must keep that ID.
