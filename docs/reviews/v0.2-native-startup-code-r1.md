## Contract checks (`crates/marmish-native/src/mdk_adapter.rs`)
- **Deadline and cancellation (`connect_startup_relay`, about L172):**
  - It keeps three turns, each with `turn_end = min(deadline, turn start + 15 s)`, computed once per turn.
  - Each dial gets `turn_end − now` as the SDK's own timeout, and waits use `wait_for_connection`'s own timeout.
  - Nothing outer can cancel a dial, and the original deadline is never reset.
  - At or past the deadline the result is `Timeout`; three turns without a connection give `Transport("relay_connect")`.
- **Pending, `State` errors and no-op success (`wait_startup_turn`, about L145):**
  - Both an `Ok` and an `Err` from the SDK lead to the same status wait.
  - It loops while the status is `Initialized`, `Pending`, `Connecting` or `Disconnected`, and leaves the turn early on `Terminated` or `Sleeping`.
  - `Banned` and `Shutdown` refuse immediately, before any dial.
  - A wait that returns early sleeps 50 ms within the turn, so there's no busy loop.
- **`Disconnected` can't get stuck:** I checked the SDK `relay/inner.rs:913-940`. With `reconnect(false)`, a failed task passes through `Disconnected` briefly and then sets `Terminated`, so the wait wakes up and the next turn really dials.
- **Publication only after Connected (activation, about L1052):**
  - `client.relay(url)` returns `Result<Option<Relay>>`, and both the error and the missing-relay case map to `relay_connect`.
  - Each endpoint must pass `connect_startup_relay` before `republish_key_package` or `activate_transport` runs.
  - `Relay::try_connect().timeout()` does the same thing the pool's `try_connect_relay` did.
- **Finite labels:** the `RelayStatus` match is exhaustive, with no wildcard. The `ErrorKind` match lists all 14 variants and adds a `_ => "other"` arm in case the enum is non-exhaustive. Nothing formats an SDK error.
- **Route, TLS and recovery unchanged:**

## Non-blocking notes
1. **Endpoints are checked one at a time.** An earlier endpoint isn't rechecked as `Connected` after later ones connect, just before publication. That matches the approved wording, and hosted runs use one relay. A final all-endpoints check would make the multi-relay case stronger.
2. **Debug output volume.** `relay_startup_status` is emitted on every check, including the 50 ms re-polls after an early wait return. That can mean a few hundred debug lines per turn; it's bounded but noisy.
3. **No direct ordering test.** The rule "no publication before Connected" is enforced by the order of calls in `activate`. The scripted tests prove the helper only returns `Ok` after seeing `Connected`, but no test checks the order inside `activate` itself.
4. **Shared stderr.** Debug events carry no owner role, and both owners write to one stderr. Activation runs A then B in sequence, so the events stay attributable.
