# Installed Actions supervisor code review r1

Reviewer: Claude Opus 5.5, `--permission-mode auto`.
Session: `a87c21f4-6fab-48c2-b57d-652902db495d`.
Scope: tools/v02-actions, actual integrated code.

**Verdict: CHANGES_REQUIRED**

The transport security core is sound: ZIP handling, redirect and credential scope, immutable staging, the child environment, and artifact-name binding. But the supervisor does not meet the approved design on three points: it doesn't react promptly to cancellation, it doesn't publish records as soon as they appear, and it retries malformed responses that should fail immediately. There are also two cheap fixes: a race that can falsely fail a successful run, and the token is never wired in.

- `npm ci --dry-run --offline`: the lockfile matches `package.json`. It has 254 entries, all from registry.npmjs.org, all with integrity hashes. Installed versions are exactly `@actions/artifact` 6.3.1 and `yauzl` 3.4.0. I couldn't check offline that these are the latest releases.

## Blockers

**B1. Cancellation isn't acted on promptly** (`supervise.mjs:59,110,146-148`; confirmed)
- Installing SIGINT/SIGTERM handlers stops Node exiting on those signals. But the cancel flag is only checked at the top of the loop.
- Before that check the supervisor can be sleeping for 30s, or up to 300s under a Retry-After. It can also be waiting on several list/download requests of up to 30s each, or an upload of up to 35s.
- When a job is cancelled, the runner sends SIGINT, then SIGTERM about 7.5s later, then kills it about 2.5s after that. So the driver would never get its SIGTERM, which the design requires ("On timeout, SIGINT or SIGTERM, request SIGTERM once of the owned driver").
- In the probe, the driver was only signalled after the full delay finished.
- Fix: use an AbortController. Have the signal handler call `owner.terminate()` straight away, make `delay()` wake on abort or child exit, pass the signal into `fetch`, and stop any running upload worker.

**B2. Publishing records is held up by download backoff** (`supervise.mjs:61-110`)
- The driver's output files are only scanned once per poll cycle, after the downloads, and the cycle can stretch to a 300s Retry-After.
- A 403 or 429 from the download API can therefore delay publishing `client-result.json` by up to 5 minutes, even though uploads use a separate service. That breaks "publishes … as each appears" and risks peers missing their deadlines.
- Noticing that the driver has exited is delayed the same way.
- Fix: scan the local files on a short timer (about 1–2s; it costs no API calls), keep the 30s API poll separate, and wake up when the child exits.

**B3. Malformed responses are retried instead of failing** (`supervise.mjs:107`; confirmed)
- Every `TypeError` is treated as a temporary network failure.
- In the probe, a Location header of `not a url` gave `TypeError: Invalid URL`, and a 200 response with no body gave a `TypeError` from `getReader`. Both were retried until the deadline and counted against the API budget.
- Real programming errors would be hidden the same way. The design says malformed artifacts fail immediately.
- Fix: wrap only the `fetcher()` call and mark network failures as retryable explicitly.

**B4. A successful run can be reported as failed** (`supervise.mjs:61-87`)
- The supervisor checks whether the driver has exited *after* scanning the output files.
- If the driver writes `server-result.json` and exits during that scan, after the file was checked, the run fails with `terminal_records_missing`. It's a narrow window, but the failure is wrong.
- Fix: record whether the driver had exited before the scan, and decide success from that.

**B5. The GitHub token is never wired in** (`action.yml`, `supervise.mjs:150`)
- A JavaScript action doesn't get `GITHUB_TOKEN` in its environment automatically, and the action has no input for it.
- Unless a workflow happens to set the env var, every API request goes out as `Bearer undefined`, fails, and turns the job red.
- Fix: add a `token` input defaulting to `${{ github.token }}`, refuse to start if it's empty, and document that the job needs the `actions: read` permission.

## Should fix (not blocking)
- **Upload worker result** (`upload-client.mjs:205`, plausible): the worker's 'exit' event isn't guaranteed to arrive after its last IPC 'message'. If it arrives first, a successful upload counts as failed. Finish on 'close' instead.
- **Temporary files in the inbox** (`transport.mjs:66`): `*.pid.tmp` files briefly appear in the inbox and identities directories, which the design says hold exactly the expected records. Confirm the Rust driver only opens exact names, or stage the temp files in a private sibling directory on the same filesystem.
- **API budget file** (`supervise.mjs:151`): it's written without an atomic rename and lives in the driver-writable workspace. It's only shared between exchange and run if the workflow passes the same `workspace` to both. A corrupted file fails safely, but use an atomic write and document the shared-workspace requirement.
- **Any 403 is retried**, so a permission error burns through the budget until the deadline. Retrying 5xx goes beyond the spec, which is fine.
- **Wasted list requests:** run mode keeps listing every cycle after all six records have arrived (still within budget). Exchange mode notices it's finished one cycle (30s) late.
- **Responses not drained:** bodies of 3xx and retried responses aren't consumed or cancelled.
- **Clock skew:** `created_at*1000 <= now` rejects any skew between runners; allow a few seconds. Input paths aren't checked to be absolute. A deleted published record goes unnoticed because ENOENT is skipped.

## Tests that are missing
- Retry-After, 403 and 429 handling, and how retries count against the budget.
- Oversized `content-length`, oversized streamed body and oversized ZIP. The design lists "oversized" explicitly.
- Any test of the upload worker (`BoundedArtifactClient`): timeout, the 64 KiB output cap, a bad IPC message, the TERM/KILL sequence.
- The force path after the cleanup reserve. The design lists "timeout ownership"; the existing test only covers an early, pre-set cancellation.
- Cancellation arriving during a delay or an in-flight request (B1), malformed-response handling (B3), and the exit race (B4).
- A successful exchange run end to end.

## npm audit (7 moderate, 0 high, 0 critical)
- All seven come through archiver → archiver-utils/readdir-glob/zip-stream → glob/minimatch.
- npm's suggested fix is a major *downgrade* to `@actions/artifact` 2.1.4, which predates the current artifact service. Don't take it.
- None of them are reachable here. The SDK's `zip.js` only calls `zip.file(sourcePath)` on the explicit file list. There's no glob or directory walk, and no patterns from untrusted input, so the minimatch DoS and the glob AbortSignal issue don't apply. The upload runs in a bounded child process.
- Accept with that reasoning recorded, and recheck when upstream drops archiver 5.

## Confirmed correct
- **Child environment:** the driver gets only a fixed PATH plus HOME, TMPDIR and LANG. The upload worker additionally gets only the four variables the SDK actually reads (`ACTIONS_RUNTIME_TOKEN`, `ACTIONS_RESULTS_URL`, `GITHUB_RETENTION_DAYS`, `GITHUB_WORKSPACE`).
- **Token scope:** the API token only ever goes to `api.github.com`. The blob fetch sends no headers and follows no redirects. The redirect must be HTTPS to an allowed host, with no credentials or port in the URL.
- **ZIP reading:** in memory only, exactly one regular file with the expected name, encrypted entries rejected, sizes checked before and during streaming, SHA-256 checked against the API digest.
- **Immutable records:** uploads come from a frozen copy in a private staging directory, and any change to a published record is a hard failure. Inbox writes use exclusive temp files plus a hard link, so an existing record is never replaced.
- **Driver ownership:** exactly one driver child, spawned with exactly the argv in the design. It gets SIGTERM once and its real exit is awaited. There's an absolute cleanup deadline of expiry + 600s, then SIGKILL, then a 5s observation window.
- **Deadlines:** the 900s job-deadline check, the 15-minute exchange barrier, 30s per network request, and the deadline is never extended.
- **Exit status:** success requires the driver to exit 0 *and* both terminal records to be uploaded. Upload failures are red and never retried under the same name. Failure output contains nothing sensitive.
- **List bounds:** 2 MiB and 100 entries, and a larger result is rejected rather than silently cut off.
- **`.gitignore`:** adding `node_modules/` and `.npmrc` is appropriate.
- **Scope:** the tooling is CI-only and nothing in the product or installer imports it.

The hosted check that records really exchange mid-run on all three platforms is still outstanding, as the design says. These offline tests can't establish it.
