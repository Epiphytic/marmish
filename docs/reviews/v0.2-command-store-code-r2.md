## Round 1 findings, rechecked

**B1, revoked client slots never retired: RESOLVED.**
- `command_maintain` now reads the slot's `authority_valid` column. At `command_store.rs:~2418` it skips a slot only when `client && authority_valid && (!projected || !consumed)`. A revoked slot therefore no longer has to be projected or consumed before it can retire.
- Everything else that blocks retirement still applies to revoked slots:
  - unacked incoming sources
  - publications that are protected, or not yet in published, invalidated or expired state
  - outgoing bindings with `acked=0 OR quarantined=1` (~2449)
  - protected queued intents
- Both revocation paths set the slot column. `revoke_record` does it at ~2769–2790 and `revoke_group_in` at ~2792–2806.
- The regression test at `:5237` covers the slot both before and after projection. It also shows that:
  - an outgoing ACK alone does not retire a projected slot; the incoming source ACK is still required (`:5262–5267`);
  - the protected invalidation group holds the slot (`:5269–5272`);
  - retirement removes both slots and the payload (`:5275–5282`).
- Native ACK requirements are not weakened.

**Changed Submit with a new request id: RESOLVED. The original record stays immutable.**
- The service returns `Refused(InvocationConflict, detail: None)` first, before any other check (`command_service.rs:123–193`).
- The store accepts a mismatched digest only when all three hold (`command_store.rs:690–795`):
  - the record already exists;
  - the decision is exactly that refusal;
  - the response result is `Err` of the same error (769–779).
- In this path the store never calls `insert_invocation` or `save_record`, so the original digest, submit and facts are untouched. Quota is still charged through `insert_slot`.
- A duplicate reattaches to the frozen response. Supplying a second response for an existing slot errors with `command_duplicate_response`.
- The store test at `:5286` checks that:
  - the facts, digest and submit are byte-identical afterwards;
  - the duplicate reattaches with identical wire bytes;
  - a `CommandDenied` refusal cannot be used to get around the digest check (`:5329–5337`).
- The service test `changed_submit_new_request_has_durable_conflict_response` (`command_service.rs:1038`) covers the same flow from the caller side.
- The same request id with changed stdin still errors atomically (`:977`). `command_submit_client` (796–853) is unchanged.

**A transient client Err set a permanent refusal: RESOLVED.**
- A refusal is now recorded only when `response.op == Op::Submit` (`command_store.rs:925–929`).
- The test at `:5340` confirms that a `RecoveryUncertain` Status error leaves the record active with no refusal.

**A third native binding aborted the whole batch: RESOLVED.**
- `record_published` (`:2632–2689`) now handles n ≥ 2 by:
  - quarantining both retained originals;
  - marking the publication uncertain;
  - returning `Ok(false)` without inserting.
- The mirror stays capped at 2 bindings.
- The final filter in `command_apply_native` (`:2184–2192`) drops bindings that were quarantined later in the same batch, so they are never ACKed.
- Outgoing ACKs require `quarantined=0 AND evidence IS NOT NULL` (`:2328–2353`).
- The test at `:5369` covers this, including that unrelated publication `b` still publishes and ACKs, and that `a` stays owned after the WEEK boundary.

**No 7-day payload retention cap: RESOLVED.** `command_configure` (`:1604–1630`) rejects a retention of 0 or more than WEEK. The test is at `:5426`.

**Incoming ACKs had no changed-row check: RESOLVED.** If any incoming source row is unchanged, the whole transaction fails with `command_source_unknown`. The test at `:5426–5455` shows that the valid source in the same call is not ACKed either.

**Quarantine retains capacity: still true, by design.** This is now nonblocker N4 below.

The approved retention r4 and async-response contracts are preserved for everything this scope covers: the immutable original, frozen replay, native ACK gating, the WEEK replay floor, and the slot and tombstone bounds.

## Nonblockers

- **N1 – `command_store.rs:905` and `:931`.** An `Ok` status response with `authority_valid=false` only clears `record.authority_valid` in the facts, through `save_record`. It does not update the slot columns.
  - Effect: `client_record` (946–956) then refuses reads and consume, but maintain (~2418) still treats those slots as authorized and waiting for consumption. They never retire.
  - This needs an authenticated server that violates the protocol, so it is not reachable with an honest server.
  - Fix: apply the same slot-column updates as `revoke_record`, or reject such responses.
- **N2 – `:737–757`.** The store accepts `Refused(InvocationConflict)` when no record exists, and inserts a new invocation that carries that refusal. The service never does this. Suggest requiring an existing record for `InvocationConflict` so the store enforces the rule itself.
- **N3 – `:2686`.** The `uncertain` state set by conflict quarantine is not sticky. A later fresh binding while n < 2 can flip the publication back to `published`. Retirement and ACKs stay blocked by the quarantined row (~2449, ACK filter), so this only affects diagnostics. Suggest excluding `uncertain` in that UPDATE.
- **N4 – design-consistent.** A quarantined or third-binding publication is kept indefinitely and its native replay is never ACKed. It holds slot capacity until an operator recovers it, so it needs operator recovery and diagnostics later on.
- **N5 – carried over.** The retention design doc header still says DRAFT, although the contract was approved at r4.
- **Test gaps:**
  - nothing exercises N1 or N2;
  - the `:5237` regression covers group revocation only; `revoke_record` was verified by reading the source.

`★ Insight ─────────────────────────────────────`
- The B1 fix works because revocation is stored on each slot row, not only in the invocation's facts. N1 is the one path where only the facts change, so reads and retirement disagree about whether the slot is still authorized.
- The conflict fix splits what is fixed from what is charged. The invocation (digest, submit, facts) is never touched, while the new request id still gets its own slot, quota charge and frozen response. That keeps replay deterministic without letting a changed request rewrite history.
