## Blockers

**LC-1: The A bootstrap can't be rendered in a single-target job.**
- Draft L68–72 requires initial A to go through the real thin bootstrap using the existing pinned-render helper. Draft L92–95 runs one independent job per target.
- `native_release.rs:282-310` (`render`) needs manifests and verified assets for all three targets before it writes any bootstrap. A per-target job only has its own A build.
- **Minimal fix (recommended):** install A with the existing `marmish install --source-dir/--manifest/--manifest-sha256`, using a manifest hash computed by the harness from its own A build. Keep the thin-bootstrap requirement for the B upgrade only, using the candidate's real rendered script.
- **Alternative:** a reviewed fan-in (three A build jobs → one render job → lifecycle jobs) with digest-bound artifacts and a new clock budget.

**LC-2: The product preflight will probably create database sidecars, so the negative check is likely to fail.**
- Draft L156–161 requires no added or changed `-wal`/`-shm` files after C's startup.
- The journal uses WAL mode (`journal.rs:145`). `native_preflight.rs:28-33` opens the MDK and journal databases with `SQLITE_OPEN_READ_ONLY` but without `readonly_shm` or `immutable`.
- In the bundled SQLCipher, the shared-memory file is opened `O_RDWR|O_CREAT` unless `readonly_shm` is set, and the WAL file is opened with `READWRITE|CREATE`. After a clean B stop has removed the sidecars, C's preflight would likely create them.
- The existing preflight test (`native_preflight.rs:136-186`) uses a rollback-journal database, so it doesn't cover this.
- The draft also says it doesn't change production behaviour, so as written it can't fix this.
- **Fix:** make an offline test a pre-implementation dependency. Close a database created by `Journal::open` cleanly, run the preflight, and assert the directory entry set and bytes are unchanged. Then do one of these:
  - name a separately reviewed preflight fix as a dependency, or
  - restate the criterion to match Phase3's "byte-identical databases" (main database bytes and any existing sidecars unchanged, newly created empty sidecars reported).

**LC-3: The harness and workflow provenance aren't bound.**
- Draft L85–87, L92–95 and L199–203 add a new lifecycle workflow and a CI build supervisor.
- The candidate's `harness_sha256` (`v02-release.yml:152-153`) covers only `crates/marmish-native`, `Cargo.lock`, `tools/v02-actions` and `v02-installed.yml`.
- **Fix — the draft must state that:**
  - the lifecycle checker is the candidate's packaged `marmish-installed-check` (bound by `tooling.json`);
  - B must be cut after this code lands;
  - the workflow, supervisor and patch spec are in the harness digest set, or run from the source commit (`github.sha == source_commit` enforced) with their file hashes recorded;
  - A/C builds use a fresh job-local target directory and never restore from `actions/cache` or sccache. "Reuse a Cargo target cache" (L56) is currently ambiguous.

**LC-4: "Observed F" has no interface.**
- Draft L76–77 asserts that B's declared journal format matches the observed one, while L161 forbids the harness from connecting to SQLite. The journal is SQLCipher-encrypted, and no product command reports `user_version`.
- **Fix:** derive F from B's release-info and manifest. That is sound because `journal.rs:175` always sets `user_version = JOURNAL_FORMAT` on a successful open, so a successful B open proves F. Otherwise, specify a reviewed read-only reader.

**LC-5: The stated clocks conflict with existing hard limits.**
- The draft's provider stage of ≤900s (L193) exceeds the supervisor's inner cap: `marmish_native_keychain_check.py:388` requires `1 ≤ deadline ≤ 540`.
- The supervisor accepts at most 16 staged inputs (`marmish_native_keychain_check.py:374`). The A/B asset sets plus the bootstrap are about 16–17 files.
- The fixture's gate wait has a hard 900s timeout (`installed_fixture.rs:331`), so steps 2–4 must finish within 900s of the fixture starting, or it exits with a timeout instead of exit 7. The draft doesn't mention this.
- **Fix:** state the extended limits explicitly, or fit within the existing ones. Add the 900s fixture window as a binding stage clock, refused at entry if there isn't enough time.

## Confirmed sound (code matches the draft)

- **Packager:** `package`/`probe` reject any binary whose release-info differs from the release tool's own compiled metadata, and take the state formats from compiled constants. C's manifest will honestly say `journal=4`, and no manifest is fabricated.
- **Commit check:** in installed mode, `native_layout::resolve` requires manifest commit = compiled commit, which holds when A, B and C all use B's base commit. The version grammar accepts `0.2.0-rc.N`.
- **Worker recovery:** the engine identifies a worker by `(boot_id, pid, start_ticks)` and reconciles a live worker without checking its executable (`marmish-engine/src/lib.rs` `reconcile_step`), so B can adopt the worker A spawned. A missing Running worker becomes `Lost` and is never relaunched.
- **Startup order** (`daemon.rs:30-104`): lease, config load, provider prepare and relay connector all run before the preflight, which runs before `MdkOwner::open`. A config-format change would fail earlier, at config load, as the draft says.
- **macOS ad-hoc ACL:** the vault sets no explicit keychain access list, so B being denied after A created the items is the expected result. The draft reports that honestly as failed/unqualified.

## Nonblockers

- The provider section says "A/B/C asset triple", but C is never used there; say so.
- Step 4 doesn't say what happens to the A client daemon.
- Define which non-database profile entries may change during C's startup (`owner.lock`, runtime directory).
- State whether A/C license inventories reuse B's verified bytes or are regenerated and compared.
- Short retention and obviously synthetic names for A/C workflow artifacts.
