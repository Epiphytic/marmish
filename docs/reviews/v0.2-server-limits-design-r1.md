Most of the design matches the code. The durable ledger model (reserving credit before engine side effects, the permanent `admitted` counter, frozen refusals, the ordinary-stop semantics and the honest limits on what `max_uptime` bounds) fits the real store, engine and lifecycle contracts. Three points need correcting before implementation.

## Blocking findings

**1. A `QuotaExceeded` refusal is frozen even when the budget is only closed by reservations that may still be released.**
`reserve_credit` (`command_store.rs:1575-1602`) closes admission when `admitted + reserved >= max`. Here "reserved" means active server rows with `engine_known=false` and no refusal. Some of those rows will later get a definite pre-engine refusal: the engine already maps its own quota and denial errors to refusals (`command_engine.rs:573`), and that frees the credit.

Under this design, a new invocation that arrives while the budget is closed only by reservations gets a frozen refusal it can never recover from. Example with N=3: admitted=2, and one uncertain dispatch is holding a credit. A fourth Submit arrives and is refused permanently. The dispatch is then refused, which releases the credit. The profile ends with 2 admissions and a client that was turned away. The concurrent N=3 test the design proposes would hit exactly this case.

This contradicts the design's own "do not latch budget closure prematurely". It also contradicts the amendment's rule that uncertain reservations do not count as confirmed admissions and that a definitive refusal frees the slot. A permanent per-invocation refusal is a latch.

- **Smallest correction:** commit the frozen `QuotaExceeded` only when `admitted >= maximum`, which cannot change without an explicit configuration change. When `admitted < maximum` but `admitted + reserved >= maximum`, keep today's deferred `command_admission_closed` handling (`command_adapter.rs:357-370`): the source stays pending, nothing is ACKed, and the existing bounded pending queue retries it.
- Split `CommandAdmissionBudget.closed` into `exhausted` (permanent) and `reserved_full` (transient).
- Add a test: a reserved credit is released by a definite refusal, and a waiting new Submit is then admitted rather than refused.

**2. The uptime check cannot actually stop admissions that happen inside a single `tick`.**
The design gives `ServiceLifetime` to the daemon owner and checks it at outer-loop turns and select branches. But admission and dispatch run synchronously deep inside `MdkOwner::tick_inner` (`mdk_adapter.rs:2385-2427`):
- inbound frames are projected through `receive_one`/`apply_effects` and then `project_command_message` → `CommandService::project_request`, with up to 64 pending items per tick;
- dispatch is scheduled in `progress_commands` → `schedule_active`, which runs twice per tick.

Dropping the future at an await point cannot prevent admissions that run between two await points after the deadline has passed. So the promise of "check expiry before new dispatch/admission" has no hook in the current design. The design also doesn't say what a Submit arriving after expiry should receive.

- **Smallest correction:**
  - Give `CommandService` a narrow admission gate (an expiry predicate or deadline sample).
  - Check it in `admission_response` before a `New` decision, and in `schedule_active` before any `EngineOperation::Dispatch`.
  - After expiry, a new Submit returns the deferred, retained, un-ACKed path (the same category as #1). It does not get `QuotaExceeded`, because uptime is not the durable budget.
  - Already-Accepted rows that haven't been dispatched keep their reservation and recover on restart.
  - Status, poll, cancel and completion handling continue to work.
  - Add a scripted-clock test where expiry happens partway through a tick that holds several pending Submits.

**3. The macOS clock source doesn't exist in the pinned `libc`.**
The design names `mach_continuous_time` "via existing libc". The locked `libc` 0.2.189 exposes `mach_absolute_time`, which excludes suspend and is therefore the wrong clock, plus `mach_timebase_info`. It has no `mach_continuous_time` binding.

- **Smallest correction:** on macOS, use `libc::clock_gettime(libc::CLOCK_MONOTONIC)`. On Darwin this clock keeps counting while the system sleeps, needs no timebase conversion, and is in the pinned crate. On Linux, keep `CLOCK_BOOTTIME`. If you prefer `mach_continuous_time`, state that it needs an explicit `extern "C"` declaration, and keep the checked timebase conversion.

## Non-blocking findings

1. **Baseline wording:** the design says the current behavior is a "dropped limit error". In fact `command_admission_closed` is already deferred backpressure: the source is retained, not ACKed, and retried. Reword the baseline so the change in behavior is described accurately.
2. **Validation order:** `CommandConfig::load` currently returns already-normalized limits, so CLI overrides have to be applied after parsing but before the cross-field check.
   - Specify something like `load_with(root, overrides)`, or split raw/normalize, with the "max_commands requires max_uptime" check after the merge.
   - Otherwise a file with only `max_commands` plus a `--max-uptime` flag would wrongly fail.
   - The check belongs in config validation, not in `Journal::command_configure`, which never sees uptime. The store tests that build a bare `CommandLimits` (`command_store.rs:4416-4472`) need no change.
3. **N bound in files:** apply the `N <= i64::MAX` bound in `RawLimits::normalize` too. Today the file parser accepts any `NonZeroU64`, and a value above the counter's cap would quietly never close.
4. **Ambiguous cases** where the test table has no defined expected result:
   - config present but no execution grants (no engine) combined with limit flags;
   - `--max-uptime` alone on a client-only role (is uptime a "server limit"?).
5. **CLI:** define the flags as fields of the `Daemon` subcommand, not as global args. Clap will then reject them on init, check and client operations, and `marmishd daemon --help` will list them.
6. **Timer waits:** the nested-select lifetime branches must also re-arm every ≤100ms and sample the boot clock. Tokio's `Instant` and `sleep_until` stop advancing during suspend, so one long `sleep_until` would stretch the deadline after a resume.
7. **Uptime and the startup deadlines:** also clamp `profile.prepare`'s 30s and `activate`'s 150s deadlines to the remaining uptime, not only check afterwards. Otherwise a short test uptime can be overrun by up to 150s before the first check.
8. **Uptime will now always hit the drop path:** the drop-on-select behavior for an in-flight `tick`/`dispatch` (already used for signals) will now run in every timed run. The code review should confirm `tick_inner` can be cancelled at each await without breaking the ACK/commit ordering.
9. **Test claims:** the design correctly separates the local disposable subprocess test from the future installed nine-pair max3/30m acceptance. Keep that separation in evidence, and claim no installed result until those runs exist.
