## The r1 blockers

**B1, profile inode receipt: fixed.**
- **The receipt type** (`installed_cleanup.rs:253-276`): `ProfileReceipt` runs `check_dir`, then holds the directory open with `O_NOFOLLOW|O_DIRECTORY|O_CLOEXEC`, then checks itself right away. `verify` compares the held directory's `(dev, ino)` with `symlink_metadata` of the path and requires the path to be a real directory, not a symlink.
- **Capture before first spawn** (`installed_autoexit.rs:1952-1958`): each client profile gets `require_no_engine` and then `capture` after its setup and configure, and before any `marmishd` spawn. That includes the uptime cohort's `client`, which is never launched.
- **Rechecks:**
  - before each client spawn (`:1999-2004`);
  - after ready and before `verify_no_engine` (`:2009-2023`);
  - before `close_clients` (`:2047-2058`);
  - inside `stop_no_engine`, both before the no-engine proof and after reap and the stop report (`:669`, `:678-679`);
  - after `close_clients` (`:2060-2071`);
  - for every receipt immediately before `remove_private_workspace` (`:2109-2114`).
- **On failure:** `force_all` runs and no deletion is attempted.
- **Negative test:** `profile_receipt_rejects_replaced_directory_and_symlink` covers both a renamed-and-recreated directory and a symlink swapped in.

**B2, maximal 64-entry IPC frame: fixed.** The test `maximal_client_invocation_page_fits_actual_ipc_frame` (`installed_cleanup.rs:691-709`) builds:
- 64 entries;
- a 64-character profile and `u64::MAX` cursor, created and next;
- `noncanonical_executable` as the refusal, which I confirmed is the longest `ErrorCode` (23 characters);
- `unknown_launch` as the state, the longest `State`.

It wraps them in the real `ipc::Response::command`, asserts the result is ≤65536 bytes, and checks that it round-trips. Oversized frames are still rejected rather than truncated (`:126`, `:132`).

## Requested changes, also verified

- **First versus final digest:** `initial_group_digest` comes from the detach-time lookup (`:1050`). It must equal the result of the PID-bound `client_group_submit` before the terminal record is written (`:1219-1224`); a mismatch is a failure.
- **Distinct digests:** the validator requires `group_submit_sha256 != submit_sha256` (`:352`). Rollup case 12 sets the group digest to the handle SHA and the validator rejects it.
- **Explicit nullable fields:** `required_nullable` has no `default`. Tests prove that a missing `engine_present`, `final_seq`, `refusal`, stream `sha256` or `Page.next` fails to decode.
- **Paging in `client_group_submit`:** an empty page that has a `next` is rejected, `next` must equal the last cursor, cursors must strictly increase, and the total is capped at 4096. Matching uses the complete `CommandHandle`; it also requires `authority_valid`, lowercase 64-character hex, and no duplicate match.
- **`OwnedCleanupGuard::final_seq()`:** it's a read-only `u64` copy. It adds no way to create or extend the guard's authority.

## Non-blockers

1. **Stop deadline overrun:** if the 30s/40s stop expires, `cleanup::stop` spends up to 5 seconds outside the deadline on terminate and reap (`installed_cleanup.rs:520-527`). It always returns `Err(Timeout)`, so the run is red and never counts as success. When `cleanup_deadline` is the tighter limit, the outer `timeout_at` can drop the work part-way through terminate. Even then, `force_all` (capped at 10 seconds) and `kill_on_drop` still reap the process, and the result stays red. **Not a blocker.**
2. **Receipt timing:** the receipt is captured after both `marmish setup` CLI runs and after configure, not after the first setup. That's unavoidable because setup creates the directory, and engine absence is checked at capture. Capturing right after the first setup and checking across the `--update` run would be marginally tighter.
3. **Detach-time lookup:** it still goes through the UID-only `local()` (`:1030`) and doesn't validate hex itself. That's safe because the value is compared exactly against the PID-bound, hex-validated final lookup.
4. **Path-based deletion:** a same-UID race between the last `receipt.verify` and the path-based `remove_dir_all` is still possible. That's accepted for this threat model.
5. **Test admission value:** the frame test uses admission `accepted` (8 characters) rather than `dispatching` (11). That's about 192 bytes short of the true worst case, with a margin of more than 20 KB.
6. **Still open from r1:** non-blockers 3 (duplicated readers in autoexit), 5 (`require_new_engine` is used as an alias, now with the receipt in front of it) and 6 (no product test for `engine_present` or `refusal`).
