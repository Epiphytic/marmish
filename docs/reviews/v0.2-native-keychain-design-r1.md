## Claims checked against the code (all accurate)
- **Helper environment:** `identity.rs:726-743` clears the environment and forwards only `HOME`, `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR`. `cli.rs:749` checks the executable layout before running the helper.
- **Files fallback:** `prepare_with` (`identity.rs:205-211`) picks Files only on `unavailable` when the choice is Auto. A keychain profile that already exists never switches to Files.
- **Providers:** Linux connects to the session bus and calls `get_default_collection` (`linux.rs:71-87`). macOS uses `SecKeychain::default()` with explicit keychain queries (`macos.rs:104`, `:146`). The macOS status codes never map to `Unavailable`.
- **List:** the helper's `List` action exists (`helper.rs:234`) and returns only reference and label, so step 2 is possible without any `Load`.
- **Ready shortcut:** `native_setup.rs:322-334` never opens the provider for a ready profile. The design is right to use a fresh `init`.
- **`init` really reloads keys:** `daemon::open` → `prepare` → MDK open → `enable_commands` derives engine material from the SQLCipher root (`command_runtime.rs:67`). It prints the hex public identity (`RuntimeStatus.identity`).
- **Explicit-keychain test proves nothing about the default:** `native_macos.rs` uses `open_keychain_namespaced`, so it cannot establish default-auto behaviour.
- **Installer:** it defaults to `key_storage=auto`, refuses root and passes its environment through to `setup` (`install-native.sh:19,42,148`).

## Required changes (smallest fixes)

1. **The fallback notice doesn't exist (invented support).** Step 5 asks for "the documented notice", but no Files-fallback notice exists in `native_setup.rs`, `identity.rs` or the Phase 3 docs. The only signal is `SetupReport.backend == "file"`.
   - **Fix:** assert `backend=="file"`, `identity_created`, and that the `keys/` directory exists on the fresh profile. Drop "notice", or scope a notice as a separate product change.

2. **Linux re-unlock has no proven headless mechanism.** The existing gnome-keyring test (`native_linux.rs:286`) locks the collection but never unlocks it. D-Bus `Unlock` needs a prompter, which isn't available here.
   - **Fix:** define "lock" and "unlock" as restarting the owned keyring child:
     - Stop and reap the exact `gnome-keyring-daemon --foreground --components=secrets --control-directory <owned>` child.
     - For lock, start a new one with stdin null; for unlock, start one with `--unlock` and the fixture password on stdin.
     - Use the same bus, `HOME` and `XDG_DATA_HOME`.
     - Require the product's probe to return `locked_or_denied` or ok respectively.
   - This reuses only the start pattern the existing test already proves.

3. **The D-Bus process must be an exact child.** The existing harness uses `dbus-run-session`, which hides the daemon from the supervisor. That contradicts "save exact D-Bus/keyring child handles".
   - **Fix:** launch `/usr/bin/dbus-daemon --nofork --config-file <owned bus.conf> --print-address=<fd>` directly. Use the existing config with no activation directories (`native_linux.rs:353`).
   - Before any product run, apply the `validate_isolation` checks to the product environment: a single `unix:path=` address with no `;`, 0700 directories owned by the runner, and `XDG_RUNTIME_DIR` inside the owned tree. This rules out the runner's ambient `/run/user/<uid>/bus`.

4. **On macOS, the supervisor can't signal the product's processes as written.** Processes started through `sudo -u` belong to another uid, so the runner can't `kill(-pgid)` them. sudo may also insert its own PTY (`use_pty`), which breaks the PTY and process-group plan.
   - **Fix:** split the supervisor in two:
     - A privileged outer stage that only creates the account, stages files, runs `launchctl bootout` and deletes the account.
     - A product stage started once as `launchctl asuser <UID> sudo -n -H -u <acct> /usr/bin/env -i HOME=<acct home> PATH=/usr/bin:/bin <python3> -I <staged supervisor>`.
   - The product stage then owns the PTYs, process groups, deadlines, `security` calls and helper `List` calls as the same uid.
   - Every `security` command for the account runs in that same `asuser` context, so unlock state and the default-keychain preference are what the product sees.

5. **Nothing verifies the runner's keychain state is untouched.** macOS sudo can keep the runner's `HOME`, which would write the default-keychain preference into the runner's account. That is exactly the forbidden change.
   - **Fix:** besides forcing `HOME` as in item 4, snapshot the runner's `security default-keychain -d user` and `list-keychains -d user` output before account creation and after cleanup. Compare in place and upload only one boolean `runner_keychain_unchanged`; it must be true to pass.

6. **macOS prerequisites are missing.**
   - **Asset access:** candidate assets, the bootstrap and the supervisor sit in the runner's workspace, which the new account can't read. Copy them into an account-readable staging directory and re-check digests after the copy.
   - **Auto-lock:** a new keychain may auto-lock on a timeout or on sleep partway through the ≤600s run. Add `security set-keychain-settings <owned path>` with no `-l`/`-u` right after creating it.
   - **Reload outcome:** the earlier selected-keychain workflow accepted `locked_or_denied` as a valid restart result, so a successful cross-process reload on macOS has never been shown. In this gate, only `ok` counts after unlock. A denial there must fail as `acl_denied_after_unlock`, not be tolerated.

7. **Linux packages aren't specified.**
   - **Fix:** add a step that installs only missing packages with `dpkg-query` version records, like `release.yml:51-66`. It covers `dbus-daemon`, `gnome-keyring` and `util-linux` on both `ubuntu-24.04` and `ubuntu-24.04-arm`, and requires `/usr/bin/dbus-daemon` and `/usr/bin/gnome-keyring-daemon` to exist.

8. **Underspecified interfaces and predicates.**
   - Name the workflow job (in `v02-release.yml`, `needs:` render, using the same artifacts as the quickstart job) and the supervisor path.
   - Give exact commands:
     - second identity: `marmish --state-dir S -i <name2> --relay wss://relay.invalid/ setup --role both --no-grants`
     - reopen: `marmish --state-dir S -i <name> init`
   - Define "without mutation" as `profile.json` bytes, `config.json` bytes and the absence of `keys/` all unchanged. Creating the profile directory or lease file is allowed.
   - For the macOS missing-default case, point the account's default at a nonexistent path inside the owned home rather than deleting the real keychain. Run it after the step 4 recovery, on a fresh name, so the cleanup predicates stay meaningful.

## Safety notes (acceptable as designed)
- The product needs no override, no environment variable and no new helper operation, and the design says it never sends a raw `Load`.
- Locked runs fail before any manifest is written: the probe runs first (`identity.rs:205`), and `create` checks for a locked keychain on both platforms.
- The upload rules (booleans, categories and counts only) are fine.
- Remaining macOS risk: a Security context that doesn't work headlessly is correctly treated as a finite prerequisite failure, not swapped for weaker evidence.
