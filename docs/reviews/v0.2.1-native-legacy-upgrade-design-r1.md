# Native legacy upgrade design review r1

Reviewer: actual Claude Code, --permission-mode auto.
Session: 50a80d11-2d81-4c77-a5b3-cee8fac689ea
Verdict: CHANGES_REQUIRED.

**CHANGES_REQUIRED**

I read the design against `native_install.rs`, `native_install_fs.rs` and the 347cf799 `install.sh`. The recognition rules are sound. The legacy wrapper template (`launcher_bytes`) is byte-identical in every historical `install.sh` revision (4a78fb3, e62fe8d, f609b6c). Version-gating on `0.1.0-experimental.N`, rebuilding the wrapper bytes without parsing shell, and using the receipt generation as the only commit decision are all correct. The recovery state machine is also well thought out. But it doesn't say how it fits the existing `run`/`recover` code, and that code would destroy or wedge the legacy state.

## Blocking findings

**B1. Existing `run`/`recover` would treat the legacy wrappers as foreign, or delete them. The design must say how it changes them.**
- `run()` calls `validate_links(&receipt, true)` before the transaction. With an empty receipt launcher list, any present launcher returns `unrelated_launcher`. Legacy detection must run before it, or `validate_links` must be made legacy-aware.
- `recover()` first calls `link(path, …, false)` on every existing launcher. An original, unmoved wrapper fails that call, so precommit recovery would wedge instead of leaving it alone.
- The same `recover()` has an unlink branch: `(created_launchers.contains(name) || !previous) && exists(p) → ctx.unlink`. The design adds migrated names to `created_launchers`. After a crash before the move, the original wrapper is at `p` and the name is in `created`, so this branch would delete the user's wrapper. This is the data-loss path.
- Required fix: when `tx.legacy` is set, recovery runs a dedicated legacy-aware pass that replaces both loops for the migrated names. That pass only unlinks an entry after confirming it is the expected native symlink. Add a test: interrupt at `transaction`, before any move, then run Status. The original wrapper must survive byte-for-byte.

**B2. The transaction size cap can make the install unrecoverable.**
- `atomic()` writes with no size cap, but `recover()` reads with `json(&p, 0o600, 8192)`.
- The legacy record holds a root path of up to PATH_MAX, which JSON escaping can double. A long but legal HOME-contained path could produce a durable transaction that recovery then rejects as `install_metadata`. Every later invocation, including Status, would be wedged with the wrappers half-moved.
- Required fix: bound the legacy root, version and target before writing. Make `atomic` enforce its read cap on the transaction. Add a maximum-size round-trip test. Do not raise the 8192 cap.
- Store only legacy root, version, target and names, and recompute the version root (`versions/marmish-V-T`) from them. Do not store a separately derived root that could disagree with the version and target.

**B3. The design contradicts itself about recovery depending on the legacy root and lock.**
- It says "Retain both locks through mutation/recovery" and that recovery must "validate legacy marker binding and old lock".
- If recovery re-reads the legacy marker, a user who deletes or edits the old tree after a crash wedges even `Status`.
- Pick one rule. I recommend that recovery is derived solely from the transaction record plus the fixed expected wrapper bytes recomputed from it. It would never read the legacy marker and never take the legacy lock. Exclusive renames already prevent overwriting, and the old installer fails closed on missing or symlinked launchers.
- The legacy lock and the marker re-read apply only to the initial migration, after the transaction is chosen and before the first move. State this explicitly and test it.

**B4. Native prefix and state need to be disjoint from the legacy root, and the legacy lock must not create files.**
- `validate_options` only forbids the default `~/.local/share/marmish`. A custom legacy root discovered as `bin_dir`'s parent could contain the native prefix. For example, bin `L/bin` with native prefix `L/native` isn't caught by `contained(prefix, bin_dir)`. Require that the legacy root is not contained in the prefix or state dir, and that they are not contained in it, and run `path()` ancestor checks on the legacy root.
- The old installer opens its lock with `O_CREAT`. The Rust side must open it without `O_CREAT`. A missing lock should refuse, not create a file in the "untouched" legacy root. Specify `O_RDWR|O_NOFOLLOW` with no create. The 0600 requirement is also stricter than the old `regular_owned`, which only rejects group/other write bits. Fail-closed is fine, but say so deliberately.

## Smaller items to fix in the doc (not independently blocking)

- Add `#[serde(default, skip_serializing_if = "Option::is_none")]` on the new `legacy` field. That way non-legacy transactions serialize byte-identically and older records still parse. Say that `deny_unknown_fields` means a downgraded binary refuses a legacy transaction, which is acceptable.
- `validate_transaction` needs explicit legacy rules:
  - The legacy names must be a subset of `created_launchers`.
  - The legacy record must appear only with `operation == "install"`, `previous_active == None` and no previous launchers.
  - The legacy name list must be ordered and without duplicates, matching the existing `created_launchers` check.
- Specify the wrapper read: `O_NOFOLLOW`, read at most expected-length+1 bytes, fstat for regular file, nlink 1, uid, and mode exactly 0755. Re-lstat the same dev/ino immediately before each rename. A same-user swap isn't a privilege issue, but it would move a foreign file into the backup name and wedge recovery. This is a hardening step, not a blocker.
- Add tests for:
  - non-UTF8 or non-normal legacy paths;
  - the old lock held by a live process;
  - a legacy lock that is missing;
  - the legacy root overlapping the native prefix;
  - the transaction size bound;
  - recovery with the legacy tree deleted;
  - Select/Status/Uninstall after migration.
- Document that Uninstall after migration removes only the native links. It does not restore the old wrappers, and the backups stay.

## Optional simplification

- Drop the "ordered nonempty subset of names" record. Store a two-valued enum or a pair of booleans. The record is then fixed-size, which also helps B2.
- The default-root and bin-parent discovery can collapse into one rule: candidate root = bin_dir's parent if its last component is `bin`, else `~/.local/share/marmish`. The marker's `launcher_dir == bin_dir` check already makes ambiguity nearly impossible. Keep the refuse-on-two-matches check only if it's cheap.

Re-review is needed after B1–B4 are in the doc. I made no edits and ran no builds or tests.

Disposition: all four blocking findings incorporated into the revised design before implementation; actual r2 requested. No source code changed during r1.
