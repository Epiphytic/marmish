## Nonblocking notes for the implementer
1. **Native error codes must survive in both modes.** `Provider::load` and `probe` currently collapse codes via `status()` into `Error::LockedOrDenied`. For the design's finite categories to hold, including "underlying category" on a failed verification, both Interactive and Verify must use a new internal detailed-error layer at the probe and query level. Verify cannot just call `Vault::load`. The ordinary public `Error` mapping stays untouched, and a regression test should assert that. Cover all of -25308, -25293, -128, -25300 and -25307, plus the probe's locked bit being distinct from `SecKeychainGetStatus` errors.
2. **Signal streams must span both phases.** Create one set of streams and one flag per command, and check the flag between phases before spawning verification. A signal in the gap should not be lost or silently ignored. After a child exits, check the flag and `ExitStatus::signal()` so a Ctrl-C that kills the helper first is classified as interrupted, not `keychain_failed`.
3. **Registering Tokio handlers removes the default termination for those signals.** If kill and wait ever wedge, repeated Ctrl-C will not end the frontend. Consider a bounded join, or a second signal that escalates to `_exit`. Also pick and document exit codes for interrupt and timeout.
4. **Hidden entrypoints should keep the layout check.** Route `_vault-authorize` and `_vault-verify-authorization` through `validate_executable_layout()`, like `_vault-helper` at `cli.rs:756`. Both exchanges should use identical env, stdio and argv construction apart from the helper kind, so verification stays comparable.
5. **A running daemon makes the command fail with `profile_in_use`.** Document that the user must stop it first.
6. **Test the explicit-flag detection in both argument orders.** Cover `--socket x keychain-authorize` and `keychain-authorize --socket x`. Confirm that defaulted `key_storage`, `retention_seconds` and `wait_seconds` do not trigger rejection.
7. **Verification proves access, not identity binding.** The earlier suggestion remains optional: the helper could derive the Nostr public key and the frontend could compare it to the manifest. The narrow "Keychain access verified" wording is honest as written.
