**Verdict: CHANGES_REQUIRED**

I found three blockers. Each needs a small, bounded fix. None of them makes the code unsafe: it fails closed in every path I traced. The blockers are about where the code departs from the approved design or leaves its key safety logic untested.

I reviewed `crates/marmish-native/src/installed_benchmark.rs` at SHA256 `3e06944c…901168f`, read-only. I didn't run Cargo or start any processes. No live acceptance or throughput numbers are claimed.

## Blockers

**B1. A failed run's record disappears from the rollup** (`installed_benchmark.rs:753-793`; callers in root-owned `installed_local.rs::rollup`)
- `validate` only accepts a fully passing record, and `markdown_summary` refuses anything incomplete.
- So when a run fails honestly, its record never reaches the rollup. The role shows up only as `missing_or_invalid`, and the failure category, the four sample slots and the null metrics are all lost.
- That contradicts design lines 236-241: JSON and Markdown must report all 12 slots with unqualified/null metrics, and the rollup must fail.
- Fix:
  - Split `validate` into two functions. `validate_record` checks that the record is genuine: bindings, nonces, slot order, receipts and handles for passed samples, null metrics for non-passed samples, `successful_samples` equal to the passed count, and `failure` set exactly when the run is incomplete.
  - `validate` then becomes `validate_record` plus the completeness checks.
  - Make `markdown_summary` print every slot, writing "unqualified" and "null" where needed, and compute warm min/median/max only when all three warm samples passed.
  - Root then needs a three-line change in `local.rs` to embed a genuine-but-failed record with `complete:false`.
  - Converting `temperature` and `disposition` (lines 51-52) to closed serde enums would make the failed-record schema strict for free.

**B2. Cleanup can use up the time reserved for stopping** (lines 363-403, 686-693)
- Cancel, `prepare` and `remove_installed` all use L+1770, the same deadline as the stops.
- On a failure path, `prepare` keeps polling `draining` until L+1770. Ordinary stop then never gets a chance, and both daemons are force-killed.
- The design gives cleanup 360s and stop 60s.
- The two stops also run one after the other. In the worst case the second stop's 5-second kill can end at L+1780, but the design says "may finish by L+1775".
- Fix: give cancel, prepare and remove a deadline of `cleanup_deadline - 60s`, and run both `Daemon::stop` calls concurrently with `tokio::join!` against L+1770.

**B3. The unknown-admission and no-continuation logic is untested** (lines 630-658 and the close gate at 370-377)
- Design lines 251-260 list tests for:
  - no warm continuation after a failure
  - a timeout, or a missing handle, stays an unknown admission and denies tree removal
  - cancellation limited to known handles
- None of the seven tests covers these. They test `execute`'s timeout and cancellation, but not the decision that follows it.
- Fix: move the handle-binding step (lines 633-655) into a pure function and test it:
  - a missing handle sets `unknown_admission`
  - a duplicate invocation sets `unknown_admission`
  - a changed session marks the sample failed
  - the loop stops at the first error
- Also test that `close` skips cancel and prepare when `unknown_admission` is set.

## Nonblocking findings
- **SIGTERM handling:**
  - A SIGTERM that arrives between samples is only seen after the next CLI process has been spawned (lines 288-303). That sample then counts as an unknown admission, which blocks cleanup of a run that could otherwise be cleaned up.
  - A SIGTERM during configuration still lets both daemons start (lines 584-599) before the select at line 615 sees it.
  - A SIGTERM after sample 3, or during `close`, is never latched, though the rollup's `job_result == "success"` check stays red in that case.
  - Fix: check for a pending signal, without blocking, before each spawn, before launching the daemons, and after `close`.
- **Config check:** `configure_value` (line 150) merges in `allow_exec` without checking that `command_policy.keys` and `deny_exec` are empty first. Requiring the exact setup-produced policy shape would enforce "refuse unexpected configuration" properly. Matrix has the same gap.
- **Clock skew:** if the clock is earlier than `created_at`, `new_result` fails (line 412) before any failure record is written.
- **Report contents:** the Markdown leaves out payload counts and the relay set (design line 232). There are no client-measured stream hashes either. They equal the expected values by construction, but the schema lists "expected/measured".
- **Duplication** (what ripwire flagged): it's real, but the parent ruled out extraction for now.
  - `Runtime::close` copies matrix's lines 623-659 apart from the row bound and the unknown flag.
  - `configure` (lines 165-237), `copy_fixture` (lines 238-273) and `parsed_handle` (lines 115-129) copy the matrix versions.
  - The copies have already drifted: `copy_fixture` adds `O_NOFOLLOW` and a glob-character check that matrix lacks.
  - `validate_samples` (lines 729-739) repeats `parsed_handle`'s field checks.
  - After the freeze, it's worth filing a bead to extract shared helpers: `close(row_bound, unknown)`, setup-report validation, fixture copy and `Handle::check`.

## Checked and conformant
- **Workload:** one same-platform cold sample plus three warm on the same daemons, profiles and room. The design's nonce tuple. Vector0 with the retained argv coverage. Exact exit 7 and exact stdout/stderr after stripping the first handle line. The full receipt is recomputed.
- **Configuration and admissions:** setup's `--update --grant/--trust` report is checked strictly. Server gets `max_commands` 5 and uptime 1800; the client has no count. Four admissions are expected, and `prepare` requires the ledger to match exactly, so a fifth row fails.
- **Deadlines:** 2220 seconds required at entry, 2070 at launch, 150 for configuration. Readiness, workload and cleanup deadlines at L+150, L+1350 and L+1770. Each sample is capped at 330 seconds. Context age and remaining time are recorded and cross-checked.
- **Ownership:**
  - Tools are verified, and the fixture copy is hash-checked twice.
  - The environment is curated, the launchers are the installed ones, and the absence of `commands/` is checked before spawn.
  - `execute` kills, reaps and joins on both the timeout path and the SIGTERM path.
  - Cleanup goes through the sealed guard and `remove_installed` only.
- **Rollup inputs:** the record is written once, exclusively, and parsing rejects unknown fields.
