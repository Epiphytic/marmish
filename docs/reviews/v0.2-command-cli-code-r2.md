## Remaining blockers

**F1. Discarded invalid chunks always report `command_consume`, never `output_gap`.** Lines 631–645 and 299.
The store marks the answer consumed and then returns `Err("command_output_cursor_invalid")` (`command_store.rs` around 1493/1509). `command_local::failure` turns that into `Failure{category:"command_output_cursor_invalid"}`. `consume()` maps every non-`Consumed` result to `invalid("command_consume")`, and the `?` at 643 then reports that.
- **Effect:** the discard path can never actually print `output_gap`, so the category is wrong every time this path runs.
- **Fix:** in the discard branch, treat `Failure{"command_output_cursor_invalid"}` as the expected result and return `invalid("output_gap")`.
- **Test:** add an IPC case where the server replies with exactly that Failure.

**F2. Local timeouts are reported as `remote_pending` with no handle.** Lines 136, 420–426, 980, 1092–1095.
`report_error` maps every `Error::Timeout` to `remote_pending`. That is wrong whenever nothing has been sent yet:
- stdin without EOF within 15 s (`read_stdin`)
- a `prepare` call that times out
- `entries()` / `select()` paging
- **Effect:** a script reads "remote_pending" (something may be running) when no invocation exists and no handle is printed. This contradicts the design's "Timeout 255 category remote_pending *with handle*".
- **Fix:**
  - `read_stdin` returns a local category such as `invalid("input_timeout")`.
  - `run()` maps `Timeout` to a local category such as `local_busy`/`local_timeout`.
  - Leave `remote_pending` only on the `wait_deadline` and `read_operation` paths, which do print the handle.

**F3. The known outcome is still lost on several timeout paths after a Finish Busy.** Lines 822, 841, 859, and the `recover` error arm at 809.
After `known_terminal` is set, these lines propagate any error with `?`:
- `self.cursors(handle, deadline).await?` (822)
- `decode_answer(...)?` (841)
- `apply_answer(...).await?` in the poll path (859), including an internal consume Timeout

Only the top-of-loop check, the `recover` Timeout/Io arm and the Poll-call Timeout honour `known_terminal`. If the deadline runs out inside `cursors` or a consume, the result is 255 `remote_pending`. That is likely, because each call can take up to 15 s and the Busy usually comes back late.
- **Fix:** split the loop body into `wait_loop(&mut progress)`. In `wait_inner`, map `Err(Timeout | Io(_))` with `progress.known_terminal.is_some()` to `delivery_pending` plus the known code.

**F4. NotFound is retried for a plain `wait`/`output` on an existing handle.** Lines 762–764, 868, 498–502.
`authenticated` only covers the current process and starts out false for `Action::Wait`/`Output`. For an invocation whose server history has been collected (the design says this must return an error), every Poll gets NotFound. The CLI consumes it and re-polls once a second until the deadline, about 180 s by default, then prints `remote_pending`, which hides the real `not_found`.
- **Fix (either one):**
  - Allow the pre-acceptance NotFound retry only on the submit path, e.g. pass `authenticated: true` initially from `run_inner` for Wait/Output.
  - Or remember the last refusal, and at the deadline report `not_found` instead of `remote_pending`.

## Non-blocking

- **559–561:** `marmish: stdin_unconsumed` is printed on every Poll, about once a second while the command runs. Print it once by tracking it in `WaitProgress`.
- **448 and 904:** NotStarted maps to 255 and is labelled `remote_exit`. A distinct `not_started` category would be accurate.
- **761–768:** in `recover`, any Finish refusal other than Busy (e.g. `result_expired`) ends the whole wait, even when the output was already fully delivered. Consider reporting `delivery_pending` for `op == Finish` instead.
- **Design note:** Finish Busy is triggered by a changed terminal fingerprint, often new gaps. So the Poll right after it often fails with `output_gap`, and the earlier known code is dropped. 255 is conservative and acceptable, but it's worth documenting.
