## Blocking findings

### N1. A disjoint group route is accepted, then permanently wedges `tick` and `open`

**Where:** `mdk_adapter.rs:1206-1218`, `:716-734`, `:179-188`, `:549`.

`check_group` only decodes the routing component. The relay intersection check happens later, in `ExplicitRouting::group`, and returns `Transport("group_relay_intersection")`.

**How it fails:**
- In `project_join`, the conversation and trust digest are committed first (`bind_authority` and `accept_conversation`). Only then does `routing.group` fail.
- After that, every `tick` calls `rebuild_routes` first, gets `ensure_trusted` Ok, and then hits the same `Transport` error. The whole account is degraded forever: no drain, no receive, no sends.
- On restart, `MdkOwner::open` also calls `rebuild_routes()?` (`:549`), so the account can't open at all.
- The trigger is an allowed peer, or any MDK client using that peer's key, sending a Welcome whose route relays don't overlap ours.

**Fix:** check the intersection inside `check_group` and return it as a policy `Mdk` rejection. The join is then rejected and forgotten, and a later route change already revokes through the digest.

### N2. Journal capacity is a lifetime quota, so ordinary traffic eventually wedges the account

**Where:** `journal.rs:478-489`, `:589-604`, `:203-210`, `:258-264`, `:612-625`; `mdk_adapter.rs:1156-1179`.

Nothing in the journal ever deletes a row (there is no `DELETE` anywhere). `prune` only clears payloads to NULL. Yet `capacity()` counts every row, including those NULL-payload tombstones. Your own test `authority_is_immutable_and_journal_capacity_backpressures` proves this: it hits `journal_capacity` using 4096 NULL-envelope rows.

The resulting lifetime caps:

| Table | Lifetime cap |
|---|---|
| `incoming` | 4096 rows |
| `outgoing` | 4096 rows |
| `rejected` | 4096 rows |
| `rejected_groups` | 4096 rows |
| `conversations` (revoked ones included) | 64 rooms |

Every message also creates a receipt, so a normal pair exhausts `incoming`/`outgoing` after roughly 2,000 exchanged messages.

**What happens at the cap:** `classify_backpressure` turns the error into `Transport`, so pending work is kept and not ACKed, as intended. But `apply_effects` aborts on the first stuck pending event. Every later tick therefore fails right after `drain`, and `drive_retained` and `submit_unsubmitted` never run. That is a permanent account-wide stall, not the "finite busy" state the design calls for (phase doc lines 104 and 108).

**Who can reach it:**
- Honest long-running traffic.
- An allowed peer, through malformed events (`rejected`) or by creating and then mutating 64 rooms.
- Possibly strangers, through unsolicited Welcomes (`rejected_groups`), depending on how fast KeyPackages rotate. I didn't verify that part.

**Fix:** evict tombstones beyond the replay horizon so the caps bound the working set, not the account's lifetime. Avoid one stuck event blocking all others (head-of-line), or at least make each blocked state recoverable.

## Prior blockers re-inspected

- **B1:** `activate` publishes the KeyPackage and calls `activate_transport(None)` before `drain` (`:797-805`). Fixed.
- **B2 / B6 (relay loss and reconnect):**
  - Relay failures now go through `recover_transport` and degrade rather than kill the daemon.
  - Reconnect uses the same `client` and connector and respawns the forwarder.
  - It retries every 2 s (fixed interval), with at most one connect per relay per turn.
- **PublicationGate:**
  - It wraps the adapter used by every runtime publish: drain/fanout retries, frozen targets, Welcome redelivery, convergence, and queued sends.
  - When blocked it returns `RetryableUnavailable` with reason "recovery_paused", never `MissingRoute`. Upstream treats that as retained (`traits/transport_adapter.rs:643`).
  - The test `paused_publication_preserves_exact_native_welcome_and_application_obligations` shows the Welcome and the fanout requests or queued intents stay byte-identical across two drains.
  - Resume (`:1644-1656`) requires all of: re-subscribed, unchanged loss value, every relay connected, and `account_subscription_eose().complete()`. Upstream defines `complete()` as every endpoint attempt being admitted and placed.
  - A baseline reset alone does not unpause; the test checks this.
- **B3:**
  - Welcome redelivery uses `outstanding_welcome_deliveries` and `redeliver_welcome`, so the exact stored Welcome goes to its original target.
  - Convergence and queued work are driven per conversation.
  - `QueuedIntentRefused` invalidates only the bound intent.
- **B4:**
  - Group-state query failures become `Transport("group_state_unavailable")` and don't revoke (tested).
  - Only `Mdk`-class trust failures revoke.
- **B5:**
  - Pending events are processed joins first.
  - Rejections and tombstones are committed before `delete_pending_application_events`.
  - Unpersisted ingest is never ACKed.
- **Receipt boundary:**
  - Receipts are created as `unsubmitted`, then marked `prepared` before `runtime.send`.
  - On restart, a prepared record with no matching fanout becomes `uncertain` and is never sent again automatically (tested).
- **Trust tests:** they use production `create_group`/`ingest`/commit APIs with no test-support features. They cover:
  - accepting an authenticated two-party room;
  - unsolicited, third-account and sibling-leaf rejection;
  - wrong or missing welcomer (the hand-set `welcomer` is honestly labelled as an application-gate test);
  - wrong purpose and extra admin;
  - purpose and admin mutation after acceptance;
  - the 65th valid room being rejected without failing the account.
- **Capacity classification:**
  - The 65th room is `Mdk("conversation_capacity")`, a definitive per-room rejection.
  - Known capacity errors become `Transport`, and genuine `Storage`/`Io` errors stay distinct.
  - I found no path where capacity causes false revocation or daemon exit. The remaining problem is the permanence covered in N2.

## Nonblockers

1. **Missed messages after resume.** Resume happens when history is *placed* in the queue, not when the daemon has *ingested* it. `receive_one` pulls one delivery per 20 ms step, so retained publishes can go out before queued history is processed.
2. **Upstream replay-loss signal unused.** `take_replay_status().loss` is never drained. Because every activation subscribes from the start, this is probably harmless, but I couldn't prove it from the pinned source.
3. **Slow resend after resume.** Nothing wakes retained fanouts when recovery finishes. The runtime exposes no wake API; marmot-app does this in `client/sync.rs:912`. Sends can wait out upstream backoff, up to an hour.
4. **KeyPackage publishing bypasses the gate.** `Publisher` uses the raw relay. This is not a group obligation, but worth documenting.
5. **Duplicate transport group IDs are allowed.** Two rooms can share a `transport_group_id` (peer-chosen), and `publish_target` returns the first match. Reject duplicates.
6. **A `runtime.send` error in `submit_unsubmitted` kills the daemon.** It is wrapped as `Mdk("runtime")`, which is daemon-fatal. The record stays `prepared` and becomes `uncertain` on restart, so this is safe, just harsh.
7. **Welcome retry never stops.** It cycles 1 s / 2 s / 60 s indefinitely rather than giving up.
8. **Round-2 nonblockers** that are still open: runtime directory under `/tmp`, no degraded backoff, stale queued IPC requests still run.
