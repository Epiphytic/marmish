## Claims verified against the code
- **Serialized engine ownership.** Only the `marmish-engine` OS thread owns the engine and its tokens; the master is dropped after open (`command_engine.rs:92-136`).
  - Readiness becomes Ready or Failed only from engine events. A Failed state refuses enqueue and cleanup (`:174-201`, `:223-236`).
- **Bounded queue and barrier.**
  - The queue and recovery limits are 64 and 32.
  - A registration is inserted only after `try_send` succeeds.
  - A completion releases the barrier only when id and revision match, and only after `ack_committed` receives a matching CommittedDecision.
  - Every result, including a known row, goes into `unresolved`, so status-first recovery holds before any new dispatch.
  - When a key is already known and the engine reports NotFound, the result is Missing and nothing is dispatched (`:517-560`). Tests `known_then_collected_ack_…` and `real_engine_canonical_refusal_…` cover this.
- **Authority.** `authority_valid` is checked only on the submit path. Observe and Status facts are still produced when authority is revoked, matching interfaces L188–190.
- **Stdin.**
  - An ambiguous Beginning, WriteIntended or EofIntended becomes Observe and is never repeated. A Gap or Uncertain stream gets one Cancel.
  - `eof_sent` is reported only when the generation, the full delivery and the engine's confirmation all match (`:776-829`, `:903-959`).
  - A missing payload is reported as `command_payload_expired`, as retention-and-ack requires.
- **Fair output.** Each stream first gets up to half of `max` (at most 8192), then the leftover goes to stdout, then stderr. This meets interfaces L489–491.
- **Stop.**
  - Ordinary Stop returns without sending Cancel and without calling `into_cleanup`.
  - `shutdown` drains events inside the full-queue retry, as r1 fix R1 required.
  - The keeper keeps the same `ProfileLease` until the thread is actually joined *and* the frontend handoff has closed. Then it runs `cleanup_runtime`, and drops the profile last (`command_lifecycle.rs:119-165`).
  - The Frontend guard drops the owner before the sender, so cancelling the stop is safe.
  - When the observer deadline expires, the caller gets the same pending handle back, unchanged.
  - A panic or JoinError forces `engine_quiesced` and `runtime_cleanup_complete` to false. The first failure is preserved.
- **Fixture.**
  - The nofollow, inode-checked unlink of the engine tree runs after the matching fence reaches Quiesced, while the server owner and the `CleanupGuard` are still alive. It is re-checked after the unlink and before `stop_owned`.
  - If the second identity fails to open, the first is owned-stopped. If that stop is incomplete, the root is kept rather than deleted.
  - `private_root` creates its directory with an explicit 0700 and checks the HOME owner and its write bits.
  - `detail` and `cleanup_detail` are both finite.
- **Engine crate.**
  - `inspect_canonical_exec` returns a closed set of outcomes, and `require_*` keeps its old behaviour.
  - `terminal_status` and `owned_worker_presence` are read-only; any error maps to Unknown or RecoveryUncertain, never Absent.
  - `cursor_after_gap` no longer rewinds: an open-ended gap now leaves the cursor in place. There is a regression test for it.

## Findings (all non-blocking)

**N1 (Low): the Poll budget arithmetic can panic.** At `command_engine.rs:731`, `max - stdout.bytes.len() - stderr.bytes.len()` is unchecked, and so is `remaining -= more.bytes.len()` at `:740`.
- **Effect:** this is only safe if `read_output` never returns more bytes than requested. If it ever did, the engine thread would panic, and the panic would degrade the stop report. That fails closed, but a bounds violation should be a finite error, not a panic.
- **Fix:** use `checked_sub` and return an `engine::Error`, or have the read closure reject `bytes.len() > limit`.
- **Test:** a fake `read` returning `limit + 1` bytes should give a finite Err with no panic.

**N2 (Low/informational): a non-matching completion still enters the queue.** At `:149`, a completion whose id or revision does not match is still pushed to `completions`.
- **Effect:** none if the actor follows interfaces L475–480, which require slot filling to match key, OperationId and revision, and rejects anything else. That code belongs to the root/store review, so I did not verify it.
- **Fix:** either drop the completion here or document that the actor is the only filter.
- **Test:** a stale-revision completion must leave its slot Pending and the barrier unchanged.

**N3 (Informational): a key whose result is Uncertain blocks all new dispatches until a later observation settles it.** This is by design, since interfaces L404 says "Unknown errors retain the barrier". It deliberately fails closed. The cost is availability: one wedged key holds up every new dispatch. Operators should see this as a visible "recovery_uncertain" state.

**N4 (Informational): worker hardening is narrow.** The worker sets a panic hook and disables core dumps with RLIMIT_CORE=0; it does not call `PR_SET_DUMPABLE`. It is a sibling binary with no Tokio runtime or network. Nothing in the contract requires more, so I am not raising this as a defect.

**N5 (Informational): Stop can be delayed by up to about 60s.** `WriteInput` has a 60s timeout and runs in a single engine turn. The keeper's one-second loop handles this correctly. It is a reason the 30s daemon observer must not be read as a guaranteed exit time, which owner-stop L126–127 already says.
