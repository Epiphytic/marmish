**What I checked:**

1. **The macOS clock call still matches the system interface.**
   - `Cargo.lock` pins `libc` 0.2.189.
   - In that version, `libc/src/unix/bsd/apple/mod.rs:307` declares `mach_timebase_info` as a struct of two `u32` fields, `numer` then `denom`. It's defined inside libc's `s!` macro, which makes it `repr(C)`. It's marked deprecated since 0.2.55 in favour of `mach2`.
   - Line 179 makes `mach_timebase_info_data_t` a deprecated alias of that struct.
   - Line 4514 declares `fn mach_timebase_info(info: *mut mach_timebase_info) -> c_int`, and `c_int` is `i32`.
   - The new local `#[repr(C)] struct TimebaseInfo { numer: u32, denom: u32 }` and `fn mach_timebase_info(*mut TimebaseInfo) -> i32` have the same layout, field order, pointer argument and return type. That also matches Apple's header (two `uint32_t` fields, returning `kern_return_t` = `int`).
   - `mach_continuous_time() -> u64` is unchanged and was already declared locally.
2. **Clock behaviour is unchanged.** The function still uses `mach_continuous_time`, which keeps counting while the machine sleeps. The checks and maths are the same: error on a non-zero return or `denom == 0`, then checked u128 multiply, divide, and convert to seconds. The only difference is the binding source, so a fully qualified `libc::` name became a local one with no name collision.
3. **No fake macOS tests.** The diff adds no tests. `actual_clock_is_available_and_monotonic` just calls `continuous_time()`, so on macOS it would exercise the real clock.
4. **The `version_str` gate is safe.** Its only caller is `crates/marmish-vault/src/linux.rs:155`, and the `linux` module is itself gated to Linux (`lib.rs:29-30`). Neither `macos.rs` nor `helper.rs` uses it, and since it's `pub(crate)` nothing outside the crate can. On macOS it would have been unused code, and `-D warnings` turns that into a build error. `version()` stays ungated because `macos.rs`, `helper.rs` and `lib.rs` all use it.
5. **Linux test log.** `/tmp/marmish-clock-portability-tests.log` shows 4 passed, 0 failed, including `actual_clock_is_available_and_monotonic`, which on Linux reads `CLOCK_BOOTTIME`.

**Non-blocking notes:**
- **Zero-numerator check.** `command_limits` rejects `denom == 0` but not `numer == 0`, while `crates/marmish-engine/src/platform/macos.rs:113` rejects both. A zero numerator would freeze the time at 0, so `remaining()` would never shrink and the uptime limit would never trigger. This was already the case before the diff, and macOS never returns zero in practice. Adding the check later would make the two crates consistent.
- **Inconsistent fix across crates.** `marmish-engine` (out of scope) still uses the deprecated libc items under `#[allow(deprecated)]`, so it compiles cleanly. The two crates now solve the same deprecation in different ways, which you may want to unify eventually.
- **No macOS build yet.** Neither change has been compiled or run on macOS. Both still need a macOS clippy and test run before macOS acceptance.
