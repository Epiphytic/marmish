**What I confirmed:**
- **`native_layout.rs` (the only product-behaviour change):**
  - In a managed install, every frontend (`marmish`, `marmishd`, `marmish-worker`) uses the verified `versions/<id>/marmish`. The manifest, receipt, version and target checks are unchanged.
  - In an ordinary sibling layout, the helper must equal `parent/marmish` after validation, so a missing, symlinked or writable helper fails closed.
  - The exact downloaded `marmish-<version>-<target>` name stays its own helper. Neither `marmishd` nor the worker gets that exception.
  - `resolve` canonicalizes `current` once, so a later launcher retarget cannot move an already-resolved helper. The retarget test covers this.
- **`installed_version_lifecycle.rs`:**
  - The four helper sites use `marmish`: capture at 1722, verifies at 1756 and 1794, and `bin/marmish` canonicalized at 1805.
  - The only other `"marmishd"` string in the file is the daemon-selection assertion at 1796, which is unchanged.
  - The legacy-launcher transaction and the patch-version-generic lifecycle tooling are untouched.
- **`native_install.rs`:** the new test goes through the real `bin/marmish`, `bin/marmishd` and `current/marmish-worker` launchers. It checks that each helper and worker equals the canonical version directory with no `current` component, and that both survive `Uninstall`.
- **Provider `daemon_reload`:**
  - It is a separate method that runs the real `marmishd --state-dir <state> -i <name> init` with a 120-second timeout.
  - It is called only from `Qualification.run`, after the first reload and after unlock.
  - The inherited `reload()` and the version-generic lifecycle `upgrade_reload` are unchanged.
  - Its test pins the argv, environment and timeout, rejects an identity mismatch, and propagates `Refused`.
- **Docs:** `agent-spec.md` and the lifecycle design doc are consistent with the code. They state that the macOS denial cause and full daemon startup are unconfirmed, and that no ACL or fallback policy changes.
