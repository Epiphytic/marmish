## B1: fixed and verified
- **Classification:** `command_adapter.rs:354-370` now includes `command_poll_busy` in `command_projection_deferred`. Both places it is used (`:133` decode and `:157` projection) return `Ok(())` before the `delete_pending_application_events` at `:163-165`. The MDK pending event therefore stays unACKed. The unit test at `:376-397` covers both the `Invalid` and the `Mdk` forms.
- **Retry owner:** every `apply_effects` pass re-lists and re-selects the durable pending queue (`mdk_adapter.rs:1769-1796`, through `select_pending`). A deferred Poll #2 is therefore retried on a later tick with no new code path.
- **Store semantics:** `answered_unretired_server_poll_defers_same_source_until_ack_and_maintenance` (`command_store.rs:~4789`) shows the following sequence:
  1. Poll #2 gets `command_poll_busy`.
  2. The failed transaction leaves no request row and no native binding for that source.
  3. Poll #1 is ACK-settled and `command_maintain` retires it.
  4. The *same* source then projects and is answered, with its binding recorded.
- **Is a full adapter-plus-pending integration test required?** Not for this internal increment, in my judgement. The adapter's deferral is a single early `return Ok(())`. Its classification is unit-tested, the store transition is tested, the replay owner is the existing pending-queue scan, and the final live direct repeat reports a pass. I list the missing test as a low-priority note below.

## Client fixture retry (`command_check.rs:374-405`)
- Only the exact `Err(Error::Invalid("command_poll_busy"))` is retried. Every other error returns.
- The request ID and op are reused unchanged.
- The retry is safe because the store rejects inside a transaction that rolls back. `freshness` checks against the replay floor, not wall-clock age, so retrying the same ID inside the deadline cannot turn it stale.
- Each retry drives `pair.turn(deadline)`. That ticks both owners, tolerating only the existing list of transient transport errors, and returns `Timeout` once the deadline passes. So the loop is bounded and masks no other errors.
- This code is in the fixture only, not public CLI behaviour.

## Other changes reviewed
- **The two runtime-effects tests in `mdk_adapter_tests.rs:1686-1860`:**
  - Both use real accepted command rooms, a real authenticated encrypted request, and real native effect DTOs through the full `apply_effects`. They don't constitute live evidence.
  - First test: an unknown `QueuedIntentRefused`, followed by a known `Published`, persists exactly one unACKed binding with matching evidence, and the publication becomes Published.
  - Second test: 256 pending invalidations set up capacity pressure. The invalidated publication ends terminal Invalidated with no binding or ACK marker. An unrelated later `Published` still persists.
- **Guarded unlink:** my round-1 gate saying the guarded fixture unlink was unimplemented was **wrong, and I withdraw it**. The mechanism exists:
  - `command_check.rs:298` `remove_engine_tree` takes the cleanup fence, waits for `Quiesced` at that fence, then calls `EngineTree::remove`.
  - `EngineTree::remove` (`:910`) checks device/inode receipts and snapshots the tree before the first unlink, then uses descriptor-relative `unlinkat`. It re-checks the fence afterwards.
  - Unit tests `cleanup_tests` cover the owned-subtree case and the symlink and hardlink rejection cases.
  - The live direct reports say cleanup was true. That is the root's evidence; I didn't re-run it.
- **Retention design header:** now reads "APPROVED round 4". The round-1 note is resolved.

## Low-priority notes (non-blocking)
1. There is no end-to-end adapter test showing that a server `command_poll_busy` keeps the MDK pending event and the next tick answers it. It would be a worthwhile regression guard once someone is working in this fixture area again.
2. Store r4 N4 is carried over: quarantine is not visible in publication state, and there is no operator recovery tooling.
3. Changing the relay configuration permanently revokes command rooms. This is consistent with the foundation design but should be documented for operators.
4. A daemon signal can cancel in-flight dispatch or tick futures. This predates the increment, and owned stop still follows.
5. `command_store.rs:757-764`: the `command_transient_refusal` arm is unreachable.
6. Ripwire is not green. The concrete cross-component risk I see is growth in the owner maintenance paths (`maintain_journal`, `apply_effects`), which raises the cost of reviewing future seams. Name-collision and SQL/test-similarity findings are not defects. Don't treat this as a passing metric.
7. Strict Clippy fails because of unused future IPC APIs. This is disclosed honestly, and no blanket allow was added.
