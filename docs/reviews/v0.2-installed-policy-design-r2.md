## Blockers

**P-B1. The zero-grant probe leaves a dead or stale command room that the granted phase reuses.**
- The client treats a room as ready once its own welcome and intents are published. Server membership is never checked (`command_ready_room`, `command_local.rs:262-289`).
- Every daemon publishes a key package when it activates (`mdk_adapter.rs:1401-1410`), so the zero-grant server can be discovered. The client CLI will therefore probably create a room and may publish the probe's Submit.
- That room stays in the same client profile's journal. In the granted phase, `CommandPrepare` returns the first matching room, which is the old session. Then one of two things happens:
  - The server dropped or ignored that group (on the foundation path, `project_join` → `forget_and_confirm`, `mdk_adapter.rs:1930-1942`; I didn't confirm the command-room path). Every denial then times out.
  - The server joins the group later and handles the old Submit. That adds a sixth server row, and an execution if the probe's executable is allowed.
- Either way, the ALL-five-rows equality fails. It fails closed, but it fails on every run. "Preserving the same platform/profile identity" across phases is what causes this.
- **Fix:** run the zero-grant probe from a separate, throwaway third client identity, with its own setup budget slice. In the granted phase the server rejects that identity as `untrusted_peer`. Also:
  - Record the probe's client invocation entries.
  - Require the granted session to differ from any probe session.
  - Pin the probe to an executable the granted policy would deny anyway, as a second safeguard.
  - Alternatively, require and prove an exact failure category that occurs before any room is created. The source suggests that's unlikely.

**P-B2. Through the local IPC, the local conflict returns `command_handle_binding`, not `command_invocation_conflict`.**
- Changed Submit bytes with a fresh request ID produce a new handle with a different `submit_sha256`.
- `CommandSubmit` calls `local_owner` first (`command_local.rs:409-417`). `validate_entry` then fails on `submit_request_sha256` with `command_handle_binding` (`command_client.rs:178-186`), and that error is returned before the store runs.
- `command_invocation_conflict` (`command_store.rs:875`) can only be reached through the in-process journal call used in `command_check.rs:1042-1046`.
- This also corrects my r1 non-blocker 4, which wrongly said the IPC path would produce the conflict category.
- **Fix:** expect exactly `LocalResult::Failure{category:"command_handle_binding", handle:None}`, with no new client entry, no server row and no receipt. Pin it with an offline test that goes through `dispatch`, so the actual IPC mapping is exercised.

## Non-blockers
1. **Failure-path cancel needs its own helper.** `cancel_fixture` counts every evidence row against `max_rows<=4` (`installed_cleanup.rs:529-548`), so it fails at the fifth row even with a one-key map. Name a narrow helper: page all evidence, match exactly one `(principal, invocation)`, and send `CommandLocalCancel{cursor}`.
2. **Prove the first request actually landed before the retry.** Writing a frame and disconnecting doesn't show the daemon processed it. Between the disconnect and the retry, poll `CommandInvocations` for the exact handle. Otherwise the "retry" may really be the first submit. The existing `response()` can't do write-then-close, so this needs a small raw framed writer.
3. **Reuse the existing IPC helper.** Lines 116-118 propose a "new narrow typed local IPC helper", but the shared PID-bound `cleanup::command_request` (`installed_cleanup.rs:177-188`) already returns `LocalResult`. Line 201 already relies on it. Reuse it; that's the smallest implementation.
4. **State the server extension explicitly.** The corrections document allows the no-engine branch only for "fresh owned client profiles". This design also applies it to the zero-grant server. The conditions do hold for the server (`verify_no_engine` checks no role), but say so and give the reason.
5. **Budget room readiness.** Discovery, the welcome, and `CommandPrepare` reaching `Ready` in the granted phase have no budget line. "evidence/preparation15" is too tight for real relays. Put it inside the first denial's 90 s or split it out.
6. **Rename the result field.** In the closed result schema, rename "submit SHA" to `request_sha256` plus `group_submit_sha256`, to match line 195.
7. **Check the fixture copies.** Confirm the fixture doesn't derive its receipt location or identity from its own executable path, so the copies in `policy-bin/` behave identically.
8. **Read the group digest before consuming.** Do the `client_group_submit` lookup before `CommandConsume`, so retention can't affect it.

## Sound as designed
- The refused-row predicate matches `command_cleanup_counts`, which excludes refused `Unknown` rows from `worker_unknown` (`command_store.rs:3633-3634`).
- Denials can be bound through `wire::Response.request_sha256` (`command_wire.rs:94-100`) and `LocalResult::Answer`.
- The lost-reply retry with the same ID and same bytes attaches to the existing row as an exact retry (`command_local.rs:409-412`).
- Making `prepare`/`evidence` take an explicit per-row disposition is a small, safe change to the sealed guard (`installed_cleanup.rs:309-365, 430-485`).

`★ Insight ─────────────────────────────────────`
- On the client, a "ready" command room only means "my welcome was published". It does not mean "the peer joined". So any phase that touches a remote peer leaves durable room state behind, and later phases using the same profile pick it up.
- The local IPC adds a handle-binding check in front of the store. Errors that in-process tests reach directly (like `command_invocation_conflict`) can come out under a different category over IPC. Expected categories need to be pinned at the same layer the harness will actually call.
