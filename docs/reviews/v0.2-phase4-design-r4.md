## Amendment: r3 clarifications confirmed

- **Pure terminal refresh (lines 106-111):**
  - A read-only `job_state` check runs first. Any state other than Exited fails preparation without reconciling.
  - For Exited rows only, status is read through `owner → job_for → store.status`, then raw presence.
  - `Engine::status`, `authorized_job` and `reconcile_step` are forbidden for this pass.
  - This matches the source: `store.status` is a pure load and owner check (`store.rs:771-775`), and `start_accepted` is reachable only through `reconcile_step`.
- **All rows (lines 105, 119):** every server ledger row in the profile is refreshed, including unexpected admissions and rows already terminal, and acceptance requires all of them to be at or after the fence. There is a test at line 245.
- **Quiesced equivalence (lines 98-99):** `engine_quiesced == (cleanup=="quiesced")`, and an inconsistent status is rejected.

**One non-blocking clarification, line 108:** a refresh failure before consumption should explicitly move to `failed`. Lifecycle line 151 already implies this, since the state never returns to open. The text should also say the engine, which is still unconsumed, stays unused, as line 159 does for a failed consume. Otherwise someone could read it as leaving the instance in `draining` with a live engine.

## Phase 4: r3 clarifications confirmed

- **Ten sequential waves, at most 4 jobs concurrent (lines 120-130):**
  - Each wave runs three platform jobs, plus a fresh onion owner in each T-wave.
  - The cross-wave barrier waits on both the platform jobs and the owner of the previous wave.
  - It can't deadlock, because each owner waits only on its own wave, which is already running.
  - It also stops a draining owner from becoming a fifth concurrent job.
- **Qualification budget (lines 133-146):** 10m readiness + 14m work + 6m reserve = 30m = U. With launch by minute 20, everything ends by minute 50, leaving the 5-minute margin. There is one profile per wave and no shared reserves, so the feasibility gap from r3 is closed.
- **Matrix schedule:** `L+U−6m`/`−5m`/`−1m`, with readiness ≤ `L+4m` when U=30. A miss produces the named `matrix_readiness_budget_missed`.
- **Conservative wall deadline (lines 101-107):** ServerReady carries the client deadline in UTC. Remote clients reserve their full operation cap minus the 120-second skew, and a miss gives `remote_client_budget_missed` with no new invocation. Enforcement stays on local monotonic time.

**Non-blockers:**
1. **Line 138 / 174, recovery restart.** State the restarted instance's values explicitly:
   - uptime `U' = (L+U) − L'`, so its 6m/5m/1m reservations still end at the original `L+U`;
   - `--max-commands` set to only the planned admissions that remain. Phase 2 line 511 counts admissions per daemon, so after a restart the count could reset and admit fresh commands.
2. **Lines 120-130, wall time.** Ten serial waves is roughly 5×55 + 5×65 ≈ 10 hours, plus builds. Because the result must come from a single attempt, any flake means re-running the whole ~10-hour workflow. Record this as an accepted cost and keep it in mind for runner budgeting.
