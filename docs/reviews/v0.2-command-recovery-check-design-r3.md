## Verified against the code

**1. Keeping the normal original Submit ID: correct.**
- The client refuses a fresh Submit request ID for an existing invocation: `check_original_submit` returns `command_submit_client_request_conflict` (`command_store.rs:1095`).
- Retrying with the original ID is idempotent:
  - `prepare_command_publication` builds the event deterministically, with the timestamp from `id_timestamp(request_id)`, so the same request produces the same `app_event_id`.
  - `check_slot` sees the existing slot, so no new slot is inserted.
  - `insert_publication` returns `Ok` for an identical existing row.
  - A store test (5825–5832) already asserts the same key on a repeat call.
- The design correctly labels this as local evidence only.

**2. Fresh raw identical probe: matches the server behaviour.**
- For a new request ID on a known invocation with the same digest, `admission_response` returns `(Existing, Some(Ok(Submit{Existing, status})))` (`command_service.rs:230–239`).
- It doesn't go through `bounded_admission`, so it reserves no budget.
- `command_project_request` accepts it: there is no existing slot, a response is present, and the digest matches. It then inserts a new slot and response, and the invocation stays unchanged.

**3. Fresh raw conflict probe: matches the server behaviour.**
- A digest mismatch produces `Refused(InvocationConflict, detail None)` with a response (`command_service.rs:215–225`).
- The store lets exactly that decision through (`command_store.rs:782–793`) and checks the refusal bytes (836–846).
- This looks like the pinned fix, but I did not review it; that still needs its own service/store review.

**4. Probe slot: no fake ownership or ACK.**
- A response carrying a probe's request ID has no client slot, so `command_project_response` fails with exactly `command_not_found` (`command_store.rs:949`). That is the only hook point the design uses.
- A cached Existing response for the original ID matches a real client slot, so it can never reach the probe. The refinement's claim about this holds.
- The slot holds one result, filled slots are never overwritten, the closed `CommandProbeExpected` enum fixes the expected outcome, the `op == Submit` check is now explicit (round-2 note 4), and taking the result is required before re-arming. Two sequential probes therefore can't overwrite each other.
- The two retained unowned obligations use the exact APIs round 2 asked for (note 2). A missing obligation is now explicitly red.

**5. Timing: still bounded.** Probe 1 is now counted against both the 20 s identical-retry stage and the 30 s remote-probe stage. Counting it twice only makes the bound more conservative, so the 321 s total and the 39 s margin under the script's 360 s fail-safe still hold.

**6. Lifecycle and guarded cleanup: unchanged.** The stop/reopen state machine, the comparison of both held receipts after reopen, and "recovery means `recovery == false`" (round-2 note 3) are kept.

## Blocker

**B1. `capture_path` removes the only typed capability on deletion, so "grants no independent deletion authority" is false as written.**
- `command_check` is `mdk_adapter::command_check`, so `pub(super)` makes `capture_path` and `remove` callable from anywhere in the `mdk_adapter` module tree.
- `remove(self)` takes no CleanupGuard, fence or lease argument. The guard requirement exists only as a comment (913–914) and in how `remove_engine_tree` is written (300–349). Note that it uses the `command_begin_cleanup` fence; no `CleanupGuard` value is passed in.
- Before this change, building a receipt required a `&ProfileLease`, which was the one type-level witness. `capture_path(&Path)` drops it, so any code in that module tree could capture any `<root>/commands` and then remove it.
- The doc's sentence "`remove` … requires the caller's live actual CleanupGuard, lease/installed-owner equivalent and unchanged quiescent fence" describes a convention, not something the API enforces.
- **Fix: pick one and say which in the doc.**
  - (a) Make `remove` take an explicit witness, such as `&CleanupGuard` or the observed fence plus an owner/lease reference.
  - (b) Have `capture_path` require an installed-owner or lease-equivalent witness type instead of `&Path`.
  - (c) Keep `capture_path` private to `command_check`, and give the installed-acceptance reuse a constructor that does require a witness.
- Also name the installed-acceptance caller and confirm `pub(super)` actually reaches it. If that caller lives outside `mdk_adapter`, the visibility as designed is either too narrow or will be widened later, and that widening would need its own review.

## Non-blockers

1. **Original-ID retry after the publication row is retired.** If the client's original publication row has been pruned or retired by the time of the retry, `insert_publication` falls through to the association check (2031–2046). That might fail or re-queue. State the expected result (red, or allowed) so implementers don't treat a binding error as a pass.
2. **Budget wording.** Give a single start instant for each stage, e.g. "probe 1 is timed from send; the 20 s stage runs from the local retry", so the double-counted window can't be read as two separate allowances.
3. **Server-side retention.** The Existing and refusal responses each add a server request slot and a response publication. Say that these count only toward existing bounded request retention, not active/uncertain counts. That is consistent with `begin_cleanup`, but worth stating.
4. **Existing worktree code.** `capture_path`, the delegation, and a parity test (`path_capture_matches_lease_receipt`, which compares `parent_id`/`root_id`) are already in the worktree. I did not treat that as implementation acceptance. The parity test should also assert that a receipt captured at a path without a lease cannot be removed, or it should be retired along with the B1 fix.
5. **Pre-existing items still open.** Round-2 note 5 (finalize red without waiting on an unbounded `PendingStop`) is still unaddressed, and the doc's status line correctly leaves the refinement pending.

Once B1 is fixed, I expect to approve this design-only scope, with no further refinement changes needed.
