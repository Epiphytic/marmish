### Blocker

**B1 — `SIGKILL` can reach a PID the script no longer owns** (fixture lines 19–20 in `bounded()`, lines 66–68 in `cleanup()`).
- After the grace wait, `kill -KILL "$pid"` runs whether or not the child is still alive.
- I tested this: bash reaps a background child on its own as soon as it exits, before any `wait`, and `/proc/$pid` disappears.
- In the normal path the relay exits cleanly on SIGINT, gets reaped, and then still receives a KILL aimed at a freed PID. The same happens in `bounded()` whenever `gh` exits on TERM.
- With Linux `pid_max` at 4194304, actually hitting another process is very unlikely. But it breaks your "no reused-PID signals" rule on every successful run, and the fix is two lines:
  - Line 20: `if kill -0 "$child" 2>/dev/null; then kill -KILL "$child" 2>/dev/null || true; fi`
  - Line 68: `if kill -0 "$pid" 2>/dev/null; then kill -KILL "$pid" 2>/dev/null || true; fi`
- This shrinks the race to microseconds. Pure bash can't close it fully, so say that in a comment.

### Not blocking
1. **Deadlines overshoot by up to about 12s.** The `sleep 10` calls at lines 123 and 145 aren't clamped to the time left (a 12s budget took 22s in testing). That leaves only about 20–30s of slack in the owner job before its 30-minute timeout, which could cut off the cleanup step. Fix: don't sleep past `until_at`, or lower the `1700` at workflow line 94 to about 1650.
2. **Cold-cache timing is tight.** The Deaddrop build target (`$RUNNER_TEMP/deaddrop-target`) isn't cached, and each client runs the full `cargo test --release` before its live flows. A first run could hit the owner's 1730s relay lifetime. It would fail cleanly, but it's likely to be flaky.
3. **API call volume.** `wait_clients` re-lists the artifacts once per platform per loop. Together with three clients polling, the worst case is roughly 700 calls an hour against the 1000/hour `GITHUB_TOKEN` limit. Fetching the list once per loop cuts that to a third.
4. **Live-flow checks are looser than the owner's.** The direct and onion checks at workflow lines 178 and 195 don't verify `.schema`, `.protocol` and `.phase`, which the owner check at fixture line 101 does. Neither step has `timeout-minutes`. The 600s internal deadline in `foundation_check.rs` still enforces the 10-minute cap, so this is only a safety margin.
5. **Clients don't notice a failed owner.** They wait the full 1200s for readiness even after the owner has failed. Polling for the owner-outcome artifact would let them fail early.
6. **"Re-run failed jobs" will always fail**, because artifacts are bound to the attempt number; that's the correct fail-closed behaviour. Document "re-run all jobs".
7. **Small gaps.** `bounded()` signals only its direct child; a mock `gh` left a `sleep` grandchild running, though the real `gh api` is a single process. `unzip -p` (line 41) is size-checked only after extraction; piping through `head -c 65537` would cap it.
8. **SIGINT to the relay is untested live.** The relay starts in the background of a non-interactive shell, so it inherits SIGINT as ignored. My bash mock relay couldn't trap it and got SIGKILL after 20s. The real Deaddrop uses `tokio::signal::ctrl_c`, which should install its own handler and override that, but I haven't confirmed it on the real binary.
9. **Actions pinned by tag, not commit SHA:** `actions/*@v4`, `Swatinem/rust-cache@v2`, `dtolnay/rust-toolchain@1.97.1`.

### What already meets the spec
- **Concurrency:** the client jobs don't depend on the owner job. The owner publishes readiness only after its own encrypted onion check passes, then stays up until all three client results arrive or its deadline passes.
- **Run/attempt/SHA binding:** artifact names include run and attempt, and the downloader checks run id, head SHA, that exactly one match exists, size, the single zip member, and the binding fields inside the file. Mocks with a wrong SHA, wrong attempt or duplicate artifact all failed closed.
- **Success criteria:** `ok` requires the decrypted bytes to match, a durable `received` receipt, rejection of a conflicting resend, and a fresh exchange after restart. Relay acceptance alone can't pass. A client marked `ok:false` makes the owner job fail.
- **Expressions:** no `${{ }}` inside any `run:` block, and `inputs.direct_relay` goes through env.
- **Token handling:** `GH_TOKEN` is now set only on the two API steps. The `marmish` runs use `env -u GH_TOKEN …`, and `serve` unsets the tokens (the mock child saw none).
- **Secrets stay out of artifacts:** uploads contain only readiness/cleanup/client JSON, `cargo tree`, the lockfile hash, `rustc -Vv` and the `foundation-check` reports. Private logs and state live in a 0700 root that cleanup deletes.
- **macOS:** the client-side modes use only bash 3.2-compatible syntax plus BSD `mktemp -d` and Info-ZIP `unzip -Z -1`/`-l`.
- **External references:** Deaddrop at the pinned commit has the `deaddrop-server` package, `deaddrop` binary and `relay --data-dir` command, and writes exactly `{"onion_url","relay_url"}`. The `dtolnay/rust-toolchain` `1.97.1` branch and the Deaddrop commit both exist. The repo is public, so `ubuntu-24.04-arm` runners are available.
