## What I verified against the approved design
- **Fixed deadlines:** the exchange deadline is set once from the start time and capped at 120 s. The join keeps its 90 s deadline. Each tick gets `min(deadline, now + 15 s)` as its own deadline, with no outer cancelling timeout. The test confirms persistent failure ends at exactly 120 s (90 s for the join), and every recorded tick deadline is within both bounds.
- **Both peers progress:** a recoverable error in the receiver's tick is recorded and the sender still ticks in the same cycle. Fatal errors stop immediately, before the other owner ticks.
- **Terminal errors:** the eight terminal transport labels match the design exactly, and so does the retryable set. Storage, Identity, Mdk, Invalid and Io errors are terminal. When the deadline runs out after recoverable errors, the category is `deadline` (`category()` maps `Timeout` to it), and the role and label are kept in `last_recoverable`.
- **No initial-send retries:** `send` is called exactly once before receipt, and an initial send error ends the check without any ticks. The post-receipt duplicate and conflicting sends stop the check on any error.
  - The conflicting-send check is now stricter. It requires exactly `Invalid("application_id_conflict")`, which is what `journal.rs:404` returns from `verify_outgoing` before any network I/O. Before, any error was accepted.
- **Received and receipt proofs:** both the exact bytes and the sender's `received` status are still required. A byte mismatch gives `Mdk("byte_preservation")`.
- **Join behaviour:** it uses the same driver. The joiner (B) ticks first, as it did before, and counts as `receiver`.
- **Diagnostics:** every value is a fixed `&'static str` from the allowed lists, and anything unknown becomes `other`. Tests show a raw-looking label such as "private relay URL" serializes as `other`. The `diagnostic` object is additive.
- **Dev dependency:** `tokio` with `test-util` is added under `[dev-dependencies]` only.

## Non-blocking notes
1. **`last_recoverable` can be stale.** It lives for the whole run and is never reset at the start of each join or exchange. If a later stage runs out its deadline without any tick errors, the report shows a recoverable error from an earlier stage. The report's `stage` field doesn't tell you where that error came from. I'd suggest resetting it at the start of the driver, or recording its stage, before the hosted rerun, since that run is meant to diagnose exactly this.
2. **`terminal_label` is set for any transport error that ends the run.** That includes errors from the initial send or from activation that aren't on the terminal list (for example `relay_reconnect`, or `other`). This fits the meaning "the transport error that ended the run", but the doc wording "only for a terminal transport error" could be read more narrowly.
3. **Last cycle near the deadline.** If the receiver's tick uses up the remaining time, the sender doesn't get a final tick. That is fine at the deadline.
4. **Outer execution timeout.** When the overall execution timeout fires, `terminal_label` stays null and `operation` keeps its last value. That is consistent and sanitized.
