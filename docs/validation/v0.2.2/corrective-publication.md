## macOS recovery still requires an interactive test

After updating, stop any daemon using the profile, then from a foreground Mac
terminal run `marmish --debug keychain-authorize`, followed by
`marmishd --debug`. Supply the same configured `-i NAME` and `--state-dir DIR`
on both. The command reads only the two existing credential refs, requests
consent, then verifies access in a fresh helper with prompts disabled. It creates
no identity, rewrites no ACL and changes no backend. An OS one-time allowance
may fail the fresh check; persistent authorization is the user's OS choice.

The reported failure after successful unlock does not establish its OSStatus or
ACL cause. Native compilation/tests and headless/file-backed setup do not prove
interactive consent, persistence or recovery of that user's failure. Successful
credential verification alone does not prove database integrity or daemon startup.
Full installed platform matrix, provider/lifecycle/benchmark qualification remains
incomplete. Tor is optional/experimental; Linux requires glibc 2.39+, macOS requires
Apple Silicon/macOS 15+, ad-hoc signed and not notarized.

The two original report files are distinct owned outputs, not byte-identical;
each persisted JSON matches its original bytes. Their identical recovery-output
hash is expected for the same fixture output; the identical 6,796 ms sample
does not make the other independently differing timings equal.
[Process observations](process-observations.json) preserve each report hash and
outer-process stderr byte count/hash, separately from the remote command samples
whose own `stderr_bytes` values include expected fixture output. Raw stderr
containing process identifiers stays outside source.
