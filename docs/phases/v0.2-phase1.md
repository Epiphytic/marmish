# Marmish v0.2 Phase 1: native identity, storage and transport foundation

Independently approved by Claude after two design-review rounds; see [the review record](../reviews/v0.2-phase1-design.md) for scope, findings and dispositions. Implementation follows the user-authorized phased workflow. Parent epic: `marmish-7nw`. No v0.1 work resumes. This phase implements no remote command execution, interactive shell, tmux, browser, Python launcher, external wnd, network namespace or mandatory OS sandbox. Existing Python is retained only as an optional later interoperability fixture, outside the v0.2 runtime/build dependency closure.

## Deliverable and exit

A Rust daemon/library and thin Rust CLI can initialize/select named local identities, exclusively open encrypted native MDK state, establish a dedicated two-party Marmish conversation, exchange authenticated encrypted test payloads and resume after restart. Demonstrate this with freshly generated keys over (1) an explicitly configured direct relay and (2) an explicitly configured onion relay reached through embedded Arti. No public relay defaults and no direct fallback from Arti. A namespace capability is not required to run either mode.

Phase1 acceptance is native identity/message transport, not command execution or complete v0.1 protocol compatibility. Preserve a distinction between socket/relay acknowledgment, authenticated decrypt success and durable application receipt. Successful relay publication alone cannot satisfy acceptance.

### Confirmed composition and event driving

These are audited source contracts, not compilation or live evidence. Build one immutable local `Keys`-backed `MarmotNostrSigner` per selected identity. The account proof signer implements synchronous `sign_account_identity_proof(&AccountIdentityProofRequest)->Result<[u8;64],String>` by checking its account, signing `request.proof_event()` and returning `request.signature_from_signed_event(...)`; never sign arbitrary proof bytes. Reuse that account signer for `NostrMlsPeeler::new().with_welcome_signer_arc(...)`, SDK authentication and `NostrSdkRelayClient::with_account_signer(...)`. The peeler handles Nostr/MLS envelopes; it does not select destinations.

The runtime factory constructs the injected-transport SDK client, immutable-account relay client, `NostrTransportAdapter`, and Marmish-owned `ExplicitRouting(Arc<RwLock<RoutingState>>)` implementing `TransportRoutingPolicy`. One clone belongs to the runtime and one to the serialized owner; this small shared policy replaces the immutable consuming builders of `StaticTransportRouting`. Its immutable configured endpoint ceiling cannot be enlarged. Register the peer inbox route from configured endpoints **before** `create_group`, which publishes Welcomes internally. After GroupCreated or an accepted GroupJoined, read/decode `NOSTR_ROUTING_COMPONENT_ID` through `runtime.app_component`, intersect its endpoints with the configured set, install the group route, then `sync_transport_groups`. An empty intersection fails closed. Rebuild accepted live-group routes from `live_group_ids()` and authenticated components after open and before activation; remove routes on rejection, revocation or forgetting. Missing routes are finite failures, never an excuse for default relays. Phase1 peers must explicitly configure a shared relay: inbox publication uses the configured set and does not discover or adopt peer-advertised inbox URLs.

Persist a random device slot before key-package publication. A Marmish publisher implements `prepare_key_package` with **no network exposure**, producing a signed artifact; `publish_prepared_key_package` publishes that same artifact on retries and reports actual receipt/failure. The no-op publisher is forbidden in live gates.

### Bounded KeyPackage discovery

Use the **same injected-policy SDK Client** directly for bounded kind30443 acquisition, with exact peer-author filter, `ReqTarget::single` for each endpoint and `AcquisitionLimits`. Sources must be a nonempty subset of configured endpoints; no implicit directory/default relay list. Do **not** use `NostrSdkDirectoryRelayFetcher`, even its injected `new(client)` constructor: at this upstream pin its trait fetch method calls `Self::standalone()`, inspection builds `nostr_builder()`, and completion calls a helper that also builds a fresh default client (directory.rs:960,1049,1111). Constructor injection alone therefore does not enforce this design's egress policy. Do not construct another SDK client, an HTTP directory/ranking client or standalone fetcher.

Implement bounded local selection using `cgka_engine::key_package_metadata`; do not add `nostr-directory` just for discovery. Founding requirements are fixed: Current profile, upstream default ciphersuite, advertised components covering the exact set below, current not_before/not_after validity, and credential_identity_hex equal to both signed event author and expected peer. Cross-check event tags against decoded KeyPackage metadata, including profile/ciphersuite/components, then rely on `create_group`'s engine validation of all founders. `invite_key_package_requirements` requires an existing live group and is not a founding-path runtime API; later member additions are outside Phase1. Verify the signed event before selection. Reject mismatching signer/credential identity, malformed, expired or unsupported candidates. Limits: at most16 candidates across the complete operation, 1MiB per wire frame, 4MiB aggregate admitted event bytes, and15s absolute discovery deadline (subject to the operation's earlier deadline). SDK acquisition item/byte/deadline limits must apply before collecting results, and the connector enforces the frame limit before decoding. Request one extra candidate to detect truncation; truncated/over-budget/incomplete acquisition fails this phase's deterministic discovery rather than choosing from a silent partial result. Query configured endpoints serially within the same aggregate budget; no unbounded parallel fetch. Select newest-valid with event-ID tie break. Empty/out-of-set source lists fail before any connector call. SDK item/byte limits count admitted event JSON per relay, not WebSocket/parser allocations: decrement one operation-wide item/byte/deadline budget across serial endpoints. Confirm the pinned SDK acquisition report and custom WebSocketTransport's pre-parser frame-size enforcement as explicit compile gates; a missing bound is a review blocker, never permission to call the default-directory path.

After `activate_transport`, the daemon drives adapter deliveries through `ingest_delivery(&TransportDelivery)`, maintenance, convergence, outbound publication retry and effects draining. It retains delivery ownership until the successful processing/persistence acknowledgment. Process every effects category: authenticated events, queued intents, pending convergence, transport reports, publication failures, unresolved publications, welcome failures, superseded intents and failed application messages. `left_object_unpersisted` cannot become a successful durable receive. `GroupEvent::MessageReceived` supplies authenticated sender account `MemberId`, optional leaf index, group, epoch, binary payload, message ID and authority/retention metadata; preserve those facts in Marmish's sealed received type. A leaf index is not a stable device identity, and phase1 makes no production device-pairing promise. Wrong-account delivery is rejected by runtime and remains an explicit negative test.

Advertise exactly `default_group_components()` (profile0x8001, admin-policy0x8003, lifecycle0x800c) plus imported `NOSTR_ROUTING_COMPONENT_ID`0x8004 on both peers through `SessionConfig.supported_app_components`. Explicitly exclude `ACCOUNT_DEVICES_COMPONENT_ID`0x800d: this phase requires one leaf per account, not self-extending multi-device groups. Phase1's one-day retention is **local journal retention**, so it does not advertise or supply group retention0x8005. CreateGroupRequest.app_components supplies `AppComponentData` for0x8004 using `encode_nostr_routing_v1(NostrRoutingV1::new(random32, configured_relays)?)`. Use public constants/types rather than numeric literals in code. Let `CreateGroupRequest.name/description` populate the engine-owned group profile; never override `GROUP_PROFILE_COMPONENT_ID` manually.

Phase1 rooms use `marmish/v2/<sessionhex32>` and description `marmish/v2 identity transport`. No new component ID is needed. A later reviewed Marmish purpose component can use upstream's application-owned range starting0xf000 (max4096-byte component payload), rather than claiming a protocol allocation. Phase1 has no command dispatcher, and ordinary DMs never become execution rooms.

Responder trust is an explicit per-identity foundation-peer allowset, or a specific pending `OpenConversation(peer)` expectation; there is no trust-on-first-Welcome. The live driver supplies Alice/Bob's exact peer expectations. Upstream autojoins Welcomes, so GroupJoined is a **provisional** engine result. Before projecting an accepted conversation or installing its route require `welcomer == Some(expected_peer)`, canonical membership exactly self+peer with one leaf each, the exact name pattern/description and fresh session, creator-only expected admin set, and exact required/forbidden component policy above. Read canonical membership, `admin_pubkeys` and `app_component` through runtime APIs. For a never-accepted unsolicited/wrong-welcomer/malformed room, `forget_group_local`, prove pending cleanup by re-listing, and only then acknowledge the pending GroupJoined via its `via_welcome` identifier. The approved retention amendment removes rejection-row allocation for these deterministic policy failures; accepted/revoked authority history and capacity-refusal decisions follow its separate durable rules. Do not generate an application receipt or expose the provisional group as trusted. If any step fails, retain the pending event/rejection state for retry.

Retain the accepted immutable conversation binding in the encrypted journal. Any later member/admin/profile/retention/disband change, or additional leaf including a same-account sibling, makes the conversation terminal `revoked`: commit the tombstone, remove routing, refuse new sends/projection and forget locally through supported APIs. Check canonical membership/components after relevant effects and before every application receive/send, since a sibling addition need not emit MemberAdded. Handle `AppMessageInvalidated` (LosingBranch, BeyondAnchor, BeyondAppRetention or UndecryptableInCanonicalState) by marking affected journal projections and their receipt evidence invalidated. A prior receipt means durable receipt at that time, not irreversible authority: an invalidated source cannot remain counted as current success. In live acceptance, invalidation before final drain/final report fails the affected exchange; later status surfaces the invalidation rather than preserving a false success.

### Exact foundation application envelope

Both message variants are encoded inside `MarmotAppEvent` with kind30100 and exactly one tag `["marmish","v2-foundation"]`. Content is canonical compact UTF-8 JSON with lexicographically sorted object keys and no whitespace/newline. Strict decode rejects duplicate/unknown/missing keys, noncanonical encoding, invalid UTF-8, invalid base64, wrong types and bounds. Each variant has exactly these top-level keys: `protocol`, `type`, `session`, `id`, `sender`, `recipient`, `body`. `protocol` is the literal `marmish-foundation/2`;  `type` is `message` or `receipt`; `session` and `id` are lowercase32-hex strings (12 timestamp characters followed by 20 random characters, except deterministic receipt suffixes); `sender` and `recipient` are lowercase64-hex account public keys. These names and discriminants are frozen before code.

For `type=message`, `body` has exactly `data`, standard padded canonical base64 of0..16384 decoded bytes. For `type=receipt`, `body` has exactly `message_id` (the received message's32-hex application `id`) and `payload_sha256` (lowercase64-hex SHA256 of decoded message bytes). Receipts have a deterministic `id` bound to the complete original message identity and payload digest, as specified in the approved retention amendment, and never generate receipt-of-receipt loops. Both variants require the same authenticated group/session/expected peer binding; the sender must match MLS and `MarmotAppEvent::validate_sender`, and recipient must be local. Reject wrong kind/tags and foreign-session data before projection. Receipt references must resolve to an exact journaled message from local sender to this peer in this group/session, with matching digest and noninvalidated source; arbitrary matching IDs in other groups do not satisfy it. Enforce32768 encoded content bytes and the transport frame bound. Dedup key is authenticated group+sender+application `id`; identical replay yields the existing result, while changed type/session/recipient/body is a conflict. Pure foundation decode returns untrusted data; only the adapter can seal `AuthenticatedMessage` after these checks. No execution opcode is recognized.

## Proposed Rust boundaries

Use one new `crates/marmish-native` crate with thin `marmish`/`marmishd` binaries and `identity.rs`, `transport.rs`, `mdk_adapter.rs`, `journal.rs`, `foundation.rs`, plus root-owned daemon/IPC/error modules. Reuse `marmish-vault` through its narrow namespace extension, not the execution engine. Avoid tiny abstraction crates or a general connector/provider framework. `identity` owns public named-identity records, key references, profile locking and verified Nostr identity loading. `journal` owns its separate SQLCipher connection and local application transactions; `mdk_adapter` owns opening upstream storage and serialized reconciliation. There is no cross-file engine/application atomicity claim. `transport` owns canonical destinations, immutable transport policy, Arti lifecycle and connection budgets. `mdk_adapter` owns upstream engine interactions and maps verified inbound content to `AuthenticatedMessage` containing verified account/device identities, group/epoch identifiers and application bytes. The daemon actor owns these modules. The CLI uses an owner-only0700 socket directory,0600 Unix socket and matching effective-UID peer checks (Linux SO_PEERCRED; macOS getpeereid). It may autostart the selected identity daemon under the same exclusive profile lock; racing starts yield one owner. Persistent OS service installation belongs to phase3. Choose a short owner-only runtime socket directory whose complete path fits macOS's104-byte sun_path including terminator; do not concatenate unbounded profile names. Bind it to the profile's immutable identity/lock and fail on collision or unsafe ownership. Serve Status/Subscribe through actor-published read-only snapshots/watch notifications so an in-flight network await cannot block IPC status; mutation still goes through the single bounded actor. The CLI receives public status and authenticated application results through that local IPC boundary; it never opens the MDK database or owns another copy of the daemon's engine state.

Proposed actor messages are `OpenConversation(peer, dedicated_purpose)`, `Send(conversation, message_id, bytes)`, `Receive/Subscribe`, `Status`, and `Shutdown`. Implement these actor operations through the confirmed runtime composition above; final Rust types wrap upstream types rather than exposing an independent engine. A sealed `AuthenticatedMessage` can only be constructed after upstream credential validation, group membership and Marmish application-purpose checks. Do not derive command authority from outer Nostr event author or NIP42 connection authentication. Phase1 application payload is a strictly versioned finite test/message envelope, not a shell instruction.

One service owns one identity and one lifetime lock. Multiple CLI connections share that owner. Two processes opening the same profile fail before opening its database or making network connections. Different named identities have distinct profile locks, Nostr references, storage keys, MDK state and Arti state/isolation context. One serialized actor/worker owns mutable MDK/store access; no concurrent CLI/daemon database access. Blocking storage and keychain work runs outside Tokio executor workers; do not hold async actor state locks across provider calls. Shutdown stops new admission, drains admitted sends/state transitions with a deadline, closes MDK/storage and only then releases the profile lock.

## Fresh named identities and keychain storage

Reuse `marmish-vault`'s native macOS Keychain/Linux Secret Service provider implementation and zeroizing secret/finite error patterns where useful; fresh v0.2 references and profile schemas are deliberately allowed to break compatibility. Do not preserve a v0.1 reference namespace or catalog merely because the helper currently validates it. Its public calls are blocking and have no built-in deadlines; use the existing Rust keychain helper protocol under bounded Rust supervision for provider prompts rather than assuming cancellation of a blocking task interrupts a native provider. Secrets travel through private pipes only, never argv, environment, logs, general error text or public JSON. MDK itself remains an in-process library; no wnd/Python broker is introduced.

Add explicit `Vault::open_namespaced(Namespace::MarmishV2)` and v2 KeyRef validation, retaining the old constructor only for the isolated legacy fixture. macOS services are `marmish.v2.nostr` and `marmish.v2.sqlcipher`; Linux exact item attributes include application=marmish, version=2, purpose and unpredictable reference ID. Extend the private helper protocol with an explicit validated namespace selector, never ambient environment; root uses one fixed hidden native binary helper entrypoint under bounded supervision (15s per provider operation, killed/reaped on timeout). Maintain existing8KiB request/128KiB response ceilings. Add test-only exact-reference deletion for items proven created by that test, not a production search/delete API. References bind namespace/version/purpose/backend and immutable ID, with no alias-based secret selection. Named profile manifests contain only public identity, versioned reference metadata and immutable profile identity binding. Automatically choose keychain when present for a new identity; unavailable may select an explicitly documented private-file backend. Locked, denied, missing, ambiguous or corrupt references never trigger regeneration or plaintext fallback. Phase1 creates fresh identities; importing an existing secret is a later explicit feature, not an automatic discovery/migration path. Identity initialization is a recoverable state machine under the profile lock: first atomically write/fsync an owner-only, versioned `initializing` manifest containing fresh unpredictable key-reference IDs, chosen backend and transaction ID but no secrets. Then create/read-back the Nostr secret, derive/record its public identity, create/read-back an independent random32-byte SQLCipher root, create the encrypted store, and atomically fsync/replace with `ready` only after an encrypted reopen and identity check. Crash recovery examines each exact reference: missing entries may be created only for an `initializing` transaction; existing entries must load/validate and are never replaced. An `Exists` result is verified by exact reference/read-back rather than adopted blindly. Locked/denied/ambiguous/corrupt items stop recovery. A crash after one secret therefore resumes forward instead of rolling back via a nonexistent vault transaction API. Failures retain the initialization manifest and exact references for diagnosis/retry; no search-based or unrelated-item deletion. A ready profile with a missing secret fails closed. Explicit cancellation/garbage collection of abandoned transactions is outside phase1; owned test cleanup may delete only exact items demonstrably created by that test through provider-specific test support. Private-file fallback uses the same ordering and0600 no-follow/create-new files; ready identity never silently switches backend.

No v0.1 migration or disk-format preservation is required: there is no installed-base compatibility obligation. Use fresh v0.2 profile, SQLCipher schema, reference formats, key-derivation domains and MLS groups. Preserve old state only as an explicitly isolated optional protocol fixture. Existing secrets/catalogs/databases are neither scanned nor adopted by v0.2. Future secret import or data migration would require its own explicit design, and is not a phase1 exit criterion.

## SQLCipher boundary

All durable secret-bearing MDK state and application message state are SQLCipher encrypted. No secret-bearing plaintext SQLite, exported in-memory snapshot, temporary dump or private-key JSON fallback is accepted. Retain owner-only directories/files and reject unsafe symlinks. Verify cipher_version and wrong-key failure before trusting schema. Key material is zeroized where owned; never include keys in PRAGMA text/debug SQL or diagnostics. Pin cipher settings and validate reopen behavior and sidecar encryption. Existing engine/cipher.rs is an audited fail-closed pattern, but private job-domain functions are not a reusable upstream MDK storage API; extract only a justified shared opener after dependency/storage contract review.

### Durable effects and reconciliation

Use upstream storage/fanout transaction machinery rather than a second engine or changes to MDK tables. Open one upstream `SqliteAccountStorage`, retain a clone of its shared-connection handle for actor-owned public `MessageStorage::list_pending_application_events`/`delete_pending_application_events`, and pass the other handle through `SessionConfig::with_storage`. `SqliteAccountStorage` derives Clone and its documented app/protocol handles share the connection; cloning does not open a second MDK database connection. All handle access remains serialized by the same actor. A separate Marmish SQLCipher journal connection/file stores application intent/projection rows; it never opens the MDK file. Derive both database keys from the independent random32-byte SQLCipher root using HKDF-SHA256, salt ASCII `marmish/v2/storage`, info ASCII `mdk` or `journal`, each32-byte output. Never use the root raw as a database key or reuse a Nostr secret for encryption; these domains are fixed v2 format decisions. No atomic transaction across these two stores is claimed.

For sending, construct `MarmotAppEvent` first: its constructor computes the NIP01 app_event_id before runtime send. Commit an application intent (random application ID, conversation/session/peer, exact encoded event bytes, precomputed app_event_id, payload digest and state prepared) before calling runtime `send`. Upstream owns frozen encrypted fanouts. Reconcile `PublishedApplicationMessage` effects into the journal idempotently, then call `acknowledge_published_app_messages`; a crash between commits causes a harmless repeated projection. On restart drive `resume_outbound_fanouts` before new sends. Reconcile prepared intents with `runtime.outbound_fanouts_for_group` and each fanout's `application_message().app_event_id`: an existing exact binding means resume the frozen artifact, never create a second one. Verify in the implementation that fanout staging precedes all exposure and that every fanout retirement path (including failed/superseded outcomes, not only successful acknowledgment) is journaled before losing its reconciliation evidence. Only under those invariants does absence prove never staged, permitting a send of the identical encoded bytes (not a new event/timestamp). If the supported APIs cannot establish this, preserve `uncertain` and require explicit retry with a new application ID; phase1 promises no exactly-once send or automatic uncertain resend. Group creation/Welcome publication likewise retain pending/uncertain state and reconcile upstream outcomes rather than silently creating replacement groups.

After encrypted open, rebuild trusted routes without networking, ready the RelayConnector (including Arti bootstrap for applicable routes), then call `runtime.drain()` before admitting new sends or subscription activation. `drain()` itself may publish/resume fanouts, so it is not a network-free replay step; connector failures remain finite publication/retry state under the same configured routes without fallback. Upstream hydrates pending events into that drain, including GroupJoined keyed by via_welcome. After draining and committing trust decisions, activate subscriptions. Dedup effects arriving both from ingest and restart drain. Acknowledge MessageReceived by message ID only after projection commit (including a durable rejection decision for untrusted content); acknowledge GroupJoined by via_welcome only after accepted/rejected decision commit. For receiving, commit an idempotent application projection keyed by authenticated group+message ID and bound peer/session before acknowledging/removing its upstream pending application event. Replay of that durable pending event after a crash deduplicates the same journal row; rejected/revoked tombstones also prevent restart resurrection; acknowledge only after successful commit. Reject same application ID with different peer/session/payload binding. Transport cursor advancement must not discard unpersisted application effects. An encrypted application receipt can be generated only after durable projection, and itself uses the same outbox. Do not equate relay acceptance with that receipt. Authority/retention side effects and incoming Welcome processing remain driven even if a publication fails.

Test every cross-store crash boundary. A phase1 restart reopens the same identity/group and exchanges fresh encrypted data without stale MLS rollback; uncertain outcomes are surfaced, never converted to success. No key rotation/migration promise in this phase. The confirmed public MessageStorage pending-event operations and retained shared-handle ownership must compile unchanged against the pin; lack of a supported replay/authority seam in actual integration is a review blocker, not permission for direct table writes or a fork.

## Transport policy and limits

The proposed default route mode is `auto` (onion through Arti, ordinary relays
direct), with explicit `always` and `off` modes. `always` routes every configured
relay through Arti; `off` refuses onion destinations. Failure never changes mode
or destination. In a mixed onion/ordinary relay set, `auto` intentionally permits direct delivery to ordinary configured relays; it is not a Tor-only privacy mode. Select `always` to route the entire configured set through Tor.

Configuration contains an explicit finite relay set and transport selection. Canonicalization happens once before connection creation. Direct mode accepts explicitly configured secure `wss` destinations. `ws` is allowed only for validated v3 onion destinations over Arti, never clearnet. `wss` over either path verifies hostname/certificate using pinned rustls/webpki Mozilla roots on every platform; no ambient trust/proxy override or insecure certificate switch. Onion destinations use Arti without system DNS. Any optional clearnet-over-Arti capability must retain end-to-end TLS and be explicit, not inferred. Reject credentials, fragments, ambiguous ports, invalid onion checksums and unsupported schemes. Do not inherit proxy environment variables as transport authority. No peer-supplied relay, key-package tag, restored state or retry can enlarge the configured set. URL path policy must be explicit and support the configured relay endpoint; do not inherit v0.1's root-only constraint accidentally.

Only `transport` can construct outbound relay connections; direct mode alone may invoke direct TCP/DNS. Arti mode supplies an Arti-created stream to the WebSocket handshake and cannot call the default direct connector on bootstrap/connect/handshake/TLS failure. Instrument connector/resolver seams to assert zero unauthorized calls. The custom SDK WebSocketTransport connect hook rejects a supplied proxy (`Some`) rather than accepting another routing authority. No hidden discovery/media/telemetry/QUIC clients are enabled. Arti's Tor guard/directory network connections are necessary infrastructure and are distinguished from application relay destinations; an exact relay allowlist is not an allowlist of all Tor IP connections.
