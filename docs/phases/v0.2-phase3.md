## Deliverable and existing boundaries

Install a complete native Rust product on Linux AMD64/ARM64 and macOS ARM64,
without Python, uv, Cargo, external wnd/MDK processes, namespaces or mandatory OS
confinement. A thin POSIX bootstrap downloads and verifies executables; Rust owns
installation and setup. Single-key c/s/b setup defaults to both, with no inbound
execution until execution grants exist. Same-platform installed command flows
are Phase 3 acceptance; full nine-pair direct/expanded Arti acceptance and
published benchmarks remain Phase 4. Installation alone proves neither.

Existing `crates/marmish-native/src/cli.rs` has named identities, explicit relays,
key-storage auto/keychain/file and offline `init`, but no install/setup commands.
`identity.rs` provides leased private profiles, transactional initialization,
independent Nostr/SQLCipher roots and a separate v2 keychain namespace. Both
native frontends already embed `_vault-helper` before runtime creation. Reuse
these implementations. Auto fallback is only for genuine provider unavailability;
locked/denied/error never silently switches storage or regenerates an identity.

Phase 2 proposes a native-package sibling `marmish-worker` using existing engine
worker_main and argv(root,jobhex), without a worker discriminator. It must exist
before qualification. This design does not approve or implement Phase 2. No
legacy profile/database migration or legacy architecture restoration is required.

## Proposed interfaces

```
marmish-install-0.2.0.sh [--prefix DIR] [--bin-dir DIR] [--asset-dir DIR]
                         [--quickstart] [--debug] [--help]
marmish install --source-dir DIR --manifest FILE --manifest-sha256 HEX64
                [--prefix DIR] [--bin-dir DIR] [--state-dir DIR]
marmish install --select-version VERSION [--prefix DIR] [--bin-dir DIR]
marmish install --status [--prefix DIR]
marmish uninstall [--prefix DIR] [--bin-dir DIR]
marmish setup [-i NAME] [--state-dir DIR] [--key-storage auto|keychain|file]
              [--debug] [--update] [--revoke NPUB...]
              [--trust NPUB...] [--untrust NPUB...]
marmish setup --non-interactive --role client|server|both --relay URL...
              [--tor auto|always|off] [--grant NPUB... | --no-grants]
              [-i NAME] [--state-dir DIR] [--key-storage auto|keychain|file]
              [--update] [--revoke NPUB...] [--trust NPUB...] [--untrust NPUB...]
              [--debug]
```

Local `--asset-dir` uses exactly the same embedded manifest digests and file
verification as HTTPS, not a verification bypass. Rust install never initializes
an identity, contacts a provider/network, or starts a service. Setup uses native
profile/configuration APIs, not a generated shell script. No replace flag exists.
Uninstall preserves all identity/config/database state and installed versions.

## Asset manifest and bootstrap trust

Publish separate per-target executables and `THIRD-PARTY-LICENSES`, avoiding any
shell archive extraction. Asset basenames are
`marmish-VERSION-TARGET`, `marmishd-VERSION-TARGET`,
`marmish-worker-VERSION-TARGET`, `THIRD-PARTY-LICENSES-VERSION-TARGET` and
`marmish-VERSION-TARGET.manifest`. Map manifest file names to those four asset
names by this fixed template; no metadata-supplied URL/path is executed or used.
The installed basenames are the four fixed names below plus `manifest`.

Manifest format 1 is ASCII, LF-terminated, at most 4096 bytes, with exactly these
ordered lines and one final LF. Uppercase tokens below are grammar variables:

```
marmish-manifest 1
version VERSION
target TARGET
commit HEX40
signing SIGNING notarized=BOOL
minimum FAMILY=MAJOR.MINOR
state profile=PROFILE journal=JOURNAL engine=ENGINE config=CONFIG commands=COMMANDS
file HEX64 BYTES 0555 marmish
file HEX64 BYTES 0555 marmishd
file HEX64 BYTES 0555 marmish-worker
file HEX64 BYTES 0444 THIRD-PARTY-LICENSES
end
```

`VERSION` is canonical `0.2.P` or `0.2.P-rc.N` with nonnegative P and positive N,
no leading zeroes except literal zero. TARGET is one of the three named triples.
HEX40/HEX64 are lowercase hex. BYTES is a positive canonical decimal; each binary
is at most 256 MiB, licenses at most 16 MiB, aggregate at most 784 MiB. PROFILE,
JOURNAL, ENGINE, CONFIG and COMMANDS are positive canonical decimal format
identifiers, in exactly that key order. Generate them from exported source
constants: existing profile=2, journal=3, engine=1; Phase 2 proposes config=1
and its command ledger's actual format N supplies commands=N. N is a design
placeholder, never literal manifest text or an invented schema number. Phase 2
must export its actual constant before manifest generation. Never derive state
formats from the package version. Install treats this line as informational;
runtime compatibility checks below enforce supported state.
GNU targets require FAMILY=glibc, SIGNING=none, BOOL=no; Darwin requires
FAMILY=macos, SIGNING=adhoc or developer-id, BOOL=no or yes. Adhoc with yes is
invalid. MAJOR.MINOR are canonical decimals. No CR, tab, leading/trailing space,
blank/unknown/repeated lines, extra files or missing end/final LF is accepted.
Modes above are final installed modes; source download modes grant no trust.

The release-specific script embeds VERSION and exactly three manifest SHA256s,
keyed by TARGET, generated only after signing/hashing all final assets. It
fetches the manifest first, applies the 4096-byte cap and checks its embedded
hash before parsing it. Shell and Rust implement the same grammar and share
positive/negative vectors. Native install revalidates manifest and every file;
the shell passes the verified expected manifest hash explicitly as a required
`--manifest-sha256 HEX64` install argument (also required for local assets).
The native CLI's metadata reports its compiled version/target; it must match the
manifest, as must the worker/daemon release build provenance. `SHA256SUMS` may be
published for humans but is not installer input.

For each fixed asset, download using HTTPS-only curl with a bounded deadline and
`--max-filesize BYTES`, check exact byte count, compute SHA256 and compare to the
manifest; never invoke a manifest-driven checksum `-c` or shell evaluation.
Checksum tools are sha256sum on Linux or shasum -a 256 on macOS. This protects
consistency with the script's trusted release channel, not publisher authenticity
against compromise of that script/channel. Signing/notarization are separate.

## POSIX execution and diagnostics

The entire bootstrap is inside `main() { ...; }`, followed only by `main "$@"`
on its final line, so an incomplete function download executes no installation.
Use `set -eu`, umask077, private mktemp, traps and quoted arguments; no `set -x`.
Missing/relative HOME or effective UID 0 fails in both shell and Rust. Both use
the same HOME environment value, not competing passwd/path conventions. Explicit
prefix/bin paths must be absolute. Needed utilities are sh, curl, uname, id,
mktemp, chmod, mkdir, rm, mv, cat, wc, tr, an exact-line parser such as awk, and
one checksum tool; macOS Rosetta detection additionally uses sysctl. No Python,
uv, compiler, jq, tar or shell product configuration engine is needed.

Select only Linux x86_64/aarch64 (documented arm64 synonym) or Darwin arm64.
Darwin `sysctl.proc_translated=1` fails with native-arm64-shell guidance; do not
mistake an x86_64 Rosetta shell for an unsupported physical machine. Unsupported
OS/architecture fails before install mutation. After full verification, chmod
only the staged CLI executable and run its native version/target probe. A
non-executable temp filesystem (exit126) gives TMPDIR guidance; exit127/loader
failure gives a finite incompatible_runtime diagnostic covering incompatible
libc/userland/loader. Do not claim those exit codes uniquely diagnose one cause;
retain bounded stage/exit code without emitting raw loader output. A failed
probe never attempts installation or key access.

Keep downloaded versioned asset basenames in the temporary directory; it must
contain neither `manifest` nor `.version-receipt.json`. The verified temporary
CLI therefore runs in development mode for both the version/target probe and
the install operation; the versioned manifest basename is passed explicitly.

Native install receives `</dev/null`; quickstart invokes the installed CLI with
`</dev/tty`. Native setup independently opens /dev/tty and verifies foreground
ownership, failing no_tty if unavailable. It must not consume remaining script
stdin. Debug is bounded records with fixed stages arguments, target, manifest,
asset_download, asset_verify, runtime_probe, install_validate, install_stage,
install_commit, install_recover, setup_choices, profile_open, config_commit and
complete; no raw arguments/environment/provider responses/config dump.

## Prefix isolation and canonical executable lifetime

Default prefix is `$HOME/.local/share/marmish-native` on both OSes, independent
of XDG_DATA_HOME. Default bin directory is `$HOME/.local/bin`. Native install
rejects a prefix equal to, within or containing the legacy prefix
`$HOME/.local/share/marmish`, or the default/configured v0.2 state root. Linux
state is absolute XDG_DATA_HOME/marmish/v2 or HOME/.local/share/marmish/v2; macOS
state is HOME/Library/Application Support/Marmish/v2. Apply containment checks
after safe existing-ancestor canonicalization and include any explicit state
root through a proposed install `--state-dir` option. Reject prefix/bin nesting
that overlaps version/state contents; bin_dir cannot be inside the prefix.
No installer operation traverses, opens or modifies identity/database contents.

At startup every native executable canonicalizes current_exe once, before
profile/provider access. Installed mode means either `manifest` or
`.version-receipt.json` exists in its canonical parent; both must then validate.
In that mode its canonical parent is
`<prefix>/versions/<version>-<target>/` with validated manifest and ownership
receipt. Use that canonical frontend path for the helper and its canonical
sibling marmish-worker for launches; never PATH, argv[0], or current again. In
an explicitly recognized development/Cargo layout use canonical current_exe and
canonical sibling worker under the same engine checks, without pretending it is
an installed/manifest-verified release. A malformed claimed installed layout
fails rather than falling back to development mode. Validate helper/worker
identities at startup and immediately before spawning under the reviewed engine
contract. Owner-controlled mutation is not an OS sandbox guarantee.

Check safe destination ancestors before creating even the prefix/lock, so a
group-writable home is rejected before installation mutation. Export the existing engine trusted-executable predicate as a narrow public API
(e.g. validate_executable_path -> canonical PathBuf); delegate to existing
trusted_worker_executable/ancestor checks, do not duplicate or weaken them.
Native install calls it on staged and final executable paths before activation.
Ancestors must be root/user-owned without group/world write, except the existing
root-owned sticky-directory exception. Failure is unsafe_install_path. Files
are 0555, licenses/manifest0444, populated version directories0755; private
staging starts0700. Validate final owner, regular-file/link count, no symlink
components and digests again. A group-writable home fails before activation.

Retain versions indefinitely: no automatic GC or prune in this phase. Upgrade
and rollback change selection only; running daemons retain canonical helper and
worker paths/inodes from startup. Uninstall removes owned launchers/current but
keeps versions and an inactive ownership receipt, printing the retained prefix.
A later prune operation requires separate review. Runtime performs read-only
supported-format checks for profile, journal, engine, config and command ledger
before opening upstream MDK storage-sqlite or any mutable schema initialization.
Derive/open only the required local keys and read-only metadata for this pass;
absent stores are initializable only after every existing store passes. Phase 3
owns this read-only preflight in marmish-native, using the format constants
exported by Phase 2; this requirement does not reopen Phase 2 or assume those
preflight APIs already exist. A proven unsupported version maps to incompatible_state, including the
existing journal_schema/engine version-mismatch cases; distinguish version
mismatch explicitly instead of relabeling arbitrary StorageFailure/corruption.
No older upstream migration may run before these checks. A release changing
upstream storage incompatibly must bump its product compatibility format so
the preflight rejects it. Read-only probe failure is fail-closed without repair
or schema/data writes. Do not infer downgrade safety from executable rollback.

## Installation transaction and recovery

A mere valid manifest does not prove an existing directory belongs to this
installation. Adopt no version, staging directory, launcher or selector without
this installation's durable ownership evidence. First use requires a nonexistent
prefix created exclusively, or an existing empty owned safe directory. One
precise crash-recovery exception counts as empty: its only entries are a user-
owned regular single-link 0600 `.lock`, plus optionally one reserved
`.marmish-native-install.json.tmp-<hex32>` regular single-link 0600 user-owned
file. Under the lock, validate that exact entry set, unlink only that reserved
temporary receipt without interpreting its contents, fsync prefix and write the
initial receipt durably. This covers a crash after mkdir/lock or during first
receipt writing. Any other entry or unsafe file fails without cleanup/adoption.
Create/hold `<prefix>/.lock` safely. All metadata reads use nofollow, owner/mode,
regular-file and size checks; directory operations are relative to held validated
handles. Parent-directory fsync follows durable creates/renames. No recursive
cleanup is allowed from an arbitrary metadata path.

The authoritative receipt `.marmish-native-install.json` is bounded 8192-byte
strict JSON with exact fields:
`format:1,install_id:HEX32,prefix:ABS,bin_dir:ABS,generation:U64,active:null|ID,
launchers:[NAME...]`.
ID is exactly VERSION-TARGET. Initial generation0 has active null and is durably
written with launchers=[] before an install transaction. It is also the retained inactive receipt
after uninstall, enabling safe reinstall and ownership verification of versions.
Supported format/generation bounds fail closed. Receipt binds canonical paths;
changing bin_dir is out of scope. Existing launcher paths are allowed only when
they are exact owned symlinks to this receipt's `<prefix>/current/<name>` and
were recorded as created by this installation. Legacy shell launchers and all
other existing objects produce unrelated_launcher; offer --bin-dir or the
separate pinned legacy uninstaller. No replace option.

Before staging, durably write `.transaction.json`, exact fields
`format:1,install_id,txid:HEX32,operation:install|select|uninstall,previous_generation,
next_generation,previous_active,next_active,previous_launchers,next_launchers,
manifest_sha256:null|HEX64,
staging:null|BASENAME,created_launchers:[NAME...]` (8192-byte limit, strict schema).
Previous values must match receipt; next generation is previous+1; names are
only marmish/marmishd, unique and in that order. Previous launcher set must match
the receipt; next is both names for install/select and empty for uninstall.
Created launchers are exactly the next-set paths absent at transaction start;
they can include a recorded launcher deleted by the user. Staging is exactly
`.staging-<txid>`. Record planned new launchers before creating them. A select
transaction may recreate a missing recorded launcher exclusively after rehashing
the selected version; it never replaces an unexpected existing object. Without
a transaction, status reports a missing launcher and advises select. During
recovery, a previously recorded missing launcher may similarly be recreated
only when absent, or accepted when its owned symlink is exact. Validate both launcher destinations before
any selector change. An upgrade does not replace its existing fixed symlinks.

Commit ordering under the lock is:

1. Persist transaction; exclusively create its staging directory. Copy fixed
   files/manifest, fsync each, rehash, apply final modes and validate executable
   paths. Keep staging directory0700 through this step. Write
   `.version-receipt.json`, a strict JSON regular single-link 0444 file capped
   at4096 bytes, with exact fields `format:1,install_id:HEX32,txid:HEX32,id:ID,
   manifest_sha256:HEX64`; then fsync staging. Its paths/IDs must agree with the
   enclosing transaction and manifest, never supply another directory name.
2. Rename to versions/ID without replacement using Linux
   renameat2(RENAME_NOREPLACE) or Darwin renamex_np(RENAME_EXCL), not plain
   rename(2); lack of that primitive is a finite unsupported-install error.
   Set the now-owned final directory0755 and fsync it and versions before any
   activation. A crash after rename but before chmod retains a complete owned
   unselected version; an explicit retry may finish its checked mode. An existing ID is
   usable only on an explicit install/select request, with this installation's
   exact version receipt, manifest and complete matching bytes. Recovery alone
   never adopts an unreferenced version. Otherwise fail version_conflict; never overwrite.
3. Create any missing recorded/first-install launcher symlinks exclusively (fixed targets); fsync
   bin_dir. Persist transaction evidence before each creation as above. Create
   the exclusively named `.selector-<txid>` temporary relative symlink to versions/ID and
   atomically rename over verified owned current; fsync prefix. For uninstall,
   unlink only the exact verified selector/launchers; preserve versions.
4. Atomically replace the authoritative receipt with next generation/active/launchers and
   fsync prefix. **This receipt is the commit point**, not current or a launcher.
   Clear the transaction only after verifying receipt, selector and launchers.

Metadata replacements use exclusive single-link0600 temporaries with fixed
templates `.transaction.json.tmp-<hex32>` and
`.marmish-native-install.json.tmp-<hex32>` in the owned prefix. Before another
transaction, remove only safe regular owner-only files with those exact
templates after establishing the authoritative receipt/transaction, never by a
broad prefix glob. A partial transaction temporary is not a committed
transaction and cannot authorize a stage. An existing transaction identifies
its exact `.selector-<txid>` temporary; recovery removes it only if it is the
expected owned symlink to next_active. Otherwise preserve/fail. This keeps
metadata-write/selector-temp crashes from creating unexplained adoption rights.

Recovery always runs under the lock before another operation. If receipt is at
previous generation, roll back selector to previous_active (or remove the exact
owned new selector when previous_active is null), remove only the transaction's
exact newly created symlinks, and restore any exact owned uninstall links. If
receipt is at next generation, finish/check next_active and owned links. Receipt
at neither generation, malformed metadata or unexpected object means
install_recovery_required; do not guess, delete unrelated objects or activate a
version based on its own manifest. Rehash an active version before recreating
links. A durable transaction itself proves partial staging ownership when its
exact `.staging-<txid>` is a non-symlink user-owned0700 directory, even before a
version receipt exists. Cleanup examines only the fixed basenames marmish,
marmishd, marmish-worker, THIRD-PARTY-LICENSES, manifest and
.version-receipt.json. Each existing entry must be a user-owned regular file
with link count1 and mode in {0600,0555,0444}, opened nofollow; remove only those files, then rmdir and fsync
prefix. No recursive walk, arbitrary temporary names or wildcard deletion. Any
other entry/type/link/ownership/mode means preserve and install_recovery_required.
An absent staging directory is already clean. A partial staged receipt is just
one removable regular file under this cleanup rule; its contents are never
adopted as ownership proof. Final versions always require a fully valid matching
receipt. The pre-receipt copy crash is recoverable
through this exact rule; unrecorded staging is never adopted or deleted.
Complete unused versions remain retained. Current may temporarily differ from
the old receipt before crash recovery; each selected executable set is already
complete. Installation success is reported only after durable commit/recheck.
The ownership model does not defend against a malicious same-UID process that
can modify all installation files. Recovery may remove an identical owned
symlink recreated by that user after a crash; this limited same-UID race is
accepted. It still never replaces/deletes a different unexpected object.

## Setup configuration, authority and repeat behavior

Use Phase 2's exact config.json version1 fields:
`version,role,relays,tor,trusted_remotes,execution_clients,command_policy,cwd,limits,aliases`.
Do not add inbound_enabled. Both with execution_clients=[] means no new inbound
execution; historical jobs remain recoverable under Phase 2's engine union and
current-grant network gating. Setup acquires the same exclusive profile lease
before initialization/config reads and holds it through atomic config commit.
If a daemon holds it, return identity_in_use with no mutation; configuration is
restart-only, not hot reload. No autostart/service manager installation here.

Prompt via /dev/tty for identity name (default default), `[c]lient/[s]erver/[b]oth`
(Enter b), explicit relay(s)/Tor mode and optional execution grant npubs. For
client/both, separately prompt for outbound trusted server npubs (empty allowed,
with guidance that outbound commands require trust first). Single
letters suffice; arrow keys are optional. Native parsers validate all values.
Print public npub/backend only. No public relay defaults or implied shell grants.
Empty grants with server/both are valid and explicitly reported as disabled.
Noninteractive server/both requires --grant or --no-grants; conflicting options
fail. For client-only neither option is required, --grant is rejected, and an
optional --no-grants is only an assertion of no inbound grants (never revocation).
Outbound trusted_remotes are separate explicit choices; a grant does not
automatically authorize outbound execution or silently change transport trust.
Bind to Phase 2's separation: execution_clients authorizes inbound command-room
admission/execution independently of outbound trusted_remotes. Setup must not
add granted clients to trusted_remotes automatically. This mapping requires
confirmation in the approved Phase 2 contract; any change reopens this design
instead of being guessed during implementation.

Initial creation uses the Phase 2 default policy/limits/cwd/aliases constructors.
Existing command_policy, limits, aliases and cwd are never changed by setup.
Identical requested fields are a no-op. A changed role, relays, tor or trust/grant
field requires --update and changes only explicitly named fields. --grant adds
principals; absence never removes existing grants. Explicit --revoke removes
named execution principals, requires --update, rejects overlap with --grant and
does not remove outbound trust. --trust adds only outbound trusted_remotes;
--untrust removes only named outbound remotes. Both require --update on an
existing config, are disjoint from each other, and never edit execution_clients.
An interactive update uses the same explicit additions/removals rather than
treating a blank prompt as deletion. --no-grants on an existing nonempty grant set is
not implicit revocation: reject with explicit --revoke guidance. Preserve
unmentioned fields semantically and persist only after full validation. Effective
restrictions remain Phase 2 additive defaults/per-key policy, not last-entry
replacement. Enabling inbound later is an explicit grant/config operation.

Secrets/config directories0700, files0600; fsync atomic config replacement.
Interrupted/provider-failed setup preserves old configuration and transactional
identity semantics. Named repeat keeps npub and secret references. Linux needs
an available unlocked user Secret Service/session bus. On macOS an ad-hoc
upgrade or rollback may return keychain_locked_or_denied because creator access
is code-identity dependent. Never regenerate/switch to files; offer rollback to
the creating version or re-authorization in a GUI session, with no promise the
current no-UI provider performs that re-authorization itself. Record actual
create/upgrade/load/rollback/load results by signing kind on a disposable owned
keychain. Rollback-to-creator access is a required qualification, not a source
assumption. Stable Developer ID continuity likewise needs actual evidence.

Finite setup/install errors include no_tty, identity_in_use, invalid_relay,
invalid_grant, config_invalid, config_exists, keychain_locked_or_denied,
keychain_failed, incompatible_state, incompatible_runtime, unsafe_install_path,
unrelated_launcher, version_conflict, install_recovery_required and interrupted.
No raw secret, private provider reply or arbitrary exception string is public.

## Platform qualification and Cargo route

GNU releases declare measured minimum glibc and dependencies for every binary.
Inspect ELF NEEDED and highest GLIBC symbol version; allow only qualified libc,
libm, libgcc_s, loader and pthread/dl where present. An unexpected dependency
blocks publication. Test on each declared oldest userspace/architecture. Initial
Ubuntu24.04-built candidates declare glibc2.39 unless a deliberately older build
and execution gate proves another baseline. Bundled SQLCipher/OpenSSL does not
make the executable static. Musl is unsupported until separately qualified.

Set MACOSX_DEPLOYMENT_TARGET=15.0 for initial candidates, verify Mach-O minimum
and actual dependencies and execute on macOS15 ARM64. Sign all Mach-O files
before hashing and require codesign --verify --strict after installation. Publish
ad-hoc/Developer ID/notarization status honestly; source build success is no
notarization proof. Preserve versions needed for keychain and detached workers.

Optional source installation is `cargo install --locked --git
https://github.com/Epiphytic/marmish --tag v0.2.0 marmish-native`, conditional on
Phase 2 placing all three binaries in that package. It uses canonical sibling
resolution and is not a managed-prefix install or a crates.io publication claim.
Validate this exact route from a clean Cargo environment before advertising it;
otherwise mark it unavailable. Binary users require no compiler or Cargo.

## Acceptance, fault coverage and publication

Use separate native workflows and `scripts/install-native.sh`; release asset
`marmish-install-0.2.0.sh` is generated from that source and embeds final manifest
hashes. Leave scripts/install.sh, release.yml and installer-validation.yml intact
until reviewed native qualification/publication, and retain a pinned legacy
route thereafter. Use v0.2.0-rc.N/v0.2.0 tags, not a legacy experimental-pattern
tag; test legacy release selection skips those tags. No default head-script
switch before all v0.2 assets are verified publicly available.

Native CI uses immutable action pins and candidate local assets on concurrent
ubuntu-24.04, ubuntu-24.04-arm and macos-15. Trigger on installer/packager,
native/vault/worker and Cargo changes. Test HTTPS downloads separately after
publication and before README/Iris channel changes. Strip API credentials from
product children. Keep bounded sanitized reports and failures, never skip a
failed runtime gate. Required coverage:

* Run shell syntax/strict manifest vectors, platform/root/Rosetta rejection,
  missing/relative HOME, missing/truncated/extra/duplicate assets, exact size/hash
  mismatch, loader/noexec errors and no-tty quickstart. A truncated bootstrap
  must perform no install.
* Under env -i with disposable HOME and explicit utility-only PATH, prove python3,
  uv, cargo and rustc are unresolved; install then use installed CLI/helper/worker.
  Keep macOS's Python shim outside PATH. Inspect real executable formats and
  dependencies; do not call a script a native binary.
* Check spaces, symlinks, unowned/group-writable ancestors, legacy/unrelated
  launchers, concurrent installs, repeat/version conflict, upgrade, rollback,
  uninstall/reinstall. Hash legacy/v2 state trees before/after: unchanged.
* Fault injection must not enter the release feature graph. A dedicated test
  harness terminates owned installer children at deterministic transaction
  boundaries using a private test-only synchronization seam. Cover every
  receipt/transaction/fsync/rename/unlink boundary, including prefix/lock before
  the first receipt, partial initial receipt, partial copied staging without a
  version receipt, partial version receipt and selector temporary, first install/upgrade/select/
  uninstall, and ambiguous/unowned recovery objects. Recovery gives previous
  or complete next selection, preserves unrelated files and never adopts based
  on a manifest alone. Ordinary install failure must restore previous selection.
* Controlled PTY c/s/b/Enter, noninteractive mode, named npub reuse, exact repeat,
  explicit update/revoke/trust/untrust, unchanged restrictions and independent
  inbound/outbound trust, client-only setup followed by a real same-platform
  command without hand-edited config, setup while daemon holds
  lease, interrupted config commit and visible unavailable-only file fallback.
  Real remote attempt with empty grants is rejected without worker creation.
* Disposable owned provider qualification includes macOS create/upgrade/load/
  rollback/load for each signing kind. Ordinary CI explicitly uses file storage;
  no ambient keychain access. Scan arguments/environment/debug/report artifacts
  for test secret roots/nsec without printing a matching secret.
* Real installed same-platform commands through Marmot on all targets validate
  binary argv/stdin/stdout/stderr/exit, authorization, disconnect/reconnect and
  detached-worker survival. Start daemon/long worker, switch installed version,
  prove old canonical helper/worker inodes are retained, restart and recover exact
  output/exit. Rollback with an unsupported synthetic state-format declaration
  gives incompatible_state with byte-identical databases; never write upstream
  tables or imply arbitrary downgrade safety.

Publish only complete candidate assets after actual code/evidence review and
scoped experimental-release authorization. Record source/lock/features/toolchain,
licenses, format support, platform baseline and signing. Verify GitHub assets,
both source mirrors and Iris availability before changing public quickstart.
Partial publication is a reported Beads blocker. Phase3 exits only with honest
all-target installed/setup/command evidence and reviewed Cargo-route disposition;
conditional design approval attests no implementation or acceptance result.
