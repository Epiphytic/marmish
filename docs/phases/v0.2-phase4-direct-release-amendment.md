# Phase 4 direct release acceptance amendment

Status: [actual Claude round 2 APPROVED](../reviews/v0.2-phase4-direct-design-r2.md),
with its nonblocking clarifications incorporated below. Implementation and release
acceptance remain separate gates. This updates the accepted Phase 4 design for the user's
optional Tor scope and the newer reviewed Finish/count-exit protocol. Existing
byte, recovery, authority, artifact-binding, bounded workload, cleanup, provider,
performance and publication requirements continue to apply.

## Required runtime and installed matrix

The required cells are Linux AMD64, Linux ARM64 and macOS ARM64 clients against
each of those three server platforms, nine direct-relay cells. Tor command cells
are experimental evidence only and cannot block v0.2. Every installed product
process is one of the three native Rust binaries; Python, uv, Cargo and rustc
must not be available through its runtime PATH. Build tools may compile the
separate Rust acceptance driver and fixture before that boundary.

Each platform job owns a separate client identity/profile and server identity/
profile. This avoids a self-DM on the same-platform cell while exercising named
identities and one account owner per service. Setup first creates both local
identities offline; initial server setup uses both mode with no execution grants
and therefore no enabled inbound execution. The job publishes only immutable
run/attempt/source-bound public identities. After receiving the complete public
identity set, setup updates each server to grant all three client identities and
each client to trust all three servers. Private keys never leave their jobs.

The three platform jobs run concurrently, each retaining its own server while
its client connects to all three remote servers. The existing immutable artifact
rendezvous mechanism must not require a producer job to end before readiness is
available. Every rendezvous and result is bound to the same source, attempt,
platform, candidate digest tuple and fresh run nonce. Missing, conflicting,
foreign or stale artifacts fail; no latest-release lookup occurs inside jobs.

Qualification and publication have this exact order:

1. Run the installed matrix using the reviewed candidate bootstrap and pinned local asset directory.
2. Publish those immutable versioned assets only after local-asset qualification passes.
3. Commit the generated pinned native bootstrap as scripts/install.sh to both mirrors, synchronize Iris and verify both source URLs return identical bytes.
4. Run actual HTTPS installation through each URL on all three platforms against the same immutable assets. No latest-release selection is allowed.
5. Cut over README/quickstart only after HTTPS qualification passes. If it fails, revert the bootstrap commit on both mirrors to the previous default, verify both external bytes, preserve candidate evidence, and fix/requalify a new immutable candidate.

The published version string is exactly the qualified one: an rc cannot be relabelled 0.2.0 without rebuilding and repeating qualification. The installer must report
0.2.0 (or the explicit reviewed 0.2 prerelease), all three binaries must report
matching version/target/commit/formats, and a v0.1 result or fallback is failure.
The runtime contract includes the installed launchers, managed immutable version
layout and the actual setup flow; bypassing those with target/release executables
is not installed acceptance.

## Finish count and protected cleanup

The newer server-limits design allows a max-commands server to exit after its
Nth confirmed Finish and complete native source acknowledgements. Such ordinary
exit does not prove engine quiescence or authorize removing engine state. The
general rule for EVERY protected-cleanup cohort is admission ceiling = planned
admissions + 1, including benchmark (5 for 4), recovery (3 for 2) and policy
(2 for at most 1). Zero-grant runs without max-commands, which requires a grant.
The matrix uses ceiling 4 and expects exactly 3, one from each client.
It has an explicit finite uptime, at most 30 minutes, and reserves cleanup time
within that original uptime. A fourth or any unexpected invocation fails the
rollup; it cannot be ignored merely because the configured ceiling is four.
The ceiling detects rather than prevents an unexpected admission. If that extra
admission triggers auto-exit, the run is red and state is preserved; no guard is
inferred. Read the COMPLETE ledger by cursor, including unexpected rows.
A recovery restart always retains the SAME TOTAL ceiling, never remaining credit
or admitted-so-far. The budget is durable across process lifetimes. Its uptime
is only original-deadline minus restart time, never an extension.

After all three exact client terminals and matching fixture receipts are bound,
the supervisor obtains cached evidence/counts, explicitly prepares cleanup,
checks the new fence for every ledger row, and performs the existing bounded
protected removal while the actual child remains alive holding CleanupGuard.
It then obtains the same-fence quiescent reply and requests ordinary stop,
checking actual joined shutdown flags. Failure cleanup explicitly cancels only
its own known fixture rows; unknown launch or missing child proof preserves
private state and fails the run. No expiry/disconnect cancellation is introduced.

A separate required auto-exit wave runs as three concurrent 55-minute platform
jobs after the primary matrix wave, with three distinct local client profiles
on each platform targeting that platform's fresh server. This tests actual
three-identity Finish accounting on every platform without another inter-job
identity barrier. It uses max-commands 3 and a fixed 20-minute server uptime.
Install/three offline client and server setup takes at most 10 minutes; grants
are installed before launch. Launch-to-ready is capped at 150 seconds; workload
is capped at 6 minutes, leaving 90 seconds for Finish/native publication and exit.
Before launch require the remaining budget through minute 50 fits its full
20-minute uptime, 9.5-minute cleanup instance and stop, plus the final 5-minute
job margin. Require natural exit 0 within 10 minutes of launch, with
no supervisor Stop/signal sent and at least 10 minutes before uptime expiry.
Thus an ordinary uptime exit cannot masquerade as count success. Each client
records exact terminal bytes immediately; a missing Finish acknowledgement is
only diagnostic and cannot suppress its terminal artifact. The actual server
exit and complete ledger/fixture results cover Finish; matrix cleanup evidence
need not add a fabricated finished field.

The three local clients still execute through the explicit direct relay, never
local IPC as a substitute for Marmot. If count exit is missed at L+10, mark red,
wait for the original L+20 uptime exit (no deadline extension), then run the same
required cleanup-instance procedure; a failed workload cannot become green.

Cleanup is required. Before starting the separate cleanup instance, check the
remaining budget through minute 50 can fit its 150-second activation, a 6-minute cleanup
reserve and 1-minute stop/reap. Start with max-commands 4 (above durable count 3)
and at most 10-minute uptime, never resetting counts. Freeze launch and expiry;
obtain the complete ledger, explicitly prepare, refresh every row under a new
fence and require exactly the three planned admissions at that fence. Grants
remain unchanged; any admission during the short open window fails the run.
Perform protected removal while the owner holds CleanupGuard, verify same-fence
quiescence, then ordinary stop/reap. Failure, insufficient time, unknown launch
or missing guard preserves state and records a red cleanup disposition; never
remove it using exit 0 alone.

## Other retained gates

The native fixture is the only granted executable, at an absolute canonical
owned path. Its independent receipt binds the run nonce, client marker and exact
input/output hashes. Client bytes and server ledger/fixture observations must
agree independently. Tests include quotes, dollar/backtick syntax, newlines,
Unicode, non-UTF8 Unix argv and all 256 byte values in finite stdin, independent
stdout/stderr and remote exit 7. Startup zero grants, additive default/per-key
restrictions, malformed/unauthorized traffic, immutable retry/conflict and
running-job recovery remain separate bounded cohorts as already designed.

Publish cold wall time and verified output goodput per directed pair. Use a
separate fresh same-platform benchmark cohort for one cold and three warm
observations; do not consume the three-command matrix cohort's admission budget.
Report sample counts and platform/relay/byte counts; nine single samples do not
establish tail percentiles. No warm result may silently reuse a failed run.

The resolve job generates the fresh run nonce once and pins it in the candidate
binding alongside source, run ID/attempt, manifests and per-role nonces. Public
identity setup/grant/trust updates finish BEFORE any server daemon launches,
within the original 10..15 minute identity barrier; no setup runs under a live
profile lease. Missing the barrier fails before command admission.

This amendment explicitly supersedes the base Phase 4 Arti cells and T-waves,
onion owner/Arti predecessor, 9+5 rollup, approximately 600-minute schedule,
max-commands equal to expected admissions, closing admission by lowering its
ceiling, and recovery remaining-credit restart clauses. Tor experiments use
separate non-gating jobs/reports. The six direct waves consume about 330 minutes
plus builds, retain cross-wave barriers and at most three concurrent platform
jobs. This explicitly replaces phase3-release-entrypoints default-head wording
at lines 35–38 and item 5: public head temporarily serves v0.2 between bootstrap
publication and HTTPS qualification, with rollback required on failure. Published
assets are never overwritten; failed candidates consume their version, and fixes
use a new rc.N or patch version. Required direct waves retain their existing
55-minute bounds plus the explicitly scheduled auto-exit wave above.

Final acceptance requires completed code review, all required installed cells,
all retained negative/recovery/provider/cleanup gates, sanitized evidence and an
always-run strict rollup. Promote only the exact qualified native release after the ordered asset,
bootstrap and HTTPS gates above. Publication, bootstrap switch and README
cutover remain separate recorded actions; a successful build is not a
release or an externally working installer.
