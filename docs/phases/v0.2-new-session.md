# Native v0.2 explicit fresh command sessions

Status: APPROVED by [actual Claude round 3](../reviews/v0.2-new-session-design-r3.md).
Implementation and runtime acceptance remain separate gates.
Beads: `marmish-2y4`. This completes the explicit `--new-session` requirement
in the approved Phase 2 plan. It supplements the local-client amendment, whose
"no automatic new-session creation in this increment" limit did not defer the
explicit user option. No wire format or execution authority changes.

## Behavior and interfaces

`marmish --new-session npub@relay -- /absolute/command ...` opens a fresh,
independent command MLS group with the same explicitly trusted remote. Without
the flag, existing verified default-client-room reuse remains unchanged. Both default
selectors (readiness and opening) skip every session recorded in the preparation
table, irrespective of marker peer/relay values; a fresh-first profile therefore
creates its first ordinary room on the next unflagged command. A later ordinary
command never silently selects a fresh room based on random group-ID order. The flag is
valid only with a new remote command, including detached submission; reject it
with local handle/status/wait/output/cancel/list, setup, daemon and administrative
subcommands before autostart, identity access or network work. It does not take a
session ID, key, group ID or authority value from the user.

Add `new_session: bool` to `command_cli::Action::Submit`. Before its existing
Prepare loop the CLI generates one timestamped random preparation token for a
flagged invocation. Freeze `CommandPrepare {remote, relays, fresh: Option<String>}`
once; all socket retries send exactly that token. Missing `fresh` decodes as None
for existing local callers. A present token must be canonical timestamped Id;
it is only an idempotency locator, never an MLS key or caller-selected session.
The daemon generates the actual session using existing `foundation::fresh_id`.
Existing command handles, Submit bytes, wire session binding and later status,
poll and consume calls are unchanged. However, the first Submit readiness gate
must check its exact session: accept only the currently selected ready default
room OR a preparation-bound fresh session for the exact peer/relay digest, with
actual context and native control-work drain checks. The default session must
equal the current default selection; a fresh session must be marker-bound. No
other unreserved room session is accepted.

`command_local` checks exact normalized configured relay-set equality and current
outbound role/trust before reading or allocating preparation state. The profile
lease and journal identity bind the local account. Persist a relay-set digest
SHA256(serde_json encoding of the normalized sorted URL string vector), computed
only after exact current profile-policy equality. This prevents a token being
rebound after a daemon restart with changed relay configuration. A token's stored
peer and relay digest must match the request; changing peer is a finite refusal, even if both peers
are trusted. Direction is always Client. Recheck current trust and actual native
room membership/purpose/authority before every Ready response. Revocation never
causes an automatic replacement group.

## Durable preparation and native atomicity gap

Current room creation discovers, calls native create_group, accepts the actual
room into the journal, then projects effects. Native creation and journal room
acceptance are not atomic. Existing orphan reconciliation deletes unaccepted
groups; adopting an orphan as authenticated creation is outside this amendment.
Existing foundation outgoing/queued_bindings records require a real group and
publication, and command_rooms require authenticated accepted authority. None
can represent a pre-creation idempotency fence without weakening its contract.

Add `command_preparation.rs` as a journal child with one bounded table:
`command_preparations(token BLOB PRIMARY KEY, peer BLOB NOT NULL,
relays_sha256 BLOB NOT NULL, session BLOB NOT NULL UNIQUE)`.
Every token/session is exactly 16 bytes; peer and relay digest are exactly 32,
enforced by SQL CHECK constraints and typed reads. No keys, argv, stdin, output
or relay credentials are stored. There are at most 4096 permanent rows per
profile, including failed/uncertain creation attempts. The marker limit is
4096 attempted explicit fresh preparations over the profile lifetime; retention
expiry does not reset it. Existing active-room cap 64 and total-room metadata
cap 4096 remain enforced independently. There is no ordinary room retirement:
successful fresh rooms consume the 64 live-room slots for the profile lifetime,
shared with default and inbound server rooms. In practice successful fresh
sessions are limited to 64 minus those other rooms; authority revocation/forget
is not a user-facing retirement workflow. Active capacity refuses further fresh,
new default-for-other-peer and inbound rooms with command_room_capacity. Reuse
of an existing valid default room remains available. The 4096 marker cap mainly
bounds failed/uncertain attempts. A capacity failure is finite; there is
no automatic eviction/GC or reset recipe that would destroy existing identity,
jobs or replay fences. Ordinary default-room reuse remains available at marker
capacity. Supporting a future safe marker GC is outside this change.

Bump native journal format from 5 to 6, accept old supported formats for forward
initialization, and report 6 through the existing compiled release-info constant;
preflight must refuse unsupported rollback. No Python-format compatibility is
promised. Journal API is actor-only:

* `command_preparations_init()` creates the table.
* `command_preparation(&token,&peer,&relays_sha256)` returns an immutable
  `Option<CommandPreparation {session:Id, peer:Account, relays_sha256:Digest}>`, or refuses a binding mismatch.
* `command_preparation_session(session)` returns an optional full preparation
  binding for ANY marker owning that session, for default-room exclusion and
  exact-peer/relay-digest fresh Submit checks.
* `command_begin_preparation(token,peer,relays_sha256,session,now)` atomically
  returns `PreparationStart::Created(record)` or `Existing(record)` under one
  transaction. An exact existing token returns its original session before new
  freshness/capacity checks; wrong peer or relay digest refuses. For a new token,
  reuse existing `command_store::freshness(conn,id,now)` for both token and
  daemon session through a visibility-only private-to-pub(super) change. Enforce
  active-room/total-room/4096-marker caps and session uniqueness before INSERT.
  A successful INSERT is the durable one-time creation fence. Only Created
  permits native create_group. There is no reserved-but-unattempted state,
  separate CAS update, or marker allocation during Prepare polling, queue-full,
  start-by expiry, discovery failure or other pre-create validation failure.

Every row means attempted; retain it permanently even when native creation never
starts after the commit. A marker is not a room, peer admission, command admission
or execution grant. Canonical token validation occurs before queue admission.

Ready lookup for fresh prepares selects only the stored session, exact peer and
Client direction, then applies existing command_context authentication and
retained Welcome/publication drain checks. It must never fall back to another
room. Lookup includes revoked room metadata or otherwise refuses attempted
missing sessions; it must not treat revocation as permission to allocate.

Room-intent FIFO/outcomes become keyed by `(remote, fresh_token)`; ordinary None
retains peer coalescing. Preserve eight queued intents, eight finite outcomes,
60-second outcome cooldown and the 15-second bounded actor turn. Ordinary
start-by remains arrival+60 seconds. Define shared `FRESH_PREPARE_SECONDS=60`
and `ROOM_TURN_SECONDS=15` constants. The CLI freezes its fresh observation
deadline with the token once; its monotonic budget cannot be extended by retry.
At first enqueue, compute remaining token-epoch window against current time,
clamp to at most 60 seconds, reserve the full 15-second turn, and set fresh
start-by to arrival + remaining - 15 seconds. Expired/insufficient windows refuse
without enqueue or marker. Repeated probes never renew this deadline, and the
actor rechecks start-by immediately before beginning discovery/creation. A future
within-policy token cannot extend the first-arrival bound. Thus no fresh turn
starts too late to finish within the CLI's original 60-second window; no creation
starts after that window. This fits the installed 90-second detach stage.

On a room turn, reconcile existing owned orphans and look up the exact marker
and authenticated room again. An existing attempted marker lacking a journal
room immediately returns `command_room_uncertain`; never discover or create for
it. Unknown tokens can discover with no durable marker. Recheck current role,
trust, relay binding, timestamp window and both room capacities after discovery.
Commit command_begin_preparation immediately before native create_group, using
the returned daemon-generated session in the command-purpose group name.
Only Created can issue native creation; Existing instead resolves the exact room
or fails uncertain. After accept_command_group, require exact reserved session,
peer and Client direction. A mismatch is forgotten/confirmed and remains
uncertain; never return it or silently bind the token to a different group.
Existing bound rooms retain existing Welcome/publication obligations and never
trigger replacement creation while delivery is pending.

If creation times out, fails, is interrupted, or process death occurs after the
fence, a marker without a journal-bound authenticated room is permanently
`command_room_uncertain` for that token. Existing owned orphan cleanup still
runs, but even proven cleanup does not authorize retry creation for that token.
The user may explicitly start another CLI invocation/new token, subject to caps.
Existing retained Welcome effects may already have been sent before orphan
cleanup; this design does not claim atomic peer invisibility. Some interruptions
conservatively lose a requested session; none silently recreate it or submit a
command. Cancellation/observation expiry never cancels an admitted job.

Keep the existing internal `open_command_room(peer, new_session, deadline)`
fixture API. Extract a shared creation helper taking an optional prepared
token/session fence; existing internal callers keep their semantics. Public
preparation uses only the fenced variant. No second MDK owner, actor journal
connection, or engine thread is introduced.
