# Phase 4: installed native interoperability and release acceptance

**DESIGN APPROVED — [independent Claude r4 review](../reviews/v0.2-phase4-design-r4.md),
with its nonblocking budget/restart clarifications incorporated below.** This is conditional
planning for Beads `marmish-7nw.5`. Phase 1 hosted acceptance is still open;
Phases 2 and 3 are unimplemented. Their completed interfaces, code reviews and
acceptance evidence are prerequisites, not assumed results. Existing phased
implementation authorization applies once dependencies and actual design review
pass; this document invents no additional human approval gate.

This supplements [the overall plan](../v0.2-plan.md), [Phase 2](v0.2-phase2.md),
[its interfaces](v0.2-phase2-interfaces.md) and [Phase 3](v0.2-phase3.md).
The [acceptance interface amendment](v0.2-phase2-acceptance-interfaces.md) shares
that design approval; its implementation and completed-code review remain
prerequisites before evidence/drain gates are available.
Those contracts govern product behavior. This phase adds native Rust acceptance
orchestration, strict reconciliation and measured evidence, not another command
protocol, storage owner, relay service product or installer architecture.

## Deliverable and boundaries

Qualify installed Linux AMD64, Linux ARM64 and macOS ARM64 clients and servers:
all nine directed pairs over an explicit direct relay; all three same-platform
pairs plus Linux AMD64→macOS ARM64 and macOS ARM64→Linux AMD64 via Arti. Each
same-platform cell uses separate identities, profiles and processes through the
relay, never local IPC in place of Marmot. Different route cohorts use fresh
identities/state. Test both directions where specified; one successful direction
is not evidence for its reverse. The nine direct/five Arti cells, benchmark/recovery/zero-grant cohorts and all
their cleanup records must pass in one exact workflow run attempt against one
immutable candidate tuple. Provider/installer-fault/Cargo qualification links
separate reviewed reports by that identical candidate tuple and source; those
reports cannot substitute for a failed live cell. No failed-cell-only rerun can
assemble a green result from different attempts.

The installed executable set is `marmish`, `marmishd`, `marmish-worker` and its
licenses/manifest. Embedded `_vault-helper` remains embedded. No Python, uv,
legacy wnd, browser or mandatory namespace/sandbox is introduced. A small POSIX
bootstrap remains Phase 3's authorized download entry. Optional legacy wire/MLS
fixture results remain separately labelled and cannot satisfy native cells.

## Candidate pin and handoff assertions

A short resolve job freezes repository, source SHA, Cargo.lock SHA256, harness
SHA, release version, installer bytes/SHA256 and all three target manifests and
asset digests/sizes. Use Phase 3's individual executable assets, not assumed tar
archives. The candidate tuple contains target, manifest SHA256, source commit,
compiled format IDs, minimum OS/libc and signing/notarization status. Build the
harness and fixture once per target in the build jobs, pin their digests too;
platform runtime jobs never rebuild them or require a compiler. Every
executable including the worker must agree with that tuple. Never resolve
`latest`, branch `head`, or mutable asset names separately in platform jobs.

Required Phase 2/3 handoffs are assertions to verify before implementation:

- Installed CLI exposes the approved destination/handle and finite exit behavior;
  `--max-commands N` counts unique engine admissions and `--max-uptime 30m`
  preserves accepted workers. The actual completed CLI spelling is consumed;
  this design adds no invented test flags.
- Setup supports the approved noninteractive explicit file backend, separate
  grants/outbound trust, explicit relays/Tor route and fresh named profiles.
- The proposed local acceptance amendment provides same-UID actor-owned paged
  `command_evidence`/`command_cleanup_status`, explicit local cancellation and
  final consuming engine quiescence proof. No second live database owner or raw
  worker PID API is used. Until that amendment is approved and implemented,
  authenticated evidence and cleanup gates are **unimplementable**, not passable.
- Worker provenance is solely the manifest digest and checked selected executable
  inode/path. Never execute `marmish-worker --version` or any diagnostic flags:
  its only worker argv contract is root/jobhex. Format IDs come from package
  metadata/manifest, not execution of the worker.


The native harness defines strict `RunBinding`, `PeerReady`, `PairResult`,
`ServerResult`, `CleanupResult` and `Rollup` schemas. Product wire types are
reused through the installed CLI, never reimplemented by the harness.

## Scheduling and bounded rendezvous

Use concurrent hosted `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15` platform
jobs with fail-fast false. Each job runs its local server concurrently with its
client contacting the three servers serially. Thus three server and three client
processes need three platform jobs, not six runner slots. Within a wave no platform job has
`needs` on another platform job or its own owner that is waiting for clients.
Only resolve/build prerequisites finish first; an always-run rollup depends on
all completed platform jobs. Use pinned Actions revisions and read-only contents/
actions permissions; disable checkout credentials. A mandatory ephemeral onion owner runs concurrently with each Arti cohort,
publishing bound RelayReady before waiting for consumers; never gate consumers
on that owner's completion.

Use uploaded immutable artifacts while producers remain alive, not terminal job
outputs. Adapt lessons from the old installed harness, not its Python or runtime
requirements. Current `v02-native.yml` already demonstrates a concurrent owner,
exact-run readiness and terminal outcomes. Its Bash child signalling caveat is
not copied as a claim of exact process ownership: new Rust supervision owns
child handles/process groups and verifies cleanup conservatively.

Every record binds schema, repository, run ID, attempt, source SHA, harness SHA,
candidate digest, cohort, role and fresh role nonce. Roles are exactly
`linux-amd64`, `linux-arm64`, `macos-arm64`. Canonical sorted JSON plus LF defines
record digests. Peer-ready additionally binds server/client public keys, exact
canonical relay set/route, installation tuple, fixture digest and expiry.
Server-ready additionally carries the server's client deadline as a UTC wall
time and binds it to original launch/uptime. Remote clients apply the120second
skew allowance conservatively, reserving their complete operation cap before
that deadline; insufficient time yields finite remote_client_budget_missed with
no new invocation. Server enforcement and all durations remain local monotonic;
wall-clock subtraction across hosts never becomes a latency measurement. Record
actual launch-to-ready durations and named readiness misses without claiming
readiness timings from design caps. Server-ready binds the complete three-peer digest map; terminal reports bind
both complete identity-ready and server-ready maps. An artifact is evidence only
for the expected workflow/run/head/attempt/name and exact schema; reject duplicates,
unknown roles, expired records, mismatched maps and future timestamps.

Artifact API/ZIP reads have finite HTTP/body/entry/expanded-size limits, no path
extraction and one exact expected member. Pin immutable artifact ID and digest
when discovered. Never interpolate a relay/account/path from metadata into a
shell command. Only the rendezvous adapter receives Actions credentials;
installers, product daemons, workers and fixture children receive a scrubbed
utility-only environment. Public artifacts never contain those credentials.

Run ten explicit sequential waves after target builds/resolve: D-matrix,
D-benchmark, D-recovery, D-zero-grant, D-policy; then corresponding five T-waves.
At most four hosted jobs run concurrently: three platform jobs, plus a mandatory
fresh onion owner in EACH T-wave. Start the next wave only after preceding
platform jobs AND their owner have completed cleanup. This cross-wave barrier
cannot deadlock its own consumers: each owner waits only its already-running
wave. It prevents a draining prior owner becoming a fifth concurrent job. Always-run rollup waits all waves/owners, including
failures; missing prerequisites produce missing required cells, never green skips.
D/T-matrix have nine/five cells. Each remaining wave qualifies same-platform
workloads in its own fresh profile, never spends main matrix admission credits,
and has at most one server per platform active. This intentionally splits the
former combined qualification job; no three-profile cleanup budget is assumed.
Accepted scheduling cost is approximately5×55+5×65=600minutes (~10hours),
plus builds, if every wave consumes its full job budget. This is a budget
estimate, not measured execution time. A failed cell requires a whole new
workflow attempt rather than stitching reruns; reserve runner capacity accordingly.

Qualification per-platform budget table (limits, NOT measured timings):

| Wave | One profile's bounded workload | Launch-to-ready cap | Ready-to-client-deadline budget | Cleanup reserve |
| --- | --- | --- | --- | --- |
| benchmark | exactly one cold+three warm fixed invocations, max-commands4 | 10m | at least14m with U=30m | 6m |
| recovery | detach/reconnect and daemon restart, same handle/ledger; max-commands2 | 10m | at least14m with U=30m, including restart | 6m |
| zero-grant | refusal and no-worker evidence, lazy engine; no admitted command | 10m | at least14m with U=30m | 6m |
| policy | forbidden path and immutable digest-conflict checks, at most one admitted baseline | 10m | at least14m with U=30m | 6m |

One profile therefore consumes at most30minutes of the35minute interval15..50;
no cleanup reserves are shared between profiles. Install/barrier through15,
launch by20, complete cleanup by50, remaining5minutes margin. If launch slips or
U is reduced, recompute the exact ready/work/cleanup caps BEFORE launch; reject
an infeasible cohort rather than advertise that readiness/throughput is proven.
Direct and Arti use identical fixed workload caps; failure to meet one is red,
not authority to extend its owner, daemon or job deadline.

Each matrix platform job has55minutes: 0..10 install/init; 10..15 identity barrier;
15..20 server readiness; cleanup/report by50; last5margin. Service and cleanup
budgets are LAUNCH-relative, not a promise that every client can run to minute45.
At each launch freeze `L` and `U=min(30m,remaining permitted cohort lifetime)` on
local continuous time; never extend U later. Client deadline is `L+U-6m`.
Before that deadline all expected client terminals must be reconciled, or the
cohort is red. Then explicitly local-cancel remaining fixture rows and poll cached
cleanup facts; prepare must begin no later than `L+U-5m`. Protected engine removal
and renewed daemon liveness/status proof must finish by `L+U-1m`, leaving one
minute for ordinary stop/reap. Matrix readiness must leave at least20minutes before the
client deadline; otherwise emit finite matrix_readiness_budget_missed before
admitting clients. This20minute rule does not apply to qualification profiles,
which use the explicit qualification table above. Each serial pair gets
min(remaining client time/cells still unattempted, its original operation cap),
so one timeout cannot consume the other cells or cleanup reserve.

Qualification jobs use the same55minute bound: install0..10, relay ready through15,
its single listed workload and protected cleanup by50, last5margin. Each
fresh profile receives U capped by its remaining cohort time and30m, with the
same6m/5m/1m launch-relative reservations, including max-commands4 benchmarks.
Their readiness cap is10m, leaving at least14m for the listed workload withU=30m;
misses emit finite qualification_readiness_budget_missed.
Readiness/workload feasibility is checked BEFORE launch: fixed per-workload
operation caps plus cleanup reserve must fit the remaining shared budget; if
not, fail the cohort instead of starting an inevitably unsafe server. Restarting
the recovery profile does not extend its original cohort deadline. A restarted
instance at L' receives exactly remaining uptime U'=(L+U)-L'; its6m/5m/1m
reservations still end at original L+U, never L'+U. Set its max-commands to only
planned admissions still remaining after durable evidence reconciliation; a
per-daemon counter reset cannot create new admission credit. If no admissions
remain, restart with admission closed while status/poll/recovery remain available.
An uncertain earlier admission retains its reservation. Mandatory workload limits may be
shorter than their product maxima, recorded in evidence; no successful workload
substitutes for a missing planned one. An offline schedule validator exercises
early/late launches and rejects any plan lacking protected cleanup time before
original uptime. This supersedes fixed45..50 cleanup assumptions.

Each Arti wave owner starts with its consumers, has a60minute absolute lifetime and
65minute job timeout including cleanup. It must publish RelayReady by minute15,
remaining live through all consumer deadlines (minute50) plus5minutes cleanup.
Readiness includes common RunBinding/cohort/owner nonce, onion URL+SHA256 and
expiry, and records actual encrypted readiness qualification. Insufficient lifetime
fails before clients start. Owner waits exact three bound platform terminal
outcomes, then stops/reaps its relay; deadline without them is failure. A fresh
owner is mandatory for each T-benchmark/recovery/zero-grant/policy wave; no expired endpoint reuse or lifetime
extension. The pinned native relay fixture receives no external deployment.
Its completed Phase1 Arti restart qualification remains an explicit predecessor;
Phase4 cannot waive a still-open Tor platform gate.

Trust only workflow_dispatch and protected-branch pushes; never pull_request_target,
fork-provided code or arbitrary executable inputs. Re-run all jobs to obtain a
new attempt; run ID/attempt binding, not wall clock alone, prevents stale mixing.
Validate artifact wall-clock expiry/future fields with ±120seconds allowed skew;
those checks do not calculate latency. All duration/deadline accounting is local
continuous monotonic time. External driver notifies the user if jobs have not
started within five minutes; an unscheduled job cannot observe its own queue.


## Real installation and setup on every target

Invoke the exact candidate `scripts/install-native.sh` as a real child with its
local `--asset-dir` path and the approved prefix/bin options. This runs the same
hash/manifest/native installation path as downloads; it is not source frontend
execution or a verification bypass. Qualify HTTPS bootstrap separately after
assets are publicly available and before changing the public install channel.
Run with fresh owned private HOME/state/install directories and utility-only
PATH where Python, uv, cargo and rustc are absent. Harness/build tools run in a
separate environment and cannot supply product runtime dependencies.

Use installed binaries only after rehashing the selected manifest and each
binary; verify executable format, target, OS baseline, loader dependencies and
macOS signature. Verify worker location/inode/digest through the installed engine
path, not PATH lookup. Record installer/install/identity-ready timings separately.
Configure client/server fresh identities, file backend, exact relays and explicit
cohort-specific expected-client grants. Never default to public relays. The user explicitly selected
test relay may be public; source documentation must not imply it is a default.
A zero-grant setup must independently prove no worker is created on an attempt.

Keychain tests remain separate qualification: Linux provider availability and
macOS create/upgrade/load/rollback/load by actual signing kind. Headless file
backend success is required and does not imply provider success. Provider failure
must not downgrade an existing profile or regenerate keys. No real user keychain
or installation is touched. Installer transaction/fault/upgrade tests from Phase 3
remain required; nine-pair success does not replace them.

## Execution fixture and independent evidence

Each server admits at most three unique commands with `--max-commands 3` and
`--max-uptime 30m`: exactly one from each expected client identity. Admission
limits are not authentication; configured grants/policy enforce that boundary.
For the selected five-cell Arti cohort, expected distinct clients/counts are two
for Linux AMD64, one for Linux ARM64 and two for macOS; configure the corresponding
max-commands count (never above3) and grants for exactly those cells. There is no
claim of three Arti clients on a server with only one or two selected cells.
The server stops new admission at its expected count, but continues local IPC,
Marmot status/poll/cancel and retained convergence until explicit supervisor stop
or its original uptime. Supervisors stop only after verifying every expected
ClientTerminal artifact or on failed deadline; there is no invented client-ACK wire.
Receipt count alone cannot pass until exact expected principals/invocations and
all client terminal records reconcile. On uncertainty clients keep the same durable
handle/invocation, never generate a fresh invocation to retry. A daemon exit0
at a lifetime limit does not mean successful acceptance.

Use the small native Rust fixed-role fixture built in the pinned target build job. Install it under a private fixed executable path, hash it before server launch and again before cleanup, and
grant only that canonical path under the additive Phase 2 policy. The fixture accepts only a lowercase64hex pair nonce and fixed vector ID, plus
the frozen byte-edge vector arguments; these never supply a path. It derives a
sibling owner-only `receipts` directory from its verified canonical executable
location and creates exactly `<pair-nonce>.receipt` using exclusive/no-follow
creation. The harness precreates that directory0700 and fixes configured cwd to
a private harness working directory. The fixture never writes under passwd HOME.
It writes completion only after verifying input/arguments and producing/flushing
output. Granted commands still receive the real passwd HOME/USER/LOGNAME and
fixed worker PATH as Phase2 specifies; disposable profile HOME is not command HOME.
The harness supervisor alone reads that private receipt, validates exact fields
and exports a sanitized digest/count. Fixture claims are compared with the
server actor's authenticated command/engine evidence, never treated as proof of
which Nostr principal invoked it by themselves. No general shell grant is needed.

One invocation per pair tests binary stdin/argv/stdout/stderr, nonzero exit7 and
fixed multi-chunk output. This fixture consumes all stdin before output, avoiding
the documented early-exit EPIPE race; an optional head-style race probe belongs
only in separately reported qualification, never the exact-byte acceptance oracle. Use argv with spaces, quotes, apostrophe, backslash,
newline, Unicode, glob metacharacters and platform-valid non-UTF8 bytes; reject
NUL/empty argv0 and test canonical/symlink policy independently. Stdin includes all
256 values, NUL and CR/LF within16KiB; combined encoded request must fit32768.
Each stream emits a distinct deterministic128KiB pattern, beyond64KiB paging,
with hashes/exact byte counts independently computed from the public vector.
No `echo`, shell quoting or terminal rendering is used as an output oracle.

Pair identity derives from run/candidate/cohort, roles, both public identities and
nonces. Server evidence binds authenticated principal, MLS group SHA256/session,
invocation and immutable submit digest, one engine admission, stream
produced/closed/gap observations, outcome and final authority validity. The
supervisor ServerResult separately binds the exclusive fixture receipt digest to
that invocation via the fixed pair nonce/vector and expected submit digest; the
actor does not claim it observed a receipt file.
Server stream hashes are optional and must be null unless actually read completely
from retained gap-free output; no cheap full-output hash is promised. Client and
fixture exact stream hashes remain independent required oracles. Unknown actor
admission/outcome/authority/worker facts fail qualification. A separate gate
requiring missing server hashes is not qualified, never inferred from fixture data. Client verifies complete
stdout/stderr bytes, exit mapping and durable authenticated terminal response;
relay publish acceptance is insufficient. Duplicate/replayed immutable requests
must retain the one admission; a conflicting digest must fail without a worker.

Test accepted command survival after client detach/disconnect and reconnect on a
separate bounded same-platform qualification workload, preserving the exact handle.
Test daemon restart while workers survive and authoritative engine-known recovery.
Prepare consuming cleanup only on the final instance; verify evidence cursor
continuity across restart and refresh every included row under the final fence.
These extra commands and every zero-grant/forbidden-path/digest-conflict
negative run in qualification profiles, never main matrix profiles. Negative
cohorts have independent finite caps and assert zero new engine admissions for
expected refusals; no negative is assumed noncounting merely because CLI failed. No implicit cancel on CLI disappearance or Ctrl-C; explicit cancellation
and deadline cleanup remain distinguishable. Do not invent an atomic stdin launch
claim or hide the documented EPIPE/input-failed race.

## Metrics, strict reconciliation and failure evidence

Use monotonic continuous time within each process; never subtract timestamps from
different machines. Record clock resolution/drift validity. Separate installation,
identity, Arti bootstrap, relay activation and cold room/handshake stages. For
commands measure client wall from immutable submit to verified terminal/drained
output, first nonempty output, last byte/drain and exact verified goodput. Include
harness/CLI overhead in the definition; do not label wall time isolated network
latency. Stream observations use arrival timestamps and verified bytes, not relay
message counts. Command goodput=(verified stdout bytes+stderr bytes)/(immutable
submit→verified terminal drain duration); drain goodput=that same verified byte
count/(first nonempty output→last byte duration). Both use seconds and report B/s.
Zero-byte/zero-duration throughput is null.

Main matrix gives n=1 command per directed pair; chunks within a command are not
independent command samples. Additional same-platform direct and Arti benchmark
cohorts use one cold plus exactly three warm fixed-workload invocations per
platform (separate servers with `--max-commands 4`). Record every sample and
failed/null metric, payload size, source/target, route, Arti cold/warm state,
compiler/features and installation tuple. Aggregate only comparable workloads;
report min/median/range where justified, no p95/p99 or one-way latency inference.
Do not set an invented throughput target. Publish JSON and readable Markdown in
`docs/validation/` with exact reproduction command/workflow inputs and sample counts.

Rollup accepts exact nine direct plus five Arti cells, separate benchmark and
negative/cleanup/provider dispositions. Independently recompute pair derivation,
manifest/source maps, vector hashes and expected bytes/outcomes; cross-check client,
server authenticated evidence and exclusive fixture receipt. Require final cleanup
quiesced and every profile server-ledger evidence row (including unexpected admissions)
observed_seq >= the fence allocated
BEFORE final refresh; later authority invalidation voids that proof. Require exact expected
principal set, command count, no unexpected admission and native authority validity.
Missing, failed, stale, duplicate, invalidated or unverified cells cannot be green.
A negative gate passes only its expected refusal with no execution. Preserve finite
failure stage/category and null metrics; never substitute a previous attempt.

Always emit installation and terminal outcomes even on preparation failure.
Sanitized public reports contain closed labels, public test identities/digests,
counts/durations and boolean cleanup proofs. Bound reports to1MiB each and total
artifact to16MiB. Keep raw private logs/databases/stdin/output/secret roots out of
Git/GitHub artifacts. Scan for disposable secret material without printing a match.
Finite diagnostics reuse reviewed allowlists; do not publish arbitrary native or
provider errors, paths, command environments or credential-bearing relay URLs.

## Cleanup, release gates and ownership

The supervisor owns exact children and groups from spawn; startup interruption,
partial install and failed setup enter conservative cleanup. For a live daemon,
FIRST explicit local ledger-key cancellation of remaining owned fixture rows,
then poll active/uncertain/presence facts, then prepare cleanup under the frozen
launch-relative6m/5m/1m schedule. Do not ordinary-stop the daemon first: that loses
the local cancellation channel and consuming guard proof. No broad pkill, raw PID
kill or PID-file trust is permitted. prepare irreversibly closes admission and
allocates the observation fence before final status+raw-presence refresh. Every
included row must commit observed_seq >= final_seq before engine consumption.
A failed consuming call leaves cleanup=failed with engine unavailable, never
reopened, and state preserved. UnknownLaunch/Lost or uncertain worker facts fail
this run; actual engine recovery semantics remain authoritative.

Engine consuming into_cleanup must prove Exited jobs, recorded worker absence
and held frontend/job/IO locks; terminal output alone is insufficient. Keep the
current profile lease and consuming guard alive while removing only the exact
registered engine subtree. Check waitpid(WNOHANG) before first unlink and after
last unlink, then same-socket cleanup_status still quiesced with the same fence.
Only after protected removal and renewed liveness proof request ordinary daemon
stop/reap and remove remaining owned profile state. Uptime/stop during draining
or quiesced, daemon failure, later authority invalidation, failed refresh or failed
removal makes proof invalid and cleanup red; never delete using a stale response.
If daemon already died at failure/timeout, its engine state is preserved without
fallback deletion. Unknown workers or escaped descendants are failed cleanup,
not permission for unsafe external signalling. Completed protocol behavior still
preserves accepted user commands on ordinary disconnect/stop.
Remove only owned test state after verified shutdown. Any uncertain child absence,
failed engine stop or unresolved worker fails cleanup, preserving private state
for bounded local investigation rather than reporting deletion. Capture final
cleanup outside the state directory after removal. Report process, worker, socket,
provider-entry, private-state and installer ownership separately. Uninstall uses
Phase 3's real ownership-aware operation and preserves user state by contract;
test-owned state removal is a separate harness operation.

Implementation ownership is bounded: agent A native rendezvous/install supervisor;
agent B fixtures/authenticated evidence and cell execution; agent C strict rollup/
metrics/schema tests; root workflow/adapter seams, integration and publication.
Define concrete Rust module interfaces at implementation handoff from accepted
Phase 2/3 APIs; any changed trust/storage behavior requires independent review.
All offline malformed-rendezvous/provenance/receipt/cleanup tests and actual cells
must pass, followed by integrated Claude auto-mode code/evidence review with no
blocking findings. Update specification, usage, dependency/license attribution and
.gitignore; inspect exact staged files for secrets and publish reviewed increments.

Release version0.2.0 or reviewed v0.2.0-rc.N is separate from legacy experimentals.
No release tag/assets are created by this planning step. Before authorized release,
require all target install/format/ABI/signing gates, direct/Arti matrix, benchmarks,
negative/replay/recovery and cleanup gates; explicitly report provider/Cargo-route
qualification status without advertising unverified functionality. Existing release
scope authorization does not authorize unrelated deployment or external messaging.
Publish immutable executable assets/manifests/bootstrap through GitHub Releases;
push exact source branch/tag to GitHub origin and Radicle rad, verify refs and
Iris immutable source/bootstrap bytes. Compare external HTTPS downloaded hashes
and run downloaded installs before switching README/quickstart channel. A source
push is not binary availability; Iris source reachability is not GitHub asset
reachability. Any partial mirror, asset, replication or install failure stays a
reported Beads blocker. Never call the release or phase complete on a partial gate.
