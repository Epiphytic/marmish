# Native candidate CI optimization

Status: design APPROVED by Claude Opus 5.5, round 2; implementation and hosted validation in progress. See [review evidence](../reviews/native-ci-optimization.md). User authorization covers CI acceleration including caches; this document adds no new permission requirement. Tracking: Beads marmish-poz. Scope is CI infrastructure and qualification provenance; no product behavior, command timeout, runtime, public release, installer pins or release version changes.

## Evidence and objective

Successful cold candidate 43174030584, attempt 1, built source 05bec8b2b4c4ea0a161a1adbc494b0d180a92ba8. Package jobs took approximately 60m42s on Linux AMD64, 61m16s on Linux ARM64 and 66m39s on macOS ARM64; the whole candidate took 68m13s. Cargo compilation/Clippy profile completion sums were 20m42.70s, 24m34.47s and 40m50s respectively. Summed test-harness execution was 39m21.92s, 36m04.22s and 24m41.56s. Linux execution therefore dominates substantial parts of the pipeline; caching alone cannot remove that floor.

Keep all existing Rust tests and strict Clippy checks, production/installed-feature separation, macOS serial test qualification, signing, ABI/import inspection, locked licenses, packaging, installer/quickstart/provider gates and artifact provenance. Reduce elapsed time by executing the independent product/default-feature and installed-feature lanes concurrently and reusing dependency compilation across runs. Do not optimize by skipping tests, reducing negative-case coverage or interpreting successful uploads as passing qualification.

## Job architecture and bounded load

Retain the single eligibility job. The existing three-job package matrix continues default-feature tests and Clippy, locked production release build, strict macOS ad-hoc signing, final ABI/import inspection, license collection, product packaging and render-tool upload. Introduce a three-job installed-tools matrix, also dependent directly on eligibility, with only runner and target matrix keys and independent checkout, source validation and pinned Rust 1.97.1 toolchain. Its exact expanded job names are `installed-tools (ubuntu-24.04, x86_64-unknown-linux-gnu)`, `installed-tools (ubuntu-24.04-arm, aarch64-unknown-linux-gnu)` and `installed-tools (macos-15, aarch64-apple-darwin)`. It runs all installed-checks feature tests and strict Clippy, then builds the two test tools plus its own marmish-release-tool in a single locked release invocation. It signs copied macOS test tools and uses its own release-tool to package existing installed-tools artifacts.

Keep matrix fail-fast=false. Each matrix max-parallel=3, yielding at most 6 heavy jobs and 2 Mac jobs per candidate. Keep existing workflow concurrency cancel-in-progress=false so concurrent normal candidates are serialized; normal and explicitly caveated groups remain separate as today. The organization has documented Team hosted limits of 60 total jobs and 5 Mac jobs; actual hosted dispatch and any competing workflows can still queue. These hosted runner labels are separate from the organization self-hosted pool. Keep one Cargo command at a time per runner, normal Cargo internal parallelism and macOS RUST_TEST_THREADS=1. No extra simultaneous builds inside a runner.

Use default `target/` independently on each lane's separate VM and distinct cache namespaces. Remove the installed lane CARGO_TARGET_DIR override rather than relying on unverified absolute-path cache mapping. Before cache restoration and before any Cargo operation, the tools macOS lane explicitly sets MACOSX_DEPLOYMENT_TARGET=15.0 and RUST_TEST_THREADS=1. The product lane also restores cache only after its existing qualified macOS deployment-minimum step. Do not restore one lane's whole target directory into the other. Product signed files continue to be copied out of Cargo hardlinks before packaging. The tools runner never downloads or receives product assets, so it cannot mutate them; this structural isolation replaces the old same-runner before/after product hash comparison. Retain final tool byte hashes, probes, signing and metadata checks.

Render waits for both build matrices on ordinary candidates; quickstart/provider remain dependent on render. The normal inventory becomes 14 jobs: 1 eligibility, 3 package, 3 installed-tools, 1 render, 3 quickstart and 3 provider jobs. Preserve exactly 15 artifacts and 10 v0.3 reports using current names, schemas and run/attempt suffixes. No performance artifacts or arbitrary new artifact members are introduced.

## Immutable source, feature and artifact bindings

Both build lanes check the same full 40-character lowercase hexadecimal MARMISH_BUILD_COMMIT, actual HEAD, expected native host/target, source existence, clean tracked tree and allowed master ancestry. Pass the same source explicitly through all Cargo commands. Repeat clean-tree/HEAD checks after building. Tool packaging uses the same existing sourceDigest input list and harness digest as consumers. The workflow itself is already included in SOURCE_PATHS; a new helper belongs under the already-covered scripts directory, otherwise update shell and Node fingerprint input lists together.

The installed lane builds marmish-release-tool with installed-checks so its package-tooling command compares each tool's --release-info with its own compiled version/target/source/formats. Existing packaged tooling manifest records the exact bytes and hashes of both tools, source, target and harness. Existing candidate inspection still validates eligibility, authenticated run/attempt, exact job inventory, exactly 15 artifacts, 10 closed reports, product metadata and hashes, tool source/harness/hash probes and bootstrap pins. A successful cache restore does not satisfy any of these gates.

## Source-bound job inventory compatibility

Introduce a literal workflow-level marker in the new source:

```yaml
  MARMISH_CANDIDATE_LAYOUT: split-v1
```

Select inventory from the candidate's authenticated source commit by bounded git show of that source's .github/workflows/v02-release.yml, rather than coordinator HEAD, version number or unauthenticated caller input. The source must already have passed run/eligibility/source checks. Use the required API `checkJobs(jobs, {layout, skip})`: layout has no default and must be exactly `legacy-v1` or `split-v1`; unknown or missing layout rejects. Current candidate inspection explicitly supplies the source-selected layout.

The closed source-layout parser first requires `git ls-tree <source> -- .github/workflows/v02-release.yml` to return exactly one regular `100644 blob` entry for the exact path. `git cat-file -s` must succeed and report a positive finite integer size at most 256 KiB before reading. Read the exact source workflow with bounded git show maxBuffer set to 256 KiB and reject any command error, missing file, symlink, oversized output, BOM or CR characters. Count every occurrence of the substring MARMISH_CANDIDATE_LAYOUT: zero selects legacy-v1; exactly one is valid only as the exact line `  MARMISH_CANDIDATE_LAYOUT: split-v1` inside the unique top-level `env:` block, after `^env:$` and before the next line starting in column 0. Any other occurrence or placement rejects, including comments, job-level env, run blocks, quoted keys/values, split-v2 and duplicate markers. File-read failure never means marker absence. A general YAML dependency is unnecessary with this deliberately closed grammar.

Use the selected inventory in release-candidate.mjs checkJobs and skipped-job validation. Split source requires exactly 14 successful jobs; legacy source requires exactly 11 successful jobs. Missing/duplicate/wrong-name/cancelled/failed/in-progress jobs remain errors. Add installed-tools to split expanded/collapsed skip categories. Do not accept either count opportunistically or infer layout from returned jobs.

Fixed historical report replay passes a hard-coded `legacy-v1` tied to ORIGINAL.source and historical candidate 42747078282, without reparsing git. Keep its assertion requiring exactly 11 unique job IDs and its historical 11-job fixtures. Current split candidate fixtures require 14 jobs and reject an otherwise valid 11-job response. Negative tests prove source selection cannot be changed by coordinator HEAD, unauthenticated input or returned job names/counts.

## Eligibility, caveated and skipped paths

Normal build: an eligibility decision of build starts both matrices; render requires both to succeed; quickstart/provider execute normally.

Before evaluating eligibility, the eligibility job now runs the standard-library Python workflow trust policy tests. Drift in the native or provider workflows can therefore fail eligibility before either build matrix starts. This is an additional fail-closed gate, not a substitute for the existing eligibility checks.

Skip-by-design: eligibility passes and both build matrices skip; downstream jobs skip. Inspector accepts only exact collapsed or expanded category sets for the selected layout. This is a deliberate skipped result, never full qualification.

Explicit caveated_release retains its existing source-equivalence checks, authorization boundaries and behavior: product packaging/render may run while native/installed qualification is skipped. The new tools matrix is skipped. Render uses exactly `needs: [package, installed-tools]` and `if: ${{ !cancelled() && needs.package.result == 'success' && (needs.installed-tools.result == 'success' || (inputs.caveated_release && needs.installed-tools.result == 'skipped')) }}`. This accepts successful package with tools skipped only for the existing explicit caveated path and rejects failed/cancelled/missing tools for normal candidates. Preserve workflow behavior rather than allowing a skipped dependency to skip caveated render accidentally. Caveated outputs do not qualify as a normal 14-job candidate or constitute acceptance evidence. The existing caveated path cannot run end to end at current 0.3.1 source: it requires 0.3.0 and a tightly allowed diff from ddda8a0. Its preservation is therefore supported by static policy/mutation tests only, and must not be represented as a newly exercised runtime path.

## Dependency-only cache

Use unique prefix-key `marmish-v02-release-split-v1` only in v02-release.yml, with an explicit policy test rejecting its use elsewhere. Use Swatinem/rust-cache v2.9.3 pinned to dereferenced commit d1527c8f67ef9af357290475d4af4b0fab8f12e0 after toolchain installation. Pinning was verified through GitHub git tag API; inspect the pinned action during implementation. Retain dependency-only defaults, explicitly cache-all-crates=false, cache-workspace-crates=false and cache-bin=false. Keep cache-on-failure=false and save only successful trusted master builds using explicit `save-if: ${{ github.ref == 'refs/heads/master' && !inputs.caveated_release }}`. SHA-pin moving rust-cache and rust-toolchain actions in existing relevant master cache writers, including v02-native.yml and v02-provider.yml, to reviewed immutable revisions. Inspect existing native-validation.yml and release.yml whole-target cache writers for capacity competition; do not expand or share their namespaces. Never cache package assets, binaries of workspace crates, runtime state, keys, keychains, credentials or test results.

Keys distinguish build lane, native target/runner baseline and a manually bumpable cache epoch, retaining action hashes of actual rustc/toolchain/host, workspace manifests, Cargo.lock, Rust toolchain/Cargo config and compiler environment. Preserve default CARGO CC CFLAGS CXX CMAKE RUST prefixes and additionally include MACOSX_DEPLOYMENT_TARGET SDKROOT ImageOS ImageVersion. The manually maintained cache-key suffix `macos15-glibc239` identifies the deployment baseline and must be bumped whenever that baseline changes. Native image updates intentionally invalidate native dependency caches. Do not key on source commit/MARMISH_BUILD_COMMIT because workspace artifacts are excluded and dependencies should be reusable across source changes. Record the action's implicit CARGO_INCREMENTAL=0; it changes build caching strategy, not tested behavior.

The action has no per-cache size cap input. Six native lane/target caches share the repository 10 GB allowance with any other caches. Measure actual compressed cache bytes through API after the cold run, plus restore/save time, exact/fallback hit and relevant disk usage. If the six new caches exceed 7 GB total or any is evicted between paired cold/warm runs, change installed lanes to cache-targets=false (registry/dependency-download-only) and repeat the measured pair; do not silently combine feature target directories or expand allowance. Cache misses/eviction/failure must retain a correct cold path. Do not delete unrelated repository caches. If ImageVersion changes between paired runs, rerun the pair with matching image inputs rather than relaxing the required exact warm hit.

Residual trust decision: dependency rlibs restored from cache are not independently authenticated as source-derived; any sufficiently privileged step in any trusted master workflow can write a matching cache key, and first writer wins. A unique prefix plus action SHA pins and successful-master-only saves reduces accidental collisions and moving-action exposure but cannot create isolation from other trusted master jobs. The user explicitly authorized CI acceleration including caches; trusted master workflow code already has authority to alter build source and resulting product. Proceed within that existing trusted-master boundary, record this remaining risk and rationale honestly, and do not fabricate additional human acceptance or create a new approval flow.

## Diagnostics and expected benefit

Write cache hits and sanitized dependency cache size/restore/save timing and each major Cargo/test/build wall duration into logs and GITHUB_STEP_SUMMARY. Keep raw cache/API/job logs private; collect existing job metadata through read-only API, then commit sanitized measurements under docs/validation. No product instrumentation or additional artifact inventory is needed.

A cold split is estimated near 35 minutes for the critical path plus queue/setup/downstream overhead from the existing measurements, compared with the 68-minute observed serial candidate. Warm runs still execute all tests; slower default/installed test branch is roughly 20 minutes on Linux or 13 minutes on Mac before workspace rebuilding, cache transfer and downstream gates. These are estimates, not promises; publish actual cold/warm measurements with cache bytes and queue delays. Aggregate runner work remains similar, with extra VM/cache overhead and a release-tool link in the tools lane; benefit comes from elapsed-time overlap and reused dependencies.
