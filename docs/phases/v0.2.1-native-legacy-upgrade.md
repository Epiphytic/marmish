# Recognized v0.1 launcher upgrades

Status: APPROVED by actual Claude Code auto design r2 and narrow r3 clarification; see
[review](../reviews/v0.2.1-native-legacy-upgrade-design-r2.md). Beads: marmish-zns.

The user explicitly requests automatic updates of previous Marmish versions.
This increment upgrades recognized installer-owned launchers, retaining the old
runtime and launcher backups. It does not migrate profiles, keys or databases.
It ships with a new native installer binary (v0.2.1); the generic bootstrap can
continue calling `install`. Do not change the generated public pinned bootstrap
before matching assets are available. Existing receipt-owned native upgrades
continue through their existing path.

## Actual contracts and boundary

The v0.1 script at git 347cf799 (`scripts/install.sh`, `launcher_bytes`,
`validate_marker`, `validate_previous`) installs regular 0755 launcher files:
`#!/bin/sh\n# marmish installer format 1\nexec PATH "$@"\n`, where PATH is
Python shlex.quote of the absolute version-root/bin/name. Recognition reconstructs
those exact bytes; it does not interpret shell syntax, execute a launcher or read
an arbitrary symlink target. Its strict four-field marker `.marmish-install.json`
is `{format:1,version,target,launcher_dir}`. Its owned `current` symlink must equal
`versions/marmish-VERSION-TARGET`. This is local ownership evidence, not a claim
that the old runtime's cryptographic provenance has been revalidated.

Only marker versions `0.1.0-experimental.N` with canonical nonnegative decimal N
are accepted, and target must equal the incoming native target. Both previously
published .1/.2 templates use this same contract. Other versions fail closed.
Legacy root is discovered only at the old default HOME/.local/share/marmish or
at bin_dir's parent when its last component is `bin` (old --prefix contract).
Exactly one matching root may authorize migration; ambiguous matches refuse.
Reject overlap in either direction between legacy root and native prefix.
Existing validate_options still forbids native prefix/bin_dir overlap with state.
The legacy root MAY contain v2 state: Linux default v2 state is precisely
HOME/.local/share/marmish/v2, so a blanket root/state exclusion would prevent
default upgrades. This helper never traverses, opens or removes that subtree;
it reads only the fixed marker/lock/current/version-root/bin ownership evidence.
No state path is moved. bin_dir may be under legacy root for custom installs. All paths must be UTF-8 absolute normal-component paths with the existing trusted
ancestor checks. Marker/current/version-root/bin and launcher directories must
have current-user ownership and existing installer permission checks; marker
0600, launcher0755, nlink1, no symlink. Root is private (no group/other bits).
Unknown/malformed ownership markers, mismatched paths, foreign files and dangling
symlinks refuse without replacing any launcher. A missing one of the two old
launchers is accepted, provided every existing launcher matches the same marker.
At least one matching launcher is required. A regular unrelated second launcher
blocks the entire migration before any move. Do not follow its target or print
its contents.

Acquire the old installer's `.marmish-install.lock` with O_NOFOLLOW, 0600,
current uid/nlink1 and nonblocking flock, under the existing native prefix lock.
Open the old lock O_RDWR without O_CREAT: missing or non-0600 locks refuse
(deliberately stricter than historical permissive existing-lock acceptance).
Retain the legacy lock through the initial migration only; native recovery does
not require the old tree/lock. Never run as root. No new process,
network dependency or provider access is introduced.

## Small implementation boundary

Add a private `native_install_legacy.rs` child of native_install, using existing
Anchors, metadata validation, serde deny_unknown_fields, lock and sync helpers.
The native installer detects migration only for Install with no active native
version and no receipt-owned launchers. Select/Status/Uninstall never initiate it.
Initial native receipt creation is harmless metadata; refusal may leave it, but
never modifies old wrappers/state. No shell JSON parser or new CLI option.

Extend existing Transaction with #[serde(default, skip_serializing_if = "Option::is_none")]
on an optional legacy record (so earlier
native transaction records remain readable). Record root/version/target and the
ordered nonempty subset of recognized launcher names; backup names derive only
from the validated random txid and fixed launcher names:
`.marmish-legacy-TXID-marmish[ d ]` in the held bin_dir. Validate the record against
receipt/action and restrict it to install with previous active None/launchers[].
These names must be absent before writing a new transaction. Legacy root UTF-8
bytes are bounded to2048; version to64 and target to64. More importantly atomic
transaction serialization checks the COMPLETE serialized JSON plus LF <=8192
BEFORE creating/writing any temp file. The existing read cap stays8192.
The legacy names must be a strictly ordered nonempty subset of LAUNCHERS and
created_launchers. Nonlegacy transaction serialization is unchanged; an older
binary intentionally refuses a new legacy transaction rather than adopting it.

All incoming assets are already verified before mutation. After validation of
BOTH launcher paths, atomically persist/fsync the existing transaction BEFORE
moving wrappers. Detection precedes run's validate_links: skip that native-only
check only for the fully validated migration plan. Read wrappers O_NOFOLLOW with
fstat uid/nlink1/mode0755 and expected-length+1 bound, then recheck dev/ino before
each move. Rename recognized launchers to exclusive same-directory backup
names, syncing bin_dir after each. Include those launcher names in the native
created_launchers list, then use the existing stage/copy/symlink/selector/receipt
commit. The old runtime, marker, current symlink and private state are untouched.
On success retain original launcher files at their backup paths; report the
backup paths as JSON-escaped path-only informational diagnostics. They are never
executed or recursively removed. No backup GC or old version pruning.

## Recovery

Native receipt generation remains the only commit decision. Before ANY recovery
mutation validate the complete allowed launcher/backup state and all fixed expected
wrapper bytes reconstructed solely from transaction root/version/target/name.
Do not reopen the legacy tree, marker or lock during recovery; deleting the old
runtime after an interruption must not wedge recovery. Initial recognition holds
the old lock and revalidates marker/wrappers before the first move. Recovery from malformed or
unrelated entries is fail-closed, preserving all entries and transaction evidence.

Before receipt commit, each migrated name may be either original exact wrapper
with no backup (move not yet done), or exact backup with launcher absent or the
expected owned native symlink. Both original wrapper and backup present is
ambiguous and refuses. Nonmigrated names use existing native recovery checks.
The legacy-aware pass REPLACES both existing recover launcher loops for migrated
names; never send an unmoved original wrapper through the native unlink branch.
Remove only verified expected created native links, restore moved wrappers with exclusive
rename, and sync. Original unmoved wrappers remain. Existing stage/selector
rollback still runs. Delete the transaction only after successful rollback.

After receipt commit, every migrated backup must exist and match. Launcher paths
may be absent or expected native links, never old wrappers or foreign entries.
Existing recovery restores any missing expected native link and selector; retain
backups. Delete the transaction only after successful roll-forward. Recovery is
idempotent after interruption at any individual step (including during restore).
Uninstall after migration removes native links only; backups remain and old
wrappers are not automatically restored. A backup already restored to its original exact wrapper is accepted as the first
precommit state. Locks are reacquired on a later invocation.

As with the existing installer, failures may leave a durable transaction; the
next invocation automatically recovers first. Do not claim synchronous rollback
on SIGKILL/power loss or erase evidence when a path was replaced. Select/Status
can complete recovery without initiating a new migration.

## Diagnostics and validation

For an unrecognized launcher, emit JSON-escaped path-only diagnostics naming the
conflicting path and suggesting a separate --bin-dir or preservation/removal of
an independently reviewed conflicting program. Do not emit shell commands or
inspect/print arbitrary targets. The finite error remains unrelated_launcher.

Inline tests reuse the existing native asset/transaction fixture, with canonical
private HOME-contained paths (macOS aliases normalized). Required cases:
- exact old wrapper/marker/current fixture -> native install; both old runtime
  sentinel and wrapper backups unchanged; managed native reinstall still works;
- one missing old launcher; both present; default/custom roots; shell
  metacharacters, spaces and apostrophes match Python shlex.quote exactly;
- interruptions before moves, after first/second move, after selector and commit;
  Status recovers original wrappers precommit and native links postcommit;
- failure in copied assets/staging, malformed receipt/marker/current/version,
  foreign/dangling symlink/regular file/hardlink/permissions, altered backup and
  occupied backup name: no unrelated bytes replaced, both paths prevalidated;
- partial recovery resumed, lock contention and wrong-target/version refusal;
- maximum-size transaction roundtrip and oversize rejection BEFORE any durable
  transaction; non-UTF8/non-normal paths; missing/held legacy lock; native prefix
  overlap; recovery after the old tree is deleted; Select/Uninstall after upgrade;
- no identity/key/profile files opened, old runtime sentinel preserved; explicit
