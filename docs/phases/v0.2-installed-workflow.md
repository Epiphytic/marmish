# Installed native matrix workflow integration

This integrates the approved direct-release amendment and artifact supervisor.
It qualifies the matrix first; auto-exit, benchmark, recovery, policy and real
keychain gates remain required before release.

The manual workflow runs only from master. Inputs select the exact successful
candidate run ID, run attempt, immutable source commit and explicit relay.
Permissions are contents:read and actions:read. Resolve verifies that the
candidate belongs to this repository and candidate workflow, was dispatched on
master, completed successfully, has the selected attempt. Check the exact attempt endpoint, workflow path,
event=workflow_dispatch, head_branch=master and head_repository=this repository.
Dispatch head_sha may differ from selected source; authoritative source binding
comes from every product manifest.commit and the candidate tooling records. Both workflows must be rerun in full; rerunning only failed jobs is unsupported
and attempt-bound artifacts fail closed. The source must be an ancestor of origin/master. There is no
untrusted PR input or implicit relay selection.

Product and tooling must come from the same reviewed source. Candidate packaging
copies and hashes the three final product executables before a separate
`installed-checks` build in an isolated Cargo target directory. Its two tools
are uploaded separately and never become install assets. Each platform artifact
also contains a strict `${role}-tooling.json` record with schema=1, source_commit,
harness_sha256, target and exactly two file entries (name => sha256, bytes).
After the tooling build rehash all copied product inputs to prove unchanged. Feature-enabled tests
and strict Clippy checks cover these tools before upload. macOS tools are ad hoc
signed. A new candidate build is needed after the tooling lands; the earlier
25c5340 candidate cannot qualify this workflow.

Resolve downloads all three original five-file candidate asset sets, the Linux
AMD64 tooling and the original pinned bootstrap using pinned official Actions
and explicit run ID/token. It copies the exact manifests into role.manifest
names, mode 0600. A common tooling-source SHA-256 hashes the deterministic
`git ls-tree -r` records for the whole crates/marmish-native tree, Cargo.lock,
tools/v02-actions and .github/workflows/v02-installed.yml. Hash immutable sorted
git output with SHA-256. Require the selected source equals github.sha in this
first implementation, so workflow control, local action and candidate tooling
share exactly one immutable source. The tooling source binding additionally
covers the whole native crate's dependencies through that commit. This is a source digest, never a platform binary digest. The
Rust context command binds the repository, current installed-workflow run ID and
attempt, source, tooling digest, manifest digests, explicit relay and expiry
thirty-seven minutes after creation. It additionally pins candidate_run_id,
candidate_run_attempt, one fresh random 32-byte run nonce, bootstrap SHA-256 and
all three original tooling-record digests plus exact per-tool hashes/bytes. Context is uploaded as one current-run artifact.

Three concurrent matrix jobs use Ubuntu 24.04 AMD64, Ubuntu 24.04 ARM64 and
macOS 15 ARM64, fail-fast false, each with a 55-minute timeout. Their first step
records first-step time plus 52 minutes as the internal deadline, leaving a
three-minute runner setup margin beneath timeout-minutes=55. This is an internal
safety bound, not a claim to know the runner's real job-clock start. Context
expiry + ten-minute cleanup + five-minute margin must fit it. They download the matching candidate
assets and tooling and the pinned bootstrap from the selected prior run, plus
the common context from the current run. Checked-out source and common tooling source digest must match. Each binary
hash/size and target/source must match context before chmod0500 and execution.
The downloaded bootstrap's exact hash must match the common context before
installation, and identity-ready must repeat the same pins.
No tool is rebuilt after context creation. Install and prepare use a short
private canonical directory (Linux /tmp; macOS /private/tmp), fresh profiles and
explicit file storage. Workflow creates only a private canonical parent and
passes a nonexistent leaf, because prepare exclusively creates the workspace.
The driver checks canonical parent spelling. It creates a private utility-only
PATH containing exactly the install tools from the existing PTY harness and
asserts python/python3, uv, cargo, rustc and node cannot be found; a standard
/usr/bin PATH is insufficient. LANG=C works on both operating systems. An explicit
utility-only environment keeps Actions credentials and language runtimes out of
product processes. Real default-auto keychain is qualified separately.

The Rust driver also enforces identity_ready_at <= context.created_at+900.
Queue delays that miss this barrier are infrastructure failures, never product
passes. At launch server uptime is min(1800, context expiry minus launch time
minus the bounded protected Finish/cleanup budget); fail before launch if less
than readiness plus workload plus Finish minimum. The same explicit bound is
reported in server-ready. Ordinary work has the original context deadline.

The local JavaScript action receives explicit absolute paths, the actual job
deadline and a token defaulting to github.token. Exchange and run use the same
private workspace and API-budget receipt. Exchange uploads the local identity
and downloads exactly three records before the driver can enable any server.
Run owns exactly one Rust driver child and publishes each atomic public record
while it is running. Only the reviewed finite records are uploaded for
failure diagnostics; no runtime directories, identities, keys or raw logs.
A runner-initiated cancellation or hard timeout is always red with cleanup
unproven; its roughly ten-second signal escalation cannot supply the internal
ten-minute cleanup reserve. The driver gets TERM immediately but only an internal
supervisor timeout can use that reserve. The ephemeral VM supplies final teardown.
The artifact service transports records; Rust validates their full schema and
trust binding. The Actions coordinator cannot declare a command successful.

An always-evaluated rollup job requires successful resolution, downloads the
exact expected public record artifacts for this run/attempt, and invokes the
Rust rollup tool. Missing or failed cells, extra admissions, mismatched
provenance, unconfirmed cleanup or missing terminal records fail the rollup.
Rollup receives the matrix job result and refuses success unless all jobs passed.
It uses a context-pinned Linux tool binary, requires all nine directed cells and
exactly three admissions under ceiling four on each server. Its JSON scope is
installed-matrix, with explicit pending gates: auto-exit, benchmark, recovery,
policy, keychain, asset publication and HTTPS. It has no release-qualified flag.
Failure diagnostics use a distinct ignored `v02-installed-diagnostic-*` namespace,
limited to the same four sanitized public records.
The aggregate JSON and Markdown publish measured latency and throughput with
actual sample counts. A single sample per directed pair never implies a tail
percentile. Success still requires all three matrix jobs and the rollup green.

Validate with actionlint, local tooling tests, independent Claude design and
code reviews, then the actual hosted matrix. The first hosted run must prove
mid-run artifact exchange. Subsequent release gates add their concrete reviewed
driver modes and budgets. Immutable v0.2 release assets and both public HTTPS
installer paths are qualified after those gates; scripts/install.sh remains
unchanged until that controlled cutover.

## Input and API budget contract

All user-controlled shell inputs enter only through env mappings and are quoted;
never splice inputs.* into a run script. Validate positive decimal run/attempt,
40 lowercase hex source, and explicit supported relay before constructing URLs.
Use `npm ci --ignore-scripts` with no token in that step's environment. A serialized
concurrency group prevents overlapping installed runs. Each supervisor has a
shared 120-call budget across exchange and run (37-minute total context yields
at most 74 regular polls plus 18 exact downloads, retries consume remaining
capacity). Three roles use at most 360 REST calls, reserving at least 100 for
resolve, rollup and official artifact downloads. The complete run stays below
460 calls; consecutive cohorts also remain below 1000/hour. Record these bounds
and fail closed rather than resetting the budget. Workflow dispatch and manual
inspection share external API quotas and must not continuously poll.
