# Automatic GitHub release qualification

Beads `marmish-0aa`. The user requested automatic publication after end-to-end tests on 2026-11-25. This phase replaces the manual publication hold and private dispatch controller in the [v0.3.1 plan](v0.3.1-release.md). Historical preflight and the v0.3.0 release remain as recorded.

## Workflow

1. Keep the trusted master candidate trigger on a new native version. The ordinary candidate builds and checks all three release packages and their pinned installer. The publisher inspects its exact workflow ID, attempt, source, closed artifact inventory, bootstrap and ontology. Skip candidates with no release bump. Continue to exclude caveated candidates.
2. Run the installed streaming workflow as a read-only reusable workflow for all eight reviewed cohorts. Schedule one cohort at a time with fail-fast and up to three platform jobs per cohort. Cohort order is immaterial. The publisher has its existing concurrency key. Reusable calls do not take the manual workflow concurrency keys. Use the GitHub job matrix aggregate result, never an individual reusable-workflow output, to admit verification. Keep the manual diagnostics entry point. Bind candidate run, attempt and source to the publisher inspection. Each cohort installs the same archives using the candidate's pinned bootstrap, runs across Linux AMD64, Linux ARM64 and macOS ARM64, and must pass its native rollup. Give workflow-owned uploads distinct names per cohort while keeping manual artifact names compatible. The coordinator already qualifies its peer artifact names by run, attempt and cohort. Extend the artifact listing to at most five 100-entry pages for same-run qualification. Require a consistent total, the expected count on each page, exactly the total across pages, and unique IDs and names. Count drift and repeated valid entries caused by a shifting page boundary are a bounded consistency retry. The platform supervisor uses its existing deadline and persisted 120-call budget shared across exchange and run. The collector uses its own existing 120-second deadline and persisted API budget. Each page consumes one call. Reject malformed entries or excessive counts. Preserve single-page behavior for existing callers. Only the three platform jobs in a cohort may concurrently upload peer records.
3. Run the existing finite benchmark after the streaming matrix as a read-only reusable workflow on the same candidate. Keep its per-platform and aggregate reports. Keep native macOS regression available as an independent diagnostic and preserve ordinary candidate macOS checks. Maintain the previously used explicit relay endpoint as the release default, with a repository variable for an approved replacement.
4. Require successful qualification and benchmark before the independent inventory verification and the contents-write job. Require success explicitly for all direct dependencies. Explicitly grant the reusable calls only contents and actions read. Only the publisher receives contents write. The publisher consumes no gate artifacts and uses exact artifact IDs for trusted inspection and inventory. Both automatic and manual recovery entry points use this DAG. Recheck candidate artifact identities and digests before publishing. Use existing publisher recovery at the original candidate source, and at its exact installer-only child when the existing installer-cutover proof succeeds. Only the trusted automatic qualification path may use that direct child; validate the git parent and exact changed path, bind the candidate to the original SHA throughout, and keep manual installed diagnostics bound to their current SHA. Git must confirm a direct single-parent child of the candidate SHA, with only a modified executable scripts/install.sh, and bytes matching the inspected bootstrap. Other master advances require a fresh candidate at current master. Coordinate ordinary master merges while a release is in flight to avoid wasted work. Never bypass the latest master or candidate-attempt check.
5. Keep the real GitHub Releases draft/upload/verify/publication sequence. For versions from 0.3.1 onward, use the existing native 0.2.N/0.3.N grammar and tag parser. Draft creation and recovery match the prerelease flag for the intended version. Stable drafts specify prerelease false and make_latest false. Stable publication sets draft false, prerelease false and make_latest true. Release candidates remain prerelease and are never latest. Older native versions retain the historical prerelease convention, including recovery at a matching provenance marker. Update the release body to describe the installed tests and benchmark actually run and preserve the runtime/platform and historical findings. A disabled ruleset is inert; preserve classic protection checks and fail closed on active, evaluate or unknown ruleset modes. Keep master-ref, branch ancestry, asset digests, conflict checks, cutover and provenance rules. Publish assets only on GitHub. Mirror reviewed source, release source tag and completed installer cutover to Radicle manually outside CI. Verify Iris.

## Validation and rollout

Use workflow policy tests to prove the disabled/failed/skipped/missing qualification paths cannot reach the write job, that exact inputs and permissions are used, and that the cohort list and archive pinning stay closed. Exercise bounded listing pagination, incomplete or duplicate pages, source recovery checks and stable/prerelease behavior in Node. Run syntax checks, full release-tool tests, ontology and staged-diff checks. Obtain Claude design and integrated code approval.

Merge the reviewed gate, verify the publisher settings and enable it once on master. No prior held candidate is used for public assets. Dispatch a fresh ordinary v0.3.1 candidate at the reviewed master SHA because the version landed earlier. Later version bumps use the master push trigger. Observe all cohorts and benchmark, then verify the GitHub release page and assets, HTTPS installer selection, source and tag parity, and Iris bytes. Save sanitized timing and test evidence. If a gate fails, leave the workflow enabled and resolve the failure without publishing an unqualified release.

The prepublication installer tests install from pinned local candidate artifacts. Public release downloads and both HTTPS script sources are separate checks after cutover. If HTTPS installation fails, keep immutable assets and evidence and review a corrective installer-only commit or a subsequent release as appropriate. A successful publication-state record does not establish broad HTTPS installation compatibility.

A failed or cancelled qualification creates no tag, draft, public release or installer cutover. Re-run all jobs in the publisher or dispatch a fresh publisher using the same original candidate attempt for recovery within the 14-day artifact retention. Do not combine successful jobs or artifacts across publisher attempts. Partial tag, draft, public asset or cutover recovery uses the existing provenance marker, identical inventory hash, and all required gate jobs. An arbitrary master advance invalidates recovery rather than silently changing its source. The short-term restore Bead closes after the revised workflow is active on master and GitHub starts its fresh automatic gate.
