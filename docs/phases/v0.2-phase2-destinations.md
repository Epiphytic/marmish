# Phase 2 amendment: destinations and explicit SRV discovery

> Historical design: public-default restrictions are superseded by
> [White Noise defaults](whitenoise-default-relays.md).


**Design approved** by [independent Claude review](../reviews/v0.2-destinations-design-r1.md),
with the nonblocking grammar/lifecycle refinements below incorporated. This closes
a requirements omission, not an implemented capability. Historical [build plan](../build-plan.md)
Requirements and defaults assigns host/URL and explicitly configured SRV parsing
to Phase2. Approved [Phase2](v0.2-phase2.md), Local IPC and CLI, freezes ordinary
hosts/URLs/IPv6/aliases but does not define SRV. It does not explicitly defer SRV.
Phase1 acceptance remains the integration/activation gate. The separately reviewed
scheduling amendment may allow isolated codec/configuration work; this document
alone grants no early implementation exception.
No existing approved document or production dependency is changed by this draft.

## Inspected contracts and implementation gate

Legacy `tools/marmish_app.py::destination` splits remote@host, canonicalizes a
wss URL and requires configured membership; it does not perform SRV discovery.
Legacy transport resolver helpers resolve socket addresses, not SRV service
records. `marmish-core::config::RelaySet` validates URLs without DNS and explicitly
is not an egress boundary. Native `transport::RelayPolicy` is the authoritative
immutable canonical URL/route ceiling (1..16 relays); it rejects unsupported
plaintext and routes ordinary hosts directly in auto, every host through Arti
in always, and onion through Arti in auto. Its direct Tokio TCP connector resolves
A/AAAA; its Arti connector passes host+port into Tor. Neither supplies SRV.
The inspected native manifest/Cargo.lock contain no Hickory/trust-dns SRV resolver.

Reuse URL canonicalization and RelayPolicy rather than duplicate transport code.
Read-only official crate-source audit selects the upstream high-level resolver:
`hickory-resolver = {version="=0.26.3", default-features=false,
features=["tokio","system-config"]}`. MSRV1.88 fits this workspace; license
MIT OR Apache-2.0. This uses the library's DNS transport, parsing, retry and CNAME
handling, not a Marmish DNS transport or packet parser. No dig/host/Python or
new mandatory DNS-server setting. Confirm the complete feature graph and all-target
compilation during implementation; no dependency/lockfile has been edited.

Confirmed public contracts are `system_conf::read_system_conf`,
`ResolverConfig::{into_parts,from_name_servers}`, `NameServerConfig::udp_and_tcp`,
`Resolver::builder_with_config`, `ResolverBuilder::with_options/build`,
`TokioRuntimeProvider`, `Resolver::srv_lookup`, and `Lookup::{answers,valid_until}`.
Linux reads resolv.conf; Apple reads SystemConfiguration's global DNS dictionary.
This is not full macOS scoped/split-DNS emulation: system configuration unavailable
or unable to resolve the explicit owner fails, without a public-resolver fallback.

## Frozen CLI grammar

`-i NAME` selects the local named identity/profile only; it never takes a private
key, remote Unix login or secret value. NAME uses the reviewed local profile-name
validator. `-u ACCOUNT` selects a remote npub or configured remote alias, never
Unix user mapping. ACCOUNT npub must decode to exactly32bytes with the correct
Nostr public-key prefix/checksum; nsec and ambiguous hex/name strings are refused.

Exactly one of these destination forms precedes the required command separator:

- `marmish [-i NAME] npub@HOST -- /absolute/program args...`
- `marmish [-i NAME] npub@wss://HOST[:PORT]/ -- /absolute/program args...`
- `marmish [-i NAME] npub@srv:_SERVICE._tcp.DOMAIN -- /absolute/program args...`
- `marmish [-i NAME] ALIAS -- /absolute/program args...`
- `marmish [-i NAME] -u ACCOUNT --relay URL [--relay URL ...] -- /absolute/program args...`
- `marmish [-i NAME] -u ACCOUNT --srv NAME [--srv NAME ...] -- /absolute/program args...`

With -u, an optional sole positional HOST, full URL or srv:NAME may replace the
corresponding explicit relay options. With no relay/destination, `-u npub` uses
only the explicitly configured named profile relay set; missing/empty configuration
returns invalid_destination, never a public default. `-u ALIAS` with no relay uses
the alias's exact set, which must still equal the profile set. Never
accept inline ACCOUNT@... together with -u, multiple destinations, or mixed
--relay/--srv/inline relay sources. There is no comma-separated relay shorthand.
Use repeated options; command argv after -- is never reparsed as CLI options.
The `srv:` prefix is reserved and always selects SRV grammar: `npub@srv:443`
is not a host/port destination. A literal host named srv with port443 must use
`npub@wss://srv:443/`.
The separator is mandatory even when command arguments appear unambiguous.

HOST is an ASCII DNS name, IPv4, or bracketed IPv6, with optional decimal port
1..65535. Bare HOST becomes wss://HOST/ (443 implicit). Unbracketed IPv6, zone IDs,
userinfo, URL query/fragment, backslashes, controls and whitespace are rejected.
Full URLs reuse native canonicalization: wss normally, ws only for a valid v3
onion endpoint over Tor; no arbitrary paths beyond the existing accepted URL
contract. Explicit URLs preserve their canonical path if native policy permits it.
Trailing DNS root dot and default ports use the native canonicalization result;
no alternate host parser may create a second policy identity.

Aliases resolve to the approved `AliasTarget {remote:Account,relays:RelaySet}`:
exact npub plus exact canonical URL set, never a Unix user or discovery expression.
Alias names are distinct from npub syntax and use a validated config identifier.
ALIAS alone selects both fields; alias via -u must agree with the explicit relay
set, not silently override it. Repeated canonical URLs deduplicate before the
1..16 distinct limit, with raw option count capped16 to prevent unbounded parsing.
A standalone alias cannot be combined with inline/explicit relay overrides.
SRV-derived sets can be written into an alias only by explicit configuration;
normal invocation never rewrites aliases or profiles.

## Exact ceiling, identity and resolution boundary

The selected account is independently authenticated; DNS/relays never choose a
remote Nostr identity. All selected canonical relays must equal the running named
profile's configured RelayPolicy set. A single inline relay cannot silently
narrow a configured multi-relay daemon, nor can a discovered target enlarge it.
Mismatch returns destination_policy_mismatch before account activation,
publication or command admission (SRV must first resolve to permit this comparison). Configure a matching explicit profile first;
CLI selection never swaps a live daemon's connector or opens another MDK owner.
This conservative equality rule preserves the approved account+exact relay-set
alias contract. No public endpoint, DNS search suffix, NIP metadata or advertised
peer relay is an implicit fallback.

SRV resolution runs only in the short-lived CLI process, before IPC to the
daemon and before any authenticated account operation. The daemon and MDK actor
never resolve SRV. The CLI submits only the resulting canonical exact relay set;
the daemon independently checks equality with its immutable connector policy. The same approved exact ceiling covers account setup,
KeyPackages, Welcome, rooms, retry and discovery. Resolver traffic is separately
bounded setup traffic; SRV consent does not authorize arbitrary relay dials.

## Explicit SRV lookup semantics

`srv:NAME` and --srv NAME require a fully qualified ASCII DNS service owner:
_SERVICE._tcp.DOMAIN, with one optional final dot, total wire-name length<=255,
labels1..63, no empty interior labels. SERVICE is caller supplied, not inferred
as _nostr or _marmish. Query that absolute name only; no resolver search domains,
service guessing, TXT/HTTPS/NAPTR fallback, or query for the npub/alias. SRV
syntax explicitly authorizes direct DNS setup through the host's configured
recursive resolvers. Read system configuration once, discard domain/search and
all inherited resolver options, deduplicate server IPs in configured order, retain
at most the first3, and rebuild `ResolverConfig::from_name_servers` using ordinary
UDP/TCP configurations. Empty/unavailable configuration fails before lookup; no
Google/Cloudflare or other compiled-in/public fallback. Reject unspecified or
multicast server addresses. Reject IPv6 link-local nameserver entries because
conversion to IpAddr cannot preserve their required interface/zone; if no usable
servers remain, fail closed instead of guessing an interface or public resolver. This is normal system-DNS consent, not authorization
for additional relay dials. Input is capped4096bytes and16 distinct owner names;
reject duplicate canonical owners. DNS is never triggered by an npub or alias.

Construct `ResolverOpts::default()` then explicitly set timeout1second,
attempts1, num_concurrent_reqs1, max_active_requests1, cache_size0,
use_hosts_file=ResolveHosts::Never, preserve_intermediates=true,
positive_max_ttl300seconds, negative_max_ttl0, try_tcp_on_error=false. Keep the
library's normal UDP-truncation TCP behavior; disable optional opportunistic
transport probing and do not enable DoH/DoT/DNSSEC features. Submit absolute
root-terminated owner names serially through `srv_lookup`, under ONE original
5second monotonic deadline shared by the whole owner set; never renew it for
another owner, CNAME, nameserver or retry. No extra application retries.

The pinned library bounds recursive CNAME query depth at8 (an internal depth
limit, not a promise of eight additional aliases). Its attempts1 means an initial
request plus at most one counted retry, not one total wire packet. Busy responses
do not decrement that counter; the outer deadline remains authoritative. At most
3 imported nameservers and one concurrent server request limit fanout; UDP/TCP
fallback and CNAME work remain library-owned. This design claims neither an exact
wire-transaction ceiling nor that the application prevents the decoder from
allocating the bounded DNS response before validating its record count. After
lookup reject more than16 SRV answer records total across owners before dedup,
malformed/empty/unavailable answers and any failed owner: no partial selection.
Only answer-section SRV records from the resolved owner/CNAME chain are eligible;
validate preserved chain/answer ownership, reject cycles/unrelated records, and
ignore additional-section addresses. Target '.' means service unavailable.
DNSSEC is not required or claimed; TLS and Nostr authentication remain mandatory.

Own this short-lived setup resolver and all its clones inside a dedicated
current-thread Tokio runtime on a setup thread, before creating the account
transport. Timeout/drop the lookup, drop resolver/provider handles and then drop
that runtime on every exit, cancelling its asynchronous DNS tasks before reporting
a snapshot/failure; no persistent DNS worker, detached task or refresh timer.
This is library lifecycle containment, not a new DNS implementation. The pinned
Tokio provider stores spawned tasks in an Arc-held JoinSet, so dropping only a
lookup future is insufficient evidence of cleanup. Test runtime teardown and
socket/task absence with injected local fixtures. System configuration loading is
synchronous upstream platform I/O: it runs off the MDK actor; the5second deadline
is checked immediately afterwards and bounds DNS resolution, but is not a claim
that an OS configuration call itself can be forcibly interrupted. No query is
started if configuration loading has already exhausted the deadline.

All accepted targets must be absolute ASCII DNS hostnames, valid port1..65535,
not IP literals, not onion and not URL syntax. Convert each to wss://TARGET:PORT/
and validate through native RelayPolicy, then deduplicate the complete set.
SRV is explicit endpoint-set discovery, not RFC2782 weighted load balancing:
all returned priorities/weights are parsed as U16 but the full bounded set is
selected and canonicalized, not sampled; existing transport connection order is
unchanged. Document this behavior rather than pretending the canonical sorted
connector honors priority/failover weights. Caller-configured RelayPolicy equality
must hold for the complete discovered set or the operation fails closed.

TLS SNI/certificate identity, HTTP Host and WebSocket URL use the SRV TARGET,
not the service owner, and the SRV port is used exactly. No downgrade to plaintext,
certificate bypass, redirect follow or connection to an SRV-owner address occurs.
A/AAAA lookup for the validated target remains the existing direct connector's
bounded responsibility; this is not an IP egress/rebinding protection claim.

Resolve once per invocation, validate the complete result against the existing
profile ceiling, and discard the resolver/results after use. Under exact equality,
SRV confirms the configured relay set; it cannot add or replace a relay. There is
no application snapshot cache or TTL-based reuse between invocations, consistent
with cache_size0. Record-count/TTL validation may inspect lookup metadata without
establishing a cache. No background SRV refresh mutates an active account's ceiling.
Durable command handles remain bound to their previously frozen exact relay set;
status/retry does not switch relays or recreate a command because DNS changed.
When explicit SRV is supplied on a later invocation, resolve afresh and enforce
that same equality. DNS changes require explicit profile reconfiguration/restart,
not retry-induced policy widening.

## Tor privacy and finite failures

SRV is supported with off, or auto when the configured profile contains only
ordinary direct endpoints. Always and mixed/onion auto profiles reject explicit
SRV as srv_route_unsupported BEFORE system configuration loading or any DNS.
Explicit SRV on an ordinary auto profile authorizes direct system DNS, consistent
with that mode's existing ordinary-host routing. Direct
URLs/hostnames continue to work with always using Tor-side hostname resolution;
onion never enters system DNS. An onion SRV owner or returned onion target is
always rejected before querying/connecting respectively. No direct fallback after
Tor failure, and no claim that Arti's ordinary hostname API supports SRV queries.
Users can explicitly supply the resolved URLs with always, without local SRV DNS.
Supporting SRV over Tor later requires a separately audited Tor-capable DNS query
transport, not a hidden resolver exception.

Closed failures: invalid_destination, conflicting_destination,
invalid_remote_identity, unknown_alias, relay_count, destination_policy_mismatch,
invalid_srv_name, srv_route_unsupported, srv_backend_unavailable,
srv_timeout, srv_response_limit, srv_invalid_response, srv_unavailable,
srv_resolution_failed. Map to Phase2's local/transport exit255, no new invocation
on pre-admission failure. Logs include finite stage/category/counts only; no raw
DNS errors, response bytes, account identity, credentials or private query names.
A server command already accepted keeps running when later resolution fails.

## Acceptance and handoff

Root owns CLI/config normalization; resolution is bounded CLI pre-IPC setup
that supplies the canonical set for independent daemon validation; transport owner keeps the unchanged
immutable connector and TLS checks. Resolver tests use injected DNS responses and
clock, never require live public DNS. Verify all grammar collisions, IPv6/ports,
npub/nsec/alias distinction, exact-set equality,16limits, malformed records,
CNAME loops/depth, imported-server/option bounds, total deadline, partial failures, TTL0/no inter-invocation reuse,
service unavailable and target SNI/Host/port. Prove zero DNS calls for bare onion,
SRV under always or mixed/onion auto, and onion SRV owner; zero out-of-set dials on SRV changes.
Test resume with the same durable handle after DNS changes, no fresh invocation,
and no actor/blocking DNS work. Compile and test the chosen audited resolver on
Linux AMD64/ARM64 and macOS before claiming SRV support. The selected resolver/source contracts above are audited read-only; actual dependency
resolution, teardown/response validation and target compilation/tests remain
implementation gates. Design approval does not claim implementation or validation.
