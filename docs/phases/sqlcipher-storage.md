# SQLCipher storage follow-up

Implementation completed under Beads `marmish-315.13`; full and final focused Claude code reviews approved. See [validation and review dispositions](../reviews/sqlcipher-validation.md). The design below records the reviewed contract.

The user selected SQLCipher for Marmish after the phase-2a live transport smoke. Beads `marmish-315.13` tracks this storage increment, before production transport integration. The existing command engine uses ordinary SQLite for metadata, command requests and queued stdin, and separate plaintext stdout/stderr files. This increment encrypts both state and retained output while preserving detached execution, durable admission, replay fencing and explicit output gaps. It does not enable production networking or change Unix account policy.

## Dependency and encryption contract

Align the SQLite dependency with the inspected MDK baseline: exact `rusqlite =0.40.1`, `default-features = false`, `bundled-sqlcipher-vendored-openssl`, and the root `libsqlite3-sys` patch at `https://github.com/rusqlite/rusqlite.git`, revision `5ae7fdf83085c595fd54f977b3a56ccacabaf16b`. Retain the updated root lockfile. Do not enable SQL statement tracing. This is a build dependency alignment, not permission to alter the shared dirty MDK checkout. Dependency fetches are permitted build setup; verification runs locked/offline after caches are ready. Record the actual compiled SQLCipher version and resolved native dependency in evidence. Do not claim that a feature flag alone encrypts data.

Add one internal cipher/key module using rusqlite and existing protected-path primitives. Before schema access, require a nonempty `PRAGMA cipher_version`, set SQLCipher compatibility 4 and memory security, apply the key, then verify an actual schema read. Set `temp_store=MEMORY` so plaintext temporary tables do not spill. Preserve main-database WAL and `synchronous=FULL`; SQLCipher encrypts WAL page content. Keep diagnostics fixed and never include SQL text, keys or arbitrary database errors. Follow the MDK keyed-open ordering inspected at `crates/storage-sqlite/src/connection.rs:1124–1175`. Official references: [SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/) and [SQLCipher storage design](https://www.zetetic.net/sqlcipher/design/).

## Key lifecycle and existing state

Use a cryptographically random 32-byte master key in a versioned, owner-only file under the existing private state root. Initialize only under the frontend lock, using an exclusively created private temporary file, full write and file synchronization, atomic non-overwriting publication, and directory synchronization before creating encrypted state. Validate exact ownership, regular type, mode, single-link count and length without following symlinks. If initialization is interrupted, never overwrite a partial or existing key: fail closed with a recoverable diagnostic. Existing workers load this same key locally without generating a replacement. A missing key for an existing database, wrong key, malformed key or unsafe permissions fails before logical state mutation or maintenance; SQLite may checkpoint an existing encrypted WAL without authenticating application content; never silently create a new identity/database, fall back to plaintext, or retry a launch.

Hold key bytes in zeroizing containers; do not implement Debug/serialization for keys. Use a standard HKDF-SHA256 derivation with fixed versioned domain labels and database context to obtain separate raw SQLCipher keys for the state DB and each job/stream DB. The master key has random entropy; use SQLCipher's documented raw-key syntax with a generated zeroizing hex representation rather than paying a passphrase KDF on every worker/read. No key enters OS arguments, environment, child command inheritance, diagnostic output or the command journal. File descriptors remain CLOEXEC. Worker arguments stay root path and job ID. Key rotation, external key stores and supplied storage-key interfaces are deferred.

The protected key file enables unattended offline workers. It does not protect against compromise of the same Unix account or acquisition of both key and database, and it is not a claim of whole-disk protection. Backups must account for the key separately; loss of the key loses stored data. SQLCipher does not encrypt arbitrary child-created files, swap, core dumps or execution memory.

This project is unreleased. Existing plaintext engine roots are rejected without mutation; no automatic in-place conversion, deletion, rekeying or purge is attempted. Tests construct such roots and prove their bytes remain intact. A later explicit migration utility can handle real retained state if needed. Existing active plaintext workers are unsupported across this format change: operators must finish them and preserve the old root before selecting a fresh encrypted root. Document this prominently instead of silently abandoning running jobs.

## Encrypted output with the existing spool contract

Keep `Spool::open/append/close/read` semantics, `OutputCommit`, `IoGuard` and worker pending-commit semantics; `open` and `read` gain a borrowed key-ring argument as specified below. Replace each job's plaintext stdout/stderr file with a SQLCipher database under distinct versioned names. Use DELETE rollback journaling with `synchronous=FULL`, memory temporary storage, an explicitly configured and verified 4096-byte cipher page size, and bounded BLOB chunks indexed by logical byte offset. Record and verify the format version, job ID and stream context inside the encrypted database. Do not create a private cryptographic chunk-file format.

Appending output commits encrypted bytes durably before `Store::commit_output` publishes the retained cursor, preserving the existing two-step crash boundary. Keep the existing before/after spool-sync fault points around that durable commit. On recovery, validate a contiguous prefix, remove an uncommitted suffix beyond the main DB's retained cursor transactionally, and preserve existing storage-failure/limit/uncertain-tail gap semantics. Corrupt or missing output must never be returned as plaintext or replaced silently with valid-looking bytes. Read only bounded ranges and enforce existing logical byte caps; coalesce bounded chunks so tiny writes cannot produce unbounded row overhead. Document and test a finite physical page/rollback-journal overhead above the logical cap. Output overload still drains/discards and records a gap.

All stream DB files and rollback journals use owner-only regular-file validation, symlink rejection, and private parent directories. Add stat-based validation following `StateRoot::verify_db_files`; do not open and close an extra descriptor for an active SQLite inode, which would release process-wide POSIX locks. Verify database descriptors are CLOEXEC. Close a spool connection before expiry/removal; remove the DB and its known journal under the existing I/O guard, sync the parent, and ensure an expired stream cannot be recreated by a live worker. No WAL/SHM stream files are expected with DELETE mode; unexpected unsafe sidecars fail closed. Plaintext legacy spool files in an existing root must not be opened as new-format databases.

## Review refinements: bootstrap decision table

The first review is recorded in `../reviews/sqlcipher-plan-initial.json`. The following rules refine the earlier prose and take precedence where more specific. Acquire and verify `FrontendGuard` first. Establishing the existing private directory/lock scaffolding may create lock files; rejecting legacy state never creates a key or changes database/spool contents. Before opening any SQLite connection to this root in this process, classify the main file using a protected descriptor and its first 16 bytes, then close it. Reject the `SQLite format 3\0` header. Inspect job directory entries for legacy plaintext `stdout`/`stderr` names without opening their content. Any legacy data is rejected intact, even if a key also exists.

| Final key | Main database | Other state | Result |
| --- | --- | --- | --- |
| Absent | Absent or zero bytes | Empty jobs directory; no DB WAL/SHM/journal | Initialize key durably, then database |
| Valid complete key | Absent or zero bytes | Empty jobs directory; no DB WAL/SHM/journal | Reuse key; complete first database initialization |
| Valid complete key | Nonempty encrypted candidate | Safe files; no legacy spools | Load key, authenticate schema, then recover; failed authentication never mutates data |
| Absent/invalid key | Nonempty database | Any | Fail closed; never regenerate |
| Any | Absent/zero-byte database | Any job directory or DB sidecar | Fail closed; never orphan-reap or create state |
| Any | Plaintext main DB or legacy spools | Any | Reject intact; no conversion |

All combinations outside the permitted rows fail closed. Workers have no initialization path. A valid key without a database is accepted only for an otherwise pristine root. Name the final file `engine.key`, with an 8-byte version magic followed by exactly 32 random bytes; name the private staging file `.engine.key.pending`. Use `openat` with NOFOLLOW/CLOEXEC and exclusive creation, verify uid/type/mode0600/nlink1/exact length, sync, then `renameat2(RENAME_NOREPLACE)` and sync the directory. Never publish a partial final key. A stale staging file may be removed and initialization retried automatically only in the first pristine-root row after validating its owner/type/mode/link count; otherwise leave it untouched and fail with a fixed diagnostic. Never overwrite the final file. This provides automatic recovery from interrupted pristine initialization without an ad hoc repair tool or deleting user state.

## Review refinements: exact key interfaces

Introduce `cipher::StorageKeys`, a non-Debug/non-Clone zeroizing master-key holder. Keep it out of the Debug-derived `StateRoot`. `StateRoot::initialize_storage(&FrontendGuard) -> Result<StorageKeys>` verifies the guard's root identity and applies the table; `StateRoot::load_storage_keys() -> Result<StorageKeys>` only loads the final protected file. `Engine` owns keys alongside its root and store. The worker entry point loads its own holder before opening the store and keeps it through supervision. `Store::create_frontend`, `Store::open_worker`, and their internal connection function accept `&StorageKeys`. `Spool::open/read` and the worker output-pump setup accept the same reference; append/close remain key-free because the connection is already keyed. Tests initialize under an actual frontend guard. Do not implicitly initialize from spool or worker code.

Pin `hkdf =0.12.4` and `hmac =0.12.1` as the HKDF implementation/transitive resolution, retaining SHA-256 at its existing pin. HKDF salt is the fixed bytes `marmish-storage-hkdf-v1`; info starts with `marmish-storage-key-v1\0` followed by either `state\0` or `spool\0` plus the exact 16-byte job ID and one stream byte (0 stdout, 1 stderr). Derive exactly 32 bytes. Never use variable-length ambiguous concatenation. Apply the raw-key representation through a narrowly scoped FFI key call with a zeroizing generated `x'64hex'` buffer; SQLCipher's key API still needs that documented raw-key representation. Do not format secret-bearing rusqlite errors or SQL statements. The raw key and representation never derive Debug, serialize, or use unwrap/expect.

The first reviewer suggested disabling process dumpability and core dumps. That is deferred: Engine is an embeddable library and those are process-global irreversible restrictions; they also do not isolate same-uid commands, which can read the protected key file directly under this baseline. No claim is made to protect keys from same-account commands, ptrace, core dumps, swap, or a whole-root backup. A future executable-level hardening policy can apply those restrictions deliberately. The current change's confidentiality claim is encrypted database/output copies when their key is unavailable, plus filesystem access restrictions. Backup instructions explicitly exclude `engine.key` when producing encrypted-data-only backups.

## Review refinements: spool schema, errors and limits

Use `stdout.db`/`stderr.db` with format metadata and a chunks table keyed by `start`, carrying indexed `end` and bounded BLOB `data`. Chunks have at most 16,384 bytes. Fill the final partial chunk before adding another row so row count is at most ceil(retained/16,384). Use bounded `substr` SQL reads; do not enable blob APIs just for unbounded blob materialization. Validate contiguous starts/ends and `length(data)` without loading all payloads. Recovery inside a row uses a bounded substring UPDATE, then deletes later rows. Validate metadata against the job, stream and format context.

Set/verify `cipher_page_size=4096` before key/data access. Bound each stream DB with `max_page_count = ceil(2*logical_cap/4096)+64` and reject an existing DB already exceeding that count. The physical DB is therefore bounded by approximately twice the logical cap plus 256 KiB; journal files have a conservative bound of twice that DB bound plus 64 KiB. Verify these bounds around transactions and exercise tiny appends and cap saturation; this overhead is explicit alongside the existing logical quota. Unexpected bounds violations stop persistence and report storage gaps rather than continuing to grow. No stream WAL/SHM is allowed.

SQLITE_BUSY/LOCKED maps to Busy without changing in-memory commit, produced bytes or failed state; worker flush retains its bytes and retries. Other persistent storage failures preserve already authenticated prefix when available and record a StorageFailure gap; a corrupt/mismatched stream with retained data yields no plaintext, a gap covering unavailable produced bytes, and no deletion/recreation/write. An empty keyed stream DB without schema is a crashed initialization and can be initialized only in writer open. Spool creation is allowed only for an open job; reader opens are read-write WITHOUT CREATE so hot rollback journals can recover. Always use SQLITE_OPEN_NOFOLLOW, including the main DB. Never use exclusive locking mode.

Place BeforeSpoolSync after SQL writes and immediately before COMMIT; AfterSpoolSync follows successful COMMIT. Process-death tests inspect the stream DB after both faults: before commit rolls back, after commit leaves an uncommitted logical suffix which writer recovery trims. Preserve subsequent main-metadata fault points. Main database uses secure_delete ON, while acknowledging old encrypted WAL frames can retain historical data until checkpoint/reuse.

Generalize stat-only file checks and CLOEXEC descriptor checks to all known DBs/sidecars; validate before opening and after transactions. Expiry/removal runs only after acquiring the job lock (ensuring the worker and its spool connections are gone), then the I/O guard. Delete DB and journal safely and idempotently, including the journal-only crash remainder; sync parent directory changes. Add crash tests between DB and journal removal and reject a journal-only stream on normal reader/writer open rather than inventing a database. Update hard-coded names in engine public/fault tests and launcher tests. The plaintext credential file is an execution-authority token, not retained terminal content; job names, sizes, mtimes and WAL-index metadata remain visible and are explicitly outside content-encryption claims.

Add feature-gated faults around key staging/publication/directory sync and initial DB creation/schema creation, testing both accepted pristine recovery and refusal with surviving jobs. A key-load failure before worker claim follows the existing bounded worker-start attempt limit (three), never indefinite respawn or command rerun. Test SQLCipher operation when memory locking is unavailable; memory-security allocation failures must not silently disable encryption. Build evidence records the cached native git revision, actual openssl-src resolution and required Perl/make/C compiler tooling. No encryption source changes begin until this refined design receives final approval.

The final plan review (`../reviews/sqlcipher-plan-final.json`) approved implementation. A valid keyed database with no tables may finish initial schema creation only when the root is otherwise pristine with no jobs; authentication always precedes maintenance or orphan reaping. Unsupported `RENAME_NOREPLACE` fails with a fixed diagnostic and never falls back to overwriting rename/link. Zero-byte database plus sidecars remains fail-closed; diagnostics identify the known artifact names without exposing content.
