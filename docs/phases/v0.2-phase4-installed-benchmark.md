## Workload and meaning of cold

Run three independent concurrent platform jobs: Linux AMD64, Linux ARM64 and
macOS ARM64. Each owns a fresh installation, server profile and distinct client
profile. Each client targets only its same-platform server through the explicit
configured direct relay set. There are three directed pairs with exactly four
commands each: cold index0 and warm indices1..3, twelve samples total. Cross-
platform matrix cells remain nine separate n=1 observations. There is no nine-
pair benchmark expansion and no Arti predecessor; Tor evidence is optional.

Cold means the first command through fresh installed client/server daemons and
an as-yet unopened command room. Both daemons must have reached actual active
status first. It is not a claim to measure process launch, DNS, TLS handshake or
Tor bootstrap independently. Warm commands use the same two live daemons,
profiles and authenticated room; each command still runs a fresh installed CLI
process. No daemon restart, room substitution, alternate relay or profile reset
is allowed between samples. The handle's remote account and session must match
the cold sample for all warm samples; invocation IDs must be distinct.

Use exactly the existing native fixture executable and fixed vector0 for all
four samples: 16384-byte immutable stdin, 131072-byte stdout, 131072-byte stderr,
all256 byte values and exit7. Retain the existing quoted/metacharacter/newline/
Unicode/non-UTF8 argv coverage. Only a deterministic per-sample nonce changes;
sizes, vector algorithm, command shape and binary stay constant. Nonce is SHA256
of canonical JSON plus LF for `(installed-benchmark/1,context_digest,role,
client_account,server_account,index)`. The fixture is the only granted canonical
absolute executable; fixed cwd is its owned parent and receipts remain sibling
`receipts/<validated_nonce>.receipt`, never passwd HOME. No shell grant exists.

## Deadlines and command scheduling

The `prepare --cohort benchmark` executable checks2670 seconds remaining before
installation (600 conservative preparation reservation plus2070 launch budget).
Prepare plus supervisor handoff must fit within450 seconds to pass the separate
2220-second cohort entry check; otherwise it fails closed.
This allows at most630 seconds of initial queue/download age. Its existing
install/setup operations still share a single300-second bound, additionally
capped by created_at+900 for the identity-ready publication. Thus late entry
may have less than300 seconds; passing entry never promises the full allowance.
The separate `cohort` executable checks2220 seconds remaining BEFORE its two
installed setup updates/config writes, which share one150-second deadline; it
then rechecks the2070-second launch requirement after both updates. Before
daemon launch require
at least2070 seconds to the original Context expiry: 150 for activation,1200
for the whole four-command workload,360 for cleanup,60 for stop,300 for report/
artifact/failure margin. Record one local monotonic launch origin L. Start both
daemons before awaiting readiness, and require each active by L+150. Server
uptime remains the fixed1800 seconds from its own process origin; never extend
it or retry with a fresh lifetime. The workload ends by L+1350; cleanup and stop
must complete by L+1770, leaving30 seconds before the server uptime. Both
daemon stop operations share that same L+1770 deadline; a timeout remains red
and its bounded5-second owned-group kill/reap may finish by L+1775. Hosted
runner suspension is not supported by this monotonic margin: daemon uptime is
suspend-aware; a suspended/late runner fails rather than claiming protected
cleanup from an expired owner. Context
expiry is an additional hard bound, never a replacement budget.

Run samples serially. Use actual installed `marmish --no-autostart --stdin
--wait-seconds 300 <server-npub> -- <fixture> <fixed-argv>` through the live
client daemon, with a single invocation per sample. Each CLI child has at most
330 seconds, capped by the shared L+1350 workload cutoff. No hidden rerun, fresh
invocation on timeout, discarded failed sample or continuation to warm samples
after failure is allowed. Internal retries within one CLI process preserve
the same invocation and are allowed; they are not new sample submissions.
The existing15-second cold Prepare/room-open bound is unchanged: failure is
`local_busy`, including warm busy while prior Finish obligations drain. The CLI does not
distinguish room-Prepare busy from non-ambiguous Submit busy: exit255 with no
handle is still unknown admission to this harness and preserves its tree.
A timeout, delivery_pending exit254, engine/input
warning, gap, wrong exit or output mismatch permanently fails the cohort.

Require actual exit7 and exact stdout/stderr bytes after separating the strict
durable handle line from remote stderr. Verify all handle fields, canonical
fixture argv hash and per-sample immutable fixture receipt independently. Each
successful sample must have the expected authenticated terminal outcome and
output before its measurement qualifies. A fixture receipt or relay publication
alone cannot substitute for successful client observation. No new remote
operation or artificial client ACK is introduced.

## Full ledger and cleanup

After sample3 require all four independent receipts and exactly four distinct
handles sharing one client/server account pair and session. Build the sealed
guard's expected binding map `(principal,invocation)->(session,submit_sha256)`
for all four. Read the complete actor-owned ledger through bounded cursor pages,
including every unexpected row. Require exact equality, each admitted once,
exit7, valid authority, closed gap-free streams and expected counts. Optional
server output hashes remain unknown when unavailable; client and fixture hashes
are independently mandatory, with no invented full-output hash claim.

Explicit cleanup allocates its new fence before refreshing every row. Require
all rows observed at or after that same fence, terminal worker Exited,
no active/uncertain work, no pending observation, engine_quiesced true and the
same actual live owner. Use only `EngineTree::remove_installed` with the sealed
guard; preserve the original profile/commands inode receipt and revalidate it
after the last await before synchronous unlink. Verify same-fence quiescence
after removal, then ordinary stop/join both daemons and require their actual
lifecycle flags. Neither CLI exit nor count/uptime exit grants deletion.

SIGTERM latches failure and invokes the same bounded cleanup. Failure cleanup
may cancel only already known owned fixture rows through the existing actor
cursor API (four distinct known rows, requiring a coordinated reviewed
row-bound argument to installed cleanup cancel: matrix3, benchmark4;
not a global increase of the three-row matrix bound); retain source bindings and exact handles once a successful run_input return exposes
them. run_input discards partial output on timeout/input failure: such a sample
has UNKNOWN admission, no invented parsed handle and no cancellation authority
for it. Preserve the private tree and record cleanup red; previously completed
samples' known handles remain available for bounded cancellation. Do not claim
a streaming handle observer or cancel an unseen invocation. Unknown admission, missing
handle, dead owner, changed receipt/fence, cleanup failure or exhausted budget
preserves private state and records cleanup red. Never signal an artifact PID or
delete an unproved engine subtree. Ordinary stop/disconnect does not cancel jobs.

## Closed result and rollup

The private cohort interface is
`async fn run(ctx:&Context,workspace:&Path,output:&Path)->Result<()>`; its module
also owns `fn validate(record:&BenchmarkResult,ctx:&Context,identity:&IdentityReady)->Result<()>`
and the closed serde result types. Validate role and identity-ready digest
against that exact record; derive both accounts, nonce and installation tuple
from it. Add a strict single-role identity reader; the existing exact-three
reader remains unchanged for matrix. This module also owns its n=1/n=3 summary.
Dispatch supplies no engine/DB handle. The
result writer uses exclusive immutable publication, including on failure once
the Context and own identity were validated. Root owns workflow/artifact merge;
only three benchmark-result records are required, with no inter-job rendezvous.

BenchmarkResult has schema1, kind `benchmark-result`, Context digest, role,
identity-ready digest, installation/provenance tuple, route `direct`, exact
configured relays, fixture hash, planned_samples4, successful_samples0..4,
samples (exactly four ordered slots), failure category, cleanup/stop flags and
complete. A sample has index0..3, temperature `cold` or `warm`, disposition
`passed|failed|not-run`, bounded finite failure category or null, nonce/vector,
optional exact handle, argv hash, expected/measured stream counts/hashes,
optional command_wall_ns and optional payload_bytes_per_second. Missing
observations are null, never fabricated zero. Failed sample timings may be
recorded but have qualified=false and cannot enter successful statistics.
All fields and nested types reject unknown/duplicate fields as applicable;
strict validation recomputes expected nonce/bytes/hashes/binding/provenance and
requires exact four slots, four successes and all cleanup flags for complete.

Measure command_wall_ns using the existing run_input monotonic interval around
the CLI process and joined output drains. This is end-to-end installed command
wall time including encrypted request, execution, output transfer and Finish
handling; it is not network RTT, one-way latency or isolated execution time.
Verified output goodput = (stdout_bytes+stderr_bytes)*1e9/command_wall_ns, excludes
stdin and requires positive measured duration and all byte/terminal checks.
Report payload counts, direct relay set, installation/source/tooling tuple and
sample boundaries. Exclude the handle line from stderr byte counts and
goodput. No invented throughput acceptance target exists.

JSON and Markdown report all12 sample slots, cold n=1 and warm n=3 per platform.
Warm min/median/max/range may summarize only the three comparable successful
warm samples for that platform. Keep cold separate; do not pool platforms or
present p95/p99, confidence intervals or chunk counts as independent samples.
Report unqualified/null metrics and fail the always-run strict rollup if any
required role/sample/job/cleanup is missing, foreign, conflicting or failed.
Cross-wave release aggregation must additionally require the same immutable
candidate/source/version, target manifests, bootstrap and exact tooling pins
for matrix and every required local wave despite distinct Context/run/nonces.
This benchmark alone never emits a release-qualified boolean. Root publishes
sanitized evidence under docs/validation only after actual execution; no actual
timings are advertised by this design.
