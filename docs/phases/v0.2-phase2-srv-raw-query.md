# Explicit SRV raw-query correction

**Design approved** by [actual Claude review](../reviews/v0.2-command-srv-raw-design-r1.md). This narrowly
amends [destinations](v0.2-phase2-destinations.md). It does not change selected
relay policy, account authentication, direct-only SRV consent, or command wire.

The pinned Hickory 0.26.3 `CachingClient::handle_noerror` rewrites its search name
to an SRV target while folding CNAME/SRV answers. A real loopback fixture proves
that a CNAME plus SRV answer can issue another SRV query for the target before
Marmish validates the original response. The existing fail-closed final result
therefore does not prevent response-directed DNS, including a malicious `.onion`
target. The prior component approval did not qualify this privacy behavior.

Use the same pinned dependency's public `NameServerPool::from_config`,
`PoolContext::new(options, TlsConfig::new()?)`, `TokioRuntimeProvider`, and
`net::xfer::DnsHandle::lookup(Query::query(owner, RecordType::SRV), options)`.
Consume one response using the existing futures-util StreamExt dependency.
`NameServerPool::send/try_send` performs bounded configured-server I/O and response
class checks; it does not interpret CNAME/SRV data or generate followup names.
This bypasses Resolver/CachingClient entirely, without writing a DNS packet
parser, adding a dependency, or forking Hickory.

Retain the exact system-server import (first three usable ordered IPs, UDP/TCP53,
no public fallback/search/hosts), one concurrent server, one-second pool timeout,
and one original five-second deadline across every explicit owner. Remove the
high-level resolver retry layer: no application retry or additional alias query.
Keep normal library UDP-truncation TCP handling to the configured server. Request
options are constructed explicitly with recursion desired and the existing
EDNS/case-randomization settings; DNSSEC/DoH/DoT remain disabled. The recursive
system server may internally resolve aliases; this is ordinary explicit direct
DNS, not an anonymity claim. Marmish itself queries only each caller-supplied
absolute owner, never an answer's SRV target or CNAME alias.

Validate response success, matching original question, and answer-section data
before selecting anything. Reuse the existing strict IN-class connected CNAME
chain (at most eight aliases), record ceilings (sixteen SRV across owners), target
and canonical URL checks. Same-packet CNAME plus terminal SRV records may succeed.
CNAME-only, incomplete chains, unrelated records, `.onion`/numeric targets, empty
or non-success responses fail closed; no supplemental query is attempted. Ignore
additional-section addresses. Failure of any owner returns no partial selection.

Keep the dedicated current-thread runtime/setup thread and destroy the runtime
before delivering a result, closing asynchronous DNS tasks and sockets. Existing
system-configuration-read/caller-cancellation limitations remain truthful; no
unbounded resolver task is introduced and no deadline is renewed.

Acceptance uses inert loopback DNS only: valid same-packet CNAME+SRV succeeds with
exactly the explicit owner query; CNAME-only and malicious `.onion`/numeric SRV
responses fail without a second datagram; wrong question/non-success fails;
existing owner/record bounds, silent-server deadline, uncached repeated lookup,
and exact client socket reuse after runtime teardown remain covered. Focused
CLI/SRV tests, formatting and strict all-target Clippy precede actual Claude
completed-code review. This is component qualification, not live command or phase
acceptance.

Implementation clarifications from review: require NoError and exactly one matching
IN/SRV question even on TCP; ignore authority as well as additional-section
records after the pool class checks. Configure only pool-used options; its one
second total budget does not promise failover past a silent first server.
