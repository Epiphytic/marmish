# v0.2.2 explicit macOS Keychain authorization

Status: independent Claude design r2 APPROVED; implementation and real macOS qualification pending. See [review](../reviews/v0.2.2-keychain-authorize-design-r2.md). Beads: `marmish-0or`. Existing v0.2.1 assets remain immutable.

## Problem and actual contracts

A user can install/setup successfully yet receive `identity: locked_or_denied` from `marmishd --debug`, including after successfully unlocking the default Keychain. This does not establish a particular ACL cause. `marmish-vault/src/macos.rs::status` collapses interaction-not-allowed (-25308), authentication-failed (-25293), and user-cancelled (-128). `UiLease::acquire` deliberately disables Keychain interaction for ordinary provider calls. `Provider::probe` additionally rejects a locked default Keychain before loading data. Setup's existing-ready shortcut in `native_setup.rs` reads cached public metadata without loading credentials.

The reviewed shared-helper change makes both installed frontends use the canonical versioned `marmish` executable, not differently signed `marmishd`. It does not authorize a new ad-hoc code identity to read older items. This increment offers explicit OS consent and preserves background fail-closed behavior; it cannot promise that every native denial is recoverable.

The pinned security-framework 3.7.0 exposes `SecKeychain::user_interaction_allowed` and a disable-only RAII guard; its guard drop unconditionally enables interaction. The dedicated interactive path therefore needs a narrow raw `SecKeychainSetUserInteractionAllowed` binding with checked result and restoration of the actual previous value, rather than reusing that guard or constructing the ordinary UiLease. Existing raw Security bindings in macos.rs provide the linking pattern. Apple documents the native API as controlling automatic Keychain dialogs: [SecKeychainSetUserInteractionAllowed](https://developer.apple.com/documentation/security/seckeychainsetuserinteractionallowed(_:)). [errSecInteractionNotAllowed](https://developer.apple.com/documentation/security/errsecinteractionnotallowed) denotes disallowed interaction, not proof of a locked item.

## Public command and limits

Add `marmish [-i NAME] [--state-dir DIR] keychain-authorize`, without command-specific options. Accept only `!daemon_binary` (the marmish frontend); reject `marmishd keychain-authorize`. Do not test the executable basename: the existing standalone versioned layout is also valid. On non-macOS return finite `keychain_authorize_unsupported` before profile/provider work. On macOS require stdin and stderr to be TTYs and the calling process group to own the stdin controlling terminal (`tcgetpgrp`); failure is `keychain_authorize_foreground_required`. There is no stdin password reader, password argument, secret logging, or environment credential input. Use a closed explicit-argument allowlist: only debug, state-dir and identity are accepted, plus ordinary help/version. Reject every other global explicitly present, including socket, tor, relay, key-storage, allow-peer, retention-seconds, user, srv, stdin, stdin-none, detach, new-session, wait-seconds, no-autostart, max-commands and max-uptime. Detect explicit presence with clap ArgMatches::value_source == CommandLine before converting matches into Args; defaulted values must not be mistaken for user input.

Explain on stderr, before helper launch: macOS may ask for consent for the two existing Marmish items; persistent background access requires the user's own persistent OS authorization choice. Marmish never selects an OS dialog button. `Allow` once is not a promise of future daemon access. On verified success print only `Keychain access verified for this profile.` Retry the ordinary daemon as a separate user action; this command neither starts it nor contacts relays.

One absolute monotonic 120-second deadline begins at command dispatch, covering profile lock acquisition (nonblocking), both helpers, response handling and reap. Reserve the last 15 seconds for fresh verification: the interactive phase deadline is T0+105 seconds, verification deadline T0+120 seconds. The interactive helper self-watchdog is 120 seconds (outer supervisor ends its phase sooner); the fresh verification helper retains the normal 15-second watchdog. Each launch is clipped to these original deadlines; no renewal. Before spawning, install Tokio Unix signal streams for SIGINT, SIGTERM and SIGHUP. Run the bounded synchronous exchange in a joined spawn_blocking task with an Arc<AtomicBool> cancellation flag; the async signal select only sets the flag and then awaits that task. The 2 ms exchange loop checks it each iteration, and an owned-child RAII guard provides kill/reap on every failure/unwind. Keep helpers in the foreground process group, with no setsid; Ctrl-C can reach them directly too. Preserve the existing three-argument ordinary helper_exchange wrapper; a private controlled exchange returns both bounded bytes and ExitStatus for the new path and accepts cancellation. Cancellation must close pipes and kill/reap before the frontend returns nonzero. Timeout likewise kills/reaps; neither becomes success. Native consent already granted before cancellation is not rolled back or misreported as transactionally undone. A bounded UI request can still fail in SSH/no-GUI sessions even with a TTY. SIGKILL of the frontend cannot run its cleanup; the orphaned helper is bounded by its own watchdog. Rust Instant on macOS excludes system sleep, so this is a monotonic active-time bound, not a promise of elapsed wall time across sleep. Watchdog exit 124 maps to timeout, not generic keychain failure.

## Existing-profile boundary

Do not call `prepare`, setup, init, `Vault::create`, `ProfileLease::acquire`'s create-if-missing path, or any database/network API. Add a narrow `ProfileLease::acquire_existing` using the existing canonical directory, owner/mode, no-symlink, bounded manifest and exclusive owner-lock checks, using check_dir only (never private_dir), and open_private(owner.lock, false). Missing manifest fails; require exactly profile format 2, Ready and Keychain after validate_manifest. Refuse missing, initializing, malformed, unsafe, file-backed or in-use profiles before contacting Keychain. No profile directories, manifest, lock or keys may be created by this command. Keep the acquired lease through both subprocesses.

Inside identity.rs a private authorization request is derived solely from the validated ready Keychain manifest: namespace MarmishV2, exact v2 Nostr and SQLCipher refs. No CLI-supplied ref/service/keychain path, broad list or legacy namespace is accepted. Reuse `validate_manifest` and `KeyRef` validation. Request construction is not a public export of refs. The canonical native_layout helper and retained installed-version manifest/hash checks are unchanged. The ready public-key binding is unchanged; loading the same immutable refs does not rewrite profile metadata or derived keys.

## Dedicated helper contract

Keep `_vault-helper` and its request enum entirely noninteractive. Add separate hidden canonical-helper entrypoints `_vault-authorize` (interactive) and `_vault-verify-authorization` (noninteractive), both routed before Tokio construction. They accept only a dedicated closed JSON schema:

`{"version":1,"namespace":"marmish-v2","nostr":{"version":2,"purpose":"nostr","id":"<64 lower hex>"},"sqlcipher":{"version":2,"purpose":"sqlcipher","id":"<64 lower hex>"}}`

Use deny-unknown-fields typed parsing, rejecting duplicate/unknown/missing/trailing values, incorrect versions/purposes and over-limit input before provider access. No action, UI boolean, label, secret or alternate namespace is accepted. Reuse the 8192-byte input/output cap, bounded EOF reads, zeroizing secret buffers, core-dump disabling, finite panic behavior and owned-child pipe/exchange cleanup. Extend the exchange implementation with a private closed helper-kind enum rather than a caller-supplied arbitrary argv string; ordinary callers keep their exact existing default behavior. Dedicated responses never serialize secret material and are a closed success `{"version":1,"ok":true,"result":{}}` or failure `{"version":1,"ok":false,"error":"<finite category>","purpose":"nostr|sqlcipher|provider"}`. Verify child status and payload agreement; nonzero cannot be success. A native failure is parsed even on nonzero exit so its finite category survives.

Freeze the vault export as `helper::AuthorizationMode::{Interactive,Verify}` and `pub fn run_authorization(mode: AuthorizationMode)->ExitCode`. Wire DTOs remain private. Only `helper::run_authorization` can reach the new macOS authorization function; expose no general interactive Vault constructor. A separate fresh helper process prevents global UI policy racing ordinary Vault users. The hidden action is invocable by any same-UID process; its piped stdin cannot prove foreground status. The public frontend enforces the TTY contract, and the helper is an explicit consent capability, not a new security boundary against its own UID. Use a dedicated private Provider construction with `_ui: Option<UiLease>`: ordinary constructors always hold Some(UiLease), while only run_authorization may construct the no-lease provider in its fresh process. Refuse any active ordinary UI_STATE lease before changing policy; hold the existing UI-state mutex through the dedicated operation so a future overlapping ordinary constructor cannot race it. The interactive process records previous UI permission, checks the raw Set(true) result, enables it only for the two exact reads and restores it on all ordinary exits. A restoration guard performs fallback restoration on unwind, and the explicit final checked restoration must succeed before an exit-0 response; restoration failure is backend_failure/nonzero. The Verify mode explicitly sets false and checks/restores the previous policy likewise, with no UI-enabled interval. Process termination ends its policy lifetime. The verification process explicitly disables UI and uses the ordinary provider load semantics, independently rereading both refs, then drops/zeroizes both secrets. No credential bytes leave either helper.

Retain the existing locked-Keychain probe in both paths. If locked, return `keychain_locked` and instruct the user to unlock the default Keychain explicitly, then rerun; no new unlock/password API. With an unlocked Keychain, authorize exact existing items in fixed Nostr then SQLCipher order. Reuse the existing exact service/account/retained-keychain query and ambiguity checks; refactor a small private query primitive if necessary rather than duplicate predicates. Each item must be unique and decode to exactly 32 bytes. Read and drop secret data; never create/update/delete items or invoke SecAccess/SecACL trusted-app editing. OS dialogs may apply the user's own persistent consent, which is an explicit user-controlled OS effect, not an application ACL rewrite.

After interactive success the frontend launches the fresh `_vault-verify-authorization` process with the identical frozen request. Only both noninteractive loads succeeding permits exit 0. This avoids same-process authorization caching and verifies current persistent access for the same canonical helper code identity. Partial interactive success leaves native consent as actually granted but returns nonzero if either item or the fresh verification fails; a later retry is safe. Success does not establish provider upgrade/rollback support for another code hash or prove database health.

## Finite diagnostics

Preserve all existing daemon/provider error mapping and wire response behavior. The new path alone can preserve native status before it is collapsed: -25308 -> `interaction_not_allowed`, -25293 -> `authentication_failed`, -128 -> `user_cancelled`, -25300 -> `missing`, -25307 -> `uninitialized`; local probe locked bit -> `keychain_locked`; local duplicate/data validation -> `ambiguous`/`malformed`; everything else -> `backend_failure`. Include only finite purpose and category, no arbitrary native message, account/ref, service contents, filesystem path, identity key or raw response. Missing/malformed/helper deadline and child errors remain finite. A verification failure is identified as noninteractive verification failure with the underlying finite category, without claiming the OS refused persistent consent for a specific reason. Normal daemon diagnostics remain unchanged in this increment. Frontend errors use finite static Error::Identity labels (for example keychain_authorize_authentication_failed and keychain_verify_interaction_not_allowed); stderr includes only that stable failure label and an allowlisted purpose, never interpolated provider text. No raw OSStatus or error strings leave the helper.

## Ownership and validation

Proposed implementation ownership: native cli.rs (parser/dispatch/hidden entrypoints), identity.rs (existing-only lease/private request/bounded subprocess), vault helper.rs and macos.rs (dedicated strict protocol/read-only native path), plus narrow vault lib.rs exports if required. Inline or dedicated unit tests; README and agent-spec document explicit foreground recovery and limits. No installer, release pin, journal, transport, ACL, dependency or manifest change. Parent assigns exact file ownership after design approval.

Offline tests must cover parser/frontend/non-macOS restrictions; existing-only absent/initializing/file/in-use/unsafe fixtures without writes or provider calls; exact refs frozen across both helpers; strict duplicate/unknown/secret/UI injection rejects; malformed/nonzero/oversize helper responses; fresh-helper sequence and no verify after failed authorization; cancellation/timeout reaping; deadline nonrenewal; finite native mapping; secret-free outputs; existing ordinary noninteractive regression tests unchanged. Add ordinary-constructor UI-disabled regression coverage and exact before/after directory-tree snapshots proving existing-only failure does not create state. Use real owned subprocess fixtures for bounds/cancellation, not source-string assertions. Mock provider seams prove read-only call order without treating them as native consent evidence.

Real macOS acceptance is a separate required qualification before claiming this fixes the user's denial: use disposable existing profile and dedicated owned Keychain in a signed installed macOS session with actual interactive consent. Observe denial/cancel remains red; persistent OS consent permits the fresh verification and ordinary `marmishd` no-subcommand startup using the same existing profile; ordinary daemon remains noninteractive. Compare original profile/config/database bytes and original key public identity; no regeneration/fallback. Item password bytes must not be printed/exported. Test locked default Keychain path and deadline/interrupt cleanup. CI headless inability to approve dialogs is a reported limitation, not a substitute pass; user-controlled manual foreground evidence may be required. Initial provider qualification and cross-version ad-hoc ACL lifecycle remain independent gates.
