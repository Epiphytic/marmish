# Phase 2 command recovery acceptance extension

Status: design approved by [Claude round 4](../reviews/v0.2-command-recovery-check-design-r4.md), including the original-Submit-ID refinement and private fixture cleanup authority. Implementation and live acceptance remain separate gates.
This narrows existing [Phase 2 acceptance](v0.2-phase2.md) into one bounded
addition to `command_check.rs`. It uses the approved [owner-stop
contract](v0.2-phase2-owner-stop.md), durable response consumption, current sealed
command authority and existing recovery barriers. It changes no protocol or
ordinary command lifetime. Beads `marmish-7nw.3.3` remains parent tracking.

## Scope and prerequisite

Keep the three existing byte/exit command cases. Add one fourth invocation for
actual owner restart, identical Submit retries and conflicting Submit rejection.
Keep one original 600-second driver deadline, explicit relay set, disposable
file-backed identities and registered private allocation. Reserve the existing
30 seconds for cleanup; every observer uses the remaining original deadline.
No live run is authorized by this document, and a direct result does not satisfy
Arti or cross-platform acceptance. A first three-case live run may proceed
independently while this design is reviewed. In the extended driver, run the
recovery case first after initial cold activation/room acceptance, followed by
the three existing cases. There are still exactly four unique invocation IDs.

The current normal client API rightly rejects changed invocation content before
publication. Separately, the current remote service/store path returns local
`Invalid(command_invocation_conflict)` and deletes the frame instead of producing
the protocol's `InvocationConflict` response. This is an implementation defect,
not a weaker test contract. The recovery extension must fail until the remote
path returns the approved finite refusal without replacing the immutable job,
allocating a second job, or changing its original Submit digest. The service and
store owners must review that fix independently; this fixture cannot bypass the
local immutable-ledger check to hide the defect.

## One bounded, observable command

Use canonical `/bin/sh` as an ordinary Exec argv; Engine ShellCommand remains
disabled. The fixed script receives only fixture-created absolute paths as
positional argv, never interpolated into script text. Its payload is:

```sh
umask 077
printf '%s\n' run >> "$1" || exit 123
printf '%s' before-restart
printf '%s' before-stderr >&2
n=0
while [ ! -f "$2" ] && [ "$n" -lt 360 ]; do
    sleep 1
    n=$((n + 1))
done
[ -f "$2" ] || exit 124
printf '%s' after-restart
printf '%s' after-stderr >&2
exit 7
```

The private execution marker and initially absent release gate live under the
fixture's registered allocation, outside the engine subtree. Neither path comes
from a remote request. Before execution, verify both names are absent. Empty
stdin must reach committed EOF before stopping the owner: reopening an unfinished
input generation is intentionally unsafe and would test cancellation instead of
successful command persistence. The script's finite loop is a fail-safe, not a
new guaranteed wall-clock bound or a replacement for the external supervisor.

Retain the fourth fresh invocation ID and the canonical original Submit bytes.
Through real command transport, require accepted Submit, a subsequent Status or
Poll reporting Running, committed healthy EOF and the exact stdout/stderr prefix.
Consume each verified Poll with the current durable cursor pair. Require the
independently opened nofollow, owned regular marker to contain exactly `run\n`.
Its device/inode receipt is retained; reject a link, changed identity, extra line
or more than the bounded expected bytes. Verify the held parent directory receipt
and marker absence before Submit, and use O_NOFOLLOW for every later read. The
script append is not race-proof against another same-UID actor; that is outside
this private fixture threat model. Check only these fixed fixture paths.

Stage budgets after the recovery Submit starts are: initial Submit20s, Running/
healthy EOF/prefix20s, joined stop30s, daemon reopen30s, activation/recovery150s,
fresh recovered Status20s, identical retry20s, local refusal1s and remote probe30s.
Each deadline is clipped to the same original exercise deadline (600s minus the
cleanup reserve). Their pre-gate sum321s leaves39s below the script fail-safe;
these are test observer bounds, not changes to transport timers. A 124 exit or
any expired sub-deadline makes the case red. Probe expiry cannot consume the
cleanup reserve: create the release gate on this known path, or explicitly
cancel, then execute cleanup. No retry extends a sub-deadline.

## Real stop, absence of a second owner, and reopen

`Pair` gains `server_stop: Option<PendingStop>` and a closed lifecycle state
`Running | Stopping | Stopped | Reopened`. Running/Reopened require exactly one
server owner/profile tuple and no keeper; Stopping requires no owner/profile and
exactly one keeper; Stopped requires neither. Transition code owns the keeper
while awaiting it and preserves the Pair allocation until joining finishes.
Never reopen from Stopping, and never final-stop the old server a second time.
While stopped, do not call the two-owner `turn`; no turns are needed during
joined stop/open, and the client may remain idle. Its transport will recover
normally after the new server is ready.

Irreversibly stop actor ticks/submissions for the existing server owner. Transfer
its actual `MdkOwner` and actual `ProfileLease` to `stop_owned`; do not invoke
cleanup or cancellation. Observe within 30 seconds clipped to the original
deadline. If it returns PendingStop, store it in server_stop/Stopping and finish
that same keeper before final stop or deletion. Never reopen after this case
failure. An observer expiry makes this case red even if eventual joining
succeeds; preserving ownership still takes precedence over bounded reporting.
Require real engine join, MDK close and runtime cleanup. Ordinary stop does not
claim worker absence or authorize deleting its engine directory.

While the lease keeper still owns an incomplete stop, a competing profile
acquisition must fail; the existing offline lifecycle test proves that boundary.
The live test never opens another profile speculatively. Only after completed
stop may `daemon::open` acquire the same server profile with the same identity,
configuration, relay set and private engine state. Keep the client owner/profile
running. Only completed stop with all three required flags permits reopening.
A failed open leaves Stopped and preserves state, with no guard-authorized engine
removal. An acquired owner whose activation fails is owned-stopped on cleanup.
The implicit Pair drop remains degraded and retains the allocation and resources;
it is never cleanup evidence. Use the exact previously joined command
room/session, not a replacement
room or identity. New owner activation/recovery uses the remaining original
budget; no restart of that budget on relay reconnect.

After activate and actual recovery_caught_up, before writing the release gate,
obtain a fresh real-transport Status/Poll from
the reopened server showing the same invocation still Running with
InputStatus.eof_sent=true, healthy InputHealth (no Gap/Uncertain), and the same
verified output prefixes. Require an unchanged
one-line marker. Thus the gate has not allowed natural completion before owner
recovery, and a newly admitted substitute cannot masquerade as recovery. Do not
infer successful recovery from relay publication or a cached client snapshot.

The initially registered engine directory receipt remains held across ordinary
stop/reopen. After daemon::open returns, independently open the new profile root
and its commands child with O_NOFOLLOW and require their device/inode identities
to equal BOTH original held receipts. Never recapture after restart. Recreated,
renamed or substituted directories make the case red and retain state. Final
cancel/begin_cleanup/poll_cleanup calls use only the reopened current owner and
new lease; protected unlink uses the original directory receipt under that new
owner's actual CleanupGuard. The old owner/lease no longer exists.

## Identical and conflicting submissions

With the release gate still absent, retry the original canonical Submit with
its ORIGINAL request ID through the normal durable client command API. Require
idempotent local attachment and unchanged original invocation/request digest.
A retired original publication that cannot attach safely makes this case red;
never replace the request ID to force acceptance.
This check is explicitly local retry evidence, not a fresh remote response.
Normal client preparation intentionally refuses a fresh Submit request ID for an
existing invocation: crash recovery must retain the original Submit request ID
and canonical request digest. Do not weaken that invariant for this fixture.

For fresh remote identical-retry evidence, construct a canonical identical Submit
with a fresh request ID and send it through the real MDK AppMessage path described
below. Arm the same capacity-one authenticated probe with expected result
`Existing` before sending. Require a newly authenticated response exactly
`Ok(Submit { disposition: Existing, .. })`, op Submit and exact canonical request
SHA256/binding/request ID. The status must identify the original invocation;
require the same immutable server digest and read the marker again: exactly one
execution. This raw fixture request is not inserted as a fictitious normal
client ledger slot. Complete/take this probe before arming the conflict probe.
Each probe has a 15-second observer bound, measured from its send, within the
original combined 30-second remote-probe budget. The earlier identical-retry
20-second stage starts before the local original-ID retry and covers that retry
and the entire first probe together. No retry resets either bound.

Attempt changed argv under that invocation through the normal client API and
require its existing local `command_invocation_conflict` refusal. That local
check alone is not a remote rejection test.

For the remote negative, the explicit fixture constructs one canonical inner
Submit with a fresh request ID, same actual room/session/account binding and
invocation, but a different fixed output literal in argv. It sends the event
using the existing real MDK `SendIntent::AppMessage` and ordinary native effects
processing from the actual client owner. Use the existing command event
builder and closed codec; MLS provides sender authentication. No forged context, synthetic GroupEvent, direct service
call, SQL write, alternate identity, or relaxed authority is permitted.

Use one bounded crate-private observation slot on MdkOwner rather than copying
receive_one/tick or racing a pending-event scan. Exact API:

```rust
enum CommandProbeExpected { Existing, InvocationConflict }
fn arm_command_probe(&mut self, group: GroupId, request: wire::Request,
                     expected: CommandProbeExpected) -> Result<()>;
fn take_command_probe(&mut self) -> Option<bool>;
fn clear_command_probe(&mut self);
```

Arming verifies the real client-direction command_context, exact binding and
canonical bounded Submit, stores group/session/request ID/canonical request
SHA256, and rejects an already armed or untaken slot. Capacity is exactly one.
Only the explicit fixture calls it; no IPC or remote method exposes arming.
During normal project_command_message, AFTER existing decode_command_event has
validated actual sender/leaf/role/current authority and BEFORE the normal exact
command_not_found client-response rejection, a matching group/session/request/
hash response with op Submit fills the slot with whether result matches the
closed expected enum: Existing requires exactly Ok(Submit) with Existing
disposition; InvocationConflict requires exactly Err(InvocationConflict) with no
detail. Both also require exact invocation/session/account binding. Each server response
adds only existing bounded request-retention/publication obligations, never
another active or uncertain invocation. The probe
observes only the existing exact command_not_found client-response rejection;
it does not intercept ordinary durable delivery. No context is forged and no command
permission changes. Keep normal tick, drain, production projection and unmatched
response deletion unchanged. A second matching frame never overwrites a filled
slot. take clears the slot only after a result; clear disarms on timeout/error,
and owner stop destroys the slot. A mismatched response never satisfies it.
This is one armed finite verification bit, not a callback/global hook or volatile
replacement for normal durable client delivery.

The two sequential raw probes have no normal client journal request/publication
rows. Their two native outbound obligations are deliberately retained as unowned: do not fabricate
journal ownership or ACK it from volatile evidence. Normal native convergence
may republish the same frozen event/source; the server must replay its same
durable refusal without side effects. Read storage.list_outbound_fanouts() matching each exact application_message().app_event_id
and storage.list_queued_outbound_intents(&group) matching each exact AppMessage
payload before final stop. Record separately whether each is a fanout or queued
intent and probe_native_retained only if both are actually retained (never infer
ACK or absence). A missing obligation makes the case red. The three later command
cases do not rely on room-wide uncertainty classification while these unowned
obligations remain. Record the
expected purpose_ownership_unknown diagnostic honestly. This test does not claim
its normal native publication ACK or an empty outbound queue. Only after all
fixture jobs are proven quiescent, protected engine removal succeeds and BOTH
actual owners are joined/closed may the disposable remaining MDK state (including
those injected obligations) be deleted. This explicit negative-test allocation
teardown does not authorize production GC or weaken normal publication ACK rules.

The two probes share a 30-second observer budget, at most 15 seconds each,
clipped to the original exercise deadline.
A missing response, silent drop, wrong response, or timeout is red, never refusal
proof. Write the release gate or explicitly cancel so cleanup still has time.
Require the server's original immutable invocation digest and independently read
execution marker to remain unchanged.

The separate service/store fix must meet this exact observable contract:

- A fresh conflicting request ID gets its own durable source/request/terminal
  refusal publication, attached to the existing invocation's owner/key without
  changing the original Submit payload/digest/admission or existing request slots.
- Response id is the probe ID; unchanged binding; request_sha256 is the canonical
  conflicting request's SHA256; op=Submit; result=Err(InvocationConflict) with
  detail=null, no status payload. It is a command-owned native publication.
- Identical replay of that request/source reuses the same refusal. A reused
  request ID with different content follows the existing request-ID conflict rule.
- This refusal adds no active/uncertain/unknown invocation and never dispatches,
  feeds or cancels the original job. Existing active/terminal accounting remains
  that of the single original invocation. Refusal slots obey existing bounded
  retention/source/ACK rules.
- Update accepted_bytes_duplicate_attach_and_conflict_are_atomic to verify this
  durable refusal and unchanged invocation, replacing its current is_err check.

The refusal fix requires independent design/code review by its service/store
owners; this document pins acceptance, not permission to bypass their review.

Finally create the release gate atomically as an owned 0600 regular file. Poll
from the persisted client cursor pair to terminal completion. Require exact
concatenated stdout `before-restartafter-restart`, exact stderr
`before-stderrafter-stderr`, no output gaps or input warning, and natural exit7.
Validate terminal outcome and byte slices before consuming each response. Require
one unchanged `run\n` marker after terminal completion. This is bounded evidence
of no duplicate execution for this case, not a universal exactly-once guarantee.

## Cleanup and finite results

Retain all four UNIQUE fixture invocation IDs, including the fourth before Submit.
Identical/probe retries reuse the fourth ID and never add another cancel ID. The
explicit cancellation seam's current at-most-three bound in
command_service.rs::cancel_fixture_invocations must become four (only
this fixed driver workload); preserve its uniqueness, ownership, known-admission
and ambiguity checks. No arbitrary bulk administrative cancellation is added.
On failure request explicit cancellation only for this fixture's registered
IDs, then progress actual engine completions. Additional duplicate/refusal request
slots do not create another server invocation and cannot make ID lookup
ambiguous. Unknown/missing IDs or uncertain
admission cannot be treated as successful cancellation. Preserve state and report
red when proof is unavailable.

After successful cases or proven cancellation, use current zero-active/uncertain/
worker-running/worker-unknown checks, all-row fresh final observation and matching
committed fence. Consume cleanup only on the sole engine thread. Require the
same quiescent fence immediately before and after descriptor-relative registered
engine removal while the actual CleanupGuard and profile lease remain held.
Only then joined-stop both current owners and remove remaining private state.
A partially reopened pair, failed activation or early return must follow the same
owned-stop path; no TempDir destructor may delete live state. No cleanup failure
may become green because the external supervisor killed a process.

Publish only finite booleans/counts, stage/category, platform/route, elapsed
milliseconds, verified byte counts and SHA256 values. Record restart stop/open/
activation time separately, one fourth-case wall time, execution_count=1,
identical_submit_existing, local_conflict_refused, remote_conflict_refused,
recovered_output_verified, probe_native_retained and the existing separate cleanup
flags. Replace both current not_tested string fields with these closed booleans;
any absent/failed stage has false/null values. Never publish
keys, private paths, endpoint URLs, script text or raw provider errors. Missing
results are false/null and the run is red. The result does not replace the full
Phase 2 fault-injection, platform, Arti and independent code-review gates.


## Original-Submit-ID refinement scope

This refinement changes fixture observation only. It preserves the ordinary
client original-request invariant, wire, execution authority, quotas, timers,
ordinary ACK rules and exact remote service contract. The capacity-one probe is
fixture-only, never exposed through IPC; sequential probes cannot overwrite each
other. An Existing response from a cached normal client slot does not satisfy the
remote probe. The stop/reopen state machine and held-directory identity proofs
above remain mandatory. Actual recovery completion means the reopened owner's
`recovery` flag is false after its EOSE catch-up, not a matching diagnostic string.

Installed-harness reuse is excluded from this recovery refinement. EngineTree
remains private to command_check, with capture requiring the actual ProfileLease
and removal reachable only through the existing guarded local cleanup path.
No capture_path or remove visibility expansion is authorized here. Installed
acceptance must separately specify and review a sealed cleanup-authority witness
before sharing deletion code; comments about a remotely held guard are not a
typed deletion capability.

That separate authorization is now recorded in the
[installed cleanup authority design](v0.2-installed-cleanup-authority.md) and
[actual round 3 approval](../reviews/v0.2-installed-cleanup-design-r3.md).
The shared removal path requires its sealed live-child guard, then compares the
guard profile with the original receipt parent/root inodes immediately before
synchronous removal. This does not authorize path-only deletion or establish
installed acceptance.

A timed-out daemon reopen must remain an owned task whose eventual owner/lease
result is retained and joined-stopped during cleanup. Do not drop an in-progress
open future after it may have created an engine, and never launch a second open.
Observer expiry remains red even if eventual open/stop succeeds. This has the
same ownership priority as the existing PendingStop keeper: final state deletion
cannot precede actual joined completion, and the external supervisor remains the
final wall-clock bound rather than a false bounded-cleanup claim.
