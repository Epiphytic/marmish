# Native bounded-server limits

Status: independently design-approved in [round 4](../reviews/v0.2-server-limits-design-r4.md),
with the nonblocking clarifications below incorporated. Implementation remains gated on
root authorization. Beads: `marmish-7nw.3.4`. This proposal supersedes the admission-only lifetime section in
[the acceptance amendment](v0.2-phase2-acceptance-interfaces.md#Admission-only-max-commands-semantics):
the user requested automatic count exit, not merely admission closure. Native
wire extension is authorized in scope; this approval covers design, not completed
implementation. Automatic cancellation remains excluded.

## Actual baseline and scope

`CommandLimits` already parses `max_commands: Option<NonZeroU64>` and
`max_uptime: Option<Duration>` (JSON integer seconds, uptime 1..1800). The native
CLI exposes neither flag. `daemon::serve_owner` has signal-driven shutdown and
100ms ticks, but no service deadline. `command_store::reserve_credit` already
checks permanent `command_replay_state.admitted` plus unresolved reservations;
`command_commit_completion` increments admitted only on the first durable
false-to-true `engine_known` transition, in the facts transaction. Existing tests
cover reservation release on definite refusal and permanent counting after exit.
The missing behavior is configuration plumbing, finite permanent-exhaustion refusal rather than only deferred
limit backpressure, launch lifetime, and integrated recovery/drain tests.

Reuse those tables, Engine recovery barrier, one account owner and one journal
connection. Do not add a launcher, another database connection, second signer,
engine launch counter, queue, polling protocol or engine storage change.

## Configuration and public entry points

Add optional `--max-commands N` and `--max-uptime D` to native daemon startup only:
`marmish daemon --max-commands 3 --max-uptime 30m`, and the existing `marmishd`
entry's explicit `daemon` subcommand. This does not promise an implicit-subcommand
CLI. Flags on init/check/client operations are usage errors. N is a nonzero u64
bounded by the journal's signed64 counter maximum. D is an unsigned integer with
exactly one optional lowercase suffix `s` or `m`, no whitespace/sign/fraction;
unitless means seconds. Checked conversion yields 1..1800 seconds. Thus `1800`,
`1800s`, `30m` are equivalent; `0`, `31m`, overflow and `1h` fail before opening
state/network. No new dependency is needed. The maximum applies to file values too; validate it
in RawLimits normalization, not only in the CLI parser.

Resolve effective settings once: each provided flag replaces that field of the
loaded private config; omitted flags preserve its value. Other settings remain
unchanged. A flag without a command config is invalid (do not silently create
execution grants or a server). Merge via `CommandConfig::load_with(root, overrides)` before cross-field
normalization, preserving ordinary `load` with empty overrides. With max_commands
and no explicit/configured max_uptime, use a documented 1800 second fallback; this
replaces the earlier requirement to reject max_commands alone. Uptime alone is
allowed on every role and bounds this daemon service. Max_commands is rejected
for client-only role and for an empty execution grant set; no engine is created.
Both role counts only incoming server-side admissions, not outgoing commands.
No hot reload. Bare limits built in low-level store tests need no uptime field
validation because the store never owns service lifetime.

Expose only narrow internal override/config getters; keep raw policy private.
Retain all existing policy and trust checks. Neither a CLI flag nor a configured
limit grants a principal execution access.

## Durable command budget

The budget belongs to the profile's durable ledger, not a process launch or MLS
room. Restart, command retention, room replacement, successful exit, cancellation,
authority invalidation and SQLite maintenance never reset admitted. A restart
with max 3 and admitted2 has at most one remaining new admission; with admitted3
it serves existing work but admits none. Lowering a maximum below admitted or
reservations closes new admission; raising it explicitly permits only the
additional credit. Removing the maximum is an explicit operator configuration
choice, not an implicit restart reset. A fresh disposable profile has zero count.

Use the existing reserve predicate inside the same transaction as new invocation
admission: admitted + unresolved_reserved < N. Unresolved means a server-side
active row with engine_known=false and no definite refusal; active counts are
already bounded at 32. Credit is reserved BEFORE token issue/engine side effects.
Engine status recovery and immutable digest rules remain authoritative. A launch
whose result is uncertain retains its reservation. A definitive pre-engine
refusal releases it. First engine_known transition consumes one permanent credit
and removes that reservation atomically; duplicate completions cannot increment
again. EngineKnown remains sticky even if the engine later collects a job.

Add a read-only `command_admission_budget() -> Result<CommandAdmissionBudget>`
with `{admitted:u64,reserved:u64,finished:u64,maximum:Option<u64>,
exhausted:bool,reserved_full:bool}` using exactly
the existing reserve calculation. The service checks it for a NEW authorized,
policy-valid Submit after duplicate/conflict lookup. When permanently exhausted (`admitted >= N`), prepare
`QuotaExceeded`, detail:null, and project an ordinary definitive refused Submit
slot/invocation/source/exact response atomically. It consumes retained refusal
capacity, but neither active credit nor admitted count. It remains a frozen
refusal on duplicate retry even if a later configuration increases the maximum;
a genuinely new invocation can try the increased budget. Changed bytes still
conflict. No false Accepted response may be committed before this decision. When only
`admitted + reserved >= N` but `admitted < N`, retain the existing deferred
command_admission_closed path: no frozen refusal, source ACK or new admission.
A later definite refusal can free that credit for the waiting Submit.

The store's existing transactional reserve remains the final guard. Same actor
serialization means no await or intervening engine completion between the budget
read, response preparation and journal transaction. If that guard still reports
closed (future integration/reentrancy), discard the uncommitted Accepted candidate,
re-read and either project QuotaExceeded if permanently exhausted or return
the retained/unACKed transient path if merely reserved_full; never ACK until
that refusal is durable. A full retained journal remains recoverable bounded
backpressure: no pretend stored response, no source ACK, no engine side effect.
No blanket swallowing of storage/IO errors or relaxing other quota checks.

## Completion acknowledgement and automatic count exit

Admission count alone is not an output-drain proof. Add one authenticated native
operation `finish` in marmish-command/1 (unreleased authorized wire amendment).
It never issues engine tokens, runs a command, feeds stdin, changes cancellation,
or grants execution authority. Canonical outer binding/purpose/direction/ID/
request hash and 32KiB frame checks are identical to other command requests.
Body has exactly `{invocation,submit_sha256,terminal_sha256,stdout_cursor,
stderr_cursor}` with existing lowercase hex and signed64 cursor bounds.
`submit_sha256` is the existing group-bound immutable submit digest, supplied
by the client actor's ledger, not guessed from a public handle.

Terminal fingerprint is SHA256 of the domain bytes
`marmish-command/1/finish` followed by NUL, group length u32 big-endian, exact
native MLS group bytes, and canonical compact sorted-key JSON (no newline) of:
`{client,server,session,invocation,submit_sha256,outcome,stdout,stderr}`.
Each output field is exactly `{produced,gaps}` from a terminal Status; outcome
is its exact `{kind,value}`. All identifiers/digests use the existing hex codec;
gaps use existing bounded canonical Gap encoding, at most 4/stream. Fingerprint
excludes changing retained-byte counts, cancellation flags and credit counters.
Both streams must have closed=true, state=exited, engine_known=true and a real
outcome. Final cursors must equal those exact produced lengths, traversing every
reported gap under the existing gap-aware cursor rules. Unknown/Lost/Accepted/
possibly-running states cannot finish. Engine failure/nonzero/signal exits can.
The server verifies this against its durable latest authoritative terminal facts;
a changed terminal fingerprint returns finite Busy, and the client obtains a
fresh Poll before retry. Finish projection uses Busy only for this changed-fingerprint
case; temporary storage/transport failures retain their existing deferred handling
and do not manufacture a Busy response or spend a Finish attempt. Never equate output size with absence of gaps.

The client actor derives Finish from the exact terminal Status in the consumed
Poll response that advances both cursors to produced, never from record.status
(which may be overwritten by out-of-order replies). After the candidate consumption transaction, no other unconsumed response or
unanswered request for this invocation may remain, and resulting durable client cursors must actually equal
produced on both streams; a consumed flag alone is insufficient because invalid
chunks can be marked consumed without advancing. Derive/prepare the candidate
Finish before the last consumption transaction, then atomically commit cursor
advancement, consumed marker, fixed Finish request ID, exact native event and
outbox slot in that same connection/transaction, or commit none. Repeating
consumption returns the current durable cursors and reuses this frozen Finish;
no crash window may consume the terminal response yet lose the only Finish
creation opportunity. Final consumption cannot require any network/engine await.
The client actor derives Finish only after all corresponding Poll chunks and
terminal status satisfy these durable consumption preconditions. A durable latest
Finish slot answered Busy, with no Finish pending, is a second trigger: issue a
fresh Poll at durable cursors and atomically consume its terminal response plus
create a new Finish, even when its chunks are empty and neither cursor moves.
Require exact produced==durable cursor equality for both streams, valid gap-aware
traversal and no other unconsumed/unanswered requests. Always use this Poll
response, never record.status. Persist `finish_attempts` (initially 0) and `latest_finish_request` (initially null)
in the client invocation facts JSON. The referenced durable slot supplies its pending/Busy
trigger; these fields and slot creation commit together. At
most four Finish attempts total per invocation (initial plus three Busy
replacements), unchanged across restart. This is an explicit bound, not a claim
that gaps can change only three times. On exhaustion stop automatic Finish
attempts and preserve known command result; original uptime remains the exit.
Network retry of identical pending Finish bytes is not a new attempt. A Busy
replacement gets a fresh frozen request ID; repeating the same consumption
transaction must reuse its existing new ID, not spend another attempt. Existing external-write-before-consume crash duplication remains; this is
an authenticated peer's assertion of consumption, not proof of a filesystem fsync
or a human reading the bytes. CLI disconnect before Finish keeps output serving.
Finish is a separately durable client request/publication, not a volatile callback.
It is allowed alongside an old Poll only after that Poll has been consumed.
No response/engine output hashes are invented after payload retention expires:
if terminal facts or required cursor proofs are unavailable, no Finish is created
and the finite uptime remains the escape hatch.

On the server, perform existing duplicate/conflict/authority checks first, then
atomically record the verified consumption marker, request/source and exact
response publication. `ResponseResult::Finish {finished:true}` is the sole success
body; ordinary closed WireError codes remain. Unknown invocation→NotFound;
wrong digest/binding/fingerprint not silently accepted. A canonical duplicate
request gets the same frozen response. Persist the first accepted fingerprint and
final cursor pair with client_finished. A fresh request ID for an already-finished
same invocation returns success without increment only if digest/fingerprint/
cursors match that immutable first claim; a changed fingerprint gets frozen
InvocationConflict/null. A Busy response is frozen per request ID: fresh Poll
then fresh Finish request ID are required after a changed fingerprint. Reject
mismatching replays. NotStarted with known Exited and a real outcome can finish;
Lost/UnknownLaunch and unknown outcomes cannot.
Finish is accepted only from the currently authorized original client in the
correct server-direction room. Revoked authority cannot finish a new claim;
that run waits for uptime/explicit stop rather than bypassing revocation.

Finish is handled synchronously in request projection, never scheduled as an
EngineOperation. schedule_requests skips it after its response is durably
projected; definitely pre-engine refused invocations (!engine_known) first
return the original stored refusal. Engine-known rows later marked ResultExpired
by collection still verify Finish against retained authoritative terminal facts;
missing facts produce finite ResultExpired and uptime fallback, never a made-up
terminal proof. Refactor
ResponseResult::status into an optional status accessor and adjust validation/
client projection exhaustively: Finish responses cannot overwrite engine_known,
authority, terminal status, feeder or admission facts.

Add a sticky `client_finished` fact plus permanent aggregate `finished` to the
same existing replay-state row. Fresh CREATE includes finished=0. On schema4,
probe table_info and add the checked finished column only if absent in a bounded
transaction; make reopening after partial initialization idempotent. Facts gains
default-false client_finished and optional first-fingerprint/cursor fields for
old JSON records. Existing schema3→5 initialization is explicitly tested; write
user_version=5 LAST after checked schema initialization, before admitting any
actor work. Do not falsely claim the existing multi-step initialization is one
transaction. Old binaries refuse schema5. The counter increment requires
finished<admitted and exactly one affected row; guard failure is operational
Storage, not successful Finish. First verified Finish increments finished once
in the same transaction; retain enough immutable finish binding/digest with
existing metadata to reject conflicts while the invocation exists. This is a
historical peer assertion accepted under authority at commit time, analogous to
historical engine admission, not a continuing assertion that the job or MLS
message is currently valid. Later authority/source invalidation revokes cached
success and publications under existing rules but cannot reverse the historical
consumption counter or create engine work. The reviewer must explicitly assess
this irreversible local-stop effect; it must never be reused as job success,
current authorization or an acceptance evidence shortcut. Keep the aggregate
through safe invocation GC; do not retain unbounded finished rows. On enabling
limits for an old profile, historical admissions lacking Finish remain unfinished;
there is no inferred completion from missing rows, engine collection or TTL.
They may therefore require uptime exit. Ordinary safe GC of an unfinished exited
row has the same consequence; this increment does not extend payload retention
or keep unbounded unfinished rows. Fresh CI profiles have complete history.

Auto-exit predicate is N configured, admitted>=N, reserved==0 and
finished==admitted, with no
uncommitted local engine completion/ACK control message, current projection or
source-ACK turn still executing. Evaluate only after an actor turn commits and
returns, never from inside projection. Close new admission once admitted==N but
continue status/poll/cancel, feeding, convergence and output serving until this
predicate, supervisor stop or uptime. Pending reservations retain/release their
existing credit and cannot make a premature permanent closure. A canonical
Finish cannot increment beyond admitted. Additionally no command publication anywhere in this identity may be in
Unsubmitted, Prepared or Uncertain (including the Nth Finish response); only
Published, Invalidated or Expired are terminal for this predicate. Query the
whole bounded publication table, not only expected client requests. Preserve
all exact native obligations and ACK rules; never fabricate an ACK or delete
state to satisfy drain. Publication terminality is not proof of remote client
receipt; Finish is the peer's separate assertion. A pending/uncertain publication
can therefore delay automatic count exit until uptime. Existing frozen native
obligations survive ordinary Stop if uptime ends first. The client already has
its terminal result before sending Finish, so missing Finish response does not
turn that known remote outcome into an unknown execution. CLI exit reflects that
known command outcome; any Finish acknowledgement timeout is a separate finite
diagnostic under the existing client deadline, not command exit255. Its durable Finish can
retry after a restart without incrementing again. CLI result success must not
claim server exit; a supervisor separately proves process exit and cleanup.

The same-UID validated-client coordinator may explicitly Stop as a CI cleanup
fallback, but that is not evidence of standalone automatic count exit. Standalone
acceptance must observe the real auto-exit predicate and process exit0. Reaching
uptime without all required client terminals is failed installed acceptance even
if ordinary stop exits0. There is no implicit cancellation on count or uptime.

## Service lifetime

Capture launch time immediately after CLI argument parsing, before config load,
identity/keychain, database or network setup. Use a private suspend-inclusive
monotonic clock: Linux CLOCK_BOOTTIME via existing libc; macOS
an explicit reviewed `unsafe extern "C"` declaration for mach_continuous_time
plus checked libc mach_timebase_info conversion (the pinned libc does not expose
mach_continuous_time itself). Clock failure/overflow is
finite startup failure, never a wall-clock or suspend-excluding silent fallback.
Effective uptime is known after reading config, but its deadline is computed from
the captured launch sample, not from completion of activation. Delayed config
loading can exhaust the budget without permitting activation/admission. A
supervisor that restarts a fixture supplies remaining original uptime, as the
acceptance amendment requires; process-local uptime is not a persisted reboot
clock and restarting never resets the separate admission counter.

Use a private `ServiceLifetime` with `remaining()/expired()` checked against this
clock; a test clock is injected only into private behavioral tests. Timer waits
use min(remaining,100ms) so resuming from suspend rechecks promptly. Check expiry
before opening/activation, every outer actor turn and after bounded blocking
preparation returns. Share a narrow immutable ServiceLifetime gate with
CommandService: check before every New admission deep inside a tick and before
every EngineOperation::Dispatch, not just in the daemon outer select. Expiry
returns the existing deferred/unACKed path for unadmitted input; already-accepted
undispatched rows retain their reservation for recovery. Read/cancel/completion
projection remains valid until the outer loop initiates Stop. Bound each activation/dispatch/
tick await by BOTH its existing deadline and remaining service time; put the
lifetime branch in nested selects, including activation. Re-arm lifetime waits at most 100ms even inside each nested select; a long Tokio
sleep_until alone is not suspend-inclusive. Clamp identity prepare 30s and
activation 150s as well as tick/dispatch. Audit cancellation safety of each await
against existing journal/native ACK ordering; never add an early source ACK.
No fresh per-operation uptime. Synchronous actor work cannot be forcibly preempted safely: uptime means
no new work after observed expiry and shutdown initiated within one 100ms timer
turn plus already-running bounded synchronous work; do not advertise hard
real-time process termination. A stalled OS/keychain call may delay return, but
must not permit a late command admission once its owner resumes.

At expiry close IPC/admission and follow existing ordinary owned Stop. Do not
call Cancel, FinalObserve, into_cleanup, fixture cleanup, signal arbitrary workers
or delete state. In-flight engine operations retain the existing commit/recovery
barrier and engine owner/profile lease discipline; shutdown must not fabricate a
completion/ACK. Current bounded owned-stop may retain a pending engine thread and
lease until its actual completion. Consequently max_uptime bounds service work,
not the time an uninterruptible OS thread or admitted command can survive. A
normal complete ordinary stop returns exit0; incomplete/failed stop returns the
existing failure, never 'successful drain'. Bounded fixture supervisors separately
prove cleanup before stop; output remaining at uptime makes that acceptance run
fail even if the daemon exits0. Disconnect alone changes neither budget nor life.

Use static diagnostics `server_limit: quota_closed` / `uptime_expired`; no
principal, key, argv, payload or private paths. No new public status schema is
necessary: existing evidence reports actual admissions; a refusal is the remote
budget signal. Future operator summaries can be added separately.

## Implementation boundaries and acceptance

One bounded integration increment, disjoint owners: config/CLI/lifetime+daemon
owner; store budget projection/counter tests owner; service/refusal tests owner.
Root integrates existing MdkOwner accessors with no parallel database ownership.
Code review must inspect all three together and the unchanged engine recovery
barrier. Existing private configuration/strict parser and ordinary-stop contracts
remain required.

Tests before closing this increment:

- CLI/config table: file/flag precedence, mixed-source implication, invalid suffix,
  limits/overflow/zero, role and operation rejection, no config/no grants; flags
  appear in actual help on both binaries with explicit daemon syntax.
- N=3 many authorized principals/rooms submitting concurrently through the one
  actor: at most 3 permanent admissions plus unresolved reservations; fourth has
  frozen QuotaExceeded/null response and no engine operation. Repeated bytes,
  changed bytes, replay and new request IDs preserve existing binding rules.
- Two uncertain dispatches reserve two credits; definite refusal releases one;
  known exit never releases permanent credit. Crash before/after engine side
  effect and before/after completion commit/reopen never exceeds N or reruns a job.
  Counter survives payload/request GC and engine collection. Lower/raise budget
  and retry an old refusal versus a new invocation explicitly.
- Full refusal capacity yields recoverable no-ACK backpressure; valid existing
  status/poll/cancel and other projection/convergence continue. Read failure is
  not treated as zero counters. Transaction rollback cannot leak accepted slots.
- Paused/scripted clock: start includes setup/activation; expiry during activation,
  dispatch and tick; no deadline extension after retries; suspend-inclusive jump;
  clock error/overflow; no admission after expiry. Runtime behavior uses short
  test budgets, not a 30-minute sleep.
- Nth real command completes and its stdout/stderr/terminal can still be polled
  before explicit stop; unrelated new command is refused. Ordinary disconnect,
  max-count closure and max-uptime do not invoke Cancel/cleanup or erase workers.
  A harmless admitted command outliving uptime remains recoverable after restart.
- Owned disposable local subprocess test validates actual CLI flags and ordinary
  stop exit semantics without relays; later installed nine-pair acceptance runs
  actual max 3/30m with explicit configured relays and independent client/server
  evidence. This design review does not claim those future runs happened.

Run affected unit/behavioral checks, strict native Clippy and independent Claude
completed-code review. Publish sanitized evidence and update supported usage only
after tests/review pass. No implementation is authorized by writing this draft.

Additional Finish acceptance: canonical golden vector including hash and exact
length; wrong peer/direction/room/digest/final cursors/fingerprint, missing gaps,
nonterminal/unknown and expired facts; one/both streams empty; binary outputs;
Finish before local durable consume refused by client API; duplicate and changed
Finish IDs; restart before/after marker/counter commit and source invalidation;
aggregate survives row GC without a current-validity claim. N=3 actual native
commands must return exact results, durably Finish and automatically ordinary-stop
with exit0 without supervisor Stop; fourth admission cannot occur. A missing
Finish keeps serving until original uptime and cannot fabricate consumption.

Round2-specific regressions: Nth Finish projected after that turn's publication
submission cannot stop until its response becomes terminal; uncertain publication
blocks until original uptime, never false-ACK. Lower N with an outstanding
reservation cannot exit until it resolves. Reordered terminal Status responses
and consumed-but-bad chunks cannot generate a wrong Finish. Same-fingerprint
fresh Finish ID increments once, changed fingerprint conflicts. Revoked Finish
is terminally rejected/ACKed according to current authority policy without
counting; it must not become permanent deferred backlog. Validate schema5
transaction rollback, column defaults and old-binary rejection.

Finish production acceptance depends on the approved local-client increment
calling durable consumption; current production daemon has no such caller. Land
Finish integration with or after that caller, not as a falsely usable standalone
server flag. Native command_check must exercise the same combined consume-plus-
Finish store API and real wire, not a test-only finish counter mutation.
Regression: output expiry changes the terminal gaps between Poll and Finish;
Busy survives restart, fresh empty Poll generates a new Finish, exactly one
finished increment occurs, and four attempts cap recovery without resetting the
original lifetime. Collected-engine retained terminal facts can still finish;
unanswered requests prevent premature local Finish creation.
