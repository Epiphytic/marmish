## Installed client handoff and terminal evidence

The full public-CLI matrix remains required and verifies ordinary CLI output.
This count cohort uses actual installed CLI `--detach` to submit the canonical
command and obtain its durable handle, then an acceptance-tool controller uses
existing same-UID product IPC to resume that handle. The controller never opens
MDK, SQLCipher or engine state, never mutates upstream tables and never replaces
Marmot transport with IPC: IPC asks the installed client daemon to perform the
same authenticated remote operations used by the CLI. No new product/test-only
IPC is added.

The distinction is necessary: public CLI may write correct terminal bytes then
return254 `delivery_pending` if Finish confirmation is lost as the server exits.
That result is not CLI success and cannot be used as proof of observed exit7.
The count design requires a durable client terminal artifact BEFORE requesting
Finish; inferring outcome from the fixture or a254 return would be false.
Potential user-facing delivery_pending/count-exit UX remains a separate honest
limitation; this harness does not change it.

The controller uses existing CommandUnconsumed/Response/Poll/Consume/Cursors.
Strictly decode the canonical response bytes after base64/digest verification;
require exact accounts, session, invocation, original submit digest, operation,
request ID and request digest. Do not attempt to reconstruct the original Submit
request or response: --detach consumes its authenticated answer and does not
expose its random request ID. Require --detach exit0, empty stdout and exactly
one stderr line `marmish handle: <closed JSON>` with the existing closed
CommandHandle schema. CommandInvocations must contain exactly that handle, with
admission Accepted, Dispatching or Engine, authority_valid true and no refusal, before any
Poll. Validate handle accounts, session, invocation and submit_sha256 against the
independently planned Submit; later cross-check this binding against the server
Evidence row (including session and engine_admitted1) and fixture receipt. Any
other detach exit, including254 local_pending or255 busy, is red submission;
never create a second invocation to hide ambiguity. Reuse each pending Poll or
Finish request ID across timeout or busy; never rebind output to a different poll.
There is at most one outstanding Poll per client. wire::MAX_BYTES is16384, so
these streams require at least16 Poll responses per client; never assume an8-Poll
bound from the combined stdout/stderr size. Each response fits the existing64KiB
IPC frame. Consume every Poll using expected_cursors equal to that exact Poll's
requested start cursors and the durable pair validated before sending it. All IPC attempts have the existing
single15-second bound capped by the original cohort deadline; actor/network
latency does not reset it. Poll loops yield and use a finite shared workload
cutoff.

Keep stdout/stderr private, bounded to their exact expected131072-byte sizes;
reject excess, mismatched chunks, gaps, stale cursor or invalidated authority.
Before consuming the final Poll require Exited, exit7, both streams closed,
exact produced/verified byte counts and hashes, no gaps/warning and valid
engine-known authority. Write an exclusive public ClientTerminal record, synced
through the existing record writer, immediately after that validation and BEFORE
CommandConsume. Only then consume the final Poll, which atomically prepares the
normal Finish outbox. Continue servicing the existing bounded Finish response
and consume it when observed. If the final Consume reply is lost, do not repeat
Consume or invent a Finish ID: discover the eventual durable unconsumed Finish
answer through CommandUnconsumed/CommandResponse; until then remain pending.
Persist observed request IDs locally before issuing a corresponding Consume.
For Finish Busy, consume that exact error, issue a fresh Poll at current durable
final cursors and revalidate the unchanged terminal output/status, then final
Consume can prepare the next persisted Finish attempt. Honor the existing maximum
four attempts and same-ID retry rules; other Finish errors never trigger a new
attempt. Missing Finish confirmation is a diagnostic, not loss of the already
validated terminal artifact. Keep every client daemon alive through server exit
so its actor can receive and ACK native publications.

## Concrete implementation clarifications

The result includes `identity_ready_sha256`, computed from the exact validated
canonical uploaded identity record. `workspace_removed` means owned private
children were removed while the required `workspace/output` directory and its
sanitized records remain; the caller writes the final cohort result last.

Each client daemon also opens an engine. Capture its original EngineTree receipt
at first launch, then prove the EMPTY admitted server-ledger equality using the
existing sealed live-owner guard, remove that exact tree, and ordinarily stop
and join that client. The three client cleanup operations run concurrently under
the original shared40-second budget. No client restart, new deletion authority
or unproved recursive engine deletion is allowed. Failure to reach actual
quiescence preserves private state and fails the cohort.

The installed IPC controller independently reconstructs canonical Poll requests
and checks their request digests. Every response additionally checks canonical
response bytes/hash, expected accounts/session/operation/request ID and handle.
Automatic Finish request bytes include a group-dependent digest not exposed by
public IPC, and detached CLI submission does not expose the original Submit
request ID; this cohort therefore does not claim independent recomputation of
those two request digests. Recovered Finish responses are checked against the
response hash from durable unconsumed discovery. The complete terminal record and
subsequent all-ledger server evidence bind the persisted Submit digest. The
separate real-MdkOwner protocol gate retains its stronger direct-wire assertions.
