## User direction and bounded change

The user requests continuing to a completed all-Rust v0.2 native release, a default
installer that selects v0.2 rather than historical Python/uv releases, and an
independently usable GitHub backup to the Radicle/Iris source URL. Working Tor
is explicitly not a v0.2 release gate; it may be deferred to v0.3. The existing
embedded Arti foundation remains experimental. Direct authenticated Marmot
commands, installed on every supported platform, still gate v0.2.

Phase 3 implementation may proceed against stabilized, reviewed Phase 2 internal
APIs while unfinished public command/recovery integration proceeds centrally.
This removes only the earlier *implementation scheduling* requirement to finish
all Phase 2 acceptance first. It does not close Phase 2, weaken its direct
command/replay/recovery gates, or authorize publishing unqualified installers.
Source and dependency changes still require root coordination and actual Claude
completed-code review. Platform and release acceptance waits for the installed
public CLI. Tor/Arti command and nine-pair Tor gates are excluded from v0.2 only;
record failures/experimental limits rather than silently claiming support.

## Two standalone source URLs, one native channel

Keep a thin POSIX bootstrap, generated from `scripts/install-native.sh` and named
`marmish-install-0.2.P.sh` in release assets, exactly as previously approved.
The live default `scripts/install.sh` on BOTH source mirrors will contain the
generated native bootstrap byte-for-byte, including the exact version and all
three manifest SHA256 pins, only AFTER all three target manifests/assets are publicly available
and native installed acceptance passes. It is not an unpinned redirect or a
second downloaded executable script. Any future indirection must pin and verify
the fetched script SHA256 before execution and needs its own review. Until then do not claim the historical
head script installs v0.2; native candidate testing uses its explicit candidate
script. Preserve a pinned historical route outside the default installer.

After qualification the two independently usable commands are:

```
curl --proto '=https' --tlsv1.2 -fsSL https://iris.radicle.network/raw/rad:z3x7GVHywRtV2nR9qA5V4VqAVvCDg/head/scripts/install.sh | sh -s -- --quickstart --debug
curl --proto '=https' --tlsv1.2 -fsSL https://raw.githubusercontent.com/Epiphytic/marmish/main/scripts/install.sh | sh -s -- --quickstart --debug
```

Each URL serves a complete standalone script; neither script fetches the other
source before it can operate. Quickstart/debug remain explicit flags and the
README advertises both separately, Radicle first. A Radicle outage therefore
has a straightforward GitHub command without requiring Radicle discovery.
The script/channel is the trusted source, as before; publisher authenticity
against compromise of that channel is not invented. No execution of partial
function definitions and no shell-evaluated metadata.

The generated script pins one exact canonical `0.2.P` or `0.2.P-rc.N` plus three
manifest SHA256s. It must never consult GitHub's general `releases/latest`, parse
an unconstrained latest tag, select v0.1/experimental Python assets, or silently
fall back to an older release. Release assets may live on the fixed GitHub
`Epiphytic/marmish/releases/download/vVERSION/` origin for both source commands.
Download failure is a finite failure, not a legacy or alternate-version fallback.
This is source-script redundancy, not independent asset hosting: both scripts
require GitHub release availability; README states that limit.
The complete native Rust asset set and target grammar stay unchanged: CLI,
daemon, worker, licenses and pinned manifest. No fourth installer executable is
added. Rust install handles local verified downloads; the POSIX bootstrap alone
uses existing curl for fixed HTTPS fetching, so no Rust HTTP dependency is needed.
A future update to the default requires replacing exact pins after qualification;
there is no runtime best-effort release selector.

## Disjoint native interfaces

New modules live in `crates/marmish-native/src/`; root owns declarations, public
CLI argument parsing and startup/daemon integration. No manifest/Cargo.lock
mutation without root coordination. Concrete boundaries:

- `native_manifest`: strict approved manifest parser and directory verifier;
  typed `Manifest`, `ReleaseMetadata`, fixed asset names and format identifiers.
  `Manifest::parse(&[u8])->Result<Manifest>` and
  `verify_directory(&Path, AssetNaming, expected_manifest_sha:[u8;32])->Result<Manifest>`,
  where `AssetNaming` is the explicit closed choice `VersionedDownloads` or
  `InstalledFixedNames`; neither mode guesses/adopts filesystem entries.
  Hash/size/mode/type/link and provenance checks are mandatory; directory receipts
  remain installation ownership evidence, not supplied by the download manifest.
- `native_install`: `run(InstallOptions)->Result<InstallReport>`, synchronous,
  no provider/profile/MDK/network calls. Options contain absolute prefix/bin/state
  paths, debug and typed action `Install{source_dir,manifest,manifest_sha256}`,
  `Select{version}`, `Status`, or `Uninstall`. `Select` means a previously owned,
  completely reverified installed version; it is not a network release lookup.
  All filesystem transaction and crash recovery invariants in the parent design
  apply. The CLI emits finite serializable reports, never raw filesystem errors.
- `native_setup`: `async run(SetupOptions)->Result<SetupReport>`. Options contain
  state root, named identity, backend, canonical helper path, interactive flag,
  optional explicit role/relay/Tor choices, add/revoke inbound grants,
  add/remove outbound trust, explicit update/no-grants and debug. No private key
  import or new credential semantics are introduced. Interactive /dev/tty c/s/b
  defaults both; empty execution clients leaves inbound disabled. CLI root maps
  approved flags to these typed options; setup owns no daemon subprocess.
- `native_layout`: `resolve(&Path)->Result<ExecutableLayout>` validates canonical
  development versus managed installed mode. Root calls this before vault helper
  dispatch, providers or profile access for all three binaries, and reuses its
  canonical helper/worker paths. Installed mode requires both exact manifest and
  ownership receipt; malformed claimed layout never falls back to development.
  Root owns the shared read-only format preflight API/integration before mutable
  MDK/engine open. Native setup MUST call that same preflight before any of its
  own `MdkOwner::open` calls, not rely on daemon-only integration. Resolve checks
  a version's own valid manifest/receipt independently of the active selector,
  retaining old running daemon/worker compatibility after selection changes.
  It emits no stdout in helper children and does not rehash the entire asset set
  on every helper spawn; install/select perform complete hash verification.

Root exports crate-local configuration validation `CommandConfig::from_bytes`
using the existing strict normalization once, with no copied policy/npub/glob
parser. Setup preserves unmentioned existing JSON values semantically, validates
full proposed config before atomic replacement, and uses established default
policy/limits constructors. Export only actual format constants: published internal journal
is4, and the separately reviewed Finish amendment is expected to bump it to5
(older design text says3). Coordinate the owning agent and export the final
actual constant, never hardcode4 or an anticipated5. Identity profile2 and engine1; config and command
ledger constants must come from their owning code. No guessing schema versions.
Runtime read-only support checks distinguish proven version mismatch from
corruption/provider failure before upstream migration. Same-root version rollback
does not establish state downgrade safety.

## Setup lifetime, failure and compatibility

Reuse `ProfileLease::acquire`/`prepare`, native keychain providers and existing
transactional identity manifest. Build/validate setup choices before generating
credentials. Exclusively hold the actual profile lease during config reads,
identity initialization and atomic fsync config commit. If a running daemon
holds it, fail without mutation. Existing restrictions/limits/cwd/aliases remain
unchanged; grants and outbound trust stay independent/additive.

A narrow read-only `ProfileLease` setup snapshot reports the existing manifest's
Ready/not-Ready phase, public npub and recorded backend without regenerating keys.
For a Ready profile, setup never opens MDK or the journal: configuration editing
and public npub reporting use the validated profile manifest. It does not call
`prepare` merely to edit ready-profile configuration.
For a fresh or not-Ready profile (including interrupted initialization retry),
setup performs `prepare` on a blocking thread with the actual lease, then calls
the shared read-only format preflight before any mutable MDK/journal open. Proven
unsupported state fails `incompatible_state`; other probe failures remain finite
failures, never repairs or migration permission. The supported existing format
set and current write format are exported separately, not inferred from a single
number. Only after preflight passes may setup open an *unactivated* `MdkOwner`
directly, obtain its actual OpenedAccountBinding and call `mark_ready`; do not
use daemon open that enables a command engine from newly written config. No `activate`,
relay bootstrap, network publication, command worker or service starts in setup.
Once an owner exists, every exit path (including config commit failure) transfers
that owner and actual lease through existing `stop_owned`. Observer expiry keeps
and finishes the same PendingStop, and failures preserve owned state honestly.
The lease cannot be released before actual owner/runtime shutdown. Mark-ready
and config are separate durable operations: a config-commit failure may leave a
valid initialized identity; retry must reuse it and never rotate keys. If identity
initialization fails, no new config is committed. Repeated setup retains npub and
secret references; installed upgrade preserves old canonical helper versions.
No setup provider prompts are suppressed by pretending denial is unavailability.

All binaries remain native Rust; bootstrap needs no Python, uv, compiler, jq,
archive extractor or Cargo. Cargo source route is advertised only after its
exact three-sibling-binary build/install validation. No crates.io publication or
new production dependency is implied by this amendment.

## Acceptance additions and honest gates

Retain all parent Phase 3 offline transaction, nofollow/path/ownership, fault,
PTY/provider, rollback and native installed acceptance tests. Add:

1. Generated-script vectors reject v0.1/experimental/out-of-range versions,
   missing target pins and unconstrained latest selection; full local candidate
   assets run through the same parser/digests. Each standalone source script
   succeeds without contacting the other source URL. Broken fixed GitHub asset
   download fails without version fallback or installation mutation.
2. Release-script pin generation happens only after final target signing/hashing;
   verify all three manifest hashes and exact asset metadata. Native probe and
   install agree on compiled version, target, source and actual format constants.
3. Every setup failure path after acquiring an owner proves actual shutdown and
   lease retention; private state is retained if cleanup cannot be proven. No
   initialization/setting update starts an execution worker or relay connection.
4. Linux AMD64, Linux ARM64 and macOS ARM64: utility-only PATH excludes Python,
   uv, rustc and cargo; invoke actual bootstrap, initialize named client/server
   identities and configuration, then execute real direct Marmot commands through
   installed public CLI/daemon/worker. Validate binary argv/stdin/stdout/stderr,
   exit status, empty-grant denial, repeat identity and independently trusted
   outbound/inbound behavior. Cross-platform direct matrix remains a release gate.
5. Before default-head/README cutover, fetch and execute both HTTPS source URLs
   independently on each supported platform, check both scripts serve identical
   bytes including identical embedded version/target pins, using the qualified v0.2 pin and
   published assets; ensure outputs name v0.2 and no legacy runtime is invoked.
   This post-publication test cannot be replaced by source-build success.

Publishing candidate assets, changing default scripts and publishing final
release are centrally coordinated under the user's existing release authority;
no agent publishes independently. Record exact source/toolchain/features,
minimum runtimes, signing, manifests, tests and latency/goodput. A partial mirror,
asset, platform or public CLI failure is a blocker, not an excuse to select v0.1.
Tor failures remain documented experimental observations and do not block the
v0.2 direct-only qualification. Actual independent Claude design and completed-
code approvals still precede implementation acceptance and publication.
