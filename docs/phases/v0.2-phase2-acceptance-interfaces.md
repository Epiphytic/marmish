# Phase 2 amendment: local acceptance evidence and bounded server lifetime

**DESIGN APPROVED — [independent Claude r4 review](../reviews/v0.2-phase4-design-r4.md),
with its nonblocking lifecycle clarification incorporated below.** This amends only local acceptance
interfaces and `--max-commands` drain semantics in the approved Phase 2 design;
its original document and interface supplement remain unchanged. Phase 1 hosted
acceptance and completed Phases 2/3 still block Phase 4 implementation. Beads
`marmish-7nw.3` and `marmish-7nw.5` record dispositions. No implementation,
process-cleanup qualification or passing command evidence is claimed.

## Scope and verified existing boundaries

The existing engine exposes `status`, `cancel` and consuming `into_cleanup`.
Status reconciles and can start accepted work; it is not a pure database query.
Cancel records a request through the authenticated engine owner, not an arbitrary
PID signal. `into_cleanup` closes storage while retaining frontend/job/IO locks
in CleanupGuard; it requires every recorded job Exited, absence of its exact
recorded worker identity and owned job directories that are a subset of recorded
jobs (at most256), not equality of those sets. Busy, uncertainty
or unexpected entries fail. Native process identity includes boot/start identity,
not only PID. Worker ChildOwner additionally verifies worker, unreaped command
leader and PGID before signalling its group. Escaped setsid descendants are not
hostile-process containment; the qualification fixture must not daemonize/escape.
These contracts are inspected in engine `lib.rs`, `cleanup.rs`, `launcher.rs`
and `worker.rs`; no new public raw PID or signalling API is proposed.

The amendment adds bounded same-UID local IPC evidence snapshots, local
administrative cancel-by-ledger-key, explicit consuming cleanup preparation and
shutdown quiescence reporting.
None is a Marmot wire operation or a way to mint a remote Owner. No second live
MDK/journal/engine database connection is opened.

## Actor-owned read-only evidence

Add local methods `command_evidence` and `command_cleanup_status`, behind the
existing Linux SO_PEERCRED/macOS getpeereid check and owner-only socket directory.
They read cached actor-owned durable command facts only; never call Engine::status
on the actor or await bridge work. Normal background Observe completions refresh
engine facts through the existing bounded engine OS thread and CommitAck barrier.
Stale/unknown observations remain explicit; reads do not trigger command launch.

`command_evidence` request is exact `{after:null|U64,limit:U32}` with limit1..64.
Return `{rows:[Evidence],next:null|U64}`. Cursor is a dedicated AUTOINCREMENT
server-ledger row ID, exclusive ascending, never reused. Each row is capped at
4096 encoded bytes; enforce the final64KiB IPC frame even at64rows, reducing the
page at row boundaries if necessary and returning its actual last cursor. Never
silently skip a row. Concurrent changes can make successive pages non-atomic;
final quiescent pass and digest agreement are required for acceptance.

Evidence exact fields are `cursor,principal,group_sha256,session,invocation,
submit_sha256,engine_admitted,outcome,stdout,stderr,authority_valid,worker_state,
observed_seq`.
Principal is lowercase hex32bytes; group hash is SHA256 of the authenticated MLS
group bytes; IDs/digests use reviewed command wire formats. No argv/stdin/output,
paths, provider metadata, PID, secret or arbitrary error string appears.
`engine_admitted` is null while uncertain,0 for definitive pre-engine refusal,
1 only after authoritative same-owner engine Found/accepted confirmation. This
is a per-invocation engine-known fact, not an independent worker launch counter.
The server cohort requires exactly three (or selected expected count) distinct
valid immutable invocations with value1; duplicates retain the same row.

Outcome is exactly the reviewed command terminal `{kind,value}` or null; it
never embeds noncanonical-path error detail or arbitrary native text. Each stream is
`{produced:U64,closed:bool,gaps:U32,sha256:null|HEX64}`. Produced/closed/gaps come
from committed engine observations. SHA256 is optional: populate only when the
server actually read the complete retained stream from offset0 in bounded pages,
verified no gap/expiry/revocation and committed the matching terminal closed
snapshot. Hashing is an optional asynchronous engine-thread operation; no cheap
constant-time full-output hash is assumed. Otherwise null. A missing hash alone
does not fabricate a failure or success: Phase 4 uses exact client+fixture hashes
independently; any gate that explicitly requires server hashes is not qualified
until complete evidence exists. Unknown produced/outcome/worker data fails final
command qualification. Native invalidation/revocation clears authority_valid and
invalidates affected success evidence; it never clears engine_admitted or permits a
rerun. Worker state is `running|exited|unknown`, where exited means a committed
engine observation proved recorded worker absence; terminal output alone is not
such proof. Unknown never means exited.

A narrow new engine wrapper is required on the OS thread:
`owned_worker_presence(&mut self, &AuthorizedContext, InvocationId)
-> EngineResult<OwnedWorkerPresence>` with `Present|Absent|Unknown` only. Its
exact read-only path is `owner(ctx)` (including check_uid), `store.job_for`,
`store.job_state`, `store.worker_identity`, then `root.presence(job, recorded)`.
It must NOT call `authorized_job`, `reconcile_step`, `recover_absent`, or write
storage: those paths may launch Accepted work. A matching Live identity maps
Present, Absent maps Absent, and Initializing, UnsafePath or any other error maps
Unknown. Missing directory for Accepted means Absent but never exited; only
state Exited AND Absent proves exited. No caller PID is accepted. This is proposed
API, not an existing public method; no engine schema/signalling change is needed.

`command_cleanup_status` request is exactly `{}`. Return
`{active:U32,uncertain:U32,worker_running:U32,worker_unknown:U32,
engine_quiesced:bool,observation_pending:bool,
cleanup:"open"|"draining"|"quiesced"|"failed",final_seq:null|U64}` capped at4096bytes.
Active uses the approved shared active predicate including feeders; uncertain
counts unresolved dispatch/engine observations and engine UnknownLaunch/Lost
states, without double counting one row. Counts are cached actor snapshots,
not claims that workers cannot change later. The duplicate representations must
always agree: engine_quiesced == (cleanup == "quiesced"); reject inconsistent
status rather than infer either value. Reads never reconcile, cancel, launch, or terminate work.

Evidence freshness uses a durable monotonically increasing observation sequence.
Preparing cleanup first allocates and commits a fence `final_seq` BEFORE its
final refresh, after closing admission and committing existing operations. Every
included server row means EVERY server ledger row in that profile, including
unexpected admissions and previously terminal rows. Each engine-bound row first
gets a read-only job_state check on the engine thread: any state other than Exited
fails preparation before consumption, without reconciliation. For Exited only,
read status via owner(ctx) -> store.job_for -> store.status, then raw
owned_worker_presence. Never use Engine::status/authorized_job/reconcile_step for
this pass; a stale cache must not cause Accepted work to launch while draining.
The observation is committed through
CommitAck with observed_seq >= that fence. A failed/unknown observation cannot
qualify. A definitive pre-engine refusal instead refreshes its stored refusal
and proves no engine binding under the recovery barrier; it cannot be relabelled
as engine-admitted. Only after all included rows have committed fresh facts may
the engine be consumed. final_seq is NOT the maximum sequence at completion:
that would incorrectly exclude rows refreshed earlier in the same pass. Acceptance
requires quiesced, all server ledger rows at/after final_seq, matching immutable
bindings, and final authority validity. Invalidation/revocation after the fence
voids the affected proof, including after quiescence; it is never masked by a
frozen engine snapshot. Failure to maintain authority observation fails acceptance.

The encoded-row test vector uses maximum-width U64/U32 fields, longest IDs and
finite terminal outcome, all hashes present, and observed_seq. The separate
command error detail bound is1024 JSON-encoded bytes (not1024 raw bytes); paths
are excluded from this evidence schema and must not be copied into outcome. It must prove <=4096 bytes without truncation;
the page test fits complete rows under64KiB and returns the last included cursor.
If the finalized closed outcome encoding exceeds4096, schema qualification fails
before implementation acceptance; arbitrary detail truncation is forbidden.

## Explicit local cleanup and shutdown proof

Add same-UID `command_local_cancel {cursor:U64}` for server ledger rows. It selects
only an existing sealed server-side Owner/key from that actor's journal and
queues the existing EngineOperation::Cancel. Return `{queued:bool}` or finite
busy/not_found/unknown/server_draining; no argv, endpoint, principal, UID or PID is accepted from IPC.
This is explicitly a new local administrative capability, not read-only evidence
and not automatic disconnect cancellation. No job is created, token issued or
new Owner constructed. Unknown dispatch remains unknown; cancellation/reconcile
must obey the existing recovery barrier and never translate operational failure
into Missing. The native harness may invoke it only for its own disposable
profile's admitted fixture rows during failure cleanup. General user commands
continue on normal client detach and ordinary daemon uptime expiration.

Add same-UID `command_prepare_cleanup {}` returning `{queued:bool}` or finite
busy/server_draining: an explicit destructive local lifecycle, never a wiremethod.
The harness invokes it only after active=0, uncertain=0, worker_running=0,
worker_unknown=0 and observation_pending=false; the actor rechecks these facts.
Admission closure is irreversible for that instance: cleanup transitions
open -> draining -> quiesced OR failed, never back to open. Draining closes all
new command/engine admission, commits registered operations, performs the final
refresh/fence above, then queues consuming Engine::into_cleanup on the sole
engine thread. No implicit cancellation occurs. The harness requests explicit
local cancellation of its own remaining fixture rows BEFORE prepare and polls
within launch-relative deadlines. Ordinary disconnect/uptime never invokes it.

into_cleanup consumes Engine even on Err. A failed consume therefore transitions
to terminal failed for that daemon instance, preserves on-disk state, never reopens
the engine, and makes every engine-dependent IPC or Marmot status/poll/cancel
reply finite server_draining/unavailable. Only ordinary stop follows; no deletion
is authorized. A pre-consumption final-refresh failure also transitions explicitly to failed.
The still-unconsumed engine remains retained but unused: no further engine
operations or reopen in this instance, the same finite unavailable responses,
no deletion authorization, and only ordinary stop follows. Actual
UnknownLaunch/Lost are engine states, not invented permanent product restrictions:
they disqualify this fixture run while unresolved, and consuming cleanup must
apply the actual engine requirement that every recorded job is Exited. No wrapper
may rewrite those states to make cleanup pass or claim the engine can never
recover them in another product session.

After success the engine thread holds CleanupGuard and serves no engine operations.
The read-only cleanup status reports engine_quiesced=true. **Keep that guard
alive until engine state removal finishes**, as the existing API requires. The
supervisor may then remove only its independently registered private engine
subtree while daemon/engine thread remain alive holding the guard. The native
harness retains its allocation receipt (parent/root device+inode and exact basename),
while daemon retains the current profile lease. Deletion uses held directory
handles and nofollow relative operations, prevalidating at most4096entries and
depth8: directories must be owned0700, files owned0600 regular/single-link. Links,
sockets/FIFOs/devices, changed identities or exceeded bounds fail/preserve; a
partial deletion cannot become successful cleanup. Walk only that registered
engine subtree, never a path from IPC/metadata or a generic rm-rf. This bounded
routine is fixture-only, not a product uninstall/state-prune feature. No IPC accepts a deletion path or PID. The current profile lease and CleanupGuard
remain held across the entire removal; neither is released on a mere status query.
The supervisor checks waitpid(WNOHANG) before the first unlink and after the last
one, then obtains a same-socket cleanup_status reply still quiesced with the same
final_seq. A zombie has released its locks and is not live proof. Only then the
supervisor requests ordinary daemon stop; after it closes journal/MDK and is reaped,
the harness removes remaining owned profile/install scratch state. If engine
subtree removal fails, retain the guard until bounded shutdown, report failure
and preserve state. A daemon failure before protected removal loses the proof:
never delete that engine subtree based on an earlier status response. Uptime
expiry or ordinary stop during draining/quiesced drops the guard and invalidates
proof; the run is red and deletion must not start/continue. The supervisor reserves
cleanup time inside the original uptime, not after it.

A finite shutdown report, on the daemon's supervisor-owned output channel outside
its removable state, is `{schema:1,engine_quiesced:bool,engine_stop_complete:bool,
mdk_stop_complete:bool,runtime_cleanup_complete:bool}`. Emit only real outcomes,
not a zero-exit inference. The supervisor owns its actual daemon child, confirms
it remained live throughout protected engine removal, then reaps it. The harness
disallows another owner; same-UID malicious replacement is outside the product
threat model. Normal daemon shutdown may preserve running user workers and state;
that is valid product behavior but not a passing fixture cleanup. Failure emits
no public secrets and cleanup is red.

## Admission-only max-commands semantics

This section replaces Phase2's bounded-drain/automatic-stop semantics (its
Server lifetime section, formerly lines511–517). `--max-commands` requires an
explicit finite `--max-uptime`; without it reject configuration rather than wait
forever. `--max-commands N` stops new unique engine admissions at N; it does **not** stop
local IPC, Marmot status/poll/cancel, retained convergence, worker completion or
output serving. Reserve bounded ledger credit so accepted concurrent admissions
cannot overshoot N. Denials, retries and ledger-only/uncertain reservations do
not count as confirmed engine admissions. Definitive pre-engine refusal releases
its reserved credit immediately; only unresolved reservations retain credit until
authoritatively reconciled. A current uncertain launch cannot release a slot as definitely absent.

After reaching N, continue serving until explicit supervisor stop or the original
`--max-uptime` deadline, whichever comes first. There is no client-ACK protocol or
new Marmot message. A test supervisor observes bound ClientTerminal artifacts and
then performs explicit cleanup while the daemon remains alive, and only after
protected removal requests ordinary stop, all inside the original service uptime. Reaching the deadline without all required
terminals is failed acceptance even if daemon exits0. Uptime/ordinary stop never
automatically cancels accepted user work; the harness uses explicit local cancel
when cleaning its disposable fixture jobs after failure.

## Focused verification and ownership

Root owns IPC/schema/daemon amendments; engine-thread owner adds cached observation,
worker-presence and consuming quiescence operations using existing safe internals.
Journal owner adds durable cursor/snapshot fields atomically with existing command
facts; no independent store or migration promise. Native profile formats are fresh.
Read-only snapshot/query types do not expose Engine or storage handles.

Tests require wrong-UID denial, exact frame/cursor bounds, no actor engine/fs IO,
unknown/stale facts remaining unknown, native invalidation removing success,
engine admitted count unchanged on duplicate/conflict, local cancellation unable
to select another profile or invent Owner, forged/reused process identities never
signalled, worker lock/identity uncertainty preventing cleanup, consuming guard
held through actual engine-state removal before shutdown, and no state removal after failed proof. An Accepted job with no directory must
return Absent without changing its row or spawning; a still-live worker at prepare
must yield failed/unavailable with preserved state. Test uptime expiry while the
guard is held, observation fence allocation before refresh, stale-row rejection,
terminal-but-unobserved worker becoming exited in final refresh, stale Accepted
cache failing without launch, all-profile-row refresh including unexpected
admissions, quiesced representation agreement, and authority
invalidation after the fence. Exercise terminal
outcome with still-live worker, escaped-descendant limitation and missing/expired
server-output hash. Verify Nth admission keeps status/poll alive until supervisor
stop, retries use the same invocation, uptime failure is not successful drain and
normal disconnect does not cancel. Require actual installed native fixture cleanup
on all targets and independent Claude completed-code review before claiming this
interface is available.
