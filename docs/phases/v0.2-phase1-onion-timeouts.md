Design approved by [actual Claude review](../reviews/v0.2-native-onion-timeouts-design-r1.md)
of SHA256 `05e8731377d70d3ff8a34a6484b5bd036e30b095e5c5c874ecd57d0ced19c6cf`.
Implementation and hosted acceptance remain pending. Beads `marmish-7nw.2`. Source
`22019f9de06327cbab7c7df373d5faf260625cff`. This is a bounded correction to
Phase1 connection timing; it does not accept Phase1, authorize Phase2 code, or
change route authority, message authentication or the wire protocol.

## Evidence and actual dependency contracts

[Hosted owner report](../validation/v0.2/hosted-41565379100-owner-cleanup.json)
records the first owner's connected WebSocket, then the second owner's completed
Arti bootstrap and three sequences of `arti_connect/begin`,
`connector_failure/timeout`, SDK transport failure and terminated status. No
second-owner `relay_stream/connected` occurs. Fixture stage is `native_check`;
relay children and private state were cleaned, native cleanup is unproven.
This locates the failure before obtaining the onion stream, not in WebSocket
handshaking. It does not prove network reachability or that more time will work.

Actual native boundaries:

- `crates/marmish-native/src/transport.rs`: `TransportLimits::default/validate`
  defaults and caps `handshake_timeout` at15s. `open_socket` applies that timeout
  to semaphore acquisition, Arti/TCP stream creation, TLS and WebSocket together.
  `connect_once` maps Arti-returned failures to `arti_connect`; the outer elapsed
  timeout becomes `Error::Timeout`, producing the observed finite `timeout`.
- `mdk_adapter.rs::connect_startup_relay` independently limits each of three
  `try_connect().timeout(...)` turns to15s. `activate` already receives one
  absolute deadline shared with bootstrap, publication and subscription work.
- `mdk_adapter.rs::recover_transport` bounds `try_connect_relay` by both15s and
  the current actor-call deadline. The daemon and foundation driver supply15s
  tick deadlines. Raising only the connector timeout leaves this cancellation.
- `foundation_check.rs::execute` gives each activation at most150s and keeps its
  existing overall570s execution/600s including cleanup. Daemon activation is
  also150s. None of those budgets will increase.

Pinned primary source inspected locally, without a network probe:

- rust-nostr `48801bf6f2f1cd55bb1729e94159946c8832a786`,
  `nostr-sdk/src/relay/inner.rs::_try_connect` wraps the entire injected transport
  future in its supplied timeout. `relay/api/try_connect.rs` defaults to15s and

  report's `transport` rather than `timeout` after our own elapsed timeout.
- SDK `relay/mod.rs::connect` immediately queues its owned connection task.
  `inner.rs::request_connect` reserves one owner; requests during retirement are
  retained; Pending/Connecting do not start another dial. The task uses
  `RelayOptions.connect_timeout`. With `reconnect(false)`, a failed attempt ends
  terminated rather than retrying indefinitely. `wait_for_connection` only waits
  for status and can time out without cancelling the connection task.
- SDK `client/api/add.rs::AddRelay` has an explicit `connect_timeout` setter;
  its constructor starts with `RelayOptions::default`, and its future passes
  those options to the pool. Setting only ClientBuilder's timeout is insufficient

  and adaptive circuit/round-trip timeout estimation. `state.rs` explicitly
  shares a spawned circuit-construction task among waiting callers. Dropping

## Proposed transport contract

Keep direct connections' existing15s total envelope unchanged. Add one bounded
`TransportLimits.tor_connect_timeout`, default120s, accepting only positive
values<=120s. Existing bootstrap timeout remains120s; existing handshake timeout
remains positive<=15s. These are connection limits, not an increased global
activation budget and not a user-facing timing configuration in this increment.

For a configured Tor route (onion or ordinary WSS with `--tor always`):

1. Acquire the existing per-relay permit and obtain the Arti stream in one
   `tor_connect_timeout` envelope. Semaphore waiting consumes that same budget.
2. After the stream exists, TLS if needed and WebSocket together receive a new
   single `handshake_timeout` envelope, never15s each.
3. Bound the whole attempt by their checked sum (default135s). Terminal connector
   cancellation remains selected throughout both phases, including permit waits.

For direct routes retain the original single `handshake_timeout` envelope over
permit, TCP, TLS and WebSocket. Do not resolve onion names locally, permit proxy
injection, introduce alternate relays or route a Tor failure directly.

Expose a small policy/connector accessor such as
`connection_timeout(&Url) -> Result<Duration>` which validates configured relay
membership and returns15s for Direct or135s for Tor with default limits. Reuse
this calculation at every SDK admission point. No duplicated route heuristics.
Set ClientBuilder's default to the policy maximum and explicitly set
`AddRelay::connect_timeout(connection_timeout(endpoint)?)`; the latter is the
operative bound for SDK-owned recovery tasks. Existing frame/queue/relay limits
and the one-permit lifetime spanning both SDK halves remain unchanged.
Pass the existing derived `RelayLimits` explicitly to `AddRelay::limits` too;
the builder-only limits otherwise do not reach this SDK admission path.

## Startup: preserve the original absolute deadline

Keep the existing maximum of three attempts and terminal Banned/Shutdown rules.
For each attempt choose `turn_end=min(original_activation_deadline,
now+connection_timeout(endpoint))`; supply its remaining duration to SDK
`try_connect().timeout(...)` and the existing status observer. Do not create a
fresh activation deadline after bootstrap, a failed attempt, or a status change.
All configured relays, bootstrap, acknowledged KeyPackage publication,
subscriptions and drain still share the caller's original absolute deadline.
Fast failures may use the next bounded attempt; a slow attempt may consume all
remaining activation time, leaving no further attempt. Preserve actual Connected
observation as a prerequisite; successful queuing or bootstrap is not readiness.

## Recovery: reuse the SDK-owned task across short actor turns

Do not add a Marmish background task, task registry or pending connection future.
Replace the recovery-only one-shot `try_connect_relay` with the existing relay's
public `connect()` and status observation. Keep explicit `reconnect(false)`.

For each configured endpoint, inspect its SDK status. Connected needs no dial;
Initialized/Terminated may receive one explicit `connect()` under the existing
reconnect pacing. Pending/Connecting must only be observed, never disconnected,
redialled or passed to a cancellation-prone one-shot wrapper on the next tick.
Banned/Shutdown remain finite failures; Disconnected/Sleeping must not be treated
as successful admission or trigger an unsupported dial. A retiring task can
transition to Terminated and become eligible on a later paced turn.

After scheduling eligible endpoints, return the existing recoverable/not-ready
outcome while any endpoint is not Connected. A bounded status wait is optional
and pending uses `Err(Transport("relay_reconnect"))`, preserving the driver's
existing retry and finite diagnostics. Extract a private production helper over
an SDK `Relay` so the real SDK task can be exercised with an inert transport.
Test both eventual Connected observation and the owner's publication fence while
any endpoint is pending. A bounded status wait, if used,
must use only the current caller deadline. Expiry of a15s tick stops waiting,
not the SDK-owned attempt. Do not reset its fixed135s SDK timeout on each tick.
The connector's own fixed phases independently bound any retained attempt.
A failed attempt may be retried on a subsequent paced turn, as current recovery
already permits; no automatic unbounded SDK reconnect loop is enabled.

This deliberately distinguishes actor-call lifetime from SDK connection-task
lifetime. Actor operations still return by their original deadline; the managed
service may remain degraded across calls. The foundation driver's outer570s
execution deadline and shutdown still terminate the owned SDK pool and connector.
No owner is considered recovered until every configured relay is Connected,
notification-loss handling and subscription recovery have completed, and the
existing publication fence is safely released. Preserve existing frozen
publication bytes, loss baselines and pending-message accounting. Do not clear
recovery merely because `connect()` returned or while an endpoint is pending.

Keep existing shutdown/Drop ownership: connector cancellation wakes in-flight
connect/permit futures, SDK pool shutdown terminates its tasks, and only then may
owned runtime paths be removed. Never detach an application-created task or infer
that dropping a waiter stopped Arti's internal shared circuit construction.

## Implementation ownership and validation

Scope is native `transport.rs`, its focused tests, the startup/recovery portions
of `mdk_adapter.rs` and focused tests, plus this amendment and sanitized evidence.
No installer, keychain, protocol, storage migration or CI deadline changes.
Coordinate disjoint ownership before coding; obtain actual Claude design approval
first, then actual Claude completed-code review after fixes and affected checks.

Use paused-time private production budget helpers with injected inert futures
rather than real Tor sleeps or tests that reproduce the algorithm independently:

- A Tor stream taking20s followed by a short handshake succeeds; the same direct
  attempt fails at15s. Tor stream>120s fails, and any post-stream TLS/WebSocket
  sequence>15s fails even when the stream was fast. TLS+WS share one15s budget.
- Permit acquisition counts toward route budget, an expired/cancelled attempt
  releases its permit, cancellation works in both phases, and both returned SDK
  halves retain the single permit until both drop. Bounds reject zero/excessive
  limits; route membership and no-direct-fallback negative tests remain.
- Startup waits beyond15s for a valid Tor connection but never beyond the exact
  original activation deadline, including bootstrap-consumed time, multiple
  endpoints and retries. Pending is not success; fast-failure count remains<=3.
- Exercise the pinned SDK's actual public Relay API with an injected inert
  delayed transport, not test-support flags: recovery Pending/Connecting spans
  multiple15s actor turns, issues one dial, and eventually recovers at>15s;
  repeated observations do not reset its original timeout. A permanent failure
  terminates within its route budget; later explicit retry remains paced.
- Cancellation/shutdown while SDK-owned recovery is pending leaves no retained
  Marmish task and releases the transport permit. Pending/failed recovery keeps
  publication paused and does not discard or regenerate native obligations.
- Existing direct/no-fallback, startup teardown races, notification-loss recovery,
  encrypted journal and trust suites pass; fmt/clippy pass. Preserve finite
  diagnostic pair vocabulary so the current owner report remains interpretable.

After code approval and publication, a fresh full hosted matrix must prove actual
Tor encrypted exchange, binary payloads, receipts, restart and cleanup. Record
failure honestly if increased bounded rendezvous time is insufficient. No phase
acceptance follows from this source diagnosis or fake-clock tests alone.
