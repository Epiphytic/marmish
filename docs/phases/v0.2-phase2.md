## Deliverable and exclusions

Native Rust client and server execute asynchronous byte-preserving commands over
actual Marmot, with durable admission, exact output/exit verification and restart
recovery. One daemon owns one named Nostr identity and may be client, server or
both; both is default, with execution disabled until execution grants exist.
Client disconnect, CLI exit and relay outage do not cancel accepted commands.

Only the current non-root Unix user executes commands, on Linux AMD64/ARM64 and
macOS ARM64. No root/setuid mapping, shell mode, PTY/tmux, multi-device pairing,
file transfer, forwarding, remote environment/cwd selection or staged/network
streaming stdin. Inline finite stdin is the first-release contract, not a claim
of SSH interactive equivalence. Executable grants confer the local user's program
capabilities; they do not sandbox arguments, files or networking.

## Existing contracts and implementation ownership

Reuse the actual `marmish-engine` Rust API, with `Engine::open_with_master`,
`NativeBinding`, `ProvidedMaster`, `authorize`, `issue_execute_token`, `submit`,
status/input/output/cancel and maintenance operations. Preserve its detached
workers, launch claims, SQLCipher state, input uncertainty and spool recovery.
Do not use `Engine::open` file-key defaults or migration APIs. Derive an independent
engine master from the profile SQLCipher root using HKDF domain
`marmish/v2/command-engine/1`; stable domain-separated profile hashes supply
NativeBinding root/key IDs. Persist this derivation version. Never pass keys in
argv/environment or reuse the MDK/journal key.

One MDK actor still exclusively owns upstream runtime and its shared encrypted
connection. Extend accepted-room purpose selection and application projection;
never open another MDK instance or SDK pool. Upstream pin remains
`8abc51befbf71a1ae3bdbb25eb0860c731e75db2`. `send`, `drain`, convergence and Welcome
retry can publish internally, so retain the actual transport-boundary publication
pause and frozen native obligations. Same explicit relay allowset covers discovery,
Arti, reconnection and publishing. Publication acceptance is not application
receipt. Upstream pending-event listing still allocates a full list: finite actor
turns cannot promise a bounded upstream allocation.

Only adapter verification constructs private `AuthenticatedCommandContext`:
local/peer account, **MLS group bytes**, transport-group ID, session, fixed

of **MLS group bytes, never transport routing ID**, target UID the daemon's UID.
A decoded payload or same-UID IPC caller cannot fabricate remote authority.

## Configuration, roles and worker placement

Use private profile-local `config.json`, version1, exact top-level fields:
`version,role,relays,tor,trusted_remotes,execution_clients,command_policy,cwd,limits,aliases`.
Role is client/server/both. Relays are nonempty explicit URL arrays; tor uses the
existing auto/always/off modes. Identity remains selected by `-i name`; config
contains no private key. Unknown keys/duplicates and unsafe file ownership/mode
fail closed. Secrets/config directories0700 and files0600. Roles/grants/policy,
limits, aliases and relay policy load once at daemon start; **hot reload is not
supported in this phase**. Configuration changes require orderly daemon restart;
workers survive. Running commands retain their accepted settings. No SIGHUP or
atomic reload API is implied.

`trusted_remotes` controls outbound targets; `execution_clients` controls local
execution. Client-only never admits remote commands. Server-only does not
originate commands. Both with no grants does **not** construct Engine because
its policy requires nonempty allowed principals. Construct Engine whenever the union of current grants and historical principals
with retained command records is nonempty, regardless of configured role. Only
a profile with both sets empty omits Engine. This permits recovery and same-UID
local status/cancel after the last grant is removed or role becomes client-only.
Cap the union at4096, matching engine admission bounds; validate before opening.
Overflow disables new network admission with identity_capacity, preserves every
record/worker and leaves local status/cancel available through the previous
valid engine owner. On cold start with an invalid union, do not truncate it or
open a second owner: report recovery_blocked and require local configuration
correction; existing detached workers continue. Admission/GC must prevent this
state normally by refusing new distinct-principal grants above4096. At each start
include that validated union in EnginePolicy. Network admission/reads/cancel
are independently gated by current service grants. Historical principals receive
no new remote execution grant by being present in the engine list. Engine command
policies use only principals in that union; inactive historical keys have no
permissive network path. Local administration uses the retained sealed owner
binding to authorize engine status/cancel; it cannot submit as a historical peer.

Install a thin dedicated Rust `marmish-worker` binary from the native package
alongside `marmish` and `marmishd`; it sets RLIMIT_CORE=0 and calls existing
engine worker_main. Vault helpers are already embedded `_vault-helper` dispatches
in the native binaries; no separate vault-helper executable is needed. Resolve its absolute sibling path from the validated executable
installation, never PATH/environment. Existing engine worker contract is precisely
argv(root,jobhex), without a `--worker` discriminator. Preserve its root/user
ownership and non-group/world-writable ancestor checks; unsafe installation paths
fail with a finite installation error. Do not weaken checks to accept arbitrary
user-writable ancestors. Native packaging must include this binary.

Freeze existing worker behavior: cleared environment with exactly passwd-derived
HOME/USER/LOGNAME, PATH=/usr/bin:/bin, LANG=C; cwd=configured existing directory or
passwd home; umask077, setsid, CLOEXEC sweep and core limit0. There is no TMPDIR,
Homebrew PATH or general resource sandbox. Validate configured cwd at startup.
All argv0 must be absolute and canonical. Enforce this in service validation and
with an always-effective engine baseline `allow_exec:["/**"]` plus user layers,
so engine launch also calls its canonical-path check. Deny aliases/symlinks such
as merged-usr `/bin/ls`; finite `noncanonical_executable` may provide the local

## Purpose and authenticated room admission

Native command room name is `marmish/command/1/<session>` and description exactly
`marmish-command/1 command transport`. Session is timestamp-prefixed hex32 as
below. The opener is client, invited peer server; persist this immutable direction
before dispatch. Reverse commands from the same both-role identity use a separate
room. Default reuse key is local identity+remote identity+canonical explicit relay
set+direction; `--new-session` creates independent MLS group keys.

Apply Current-profile membership checks: exactly self+peer, one leaf each,
expected authenticated welcomer, creator-only admin, required default components
plus Nostr routing, forbidden account-device/retention components, exact purpose,
unique session/transport-group binding and nonempty configured-relay intersection.
This requires an explicit purpose selector in current `check_group`, not passing
command traffic through its hardcoded foundation prefix. No custom component ID
or test-only profile. Cap command rooms at64 live per identity, separate from
foundation caps. Initially invalid unsolicited/policy-conflicting rooms are
forgotten and pending ACKed only after cleanup proof, without consuming rejection
metadata. Valid capacity refusals and previously accepted/revoked room history
follow bounded durable admission decisions, using the independent command floor.

Accepted membership/admin/purpose changes revoke room authority; remove routes
and refuse new remote operations. Already accepted OS commands continue, with
local cancellation available. Native invalidation changes the authenticated
status/evidence and cannot silently preserve a successful remote result. Existing
operational storage/quarantine failures preserve pending work; they are not
invented policy violations. Commands in foundation rooms, ordinary DMs and legacy
v1 rooms are never recognized by this dispatcher.

## Exact native wire contract

This conditional proposal specifies **`marmish-command/1`**, a deliberate new
application protocol, only if the user selects that direction.
It does not claim live `marmish/1` compatibility. The actual legacy MLS outcome is
`unverified-prerequisite`; preserve the pinned Python reference and historical v1
vectors as optional test material, not a production decoder/fallback. Fresh disk
formats are authorized independently; they provide no wire-break authority. The
conditional distinct wire discriminator/purpose makes a proposed protocol break
explicit rather than interpreting old fields differently. A later legacy
adapter requires separate design and compatible MLS evidence.

MarmotAppEvent kind30100, exactly one tag `["marmish","command/1"]`. Canonical
compact sorted-key UTF-8 JSON, no whitespace; reject duplicate/unknown/missing
keys, noncanonical forms, invalid base64/hex, nonfinite values and bool-as-integer.
Maximum final encoded content32768 bytes is checked after complete serialization,
including base64, tags-independent envelope and response metadata.
Outer keys exactly `protocol,type,session,id,client,server,op,body`.
Protocol literal above; type=request/response; client/server hex64 account keys;
session/request ID hex32; op submit/status/poll/cancel. Each must match sealed
room direction and authenticated sender. Requests originate client, responses
server. MLS group is supplied by authenticated context, not accepted from a body.

| Request op | Exact body |
| --- | --- |
| submit | `invocation,argv,stdin` |
| status | `invocation` |
| poll | `invocation,stdout_cursor,stderr_cursor,max_bytes` |
| cancel | `invocation` |

Invocation and request IDs are12hex Unix-seconds +20hex random suffix, lowercase.
The client normally uses a fresh request ID for each retry/status query, retaining
invocation and canonical submit bytes. Argv is1..128 canonical padded-base64 Unix
byte strings; total bytes+separators<=16384; argv0 absolute, no NUL anywhere.
Stdin is canonical padded-base64 bytes, empty means EOF, decoded length<=16384.
**These individual maxima are not simultaneously guaranteed:** combined final
submit envelope must also fit32768. CLI reads finite stdin to at most16385bytes
before admission, rejects overflow or final-encoded overflow before any send,
and never launches with incomplete input. No shell/staged upload/network input
ops exist.

Invocation digest layout is exactly the following concatenation, hashed SHA256:
ASCII `marmish-command` followed by bytes00,01; u32be group-byte length followed
by MLS group bytes; decoded16-byte session; decoded32-byte client; decoded32-byte
server; decoded16-byte invocation; u32be argc; for each argv element in order,
u32be byte length followed by its raw bytes; u32be stdin length followed by raw
stdin. Every integer is unsigned big-endian, with no terminators or implicit
Unicode conversion. Request ID is excluded. Response request_sha256 is SHA256
of complete canonical request UTF-8 bytes, no trailing newline. Response outer
id exactly echoes request id; a regenerated response to a fresh request gets that
fresh id/digest, while retained retries of one event preserve its frozen bytes.

Response body has exactly `request_sha256,ok,result,error`. Success has a result
object and null error; failure null result and `{code,detail}`. Detail is null
except noncanonical_executable may return a canonical-path UTF-8 string whose
JSON-encoded representation<=1024bytes (otherwise null). Every schema below is
closed: no additional fields, null only where explicitly allowed.

| op | Exact success result |
| --- | --- |
| submit | `{disposition,status}`, disposition=`accepted` or `existing` |
| status | `{status}` |
| poll | `{status,stdout,stderr}`, each chunk exactly `{bytes,next_cursor}` |
| cancel | `{status}`; cancellation requested is not proof of termination |

`status` has exactly `invocation,admission,engine_known,state,outcome,cancel_requested,input,stdout,stderr,warning,authority_valid`.
Invocation is hex32; admission=accepted/dispatching/engine; engine_known and the
last two boolean fields are booleans. State=accepted/launching/running/exited/
unknown_launch/lost; before a known engine result use accepted, engine_known=false.
Outcome is null or exactly `{kind,value}`: kind=code with integer0..255,
signal with integer1..127, or not_started with null. Warning=null or
stdin_unconsumed or input_failed. Authority_valid=false disqualifies authenticated
success and prevents new remote operations; local status still exposes it.
Input exactly `{length,accepted,delivered,health,eof_sent}`: byte counts integers
0..16384, health=open/eof_pending/closed/gap/uncertain, eof_sent boolean.
Each stdout/stderr status exactly `{retained,produced,closed,gaps}`; counts integers
0..2^63-1, closed boolean, gaps array of0..4entries. Each gap exactly
`{start,end,reason}`: start integer0..2^63-1, end null or integer>start,
reason=limit/storage_failure/expired/uncertain_tail. Chunk bytes are canonical
padded base64, next_cursor integer0..2^63-1. Missing/collected command history
returns error, not a synthetic exited status. A status query for a durably
refused row returns its stored finite refusal code; it never fabricates an
admission enum/state for a job that was not admitted. Input status before engine admission
has accepted=delivered=0, health=open, eof_sent=false. Input length always reflects
the immutable request, not a fresh caller assertion.

Finite **wire** errors are exactly invalid_request, unauthorized, role_disabled,
command_denied, noncanonical_executable, invocation_conflict, expired,
future_deferred, future_excessive, clock_behind_floor, quota_exceeded, busy,
not_found, result_expired, recovery_uncertain, input_failed, storage_failure,
transport_degraded, authority_revoked. Untrusted malformed frames are dropped
without reflection if no trustworthy response context can be constructed.
future_deferred/busy/quota_exceeded/storage_failure/transport_degraded remain
retryable operational errors, never a cached terminal execution decision.
A command with engine-known=false and a live operation returns accepted snapshot;
no worker_unavailable response may be interpreted as proof of no admission.
Local-only CLI/IPC categories are local_busy, invalid_config, identity_capacity,
recovery_blocked, input_too_large, envelope_too_large, local_io, remote_pending,
transport_failure, output_gap, invalidated, stdin_unconsumed and remote_exit,
in addition to wire errors. They are never silently added to the wire enum.

Poll returns status and stdout/stderr `{bytes,next_cursor}`. Cursors integer
0..2^63-1. `max_bytes`1..16384 is a **combined decoded-byte budget**, default16384;
allocate up to8192 per stream first, then unused budget to the other. Bound gap metadata to the actual engine maximum4ranges per stream; no invented
truncation flag. With at most16384 raw bytes, base64 totals at most21848 bytes;
all fixed fields, IDs, worst-case20-digit cursor integers and8gap entries must
fit a separately enforced4096-byte metadata ceiling. Thus full response<=25944
bytes, below32768. Codec rejects oversized metadata as storage_failure rather
than claiming partial cursor progress. Client has exactly one outstanding combined
poll per invocation and never speculates past received next_cursor. It deduplicates replies
before writing bytes. No throughput target is promised:16KiB per response is an
upper bound and actual direct/Arti goodput is measured. No hidden push channel.

Normative digest fixture (freshness is evaluated separately): MLS group is32bytes
of0x33; session=`00006a00000000000000000000000002`; client32bytes0x11;
server32bytes0x22; invocation=`00006a00000000000000000000000001`;
argv is one raw byte string `/usr/bin/true`; stdin empty. Concatenated digest
input has174bytes and SHA256 `783fa59ee2d2c19d7408cfcf3963e8ed542572648ce6a9b993a17ac0e5bf50be`. The argv base64 is
`L3Vzci9iaW4vdHJ1ZQ==`, stdin base64 empty string. Codec fixtures must include
this exact vector plus all closed result/error shapes above; implementation tests
may not replace these fields with engine serde enum serialization.

## Durable command ledger, freshness and crash recovery

Use separate SQLCipher command tables in the existing application journal,
transactionally distinct purpose/quota from foundation. Server row key
(server,principal,invocation) stores immutable full submit digest/context/argv/
stdin, admission state, engine-known state, input generation/progress, terminal
result and native publication references. Client row stores the same invocation/
digest/destination plus outstanding requests and output cursors; commit client
row and outgoing submit intent atomically **before** publishing. Secrets never
enter status/log artifacts.

Server states are `accepted` (canonical request/digest durably reserved, no claim
of OS execution), `dispatching` (engine operation may have occurred), then engine
accepted/launching/running/terminal or explicit uncertain state. First compare any
existing complete digest/binding; conflicting retry fails without engine call.
A new row passes role/policy/freshness/capacity and commits before any internal
token or engine side effect. Accepted does not mean launched. If the service
crashes after that commit, recovery continues the same row.

Engine thread first queries status under the exact recorded owner. For a found job, return existing and never issue a new token/submit. Digest
matching is a service invariant, not a claim that InvocationStatus exposes a
digest: the unique engine owner key could only be submitted after the matching
immutable service row reached dispatching. Only engine_known=false with
authoritative NotFound permits an internal fresh token
and submit of the immutable request. An error/timeout is **not** NotFound. Persist
dispatching before issuing token; no new request may change its digest. Explicit
engine token_lifetime=120s (default is60s), internal only. Restart changes engine
epoch; recovery status-first avoids fresh-token mismatch on existing jobs. If a
worker launched before response projection, engine status recovers it; do not
retry submit with a new token. Legacy engine accepted→launching→running→exited,
unknown_launch/lost semantics remain; neither uncertainty is automatically rerun.
No universal exactly-once OS-execution claim.

Server projection ACKs native pending command only after durable ledger admission
or a durable definitive rejection decision. Engine completion is asynchronous.
Responses describe derived state and may be recomputed for a fresh authenticated
request without reexecuting. Exact outgoing native event retries remain bound to
retained MDK bytes; do not overwrite unresolved native work or create an unbounded
fanout per repeated request. Journal outgoing rows carry purpose=command and native
bindings, with one current response obligation per request. Identical duplicates
coalesce; bounded response queue full defers pending work without ACK. Busy and
transport/storage failures are transient, not cached permanent command outcomes.

Use a command-specific persisted monotone reject-before floor, fixed7day retry
horizon initially, independent of payload TTL and foundation floor. New command
invocation/session and new request IDs below floor are permanently expired.
Allow5minute future skew; defer/unACK inputs farther ahead but within
max(now,floor)+7days, terminally reject more excessive future. Local clock behind
floor forbids generating/admitting new work until corrected. Existing invocation
binding/digest comparison precedes freshness; existing active jobs remain
queryable/cancellable using a fresh request ID even if invocation is old. Old
request IDs cannot become new effects after GC. Existing accepted old sessions
remain usable; only new session admission is freshness checked.

GC requires payload TTL expiry **and** immutable invocation timestamp below
command floor **and** terminal job/input state **and** no native fanout/queued or
response obligation; delete child source/request bindings transactionally. Never
collect accepted/dispatching/running/unknown/lost ambiguity solely for age.
Engine tombstone retention is explicitly48h minimum and must be no longer than
the7day command horizon. Use a single-engine-thread **recovery barrier**, with
no engine schema/API extension. Distinguish the one **current serialized
admission operation** from all other unresolved dispatches. Before selecting it,
reconcile every other dispatching row with unknown engine outcome; until then
run no maintenance-capable operation (issue_execute_token, submit or maintain).
Status/poll/cancel and native convergence may continue. A failed/timed-out status
never means NotFound. A found job is durably recorded engine_known=true with
observed state before another maintenance-capable operation.

For the selected row only, engine_known=false plus authoritative NotFound under
the exclusive engine owner permits token+submit. Persist its dispatching state
before token issuance. That **single current** operation may issue its token and
submit despite its own dispatching marker: same-target absence was just proven,
all OTHER dispatches were reconciled, and no other engine admission/maintenance
may interleave. The selected issue/submit may run their own pre-admission quota
maintenance safely because there is no existing target job to collect. After
submit returns success **or error**, query status and commit engine_known/outcome
before any next maintenance-capable operation. WorkerUnavailable or
RecoveryUncertain can follow durable admission and never proves no job. If the
outcome/status remains ambiguous, keep the current marker and block **all new**
maintenance-capable operations until status reconciles; observer timeout does not
release this barrier or create a second operation. Recovery after a process crash
uses the same rule, first resolving all historical dispatches before selecting
one proven-absent target for a new attempt.

Actual Engine::open_storage→Store::create_frontend validates/opens storage,
updates configuration, revokes unused tokens/input generations and reconciles
up to128pending workers. That inspected startup path does not call maintain or
delete terminal tombstones; it can therefore precede ledger dispatch recovery.
This is a source contract to regression-test, not an assumption that all engine
methods lack maintenance side effects.
Once engine_known=true was committed, a later NotFound means collected: expose
result_expired/recovery_uncertain as appropriate, never resubmit. Such ledger rows
retain their digest until safe GC even if engine history is collected. A crash
after admission but before ledger outcome leaves dispatching and the barrier
reestablishes before any implicit quota maintenance. A definite policy/admission
refusal with confirmed NotFound becomes a durable refused row; no automatic
retry of refused admission under a changed policy. Captured old invocation IDs
stay below durable floor after tombstone collection, even if freshly reencrypted.
Active jobs beyond7days retain digest/status until terminal and protected work
resolved; their operation queries use fresh IDs. Deliberate re-use of the same ID
with fresh timestamps is impossible because timestamp is part of the ID.

## Immutable stdin and engine-thread scheduling

A dedicated OS thread owns Engine and a bounded64-operation queue; no Engine
method runs on or is awaited by the MDK convergence loop. Native actor submits
bounded work and polls completion messages. Each operation has a durable local
operation ID; at most one engine operation per invocation is in flight. Queue
admission has a1s deadline, calls a15s observer deadline, initial engine open30s.
Timeout returns pending/uncertain and leaves the in-flight operation registered;
it never kills the thread or authorizes a second execution. Engine fsync/SQLite
busy waits and up-to8s worker await are not magically cancellable. A permanently
stuck engine degrades commands; MDK/status about that degradation continue. Process
shutdown deadline reports engine-stop incomplete rather than detaching an unsafe
second owner. Detached workers continue independently.

After successful admission, local feeder uses one engine generation and one
record containing the complete immutable stdin (0..16384bytes), within the
engine RAW_BYTES limit, not4096-byte network chunks. Persist generation and
intended record offset/hash before engine write; reconcile accepted/delivered/
health after each call and restart. Never call begin_input on ordinary reconnect
or blindly repeat ambiguous OS writes. Crash between begin_input and saving its
generation recovers from engine status only while the same engine frontend
remains open; do not rotate it. Actual Engine reopen revokes active input
generations, clears records and resets accepted/delivered counts. If the durable
feeder had begun but not completed EOF before engine reopen, treat that input as
revoked/Gap/uncertain and cancel rather than recreate a generation or replay
stdin. Already committed EOF is irreversible and remains recorded. Only a ledger
feeder that is definitely never begun may initialize input after reopening. A definitely
unsubmitted record uses fresh_ms=60000 locally. Once accepted, expiry may not be
refreshed by resending; engine retry/health semantics remain authoritative.

**Only queue EOF when delivered==complete stdin length and health is not Gap or
Uncertain.** Accepted means queued, not delivered. Empty stdin queues EOF at0
once generation is known. If Gap or Uncertain arises before EOF, request cancel
and report input_failed; do not feed EOF that could make an interpreter execute
a truncated program as a complete EOF-delimited input. This does not make
stdin execution atomic: a line-oriented interpreter can act on a partial prefix
before cancellation. No side-effect rollback is promised. If the command has already exited naturally, without our
cancellation, with unconsumed stdin (for example true/head), preserve its actual
exit code and report stdin_unconsumed rather than fabricate an input failure.
If cancellation raced with exit and natural termination cannot be proven, report
the engine cancellation/input failure honestly, not an invented natural outcome.
There is an unavoidable exit-check/write race: EPIPE can create Gap immediately
before an otherwise successful child exit is observed, and the resulting cancel
may make natural termination unprovable. Thus true/head with supplied stdin can
occasionally report input_failed (CLI255) despite a child code0. Test and report
that race honestly; --stdin-none avoids supplying unwanted bytes, not all
possible process races.
There is no extra120s stall timer: the engine60s record freshness/health already
bounds pending-record delivery. Feeder credit checks and bounded local operations
continue without a connected client, interleaved with other jobs/status.

This is not an atomic submit-with-stdin engine API: the process can run before
feeding finishes, and crash after OS write may leave uncertainty. Complete
canonical request storage precedes launch, but input completion must never be
claimed from that alone. Tests cover that exact distinction.

## Limits, policy and output retention

Defaults:32 active jobs,4 starting workers,10000 retained invocation records,
1024 internal outstanding tokens,8MiB output per stream,512MiB aggregate spool,
1day configurable payload/output TTL,48h minimum terminal tombstones
(validated<=7days). Complete argv/stdin payload for accepted or unresolved
admission/input is protected until feeding/reconciliation completes; TTL cannot
turn a durable immutable request into a partial launch. These are separate from foundation512/4096 quotas. All command row, room and
outbox queries explicitly filter purpose; neither purpose consumes the other
ledger's capacity. Shared transport/process resource caps are still global. Add service-ledger quotas, independently of engine global quotas: max4active
accepted/dispatching/nonterminal-or-uncertain rows per principal and32global;
max1024retained invocation rows per principal and10000global. Reserve these in
the same transaction as immutable admission. Count engine_known jobs whose
terminal status is not yet durably reconciled as active. A terminal result may
release active credit, never retained-row credit before safe GC. Defaults may be
configured downward/upward within reviewed finite bounds, but per-principal caps
must remain<=global. At the fixed7day replay horizon,1024retained rows limits a
continuously busy peer to about146commands/day and10000global to about1429/day
when no longer-lived jobs/native obligations retain credit. This is a deliberate
noninteractive initial limit, not a shell/bulk-service scalability claim. A peer
reaching its share receives quota_exceeded without locking all other shares.
Do not derive counts from volatile engine snapshots: reconcile durable ledger
state on startup before new admission. Schedule pending
requests round-robin per room/principal with64attempts/turn and blocked attempts
counted. Exhaustion returns recoverable busy/quota without dropping pending work;
per-principal admission accounting is not process/resource isolation. Run permitted maintenance before projection only after the recovery barrier
clears; drive retained native work even if one room is full, and test malicious capacity churn.

Defaults and every matching key restriction accumulate: allow lists intersect
across layers, denies union, absent allow no constraint, empty allow denies all.
Repeated key entries add restrictions, never override or last-entry-wins. Match
argv0 only; `*` excludes `/`, `**` includes it, existing escapes/fuel bounds;
128key entries/256patterns/1024bytes per pattern. Implicit effective `/**` baseline
does not weaken these layers. Shell always denied. Interpreter grants can execute
arbitrary code; make that explicit. No IP/hostname ACL exists for Marmot peers.

Spool cap/expiry yields explicit gaps; output beyond8MiB cannot claim complete
success under defaults. Continue draining OS pipes and account missing ranges
rather than blocking disconnected commands indefinitely. Local TTL never promises
relay deletion. Keep metadata/native frozen obligations independently; running
process ownership and command replay protection do not expire with chat payloads.

## Local IPC and CLI

Extend current same-UID0700-socket IPC with closed typed methods command_submit,
command_status, command_poll, command_cancel. No remote peer-auth override.
Frame<=64KiB; method request/response deadline15s; submit returns durable handle
