Beads `marmish-4a3.1` tracks this diagnostic increment. It follows the
[0.3.1 release plan](v0.3.1-release.md), without changing process ownership,
signal ordering, cleanup deadlines, retry policy or accepted terminal states.

## Diagnostic boundary

Split the combined rejection into group-first and status-second stages,
preserving the original short-circuit order and error. A pure validator uses
the existing BSD information read. Debug macOS failures may append only a
leader/other label, a group-zero boolean, an in-exit boolean and unsigned BSD
status. No process identifiers, paths, user identifiers or command data enter
these records. Existing context and the single failure emitter are retained.
Release builds omit the detail and emission.

The in-exit flag uses the documented `PROC_FLAG_INEXIT` value, 4. The selected
runner SDK must confirm that value with a C static assertion before targeted
tests. This verifies a header contract, not historical kernel state. A flag or
zombie status never substitutes for group or identity checks.

Pure tests cover unchanged success/error behavior, rejection precedence,
closed metadata and formatting bounds. Tests touching debug-only detail have
explicit debug cfg guards so release all-target compilation remains valid.
The hosted run is the first actual Darwin compilation in this increment.

## Targeted observation

An optional boolean input, default false, extends the existing immutable-source,
nonroot ARM64 macOS regression workflow. After the original structural compile,
it checks the SDK and runs the exact failing installed-feature test up to 100
times. Each invocation must report exactly one test, one pass, no failures and
no ignored tests. Stop on the first failure and retain the actual partial count.
There are no automatic retries or tolerated failures.

The original combined suites, four existing tests repeated 20 times each and
strict release Clippy remain required. Optional debug installed-feature Clippy
also checks the new Darwin-only detail before a candidate is attempted. The
45-minute ceiling, pinned actions, permissions and concurrency are unchanged.
Report compile, SDK, runtime and lint outcomes separately. Passing observations
leave the historical cause unknown; a failing observation should identify the
rejected condition before any corrective policy is designed.

binaries. Any policy change needs its own source-grounded design and tests.

workflow nor a rerun can relabel the failed candidate as qualified. Version
