# Phase-1 amendment: bounded replay and recoverable capacity

Status: independently approved by Claude after four design-review rounds; see
[the actual approval](../reviews/v0.2-retention-design-r4.md). Implementation and
independent code review remain required. Beads: `marmish-7nw.2`. This addresses N2 in
[the integrated code review](../reviews/v0.2-native-code-r3.md).
Fresh disk and foundation-message formats are allowed; no migration is required.

## Problem and boundary

Payload expiry currently leaves permanent tombstones counted against every
journal capacity. Filling one table stops the whole pending-event loop and
prevents retained native publications from progressing. Simply deleting rows
is unsafe: a peer can encrypt an old application ID inside a new MLS message.
Native transport replay protection does not provide application-ID deduplication.

This amendment covers the non-executable foundation protocol only. It does not
permit forgetting an admitted command or promising successful execution outside
a future command protocol's separately reviewed retry window.

## Timestamp-bound identifiers and durable floor

Foundation message and session IDs remain 32 lowercase hexadecimal characters:
12 characters encode original Unix seconds and 20 contain random bits. Receipt
IDs use the original message's timestamp prefix and a deterministic digest suffix
bound to its complete receipt identity. An expired ID cannot be made fresh by
changing an outer event timestamp. Existing accepted rooms remain usable after
their original session ID ages; temporal checks apply to new room admission.
Use the unreleased `marmish-foundation/2` discriminator to distinguish the new
temporal semantics from the previous foundation test protocol.

The prefix is zero-padded big-endian lowercase hexadecimal seconds; malformed
encodings are rejected. The journal persists a monotone replay floor. On open and before pending
projection it advances transactionally to the greater of its previous value and
local Unix time minus a fixed seven-day retry horizon. A future configuration
change or clock rollback cannot lower the floor. Validate new send/receive IDs
and new session admissions against that floor and a five-minute future allowance.
An unseen ID below the floor is expired and never produces a new successful message or
receipt, even if a peer re-encrypts it or the journal is reopened. A large clock
advance can expire work permanently; a later rollback fails closed instead of
resurrecting it. IDs exactly at the floor remain within the supported window.
If an ID already has a journal row, verify the complete binding and return its
existing result; this cannot restore expired content or create another receipt.
IDs beyond the five-minute future allowance are deferred unacknowledged, count
as attempts, and retry when local time catches up. Only values beyond
`max(now, replay_floor) + seven days` may be terminally refused as excessive
future dates. Apply this rule to both messages and new-session admissions.
If local time falls below the durable floor,
expose `clock_behind_floor` for new sends and admissions while continuing ingest
and existing native obligations. Never clamp a new ID up to the floor. Recovery
requires the clock to catch up or explicit profile recreation.

Payload retention remains independently configurable with its one-day default.
An expired payload cannot be restored while its deduplication metadata remains.
Garbage collection requires both payload expiry and an ID below the durable floor;
longer payload retention can therefore retain rows longer than seven days.

## Collection and native obligations

Advance the floor and collect eligible journal records transactionally before
draining native pending events. Remove related source/binding rows consistently.
Native in-flight publication/queued obligations cannot be discarded to make space.
Use these exact predicates:

- An `unsubmitted` ID below the floor becomes `expired` and is never submitted,
  including receipts left over from long downtime.
- Protect an outgoing row in any state while its app-event ID appears in native
  `outbound_fanouts_for_group`, or one of its bindings appears in native
  `list_queued_outbound_intents`. If exact correlation cannot be established,
  conservatively protect the whole group's outgoing metadata.
  Expose a fixed-category diagnostic when native obligations protect expired
  rows; indefinitely unresolved native work can keep that capacity occupied.
- A `prepared` row with neither native obligation becomes `uncertain`, as on
  restart. Uncertainty never authorizes fresh ciphertext or a success result.
- With no protected obligation, `uncertain`, `published`, `received`,
  `invalidated` and `expired` rows are collectable only below the floor and after
  payload TTL expiry.
- Delete `incoming_sources` with their parent `incoming` row; `outgoing_sources`
  and eligible `queued_bindings` with their parent `outgoing` row; and `trust`
  with its retired `conversations` row, each in the same transaction.
- Keep outstanding native Welcome deliveries for live rooms. Phase 1 does not
  automatically retire a locally created room whose peer never joins: it keeps
  its live slot. Explicit retirement belongs to the command/session phase.
- Late invalidations with no remaining collected row are applied as no-ops;
  history older than the retained horizon no longer reflects those invalidations.

Remove the per-message `rejected` table, which no decision path currently reads.
Content rejection is deterministic and native storage deduplicates processed
native IDs, so undecodable content needs no per-message application tombstone.
Group-admission rejection remains a separate durable decision.
For a previously unaccepted room, deterministic policy rejections (untrusted
peer, purpose/membership/admin mismatch, missing author or invalid session) are
forgotten and acknowledged without allocating a rejection row or moving any
frontier. Policy is checked before capacity. Only an allowed peer passing all
room policy may allocate a capacity-refusal record or advance the overflow
frontier. Re-evaluating an initially invalid room must still apply all policy and
freshness checks. Previously accepted/revoked rooms retain their durable authority
and rejection history until the retirement collection predicates are satisfied;
they do not use the initial-policy-rejection shortcut.

Rejected/revoked room metadata records a validated session timestamp where
available, local rejection time, and native-forget/pending-ack completion.
Collection additionally requires the greater of the session timestamp and
rejection time plus five minutes to be below the floor, and payload TTL elapsed.
Forget native state using the public API, then re-list pending application events
and prove the group has none. Forget clears those events, so a subsequent explicit
acknowledgment is idempotent. Only that completion proof permits recording cleanup
complete; a journal boolean written without the proof cannot authorize collection.
Old session IDs remain intrinsically inadmissible after collection. Invalid room
identifiers remain invalid without needing an eternal rejection row. Count live
rooms against the 64-room limit, rather than all previously revoked rooms.
Any remaining metadata cap must reject new room admission finitely without
blocking existing rooms. At rejection-table overflow, atomically advance a
separate monotone `admission_reject_through` timestamp through the refused
temporally eligible session timestamp, then forget the group. Every new
admission checks this frontier; existing rooms and message freshness do not.
This conservatively rejects other new rooms at or below that timestamp but
preserves rejection without an extra row. Future-deferred or excessive-future
IDs cannot advance the frontier. Own session generation never clamps above it;
report finite `admission_backpressure` until wall time advances. Preserve any
previous accepted-room cleanup state until native completion is proven.
Upstream retains its own processed transport IDs until
group deletion and reset cutoffs afterward; application collection is not a claim
that the entire upstream database has a fixed lifetime size.

## Backpressure and progress

Capacity remains a bounded working-set limit, not a lifetime quota. Keep the
global 4096-row limits and add a 512-row limit per conversation for incoming and
outgoing, with proportional source/binding caps. One full room cannot consume
the entire account's journal; eight flooding rooms can still fill the shared
global cap. At seven days, the global ceiling is roughly 290
two-way exchanges per day, lower with longer payload retention; per-room limits
are lower still. This bounded phase-1 foundation is unsuitable for interactive
traffic. Command/stream capacity needs its own phase-2 design. A full table
can refuse new work within the retry horizon; it must recover when eligible rows
expire. Persist and acknowledge only successful projections or durable terminal
rejections. Admission or room-metadata capacity produces a definitive per-room
rejection followed by forget and acknowledgment, never a blocked join. Other
storage/operational faults leave a join undecided. A message whose group has an
unresolved pending join stays unacknowledged;
never reject it merely because processing has passed an undecided join.
On open and after local group-creation failures, reconcile the union of native
`live_group_ids`, `unhydrated_group_ids`, `quarantined_groups` and
`outbound_fanout_group_ids`
against accepted/rejected journal decisions and pending joins. A native group
with neither a decision nor a pending join is an orphan: record definitive
rejection, forget native state (including its outstanding Welcome), and re-list
pending events to prove cleanup. Never wait forever for a join that cannot
arrive. This covers crashes between native creation and journal acceptance.
Temporary message capacity failure leaves the individual native event
unacknowledged, continues processing other eligible events, and still drives
retained publications and previously admitted outgoing work. Project incoming
data and prepare its receipt in one journal transaction with a capacity precheck
covering both tables; acknowledge the native source only after commit. Receipt
IDs never depend on native message IDs: their suffix is a domain-separated digest
over group, session, original sender, recipient, original application ID and
payload SHA256, with the original ID timestamp prefix. Re-encrypting the same
application message must produce exactly one receipt intent.

Replace the fatal pending-vector-length check with at most 64 attempted pending
events per turn. Use an in-memory round-robin cursor over stable keys
`(kind, via_welcome | message_id)`, wrapping after the last key. Freeze the key
cohort for each sweep; newly arriving keys enter the following sweep. Select the
next at most 64 keys and advance the cursor, then process selected joins before
selected messages. Blocked or already removed entries count as attempts, so a
finite cohort of N entries is attempted within ceiling(N/64) turns;
dependency-blocked messages are deferred as above. Newly arriving keys cannot
reset progress through the current cohort. This key snapshot has the same
unbounded-count upstream limitation as the pending vector. Share the attempt
budget across nested effects handlers in one public owner operation/turn;
reset it only at that outer boundary. Always attempt
retained-publication driving and unsubmitted-work driving
after the batch despite individual capacity failures; operational errors remain
distinct. Document upstream's unavoidable full-vector allocation separately.

The durable floor itself permits acknowledging intrinsically expired events;
do not allocate another per-event rejection tombstone for each stale replay.
Upstream forgetting alone is insufficient: later Welcome carriers and device-link
exceptions exist, so new admission must always validate session freshness.

## Acceptance

Test expiry followed by successful new admission beyond the former lifetime cap;
timestamp-bound replay rejection after collection, restart and clock rollback;
configurable payload retention without premature content deletion; partial and
ambiguous native publication boundaries; expired messages producing no fresh
receipt; live-room capacity after revoked-room retirement; and one full queue
leaving unrelated pending events and retained publications able to progress.
Include blocked-join ordering, the round-robin bound, one room flooding without
blocking another, duplicate re-encryption yielding one receipt, stale unsubmitted
work never sent, late invalidation, and clock-behind-floor behavior. After retired
metadata collection, an old-session Welcome for the same group stays rejected,
while an independently authenticated fresh session starts cleanly without old
rows or authority bindings.
Also test slow-local-clock/future deferral during `clock_behind_floor`, rejected
room metadata overflow and admission frontier persistence, and failure/crash
between native create and journal acceptance with orphan reconciliation.
Flooding unsolicited or otherwise policy-invalid Welcomes must leave capacity
rejection row counts and the admission frontier unchanged.
Use production MDK APIs and disposable SQLCipher journals, without test-support
features or writes to upstream tables. Then repeat offline checks, affected live
flows and independent integrated code review before publication.
