# Native installed default-auto provider qualification

Status: approved for implementation; Beads `marmish-7nw.4`. Actual independent
[Claude design review r2](../reviews/v0.2-native-keychain-design-r2.md) approved
the design body; parent implementation authorization is recorded in the phase handoff.
This adds a separate three-platform installed-provider gate. The existing File
PTY quickstart and public Marmot command matrix remain independent gates.
No Python/Node runtime dependency or product provider override is introduced.

## Actual boundaries

`identity::helper_exchange` starts the installed executable's `_vault-helper`
with a cleared environment, forwarding only HOME, DBUS_SESSION_BUS_ADDRESS and
XDG_RUNTIME_DIR. `Vault::open_namespaced(MarmishV2)` opens a real session Secret
Service on Linux or `SecKeychain::default()` on macOS. Auto selects Files only
on the finite `unavailable` category; locked/denied/uninitialized/error must fail.
The existing macOS disposable vault test selects an explicit keychain, so it
cannot establish default-auto frontend behavior. Ready `setup` is a local
manifest-only shortcut; an actual fresh installed `init` process is needed to
prove keys reload through the provider. No new raw-secret helper operation is
needed. The separate Nostr and SQLCipher references already exist in profile
format 2; engine material derives from the latter without another stored key.

## Owned real-provider contexts

Add `provider-qualification` to `.github/workflows/v02-release.yml`, needing
render, using CI supervisor `tools/marmish_native_keychain_check.py` and the exact source,
run, attempt, target assets and pinned bootstrap. A CI-only stdlib supervisor
owns subprocess handles, finite deadlines and sanitized output. Product children
use a utility-only PATH and explicit private profile/temp paths; test tooling is
not copied into the installation.

Linux AMD64/ARM64: install only missing dbus-daemon, gnome-keyring and util-linux
packages, recording bounded dpkg-query versions (no ambient environment). Require
/usr/bin/dbus-daemon and /usr/bin/gnome-keyring-daemon. Start dbus-daemon directly
with --nofork --config-file OWNED --print-address=FD, with no activation
directories, plus a private GNOME Keyring under an owned 0700 HOME/XDG tree.
Initialize/unlock only this service using a public disposable fixture password
on stdin. Save and supervise exact D-Bus/keyring child handles, never discover
processes by name or connect to the ambient desktop bus. Before product calls,
validate a single unix:path= address with no semicolon, an owned private socket
and directories, and XDG_RUNTIME_DIR inside the owned tree (never ambient
/run/user/UID/bus). A second private bus
with no Secret Service verifies genuinely absent-provider fallback separately.

macOS ARM64: create an exclusively owned, disabled-login local test account
using passwordless CI sudo, an unused verified UID and short private home. Refuse
any preexisting name/UID; record the created directory identity before mutation.
Use a privileged outer supervisor only for account creation/staging, launchctl
bootout and verified account removal. Start one inner supervisor with
`sudo -n launchctl asuser UID sudo -n -H -u ACCOUNT /usr/bin/env -i HOME=HOME
PATH=/usr/bin:/bin PYTHON -I SUPERVISOR`. It owns product PTYs, child process
groups, deadlines and security commands as the same UID. Copy bootstrap, assets
and supervisor into that account's staging directory and recheck every input
digest after copying. Snapshot the runner's default-keychain and list-keychains
outputs privately before creation and after cleanup; equality is mandatory and
only runner_keychain_unchanged is published. All installation/provider commands
run as that unprivileged account in the same asuser context. Create and
unlock its dedicated keychain, select it as that account's default, and inspect
its default path before the frontend runs. Disable only this owned keychain's
automatic timeout/sleep lock with security set-keychain-settings (no -l/-u).
A public disposable test-only password
may appear in security CLI arguments; no generated Nostr/SQLCipher secret ever
appears in arguments, environment, logs or artifacts. Never change the runner
account's default keychain/search list or access its items. Do not add a product
keychain-selection environment variable. If an owned account's Security context
cannot operate headlessly, the gate fails with a finite prerequisite category;
it is not replaced by File or explicit-keychain evidence. CI privilege here is
for provider isolation only, not a Marmish runtime requirement.

## Assertions and bounds

1. Run the real bootstrap `--quickstart` under a PTY with NO key-storage flag:
   default both, explicit `wss://relay.invalid/`, Tor off, no inbound/trust keys.
   Require backend keychain, identity/owner creation and actual joined stop.
2. Inspect only bounded public profile metadata and the native helper List
   metadata: distinct Nostr/SQLCipher refs, exactly the expected v2 items, no
   plaintext File-provider secret artifacts. Do not request raw helper Load.
3. Start a fresh installed `init` process for that same identity, require same
   public identity and clean stop. Create a second named identity via installed
   setup; require a distinct public identity and four distinct native entries.
   Reopen both names in new processes and require exact public identities.
4. Lock only the owned provider. On Linux, stop/reap the exact keyring child
   and restart against the same bus/HOME/XDG_DATA_HOME without --unlock and with
   null stdin; require native probe locked_or_denied. Unlock by stop/reap and
   restart --foreground --components=secrets --control-directory OWNED --unlock
   with fixture password on stdin; require probe ok. Do not require a D-Bus
   Unlock prompt or prompter. On macOS use security lock-keychain/unlock-keychain
   in the inner owned account context. Fresh `init` for an existing name and creation
   of a new name must fail finitely without Files fallback or new native items.
   Unlock the same owned provider and recover both original identities. Only
   successful fresh-process reload counts; macOS denial after unlock is finite
   acl_denied_after_unlock failure, never an acceptable restart result.
5. Linux's separate absent-service bus must choose Files, asserting
   backend=file plus identity_created and keys/ on a fresh profile; an existing
   keychain profile must refuse absent
   service without mutation. macOS has no provider Unavailable mapping: this gate proves real available and
   locked states, not a synthetic Linux-style absence case. It does not claim a
   missing-default-keychain runtime test or alter the default to a nonexistent
   path (the native setter need not accept nonexistent keychains).
6. Every child operation has a <=120s observation deadline; provider operations
   <=15s; private-service/account setup <=60s; total qualification <=600s.
   Timeout stops only children/process groups created by this supervisor,
   reaps them, and marks cleanup incomplete if safe ownership cannot be proven.
   No Marmot network or command jobs activate in this gate.

Exact installed commands after initial PTY quickstart:
`marmish --state-dir S -i second --relay wss://relay.invalid/ setup --role both --no-grants`;
`marmish --state-dir S -i default init` and `-i second init` for fresh reloads.
Without mutation means unchanged profile.json/config.json bytes and absence of
keys/ for keychain profiles; creating a profile directory or lease file is allowed.

## Cleanup and evidence

First require all frontend owners' actual joined stop. Stop/reap exact owned
Linux service processes before deleting their tree. On macOS delete only the
created keychain, stop the created user's launchd context, verify no owned child
remains, delete only the verified created account and private home. Never use
name-based global kill. If any prerequisite, join or deletion is uncertain,
report failure and preserve private state; do not claim successful cleanup.
Ephemeral runner teardown is a separate final protection, not measured cleanup.

Upload only bounded finite JSON: source/run/attempt/target, case booleans,
backend categories, elapsed times, item counts, and actual cleanup predicates.
No public npubs, reference IDs, endpoints, credentials, private paths, provider
messages, terminal transcripts or databases. Static checks are not provider
runtime evidence. Qualification requires actual success on all three targets,
independent Claude auto code review, and review of resulting finite evidence.
