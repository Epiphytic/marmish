# SQLCipher concurrent startup correction

Status: DESIGN AND CODE APPROVED: [design r3](../reviews/v0.2-sqlcipher-startup-design-r3.md), [code r1](../reviews/v0.2-sqlcipher-startup-code-r1.md), [test follow-up r2](../reviews/v0.2-sqlcipher-startup-code-r2.md). [Local validation](../validation/v0.2/sqlcipher-startup.md) passed; fresh hosted three-platform qualification remains pending. Scope: Beads `marmish-i7y`; no encryption-format change.

Candidate run 41620775751 failed three parallel engine integration tests with `sqlcipherCodecAttach: sqlcipher not initialized 1`. Eleven other tests in that process passed. This is an actual startup failure, not a reason to serialize the suite.

## Pinned dependency contract and cause

Cargo pins libsqlite3-sys to rusqlite git revision `5ae7fdf83085c595fd54f977b3a56ccacabaf16b`. Its build.rs defines `SQLITE_EXTRA_INIT=sqlcipher_extra_init`. The bundled SQLCipher sqlite3_initialize publishes SQLite isInit and releases its recursive initialization mutex before invoking SQLITE_EXTRA_INIT. Another thread may consequently open/key a connection before SQLCipher initializes its provider/private heap. sqlcipherCodecAttach then reports the observed initial error value 1. SQLite also provides SQLITE_EXTRA_INIT_MUTEXED, called under the recursive initialization mutex before isInit is published. The initial proposal to move this hook was independently rejected because its mutex allocation would deadlock; the correction below retains the original hooks.

## Correction

The initial mutexed-hook proposal was rejected by actual independent review: SQLCipher requires the old macro and its FAST-mutex allocation recursively acquires the nonrecursive static main mutex before SQLite's inProgress guard. Do not change compiler hooks; see [r1](../reviews/v0.2-sqlcipher-startup-design-r1.md).

Expose `marmish_engine::initialize_storage() -> Result<()>`, implemented with one process-wide OnceLock<i32> around unsafe rusqlite::ffi::sqlite3_initialize(). Return success only on SQLITE_OK; cache any failure and return EngineError::StorageFailure thereafter. sqlite3_initialize returns after its EXTRA_INIT hook completes. All application callers cross this barrier BEFORE any SQLite API; concurrent callers wait for the first call and only then open independent connections. No SQLite shutdown/reset, engine-only per-connection mutex, storage retry, compiler override, new crate or dependency is introduced. Connection NO_MUTEX ownership and encryption checks remain unchanged. Engine is already a dependency of native, so this single function is shared by all native openers and dedicated worker processes without adding SQLite to the pure core crate.

The production boundary audit is exhaustive for repository `Connection::open*`, sqlite3_open, and SqliteAccountStorage::open* occurrences:

- engine cipher::open: initialize before Connection::open_with_flags (covers state and spool, Engine::open and worker_main).
- native Journal::open: initialize before Connection::open_with_flags.
- native native_preflight::open: initialize before Connection::open_with_flags (absent/empty filesystem-only cases can return earlier).
- native MdkOwner::open: initialize before the first upstream SqliteAccountStorage::open_encrypted; the retained second open is after the same barrier. This protects upstream internal migrations/connections as well.
- native RelayConnector::bootstrap_inner: initialize before TorClient construction on the needs_tor branch, covering tor-dirmgr directory-cache connections, including independent bootstrap tests.
- marmish-mdk contains no SQLite opener. Cargo.lock reverse-dependency inspection finds only engine, native, upstream storage-sqlite and tor-dirmgr depending on rusqlite; all use the same libsqlite3-sys. Recheck this complete reverse-dependency list when updating dependencies.

Map barrier failure at native boundaries to finite Storage("sqlcipher_init"). Cover raw test opens in engine cipher tests, encrypted_storage, faults and native_preflight tests before their first SQLite call. Spool raw tests already run after cipher::open but explicitly crossing the barrier is harmless. Audit every literal opener after implementation; no test setup may race an ungated first connection against gated production calls. The barrier MUST be the first SQLite initializer in the process: a later barrier cannot detect another thread still running the extra-init hook after isInit is published. All current database users in product processes, including upstream storage-sqlite and Arti tor-dirmgr, are controlled by these boundaries; downstream library users mixing unrelated direct SQLite calls must initialize through this public barrier before such use. This is a first-use synchronization guarantee, not an upstream SQLite replacement or arbitrary-third-party safety claim.

## Regression and verification

Add one engine integration regression in a separate test binary. Threads call the actual shared initialize_storage boundary before opening their connection. Timeout is an explicit deadlock failure. Linux and macOS are required; Windows is outside this release scope. Its parent starts fresh child test processes, each with 16 threads synchronized before their first SQLite call. Every thread opens a distinct encrypted database, passes its key as sqlite3_key data, writes/reads a value, closes/reopens with the same key, verifies ciphertext lacks the plaintext SQLite header, and verifies a wrong key cannot read sqlite_master. Child execution has a bounded parent timeout with kill/reap on failure. No SQLite shutdown/reset in a process with other users, and no sleeps intended to serialize threads. Run against the original build first to establish whether this actual fresh-process race reproduces; record honestly if probabilistic. Verify after the change, existing encrypted-storage tests, and the actual 14-test engine integration suite with normal parallelism. Existing negative key/context tests remain mandatory. Check strict engine Clippy and source/config diff. No C configuration changes or forced dependency rebuild are expected; report actual local compile cost, and require a fresh full three-platform candidate after review.
