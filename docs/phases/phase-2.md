# Phase 2: live Marmot transport and noninteractive integration

## Scope and sequence

Phase 2 connects the reviewed offline command engine to real Marmot transport. Its first independently reviewable increment, 2a, establishes the actual MDK room and message contract using two disposable identities. It does not execute commands, enroll real users, or implement a production transport. Beads issue `marmish-315.12` records this increment; `marmish-315.4` continues to represent the full release integration.

The user explicitly authorized bounded tests on selected public White Noise infrastructure. The later command-integration requirements below additionally call for real remote command execution between disposable server/client identities; that work requires its own detailed plan and Claude review before implementation and does not expand the synthetic 2a tool. Neither this authorization nor the tool supplies default relays. Production still requires enforcing the selected relay set and a payload-safe application-message interface. Existing inert Rust network plans stay inert throughout 2a. The earlier blanket prohibition on live probes was an overinterpretation, superseded by this design.

## Increment 2a implementation boundary

Add a Python 3 standard-library developer tool at `tools/mdk_smoke.py`, with offline safety/contract tests at `tools/test_mdk_smoke.py`. Keeping it outside the Rust transport makes the experimental path distinct from a release backend. It accepts explicit absolute `--wn` and `--wnd` executable paths, required expected SHA-256 values for each, and one or more required `--relay wss://HOST[:PORT]/` arguments. No executable discovery, identity import, arbitrary message input, arbitrary command input, or production-engine access is offered. Require an affirmative `--live` flag before any subprocess capable of networking starts.

Copy the explicitly supplied regular executable files into the 0700 private root, make the copies executable only by the owner, verify the required digests on those copies, and execute only the verified private copies. Never hash an original path and later execute that mutable path. Version/help observations establish the observed binary interface, not a reproducible source build. Record both digests and the CLI version; the known installed artifacts are `wn` 0.13.0 SHA-256 `c1f5a130549a142070b477303f1cf1e50153ab33b61815b5c7b4f681546747e5` and `wnd` SHA-256 `1324c70d389fb49f37ae8f7f6ab2a16840b138a0c438d7aef10bb6f9eee20a03`. `wnd` has no version flag. Committed source at MDK `37c248a11239e108afc9bd4ee62b8f60542012e3` is an inspected reference, not a claim that these binaries were built from it. Do not modify the shared dirty MDK checkout.

Use strict URL validation: WSS only for this increment; reject credentials, fragments, queries, non-root paths, commas, control characters, invalid ports, and malformed hosts. Canonicalize to lowercase DNS host, omit the default port 443 and include exactly one root slash, then deduplicate. Pass identical canonical URL strings to both daemons and compare their reported account relay lists using the same canonicalizer; both identities must advertise exactly the selected set. Explicit DNS SRV resolution is deferred until a service-name/port/TLS contract has been verified; do not invent one for the public servers. The selected test invocation will pass `wss://relay.eu.whitenoise.chat` and `wss://relay.us.whitenoise.chat` explicitly. Both resolved and returned NIP-11 documents on 2026-10-22. This is not proof of a successful Marmot exchange.

Create a new random private temporary root, with two independent homes, sockets, logs, HOME/XDG directories, and signing identities. Set umask 0077 before creating state; directories use 0700 and files 0600. No supplied state path is accepted. Child environment fixes `LANG=C` and `RUST_LOG=warn`, omits PATH and SSL_CERT_* overrides, and otherwise is an explicit small allowlist, with private HOME/XDG locations and file secret storage; do not inherit WN/account/socket, proxy, telemetry, credential, or user configuration variables. Pass explicit home, socket, secret-store, discovery relays, and default account relays to both daemons. No shell invocation. No key export; no private keys in arguments, logs, or reports.

Start each `wnd` directly as an owned foreground child in its own process group, rather than using detached `wn daemon start`. Check process liveness and private socket readiness before CLI calls. Every CLI call must specify `--socket`: inspected `crates/cli/src/lib.rs:743–805` permits an implicit socket connection failure to fall back to a local runtime, while an explicit socket disables this fallback. Each CLI call also gets explicit home/socket/file-store arguments and its own process group. Use a short root under `/tmp` to keep socket paths below the Unix socket limit. Install SIGINT/SIGTERM cleanup handlers; use `waitid(WNOWAIT)` for liveness rather than `Popen.poll()`, which reaps. Every operation has bounded stdout/stderr, a per-call deadline, and a global monotonic deadline (default 180 seconds, hard maximum 300). Maximum captured response is 1 MiB per stream; poll at most once every two seconds, with a bounded number of publications. Pass `--logs-dir` inside the private root. Continuously drain both daemon pipes into bounded discard sinks (1 MiB cap per stream); never wait for process exit to drain them. Watch each daemon log file and terminate its owned group if the file exceeds 1 MiB. Do not surface raw daemon logs in output or reports. Keep owned process leaders unreaped until process-group cleanup, to avoid PID reuse. On success, failure, or handled interruption: terminate owned groups, escalate to kill after a short grace period, reap, and remove private state. The tool is not a sandbox for a malicious executable or descendants deliberately escaping a process group. SIGKILL/power loss cannot promise cleanup.

Use `wn --home HOME --socket SOCKET --secret-store file --json [--account HEX]` and structured JSON responses from the actual CLI. Exact command spellings and fields are checked against source/help before implementation; unexpected schemas fail closed with stage/error summaries, not raw response dumps. Identity creation is once per home. Retry only read/sync operations; do not blindly repeat identity creation, group creation, invite acceptance, or sends after an ambiguous timeout.

The exchange sequence is:

1. Run `create-identity` once per home (`result.account_id`, `result.npub`, `local_signing`, `key_package` and relay-list status). Create one fresh signing identity per daemon, capturing public npub/hex only. Verify the two identities differ. Initial relay-list and KeyPackage publication must complete or be explicitly diagnosed. Assert each reported relay-list set equals the configured set. Gate group creation on Alice successfully reading Bob's published KeyPackage using `keys fetch BOB_HEX --bootstrap-relays CSV`.
2. Run `groups create NAME BOB_HEX --retention 1d` (`result.group_id`), then inspect `groups invites` (`result.invites`) and `groups accept GROUP` (`result.accepted`). Create one room from Alice inviting exactly Bob, with application retention explicitly set to one day. Poll Bob's own daemon for the matching invite and accept it. Require exactly one matching invite with `group_id` equal to Alice's result, `pending_confirmation == true`, and non-null `welcomer_account_id` equal to Alice's hex identity; otherwise fail without acceptance. Use a nonce-bearing unique room name. If group creation times out, a single read-only reconciliation may record evidence, but never retry creation. Do not accept unrelated invitations.
3. Inspect `groups members GROUP` on both sides (`member_id`, `npub`, `local`); require exactly the two generated principals. Read `groups retention GROUP` without `--set`, or inspect `message_retention` from the group result, and require exactly 86,400 seconds. Document the installed schema.
4. Send one fixed-format non-sensitive, uniquely tagged probe from Alice to Bob and one reply from Bob to Alice. Use `messages send-event GROUP 30100 FIXED_JSON` and receive with `messages list GROUP --kind 30100 --limit 20`. The inspected response contains `result.messages[]` with `message_id`, `group_id`, `from`, `plaintext`, `kind`, and `tags`. Require the send result to have `published` as a positive integer (explicitly excluding boolean values) and a nonempty bounded `message_ids` list, and require a received record's `message_id` to belong to that list. This covers application data; if the observed binary does not support this contract, report that the boundary is not proven rather than silently substituting plain chat. Only harness-generated synthetic content may appear in argv in this tool.
5. On each recipient, require the actual received message to match the group, `direction == received`, authenticated sender field, kind and exact payload from the opposite identity. A local send acknowledgement alone is not delivery. Record that sender authenticity is trusted through the selected MDK binary; the harness does not independently reimplement MLS verification and the CLI does not expose a separate authority field. Normalize `from` as hex or npub before comparison, and never trust or report `from_display_name`.
6. Produce a bounded JSON summary containing outcome, failed stage/error category if any, explicit relay URLs, binary digests/version, public identities, group/message identifiers, and assertions established. Never include secret-store data, raw diagnostics, arbitrary received plaintext, or entire daemon responses.

No public load test, relay scanning, arbitrary-peer contact, remote execution, multi-device enrollment, or deletion/retention guarantee is part of this increment. Room retention configuration is inspected; waiting a day or certifying cleanup is later work. Relay-list defaults do not prove all outbound connections stayed within the set; say so in every evidence report. Creating disposable identities publishes public relay-list and KeyPackage events which may remain after local cleanup; record that residue explicitly rather than promising deletion. These are user-authorized test identities communicating only with each other.

## Remaining phase 2 release design gates

Use the observed exchange to freeze a reviewed production contract before writing the next increment: supervised MDK lifecycle and persisted identities, authenticated sender and exact room membership checks, payload-safe stdin/IPC/library transport, explicit relay-set enforcement including peer-discovered routes, durable inbound/outbound cursors and replay behavior, and scheduled message sweeps. The engine's `authorize` method trusts frontend-supplied principals: it must never receive identity labels copied from unverified application content.

The CLI contract remains `marmish npub-or-alias@relay`, with `-i` selecting the local identity and `-u` the remote principal. Unix-user mapping is independent server policy. The next detailed design must freeze URL/host/multiple-relay parsing and explicit SRV semantics before implementing them; use explicit URLs in 2a rather than guessing DNS behavior. It must also cover command freshness handshakes, request digests, default-room reuse, allowlists, stdin/output credits, restart recovery, command/status/attach/cancel operations, retention scheduling and diagnostics. The reviewed engine supplies command persistence and disconnected execution; transport must preserve its safety contracts.

Full phase 2 acceptance continues to require real command execution across independently configured identities, enforced relay policy including an out-of-set decoy test, no sensitive argv payloads, no replay execution, stdout/stderr/EOF/status recovery, expiry behavior, and Claude review. Multi-device, interactive tmux, forwarding, X11, file transfer and privileged mapping remain later phases.

## Next command-integration increment: required design and acceptance

Beads issue `marmish-315.14` records these additional requirements. This section defines the next design boundary; it is not implementation or a claim that command transport already passes. Before implementation, write the detailed module/interface and test plan, obtain Claude's independent review, and resolve blocking findings. Existing strict relay enforcement and payload-safe application transport gates remain in force; the synthetic argv allowance in 2a must never carry command, stdin or output payloads in the release path.

Use fresh disposable server and client Nostr keys in isolated private homes, with no real identity import or existing user conversations. Start the actual Marmish server and client on the test machine and execute bounded canary commands through the real Marmot/MDK relay path. A fake adapter, local engine call, publication acknowledgement or echo-only message exchange does not satisfy this acceptance. Select relays explicitly, set command runtime/output/input/publication and overall deadlines, restrict test commands to the disposable test directory, and clean up owned processes and state. Record unavoidable public identity/KeyPackage residue without promising relay erasure.

Create dedicated Marmish application rooms and persist a versioned application-purpose binding to authenticated server/client identities, target account, session and actual MLS group identifier. Verify exact authorized membership before admitting commands and after relevant membership changes. A matching application kind or payload field alone is insufficient. General DMs, ordinary chat messages, unrelated invitations and historical bootstrap/chat records never execute commands. Status/resumption may reconcile previously accepted durable invocations; it must not turn arbitrary recovered history into new launch authority. The design must specify how an explicitly enrolled default Marmish room is reused without accepting an unrelated existing conversation.

For each new independent session, use supported MDK create-group and KeyPackage/invitation APIs to establish fresh independent MLS group/session key material. Verify and document the selected MDK revision's actual API support and guarantees: KeyPackage generation, advertised freshness, consumption/reuse policy, group creation and acceptance, authenticated group identity, membership and stored MLS-state restoration. Mark unsupported or unverified guarantees as blockers or explicit limitations; do not invent custom MLS keys or describe a random application session ID as fresh cryptographic state. A resumed session restores its persisted MLS group and durable application state; a newly requested independent session creates a distinct group. Bind session IDs to the authenticated group, enforce stream/frame sequence rules, invocation ID plus request digest deduplication, and server-issued freshness authorization. Fresh keys alone are not replay protection. MLS key rotation, group rekeying and reconnect never authorize rerunning an accepted command.

The acceptance matrix must exercise the following through the actual client/server transport:

- Separate known stdout and stderr canaries, a known nonzero exit code, queryable running/completed status and bounded byte-exact output recovery.
- Client disconnect while a bounded command continues, followed by reconnect/status/output retrieval. Repeated submission, ambiguous-send retry and restart recovery must preserve the invocation identity and produce one durable execution marker; conflicting reuse is rejected and uncertain launch outcomes are reported without automatic rerun.
- An independently generated unauthorized sender, unrelated/wrong-purpose room, mismatched group/session binding, stale freshness authorization and replayed/out-of-order frames fail closed without creating an execution marker. Include ordinary DM/chat/history as explicit negative cases.
- Argument-vector mode preserves spaces, Unicode, single/double quotes, embedded newline, leading dash, literal `$` expansions and backticks as exact arguments. Use bounded fixtures that prove shell syntax does not execute or create side effects. Separately test explicitly selected, server-permitted shell mode and demonstrate its intended interpretation; never infer shell mode from argument content.
- Byte-preserving stdin including NUL/non-UTF-8, ordered input/EOF, separate binary stdout/stderr and frames crossing chunk boundaries. Exercise configured input/output/frame limits and credits, cap/gap reporting and continued drain of excess output without deadlock or unbounded buffering.

Preserve exact reproducible commands, selected relay URLs, source revisions, executable digests/build provenance, protocol/MDK versions, public disposable identity/group/session/invocation IDs, relevant configuration and bounded sanitized outputs in a named evidence artifact under `docs/`. For every acceptance assertion record pass, fail or not run with the exact supporting artifact; a dependency failure is not a pass. Exclude private keys, key files, raw MDK databases, unsanitized logs and real user data. Keep test homes and generated secrets ignored and outside staged changes. Report actual end-to-end results separately from offline/fake tests and from the earlier synthetic 2a exchange. After completed-code Claude auto review and final checks, perform the secret/ignore audit, commit and push the reviewed increment, and record its real revision and push outcome without fabricating earlier phase history.

## Source contract correction after design review

Follow-up verification found that `SendSummary.published` is a `usize` in committed `crates/marmot-app/src/lib.rs:960`, copied directly to the CLI result in `crates/cli/src/commands/messages.rs:169`. The send-event check therefore requires a positive integer, not the boolean suggested during review. Identity setup's `key_package.published` is a separate boolean. The implementation and its schema tests must distinguish them. This is a source-backed schema correction, with no relaxation of recipient-delivery assertions.

Received message direction is the literal `received`, as set by committed `crates/marmot-app/src/client/sync.rs:4594` and copied verbatim by CLI message projection. The earlier review's `incoming` spelling was incorrect; tests and implementation must use the actual value and reject outgoing records.
