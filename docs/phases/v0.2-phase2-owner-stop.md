# Phase 2 owner stop and explicit fixture cleanup amendment

Status: approved by actual Claude Code review [round 2](../reviews/v0.2-owner-stop-design-r2.md), session `b1bf4210-2500-4410-8b4a-8671f313be34`. Approval binds the pre-status-update design SHA256 `bf50793897ad063309b88e72d6cce2664ef5f684975cf2e0b31287fc9b59bcdd`.
This supplements Phase 2 and its acceptance interfaces. It does not change the
command protocol, engine recovery model, or ordinary command lifetime.

## Ordinary stop preserves commands

Client detach, transport failure, daemon signal and uptime expiration do not
cancel admitted commands and do not invoke `Engine::into_cleanup`. Ordinary stop
closes admission for this actor, stops its existing engine thread, closes the
MDK/journal frontend, and releases the profile lease only after both have ended.
The existing `Control::Stop` drops the engine frontend; it does not send worker
cancellation. A subsequent owner recovers persisted commands through the existing
status-first/commit-ACK barrier. Do not equate engine-thread termination with
worker absence, or normal stop with authorization to delete engine state.

The current blocking `CommandEngine::shutdown(deadline)` remains the only engine
stop primitive. Add `self.collect()` in its full-control-queue retry arm before
sleeping; currently it drains events only after Stop is queued. Without this
narrow fix, a full event channel can block the engine thread while the caller
waits for control-channel space. The fixed method drains events while retrying
the bounded control queue and retains the same OS-thread handle when the
observer deadline expires. Its blocking join runs outside the Tokio actor.

## Concrete ownership interface

Introduce a small native lifecycle module, with these crate-private interfaces:

```rust
pub(crate) struct OwnedIdentity {
    pub owner: MdkOwner,
    pub profile: ProfileLease,
}

#[derive(Clone, Copy, Serialize)]
pub(crate) struct LifecycleStopReport {
    pub schema: u8, // 1
    pub engine_quiesced: bool,
    pub engine_stop_complete: bool,
    pub mdk_stop_complete: bool,
    pub runtime_cleanup_complete: bool,
}

#[must_use]
pub(crate) struct PendingStop { /* owns JoinHandle<LifecycleStopReport> */ }

pub(crate) struct StopObservation {
    pub report: LifecycleStopReport,
    pub pending: Option<PendingStop>,
}

pub(crate) async fn stop_owned(
    identity: OwnedIdentity,
    observer_deadline: tokio::time::Instant,
) -> StopObservation;

impl PendingStop {
    pub(crate) async fn observe(
        self,
        observer_deadline: tokio::time::Instant,
    ) -> StopObservation;
    pub(crate) async fn finish(self) -> LifecycleStopReport;
}
```

`OwnedIdentity` deliberately declares owner before profile: Rust drops fields in
declaration order. An implicit drop is a degraded failure path, never a clean
stop or deletion authorization; this order closes MDK/journal before unlocking
the profile but does not substitute for joining the engine. All normal and
handled-error paths must use `stop_owned`.

`CommandService::take_engine_for_stop(&mut self) -> Option<CommandEngine>` is a
single transfer, called only after the actor has irreversibly stopped accepting
IPC, ticks and command submissions. `MdkOwner` exposes that transfer to the
lifecycle module. It is not an engine reopening or a second owner. No token,
master, journal or MDK handle enters another engine thread.

`stop_owned` immediately places the transferred `CommandEngine` and the existing
`ProfileLease` in one `tokio::task::spawn_blocking` keeper. No await separates
resource transfer and keeper scheduling. The keeper calls the existing shutdown
method in bounded one-second observer turns until the OS thread is actually
joined. An incomplete turn retains the same engine instance and lease. A join
panic is a finite failure, never evidence of quiescence; thread termination must
still be established before releasing the lease. Preserve the first failure
rather than turning a later successful join into an all-green cleanup report.

The keeper also waits for a frontend-closed handoff before releasing the lease.
The async side owns MDK/journal and attempts network shutdown within the supplied
observer deadline, then drops `MdkOwner` and signals frontend closure. Use a
small ownership guard whose drop order explicitly drops the owner before
closing the handoff sender. Cancellation of the network-shutdown future must
therefore still close the frontend before the keeper can release its lease.
Channel closure is a frontend lifetime fact, not proof that network shutdown
succeeded. Report `mdk_stop_complete=false` on timeout/error.

Poll the keeper and MDK network shutdown concurrently under the same original
observer deadline; do not spend that whole deadline awaiting MDK before polling
a keeper which may already have joined. Engine stop and MDK shutdown run
concurrently because no further actor operation can be admitted after the ownership transfer. It must hold the
profile lease until **both** OS-thread join and frontend closure. Runtime socket
cleanup occurs after frontend closure and actual engine join, while the keeper
still holds the profile lease; its real result determines
`runtime_cleanup_complete`. A client-only identity follows the same frontend
handoff even though it has no engine thread.

An observer deadline is not a resource lifetime deadline. `stop_owned` and
`PendingStop::observe` await a mutable reference to the same task handle under a
timeout, never aborting or dropping its ownership on timeout. They return that
handle in `pending` with truthful incomplete flags. The blocking task is never
aborted. Do not create another engine or acquire another profile to repair an
incomplete shutdown. The runtime and pending handle must remain supervised until
`finish` returns; a caller cannot begin runtime shutdown first. Tokio may cancel
a queued blocking closure which has not started at runtime shutdown, dropping
its captured engine and lease before a real join. A running blocking closure is
waited for. `#[must_use]` is only a warning: dropping `PendingStop` detaches the
keeper and cannot be counted as clean stop. These are caller ownership rules,
not a claim that Tokio automatically enforces the lifecycle.

The daemon stops accepting IPC, aborts/joins the IPC listener, calls `stop_owned`,
and, if its observer deadline expires, reports a finite degraded shutdown event
and awaits `PendingStop::finish`. It does not return `Ok(())`, drop the lease or
claim runtime cleanup while the engine remains unjoined. A stuck engine can
therefore prevent graceful daemon exit; an external process kill terminates the
process and releases its OS locks, but is not successful application cleanup.
The finite 30-second shutdown observer must not be advertised as a guaranteed
30-second process exit.

The explicit live fixture retains its private allocation and `PendingStop`
together after an incomplete observation, emits a red finite report, and
preserves state. Its external supervisor may enforce its original process
lifetime; such enforcement cannot become green cleanup evidence. Never remove a
fixture allocation while a pending stop still owns its lease or engine.

## Initialization and early errors

`daemon::open` currently starts the engine before `profile.mark_ready`. Reorder
that fallible readiness write before `enable_commands`: it describes the opened
MDK binding and does not require an engine. Verify that successful engine-thread
spawn and storing it into `CommandService` are followed by no fallible operation
before returning the owned identity. A failure before engine spawn can use the
ordinary existing frontend cleanup. If an engine has been spawned, an error
must pass through `stop_owned`; it cannot drop the profile by `?` propagation.

Likewise, all fallible post-open daemon setup (signal registration, socket bind,
listener setup) is inside an outer result scope followed by owned stop. A socket
bind or signal error must not bypass engine join. Do not cancel/abort a daemon
supervisor task after it owns an identity; normal signals use the existing
internal stop path. Initialization spawn-blocking work contains no engine, and
cancellation before engine spawn does not create a hidden engine owner.

Audit every other caller of `daemon::open`. CLI `Init` currently prints status
and implicitly drops `(profile, owner)`; it must perform ordinary owned stop
before returning when an existing command configuration starts an engine. It
must not cancel jobs or consume cleanup. The command-check pair constructor
must also owned-stop its first successfully opened identity if opening its
second identity fails. A pending stop retains the first lease and the private
fixture allocation; no `?` or temporary-directory destructor may delete that
allocation under a live keeper. Return/retain the partial pair or a typed
initialization outcome carrying its `PendingStop` so its caller can supervise it.
Neither caller may silently turn this early failure into successful cleanup.

## Explicit fixture cleanup remains separate

The existing acceptance cleanup contract remains authoritative. For its own
disposable jobs only, the fixture may request explicit local cancellation. It
then waits for active=0, uncertain=0, worker_running=0, worker_unknown=0 and no
registered operation. Ordinary stop never performs this cancellation.

The actor commits the approved final read-only refresh and final sequence fence,
closes admission irreversibly, and requests consuming `into_cleanup` on the sole
engine thread. A consume or final-refresh failure sets cleanup failed, preserves
state, refuses further engine operations, and permits only ordinary stop. Never
reopen the consumed engine or fabricate Exited/Absent facts to pass cleanup.

Successful consume leaves `CleanupGuard` on that same thread and keeps the
profile lease held. While that guard is still live, remove only the fixture's
independently registered engine subtree using the existing acceptance design:
held directory handles, nofollow relative operations, parent/root device+inode
and basename receipts, at most 4096 entries/depth 8, owned 0700 directories and
owned 0600 regular single-link files. Reject links, unexpected entry types,
changed identities, unknown workers and exceeded bounds. Do not use
`TempDir::close` or a recursive path deletion to remove this engine subtree after
ordinary stop has already dropped its guard.

For a separate supervised daemon, require the existing pre/post waitpid and
same-socket same-final-sequence quiescence checks. For the in-process native
fixture, retain the actual `MdkOwner`, engine and profile in scope throughout the
protected removal, require unchanged quiescent state/fence before and after, and
never concurrently run ticks/stop. This is the same owned guard, not a cached
status boolean. Only then call `stop_owned`, await the actual join and frontend
closure, and remove the remaining registered private fixture state. Any failed
proof, unlink, stop or runtime cleanup makes the run red and preserves remaining
state. Report engine-quiescence, engine-stop, MDK-stop, runtime-cleanup and
state-cleanup separately.

The new command-check driver must remain unactivated while its response-consume
or cleanup seams are unwired. Its current fail-closed placeholders and explicit
not-tested fields are not acceptance evidence.

## Exit criteria and offline tests

- An ordinary stop with an admitted running worker joins its engine frontend,
  releases the lease afterwards, and a reopened owner observes the same running
  invocation without redispatch; stop did not send cancel or consume cleanup.
- A gated slow engine/open/operation demonstrates observer expiry returns the
  same pending keeper, a competing profile acquisition still fails, and a later
  real join releases the lease. No actor thread sleeps waiting for the engine.
- Frontend shutdown failure/cancellation closes the frontend before lease
  release, reports MDK failure, and does not hide a pending engine join.
- Socket-bind, signal-setup and readiness-write failures do not drop a live
  engine's lease or leak a second owner; readiness failure precedes engine spawn.
- Quiescent fixture cleanup holds the actual guard across protected unlink;
  failed consume, changed receipts, unsafe entries and incomplete stop preserve
  state and never emit successful cleanup.
- The bounded live command check reports exact stdout/stderr/exit outcomes and
  separately truthful cleanup flags; it does not silently substitute fixture
  cancellation for the product's keep-running-on-disconnect behavior.
